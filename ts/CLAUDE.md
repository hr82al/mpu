# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Главное: качество и читаемость кода

Это основной приоритет проекта, важнее скорости получения результата. Код читают
чаще, чем пишут — оптимизировать нужно под чтение.

### Принципы, которые соблюдаются обязательно

- **KISS** — самое простое решение, которое работает. Умный код, требующий
  объяснений, хуже скучного очевидного кода.
- **YAGNI** — не закладывать абстракции «на будущее». Обобщать по факту третьего
  повторения, а не в ожидании второго. Один вызов — не повод для интерфейса.
- **DRY** — но не в ущерб ясности: два похожих куска с разными причинами
  изменения дублированием не являются, а их преждевременное слияние создаёт
  ложную связанность.
- **Минимум абстракций** — абстракция вводится только когда убирает уже
  существующую боль. Интерфейс с одной реализацией, фабрика ради фабрики, слой
  «на всякий случай» — не архитектура, а лишний уровень чтения. Конкретный тип
  по умолчанию; абстракция — по факту второй реализации или реальной границы
  тестирования.
- **Low coupling** — модуль знает о соседях минимум: узкие интерфейсы вместо
  общих типов, передача данных вместо разделяемого состояния, никаких глобалов,
  синглтонов и модульного мутабельного состояния. Изменение внутри модуля не
  должно требовать правок в вызывающих.
- **High cohesion** — в одном модуле/типе лежит то, что меняется по одной
  причине и вместе. Если файл описывается через «и» («парсинг **и** рендер **и**
  конфиг») — он разъезжается на части.
- **Явность** — никакой магии: явные зависимости, явные параметры, явный порядок
  инициализации. Никаких side-effect-импортов, декораторов с скрытой логикой,
  Proxy-трюков и работы на верхнем уровне модуля (top-level кода с эффектами).
  Поведение читается из кода вызова, а не выводится из соглашений.
- **SOLID** — прикладной минимум для TS: одна причина изменения на модуль/тип;
  расширение через новые реализации и discriminated union с исчерпывающим
  `switch` (проверка `never` в `default`), а не правку разбросанных условий;
  интерфейсы узкие и объявленные **на стороне потребителя** (1–3 метода);
  зависимости передаются явно (параметр/конструктор), а не берутся из глобалов
  или импортированных синглтонов.
- **Composition over inheritance** — композиция функций и объектов вместо
  иерархий; `extends` допустим только для подклассов `Error`. Классы — только
  там, где есть состояние с инвариантами; по умолчанию — данные (типы) и функции
  над ними.
- **Явные ошибки** — никаких проглоченных `catch {}` и плавающих промисов;
  исключение по месту либо обрабатывается, либо пробрасывается с контекстом.
  Подробности — ниже.

### Читаемость: что проверять в каждом изменении

- Имена сообщают о назначении, а не о типе. Короткие для короткой области
  видимости, развёрнутые для экспортированного API.
- Функция делает одну вещь и укладывается на экран; ранние `return` вместо
  вложенных `if`; счастливый путь — по левому краю.
- Комментарии объясняют **почему**, а не **что**. Комментарий, пересказывающий
  код, удаляется. Экспортированные сущности документируются JSDoc-комментарием
  (`/** … */` — его показывают IDE и `deno doc`).
- Никакого «мёртвого» кода, закомментированных блоков, отладочных `console.log`
  и TODO без объяснения.
- Плотность комментариев, стиль именования и идиомы — как в окружающем коде.

### Библиотеки и приёмы

Если задача решается чище и короче с подходящей библиотекой или известным
паттерном — **предлагать это явно**, с обоснованием и альтернативой из
стандартной библиотеки Deno (`jsr:@std/*`). Порядок предпочтения: встроенные API
Deno → `@std/*` → пакет с JSR → `npm:` — последний требует аргумента «что он
устраняет и почему нет на JSR». Решение о добавлении зависимости принимает
пользователь.

### Типы и API

- TypeScript строгий: конфигурация Deno по умолчанию (`strict`) не ослабляется.
  `any` запрещён (lint `no-explicit-any`); неизвестное снаружи — `unknown` +
  сужение проверками. Приведение `as` — крайняя мера с
  комментарием-обоснованием; `!` (non-null assertion) — только когда инвариант
  доказан рядом стоящим кодом.
- Вместо `enum` — union строковых литералов
  (`type Route = "native" | "legacy"`); исчерпывающий `switch` с
  `never`-проверкой.
- **Принимать интерфейсы, возвращать конкретные типы.** Функция объявляет в
  параметре ровно тот минимум поведения/полей, который использует.
- Входные объекты не мутируются; поля данных — `readonly` по умолчанию;
  массивы/объекты, за которые тип отвечает, копируются перед выдачей — иначе
  внутреннее состояние правится извне незаметно.
- Аргументов у функции немного; если их больше трёх-четырёх и часть
  необязательна — объект параметров с говорящими полями, а не позиционный
  список, где на месте вызова видны голые `true, false, undefined`.
- Отменяемые и длительные операции принимают `AbortSignal` в объекте опций
  (`{ signal }`); сигнал не хранится в полях дольше самой операции.

### Ошибки

- Бросаются только объекты `Error` (или подклассы) — никогда строки/объекты.
  Свои классы ошибок — плоские подклассы `Error` с говорящим `name`;
  оборачивание нижележащей ошибки — через `cause`:
  `throw new ConfigError("read config " + path, { cause: err })`.
- Текст ошибки — с маленькой буквы, без точки на конце и без «failed to».
  Цепочка `cause` складывается в читаемую историю, каждый слой добавляет только
  свой контекст.
- Различение ошибок — `instanceof` / поле-дискриминант, никогда по тексту
  `message`.
- `catch` без обработки запрещён; допустимо перебросить с контекстом или явно
  обосновать комментарием, почему ошибка не важна.
- Каждый промис либо `await`'ится, либо явно передаётся дальше; плавающих
  промисов нет. `void somePromise` как способ «забыть» — запрещён.
- Ресурсы закрываются детерминированно: `using` / `try…finally`; ошибка закрытия
  писателя обрабатывается — там теряется запись.

### Логирование и вывод

- CLI-дисциплина потоков: **stdout — данные, stderr — диагностика и ошибки**.
  Смешение ломает пайпы и golden-тесты.
- Логгер/принтер передаётся явно параметром или полем конструктора — глобального
  логгера в библиотечных модулях нет; `console.*` — только в слое склейки CLI.
- Сообщение — короткая постоянная строка, переменные — отдельными полями, а не
  форматная строка со склейкой.
- Секреты, токены, пароли и персональные данные в вывод и логи не попадают ни в
  каком виде.

### Асинхронность и конкурентность

Главный источник неявной сложности, поэтому правила жёсткие:

- У каждой асинхронной операции есть понятный владелец и способ остановки
  (`AbortSignal`); «висящих» промисов, таймеров и незакрытых ресурсов не бывает.
  Санитайзеры `Deno.test` (ops/resources) не отключаются — они и есть детектор
  утечек.
- Параллелизм — `Promise.all`/`allSettled` с осмысленной обработкой отказов, а
  не гонки на разделяемом состоянии. Синхронизация через `setTimeout`-сон
  запрещена и в коде, и в тестах.
- Верхний уровень модуля — только объявления: никаких top-level `await` с
  сетью/диском и работы при импорте. Всё запускается явно из `main`.

### Производительность

Старт процесса — доказанная ценность `mpu` (вызывается десятками раз за сессию),
поэтому: минимум работы до разбора аргументов, тяжёлое — лениво и только на
ветке, которой это нужно. Прочая оптимизация начинается с измерения
(`deno bench` или профиль), сопровождается цифрами «было/стало» и не разменивает
читаемость на догадки. Предварительное выделение ёмкости, когда размер известен,
— обычный стиль, не оптимизация.

### Границы модулей

- Публичная поверхность модуля — его `mod.ts`; внутренности (`internal/…` или
  файлы рядом) мимо `mod.ts` не импортируются.
- Модулей `utils`, `common`, `helpers` не существует — имя модуля называет
  предметную область.
- Циклических импортов нет.
- `main.ts` (точка входа `deno compile`) содержит только разбор аргументов
  верхнего уровня и склейку зависимостей. Логика — в модулях, чтобы
  тестироваться без запуска бинаря.

### Права Deno

Недоверенной стороны в этой системе нет: бинарь исполняется на машине
пользователя и с его же правами. Флаги `--allow-*` — гигиена, а не барьер
безопасности: они ловят случайное обращение к диску, сети или окружению,
которого команда делать не должна, и делают состав доступов читаемым. Границу,
которую действительно нельзя перейти, держат не они: чтение вместо записи в БД
обеспечивает read-only-сессия PostgreSQL, а право агента вызвать мутирующий тул
— правила разрешений его клиента.

Отсюда практика: каждое право в задаче `build` перечислено отдельной строкой с
обоснованием, и новое право добавляется не молча, а как осознанное расширение
(см. `deno.jsonc`). Тесты запускаются с тем же минимумом.

### Секреты

Пароли пользователя не хранятся нигде. Единственный секрет на диске —
статический токен доступа MCP-сервера: отдельный файл в конфиг-каталоге с
правами 0600, создаётся при первой надобности и не является ключом конфига.
Единственная поверхность, печатающая токен, — `mpu mcp token`; ни в каком другом
выводе, логе, ответе сервера или сообщении об ошибке он не появляется — это
инвариант спеки `platform/mcp-server.md`, а не пожелание.

### Проверка каждого изменения

Обязательный прогон перед сообщением о готовности:

```bash
deno fmt --check && deno lint && deno check . && deno test --coverage=cov
```

Пока это не зелёное, работа не считается выполненной — и об этом не сообщается.

Затем — разбор фактического диффа (`git diff -- ts/`, `git diff --stat -- ts/`;
без pathspec дифф зашумлён, см. раздел об изоляции) по списку выше с
**конкретными** предложениями: файл, строка, в чём нарушение, как переписать.
Если нарушений нет — сказать это прямо. Замечания к соседнему коду, не
затронутому задачей, озвучивать отдельно, а не править по ходу.

## Процесс разработки

### TDD

Цикл: **красный → зелёный → рефакторинг**.

1. Тест, описывающий требуемое поведение, пишется первым и **запускается**,
   чтобы увидеть его падение по ожидаемой причине.
2. Минимальная реализация, доводящая тест до зелёного.
3. Рефакторинг под раздел о качестве — при зелёных тестах.

Тесты проверяют поведение и контракт, а не внутреннее устройство. Табличные
тесты (`Deno.test` + `t.step` по случаям или цикл по массиву случаев) — форма по
умолчанию. Багфикс начинается с теста, воспроизводящего баг.

Что считать хорошим тестом:

- Время — `FakeTime` из `@std/testing/time`, никогда реальный `setTimeout`-сон.
- Временные файлы — `Deno.makeTempDir()` с уборкой в `finally`/`using`; никаких
  самодельных путей.
- Сравнение — `assertEquals`/`assertObjectMatch` из `@std/assert` с читаемым
  сообщением: падение теста должно читаться без отладчика.
- Внешние зависимости — за узким интерфейсом на стороне потребителя. Ручного
  фейка достаточно; mock-фреймворки не добавляются. MCP-сервер проверяется
  парами «запрос → ответ» из `fixtures/mcp-server/` поверх обработчика, без
  слушающего сокета и без сети наружу.
- Golden-фикстуры из спек (`docs/specs/fixtures/…`) копируются в `testdata/`
  модуля: тесты самодостаточны, источник истины — спека.
- Санитайзеры `Deno.test` включены: тест, оставляющий висящий таймер или
  незакрытый ресурс, — красный.

### Контроль покрытия

Покрытие измеряется и не должно падать от изменения:

```bash
deno test --coverage=cov
deno coverage cov                 # сводка по файлам/строкам
deno coverage cov --html          # построчно, что не покрыто
```

Покрытие — инструмент поиска непроверенных ветвей, а не самоцель: непокрытыми не
должны оставаться ветви обработки ошибок и граничные случаи. Отчёт по покрытию
затронутых модулей сообщать вместе с результатом.

### Атомарность изменений

- Одно изменение — одна задача. Рефакторинг, багфикс и новая функциональность не
  смешиваются в одном коммите.
- Правки хирургические: минимальный дифф, решающий задачу. Не переформатировать,
  не переименовывать и не «попутно улучшать» несвязанные участки.
- Каждый коммит оставляет дерево в рабочем состоянии: проверка из раздела
  «Проверка каждого изменения» зелёная.
- Вся работа идёт в `main`. Веток не создавать и не предлагать — это осознанное
  решение пользователя, оно перекрывает общее правило «не коммитить в дефолтную
  ветку».
- Сообщения коммитов: Conventional Commits со скоупом (`feat(xlsx): …`,
  `fix(registry): …`), тема — на русском, в императиве.

### Зависимости

Каждая прямая зависимость сопровождается строкой «зачем» — комментарием в
`deno.jsonc` рядом с записью в `imports`. Версии фиксируются; `deno.lock`
коммитится. Порядок предпочтения источников — раздел «Библиотеки и приёмы»;
`npm:`-зависимость без записанного аргумента не появляется.

### Что не делать без спроса

- Не создавать каркас модулей заранее (см. YAGNI) — структура растёт из задач.
- Не добавлять зависимости, не менять версию Deno и настройки строгости в
  `deno.jsonc`.
- Не менять флаги permissions сборки/тестов.
- Не трогать `.claude/` и `docs/` (спеки — read-only, правит
  сессия-спецификатор).
- Не переписывать существующие тесты «под новый стиль» и не рефакторить код,
  которого задача не касается.

### Формат отчёта о выполнении

1. Что изменено — список файлов и в чём смысл каждого изменения.
2. Почему именно так, если решение неочевидно.
3. Вывод `deno fmt --check`/`deno lint`/`deno check`/`deno test` и покрытие
   затронутых модулей.
4. Новые доменные имена, отсутствующие в `docs/glossary.md`, — отдельным списком
   для внесения.
5. Замечания к соседнему коду — отдельным списком, без правок.

## Команды

```bash
deno fmt              # форматирование (deno fmt --check — только проверка)
deno lint             # статический анализ
deno check .          # проверка типов всего дерева
deno test             # все тесты (санитайзеры включены по умолчанию)
deno test path/to/x_test.ts --filter "имя"   # один тест
deno test --coverage=cov && deno coverage cov # покрытие
deno bench            # бенчмарки
deno task <name>      # задачи из deno.jsonc (появятся с первым кодом)

git status --short -- ts/             # состояние; pathspec обязателен
git diff -- ts/                       # дифф перед завершением задачи
git add ts/…                          # только явные пути
git commit -m "…" -- ts/              # коммит с pathspec
```

`deno`, `git` разрешены без запроса подтверждения.

## Состояние проекта

**Модуль Deno/TS в начале переноса.** Источник знания о поведении — `docs/`
(канал спецификаций, см. `docs/CLAUDE.md`). Перенесены команда `xlsx`
(`src/xlsx/`) и локальное хранилище настроек (`src/config/`); `main.ts` —
временный диспетчер одной команды, который заменит реестр по
`docs/specs/platform/registry.md`. Ни реестра, ни MCP-сервера, ни маршрута
`legacy` в коде пока нет.

Переносится **поведение, а не структура**: питоновская декомпозиция,
классы-неймспейсы и идиомы не калькируются — модули и типы проектируются заново
по правилам выше. Паритет подтверждается golden-фикстурами спек, а не построчным
сравнением кода.

### Замысел: один бинарь, две точки входа

Одна программа — самодостаточный бинарь (`deno compile` → `~/.local/bin/mpu`) —
с двумя режимами над **общим реестром команд**:

- **CLI для человека** — `mpu <cmd> [args…]`. Разбирает argv, исполняет команду,
  рендерит результат в текст. Живёт ровно один вызов.
- **MCP-сервер для агента** — `mpu mcp`. Долгоживущий процесс, слушающий
  `127.0.0.1` (Streamable HTTP, роутер Hono); публикует те же команды как тулы и
  исполняет их по запросу агента. Два непересекающихся профиля: `ro` по пути
  `/ro` и `rw` по пути `/rw` — читающие и мутирующие тулы не смешиваются, и на
  `/ro` мутирующий тул не зарегистрирован вовсе, а не запрещён при вызове.

Режимы — не два кода, а две проекции одного объявления команды: путь,
назначение, справка, политика (`ro`/`rw`), схема аргументов, схема результата,
рендер. Из этих семи вещей CLI берёт разбор argv и текст, а MCP-сервер — схемы
тулов и структурный результат. Контракт —
`docs/specs/platform/command-contract.md`; поведение сервера —
`docs/specs/platform/mcp-server.md`.

Команды, ещё не перенесённые, остаются в реестре с маршрутом `legacy` и
исполняются подпроцессом Python-реализации; как тулы они не публикуются. Перевод
команды и откат — правка одной строки реестра
(`docs/specs/platform/registry.md`).

### Справка: руководство к действию

У справочного текста команды два читателя: человек, набравший `--help`, и
ИИ-агент, которому тот же текст приходит описанием тула. Оба читают одно
объявление команды, поэтому текст пишется один раз и обязан работать для обоих:
справка — это CLAUDE.md конкретной команды, прочитал → знаешь, как действовать.
Отсюда два равноправных требования: **экономия токенов** и **полнота,
достаточная для работы без проб и ошибок**. Если после чтения справки остаётся
вопрос, на который отвечает только эксперимент или чтение исходников, — справка
дефектна.

Экономия здесь не стилистическая: описание тула и инструкции профиля клиент
обрезает на 2048 байтах (`platform/mcp-server.md`), и текст, не уместившийся в
предел, теряется молча.

Структура — двухслойная, по уровням дерева команд:

- **Промежуточный уровень** (`mpu --help`, `mpu <cmd> --help` для группы) —
  краткий индекс: одна строка «что это» и список подкоманд, каждая с одной
  строкой назначения. Ничего больше.
- **Листовая команда** — подробности: каждый флаг и аргумент с типом, значением
  по умолчанию и ограничениями, формат ввода/вывода, коды и смысл ошибок,
  один-два примера вызова.

Требования к коду:

- `--help` работает на **каждом** уровне дерева. Это свойство обеспечивается
  конструкцией типа команды, а не дисциплиной: команду нельзя зарегистрировать
  без короткой строки назначения, а листовую — без подробной справки; отсутствие
  текста — ошибка типов или паника инициализации, не пустой вывод.
- Справка живёт рядом с командой, в том же файле, что её реализация; текст
  объявляется данными (поля объекта команды), а не размазывается по коду
  форматированием.
- Индекс родителя собирается автоматически из зарегистрированных подкоманд —
  руками не дублируется и потому не устаревает.
- Тест инварианта дерева: у каждой команды непустая краткая строка, у каждой
  листовой — непустая подробная справка, `--help` на любом уровне завершается
  успешно, не ходит в сеть и не поднимает MCP-сервер.

Конвенции репозитория: комментарии и документация — на русском, идентификаторы и
код — на английском.

## Изоляция окружения

Рабочая область — каталог `ts/`, но **сессия запускается из корня репозитория**
(`mpu/`), и профиль изоляции лежит в `mpu/.claude/settings.json`: рабочему
каталогу нужен доступ к `.git`, иначе git не работает. Сам профиль сессии не
виден. Практические последствия:

- Соседние проекты в `/home/user/mr/mp/`, а внутри `mpu/` — `py/`, `go/`,
  `docs/` и родительские CLAUDE.md закрыты и правилами permissions, и файловой
  системой песочницы. Закрыты по-разному: `py/` и `mpu/docs/` подменены пустым
  каталогом (содержимого не видно вовсе), у `go/` и соседей видны имена файлов,
  но чтение отказывает. Этот файл — единственный источник контекста; знание о
  поведении — только из `docs/specs/`.
- Спеки `ts/docs/` для реализующей сессии read-only; их правит
  сессия-спецификатор. Общего канала протокола с `go/` больше нет: брокера нет,
  `docs/specs/protocol/` не существует, платформенные контракты живут в
  `ts/docs/specs/platform/`.
- Запись сохраняется только внутри `ts/` и в `.git` репозитория. Запись мимо них
  не достигает диска, **но может вернуть успех** — на код возврата как на
  проверку изоляции полагаться нельзя, проверять надо обратным чтением.
- Сеть списком хостов не ограничена. Это свойство окружения, а не разрешение
  ходить куда угодно: сам код и тесты ходят только на источники зависимостей
  (`deno.land`, `jsr.io`, `registry.npmjs.org`), MCP-сервер слушает только
  `127.0.0.1`.
- Через `env` профиля кэш Deno перенаправлен в `ts/.deno`, а `TMPDIR` — в
  `ts/.tmp` (оба в `.gitignore`). Временные файлы — в `$TMPDIR`, не в `/tmp`.

### Git: обязательно работать через pathspec

Из-за блокировки `py/`, `go/` и `docs/` git видит сотни файлов **удалёнными и
изменёнными**, хотя на диске они целы. К этому добавляется untracked-шум:
заглушки, которыми песочница подменяет dotfiles в корне репозитория (`.bashrc`,
`.gitconfig`, `.mcp.json`, `.idea/`, `.vscode/`, старый
`ts/.claude/settings.json`). Поэтому:

- Смотреть состояние только с ограничением области: `git status --short -- ts/`,
  `git diff -- ts/`. Без pathspec вывод нечитаем и опасен.
- Индексировать только явными путями: `git add ts/…`; коммитить с pathspec:
  `git commit -m "…" -- ts/`.
- `git add -A|--all|-u`, `git commit -a|-am`, `git stash` **запрещены** — они
  закоммитят удаление соседних каталогов. Это не рекомендация: их блокирует
  `PreToolUse`-хук профиля (`mpu/.claude/settings.json`), отвечающий отказом с
  напоминанием про pathspec.
- Пути в командах разрешаются от каталога запуска, а он — корень репозитория:
  `ts/…`, а не `./…`.

Remote `origin` у репозитория есть, но отправка в него — дело внешнего
терминала, не сессии.

`ts/.claude/lock.sh on|off|status` — тумблер права сессии писать в профиль
изоляции. Запускается **только из внешнего терминала**: в положении `on` запись
из сессии запрещена правилом permissions. Скрипт достался от прежней раскладки и
всё ещё правит исчезнувший `ts/.claude/settings.json` — до его починки тумблер
не работает.
