# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Главное: качество и читаемость кода

Это основной приоритет проекта, важнее скорости получения результата. Код читают
чаще, чем пишут — оптимизировать нужно под чтение.

### Принципы, которые соблюдаются обязательно

- **KISS** — самое простое решение, которое работает. Умный код, требующий
  объяснений, хуже скучного очевидного кода.
- **YAGNI** — не закладывать абстракции «на будущее». Обобщать по факту третьего
  повторения, а не в ожидании второго. Один вызов — не повод для интерфейса.
- **DRY** — но не в ущерб ясности: два похожих куска с разными причинами
  изменения дублированием не являются, а их преждевременное слияние создаёт
  ложную связанность.
- **Минимум абстракций** — абстракция вводится только когда убирает уже
  существующую боль. Интерфейс с одной реализацией, фабрика ради фабрики,
  слой «на всякий случай» — не архитектура, а лишний уровень чтения.
  Конкретный тип по умолчанию; абстракция — по факту второй реализации или
  реальной границы тестирования.
- **Low coupling** — модуль знает о соседях минимум: узкие интерфейсы вместо
  общих типов, передача данных вместо разделяемого состояния, никаких
  глобалов, синглтонов и модульного мутабельного состояния. Изменение внутри
  модуля не должно требовать правок в вызывающих.
- **High cohesion** — в одном модуле/типе лежит то, что меняется по одной
  причине и вместе. Если файл описывается через «и» («парсинг **и** рендер
  **и** конфиг») — он разъезжается на части.
- **Явность** — никакой магии: явные зависимости, явные параметры, явный
  порядок инициализации. Никаких side-effect-импортов, декораторов с скрытой
  логикой, Proxy-трюков и работы на верхнем уровне модуля (top-level кода с
  эффектами). Поведение читается из кода вызова, а не выводится из соглашений.
- **SOLID** — прикладной минимум для TS: одна причина изменения на модуль/тип;
  расширение через новые реализации и discriminated union с исчерпывающим
  `switch` (проверка `never` в `default`), а не правку разбросанных условий;
  интерфейсы узкие и объявленные **на стороне потребителя** (1–3 метода);
  зависимости передаются явно (параметр/конструктор), а не берутся из
  глобалов или импортированных синглтонов.
- **Composition over inheritance** — композиция функций и объектов вместо
  иерархий; `extends` допустим только для подклассов `Error`. Классы — только
  там, где есть состояние с инвариантами; по умолчанию — данные (типы) и
  функции над ними.
- **Явные ошибки** — никаких проглоченных `catch {}` и плавающих промисов;
  исключение по месту либо обрабатывается, либо пробрасывается с контекстом.
  Подробности — ниже.

### Читаемость: что проверять в каждом изменении

- Имена сообщают о назначении, а не о типе. Короткие для короткой области
  видимости, развёрнутые для экспортированного API.
- Функция делает одну вещь и укладывается на экран; ранние `return` вместо
  вложенных `if`; счастливый путь — по левому краю.
- Комментарии объясняют **почему**, а не **что**. Комментарий, пересказывающий
  код, удаляется. Экспортированные сущности документируются JSDoc-комментарием
  (`/** … */` — его показывают IDE и `deno doc`).
- Никакого «мёртвого» кода, закомментированных блоков, отладочных
  `console.log` и TODO без объяснения.
- Плотность комментариев, стиль именования и идиомы — как в окружающем коде.

### Библиотеки и приёмы

Если задача решается чище и короче с подходящей библиотекой или известным
паттерном — **предлагать это явно**, с обоснованием и альтернативой из
стандартной библиотеки Deno (`jsr:@std/*`). Порядок предпочтения: встроенные
API Deno → `@std/*` → пакет с JSR → `npm:` — последний требует аргумента «что
он устраняет и почему нет на JSR». Решение о добавлении зависимости принимает
пользователь.

### Типы и API

- TypeScript строгий: конфигурация Deno по умолчанию (`strict`) не
  ослабляется. `any` запрещён (lint `no-explicit-any`); неизвестное снаружи —
  `unknown` + сужение проверками. Приведение `as` — крайняя мера с
  комментарием-обоснованием; `!` (non-null assertion) — только когда
  инвариант доказан рядом стоящим кодом.
- Вместо `enum` — union строковых литералов (`type Route = "local" |
  "broker" | "legacy"`); исчерпывающий `switch` с `never`-проверкой.
- **Принимать интерфейсы, возвращать конкретные типы.** Функция объявляет в
  параметре ровно тот минимум поведения/полей, который использует.
- Входные объекты не мутируются; поля данных — `readonly` по умолчанию;
  массивы/объекты, за которые тип отвечает, копируются перед выдачей —
  иначе внутреннее состояние правится извне незаметно.
- Аргументов у функции немного; если их больше трёх-четырёх и часть
  необязательна — объект параметров с говорящими полями, а не позиционный
  список, где на месте вызова видны голые `true, false, undefined`.
- Отменяемые и длительные операции принимают `AbortSignal` в объекте опций
  (`{ signal }`); сигнал не хранится в полях дольше самой операции.

### Ошибки

- Бросаются только объекты `Error` (или подклассы) — никогда строки/объекты.
  Свои классы ошибок — плоские подклассы `Error` с говорящим `name`;
  оборачивание нижележащей ошибки — через `cause`:
  `throw new ConfigError("read config " + path, { cause: err })`.
- Текст ошибки — с маленькой буквы, без точки на конце и без «failed to».
  Цепочка `cause` складывается в читаемую историю, каждый слой добавляет
  только свой контекст.
- Различение ошибок — `instanceof` / поле-дискриминант, никогда по тексту
  `message`.
- `catch` без обработки запрещён; допустимо перебросить с контекстом или
  явно обосновать комментарием, почему ошибка не важна.
- Каждый промис либо `await`'ится, либо явно передаётся дальше; плавающих
  промисов нет. `void somePromise` как способ «забыть» — запрещён.
- Ресурсы закрываются детерминированно: `using` / `try…finally`; ошибка
  закрытия писателя обрабатывается — там теряется запись.

### Логирование и вывод

- CLI-дисциплина потоков: **stdout — данные, stderr — диагностика и
  ошибки**. Смешение ломает пайпы и golden-тесты.
- Логгер/принтер передаётся явно параметром или полем конструктора —
  глобального логгера в библиотечных модулях нет; `console.*` — только в
  слое склейки CLI.
- Сообщение — короткая постоянная строка, переменные — отдельными полями,
  а не форматная строка со склейкой.
- Секреты, токены, пароли и персональные данные в вывод и логи не попадают
  ни в каком виде.

### Асинхронность и конкурентность

Главный источник неявной сложности, поэтому правила жёсткие:

- У каждой асинхронной операции есть понятный владелец и способ остановки
  (`AbortSignal`); «висящих» промисов, таймеров и незакрытых ресурсов не
  бывает. Санитайзеры `Deno.test` (ops/resources) не отключаются — они и
  есть детектор утечек.
- Параллелизм — `Promise.all`/`allSettled` с осмысленной обработкой отказов,
  а не гонки на разделяемом состоянии. Синхронизация через `setTimeout`-сон
  запрещена и в коде, и в тестах.
- Верхний уровень модуля — только объявления: никаких top-level `await` с
  сетью/диском и работы при импорте. Всё запускается явно из `main`.

### Производительность

Старт процесса — доказанная ценность `mpu` (вызывается десятками раз за
сессию), поэтому: минимум работы до разбора аргументов, тяжёлое — лениво и
только на ветке, которой это нужно. Прочая оптимизация начинается с
измерения (`deno bench` или профиль), сопровождается цифрами «было/стало»
и не разменивает читаемость на догадки. Предварительное выделение ёмкости,
когда размер известен, — обычный стиль, не оптимизация.

### Границы модулей

- Публичная поверхность модуля — его `mod.ts`; внутренности (`internal/…`
  или файлы рядом) мимо `mod.ts` не импортируются.
- Модулей `utils`, `common`, `helpers` не существует — имя модуля называет
  предметную область.
- Циклических импортов нет.
- `main.ts` (точка входа `deno compile`) содержит только разбор аргументов
  верхнего уровня и склейку зависимостей. Логика — в модулях, чтобы
  тестироваться без запуска бинаря.

### Песочница и permissions

CLI — недоверенная сторона и живёт с минимальными правами: флаги
`--allow-*` зашиваются при `deno compile` и перечисляют ровно то, что
нужно (сеть — только хост брокера; диск — только конфиг-каталог и явно
переданные пользователем файлы). Код пишется в предположении этих прав;
новая привилегия — расширение поверхности атаки и отдельное решение
пользователя, не тихая правка флагов. Тесты запускаются с теми же
минимальными правами.

### Секреты

Пароль пользователя не хранится нигде; на диске живёт только временный
токен (файл с правами 0600). Ни секрет, ни токен не логируются и не
попадают в сообщения об ошибках. Операции брокера — только из словаря
`docs/specs/protocol/`; новые операции в CLI-коде не изобретаются.

### Проверка каждого изменения

Обязательный прогон перед сообщением о готовности:

```bash
deno fmt --check && deno lint && deno check . && deno test --coverage=cov
```

Пока это не зелёное, работа не считается выполненной — и об этом не
сообщается.

Затем — разбор фактического диффа (`git diff -- ts/`,
`git diff --stat -- ts/`; без pathspec дифф зашумлён, см. раздел об
изоляции) по списку выше с **конкретными** предложениями: файл, строка,
в чём нарушение, как переписать. Если нарушений нет — сказать это прямо.
Замечания к соседнему коду, не затронутому задачей, озвучивать отдельно,
а не править по ходу.

## Процесс разработки

### TDD

Цикл: **красный → зелёный → рефакторинг**.

1. Тест, описывающий требуемое поведение, пишется первым и **запускается**,
   чтобы увидеть его падение по ожидаемой причине.
2. Минимальная реализация, доводящая тест до зелёного.
3. Рефакторинг под раздел о качестве — при зелёных тестах.

Тесты проверяют поведение и контракт, а не внутреннее устройство.
Табличные тесты (`Deno.test` + `t.step` по случаям или цикл по массиву
случаев) — форма по умолчанию. Багфикс начинается с теста,
воспроизводящего баг.

Что считать хорошим тестом:

- Время — `FakeTime` из `@std/testing/time`, никогда реальный
  `setTimeout`-сон.
- Временные файлы — `Deno.makeTempDir()` с уборкой в `finally`/`using`;
  никаких самодельных путей.
- Сравнение — `assertEquals`/`assertObjectMatch` из `@std/assert` с
  читаемым сообщением: падение теста должно читаться без отладчика.
- Внешние зависимости — за узким интерфейсом на стороне потребителя.
  Ручного фейка достаточно; mock-фреймворки не добавляются. Брокер в
  тестах — фейк, отвечающий парами из фикстур протокола; реальные
  учётные данные для тестов не нужны.
- Golden-фикстуры из спек (`docs/specs/fixtures/…`) копируются в
  `testdata/` модуля: тесты самодостаточны, источник истины — спека.
- Санитайзеры `Deno.test` включены: тест, оставляющий висящий таймер или
  незакрытый ресурс, — красный.

### Контроль покрытия

Покрытие измеряется и не должно падать от изменения:

```bash
deno test --coverage=cov
deno coverage cov                 # сводка по файлам/строкам
deno coverage cov --html          # построчно, что не покрыто
```

Покрытие — инструмент поиска непроверенных ветвей, а не самоцель:
непокрытыми не должны оставаться ветви обработки ошибок и граничные
случаи. Отчёт по покрытию затронутых модулей сообщать вместе с
результатом.

### Атомарность изменений

- Одно изменение — одна задача. Рефакторинг, багфикс и новая
  функциональность не смешиваются в одном коммите.
- Правки хирургические: минимальный дифф, решающий задачу. Не
  переформатировать, не переименовывать и не «попутно улучшать»
  несвязанные участки.
- Каждый коммит оставляет дерево в рабочем состоянии: проверка из раздела
  «Проверка каждого изменения» зелёная.
- Вся работа идёт в `main`. Веток не создавать и не предлагать — это
  осознанное решение пользователя, оно перекрывает общее правило «не
  коммитить в дефолтную ветку».
- Сообщения коммитов: Conventional Commits со скоупом (`feat(xlsx): …`,
  `fix(registry): …`), тема — на русском, в императиве.

### Зависимости

Каждая прямая зависимость сопровождается строкой «зачем» — комментарием в
`deno.jsonc` рядом с записью в `imports`. Версии фиксируются; `deno.lock`
коммитится. Порядок предпочтения источников — раздел «Библиотеки и
приёмы»; `npm:`-зависимость без записанного аргумента не появляется.

### Что не делать без спроса

- Не создавать каркас модулей заранее (см. YAGNI) — структура растёт из
  задач.
- Не добавлять зависимости, не менять версию Deno и настройки строгости в
  `deno.jsonc`.
- Не менять флаги permissions сборки/тестов.
- Не трогать `.claude/` и `docs/` (спеки — read-only, правит
  сессия-спецификатор).
- Не переписывать существующие тесты «под новый стиль» и не рефакторить
  код, которого задача не касается.

### Формат отчёта о выполнении

1. Что изменено — список файлов и в чём смысл каждого изменения.
2. Почему именно так, если решение неочевидно.
3. Вывод `deno fmt --check`/`deno lint`/`deno check`/`deno test` и
   покрытие затронутых модулей.
4. Новые доменные имена, отсутствующие в `docs/glossary.md`, — отдельным
   списком для внесения.
5. Замечания к соседнему коду — отдельным списком, без правок.

## Команды

```bash
deno fmt              # форматирование (deno fmt --check — только проверка)
deno lint             # статический анализ
deno check .          # проверка типов всего дерева
deno test             # все тесты (санитайзеры включены по умолчанию)
deno test path/to/x_test.ts --filter "имя"   # один тест
deno test --coverage=cov && deno coverage cov # покрытие
deno bench            # бенчмарки
deno task <name>      # задачи из deno.jsonc (появятся с первым кодом)

git status --short -- ts/             # состояние; pathspec обязателен
git diff -- ts/                       # дифф перед завершением задачи
git add ts/…                          # только явные пути
git commit -m "…" -- ts/              # коммит с pathspec
```

`deno`, `git` разрешены без запроса подтверждения.

## Состояние проекта

**Greenfield-модуль Deno/TS**: кода ещё нет — только `docs/` (канал
спецификаций, см. `docs/CLAUDE.md`). Каталог — цель переноса
CLI-поверхности Python-реализации: парсинг аргументов, справка, рендер,
реестр команд с маршрутизацией. Версия Deno и `deno.jsonc` фиксируются
первой задачей реализации.

Переносится **поведение, а не структура**: питоновская декомпозиция,
классы-неймспейсы и идиомы не калькируются — модули и типы проектируются
заново по правилам выше. Паритет подтверждается golden-фикстурами спек,
а не построчным сравнением кода.

### Замысел: CLI и брокер

Система из двух программ, разделённых границей доверия; в этом модуле
живёт только CLI.

- **CLI (`mpu`)** — этот модуль, недоверенная сторона. Один
  самодостаточный бинарь (`deno compile` → `~/.local/bin/mpu`).
  Парсит аргументы, рендерит вывод, решает маршрут команды по реестру;
  данные не добывает, а **запрашивает** у брокера.
- **Брокер** — удалённый Go-сервис, доверенная сторона: секреты, доступ
  к внешним системам, enforcement подтверждений, журнал вызовов.
  Единственный канал общения — HTTPS + JSON-RPC 2.0 с Bearer JWT;
  контракт — спеки `docs/specs/protocol/` (read-only). Локальные
  команды (например `xlsx`) работают без брокера вовсе.

### Справка `--help`: руководство к действию для ИИ

Основной читатель справки `mpu` — не человек, а ИИ-агент в песочнице.
Справка — это CLAUDE.md конкретной команды: прочитал → знаешь, как
действовать. Отсюда два равноправных требования: **экономия токенов** и
**полнота, достаточная для работы без проб и ошибок**. Если после чтения
справки у агента остаётся вопрос, на который отвечает только эксперимент
или чтение исходников, — справка дефектна.

Структура — двухслойная, по уровням дерева команд:

- **Промежуточный уровень** (`mpu --help`, `mpu <cmd> --help` для группы) —
  краткий индекс: одна строка «что это» и список подкоманд, каждая с
  одной строкой назначения. Ничего больше.
- **Листовая команда** — подробности: каждый флаг и аргумент с типом,
  значением по умолчанию и ограничениями, формат ввода/вывода, коды и
  смысл ошибок, один-два примера вызова.

Требования к коду:

- `--help` работает на **каждом** уровне дерева. Это свойство
  обеспечивается конструкцией типа команды, а не дисциплиной: команду
  нельзя зарегистрировать без короткой строки назначения, а листовую —
  без подробной справки; отсутствие текста — ошибка типов или паника
  инициализации, не пустой вывод.
- Справка живёт рядом с командой, в том же файле, что её реализация;
  текст объявляется данными (поля объекта команды), а не размазывается по
  коду форматированием.
- Индекс родителя собирается автоматически из зарегистрированных
  подкоманд — руками не дублируется и потому не устаревает.
- Тест инварианта дерева: у каждой команды непустая краткая строка, у
  каждой листовой — непустая подробная справка, `--help` на любом уровне
  завершается успешно и не ходит в брокер.

Конвенции репозитория: комментарии и документация — на русском,
идентификаторы и код — на английском.

## Изоляция окружения

Рабочая область — каталог `ts/`. Целевая схема — зеркало изоляции
Go-модуля (механика `.claude/` настраивается при первом коде, частично из
внешнего терминала):

- Соседние каталоги `mpu/` (`py/`, `go/` — кроме read-only канала
  `go/docs/specs/protocol/`, смонтированного как `docs/specs/protocol/`),
  `mpu/docs/` и родительские CLAUDE.md закрыты. Этот файл — единственный
  источник контекста; знание о поведении — только из `docs/specs/`.
- Спеки `docs/` для реализующей сессии read-only; их правит
  сессия-спецификатор.
- Сеть открыта только на источники зависимостей (JSR/deno.land); прочие
  хосты — нет.
- Временные файлы — в `$TMPDIR`, не в `/tmp`.

### Git: обязательно работать через pathspec

Как и в Go-модуле, блокировка соседних каталогов делает массовые
git-команды опасными: смотреть состояние только `git status --short --
ts/`, индексировать только явными путями `git add ts/…`, коммитить с
pathspec. `git add -A|-u`, `git commit -a`, `git stash` — запрещены.
`git push` не настроен — отправка в remote из внешнего терминала.
