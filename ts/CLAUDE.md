# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Главное: качество и читаемость кода

Это основной приоритет проекта, важнее скорости получения результата. Код читают
чаще, чем пишут — оптимизировать нужно под чтение.

### Порядок работы

- Сначала типы и структуры данных, код — вокруг них. Не превращать это в
  обобщённый реестр или таблицу правил: реестр стирает типы и тянет за собой
  фабрику и комментарий-оправдание.
- Перед тем как писать, назвать одной строкой, какое изменение придёт сюда
  следующим, и сделать дешёвым именно его — не реализуя его сейчас.
- Если изменение упирается в структуру: сначала переукладка отдельным коммитом
  (только rename/move/extract/inline, поведение и тесты не меняются), затем сама
  правка. Остановиться, как только изменение стало лёгким.

### Структура кода

- Функция ≤ 40 строк, вложенность ≤ 3 уровней. Не влезает — разделить на
  именованные части. Число параметров не лимитировать: лимит рождает
  объект-мешок состояния. Много необязательных — объект параметров с говорящими
  полями, а не позиционный список с голыми `true, false, undefined`.
- Плоско: ранний `return`/`continue` вместо вложенных `if`; счастливый путь по
  левому краю.
- Функция принимает данные, которые ей нужны, а не объект-источник (клиент БД,
  конфиг, HTTP-клиент, логгер), из которого она их достаёт. Нужен мок в тесте —
  в коде лишняя зависимость. Публичный API при этом не расширяется ради тестов:
  тестируется то, что и так экспортировано.
- Абстракция вводится, когда убирает уже существующую боль. Интерфейс с одной
  реализацией, фабрика ради фабрики, слой «на всякий случай» — лишний уровень
  чтения, а не архитектура.
- Модуль, который описывается через «и» («парсинг **и** рендер **и** конфиг»),
  разъезжается на части. Одно изменение требования — одна правка в одном месте;
  если правка тянет за собой три и более места, остановиться и сказать об этом,
  а не дотаскивать руками.
- Никакой магии: явные зависимости, явные параметры, явный порядок
  инициализации. Никаких side-effect-импортов, декораторов со скрытой логикой,
  Proxy-трюков, глобалов, синглтонов и работы на верхнем уровне модуля.
- Расширение — новой реализацией и discriminated union с исчерпывающим `switch`
  (проверка `never` в `default`), а не правкой разбросанных условий.
- Композиция вместо наследования; `extends` допустим только для подклассов
  `Error`. Классы — только там, где есть состояние с инвариантами; по умолчанию
  — данные (типы) и функции над ними.

### Имена и комментарии

- Имя говорит, что лежит внутри или что функция делает в домене задачи, а не о
  типе и не о роли в алгоритме. Короткое имя в короткой области видимости —
  норма, разворачивать не нужно.
- Комментарий объясняет **почему**; пересказывает код — переписать строку, а не
  комментарий. Экспортированные сущности документируются JSDoc (`/** … */` — его
  показывают IDE и `deno doc`).
- Никакого «мёртвого» кода, закомментированных блоков, отладочных `console.log`
  и TODO без объяснения.
- Плотность комментариев, стиль именования и идиомы — как в окружающем коде.

### Образец стиля

Новый код пишется как `src/sql/target.ts`: JSDoc на каждом экспорте, `readonly`
на полях данных, ранние выходы, узкий интерфейс потребителя (`EnvKeys` —
`Pick<EnvFile, …>` вместо всего типа), discriminated union вместо флагов, ошибка
с `cause`. Теми же свойствами обладают `src/sql/render.ts` и
`src/logs/query.ts`. Образец устарел — заменить ссылку, а не оставлять её.

### Библиотеки и приёмы

Если задача решается чище и короче с подходящей библиотекой или известным
паттерном — **предлагать это явно**, с обоснованием и альтернативой из
стандартной библиотеки Deno (`jsr:@std/*`). Порядок предпочтения: встроенные API
Deno → `@std/*` → пакет с JSR → `npm:` — последний требует аргумента «что он
устраняет и почему нет на JSR». Решение о добавлении зависимости принимает
пользователь.

### Типы и API

- TypeScript строгий: конфигурация Deno по умолчанию (`strict`) не ослабляется.
  `any` запрещён (lint `no-explicit-any`); неизвестное снаружи — `unknown` +
  сужение проверками. Приведение `as` — крайняя мера с
  комментарием-обоснованием; `!` (non-null assertion) — только когда инвариант
  доказан рядом стоящим кодом.
- Вместо `enum` — union строковых литералов
  (`type Route = "native" | "legacy"`); исчерпывающий `switch` с
  `never`-проверкой.
- **Принимать интерфейсы, возвращать конкретные типы.** Функция объявляет в
  параметре ровно тот минимум поведения/полей, который использует.
- Входные объекты не мутируются; поля данных — `readonly` по умолчанию;
  массивы/объекты, за которые тип отвечает, копируются перед выдачей — иначе
  внутреннее состояние правится извне незаметно.
- Аргументов у функции немного; если их больше трёх-четырёх и часть
  необязательна — объект параметров с говорящими полями, а не позиционный
  список, где на месте вызова видны голые `true, false, undefined`.
- Отменяемые и длительные операции принимают `AbortSignal` в объекте опций
  (`{ signal }`); сигнал не хранится в полях дольше самой операции.

### Ошибки

- Бросаются только объекты `Error` (или подклассы) — никогда строки/объекты.
  Свои классы ошибок — плоские подклассы `Error` с говорящим `name`;
  оборачивание нижележащей ошибки — через `cause`:
  `throw new ConfigError("read config " + path, { cause: err })`.
- Текст ошибки — с маленькой буквы, без точки на конце и без «failed to».
  Цепочка `cause` складывается в читаемую историю, каждый слой добавляет только
  свой контекст.
- Различение ошибок — `instanceof` / поле-дискриминант, никогда по тексту
  `message`.
- `catch` без обработки запрещён; допустимо перебросить с контекстом или явно
  обосновать комментарием, почему ошибка не важна.
- Каждый промис либо `await`'ится, либо явно передаётся дальше; плавающих
  промисов нет. `void somePromise` как способ «забыть» — запрещён.
- Ресурсы закрываются детерминированно: `using` / `try…finally`; ошибка закрытия
  писателя обрабатывается — там теряется запись.

### Логирование и вывод

- CLI-дисциплина потоков: **stdout — данные, stderr — диагностика и ошибки**.
  Смешение ломает пайпы и golden-тесты.
- Логгер/принтер передаётся явно параметром или полем конструктора — глобального
  логгера в библиотечных модулях нет; `console.*` — только в слое склейки CLI.
- Сообщение — короткая постоянная строка, переменные — отдельными полями, а не
  форматная строка со склейкой.
- Секреты, токены, пароли и персональные данные в вывод и логи не попадают ни в
  каком виде.

### Асинхронность и конкурентность

Главный источник неявной сложности, поэтому правила жёсткие:

- У каждой асинхронной операции есть понятный владелец и способ остановки
  (`AbortSignal`); «висящих» промисов, таймеров и незакрытых ресурсов не бывает.
  Санитайзеры `Deno.test` (ops/resources) не отключаются — они и есть детектор
  утечек.
- Параллелизм — `Promise.all`/`allSettled` с осмысленной обработкой отказов, а
  не гонки на разделяемом состоянии. Синхронизация через `setTimeout`-сон
  запрещена и в коде, и в тестах.
- Верхний уровень модуля — только объявления: никаких top-level `await` с
  сетью/диском и работы при импорте. Всё запускается явно из `main`.

### Производительность

Старт процесса — доказанная ценность `mpu` (вызывается десятками раз за сессию),
поэтому: минимум работы до разбора аргументов, тяжёлое — лениво и только на
ветке, которой это нужно. Прочая оптимизация начинается с измерения
(`deno bench` или профиль), сопровождается цифрами «было/стало» и не разменивает
читаемость на догадки. Предварительное выделение ёмкости, когда размер известен,
— обычный стиль, не оптимизация.

### Границы модулей

- Публичная поверхность модуля — его `mod.ts`; внутренности (`internal/…` или
  файлы рядом) мимо `mod.ts` не импортируются.
- Модулей `utils`, `common`, `helpers` не существует — имя модуля называет
  предметную область.
- Циклических импортов нет.
- `main.ts` (точка входа `deno compile`) содержит только разбор аргументов
  верхнего уровня и склейку зависимостей. Логика — в модулях, чтобы
  тестироваться без запуска бинаря.

### Права Deno

Недоверенной стороны в этой системе нет: бинарь исполняется на машине
пользователя и с его же правами. Флаги `--allow-*` — гигиена, а не барьер
безопасности: они ловят случайное обращение к диску, сети или окружению,
которого команда делать не должна, и делают состав доступов читаемым. Границу,
которую действительно нельзя перейти, держат не они, и не одна лишь сессионная
настройка PostgreSQL: `default_transaction_read_only` снимается из самого SQL
(`SET transaction_read_only=off;` перед мутацией — проверено), поэтому чтение
вместо записи держится тем, что драйвер шлёт запрос расширенным протоколом и
сервер бракует многооператорный текст. Меняешь транспорт `sql-ro` — гарантия
исчезает вместе с ним. Право агента вызвать мутирующий тул — правила разрешений
его клиента.

Отсюда практика: каждое право в задаче `build` перечислено отдельной строкой с
обоснованием, и новое право добавляется не молча, а как осознанное расширение
(см. `deno.jsonc`). Тесты запускаются с тем же минимумом.

### Секреты

Пароли пользователя не хранятся нигде. Единственный секрет на диске —
статический токен доступа MCP-сервера: отдельный файл в конфиг-каталоге с
правами 0600, создаётся при первой надобности и не является ключом конфига.
Единственная поверхность, печатающая токен, — `mpu mcp token`; ни в каком другом
выводе, логе, ответе сервера или сообщении об ошибке он не появляется — это
инвариант спеки `platform/mcp-server.md`, а не пожелание.

### Проверка каждого изменения

Проверка состоит из двух шагов, и **оба обязательны перед каждым коммитом без
исключений** — включая однострочные правки, починку тестов и правки
документации. Порядок фиксирован:

**гейты зелёные → разбор диффа → исправление найденного → гейты зелёные повторно
→ только теперь коммит.** Разбор после коммита не считается.

**Шаг 1 — гейты.**

```bash
deno fmt --check && deno lint && deno check . && deno task test --coverage=cov
deno coverage cov                 # по затронутым модулям
deno task smoke                   # собранный бинарь: права из задачи build
```

Пока это не зелёное, работа не считается выполненной — и об этом не сообщается.

`deno task smoke` обязателен наравне с остальными: `deno test` идёт с широким
набором прав и потому не видит нехватки `--allow-*` в задаче `build` — при
зелёных тестах бинарь может падать на каждой команде. Задача собирает бинарь во
временный каталог **внутри `.tmp` репозитория**, он же служит ему HOME (`$HOME`
в правах подставляется этим каталогом). Место не случайно: под `/tmp`
утверждения о правах слепнут — `/tmp` перечислен в том же `--allow-write`, и
проверка «право на `$HOME/.config/mpu` есть» зеленела бы со снятым правом,
проверяя соседнее. Там, где увести каталог из-под `/tmp` не удалось, такие
проверки честно пропускаются. Прогоняются по бинарю: `version`, режим дополнения
для bash и zsh, установку скрипта в rc-файлы, env-слой `MPU_XLSX`, подпроцесс
маршрута `legacy`, старт MCP-сервера с записью файла токена и две проверки права
на каталог временных файлов: путь дампа под `/tmp` и отказ для каталога вне
разрешённых. Активная установка (`~/.local/bin/mpu`) и настоящие rc-файлы при
этом не трогаются. Каждое право задачи `build` покрыто хотя бы одной из
проверок: убрать право — smoke краснеет.

Второе исключение — **условное** и потому названо отдельно: проверка пути
временного дампа требует, чтобы `/tmp` был доступен на запись. В окружении, где
он смонтирован только для чтения (изолированная сессия), проверка честно
**пропускается**: печатает `skip` и считается в итоговой строке, а не выглядит
зелёной. Замер 2026-08-28 на машине оператора: снятие права `/tmp,/var/tmp` из
задачи `build` роняет smoke на этой проверке — значит покрытие настоящее там,
где каталог писать можно.

Первое исключение названо здесь же, чтобы не расходиться с правилом молча:
чтение `TMUX` (`--allow-env=…,TMUX`, `platform/clipboard.md`) smoke не
проверяет. Его отсутствие даёт ровно тот же наблюдаемый исход, что и запуск не
под мультиплексором, — последовательность без passthrough-обёртки; отличить одно
от другого можно только под псевдотерминалом, а он в smoke писал бы в буфер
обмена запускающего. Права `--allow-write=…,/dev/tty` в списке больше нет вовсе:
писать в `/dev/tty` нельзя ни при каком наборе путей, только под `--allow-all`
(замер 2026-08-31), и попытка копирования, ради которой право стояло, переведена
на stderr. Расширять список исключений без такой же записи нельзя.

Второе исключение того же рода — запрет `--deny-env=USER,NODE_PG_FORCE_NATIVE`
(`deno.jsonc`): оба имени читает дерево `npm:pg` в `try/catch`, поэтому без
терминала доступ отказан и так, а с флагом и без него бинарь ведёт себя
одинаково. Флаг снимает не отказ, а вопрос Deno на терминале — отличить одно от
другого можно только под псевдотерминалом. Проверяется вместо smoke прямым
замером состояния права: `querySync` по `{ name: "env", variable: "USER" }` даёт
`prompt` без флага и `denied` с ним.

**Шаг 2 — разбор итогового диффа.** `git diff -- ts/` и `git diff --stat -- ts/`
(без pathspec дифф зашумлён, см. раздел об изоляции).

Разбор делает **свежий контекст**: субагент, получающий только дифф и текст
задачи, без истории написания. Замер на этом наборе правил: разбор своего кода
дал четыре находки, реальных из них ноль — все описывали дефекты, уже
исправленные по дороге; свежий контекст дал одну находку, и она была реальной.

В разбор идёт **только то, что есть в итоговом диффе**. Дефект, найденный и
исправленный по ходу написания, находкой не считается и в отчёт не пишется:
иначе отчёт выглядит проверенным, не будучи им.

Глубина по риску: дифф меняет поведение, контракт или обработку данных — полный
разбор. Переименование, конфиг, правка без изменения логики — строка
«тривиальный дифф (N строк, логика не менялась), гейты зелёные» вместо прогона
списка по пустому материалу.

Вопросы — про конкретные строки, а не про имена принципов:

- что вернёт или сломает функция при пустом входе, нуле, отсутствующем файле,
  мусоре вместо ожидаемого формата;
- каждая граница диапазона и каждое сравнение: включительно или нет — и что
  требует контракт (JSDoc, спека);
- каждое имя: что оно обещает и что код делает на самом деле;
- каждый `catch`, `as` и `!`: что теряется молча; различение ошибок по типу, а
  не по тексту `message`; нет пустых `catch` и плавающих промисов;
- повторный вызов с теми же данными: результат тот же, вход не изменён;
- потоки: stdout только данные, stderr только диагностика, `console.*` только в
  слое склейки;
- атомарность: не смешаны ли рефакторинг, багфикс и новая функциональность; нет
  ли попутных правок несвязанных участков.

Форма вывода: по каждому нарушению строка
`файл:строка — в чём нарушение — как переписать`. «Нарушений нет» допустимо
только вместе с перечислением того, что проверено. Замечания к соседнему коду,
которого задача не касается, — отдельным списком, **без правок**. Проблемы ради
находок не искать: починка выдуманного даёт лишние абстракции и защитный код —
нашёл, покажи строку.

Спорное решение, где обе трактовки принципа защитимы, не замалчивается, а
выносится в отчёт: «выбрано X, потому что Y; альтернатива Z отвергнута
потому-то».

## Процесс разработки

### TDD

Цикл: **красный → зелёный → рефакторинг**.

1. Тест, описывающий требуемое поведение, пишется первым и **запускается**,
   чтобы увидеть его падение по ожидаемой причине.
2. Минимальная реализация, доводящая тест до зелёного.
3. Рефакторинг под раздел о качестве — при зелёных тестах.
4. Тест на баг и сам фикс — в одном коммите; «тесты допишу потом» не бывает.

Тесты проверяют поведение и контракт, а не внутреннее устройство. Табличные
тесты (`Deno.test` + `t.step` по случаям или цикл по массиву случаев) — форма по
умолчанию. Багфикс начинается с теста, воспроизводящего баг.

Что считать хорошим тестом:

- Время — `FakeTime` из `@std/testing/time`, никогда реальный `setTimeout`-сон.
- Временные файлы — `Deno.makeTempDir()` с уборкой в `finally`/`using`; никаких
  самодельных путей.
- Сравнение — `assertEquals`/`assertObjectMatch` из `@std/assert` с читаемым
  сообщением: падение теста должно читаться без отладчика.
- Внешние зависимости — за узким интерфейсом на стороне потребителя. Ручного
  фейка достаточно; mock-фреймворки не добавляются. MCP-сервер проверяется
  парами «запрос → ответ» из `fixtures/mcp-server/` поверх обработчика, без
  слушающего сокета и без сети наружу.
- Golden-фикстуры из спек (`docs/specs/fixtures/…`) копируются в `testdata/`
  модуля: тесты самодостаточны, источник истины — спека.
- Санитайзеры `Deno.test` включены: тест, оставляющий висящий таймер или
  незакрытый ресурс, — красный.

**Мутационная проверка обязательна** для каждого нового теста, закрепляющего
инвариант или политику: сломать проверяемое свойство в коде, убедиться, что тест
краснеет, вернуть код. Тест, который не краснеет от поломки того, что он
проверяет, — не тест, а строка в отчёте о покрытии. В отчёте перечисляется,
какие мутации прогнаны и что упало. Для прочих тестов (разбор, рендер, частные
случаи) проверка желательна, но не обязательна — там красноту показывает сам
цикл «красный → зелёный».

### Контроль покрытия

Покрытие измеряется и не должно падать от изменения:

```bash
deno task test --coverage=cov
deno coverage cov                 # сводка по файлам/строкам
deno coverage cov --html          # построчно, что не покрыто
```

Покрытие — инструмент поиска непроверенных ветвей, а не самоцель: непокрытыми не
должны оставаться ветви обработки ошибок и граничные случаи. Отчёт по покрытию
затронутых модулей сообщать вместе с результатом.

### Прод не меняем ничем и никогда — проверяем только в локальном docker

Правило владельца, 2026-08-28: **на боевом контуре не меняется ничего.** Прод —
источник только для чтения: снять форму печати, сверить справочные данные,
прочитать ответ API. Любая проверка, которая что-то создаёт, правит или удаляет,
идёт в локальный docker-стек, и другого места у неё нет.

Это не «по возможности»: команда, для которой локального стенда не существует,
остаётся с непроверенным живьём выполнением — так и пишется в отчёте. Отсутствие
стенда никогда не превращается в основание сходить в прод «один раз, аккуратно».

### Живая проверка пишущей команды — на локальном стеке, не в проде

Команда, чей дефолтный режим что-то меняет снаружи (запись в БД клиента,
пересчёт витрин, миграция схемы, заведение пользователя, чистка очереди, заливка
в таблицу), живьём проверяется **только на локальном docker-стеке**: контейнеры
`sl-N-cli` / `sl-N-pg` и их соседи подняты на этой же машине. В прод такая
команда не отправляется ни разу — ни «одним безопасным вызовом», ни «на тестовом
клиенте».

- Режим печати (`--print`/`-p`, `--dry`, `--dry-run`) прода не касается и
  гоняется свободно: он и служит парной сверкой формы с рабочей версией.
- Выполнение проверяется на локальном стеке: `--local` печатает локальную форму,
  а сам вызов идёт `docker exec` в локальный контейнер. Наблюдаемый результат
  (строка в таблице, созданная схема, ответ метода) — и есть доказательство, что
  команда не только печатает, но и работает.
- Стенда для этой команды нет или он не поднимается — это не повод пойти в прод:
  скажи об этом в отчёте и оставь выполнение непроверенным, назвав, что именно
  осталось за пределами проверки.
- **Изолированная сессия работает только по спеке; всю сверку делает
  спецификатор.** Ни рабочая версия, ни стенд, ни прод из сессии недостижимы —
  ни `docker`, ни сети, ни ключей, ни кэша серверов (замерено 2026-08-27).
  Поэтому источник истины для неё — спека и гейты: тесты, голдены, `smoke`. Пару
  с рабочей версией — и по печати, и по выполнению — гоняет спецификатор на
  своей стороне и приносит расхождения в канал. Сессия обязана назвать в отчёте,
  что осталось неподтверждённым живым прогоном, иначе спека выглядит проверенной
  целиком, не будучи ею.
- В спеку идёт то, что снято на стенде: побочные эффекты названы наблюдаемым
  следом (какая таблица, какая строка, какой ответ), а не пересказом намерения.
- **Проверка — всегда парой с рабочей версией, а не соло.** На стенде вызов
  делается дважды: рабочей командой и новой, на одном и том же входе и с одного
  и того же состояния, после чего сравнивается наблюдаемый след — строки в
  таблице, ответ метода, код выхода, stdout и stderr. «У нас отработало без
  ошибки» — не результат: без второго прогона неизвестно, то же ли самое
  отработало. Состояние между прогонами возвращается к исходному, иначе второй
  вызов видит следы первого и сравнение врёт.
- Расхождение пары не правится подгонкой под чужой ответ: сначала называется,
  какое из двух поведений верное и почему, и только потом либо чинится наша
  сторона, либо расхождение уходит в «Известные отклонения» с числами.

**Как физически не дать прогону уйти в прод.** Дефолтный транспорт пишущей
команды — прод (Portainer, ssh по кэшу серверов), и «я не буду запускать без
`--print`» защитой не является: ошибка в одном флаге стоит записи в боевые
данные. Поэтому на время стендового прогона:

1. **Транспорт временно переключается на локальный.** Правится код: вместо
   прод-пути вызов идёт `docker exec` в локальный контейнер. Правка помечается
   комментарием как временная, **не коммитится** и снимается до коммита.
2. **Страховка окружением.** Прогон запускается с подменённым `HOME` (и
   `XDG_CONFIG_HOME`), где нет ни ключа Portainer, ни кэша серверов, ни адресов
   ssh. Если временная правка не сработала, вызов упрётся в отказ конфигурации —
   не в прод. Перед прогоном это проверяется отдельно: дефолтный вызов в таком
   окружении обязан падать.
3. **Локальность доказывается транспортом, а не именем.** Контейнеры стенда
   называются так же, как на ферме (`sl-1-cli` есть и там, и здесь), поэтому имя
   ничего не доказывает: доказательство в том, что вызов идёт через docker этой
   машины, а не через Portainer или ssh.
4. **Сдаваемая версия ходит в прод как оригинал.** Временные правки транспорта в
   поставку не попадают; перед коммитом дерево чистое, гейты зелёные, а в отчёте
   сказано: что правилось временно, чем подтверждена локальность прогона и что
   правка снята.

### Отсутствие признака — не наблюдение

Прежде чем трактовать тишину как успех (нет ошибки, нет предупреждения, нет
расхождения), проверить, что проверяемый шаг вообще исполнялся. Тишина мёртвого
шага неотличима от тишины успешного.

Проверяется тем, что шаг оставляет след: возраст записи, счётчик, отметка
времени. `EXISTS` отвечает на вопрос «было ли когда-нибудь», а нужен ответ на
«сделал ли это прогон» — годится `IDLETIME`, `updated_at`, размер до и после.
Замер 2026-08-28: ключ кэша существовал, IDLETIME 14285 секунд при прогоне 154
секунды назад — шаг не исполнялся полгода, а выглядел живым на каждой приёмке.

Требуется **след**, а не внимательность: внимательность не воспроизводится, след
воспроизводится.

Тем же классом — измерение, которое выглядит состоявшимся, но мерит не то: **код
возврата снимается без конвейера**, иначе `$?` относится к последней команде.
Замер 2026-08-28: `docker exec … | tail -1` дал «код 0» там, где у самого
`docker` был 1.

Туда же — **прогон сдаёт не тот код, что ожидается**: если бинарь собран раньше
коммита, который в нём предполагается, замер честен, но относится к прежней
версии. Сверяется временем сборки против времени коммита. Замер 2026-08-28:
бинарь оказался на 291 секунду старше правки, которую я объявил проверенной.

### Величина берётся там, где совершается работа

Печатаемое число сходится с текстом рядом с ним не потому, что его так назвали,
а потому, что снято с той самой работы. Брать его там, где удобно, — у
источника, у первого из нескольких действий, у счётчика, который вернул сервер,
— значит получить строку, правдивую по форме и неверную по существу.

Три случая 2026-08-28, три формы одной причины: строка называла кабинеты, а
считала связки (единицы разошлись); очистка кэша считала вкладки, а удаляла
вкладки и ключ метаданных (величина покрыла часть работы); синхронизация
печатала полученное с сервера, а вставляла отфильтрованное (величина снята до
работы).

Проверяется устройством, а не внимательностью: величина вычисляется из
результата действия — из того, что вернул сам оператор, из длины того, что
вставлено, — а не из входа, из которого работа только собиралась. Если действий
несколько, величин тоже несколько: одно число на два действия покрывает одно из
них. Вопрос при разборе — вспомогательный: у каждой печатаемой строки спросить,
та ли величина в неё подставлена, которую строка называет.

### Фикстуру стыка снимают, а не сочиняют

Фикстура, написанная под собственный код, проверяет догадку о чужой форме той же
догадкой: тест зелёный ровно потому, что обе стороны придумал один человек. Стык
— ответ чужой службы, формат чужого файла, вывод чужой команды — проверяется
образцом, **снятым с неё живьём**, и снятое кладётся в репозиторий как голден.

У снятого образца обычно есть отпечаток — опечатка, лишнее поле, странный
порядок; сочинённая фикстура их не воспроизводит. По ним и видно, снята она или
написана.

Замер 2026-08-28: величина записанных ячеек читалась из поля
`totalUpdatedCells`, которого посредник не отдаёт вовсе — его ответ целиком
`{"value": "data batchUpdate succesfull"}`. Тест был зелёным с первого прогона:
в нём поле подставляли сами. Поле при этом не перенесено, а придумано при
переезде — оригинал величину не извлекал вовсе, он печатал ответ как есть. Тем
же днём в соседней порции снисходительность к незамеренным именам полей
снималась по живому ответу — там образец был, и догадка ушла (команда потом
исключена; пример о решении, не о коде).

Снять эталон — значит взять у объекта **всё, что у него есть**, а не то, что
счёл нужным снимающий. Выбранное подмножество выглядит снимком и проверяется как
снимок, но о невзятом молчит, и это молчание не отличить от совпадения. Замер
2026-08-31: эталон пишущей половины `api` хранил у поля тела имя и тип, а
признак обязательности — нет; в переносе обязательность не проставлена ни у
одной из 23 команд, у которых она есть, при рабочем механизме отказа. Сверка
была зелёной всё это время и не солгала ни разу — она сверяла ровно то, что ей
дали.

Снимают у **объекта**, а не у его описания. Справка, README и комментарий рядом
с кодом — третья версия правды: они писались однажды и с тех пор расходились с
обеими сторонами. Замер 2026-08-31: справка оригинала обещала проверять, что
сессия **валидна**, а код проверял непустоту строки; перенос, сделанный по
справке, ушёл бы в сетевой вызов там, где его быть не должно. Расхождение
описания с кодом — само по себе находка: оно означает, что одно из двух никто не
проверял.

Где снять нельзя — служба недостижима из этой сессии — догадка называется
догадкой в отчёте, и её проверяет тот, у кого доступ есть. Названная догадка
живёт до ближайшей проверки, неназванная — до живой пары.

### Мутацию выбирают со стороны проверки

Мутационная проверка доказывает не то, что код можно сломать, а то, что проверка
**смотрит** на сломанное место. Поэтому мутация отсчитывается от проверки:
берётся величина, которую проверка читает, и портится **там, где проверка её
читает**, — а не там, где эта величина впервые появляется. Сторона роли не
играет: снять `required` в таблице объявлений и перевернуть `required` в эталоне
— обе мутации правильные, потому что обе портят читаемое.

Зелёная мутация значит одно из двух, и различать их обязательно: проверяемого у
проверки нет — либо испорчено место, чей эффект восстанавливается ниже по коду.
Замер 2026-08-31: режим файла портили в
`Deno.writeTextFile(path, text, { mode: 0o600 })`, тест оставался зелёным, и
объяснение звучало разумно; настоящий источник — следующая строка,
`Deno.chmod(temp, 0o600)`, и её мутация покраснела сразу. Правило различения
одно на оба случая: портить у самой проверки, а не у первого автора величины.

Замер того же дня в другую сторону: величина записанных ячеек читалась из поля,
которого посредник не отдаёт вовсе, — испортить его у посредника было нельзя,
потому что подставляла его сама проверка. Мутация со стороны кода нашлась бы и
покраснела; мутация со стороны проверки показала, что проверять нечего.

### У пропускаемой проверки предъявляется исполнившийся прогон

Проверка, умеющая пропускаться (нет доступа, база не поднята, нет ключа),
делится на две: сама проверка и решение её не делать. Второе исполняется всегда,
первое — неизвестно когда в последний раз. Поэтому предъявляется **прогон, где
она исполнилась, и прогон, где она покраснела**; засчитывается последний прогон,
в котором менялось проверяемое, а не обязательно сегодняшний.

Предъявляет тот, у кого есть окружение. У изолированной сессии его может не быть
по устройству — `/tmp` только для чтения, docker-сокет закрыт, — и тогда прогон
делает сторона с доступом, а сессия называет, чего не смогла. Правило это о
передаче замера, а не о внимательности исполнителя: требовать исполнившийся
прогон от того, кто физически не может его сделать, — способ получить
выдуманный.

Причина пропуска печатается дословно от источника
(`connect ECONNREFUSED
127.0.0.1:5440`,
`permission denied … unix:///var/run/docker.sock`, `Read-only file system`), а
не пересказом («база недоступна»): пересказ одинаков и для погашенной базы, и
для нехватки права, и для опечатки в адресе — то есть скрывает ровно то, ради
чего печатается.

Замер 2026-08-28: сверка схемы показывала пропуск с правдоподобной причиной и ни
разу не исполнялась — права не хватало; как долго, не мерили. Приёмка предъявила
три исхода: `ok` при верном голдене,
`FAIL … в базе нет колонок
голдена: grantee_mail` при испорченном,
`skip … connect ECONNREFUSED` при погашенной базе. Первые два и есть
доказательство, что третий — пропуск, а не тишина.

### Атомарность изменений

- Одно изменение — одна задача. Рефакторинг, багфикс и новая функциональность не
  смешиваются в одном коммите.
- Правки хирургические: минимальный дифф, решающий задачу. Не переформатировать,
  не переименовывать и не «попутно улучшать» несвязанные участки.
- Каждый коммит оставляет дерево в рабочем состоянии: проверка из раздела
  «Проверка каждого изменения» зелёная.
- Вся работа идёт в `main`. Веток не создавать и не предлагать — это осознанное
  решение пользователя, оно перекрывает общее правило «не коммитить в дефолтную
  ветку».
- Сообщения коммитов: Conventional Commits со скоупом (`feat(xlsx): …`,
  `fix(registry): …`), тема — на русском, в императиве.

### Зависимости

Каждая прямая зависимость сопровождается строкой «зачем» — комментарием в
`deno.jsonc` рядом с записью в `imports`. Версии фиксируются; `deno.lock`
коммитится. Порядок предпочтения источников — раздел «Библиотеки и приёмы»;
`npm:`-зависимость без записанного аргумента не появляется.

### Что не делать без спроса

- Не создавать каркас модулей заранее — структура растёт из задач.
- Не добавлять зависимости, не менять версию Deno и настройки строгости в
  `deno.jsonc`.
- Не менять флаги permissions сборки/тестов.
- Не трогать `.claude/` и `docs/` (спеки — read-only, правит
  сессия-спецификатор).
- Не переписывать существующие тесты «под новый стиль» и не рефакторить код,
  которого задача не касается.

### «go» — определи состояние сам

Голое «go», «го», «продолжай» без пояснений — не вопрос, а команда действовать
по состоянию: **что делать, ты выясняешь сам, а не переспрашиваешь**. Источников
состояния два — первая строка `.tmp/buf.txt` и состояние дерева.

Первая строка буфера всегда маркер: `# ЗАДАНИЕ` — лежит постановка, `# ОТЧЁТ` —
лежит уже отданный отчёт. Порядок действий:

1. `deno task handoff status` — что в ячейке, и `deno task handoff read` — сам
   текст. Читать и переписывать `.tmp/buf.txt` руками не нужно: задача пишет
   атомарно и не даёт затереть неотработанное (`handoff/`, справка — в шапке
   `handoff/main.ts`). Ждать постановку, не запуская сессию заново, —
   `deno task handoff wait task`.
2. `# ЗАДАНИЕ` → посмотреть, что из постановки уже сделано (`git log`,
   `git status --short -- ts/`, `git diff -- ts/`), и продолжить с первого
   незакрытого раздела. Свежая сессия без контекста — то же самое: дерево и
   история говорят, где ты остановился.
3. `# ЗАДАНИЕ`, и все разделы закрыты, гейты зелёные, всё закоммичено, дерево
   чистое → работа окончена: написать отчёт в файл и отдать его
   `deno task handoff report <файл>` (маркер `# ОТЧЁТ` задача поставит сама).
   **Сразу за этим — встать на ожидание следующей постановки**, фоновой командой
   `deno task handoff wait task 3600`. Она завершится сама, когда постановка
   ляжет в ячейку, и сессия проснётся без единого слова оператора. Ожидание
   ставится в фоне: сессия при этом свободна и может отвечать.
4. `# ОТЧЁТ` → отчёт уже отдан, новой постановки нет. Не выдумывать себе работу
   и не трогать код: встать на то же фоновое ожидание
   (`deno task handoff wait task 3600`) и сказать, что ждёшь следующей порции.
   Если ожидание уже стоит — просто сказать; двух одновременно не заводить.
5. Буфер пуст или маркера нет → сказать об этом и остановиться. Гадать, что
   имелось в виду, нельзя.

Единственное, что «go» не отменяет, — правила качества: гейты, разбор диффа,
мутации и атомарность коммитов обязательны и на нём.

### Формат отчёта о выполнении

Постановка порции приходит и отчёт о ней уходит через один файл — `.tmp/buf.txt`
(правило обеих ролей — `docs/CLAUDE.md`, «Передача работы»). Работа начинается с
`deno task handoff read`, а заканчивается `deno task handoff report <файл>`:
отчёт кладётся **вместо** постановки, не дописывается в конец, маркер `# ОТЧЁТ`
ставит задача. Ячейка одна и истории не хранит, поэтому всё, что должно пережить
порцию, к моменту записи уже лежит в коде, тестах и сообщениях коммитов.

Отдав отчёт, сессия **сама встаёт на ожидание** следующей постановки
(`deno task handoff wait task 3600` фоном) — оператор в передаче не участвует и
не носит сообщения между сессиями. Его дело — запустить сессию однажды.

1. Что изменено — список файлов и в чём смысл каждого изменения.
2. Почему именно так, если решение неочевидно.
3. Вывод `deno fmt --check`/`deno lint`/`deno check`/`deno task test` и покрытие
   затронутых модулей.
4. Результат разбора диффа (шаг 2 проверки) — найденное и как исправлено либо
   прямое «нарушений нет».
5. Прогнанные мутации и что от них упало.
6. Новые доменные имена, отсутствующие в `docs/glossary.md`, — отдельным списком
   для внесения.
7. Замечания к соседнему коду — отдельным списком, без правок.

Отчёт без пунктов 4 и 5 считается неполным и не выдаётся.

## Команды

```bash
deno fmt              # форматирование (deno fmt --check — только проверка)
deno lint             # статический анализ
deno check .          # проверка типов всего дерева
deno task test        # все тесты (санитайзеры включены по умолчанию)
deno task test path/to/x_test.ts --filter "имя"   # один тест
deno task test --coverage=cov && deno coverage cov # покрытие
deno bench            # бенчмарки
deno task smoke       # собранный бинарь во временном HOME: права из build
deno task <name>      # задачи из deno.jsonc (появятся с первым кодом)

git status --short -- ts/             # состояние; pathspec обязателен
git diff -- ts/                       # дифф перед завершением задачи
git add ts/…                          # только явные пути
git commit -m "…" -- ts/              # коммит с pathspec
```

`deno`, `git` разрешены без запроса подтверждения.

## Состояние проекта

**Модуль Deno/TS в середине переноса.** Источник знания о поведении — `docs/`
(канал спецификаций, см. `docs/CLAUDE.md`).

Каркас собран целиком: реестр команд с обоими маршрутами (`src/registry/`,
`docs/specs/platform/registry.md`), MCP-сервер с профилями `ro`/`rw`
(`src/mcp/`), делегация непереехавших команд подпроцессом (`src/legacy/`),
журнал вызовов, локальный конфиг и кэш-БД (`src/invokelog/`, `src/config/`,
`src/store/`). Точка входа — `src/entrypoint/`.

Маршрутом `native` идут: `xlsx` (все подкоманды), `init`, `update`, `sql-ro`,
`logs`, `mcp token`. Остальные команды — маршрутом `legacy`, их состав порождён
машинным слепком дерева Python-версии (`src/registry/legacy_tree.ts`), и перевод
команды сводится к переносу записи из слепка в реестр нативных.

Отдельно от команд лежат каталоги внешнего API Kaiten (`src/kaiten/`): карточки,
учёт времени, справочники, транспорт с обеими пагинациями и прогрев. Вызывающих
у части из них ещё нет — это оговорённое спеками отступление от правила «код
растёт из задач», поэтому неиспользуемый вызов каталога дефектом не считается.
Команды семейства `kiten` поверх них едут следующими порциями.

Переносится **поведение, а не структура**: питоновская декомпозиция,
классы-неймспейсы и идиомы не калькируются — модули и типы проектируются заново
по правилам выше. Паритет подтверждается golden-фикстурами спек, а не построчным
сравнением кода.

### Замысел: один бинарь, две точки входа

Одна программа — самодостаточный бинарь (`deno compile` → `~/.local/bin/mpu`) —
с двумя режимами над **общим реестром команд**:

- **CLI для человека** — `mpu <cmd> [args…]`. Разбирает argv, исполняет команду,
  рендерит результат в текст. Живёт ровно один вызов.
- **MCP-сервер для агента** — `mpu mcp`. Долгоживущий процесс, слушающий
  `127.0.0.1` (Streamable HTTP, роутер Hono); публикует те же команды как тулы и
  исполняет их по запросу агента. Два непересекающихся профиля: `ro` по пути
  `/ro` и `rw` по пути `/rw` — читающие и мутирующие тулы не смешиваются, и на
  `/ro` мутирующий тул не зарегистрирован вовсе, а не запрещён при вызове.

Режимы — не два кода, а две проекции одного объявления команды: путь,
назначение, справка, политика (`ro`/`rw`), схема аргументов, схема результата,
рендер. Из этих семи вещей CLI берёт разбор argv и текст, а MCP-сервер — схемы
тулов и структурный результат. Контракт —
`docs/specs/platform/command-contract.md`; поведение сервера —
`docs/specs/platform/mcp-server.md`.

Команды, ещё не перенесённые, остаются в реестре с маршрутом `legacy` и
исполняются подпроцессом Python-реализации; как тулы они не публикуются. Перевод
команды и откат — правка одной строки реестра
(`docs/specs/platform/registry.md`).

### Справка: руководство к действию

У справочного текста команды два читателя: человек, набравший `--help`, и
ИИ-агент, которому тот же текст приходит описанием тула. Оба читают одно
объявление команды, поэтому текст пишется один раз и обязан работать для обоих:
справка — это CLAUDE.md конкретной команды, прочитал → знаешь, как действовать.
Отсюда два равноправных требования: **экономия токенов** и **полнота,
достаточная для работы без проб и ошибок**. Если после чтения справки остаётся
вопрос, на который отвечает только эксперимент или чтение исходников, — справка
дефектна.

Экономия здесь не стилистическая: описание тула и инструкции профиля клиент
обрезает на 2048 байтах (`platform/mcp-server.md`), и текст, не уместившийся в
предел, теряется молча.

Структура — двухслойная, по уровням дерева команд:

- **Промежуточный уровень** (`mpu --help`, `mpu <cmd> --help` для группы) —
  краткий индекс: одна строка «что это» и список подкоманд, каждая с одной
  строкой назначения. Ничего больше.
- **Листовая команда** — подробности: каждый флаг и аргумент с типом, значением
  по умолчанию и ограничениями, формат ввода/вывода, коды и смысл ошибок,
  один-два примера вызова.

Требования к коду:

- `--help` работает на **каждом** уровне дерева. Это свойство обеспечивается
  конструкцией типа команды, а не дисциплиной: команду нельзя зарегистрировать
  без короткой строки назначения, а листовую — без подробной справки; отсутствие
  текста — ошибка типов или паника инициализации, не пустой вывод.
- Справка живёт рядом с командой, в том же файле, что её реализация; текст
  объявляется данными (поля объекта команды), а не размазывается по коду
  форматированием.
- Индекс родителя собирается автоматически из зарегистрированных подкоманд —
  руками не дублируется и потому не устаревает.
- Тест инварианта дерева: у каждой команды непустая краткая строка, у каждой
  листовой — непустая подробная справка, `--help` на любом уровне завершается
  успешно, не ходит в сеть и не поднимает MCP-сервер.

Конвенции репозитория: комментарии и документация — на русском, идентификаторы и
код — на английском.

## Изоляция окружения

Рабочая область — каталог `ts/`, но **сессия запускается из корня репозитория**
(`mpu/`), и профиль изоляции лежит в `mpu/.claude/settings.json`: рабочему
каталогу нужен доступ к `.git`, иначе git не работает. Сам профиль сессии не
виден. Практические последствия:

- Соседние проекты в `/home/user/mr/mp/`, а внутри `mpu/` — `py/`, `docs/` и
  родительские CLAUDE.md закрыты и правилами permissions, и файловой системой
  песочницы. Закрыты по-разному: `py/` и `mpu/docs/` подменены пустым каталогом
  (содержимого не видно вовсе), у соседей видны имена файлов, но чтение
  отказывает. Этот файл — единственный источник контекста; знание о поведении —
  только из `docs/specs/`.
- Спеки `ts/docs/` для реализующей сессии read-only; их правит
  сессия-спецификатор. Платформенные контракты живут в
  `ts/docs/specs/platform/`; отдельного канала протокола и брокера нет.
- Запись сохраняется только внутри `ts/` и в `.git` репозитория. Запись мимо них
  не достигает диска, **но может вернуть успех** — на код возврата как на
  проверку изоляции полагаться нельзя, проверять надо обратным чтением.
- Сеть списком хостов не ограничена. Это свойство окружения, а не разрешение
  ходить куда угодно: сам код и тесты ходят только на источники зависимостей
  (`deno.land`, `jsr.io`, `registry.npmjs.org`), MCP-сервер слушает только
  `127.0.0.1`.
- Через `env` профиля кэш Deno перенаправлен в `ts/.deno`, а `TMPDIR` — в
  `ts/.tmp` (оба в `.gitignore`). Временные файлы — в `$TMPDIR`, не в `/tmp`.

### Git: обязательно работать через pathspec

Из-за блокировки `py/` и `docs/` git видит сотни файлов **удалёнными и
изменёнными**, хотя на диске они целы. К этому добавляется untracked-шум:
заглушки, которыми песочница подменяет dotfiles в корне репозитория (`.bashrc`,
`.gitconfig`, `.mcp.json`, `.idea/`, `.vscode/`, старый
`ts/.claude/settings.json`). Поэтому:

- Смотреть состояние только с ограничением области: `git status --short -- ts/`,
  `git diff -- ts/`. Без pathspec вывод нечитаем и опасен.
- Индексировать только явными путями: `git add ts/…`; коммитить с pathspec:
  `git commit -m "…" -- ts/`.
- `git add -A|--all|-u`, `git commit -a|-am`, `git stash` **запрещены** — они
  закоммитят удаление соседних каталогов. Это не рекомендация: их блокирует
  `PreToolUse`-хук профиля (`mpu/.claude/settings.json`), отвечающий отказом с
  напоминанием про pathspec.
- Пути в командах разрешаются от каталога запуска, а он — корень репозитория:
  `ts/…`, а не `./…`.

Remote `origin` у репозитория есть, но отправка в него — дело внешнего
терминала, не сессии.

`ts/.claude/lock.sh on|off|status` — тумблер права сессии писать в профиль
изоляции. Запускается **только из внешнего терминала**: в положении `on` запись
из сессии запрещена правилом permissions. Скрипт достался от прежней раскладки и
всё ещё правит исчезнувший `ts/.claude/settings.json` — до его починки тумблер
не работает.
