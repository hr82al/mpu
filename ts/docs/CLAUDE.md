# CLAUDE.md — изолированные спецификации CLI (Deno/TS)

`docs/` — единственный канал передачи знания в изолированные Deno-сессии,
реализующие CLI `mpu`. Deno-сессия не видит `py/`, `mpu/docs/` и родительские
CLAUDE.md: всё, что нужно для реализации команды, обязано лежать здесь. Чего нет
в спеке — для Deno-сессии не существует.

Файл обслуживает две роли:

- **сессия-спецификатор** — монорепо-сессия с доступом к Python-оригиналу; пишет
  и обновляет спеки по правилам ниже. Внутри `ts/` ей можно трогать **только
  `docs/`**: код CLI, конфиги Deno и корневой CLAUDE.md модуля пишутся
  исключительно из изолированной Deno-сессии (появятся с первой реализацией).
- **изолированная Deno-сессия** — реализует команду строго по спеке; правила — в
  последнем разделе.

Постановку и отчёт роли передают друг другу через `ts/.tmp/buf.txt` — см.
«Передача работы» ниже.

## Структура

- `specs/<command>.md` — спецификация одной CLI-команды: наблюдаемая поверхность
  (флаги, вывод, exit-коды). Команда с подкомандами дробится на отдельные спеки,
  каждая самодостаточна.
- `specs/platform/<name>.md` — платформенные кусочки CLI-обвязки:
  реестр/маршрутизация, локальный конфиг, хранение токена, резолв селектора,
  журнал вызовов, HTTP-клиенты внешних систем. Контракт возможности
  — вход → результат → инварианты → ошибки, **не** API: типы и модули
  проектирует Deno-сессия.
- `specs/fixtures/<command>/` — фикстуры: golden-выводы, снятые с живой
  Python-версии, и примеры входных файлов; спека на них ссылается.
- `glossary.md` — доменный термин → каноничное имя в TS-коде. Каждая спека
  пользуется именами отсюда; новый термин — новая строка.
- Правила реализации (структура дерева, гейты `deno fmt`/`lint`/ `check`/`test`,
  ограничения) — корневой `CLAUDE.md` модуля `ts/`; его ведёт изолированная
  Deno-сессия.
- План переезда и статусы ведёт сессия-спецификатор вне канала.

## Передача работы — буфер `ts/.tmp/buf.txt`

Постановка порции и отчёт о ней ходят через один файл — **`ts/.tmp/buf.txt`**.
Он вне git (каталог в `.gitignore`), доступен на запись обеим ролям и на чтение
обеим же, поэтому оператору не нужно ничего переносить руками.

**Первая строка буфера — маркер, он обязателен обеим ролям**: `# ЗАДАНИЕ` —
внутри постановка, `# ОТЧЁТ` — внутри отчёт. По нему сессия понимает, что перед
ней, не разбирая текст и не переспрашивая: голое «go» («продолжай») означает
«определи состояние сам и сделай следующий шаг». Спецификатор на «go» читает
буфер и, увидев `# ОТЧЁТ`, принимает работу; увидев `# ЗАДАНИЕ` — порция ещё в
работе, буфер не трогает. Изолированная сессия — зеркально; её алгоритм подробно
расписан в `ts/CLAUDE.md`, раздел «go».

Правило по роли — кто ты в текущей сессии, то и делаешь:

- **изолированная Deno-сессия**: в начале работы **читает** `ts/.tmp/buf.txt` —
  там лежит постановка порции; закончив, **перезаписывает** этот же файл своим
  отчётом по форме из `ts/CLAUDE.md` (пункты 4 и 5 обязательны). Спеки при этом
  read-only, как и прежде: отчёт — единственное место, куда пишутся вопросы к
  спецификатору и замечания к соседнему коду.
- **сессия-спецификатор**: **читает** оттуда отчёт, принимает работу и
  **перезаписывает** файл следующей постановкой. Правки по итогам приёмки вносит
  в спеки, не в буфер.

**Ходить в ячейку — задачей `handoff`, а не чтением и переписыванием файла.**
Из каталога `ts/`:

```bash
deno task handoff status              # что лежит: постановка или отчёт, сколько строк
deno task handoff read                # содержимое как есть
deno task handoff post <файл|->       # положить постановку (спецификатор)
deno task handoff report <файл|->     # положить отчёт (изолированная сессия)
deno task handoff wait task [сек]     # ждать постановку и напечатать её
deno task handoff wait report [сек]   # ждать отчёт
```

Что это даёт против ручной записи: запись атомарна (временный файл рядом и
`rename` — читающая сторона видит либо старое целиком, либо новое целиком),
`post` не кладёт постановку поверх неотработанной, а `report` — отчёт поверх
отчёта (обход — явный `--force`), и появляется ожидание: сессия стартует с
`wait task` и начинает работу сама, как только постановка легла. Коды выхода:
0 — успех, 1 — состояние ячейки (пусто, не тот вид, срок вышел), 2 — ошибка
ввода. Путь ячейки переопределяется `HANDOFF_CELL` — это для проверок самой
задачи, в работе он не нужен.

Буфер — одна ячейка, а не журнал. В нём в каждый момент лежит ровно одно: либо
текущая постановка, либо текущий отчёт.

- **Запись — только полная перезапись.** Новое содержимое кладётся вместо
  старого, файл предварительно очищается; дописывать в конец нельзя. Иначе
  постановка и отчёт слипаются, и читающая сторона не понимает, что из этого
  адресовано ей.
- **Чтение — перед записью, всегда.** Прежде чем затирать, прочитать то, что
  лежит, и перенести из него всё ценное в долговечное место: спеку, план,
  `docs/migration-log.md`, сообщение коммита.

Ни постановка, ни отчёт сами по себе не источник истины: истина — спеки и
коммиты. Буфер их не заменяет и не хранит историю.

## Спека — контракт, инварианты, граничные случаи. Ничего больше

Спека описывает, **что** обещает команда, и молчит о том, **как** устроен
Python-оригинал. Фильтр на каждое утверждение — два теста:

- **наблюдаемость** — видно снаружи команды: пользователю, в файле, в БД, в
  сети, в ответе MCP-сервера;
- **проверяемость** — по утверждению можно написать падающий тест.

Состав — четыре содержательных блока (Контракт, Инварианты, Граничные случаи,
Golden-примеры) плюс служебные «Известные отклонения» и «Открытые вопросы».
Граничный случай — строго парой «вход → ожидаемое поведение»; случай без
ожидаемого поведения — не спецификация, а вопрос: ему место в «Открытых
вопросах». Ужесточения:

- **Случайное поведение — не контракт.** Деталь формы без функционального
  значения («так вышло у Python») в спеку не входит; новая реализация вольна
  сделать лучше, расхождение учитывается на differential-сверке.
- **Внешняя граница — дословно.** Для каждой внешней системы (PostgreSQL,
  HTTP API, ssh, файлы) спека фиксирует точную форму обмена: SQL-запросы (либо
  их точную семантику: таблицы, фильтры, агрегаты) и форму результата; эндпоинты
  и схемы ответов (примеры — в фикстурах); вызываемые команды; формат читаемых
  и записываемых файлов (примеры — в фикстурах). Для
  CLI-поверхности — stdout/stderr/exit-коды (golden); для MCP-сервера — коды
  HTTP, JSON-RPC-ответы и схемы тулов (golden-пары запрос/ответ).
- **Секретам и живым данным не место** ни в тексте, ни в фикстурах: входы
  синтетические или обезличенные.
- **У каждого поля вывода назван источник.** Перечислить ключи мало: на каждый
  сказано, откуда берётся значение — из одноимённого поля ответа, из вложенного
  (и какого именно: `title` у одних сущностей, `name` у других), из таблицы
  меток, построено самой командой. Ключ без источника — не спецификация:
  реализующая сессия проверить его неоткуда и вынуждена спрашивать.
- **Хвост вывода описан.** Для каждой поверхности stdout сказано, чем вывод
  оканчивается — один перевод строки, пустая строка, ничего. Иначе побайтовое
  сравнение с голденом упирается в невидимый в редакторе байт.
- **Нормативный язык**: «обычно», «может», «примерно» запрещены.
- **Размер — сигнал**: спека длиннее ~200 строк почти наверняка пересказывает
  реализацию — резать или дробить.
- **Порция — одна сессия**: спека реализуема за одну Deno-сессию, иначе дробить.
- **Никакого устройства оригинала**: имена python-функций, модули, цитаты кода,
  псевдокод — запрещены; реализация проектируется заново.
- **Самодостаточность**: ссылки только внутрь `ts/docs/`; пути в `py/` и
  приватные документы монорепо — запрещены.

## Известные ошибки оригинала — не тащить молча

Каждый баг/квирк оригинала, влияющий на вызывающих, фиксируется в «Известных
отклонениях» с вердиктом: **fix** (в новой реализации не воспроизводить;
умолчание) или **preserve** (воспроизводить осознанно, с названной причиной).
Непонятный обходной путь не переносится, пока не понят.

## Скелет спеки

Заголовки в этом порядке; неприменимый раздел — с пометкой «нет»:

```markdown
# mpu <command>

Статус: черновик | к реализации | реализовано

## Назначение

## CLI-контракт

## Ввод/вывод

## Побочные эффекты

## Конфигурация

## Инварианты

## Граничные случаи и ошибки

## Golden-примеры

## Известные отклонения

## Открытые вопросы
```

Статус «к реализации» замораживает спеку: содержательная правка после этого
возвращает статус в «черновик».

## Чек-лист спецификатора — перед статусом «к реализации»

- [ ] каждое утверждение наблюдаемо и проверяемо тестом;
- [ ] внешние границы дословны: golden, имена операций протокола;
- [ ] секретов и живых данных нет ни в тексте, ни в фикстурах;
- [ ] самодостаточность: ссылки только в `ts/docs/`;
- [ ] объём — одна сессия реализации, иначе дробить;
- [ ] термины сверены с `glossary.md`, новые — внесены;
- [ ] golden-примеры: happy path, ошибка, граница; по одному на класс;
- [ ] у каждого ключа/поля вывода назван источник значения;
- [ ] сказано, чем оканчивается вывод каждой поверхности stdout;
- [ ] голден побайтово равен требуемому выводу. Снятый с рабочей версии голден
      сверить со спекой: разошлись — либо спека неверна (править спеку), либо
      это отклонение с вердиктом fix (нормализовать голден и перечислить в
      спеке, что именно нормализовано). Голден, показывающий поведение, которое
      воспроизводить запрещено, — ловушка: реализующая сессия либо встанет на
      противоречии, либо подгонит код под него.

## Правила для изолированной Deno-сессии

- Спека — единственный источник истины о поведении и **read-only**: реализацию
  подгоняют под спеку, не наоборот. Правки спеки вносит сессия-спецификатор по
  отчёту Deno-сессии.
- Спека противоречива или молчит о поведении с функциональным значением —
  остановиться и спросить; проверить оригинал негде.
- Молчание спеки об устройстве или форме без функционального значения — свобода:
  проектируется заново по правилам модуля.
- «Известные отклонения» с вердиктом `fix` — реализуется правильное поведение;
  воспроизведение старой ошибки — дефект. `preserve` — сопровождается в коде
  комментарием с причиной из спеки.
- Доменные имена — из `glossary.md`; нового термина нет — выбрать имя и пометить
  в отчёте для внесения.
- Нужные **golden-фикстуры** копируются в тестовый каталог пакета: тесты
  самодостаточны, источник истины — спека.
- Файл канала, который читает сам код (закрытый список публикации тулов), **не
  копируется**: он импортируется из канала напрямую. Копия здесь не даёт
  самодостаточности — она даёт два источника истины и требует теста, стерегущего
  их совпадение. Канал лежит в том же репозитории и попадает в бинарь статическим
  импортом.
