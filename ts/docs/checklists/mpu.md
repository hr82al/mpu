# Чек-листы качества в mpu: откуда, как применять, проектный слой

Файлы `README.md`, `statement.md`, `design.md`, `review.md`, `practices.md`,
`research.md` — **побайтовые копии** универсального набора (чек-листы в стиле
Кея: объекты со своей памятью, решает получатель, позднее связывание,
null-объекты). Источник у набора один, вне этого репозитория; копия лежит здесь,
потому что изолированная сессия видит только `ts/`. Копии не правятся: правка —
в источнике, затем повторное копирование спецификатором. Проектный слой mpu —
`statement-mpu.md`, `design-mpu.md`, `review-mpu.md` в этом же каталоге;
применяется **после** универсального файла к тому же артефакту.

Проверка совпадения (делает спецификатор перед каждой постановкой; вывод пуст):

```bash
diff -r -x mpu.md -x '*-mpu.md' ~/mr/mp/.claude/skills/proc-ak-ts/checklists ts/docs/checklists
```

## Обязательность

Любая работа с кодом mpu идёт по этим чек-листам — без напоминания. Пункт без
записи «что изменил / ничего» не применён; «рассмотрел и отверг» без причины по
конкретному случаю — не ответ; находку «структура» нельзя отклонить без
встречного дизайна. При расхождении с `ts/CLAUDE.md` действует этот набор;
расхождение, которое здесь не разрешено, — вопрос в отчёте, не молчаливый выбор.

## Кто что делает в mpu

| Шаг | Кто | Артефакт и где лежит |
|---|---|---|
| постановка: `statement.md` → `statement-mpu.md` | спецификатор | раздел «Сценарии» спеки и текст постановки в ячейке |
| спецификация: `design.md` → `design-mpu.md` | спецификатор | спека в `docs/specs/` с пометками `[D.n]` и разделом «Пункты чек-листа» |
| код | изолированная сессия | `src/`, тесты |
| рецензия: `review.md` → `review-mpu.md` | субагент изолированной сессии со свежим контекстом (не автор) | файл `.tmp/review-<порция>.md`; путь и сводка — в отчёте |
| доводка | изолированная сессия | коммиты; в отчёте — судьба каждой находки |

Если изолированная сессия проектирует сама то, о чём спека молчит (свобода
устройства), она пишет `design.md`-артефакт в `.tmp/design-<порция>.md` **до
кода** и прикладывает путь к отчёту.

## Ядро — дословно в каждую постановку и каждый досыл

- Объект со своей памятью: запись с полями + свободные функции над ней — не
  объект; `rec.count++` снаружи — находка «структура».
- Решает получатель: особый случай — отдельная реализация, а не ветка по виду;
  `switch` по union — только для данных на границе контракта.
- Позднее связывание и null-объект вместо проверок `typeof`/`instanceof`/`null`
  в логике (один null-объект на модуль).
- Голые данные (строка-код, булев флаг поведения, кортеж) → протокол.
- Постановка — сценарии «дано → ожидается» литералами, без устройства решения;
  рецензию делает не автор, чистым контекстом.
- «Рассмотрел и отверг» — не ответ: причина по конкретному случаю. Пункты «на
  всякий случай» не добавлять.
