# Практики качественного кода — универсальные, не зависят от проекта

Выведены эмпирически (слепые тесты: кодировщики с разными чек-листами против эталонного
дизайна, два независимых анонимных судьи). Переносимы в любой проект как есть.

## 1. Постановка сильнее любого чек-листа
- Постановка описывает **только наблюдаемое поведение**: примеры «дано → ожидается», инварианты
  как факты, таблицы для правил вместо формул.
- **Никакой структуры решения** в условии: ни «какие модули», ни «кто кого вызывает», ни «как
  хранить». Утечка архитектуры из постановки перевешивает все принципы.
- **Нефункциональные требования — явно** («это должно быть дёшево», «это должно быть
  неизменяемым», «повторная доставка не меняет результат»). Без них соответствующие решения не
  появятся.
- Отдельный проход «судья утечки» по тексту — необходим, но недостаточен: дополнительно
  контрольный исполнитель без подсказок; если он воспроизвёл решения эталона — постановка их
  выдаёт.

## 2. Правило = триггер + действие + артефакт
- Вопросы («всё ли объект?») работают только на сильной модели; слабая отвечает «да» и идёт
  дальше.
- Формулировать правила так, чтобы их нельзя было «пройти» без результата: *«если в функции
  есть особый случай → выпиши его в список; каждый — отдельная реализация или строка с
  причиной, почему нет»*.
- «Рассмотри…» — не правило, а ритуал: исполнитель «рассмотрел и отверг».

## 3. Обязательный след «пункт → что изменил»
- Любое применение чек-листа даёт артефакт: для каждого пункта — что именно он заставил
  изменить, или честное «ничего».
- Это встроенная абляция: пункты с «ничего» у всех — шум, удалять.

## 4. Ограничитель — внутри, а не отдельным проходом
- Принципы, ведущие в одну сторону («убери `null` → объект»), дают разрастание. Но отдельный
  проход «убрать лишнее» ПОСЛЕ — вреден: режет настоящие null-объекты по формальным признакам.
- Работает только ограничитель внутри проектирования: сценарий использования как рассказ до и
  после; после — не длиннее; каждый объект — роль в одну фразу.

## 4a. Слабой модели нужна рецензия, а не чек-лист
- Чек-лист проектирования на слабой модели один — слабее сильной модели без чек-листа;
  проектирование + рецензия по списку нарушений — уровень сильной модели без чек-листа или
  выше. Рецензия — сильной моделью.

## 5. Таблица «сообщение → кто решает»
- В спецификации — обязательная таблица: каждая операция и кто принимает решение. Решение по
  чужим данным = перенести к владельцу данных.
- Самые сильные попадания в эталон — именно здесь.

## 6. Анти-примеры из живого кода
- 2–3 настоящих фрагмента «так нельзя → вот так» действуют лучше абстрактного пункта: модель
  узнаёт паттерн быстрее, чем применяет правило.

## 7. Слепой судья против эталона
- Сравнивать работу с эталоном анонимно, двумя независимыми судьями, по списку конкретных
  решений эталона (попал/не попал), а не «нравится».
- Судьи сходятся почти полностью — это дешёвый и надёжный инструмент.
- Для кода — golden-корпус; для дизайна — эталонный фрагмент.

## 8. Сценарий как метрика
- Написать сценарий использования как рассказ до и после доводки. Длиннее или больше объектов
  на строку — переусложнено.
