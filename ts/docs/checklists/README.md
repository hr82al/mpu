# Чек-листы качества: что, зачем, как пользоваться

Три момента в работе над задачей — три чек-листа. Набор перенесён из проекта zel
(`~/mr/ws/zel/docs/checklists/`), переписан на язык TypeScript и проверен слепым экспериментом
на TS-эталонах стиля Кея; запись замера — `research.md`. Пункты, не давшие эффекта, удалены;
формы, которые вредили, — в «Не делать».

## Файлы

| Файл | Когда | Кто применяет | Что должно появиться |
| --- | --- | --- | --- |
| `statement.md` | до проектирования — пишем постановку | сильная модель (хост) | постановка по разделам: сценарии «дано → ожидается», инварианты, таблицы правил, границы, свойства решения; для нового узла — контрольный исполнитель |
| `design.md` | до кода — пишем спецификацию | сильная модель (или слабая + обязательная рецензия) | spec с пометками `[D.n]` у решений, таблицы из пунктов (примитивы; особые случаи → реализации; «сообщение → кто решает»), раздел «Пункты чек-листа» |
| `review.md` | после кода — рецензия перед доводкой | сильная модель, чистый контекст | `review.md`: находки `[R.n]` с местом, нарушением, исправлением; структурные помечены «структура»; раздел «Пункты чек-листа» |
| `*-<проект>.md` (в skill поставки, образец `proc-ozon-cl/checklists/*-ozon.md`) | сразу после соответствующего универсального | те же | добавка к тому же артефакту; пункты ссылаются на документы проекта |
| `practices.md` | всегда, фон | — | — |
| `research.md` | при сомнении «зачем этот пункт» | — | таблицы замера, что и почему удалено |

Универсальные файлы не содержат ничего про конкретный проект — дом у них один: skill `proc-ak-ts`.
Проектные выводятся из документов проекта (инварианты, решения `D-*`, главный документ вертикали)
и живут в skill той поставки, которая их применяет. Перенос на другой язык — раздел «Адаптация» в zel `INTEGRATE.md`.

## Порядок на одной задаче

1. **Постановка** по `statement.md` → `statement-<проект>.md`. Результат — текст, по которому
   можно написать тесты, не задав ни одного вопроса, и в котором нет ни слова об устройстве
   решения.
2. **Спецификация** по `design.md` → `design-<проект>.md`. Результат — spec с обязательными
   артефактами. Код — только после неё.
3. **Код** по spec (любой моделью).
4. **Рецензия** по `review.md` → `review-<проект>.md` (сильная модель, свежий контекст —
   не автор). Результат — `review.md`.
5. **Доводка** по рецензии (любой моделью). Находку «структура» нельзя отклонить без встречного
   дизайна.

В поставке `ozon` шаги 1–2 делает хост, 3 — изолированная сессия-исполнитель, 4 — та же сессия
после `/clear`, 5 — она же после второго `/clear`; артефакты лежат в `~/tmp/checklist-k<N>/`.

## Три правила, без которых чек-листы не работают (замерено)

- **Артефакт обязателен.** Пункт без записи «что изменил / ничего» — ритуал. Раздел «Пункты
  чек-листа» в конце spec и review — не формальность, а то, по чему видно, что чек-лист применён,
  и встроенная абляция: пункт с «ничего» три задачи подряд удаляется.
- **«Рассмотрел и отверг» — не ответ.** Нужна строка с конкретной причиной по конкретному случаю.
- **Слабой модели нужна рецензия, а не чек-лист.** Чек-лист проектирования сам по себе на слабой
  модели даёт меньше, чем сильная без чек-листа; с рецензией сильной — столько же или больше.

## Не делать

- Отдельный проход «убрать лишнее» после рецензии: режет настоящие null-объекты по формальным
  признакам. Мера — внутри `design.md` п. 7 (сценарий не длиннее).
- Переписывать пункты в вопросы («всё ли объект?») — на слабой модели не работают.
- Добавлять пункты «на всякий случай»: пункт, три задачи подряд дающий «ничего», удаляется.
- Давать чек-лист без требования артефакта — превращается в ритуал.
