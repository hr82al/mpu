# mpu telegram log — персональный канал уведомлений через Bot API

Дата: 2026-08-20
Статус: дизайн одобрен, реализация не начата

## Задача

Отправлять себе персональные уведомления и заметки так, чтобы их текст не
становился доступен ни другим людям, ни агентам, читающим журнал вызовов.

Существующая группа `mpu telegram` для этого не годится: она шлёт от имени
личного аккаунта (MTProto), поэтому чат с адресатом остаётся достижим для
`telegram ls` и `telegram search`, а текст позиционного аргумента `send`
попадает в `~/.config/mpu/mpu.log` дословно — маскирование в
`platform/invoke-log.md` работает только по именам опций, а у позиционного
аргумента имени нет.

## Модель угрозы

Что защищаем — текст уведомления. От кого:

1. **Другие пользователи бота.** Закрыто свойством Bot API: сообщение
   доставляется в конкретный `chat_id`, у бота нет общей истории, посторонний
   видит только собственный диалог. Условие, без которого гарантия ломается:
   адресат не должен выбираться динамически. Отсюда — единственный адресат из
   env, отсутствие опции выбора чата и полный отказ от чтения апдейтов
   (`getUpdates`, webhook).
2. **Агенты с доступом к MCP-серверу mpu.** Профиля `ro` достаточно, чтобы
   прочитать журнал тулом `logs`. Закрывается маскированием аргументов.
3. **История shell и `ps`.** Закрывается тем, что токен живёт только в
   env-файле и никогда не передаётся аргументом.

Что НЕ защищаем и почему: уведомления, отправленные агентом через MCP-тул,
проходят через его контекст — это следствие сознательного решения дать тулу
rw-доступ ради сценария «сообщи, когда закончишь».

## Конфигурация

Ключи `~/.config/mpu/.env` (слой `platform/env-file.md`), все уже заведены:

| Ключ | Обязателен | Роль |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | да | токен бота в URL запроса |
| `TELEGRAM_BOT_ID` | да | `chat_id` получателя — личный id оператора |
| `TELEGRAM_BOT_NAME` | нет | username бота; только в тексте ошибки |

Конфигурация бота читается **отдельно** от `telegramConfig()`
(`src/telegram/config.ts`). Смешивать нельзя: та требует `TELEGRAM_SESSION` и
`TELEGRAM_API_ID`/`TELEGRAM_API_HASH`, а отправка в бота от сессии не зависит —
иначе неавторизованный `mpu init` блокировал бы работающий канал.

Отсутствующий или пустой обязательный ключ → ошибка слоя env-файла, exit 1.
Нечисловой `TELEGRAM_BOT_ID` → `telegram: TELEGRAM_BOT_ID должен быть
числом, получено '<строка>'`, exit 1. Ведущий минус допустим: так выглядят id
групп и каналов.

## CLI-контракт

```
mpu telegram log MESSAGE
```

- `MESSAGE` — позиционный, обязателен. Значение `-` означает «весь stdin».
  Пустая строка (в том числе пустой stdin) → ошибка ввода, exit 2.
- Опции выбора адресата нет намеренно (см. «Модель угрозы», п. 1).
- Вложений, Markdown-разметки, ретраев нет — YAGNI.

stdout — одна строка JSON без отступов, за ней перевод строки:

```
{"id": 5000001}
```

`chat_id` в вывод не идёт сознательно: секция `out` журнала пишется, и адресат
оказался бы в ней.

## Ошибки

- Ответ Telegram с `ok: false` → `telegram: bot API <error_code>
  <description>`, exit 1.
- `403` (бот заблокирован) и `400 chat not found` → тот же формат плюс
  подсказка написать боту `/start`: на старте это единственная реальная
  причина. Имя бота в подсказке берётся из `TELEGRAM_BOT_NAME`, если задан.
- Тело ответа не разбирается как JSON → `telegram: bot API вернул не
  JSON: <первая строка>`, exit 1. Молча считать такой ответ успехом нельзя:
  на том конце шлюз или заглушка, а не Bot API.
- Сбой вызова (сеть, предел времени) → `telegram: bot API недоступен:
  <причина одной строкой>`, exit 1.

## Архитектура

Новый транспорт внутри группы `telegram`, не пересекающийся с MTProto-частью:
общий у них только реестр. Ни сеанс (`session.ts`), ни резолв адресата
(`peer.ts`, `resolve.ts`), ни план отправки (`plan.ts`) командой не
используются — изоляция каналов структурная, а не дисциплинарная.

| Файл | Ответственность |
|---|---|
| `src/telegram/bot_config.ts` | чтение и проверка трёх ключей → `BotConfig` |
| `src/telegram/bot.ts` | `sendBotMessage(config, text, apiBase?)` — один POST |
| `src/telegram/cmd_log.ts` | разбор аргументов, stdin, печать результата |
| `src/telegram/mod.ts` | экспорт `telegramLogCommand` |

Транспорт — POST на `https://api.telegram.org/bot<TOKEN>/sendMessage`, тело
`{chat_id, text}`, **поверх платформенного шва `src/http/mod.ts`**
(`httpSend`): им же ходят Kaiten, Portainer и Loki, и от него команда
бесплатно получает два предела времени и причину отказа одной строкой.
Отдельной библиотеки Bot API не нужно — это JSON поверх HTTP. `@mtcute/deno`
не задействован: другой протокол, другая модель доступа, и старт команды не
платит за wasm-крипту MTProto.

Ошибки — существующими фабриками слоя (`src/telegram/errors.ts`): `inputError`
(`VerbatimUsageError`, exit 2) и `configError` (`VerbatimError`, exit 1). Обе
дают префикс `telegram: ` без имени подкоманды — так устроен весь слой.
`telegramFailure` не годится: он разбирает исключение MTProto и оформляет его
как `RPC error: …`.

Базовый адрес — параметр с умолчанием, а не константа внутри: тесту нужна
петля, наружу сети у него нет.

## Изменения вне группы telegram

**1. `src/invokelog/` — маскирование аргументов по решению реестра.**

Спец команды (`src/command/mod.ts`) получает `logsArguments?: boolean`
(умолчание `true`) — рядом с существующим `logsOutput`. Помеченная команда
пишется в журнал как

```
$ mpu telegram log REDACTED
```

— все аргументы после пути команды заменяются маской; у MCP-вызова JSON
аргументов заменяется маской целиком. Секции `out`/`err` сохраняются: там
только id сообщения и текст ошибки.

Механизм существующий: политика уже доезжает до `finish`
(`src/invokelog/mod.ts:148`), где собирается строка через `lineOf`. `OutputPolicy`
получает `logsArguments` и `path` — по длине пути маска отделяет аргументы от
имени команды. CLI-путь (`src/entrypoint/mod.ts:340`) правки не требует: туда
передаётся сам `Command`. MCP-путь (`src/mcp/native_tool.ts:17`) собирает
политику литералом — там поля добавляются явно.

Спека `platform/invoke-log.md` дополняется абзацем в разделе «Инварианты»:
маскирование по имени опции остаётся правилом по умолчанию, маскирование
аргументов — явная пометка отдельных команд.

**2. Реестр и политики тулов.**

Регистрация в `src/registry/mod.ts`; образец вызова в
`src/registry/contract_test.ts`; тул добавляется в rw-профиль
(`docs/specs/fixtures/mcp-server/tool-policies.json`). В ro-профиль не
попадает: команда отправляет сообщение.

**3. Спека команды.**

`ts/docs/specs/telegram-log.md` по образцу `telegram-send.md`.

## Тестирование

Сеть наружу в тестах запрещена; право теста — `--allow-net=127.0.0.1`.

- **Транспорт**: `Deno.serve` на петле, базовый адрес передаётся параметром.
  Успех; форма запроса (токен в пути, `chat_id` и текст в теле); `ok:false` с
  кодом и описанием; `403` с подсказкой и с именем бота; `chat not found` без
  имени; ответ не-JSON; закрытый порт — причина одной строкой.
- **Конфигурация**: фейковый env. Оба ключа; каждый обязательный отсутствует
  по отдельности; пустое имя бота; нечисловой и отрицательный `TELEGRAM_BOT_ID`.
- **Команда**: аргумент отсутствует; пустая строка; пустой stdin; `-` и stdin;
  stdin не читается при обычном аргументе.
- **Маскирование**: помеченная команда (аргументы под маской, путь цел),
  непомеченная (правило по именам опций не изменилось), помеченный тул.
- **Фикстуры**: golden-пара канал/копия для stdout и stderr пустого текста.

## Что сознательно отложено

Вложения, Markdown, выбор адресата, приём апдейтов, ретраи при `429`,
несколько получателей. Каждое — отдельная задача со своим обоснованием.
