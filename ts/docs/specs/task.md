# mpu task

Статус: к реализации (спроектирована 2026-08-28 в диалоге с владельцем;
решения диалога перечислены в «Известных отклонениях» и «Открытых вопросах»)

## Назначение

Канал передачи работы между двумя ролями — **спецификатором** (пишет спеку и
постановку порции, не пишет код) и **исполнителем** (пишет код строго по спеке,
не видит ни оригинала, ни прода). Третья роль — **оператор**, человек: запускает
сессии и принимает результат.

Канал заменяет файл-ячейку `ts/.tmp/buf.txt`: тот жил в одном репозитории, знал
один проект и требовал, чтобы обе стороны видели один каталог. `mpu task` живёт
в кэш-БД (`platform/store.md`), обслуживает произвольное число проектов
одновременно и работает на машине, где нет ничего, кроме бинаря `mpu`.

Через канал ходят четыре вида сообщений: постановка (`task`), отчёт (`report`),
вопрос исполнителя (`question`), ответ спецификатора (`answer`).

## CLI-контракт

Имя проекта — первый позиционный аргумент **каждой** команды, кроме `setup`
без аргумента, `status` и `history`, где оно необязательно. Умолчания нет:
ни из окружения, ни из каталога запуска. Два проекта с похожими именами не
должны различаться тем, откуда команду набрали.

```
mpu task setup [ИМЯ [--note ТЕКСТ]]
mpu task post    ИМЯ ФАЙЛ|- [--force]
mpu task report  ИМЯ ФАЙЛ|-
mpu task ask     ИМЯ (ФАЙЛ|- | -m ТЕКСТ)
mpu task answer  ИМЯ (ФАЙЛ|- | -m ТЕКСТ)
mpu task read    ИМЯ [--kind ВИД] [--keep-unread]
mpu task status  [ИМЯ]
mpu task wait    ИМЯ ВИД [СЕК]
mpu task history [ИМЯ] [-n ЧИСЛО]
mpu task history clear [ИМЯ]
```

`ВИД` — одно из `task`, `report`, `question`, `answer`.

- `setup` без имени печатает инструкцию по заведению проекта (состав — ниже, в
  «Ввод/вывод») и завершается кодом 0. С именем — заводит проект и печатает ту
  же инструкцию; повторный `setup` того же имени обновляет `--note` и не
  является ошибкой.
- `post` начинает **новую порцию**: её номер на единицу больше максимального в
  проекте. `report`, `ask`, `answer` прикрепляются к текущей (максимальной)
  порции; если порций нет ни одной, они отвечают отказом — порцию открывает
  только `post`.
- `read` печатает тело последнего сообщения проекта (или последнего сообщения
  вида `--kind`) и помечает его прочитанным. `--keep-unread` печатает, не
  помечая: для случая «посмотреть, не забирая».
- `status` печатает по строке на проект: имя, номер текущей порции, вид
  последнего сообщения, его возраст, признак непрочитанного и `--note`.
- `wait` блокируется до появления **непрочитанного** сообщения указанного вида,
  печатает его тело и помечает прочитанным. `СЕК` — предел ожидания, по
  умолчанию 3600.
- `history` печатает журнал проекта (или всех проектов) от свежего к старому:
  порция, вид, время, первая строка тела. `-n` ограничивает число строк.
- `history clear` удаляет из журнала всё, кроме текущей порции проекта; без
  имени — по всем проектам.

## Ввод/вывод

Тело сообщения приходит файлом, из stdin (`-`) либо строкой `-m`. Пустое тело
(после обрезки пробельных символов) — ошибка ввода. Тело хранится и печатается
дословно, включая завершающие переводы строк.

stdout — данные: тела сообщений, строки `status` и `history`. stderr —
диагностика и ошибки в форме `mpu task <подкоманда>: <причина>`, без
трейсбеков.

`setup` печатает инструкцию из четырёх разделов, в этом порядке: **роли и зачем
они нужны**; **как запустить исполнителя изолированно** (отдельный рабочий
каталог, режим разрешений, чего сессии быть не должно — боевых ключей, соседних
проектов, каталога оригинала); **что скопировать в инструкцию проекта** (пять
строк про источник истины, канал, ожидание после отчёта, вопрос вместо догадки,
живую проверку на стороне спецификатора); **первый цикл целиком командами**.
Пятым идёт короткий раздел частых ошибок: одинаковые имена проектов, постановка
поверх неотработанной, сессия, ждущая собственное сообщение.

## Побочные эффекты

Запись в кэш-БД `~/.config/mpu/mpu.db` (`platform/store.md`): вставка строки в
`task_messages`, при `setup` — в `task_projects`, при любой записи — чистка
журнала (ниже). Сети нет ни у одной подкоманды. Файлы читаются только как
источник тела сообщения.

`wait` опрашивает базу раз в 2 секунды; между опросами соединение не
удерживается, поэтому ожидание не мешает записи с другой стороны.

## Конфигурация

`MPU_TASK_HISTORY` — глубина журнала: число (сколько порций хранить) либо `all`
(не чистить). Не задана — три порции. Это единственная переменная окружения,
которую читает команда, и она задаёт режим отладки, а не предпочтение: правило
«цель и настройки задаются явно, не окружением» (`platform/config.md`) не
нарушается.

Нечисловое значение, отличное от `all` → отказ, exit 2, до записи.

## Инварианты

- Состояние канала нигде не хранится отдельно: «в канале лежит постановка»
  тождественно «последнее сообщение проекта имеет вид `task`». Второго
  источника правды о состоянии не существует.
- Номера порций проекта монотонны и не переиспользуются; `post` — единственная
  подкоманда, увеличивающая номер.
- Сообщение неизменяемо: правок и удалений отдельных сообщений нет, есть только
  чистка целыми порциями.
- Чистка выполняется в той же транзакции, что и запись, и оставляет ровно N
  последних порций проекта (N — из `MPU_TASK_HISTORY`, по умолчанию 3).
  Текущая порция не удаляется никогда: `MPU_TASK_HISTORY=0` означает «только
  текущая», а не «пусто».
- `read` и `wait` помечают прочитанным ровно то сообщение, которое напечатали.
- Проект, не заведённый `setup`, не создаётся ни одной другой подкомандой.
- Ни одна подкоманда не открывает сетевых соединений.

## Граничные случаи и ошибки

- Неизвестный проект → `нет проекта '<имя>'; заведи: mpu task setup <имя>`,
  exit 2.
- `post` при последнем сообщении вида `task` → `порция <N> не отработана;
  перезаписать — --force`, exit 1. С `--force` постановка кладётся, номер
  порции **не** увеличивается: это замена невзятой постановки, а не новая
  порция.
- `report`, `ask`, `answer` в проекте без порций → `порций ещё нет; начни с
  mpu task post <имя>`, exit 2.
- Пустое тело → `пустое тело сообщения`, exit 2, запись не делается.
- `read`/`wait` с неизвестным видом → `неизвестный вид '<в>'; допустимо: task,
  report, question, answer`, exit 2.
- `read` в проекте без сообщений → пустой stdout, exit 0: пусто — это состояние,
  а не отказ.
- `wait` исчерпал предел → `ожидание <вид> в '<имя>' истекло за <СЕК>s`, exit 1.
- `wait` при уже прочитанном сообщении нужного вида **не** возвращается сразу:
  ждёт следующего непрочитанного. Иначе сессия просыпается на собственном
  сообщении.
- База недоступна на запись (нет прав, нет каталога) → сообщение слоя хранилища
  с путём, exit 1. Чтение при отсутствующей базе работает и даёт пустой
  результат.

## Golden-примеры

`fixtures/task/`:

- `setup.stdout` — инструкция целиком (эталон текста, который читают на чистой
  машине);
- `status-two-projects.stdout` — обзор при двух проектах: у одного лежит
  непрочитанная постановка, у другого прочитанный отчёт;
- `history.stdout` — журнал трёх порций одного проекта;
- `err-unknown-project.stderr`, `err-unhandled-portion.stderr`,
  `err-empty-body.stderr` — три отказа.

Голдены снимаются с реализации: оригинала у команды нет, differential не с чем
сверять. Эталон формы задаёт эта спека, а фикстуры фиксируют её дословно.

## Известные отклонения

Команда новая, оригинала в Python-реализации у неё нет. Отклонения — от
прежнего файлового канала (`ts/handoff/`), который она заменяет:

- **fix** — канал знает произвольное число проектов; прежний обслуживал один и
  различал стороны только маркером первой строки.
- **fix** — вопросы и ответы ходят тем же каналом. Прежде они шли живой
  перепиской между сессиями, то есть требовали среды, где такая переписка
  возможна; на чистой машине схема была неполной.
- **fix** — состояние выводится из журнала, а не хранится полем. У прежнего
  канала состоянием была первая строка файла, и «текущее» с «историей» жили бы
  в двух местах.
- **preserve** — защита от затирания неотработанной постановки и флаг `--force`
  перенесены как есть: механика уже показала себя на живой работе.
