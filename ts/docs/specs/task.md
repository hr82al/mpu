# mpu task — канал работы между ролями (порция T1)

Статус: к реализации — порция T1 серии оркестратора (переписана хостом
2026-09-25 под грамматику строки: прежняя редакция 2026-08-28 — позиционные
аргументы и флаги — снята; полная проверка 2026-09-25 автором по списку).

## Назначение

Канал передачи работы между ролями проекта: **хост** (спецификатор: спека,
постановка, приёмка), **исполнитель** (код строго по спеке), **человек**
(владелец: правила проекта и ответы на вопросы). Канал живёт в кэш-БД
(`platform/store.md`), обслуживает любое число проектов и не требует общего
каталога: на машине, где есть только `mpu`, схема работает целиком. Порция
T1 заменяет ячейку `deno task handoff` каналом; оркестратор (профили, тик,
окна) — порции T2–T3 поверх него.

Единица работы — **порция**: её открывает постановка (`task`), закрывает
отчёт (`report`), между ними — вопросы и ответы. Решения и правила проекта
лежат в том же журнале и собираются одним документом (`decisions`).

## Виды сообщений

| Вид | Пишет | Сообщение группы | Что |
|---|---|---|---|
| `task` | хост | `post` | постановка; открывает порцию N+1 |
| `report` | исполнитель | `report` | отчёт о текущей порции |
| `question` | исполнитель | `question` | вопрос по текущей порции |
| `answer` | хост | `answer` | ответ на вопрос |
| `decision` | хост | `decision` | вопрос, решение и правило, по которому решено |
| `owner` | хост | `owner` | вопрос владельцу, не решённый правилами; открыт до ответа |
| `owner-answer` | только человек | `owner-answer` | ответ владельца; закрывает последний открытый `owner` |
| `rule` | только человек | `rule` | правило проекта; действует последняя редакция |

`question` вместо прежнего `ask`: слово `ask` — дверь строки
(`platform/ask-door.md`), сообщение с тем же именем читалось бы как она.

## CLI-контракт

Проект — ключ `project:` (имя проекта не номер сущности, поэтому не `id:`).
Тело — ключ `text:` (одно слово; из нескольких — `^…^`; `stdin` — ввод
строки) или `file:` (путь файла), ровно одно из двух — как у `run-js`.

```
mpu task setup [project: <имя> [note: <текст>]]
mpu task rules
mpu task post [force] project: <имя> text:|file: …
mpu task report|question|answer|decision|owner project: <имя> text:|file: …
mpu task owner-answer|rule project: <имя> text:|file: …
mpu task read [keep] project: <имя> [kind: <вид>]
mpu task wait project: <имя> kind: <вид> [timeout: <сек>]
mpu task status [project: <имя>]
mpu task history [project: <имя>] [limit: <число>]
mpu task history clear [project: <имя>]
mpu task decisions project: <имя> [query: <слово>] [limit: <порций>]
```

- `setup` без ключей печатает инструкцию по заведению проекта (состав — в
  «Вывод»), код 0; с `project:` — заводит проект и печатает ту же
  инструкцию; повтор того же имени обновляет `note:`.
- `rules` печатает правила письма спецификаций (состав — в «Вывод»); ключей
  нет, состояния не читает.
- `post` открывает порцию с номером на единицу больше максимального в
  проекте. Вариант `force` — заменить неотработанную постановку (последнее
  сообщение — `task`), номер не растёт; `force`, когда последнее — не
  `task`, — отказ, код 1 (заменять нечего; текст — исполнителя, голден).
- Прочие виды прикрепляются к текущей (максимальной) порции.
- `read` печатает тело последнего сообщения проекта (или последнего вида
  `kind:`) и помечает прочитанным; вариант `keep` — не помечать.
- `wait` ждёт непрочитанного сообщения вида `kind:`, печатает тело, помечает
  прочитанным; `timeout:` — секунды, умолчание 3600.
- `status` — строка на проект; `history` — журнал от свежего к старому;
  `history clear` — удалить всё, кроме текущей порции.
- `decisions` — один документ: последняя редакция каждого правила (`rule`),
  затем `decision`, `owner` и `owner-answer` последних `limit:` порций
  (умолчание 5) свёрнуто по порциям; `query:` — в порциях только сообщения,
  где слово встречается (без учёта регистра), по всему журналу; раздел
  правил печатается всегда — действующие правила нужны каждому решению.
- `status`, `history`, `decisions` — записи: `end json` печатает массив
  записей (поля — в «Вывод»).

**Правила.** Путь правила — `task <сообщение>` (`history clear` — режим
команды `history`, путь правила `task history clear`). Посев: чтение (`rules`,
`read`, `wait`, `status`, `history`, `decisions`) — `allow`; `post`,
`report`, `question`, `answer`, `decision`, `owner` — `allow` (роли пишут
без человека; запись — в локальный журнал, не наружу; строки таблицы посева
`platform/policy.md`, как `image export`); `setup`, `history clear` —
`ask`. `rule` и `owner-answer` — жёсткий запрет вне правил, как `allow:`
(`platform/policy.md`): всегда вопрос каналу, текст `записать от имени
владельца: <вид> в <проект>? [y/N] `; канал без человека — отказ `писать
<вид> может только человек`, код 1, журнал не меняется.

## Вывод

stdout — данные; stderr — `mpu task <сообщение>: <причина>`. Тело хранится и
печатается побайтово как подано (с завершающими переводами строк).

- `read`/`wait` — тело как есть.
- `status` — по строке на проект, поля через два пробела:
  `<проект>  порция <N>  <ход>  <вид последнего>  <возраст>  <непрочитано|->  <заметка>`;
  ход — `ждёт исполнителя` (последнее из `task`, `answer`), `ждёт хоста`
  (`report`, `question`), `ждёт владельца` (последний `owner` без
  `owner-answer` после него — важнее двух прочих), `остановлен` (последнее
  из `stop`/`resume` — `stop`, порция T3; важнее всех), `-` — пустой проект;
  возраст — `<N>s|m|h|d`. `end json`: `{"project","portion","turn","last",
  "age_s","unread","note"}`.
- `history` — строка на сообщение: `<проект>  <N>  <вид>  <время ISO>  <первая
  строка тела>`. `end json`: `{"project","portion","kind","at","first_line"}`.
- `decisions` — markdown: `## Правила` (тело последнего `rule`), затем
  `## Порция <N>` и под ним `- <вид>: <тело>` в порядке журнала.
  `end json`: `{"rules": "<тело>|null", "portions": [{"portion", "items":
  [{"kind","at","text"}]}]}`.
- `setup` — инструкция из пяти разделов: роли и правило единственного входа
  (работу открывает только постановка; переписка сессий ничего не делает
  обязательным, минуя спеку); изоляция исполнителя; строки для CLAUDE.md
  проекта; первый цикл командами (`setup` → `post` → `read`/`report` → `wait`);
  частые ошибки. Последняя строка раздела 1 — «перед первой спекой прочитай
  `mpu task rules`».
- `rules` — текст `fixtures/task/rules.txt` побайтово (положил хост:
  четырнадцать правил письма спецификаций с причинами).

Текст `setup` — голден `fixtures/task/setup.txt`: снимает исполнитель,
замораживает хост. `rules.txt` — эталон хоста, код печатает его как есть.

## Побочные эффекты

Кэш-БД `~/.config/mpu/mpu.db`: таблицы проектов и сообщений (схема — у
исполнителя); при записи — чистка журнала в той же транзакции. Файл `file:`
только читается. Сети нет. `wait` опрашивает базу раз в 2 с и соединение
между опросами не держит.

## Конфигурация

Глубина журнала — ключ конфига `task.history` (int, умолчание 3 порции; `0` —
только текущая; `-1` — не чистить; `platform/config.md`, закрытый реестр —
седьмой ключ). Прежняя переменная `MPU_TASK_HISTORY` не читается: env-слоя у
конфига нет.

## Инварианты

- Ход не хранится полем: выводится из журнала.
- Номера порций монотонны; растит номер только `post` без `force`.
- Сообщение неизменяемо; удаляется только чисткой целых порций; текущая
  порция не удаляется.
- `read`/`wait` помечают прочитанным ровно напечатанное.
- Проект создаёт только `setup`.
- `rule`/`owner-answer` не пишутся каналом без человека ни при каком правиле.
- Тело возвращается побайтово равным поданному.
