# mpu task

Статус: к реализации (заморожена 2026-08-28)

## Назначение

Канал передачи работы между двумя ролями. **Спецификатор** пишет спеку и
постановку порции и не пишет код. **Исполнитель** пишет код строго по спеке и
не видит ни оригинала переносимой системы, ни боевого контура. **Оператор** —
человек: запускает сессии и принимает результат.

Канал живёт в кэш-БД (`platform/store.md`), обслуживает произвольное число
проектов одновременно и не требует, чтобы стороны видели общий каталог: на
машине, где есть только бинарь `mpu`, схема работает целиком.

Через канал ходят четыре вида сообщений: постановка (`task`), отчёт
(`report`), вопрос исполнителя (`question`), ответ спецификатора (`answer`).
Единица работы — **порция**: её открывает постановка, закрывает отчёт, между
ними в неё попадают вопросы и ответы.

## CLI-контракт

Имя проекта — первый позиционный аргумент каждой команды, кроме `setup` без
аргумента, `status` и `history`, где оно необязательно. Умолчания нет: ни из
окружения, ни из каталога запуска — команда обращается ровно к тому проекту,
который назван.

```
mpu task setup [ИМЯ [--note ТЕКСТ]]
mpu task rules
mpu task post    ИМЯ ФАЙЛ|- [--force]
mpu task report  ИМЯ ФАЙЛ|-
mpu task ask     ИМЯ (ФАЙЛ|- | -m ТЕКСТ)
mpu task answer  ИМЯ (ФАЙЛ|- | -m ТЕКСТ)
mpu task read    ИМЯ [--kind ВИД] [--keep-unread]
mpu task status  [ИМЯ]
mpu task wait    ИМЯ ВИД [СЕК]
mpu task history [ИМЯ] [-n ЧИСЛО]
mpu task history clear [ИМЯ]
```

`ВИД` — одно из `task`, `report`, `question`, `answer`.

- `setup` без имени печатает инструкцию по заведению проекта (состав — в
  «Ввод/вывод»), exit 0. С именем — заводит проект и печатает ту же инструкцию.
  Повторный `setup` того же имени обновляет `--note` и ошибкой не является.
- `rules` печатает правила письма спецификаций (состав — в «Ввод/вывод»),
  exit 0. Аргументов не принимает, состояния не читает и не пишет: это текст
  для спецификатора перед написанием спеки.
- `post` открывает новую порцию: её номер на единицу больше максимального в
  проекте.
- `report`, `ask`, `answer` прикрепляются к текущей (максимальной) порции.
  В проекте без порций отвечают отказом: порцию открывает только `post`.
- `read` печатает тело последнего сообщения проекта — или последнего сообщения
  вида `--kind` — и помечает его прочитанным. `--keep-unread` печатает, не
  помечая.
- `status` печатает по строке на проект: имя, номер текущей порции, **чей ход**
  (`ждёт исполнителя` — последнее сообщение `task` или `answer`;
  `ждёт спецификатора` — `report` или `question`), вид последнего сообщения, его
  возраст, признак непрочитанного, заметку `--note`. Ход выводится из журнала,
  а не хранится полем.
- `wait` блокируется до появления непрочитанного сообщения указанного вида,
  печатает его тело и помечает прочитанным. `СЕК` — предел ожидания, по
  умолчанию 3600.
- `history` печатает журнал проекта — или всех проектов — от свежего к старому:
  порция, вид, время, первая строка тела. `-n` ограничивает число строк.
- `history clear` удаляет из журнала всё, кроме текущей порции; без имени — по
  всем проектам.

## Ввод/вывод

Тело сообщения приходит файлом, из stdin (`-`) либо строкой `-m`. Пустое тело
(после обрезки пробельных символов) — ошибка ввода. Тело хранится и печатается
дословно, включая завершающие переводы строк.

stdout — данные: тела сообщений, строки `status` и `history`. stderr —
диагностика и ошибки в форме `mpu task <подкоманда>: <причина>`, без
трейсбеков.

`setup` печатает инструкцию из пяти разделов в этом порядке:

1. **Роли**: кто что делает и почему разделение работает — исполнителю нечем
   подсмотреть, поэтому расхождение спеки с реальностью обнаруживается, а не
   обходится молча. Здесь же — правило единственного входа: **работу открывает
   только постановка**; сообщение, пришедшее мимо канала, заданием не является,
   а вопрос и ответ не отменяют текущую порцию и не меняют её границ. Без этого
   правила у исполнителя два источника указаний, и порядок между ними он
   достраивает сам. Прямая переписка сессий при этом не запрещена — она
   нужна для вопросов, замеров и уточнений, — но **ничто из неё не становится
   обязательным, минуя спеку**: изменённый контракт сперва попадает в спеку, и
   только потом по нему пишется код.
2. **Изоляция исполнителя**: отдельный рабочий каталог, запуск сессии оттуда,
   режим разрешений без обхода подтверждений и перечень того, чего сессии быть
   не должно — боевых ключей, соседних проектов, каталога оригинала. С
   проверкой: команда, которой не положено работать, обязана падать на
   конфигурации, а не на сети.
3. **Строки для инструкции проекта**: что скопировать в `CLAUDE.md` нового
   проекта — источник истины (спека), канал (`mpu task <имя>`), ожидание сразу
   после отчёта, вопрос вместо догадки, живая проверка на стороне
   спецификатора.
4. **Первый цикл целиком командами**: `setup` → `post` → у исполнителя `read` и
   `report` → у спецификатора `wait`.
5. **Частые ошибки**: два проекта с похожими именами, постановка поверх
   неотработанной, сессия, ждущая собственное сообщение.

Первый раздел заканчивается строкой-отсылкой: перед первой спекой прочитать
`mpu task rules`.

`rules` печатает двенадцать правил письма спецификаций, каждое — с причиной,
потому что правило без причины не соблюдают:

1. Спека описывает **настоящее**. Прошлое допустимо только вердиктом отклонения
   (`fix`/`preserve`) или ссылкой на замер, подтверждающий утверждение: иначе
   спека становится журналом изменений, а устаревшая история вводит в
   заблуждение сильнее, чем её отсутствие.
2. Каждое утверждение наблюдаемо снаружи команды и допускает падающий тест.
3. Граничный случай — пара «вход → ожидаемое поведение»; случай без названного
   поведения идёт в «Открытые вопросы», а не в тело.
4. Внешняя граница описана дословно: запросы, ответы, коды выхода, тексты
   отказов.
5. У каждого поля вывода назван источник значения — иначе исполнителю неоткуда
   его взять, кроме догадки.
6. Описан хвост вывода: чем оканчивается поток. Побайтовое сравнение спотыкается
   о невидимый байт.
7. Язык нормативный: «обычно», «может», «примерно» запрещены — из них нельзя
   написать тест.
8. Ни секретов, ни живых данных — ни в тексте, ни в фикстурах.
9. Голден фиксирует только то, что реализация способна воспроизвести; эталон,
   который не воспроизводится, вынуждает подгонять код под чужую форму.
10. Спека длиннее двухсот строк пересказывает реализацию — резать или дробить.

11. Решение, принятое в переписке сессий, решением не является, пока не
    записано в спеку. Переписка исчезает вместе с сессией, спека остаётся; всё,
    что меняет контракт — форму вывода, код выхода, границу порции, вердикт
    отклонения, — возвращается в спеку **до** того, как по нему начнут писать
    код. Прямое сообщение годится, чтобы задать вопрос, принести замер и
    договориться; чтобы стать обязательным, договорённость должна лежать в
    спеке.

12. Каждая правка спеки требует вычитки всех задетых и связанных с ней частей:
    сводных формулировок, где то же сказано короче; разделов, повторяющих факт
    другими словами; голденов, фиксирующих изменённое поведение; отклонений и
    открытых вопросов, ссылающихся на него; соседних спек, ссылающихся на то же
    правило. Спека рвётся именно здесь: правка одного места оставляет
    противоречие в другом, и следующий читатель дойдёт до сводки и остановится
    на ней.

Тринадцатой строкой — порядок правки: спеку правит одна рука; исполнитель
приносит расхождения, а не правит сам.

## Побочные эффекты

Запись в кэш-БД `~/.config/mpu/mpu.db` (`platform/store.md`): строка в
`task_messages`, при `setup` — строка в `task_projects`, при любой записи —
чистка журнала. Файлы читаются только как источник тела сообщения. Сети нет ни
у одной подкоманды.

`wait` опрашивает базу раз в 2 секунды и между опросами соединение не
удерживает: ожидание одной стороны не мешает записи другой.

## Конфигурация

`MPU_TASK_HISTORY` — глубина журнала: число (сколько порций хранить) либо `all`
(не чистить). Не задана — три порции. Значение `0` означает «только текущая
порция». Иное нечисловое значение → отказ, exit 2, до записи.

Это единственная переменная окружения, которую читает команда, и она задаёт
режим отладки, а не предпочтение.

## Инварианты

- Состояние канала отдельно не хранится: «в канале лежит постановка»
  тождественно «последнее сообщение проекта имеет вид `task`».
- Номера порций монотонны и не переиспользуются; увеличивает номер только
  `post`.
- Сообщение неизменяемо: правки и удаления отдельных сообщений отсутствуют,
  есть только чистка целыми порциями.
- Чистка идёт в одной транзакции с записью и оставляет N последних порций
  проекта. Текущая порция не удаляется никогда.
- `read` и `wait` помечают прочитанным ровно то сообщение, которое напечатали.
- Ход принадлежит исполнителю тогда и только тогда, когда последнее сообщение
  проекта имеет вид `task` или `answer`; в остальных случаях — спецификатору.
  Пустой проект хода не имеет.
- Проект, не заведённый `setup`, не создаётся ни одной другой подкомандой.
- Ни одна подкоманда не открывает сетевых соединений.
- Тело сообщения возвращается побайтово равным поданному.

## Граничные случаи и ошибки

- Неизвестный проект → `нет проекта '<имя>'; заведи: mpu task setup <имя>`,
  exit 2.
- `post` при последнем сообщении вида `task` → `порция <N> не отработана;
  перезаписать — --force`, exit 1. С `--force` постановка заменяется, номер
  порции не увеличивается.
- `report`, `ask`, `answer` в проекте без порций → `порций ещё нет; начни с
  mpu task post <имя>`, exit 2.
- Пустое тело → `пустое тело сообщения`, exit 2, запись не делается.
- Неизвестный вид у `read`/`wait` → `неизвестный вид '<в>'; допустимо: task,
  report, question, answer`, exit 2.
- `read` в проекте без сообщений → пустой stdout, exit 0.
- `wait` исчерпал предел → `ожидание <вид> в '<имя>' истекло за <СЕК>s`, exit 1.
- `wait` при уже прочитанном сообщении нужного вида не возвращается сразу: ждёт
  следующего непрочитанного.
- База недоступна на запись → сообщение слоя хранилища с путём, exit 1. Чтение
  при отсутствующей базе даёт пустой результат, exit 0.

## Golden-примеры

`fixtures/task/`:

- `setup.stdout` — инструкция целиком: эталон текста, который читают на чистой
  машине;
- `rules.stdout` — правила письма спецификаций целиком;
- `status-two-projects.stdout` — обзор при двух проектах: у одного непрочитанная
  постановка (ход исполнителя), у другого прочитанный отчёт (ход
  спецификатора);
- `history.stdout` — журнал трёх порций одного проекта;
- `err-unknown-project.stderr`, `err-unhandled-portion.stderr`,
  `err-empty-body.stderr`.

Голдены снимаются с реализации: эталон формы задаёт эта спека, фикстуры
фиксируют её дословно.
