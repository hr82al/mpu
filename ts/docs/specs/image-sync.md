# mpu image sync

Статус: реализовано — порция 169 (`21c77acd`, `55931ea6`, `1e00e213`); принято 2026-09-25 хостом: тестов 2527, smoke 20/1 (новая — право записи каталога образа), мутации M1–M10 красные на своих сценариях (перепроверена хостом M5 — снят предохранитель), голдены `fixtures/image-sync/{help,messages}.txt` заморожены. Живьём через MCP (Accept) `ask image sync dry` на машине владельца → `новый файл\tkiten cardsIn:\nсовпало 0, изменено 1, конфликтов 0\n`, код 0; каталог `~/mr/mp/mpu/image` не создан. Платформа (снято исполнителем): обычный `mpu messages` группу, все дети которой посеяны `ask`, не показывает вовсе. Пример `kiten ls column:` заменён на `inColumn:` — `column` ключ `kiten ls`. `image export` и таймер — 169b, `image-export.md`.

## Назначение

Образ живёт в `image.db` (`platform/image.md`); исходники методов нужны и в
репозитории — читать, ревьюить, коммитить. `mpu ask image sync` сводит базу
и каталог файлов в обе стороны по принципу unison: по архиву прошлой
синхронизации видно, какая сторона изменилась. Ничего не теряется: конфликт
не трогает ни одну сторону, пустая сторона не удаляет другую. Суточная
выгрузка без человека — `mpu image export`, порция 169b (`image-export.md`).

## CLI-контракт

- `mpu ask image sync [dry] [dir: <каталог>] [base: <адрес>]… [files:
  <адрес>]… [deletes: allow]` — путь правила `image sync`, посев `ask`
  (`rw`). `dry` — только отчёт; путь правила вариант не меняет
  (`platform/variants.md`), поэтому `dry` тоже идёт через `ask`.
- `deletes:` — ключ-выбор с единственным значением `allow` (схема ключей,
  как `render:` у `xlsx get`); другое значение — отказ реестра его формой,
  до вопроса, код 2; своего текста нет. Ответ хоста 2026-09-25.
- Результат строки — текст отчёта (как справка метода, `platform/image.md`):
  сообщения результату (`end json`, `end size`) получает объект текста и
  отвечает своим протоколом — `json` он не понимает (отказ «не понимает
  json» с ближайшими, код 2, как у `kiten cardsIn: help end json`); своего
  отказа у `image sync` нет. Ответ хоста 2026-09-25.
- Строку `image sync` исполняет ядро (`mpu-back`), как
  `define:`/`forget:`: у него образ, правила и снимок дерева. Файлы каталога
  пишет ядро. В дереве это команды группы `image`: справка, дополнение,
  `messages` — у них.
- `dir:` — каталог файлов; умолчание — ключ конфига `image.dir`
  (`platform/config.md`), у ключа умолчание `$HOME/mr/mp/mpu/image` — от
  `HOME` порта команды, не из окружения по месту; `HOME` нет — умолчания нет
  (строка образа без `HOME` и так получает отказ правил). Относительный
  `dir:` — от `cwd` вызова
  (`platform/call-context.md`), как `run:` (170). Каталог — сам
  `$HOME/mr/mp/mpu/image` или под ним; иначе отказ **до вопроса**, код 2
  (сценарии 16–17). Каталога нет — он пуст; создаётся первой записью.
- Архив — в `image.db`, свой на каждый каталог (абсолютный путь после
  разрешения `dir:`): метод → хэш определения на момент прошлой
  синхронизации; после синхронизации у метода Б = Ф = А. Новый каталог —
  пустой архив.
- Права Deno: задачи `back`, `worker`, `compile:back`, `compile:worker`
  получают в `--allow-write` путь `$HOME/mr/mp/mpu/image` — строкой с
  обоснованием в `deno.jsonc` («каталог образа, `image-sync.md`»). Пишет
  ядро; у `worker` и `compile:*` путь потому, что их права обязаны совпадать
  с правами `back` (`supervisor/src/tasks_test.ts`).
- Видимость агенту: команды доходят до агента тулом `mpu` на словах
  (`platform/mcp-objects.md`), решают дерево и правило пути (сценарии
  27–30, 33); закрытый список `fixtures/mcp-server/tool-policies.json`
  относится к снятому серверу 7337 и не трогается.

### Файл метода

| Дано | Ожидается |
|---|---|
| метод `kiten cardsIn:`, ключи `^id колонки^` | `$D/kiten/cardsIn:.mpu` = `kiten define: cardsIn: purpose: ^мои в колонке^ keys: ^id колонки^ do :col kiten ls where: column is: @col done\n` |
| метод `kiten mine`, описания ключей нет | `$D/kiten/mine.mpu` = `kiten define: mine purpose: ^мои^ do kiten ls done\n` — `keys:` не пишется |
| получатель из двух звеньев, `kiten ls inColumn:` | `$D/kiten/ls/inColumn:.mpu` |
| в `$D/kiten/foo:.mpu` строка `kiten define: bar purpose: ^x^ do kiten ls done` | строка отчёта `файл не разобран\tkiten/foo:.mpu\tв файле kiten bar, ждали kiten foo:`, код 1; метод `kiten foo:`, если он есть в базе, не тронут («Неразобранный файл») |
| `$D/kiten/cardsIn.mpu` (без `:`), в нём строка определения из первой строки таблицы | `файл не разобран\tkiten/cardsIn.mpu\tв файле kiten cardsIn:, ждали kiten cardsIn`, код 1 — имя файла равно имени метода, как оно хранится, побуквенно (сценарий 44) |
| `$D/nope/x.mpu` (`nope` — не команда и не группа) | `файл не разобран\tnope/x.mpu\tmpu nope define: метод — только у команды или группы`, код 1 |
| `$D/other/kiten/cardsIn:.mpu` (подкаталог — не получатель, в том числе другой каталог образа) | `файл не разобран\tother/kiten/cardsIn:.mpu\tmpu other kiten define: метод — только у команды или группы`, код 1 (сценарий 48) |
| `$D/kiten/notes.txt`, `$D/kiten/.cardsIn:.mpu.swp` | не читаются, не удаляются, в отчёт не идут |
| файл с BOM `EF BB BF` и `\r\n` | те же слова, что без них (сценарий 41) |
| в `^…^` неразрывный пробел U+00A0 | часть слова; файл, записанный из базы, разбирается в тот же хэш (сценарий 42) |
| байты не в UTF-8 | `файл не разобран\t<путь>\tфайл не в UTF-8: байт 0x<XX> на смещении <n>`, код 1 (сценарий 43) |

Хэш в файл не пишется. Файл пишется словами через один пробел с `\n` в
конце.

**Текст → слова.** Разделители — ровно пробел U+0020, табуляция U+0009,
U+000A, U+000D; неразрывный пробел U+00A0 и прочие — часть слова. BOM (`EF
BB BF`) в начале снимается. Байты не в UTF-8 — файл не разобран. Правило
вводит эта порция; программа из файла и stdin (170,
`platform/program-input.md`) берёт то же разбиение, а не своё.

### Неразобранный файл

Файл разобран, если он в UTF-8, в нём строка определения `<получатель>
define: <имя> …`, получатель — команда или группа, а получатель и имя строки
совпадают с путём файла. Иначе — строка `файл не разобран`, код 1, во всех
запусках (sync и `dry`; export — `image-export.md`). Адрес такого файла берётся из пути
(`kiten/cardsIn:.mpu` → `kiten cardsIn:`) и **исключается из решения**, а не
считается «Ф нет»: метод в базе, его правило и архив не меняются, в `совпало`,
`изменено` и в счёт массового удаления он не входит (сценарии 34, 35, 40).

Проверки `define:` (имя занято, тело, назначение) — не разбор, а запись
стороны базы («Запись стороны базы»).

### Адрес метода в `base:`/`files:`

Синтаксис выбран слепым замером 2026-09-25 (кандидат A, перемер без хвостового `:` — 10/10;
`docs/probes/2026-09-25-image-prefer/`). Адрес — одно слово `<звенья получателя через .>.<имя>`: имя
без последнего двоеточия, как у `forget:` и `define:` (`cardsIn` ≡
`cardsIn:`, `platform/image.md`). Слово, оканчивающееся на `:`, грамматика
строки читает ключом (снято 2026-09-25: `mpu log cmd: zzqq: limit: 1` →
stderr `у ключа cmd нет значения`, код 2), поэтому `kiten.cardsIn:` не
годится, а двоеточия в середине годятся (`mpu log cmd: a:b.c` разобран
значением).

| Метод | Адрес |
|---|---|
| `kiten cardsIn:` | `kiten.cardsIn` |
| `kiten mine` | `kiten.mine` |
| `sheet sum:with:` | `sheet.sum:with` |
| `kiten ls inColumn:` | `kiten.ls.inColumn` |

`base:` и `files:` — вход-списки: повторяются, значения копятся
(`platform/keys-translation.md`). Адрес называет все методы получателя с
этим именем: при `kiten mine` и `kiten mine:` в базе или файлах
`kiten.mine` выбирает оба.

## Решение по методу

Б — хэш метода в базе, Ф — хэш файла, А — хэш в архиве. Б и Ф — sha256
строки определения целиком, слова через один пробел, без перевода строки:
`<получатель> define: <имя> purpose: ^<назначение>^ [keys: ^<ключи>^]
<тело>` — имя как хранится (`cardsIn:`), `keys:` при пустом описании
опускается. Б считается по методу в базе, Ф — по разобранному файлу.
Столбец `hash` образа (хэш одного тела) решению не служит: правка
`purpose:` иначе потерялась бы.

| Б | Ф | А | Итог |
|---|---|---|---|
| есть | = Б | любое | совпало; архив = Б |
| ≠ А | = А | есть | `файл из базы` |
| = А | ≠ А | есть | `база из файла` |
| ≠ А | ≠ А, ≠ Б | есть | `конфликт` |
| нет | = А | есть | `удалён файл` |
| = А | нет | есть | `удалён метод` |
| нет | ≠ А | есть | `конфликт` (удалён в базе, изменён в файле) |
| ≠ А | нет | есть | `конфликт` (изменён в базе, удалён в файле) |
| нет | нет | есть | строка архива снимается; в отчёт и в числа не идёт |
| есть | нет | нет | `новый файл` |
| нет | есть | нет | `новый метод` |
| есть | есть, ≠ Б | нет | `конфликт` |

При `конфликт` ни одна сторона и архив не меняются. Строку архива без
метода и без файла снимает sync; `dry` её не снимает.

## Запись стороны базы

`база из файла` и `новый метод` — то же, что строка файла, исполненная как
`define:` (168): те же проверки (отказ — строка `файл не разобран\t<путь от
dir>\t<текст отказа define:>`, метод не тронут, код 1), тот же посев правила
обходом тела, автор — канал запуска (`human`, `agent`, `web`), время — часы
запуска, снимок дерева переписан. `удалён метод` — как `forget:`: правило
пути метода снято. `dry` проверяет и решает правила так же, не записывая:
его stdout совпадает со stdout запуска без `dry`.

Правила путей `<получатель> define:` и `<получатель> forget:` решаются на
каждый такой метод: `allow` и `ask` — без второго вопроса (согласие — ответ
на вопрос `image sync`); `deny` — строка `сбой\t<получатель>
<имя>\tзапрещено правилом «<путь правила>»`, метод, его правило и архив
прежние, код 1 (сценарии 36, 37).

Новые и изменённые файлы разбираются вместе: тело может звать метод, который
появляется в этом же запуске. Правило метода решается после правил тех
методов этого запуска, которые зовёт его тело: итог не зависит от порядка
файлов (сценарий 14).

## Предохранители

**Пустая сторона.** Удаление выводится только по архиву; пустая база и новый
каталог несут пустой архив, поэтому первая синхронизация — только
объединение.

**Массовое удаление.** M — число методов стороны до запуска, N — удаления на
этой стороне в запуске, включая выбранные `base:`/`files:`. Проверка — до
любой записи; при отказе не меняется ни база, ни файлы, ни архив, stdout
пуст. Отказ — после вопроса двери, отказом строки с готовой строкой
(решение владельца 2026-09-25, инвариант «громкий отказ с готовой
строкой»): код 2, объект `refusal` (`platform/refusal-object.md`) с
`reason` «удалилось бы» и `hint` — набранная строка с `ask` первым словом и
`deletes: allow` в конце ключей (`["ask","image","sync","deletes:","allow"]`;
с `dry`, `dir:`, `base:`/`files:` — как набраны).

| Сторона: N из M | Итог |
|---|---|
| 1 из 3 | проходит |
| 1 из 2 | проходит (ровно половина) |
| 2 из 4 | проходит |
| 2 из 3 | отказ `… удалилось бы 2 из 3 методов (база) — вызывай mpu ask image sync deletes: allow`, код 2 |
| 3 из 5 | отказ, код 2 |
| 1 из 1 | отказ `… удалилось бы 1 из 1 методов (файлы) — вызывай mpu ask image sync deletes: allow`, код 2 |
| 10 из 10, `deletes: allow` | проходит, 10 × `удалён метод`, код 0 |
| база 1 из 2 и файлы 1 из 2 | проходит |
| `dry`, 3 из 5 | тот же отказ, совет `— вызывай mpu ask image sync dry deletes: allow`, `hint` `["ask","image","sync","dry","deletes:","allow"]`, код 2 |

Форма отказа: `<строка без ask>: удалилось бы N из M методов (<база|файлы>)
— вызывай mpu <слова hint через пробел>`.

## Отчёт

stdout — строка на метод с действием: `<действие>\t<получатель> <имя>`
(у `конфликт` — третьим полем адрес для `base:`/`files:`: `конфликт\tkiten
cardsIn:\tkiten.cardsIn`; решение владельца 2026-09-25 — правило адреса у
одного исполнителя, агент и web берут адрес из строки),
действия `новый файл`, `файл из базы`, `удалён файл`, `новый метод`, `база
из файла`, `удалён метод`, `конфликт`; прочие строки:
`сбой\t<получатель> <имя>\t<причина>`, `файл не разобран\t<путь от
dir>\t<причина>`. Порядок: строки методов по получателю, затем имени
(порядок кодовых точек), потом `файл не разобран` по пути, последней — итог
`совпало N, изменено M, конфликтов K`.

- N — методы, у которых до запуска Б = Ф;
- M — строки действий этого запуска, кроме `конфликт` (в `dry` — те, что
  напечатал бы запуск);
- K — строки `конфликт`;
- `сбой`, `файл не разобран`, снятая строка архива — ни в одно число не
  входят.

Код: 1 — есть строка `конфликт`, `сбой` или `файл не разобран`; иначе 0.

## Инварианты

- Строка архива по методу меняется только вместе с применённым по нему
  действием; исключение — строка без метода и без файла, её снимает sync.
- Неразобранный файл не удаляет и не меняет метод базы.
- Итог запуска не зависит от порядка файлов в каталоге.
- Сбой записи одной стороны — строка `сбой`, архив по методу прежний, прочие
  методы применены, код 1.
- Повтор без правок — `изменено 0`.
- Отказ (массовое удаление, каталог вне права, неверный адрес) не меняет ни
  базы, ни файлов, ни архива.
- `dry` не меняет базы, файлов и архива (посев правила `<получатель>
  define:` при первом касании, как у любой строки `define:`, изменением не
  считается).

## Сценарии

Стенд: `HOME=$H` — временный каталог, `$H/mr/mp/mpu` создан заранее, `D=$H/mr/mp/mpu/image`, Kaiten
подменён (как в `line/image_test.ts`). «Три метода» — определены строками с
ответом `y`:
`mpu ask kiten define: cardsIn purpose: ^мои в колонке^ keys: ^id колонки^ do :col kiten ls where: column is: @col done`,
`mpu ask kiten define: mine purpose: ^мои^ do kiten ls done`,
`mpu ask kiten define: shipped purpose: ^готово^ do kiten ls where: column is: Готово done`.
Третий метод — `shipped`, не `ready`: `kiten ready` — команда реестра
(найдено исполнителем 169); имя после `mine` сохраняет порядок строк.
Запуск без оговорок — `mpu ask image sync`, ответ `y`; stderr — вопрос
`выполнить mpu image sync? [y/N] ` и ничего больше. «Синхронизировано» —
после одного такого запуска.
