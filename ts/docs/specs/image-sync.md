# mpu image sync

Статус: к реализации — порция 169 (после 168).

## Назначение

Образ живёт в `image.db` (`platform/image.md`); исходники методов нужны и в
репозитории — читать, ревьюить, коммитить. `mpu ask image sync`
синхронизирует базу и каталог файлов в обе стороны по принципу unison: по
архиву прошлой синхронизации видно, какая сторона изменилась. Ничего не
теряется: конфликт не трогает ни одну сторону, пустая сторона не удаляет
другую.

## CLI-контракт

`mpu ask image sync [dir: <каталог>] [prefer: db|files method: <получатель>
<имя>]… [deletes: allow]`, вариант `dry` — только отчёт.

- `dir:` — каталог файлов; умолчание — ключ конфига `IMAGE_DIR`, нет ключа —
  отказ «каталог образа не задан: dir: или IMAGE_DIR», код 2.
- Файл метода — `<dir>/<получатель через />/<имя>.mpu` (`kiten/cardsIn:.mpu`),
  содержимое — строка определения без `ask` (`kiten define: cardsIn purpose:
  ^…^ do … done`) и перевод строки. Хэш в файл не пишется.
- Архив — таблица в `image.db`: метод → хэш на момент прошлой синхронизации
  (один на обе стороны, после синхронизации они равны).
- Путь правила — `image sync` (посев `ask`).

## Решение по методу

Б — хэш в базе, Ф — хэш файла (нормализованный исходник, `image.md`), А —
архив.

| Б | Ф | Итог |
|---|---|---|
| = Ф | = Б | согласие; архив = Б |
| ≠ А | = А | файл из базы |
| = А | ≠ А | база из файла |
| ≠ А | ≠ А, ≠ Б | конфликт: обе стороны не тронуты |
| нет | = А | удалён в базе → файл удаляется |
| = А | нет | удалён в файлах → метод удаляется |
| нет или ≠ А | ≠ А или нет, А есть | удалён на одной, изменён на другой — конфликт |
| есть, А нет | нет | новый в базе → файл |
| нет, А нет | есть | новый в файлах → метод |
| есть, А нет | есть, ≠ Б | конфликт |

`prefer: db method: kiten cardsIn` / `prefer: files …` решает конфликт этого
метода на этот запуск (повторяемо).

## Предохранители

- **Пустая сторона.** Удаление выводится только по архиву; новая пустая база
  несёт пустой архив, поэтому первая синхронизация — только объединение. То
  же для пустого каталога: метод без файла при пустом архиве — «новый в
  базе».
- **Массовое удаление.** Запуск, который удалил бы больше половины методов
  одной стороны или все, — отказ «удалилось бы N из M методов (<сторона>) —
  deletes: allow», код 1, ничего не изменено. `deletes: allow` разрешает на
  этот запуск.
- Файл, который не разбирается строкой определения, — строка отчёта «файл
  не разобран: <путь>: <причина>», сторона не трогается, код 1 в конце.

## Отчёт

stdout — строка на изменённый метод: `<действие>\t<получатель> <имя>`
(`файл из базы`, `база из файла`, `удалён файл`, `удалён метод`, `новый файл`,
`новый метод`, `конфликт`), затем итог `согласно N, изменено M, конфликтов K`.
Код: 0 — без конфликтов и сбоев; 1 — есть конфликт или сбой.

## Таймер

Раз в сутки служба (`platform/supervisor-install.md`, таймер `install.sh`)
запускает синхронизацию без человека каналом `agent` с вариантом `timer`:
направления «база → файлы» и удаления файлов применяются, «файлы → база» и
удаление методов — только строкой отчёта «ждёт человека» (правка файла не
обходит подтверждение). Коммит в git — не дело синхронизации.

## Граничные случаи

| Дано | Ожидается |
|---|---|
| метод только в базе, архив пуст, каталог пуст | `новый файл`, файл создан |
| файл изменён, база = архиву | `база из файла` |
| оба изменены по-разному | `конфликт`, обе стороны как были, код 1 |
| то же с `prefer: files method: kiten cardsIn` | `база из файла` |
| база пересоздана пустой (архив пуст), 10 файлов | 10 × `новый метод`, ни одного удаления |
| каталог очищен, архив есть, 10 методов | отказ «удалилось бы 10 из 10 методов (база) — deletes: allow», код 1, база цела |
| то же с `deletes: allow` | 10 × `удалён метод` |
| таймер, файл изменён | «ждёт человека: база из файла», база не тронута |
| таймер, база изменена | `файл из базы` |
| `image sync` без `ask` | адресный отказ двери, код 2 |
| файл с мусором | «файл не разобран: …», прочие методы синхронизированы, код 1 |
| `dry` | отчёт как при запуске, ничего не изменено |
