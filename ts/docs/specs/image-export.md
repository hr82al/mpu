# mpu image export

Статус: к реализации — порция 169b (после 169, `image-sync.md`).

## Назначение

Раз в сутки без человека переносит в файлы каталога образа то, что
изменилось в базе (`image-sync.md`, решение по методу — то же). Всё, что
меняет базу, оставляет строкой «ждёт человека» для `mpu ask image sync`.

## CLI-контракт

- `mpu image export [dir: <каталог>]` — путь правила `image export`, посев
  `allow` (решение владельца 2026-09-25: пишет только файлы каталога
  образа). У пути одна посевная строка: `allow` **заменяет** посев по
  признаку `rw`, а не встаёт рядом — второе правило того же пути в посеве
  роняет посев целиком, а с ним любую строку (сценарий E11). Строка `image
  export` — `allow` стоит в таблице «Посев» `platform/policy.md`. `base:`, `files:`, `deletes:` не принимает.

Каталог, архив, файл метода, адрес, решение по методу, неразобранный файл,
права Deno — как в `image-sync.md`; эта порция их не меняет.

## Решение и отчёт

Из решения по методу `export` применяет только направление база → файлы:
`новый файл`, `файл из базы`, `удалён файл`. Остальные исходы (`база из
файла`, `новый метод`, `удалён метод`, `конфликт`) печатает строкой
`ждёт человека\t<действие>\t<получатель> <имя>`, архив по такому методу не
меняет. Неразобранный файл export печатает так же, как sync, — строкой
`файл не разобран`, код 1 (сценарий E8): исправить файл может только
человек, и упавший юнит — сигнал ему. Массовое удаление файлов — тот же
отказ. Коммит в git — не дело команды.

`ждёт человека\t<действие>\t<получатель> <имя>` — строка отчёта только
этой команды. В числа `совпало`/`изменено`/`конфликтов` не входит;
`ждёт человека\tконфликт\t<получатель> <имя>\t<адрес>` (адрес — как у
строки `конфликт` в `image-sync.md`, «Отчёт») — не строка `конфликт`: кода 1 не даёт
(сценарий E6) — суточный юнит не падает, пока конфликт ждёт человека.

Массовое удаление файлов — тот же отказ, что у `sync`, с другим хвостом:

| Сторона: N из M | Итог |
|---|---|
| `image export`, файлы 3 из 5 | `mpu image export: удалилось бы 3 из 5 методов (файлы) — вызывай mpu ask image sync deletes: allow`, `refusal` `{"reason":"удалилось бы","hint":["ask","image","sync","deletes:","allow"],…}`, код 2 |

У export `hint` ведёт в `image sync` (с `dir:`, если он набран): ключа
`deletes:` у export нет, и совет ведёт туда, где он есть. Юнит падает с
кодом 2 — сигнал человеку. Удаления базы export
не применяет и в счёт массового удаления файлов не берёт (сценарий E9).

## Суточный таймер

Раз в сутки её зовёт юнит systemd пользователя, который ставит
`ts/install.sh` (правка — в этой порции; запуск `install.sh` — хост после
приёмки):

`supervisor/mpu-image-export.service`:

```
[Unit]
Description=mpu: образ → файлы каталога образа
After=mpu.service

[Service]
Type=oneshot
ExecStart=%h/.local/bin/mpu image export
```

`supervisor/mpu-image-export.timer`:

```
[Unit]
Description=mpu: раз в сутки образ → файлы

[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
```

Клиент из-под юнита управляющего терминала не имеет: `/line`, `human:
false` (`cli-client.md`, «Канал и токен»); на `allow` строка исполняется без
вопроса.

| Дано (`supervisor/src/install_test.ts`, поддельный `systemctl`) | Ожидается |
|---|---|
| первая установка | в `$MPU_UNIT_DIR` оба файла побайтово как эталоны; вызовы `systemctl`: `--user daemon-reload`, `--user enable mpu`, `--user enable --now mpu-image-export.timer`, `--user start mpu` (юниты службы и таймера записаны до одной `daemon-reload`); строка `install: таймер образа: записан` |
| второй запуск без изменений | вызовов нет; `install: таймер образа: без изменений` |
| служба без изменений, таймера нет | вызовы `--user daemon-reload`, `--user enable --now mpu-image-export.timer`; перезапуска `mpu` нет; строки `install: служба: без изменений`, `install: таймер образа: записан`, `install: перезапуск: не нужен` |
| таймер без изменений, служба изменена | вызовы `--user daemon-reload`, `--user enable mpu`, `--user restart mpu`; строки `install: служба: записана`, `install: таймер образа: без изменений` |
| `--check` | файлы юнитов не тронуты, вызовов нет |

Изменение файлов таймера `mpu` не перезапускает. Эталоны юнитов — литералы
этого раздела, они же лежат файлами `fixtures/supervisor-install/mpu-image-export.service`
и `.timer` (положил хост); исполнитель копирует их в
`supervisor/src/testdata/supervisor-install/` и в источник установки
`ts/supervisor/`. Контракт установки службы (`platform/supervisor-install.md`)
ссылается на этот раздел.

## Журнал вызовов

Строка `image export` оставляет одну запись, как любая строка
(`platform/invoke-log.md`), в том числе запущенная юнитом.

## Инварианты

- `export` не меняет методов базы, их правил и снимка дерева; архив — только
  по применённым действиям (база → файлы).
- Строку архива без метода и без файла export снимает, как sync.
- Отказ массового удаления не меняет ни файлов, ни архива.
