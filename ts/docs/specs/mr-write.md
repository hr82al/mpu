# mpu mr — запись (create, describe, comment, note, reply, edit, delete, resolve, unresolve)

Статус: черновик

## Назначение

Write-подкоманды `mpu mr`: создать MR, заменить описание, инлайн- и
общие комментарии ревью, ответ в тред, правка и удаление своей ноты,
резолв тредов. Чтение — `mr-read.md`; авторизация, резолв `--mr`,
эндпоинты, position-механика, матчинг дискуссий и тексты ошибок
резолва — `platform/gitlab-api.md` (далее — атом).

## CLI-контракт

Общее:

- `--mr REF` у всех подкоманд, кроме `create`, — как в атоме.
- Тело текста — ровно один источник из `-m/--message TEXT` и
  `-F/--body-file PATH` (`-` — stdin). Оба сразу, или ни одного там,
  где тело обязательно, → exit 2
  `нужно ровно одно из -m/--message и -F/--body-file`; файл не
  читается → exit 2 `не удалось прочитать <путь>: <детали>`; итоговое
  тело пустое или из одних пробельных символов → exit 2
  `пустое тело комментария`. Валидация тела — до первого сетевого
  запроса.
- Note-ссылка в выводе создающих команд: `{web_url MR}#note_{id ноты}`.

`mpu mr create --title TEXT --target BRANCH [--source BRANCH]
[--project group/repo] [-m|-F]`

- `--source` по умолчанию — текущая ветка cwd; detached HEAD →
  exit 1 `detached HEAD — укажи --source`;
- `--project` по умолчанию — из git remote cwd (атом);
- описание — из `-m`/`-F`, опционально (без них — пустое);
- успех: `создан MR {project}!{iid} — {title} [{state}]`,
  `branch: {source_branch} → {target_branch}`, web_url.

`mpu mr describe [--mr REF] (-m|-F)` — заменить описание MR целиком;
успех: `описание MR {project}!{iid} обновлено` + web_url.

`mpu mr comment FILE:LINE [--mr REF] (-m|-F) [--old]`

- FILE:LINE — разделитель — последний `:` (двоеточия в пути
  допустимы); нет разделителя или пустой путь → exit 2
  `ожидается FILE:LINE, получено '<аргумент>'`; LINE не положительное
  целое → exit 2 `LINE — положительное число, получено '<аргумент>'`;
- LINE — номер строки в НОВОЙ версии файла (правая колонка диффа
  GitLab); удалённая строка существует только в старой версии — её
  старый номер + `--old`;
- проверки до POST, каждая → exit 1:
  - у MR нет diff_refs → `у MR {project}!{iid} нет diff (MR без
    коммитов)`;
  - путь не среди new_path/old_path файлов MR → `файл '<путь>' не
    изменён в этом MR; изменённые: <до 20 путей, отсортированных,
    через запятую>` + `…` при более чем 20;
  - строка не найдена на выбранной стороне диффа →
    `{path}:{line} не входит в diff MR` + один из суффиксов:
    файл удалён и сторона new → `; файл удалён в MR — используй
    --old`; на стороне нет комментируемых строк → `; на
    {new|old}-стороне нет комментируемых строк`; иначе →
    `; комментируемые {new|old}-строки: <диапазоны, атом>` + для
    new-стороны ` (строки старой версии — через --old)`;
- успех — POST треда с position (атом):
  `создано: discussion {id[:8]} на {path}:{line}` + note-ссылка.

`mpu mr note [--mr REF] (-m|-F)` — general-тред без привязки к строке;
успех: `создано: discussion {id[:8]}` + note-ссылка.

`mpu mr reply DISCUSSION [--mr REF] (-m|-F)` — ответ в существующий
тред (DISCUSSION — атом); успех:
`reply: note {id} в discussion {id[:8]}` + note-ссылка.

`mpu mr edit NOTE_ID [--mr REF] (-m|-F)` — заменить тело своей ноты;
NOTE_ID — целое (иначе exit 2 от разбора аргументов); успех:
`note {id} обновлена`.

`mpu mr delete NOTE_ID [--mr REF] [--yes]`

- без `--yes`: stdin не TTY → exit 1
  `нет TTY для подтверждения — добавь --yes`, DELETE не вызывается;
  TTY есть → вопрос `Удалить note {id} в {project}!{iid}?`; отказ →
  exit 1 без DELETE (форма сообщения отказа не фиксируется);
- успех: `note {id} удалена`.

`mpu mr resolve DISCUSSION [--mr REF]` /
`mpu mr unresolve DISCUSSION [--mr REF]`

- тред нерезолвабельный (general-тред без resolvable-нот) → exit 1
  `тред {id[:8]} нерезолвабельный (general note)`, HTTP-запрос
  резолва не выполняется;
- успех: `discussion {id[:8]}: resolved` / `discussion {id[:8]}:
  unresolved`.

## Ввод/вывод

stdin читается только при `-F -`. stdout — сообщения успеха (выше);
stderr — `mpu mr <подкоманда>: <сообщение>` (атом), без трейсбеков.
Exit: 0 — успех; 2 — ошибки ввода, валидируемые до сети (сочетание
`-m`/`-F`, чтение файла тела, пустое тело, форма FILE:LINE, нечисловой
NOTE_ID, отсутствие обязательных флагов); 1 — всё остальное (резолв
MR, API, файл/строка/дискуссия, отсутствие TTY).

## Побочные эффекты

Пишущие HTTP-запросы к GitLab (POST/PUT/DELETE — атом); локальные
git-подпроцессы при неполных `--mr`/`--project`/`--source`. Ретраев и
клиентской идемпотентности нет: повторный `create`/`comment`/`note`/
`reply` создаёт новый MR/тред/ноту. Локально ничего не пишется.

## Конфигурация

`GLAB_TOKEN` (обязателен), `GITLAB_BASE_URL` — атом.

## Инварианты

- Тело — всегда из ровно одного источника; валидируется до сети.
- `comment` промахивается только громко: строка вне диффа — ошибка до
  POST; «молча непривязанный» комментарий невозможен (position —
  form-urlencoded, атом).
- Position строится только по строке, реально существующей на
  выбранной стороне диффа.
- `delete` не выполняет DELETE без `--yes` или явного подтверждения
  в TTY.
- `resolve`/`unresolve` нерезолвабельного треда не выполняет
  HTTP-запрос резолва.
- `reply`/`resolve`/`unresolve` адресуют только треды без системных
  нот (атом): чисто системный тред недостижим по префиксу.
- Токен не попадает ни в stdout, ни в stderr.

## Граничные случаи и ошибки

- `-m` и `-F` вместе → exit 2; ни одного у
  `describe`/`comment`/`note`/`reply`/`edit` → exit 2; `create` без
  обоих → пустое описание, успех.
- `-F -` — тело из stdin целиком; пустой stdin → exit 2
  `пустое тело комментария`.
- `comment` по new-номеру removed-строки (без `--old`) или old-номеру
  added-строки (с `--old`) → «не входит в diff MR» с диапазонами.
- `comment` на context-строку → position несёт old_line И new_line
  (атом).
- `comment` на удалённый файл без `--old` →
  `; файл удалён в MR — используй --old`.
- Повторный идентичный `comment`/`note`/`reply` → второй тред/нота,
  дедупликации нет.
- `delete --yes` в не-TTY → удаление без подтверждения (сценарий
  скриптов).
- `delete` несуществующей ноты (с `--yes`) → exit 1
  `gitlab error: gitlab DELETE … -> 404: …` с подсказкой (атом).
- `resolve` уже резолвленного треда → запрос выполняется
  (предварительной проверки состояния нет).

## Golden-примеры

**Без сети — сняты 2026-08-27** с рабочей версии (ни одного мутирующего вызова
не сделано). Рабочая версия печатает их рамкой разборщика аргументов; у нас те
же случаи — одна строка `mpu mr <sub>: <текст>` и exit 2 (см. «Известные
отклонения»), тексты сохраняются дословно:

- `mr note` без `-m`/`-F` → `нужно ровно одно из -m/--message и -F/--body-file`;
- `mr comment src/a.js -m x` (без `:LINE`) → `ожидается FILE:LINE, получено
  'src/a.js'`;
- `printf '' | mr note -F -` → `пустое тело комментария`.

**С сетью — не сняты.** Мутирующие вызовы (`comment` и его `position` в
`comments --json`, `comment` на строку вне диффа, `note`, `reply`, `resolve`
общего треда, `describe`) требуют MR, в который не жалко писать. Отдельного
тестового проекта решено пока не заводить (решение пользователя 2026-08-27),
поэтому эти голдены остаются неснятыми, и спека это признаёт прямо: контракт
записи выведен из наблюдения рабочей версии и ответов GitLab при чтении, но
парой не подтверждён. Появится тестовый MR — снимаются первым делом, начиная с
`position` инлайн-комментария: это самая хрупкая часть контракта.

## Открытые вопросы

Коды выхода разведены (решение спецификатора 2026-08-27, вердикт **fix**):
**2** — ошибки ввода, разбираемые до сети (нераспознанный `--mr`, отсутствующий
обязательный аргумент, взаимоисключающие флаги, файл тела не найден); **1** —
всё, что случилось после обращения наружу (HTTP-коды GitLab, недоступность
сети) и «сущность не найдена» на стороне GitLab (MR, дискуссия, файл в диффе).
Рабочая версия отвечает `1` на всё подряд — это противоречит контракту команд
монорепо (`platform/command-contract.md`), где `2` закреплено за ошибками
ввода; сохранять единицу значило бы вносить исключение в общее правило ради
одной семьи команд.
