# mpu kiten checklist

Статус: к реализации (2026-08-14 сняты голдены всех ветвей живым
прогоном на тестовой карточке и подтверждены круговым замером через
интерфейс; 2026-08-16 спека сверена с рабочей версией построчно —
CLI-поверхность, флаги, вывод, коды выхода, внешние вызовы и отсутствие
локального состояния совпали, сверка добавила одно отклонение с
вердиктом fix и нормализовала два голдена, см. соответствующие разделы)

## Назначение

Чек-листы карточки Kaiten — единственные интерактивные чекбоксы:
`- [ ]` в описании карточки рендерится обычным текстом. `ls` — чтение
чек-листов с пунктами; `add` — создать чек-лист и/или дописать пункты;
`check`/`uncheck` — отметить или снять отметку пункта. Обвязка —
`platform/kaiten-http.md`.

## CLI-контракт

`mpu kiten checklist ls SELECTOR [--json]`
`mpu kiten checklist add SELECTOR -n/--name NAME [-i/--item TEXT]...`
`mpu kiten checklist check SELECTOR ITEM`
`mpu kiten checklist uncheck SELECTOR ITEM`

- `SELECTOR` — селектор карточки (`platform/kaiten-http.md`, «Селектор
  карточки»).
- Вызов группы без подкоманды печатает справку группы, exit 0.
- `--json` (только `ls`) — JSON-вывод вместо таблицы.
- `-n/--name NAME` (обязательна) — название чек-листа. Совпадение с
  существующим — точное, регистр и пробелы значимы.
- `-i/--item TEXT` (повторяемая, необязательная) — текст пункта; пункты
  добавляются в порядке появления флагов.
- `ITEM` — ссылка на пункт: id (из вывода `ls`) либо подстрока текста.
  Строка из одних цифр сначала пробуется как id пункта: совпал — он и
  побеждает; не совпал — та же строка ищется как подстрока. Подстрока
  сравнивается без учёта регистра и ищется по всем пунктам всех
  чек-листов карточки; годится ровно одно совпадение.

Живые сценарии: `mpu kiten checklist ls 12345678`;
`mpu kiten checklist add 12345678 -n 'Подзадачи' -i 'Спека — 1 ч' -i
'Ревью — 1 ч'`; `mpu kiten checklist check 12345678 'Ревью'`;
`mpu kiten checklist uncheck 12345678 66470402`.

## Ввод/вывод

HTTP-граница (формы — `platform/kaiten-http.md`):

- `GET /cards/{id}` — читают все четыре подкоманды; берутся
  `checklists[]` с полями `id`, `name`, `items[]`, у пункта — `id`,
  `text`, `checked`, `sort_order` (дробный, может отсутствовать);
- `POST /cards/{id}/checklists` body `{"name": <NAME>}` — только когда
  чек-листа с таким именем на карточке нет;
- `POST /cards/{id}/checklists/{checklistId}/items` body
  `{"text": <TEXT>, "checked": false, "sort_order": <число>}` — по
  одному запросу на добавляемый пункт;
- `PATCH /cards/{id}/checklists/{checklistId}/items/{itemId}` body
  `{"checked": true|false}` — `check`/`uncheck`.

`sort_order` нового пункта — `<максимум sort_order пунктов чек-листа на
момент чтения, при отсутствии 0> + <порядковый номер флага -i в
командной строке, с 1>`; пропущенные (уже существующие) тексты номер
всё равно занимают, поэтому относительный порядок добавляемых пунктов
совпадает с порядком флагов.

stdout `ls` без `--json` — по одному блоку на чек-лист:

    {name} · {отмечено}/{всего} (checklist id {id})
     id        ✓    text
     66470402  [x]  Спека отличий — 1 ч
     66470403  [ ]  Ревью — 1 ч

Пункты — по возрастанию `sort_order`, при равенстве по `id`; отметка —
`[x]` для отмеченного, `[ ]` для нет. Чек-листов нет → одна строка
`(чек-листов нет)`.

Сортировать обязательно: порядок `items[]` в ответе сервера не задан —
замер 2026-08-14 дал порядок, не совпавший ни с `sort_order`, ни с `id`.
Тем же порядком (`sort_order`, затем `id`) перечисляются кандидаты в
сообщениях о неоднозначной и ненайденной ссылке на пункт: прежняя
реализация отдавала их в порядке ответа сервера, то есть в произвольном.

stdout `ls --json` — массив в том же порядке пунктов; печатает его общий
слой CLI: отступ два пробела, не-ASCII не экранируется, в конце один
перевод строки. Ключи и их порядок — `id`, `name`, `items[]`, у пункта
`id`, `checked`, `text`; форма целиком — в голдене
`ls-json-stdout.txt`.

Чек-листов нет → `[]`.

stdout успеха мутаций:

    ok: чек-лист «{name}» ({создан|существующий}, id {id}), добавлено пунктов: {N} · {url карточки}
    ok: [x] {текст пункта} · {url карточки}          ← check
    ok: [ ] {текст пункта} · {url карточки}          ← uncheck

Exit: 0 — успех; 2 — ошибки ввода (селектор, отсутствие `--name`,
ненайденный или неоднозначный `ITEM` — см. «Известные отклонения»);
1 — ошибки API (`mpu kiten checklist {ls|add|check|uncheck}: kaiten
error: <текст>`).

## Побочные эффекты

`ls` — только `GET`, ничего не меняет. `add` — до одного `POST`
создания чек-листа плюс по `POST` на каждый добавляемый пункт.
`check`/`uncheck` — один `PATCH`. Подтверждения перед мутацией нет:
разделение обеспечивает профиль MCP-сервера (`ls` — читающий тул,
остальные три — мутирующие). Локальных записей нет.

## Конфигурация

`KITEN_API_KEY`, `KITEN_BASE_URL` — `platform/kaiten-http.md`. Других
нет.

## Инварианты

- `add` идемпотентна: повторный запуск с тем же `--name` не создаёт
  второй чек-лист, а повторные `--item` с точно тем же текстом не
  создают дублей — счётчик добавленных при этом уменьшается вплоть до
  нуля.
- `check`/`uncheck` идемпотентны по результату: повторный вызов
  оставляет пункт в том же состоянии и печатает ту же строку успеха.
- Порядок пунктов в выводе `ls` совпадает с порядком в веб-карточке:
  сервер отдаёт `items` в произвольном порядке, вывод сортируется
  всегда — иначе `ls` и карточка выглядят разными списками.
- Числовая ссылка, совпавшая с `id` пункта, побеждает подстрочный
  поиск всегда.
- Поиск пункта сквозной по карточке: пункт находится независимо от
  того, в каком из чек-листов лежит, и `PATCH` уходит именно в его
  чек-лист.
- Ни одна подкоманда не удаляет чек-листы и пункты и не меняет тексты
  существующих пунктов.
- Неоднозначная или ненайденная ссылка на пункт не приводит ни к
  одному мутирующему запросу.
- Отметка пункта — общее состояние с интерфейсом Kaiten, а не отдельная
  сущность команды: проверено 2026-08-14 круговым замером — пункт,
  отмеченный мышью в веб-карточке, немедленно виден как `[x]` в `ls`, а
  снятый командой `uncheck` — снят и в интерфейсе.
- Чек-лист карточки — единственное место в Kaiten с интерактивными
  чекбоксами. GFM-разметка `- [ ]` в описании карточки и в тексте
  комментария остаётся обычным текстом в обоих местах
  (`platform/kaiten-api-cards.md`, «Инварианты»), поэтому подменить
  чек-лист markdown-списком нельзя — ни в описании, ни в комментарии.

## Граничные случаи и ошибки

- У карточки нет чек-листов → `ls`: `(чек-листов нет)`, exit 0;
  `ls --json`: `[]`, exit 0.
- Чек-лист без пунктов → заголовок `{name} · 0/0 (checklist id {id})` и
  таблица из одной шапки.
- `add` без единого `-i` → чек-лист создаётся (или берётся
  существующий), `добавлено пунктов: 0`, exit 0.
- `add`, все тексты уже есть → ни одного `POST` пункта,
  `добавлено пунктов: 0`, exit 0.
- `ITEM` — число, не совпавшее ни с одним `id` → ищется как подстрока.
- `ITEM` дал несколько совпадений → exit 2:
  `mpu kiten checklist {verb}: пункт '{ITEM}' неоднозначен, кандидаты:
  {id}: {текст}; {id}: {текст}` (текст каждого кандидата обрезан до 60
  символов), мутации нет.
- `ITEM` не найден → exit 2: `mpu kiten checklist {verb}: пункт
  '{ITEM}' не найден; есть: {id}: {текст}; …`; пунктов на карточке нет
  → вместо перечня `(пунктов нет)`.
- `check` уже отмеченного пункта (и `uncheck` неотмеченного) → `PATCH`
  выполняется, вывод обычный, exit 0.
- Невалидный селектор → exit 2 (`platform/kaiten-http.md`).
- Ошибка API на любом шаге → exit 1; уже выполненные запросы не
  откатываются (см. «Известные отклонения»).

## Golden-примеры

Сняты живым прогоном на тестовой карточке Kaiten 2026-08-14 и
обезличены; лежат в `fixtures/kiten-checklist/`.

Чтение: `ls-empty-stdout.txt` (карточка без чек-листов → `(чек-листов
нет)`), `ls-stdout.txt` (форма таблицы, три пункта, все сняты),
`ls-json-stdout.txt` (та же карточка с `--json`).

Мутации: `add-created-stdout.txt` (чек-лист создан, добавлено 2),
`add-existing-stdout.txt` (тот же `-n` повторно: `существующий`,
добавлен только новый пункт — уже имеющийся текст пропущен),
`add-name-only-stdout.txt` (`-n` без `-i` → `добавлено пунктов: 0`),
`check-stdout.txt` (по подстроке), `check-by-id-stdout.txt` (по id),
`uncheck-stdout.txt`. Идемпотентность `check` проверена тем же вызовом
дважды — вывод второго совпадает с первым.

Ошибки: `err-ambiguous-stderr.txt` (подстрока, подошедшая нескольким
пунктам) и `err-item-not-found-stderr.txt` (подстрока без совпадений).
**Оба сняты с прежней реализации и в новой недостижимы как есть**: они
завершаются кодом 1, а правильный код — 2, см. «Известные отклонения».
Тексты сообщений воспроизводятся, код выхода — нет.

Два голдена **нормализованы** (2026-08-16, сверка с рабочей версией):

- в обоих `err-*`-файлах перечень кандидатов пересобран в порядке
  `sort_order`, затем `id`. Снятые тексты шли в порядке ответа сервера
  (`66835646` перед `66835645`) и противоречили инварианту сортировки —
  голден-ловушка;
- `ls-json-stdout.txt` переписан в форму общего слоя (отступ два
  пробела). Снятая строка была однострочной с пробелами после `:` и `,`
  — оформление JSON-принтера рабочей версии, не контракт; остальные
  `--json` семейства печатаются с отступом.

## Известные отклонения

- **fix** — ненайденная и неоднозначная ссылка на пункт завершаются
  кодом 1, тем же, что сбой Kaiten. Правильное поведение — exit 2: это
  ошибка ввода, и по коду выхода вызывающий должен отличать «указал не
  то» от «сервер отказал», как в остальных командах семейства.
- **fix** — кандидаты в сообщениях о неоднозначной и ненайденной ссылке
  перечисляются в порядке ответа сервера, то есть в произвольном, тогда
  как та же карточка в `ls` показана отсортированной. Правильное
  поведение — один порядок в обоих местах (`sort_order`, затем `id`):
  человек сверяет перечень кандидатов с тем, что видел в `ls`.
- **fix** — при выводе не в терминал текст пункта переносится по
  ширине 80 колонок, разрывая его на несколько строк таблицы.
  Правильное поведение — вне терминала печатать текст пункта одной
  строкой целиком: именно этот текст копируют в `check <подстрока>`, и
  разорванный он не ищется ни `grep`, ни глазами.
- **fix** — сбой на середине списка `-i` печатает только ошибку: уже
  созданные пункты остаются на карточке, но сколько их, из вывода не
  видно. Правильное поведение — в сообщении об отказе указать число
  успевших добавиться пунктов, чтобы повтор команды был осознанным
  (сам повтор безопасен — дубли не создаются).
