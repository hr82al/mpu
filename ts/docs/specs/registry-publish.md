# mpu registry verify / publish

Статус: черновик (2026-09-10 — постановка по живому случаю; к реализации — после ответа на
«Открытые вопросы»)

## Назначение

Положить в локальный npm-реестр версию внутреннего пакета, которую требует лок потребителя, так,
чтобы установка по локу прошла: собрать пакет из исходника **на коммите этой версии**, сверить
`integrity` собранного тарбола с локом потребителя и только при совпадении опубликовать.

Две подкоманды по правилу разделения чтения и записи:

- `mpu registry verify` — собрать и сверить; ничего не публикует (политика `ro`);
- `mpu registry publish --verify-lock` — то же и затем публикация в локальный реестр (политика
  `rw`); без совпадения `integrity` публикации нет.

**Живой случай (2026-09-10).** Влитый `main` репозитория `ozon` поднял `@sw-back/workspace-access`
`^0.2.1 → ^0.3.0`. В локальном реестре (контейнер `mp-registry`, Verdaccio, порт 4873) были только
0.2.0 и 0.2.1; боевой реестр без кред отдаёт 401. Гейты трёх веток встали. Руками:

1. коммит версии — `git log` пакета в `sw-back`: `d2c32b5b feat(workspace-access): client 0.3.0`;
2. `git archive d2c32b5b packages/workspace-access | tar -x -C <tmp>`;
3. в `<tmp>/packages/workspace-access`: `npm install --no-audit --no-fund --ignore-scripts
   --registry https://registry.npmjs.org` (devDeps: `typescript ^5` → 5.9.3, `@nestjs/common`,
   `@types/node`, `reflect-metadata`), затем `tsc -p tsconfig.json`;
4. `npm pack --dry-run --json` → `integrity` =
   `sha512-o2vSArSLYgXbrtMh4vqY4GtpFMPOF+oYc8/UcwjVNWuSzEtkHcnE7euEHC4G1nenYSykTe7N7W8y7ojv2gm+pw==`;
5. в локе потребителя (`ozon/pnpm-lock.yaml`, `origin/main`) у `'@sw-back/workspace-access@0.3.0'`
   `resolution: {integrity: …}` — то же значение, байт в байт;
6. `npm publish --ignore-scripts --registry http://localhost:4873
   "--//localhost:4873/:_authToken=local-stand"` → `+ @sw-back/workspace-access@0.3.0`;
7. проверка из контейнера потребителя: метаданные `http://mp-registry:4873/@sw-back%2fworkspace-access`
   несут 0.3.0 с той же `integrity`, тарбол отдаётся с кодом 200.

Прежнее убеждение «пересобранный тарбол не сойдётся с локом» опровергнуто этим замером: `npm pack`
детерминирован при тех же исходниках и том же компиляторе. Смежный инструмент рабочей области
(`mp-stand registry publish`) публикует все пакеты репозитория без сверки с локом и собирает
компилятором корня репозитория — это другой сценарий; дублем команда не является.

## CLI-контракт

`mpu registry verify <PKG>@<VERSION> --source <REPO> --lock <LOCKFILE> [--commit SHA] [--json]`

`mpu registry publish <PKG>@<VERSION> --source <REPO> --lock <LOCKFILE> --verify-lock
[--commit SHA] [--registry URL] [--json]`

- `PKG@VERSION` — имя пакета и точная версия (`@sw-back/workspace-access@0.3.0`).
- `--source` — репозиторий рабочей области с исходником (`sw-back`); пакет ищется в `packages/*`
  по полю `name` в `package.json`.
- `--lock` — лок потребителя: путь к файлу или `<repo>:<ref>:<путь>` (`ozon:origin/main:pnpm-lock.yaml`).
  Поддерживается формат `pnpm-lock.yaml` (ключ `'<name>@<version>'`, поле `resolution.integrity`);
  другие форматы — открытый вопрос.
- `--commit` — коммит версии явно; без него — первый коммит (по времени), на котором
  `packages/<pkg>/package.json` содержит `"version": "<VERSION>"`.
- `--registry` — адрес локального реестра; дефолт `http://localhost:4873`.
- `--verify-lock` у `publish` обязателен: публикации без сверки команда не делает (форма без флага
  → отказ с подсказкой). Флаг — в имени вызова, чтобы правило разрешений видело сверку в строке
  команды.

## Ввод/вывод

Шаги обеих подкоманд до публикации одинаковы: найти коммит → `git archive` в свежий временный
каталог → установка devDeps с публичного npm → сборка скриптом `build` пакета (`tsc -p
tsconfig.json`) → `npm pack --dry-run --json` → сравнение `integrity` с локом.

Результат (`--json`): `{ package, version, commit, built_integrity, lock_integrity, match,
compiler, published }` — `compiler` — версия компилятора, которым собрано (`tsc -v`); `published` —
`true` только у `publish` после успешной публикации, иначе `false`.

Текст (без `--json`): по строке на шаг (`коммит d2c32b5b`, `сборка: typescript 5.9.3`,
`собрано: sha512-o2vS…pw==`, `в локе: sha512-o2vS…pw==`, `совпадает`), у `publish` — последняя
строка `опубликовано: <PKG>@<VERSION> → <registry>`. Оканчивается переводом строки.

## Побочные эффекты

- `verify` — временный каталог (удаляется по завершении, в том числе при ошибке) и сетевые запросы
  к публичному npm за devDeps. В реестр, в репозитории и в лок не пишет.
- `publish` — сверх того `npm publish` в локальный реестр. Боевой реестр не трогается никогда:
  `publishConfig.registry` пакета переопределяется `--registry`.

## Конфигурация

Токен локального реестра — фиктивный (`local-stand`): Verdaccio публикацию анонимно принимает, но
npm требует видеть токен. Своих ключей нет.

## Инварианты

- Публикация только при `match == true`.
- Версия, уже изданная в реестре, не переиздаётся: `publish` проверяет метаданные реестра и при
  наличии версии с той же `integrity` отвечает `уже издано`, exit 0; с другой — отказ, exit 1.
- Лок потребителя не меняется.

## Граничные случаи и ошибки

- Коммит версии не найден → exit 1, `нет коммита с версией <VERSION> в <path>`.
- В локе нет записи `'<PKG>@<VERSION>'` → exit 1.
- `integrity` не совпала → `verify`: exit 1 и обе суммы; `publish`: то же, публикации нет. Строкой
  ниже — `compiler` сборки и диапазон компилятора из devDeps пакета: главный подозреваемый
  расхождения — другая версия компилятора.
- Реестр недоступен (`publish`) → exit 1, сборка и сверка в выводе остаются.

## Golden-примеры

Нет — снимаются при реализации на фикстуре: пакет-заглушка с `build` без компилятора (копирование
файла в `dist`), лок с совпадающей и несовпадающей `integrity`, реестр — Verdaccio в контейнере
теста или заглушка HTTP.

  в живом случае не было.
