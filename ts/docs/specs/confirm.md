# mpu confirm

Статус: реализовано

## Назначение

y/N-ворота в середине конвейера: показать человеку то, что идёт по
пайпу, и спросить, пропускать ли дальше. Между «посмотреть, что
получилось» и «записать это в прод» появляется одна команда вместо
двух шагов через временный файл:

```
mpu run-js … | mpu confirm -m 'Записать в прод?' | mpu sheet set …
```

Вопрос задаётся **терминалу**, а не stdin: stdin занят данными, и
спрашивать по нему нечего. Это и есть причина, по которой команда
существует отдельно, а не растворена флагом `--confirm` в каждой
пишущей команде.

## CLI-контракт

```
mpu confirm [-m ТЕКСТ] [-y|--yes]
```

- `-m/--message ТЕКСТ` — текст вопроса; по умолчанию `Применить?`.
- `-y/--yes` — не спрашивать вовсе: ворота пропускают буфер молча, без
  эха и без вопроса. Форма для скриптов.
- Тулом MCP-сервера команда **не публикуется**: закрытый список
  публикации её не содержит (`platform/mcp-server.md`, fail-closed). У
  вызова тула нет ни stdin, ни терминала — у ворот не было бы ни
  данных, ни собеседника.
- Политика — `ro`: сама команда ничего не меняет, она пропускает либо
  отбивает чужие данные.

## Ввод/вывод

stdin читается целиком и всегда. Без `--yes` буфер эхо-печатается в
stderr дословно; перевод строки в конце добавляется, если его не было.
В stdout при этом уходит **исходный** буфер, без добавленного перевода:
ворота меняют судьбу данных, а не сами данные.

Вопрос печатается в терминал в форме `<текст> [y/N] `. Ответ читается
оттуда же, одной строкой. «Да» — `y` либо `yes`, регистр не важен,
обрамляющие пробелы снимаются. Пустой ответ, конец ввода и любое другое
слово означают «нет»: умолчание у ворот отрицательное.

Исходы:

- «да» → буфер в stdout, exit 0;
- «нет» → `mpu confirm: отменено — pipe прерван.` в stderr, exit 1,
  stdout пуст;
- терминала нет → отказ с диагностикой, exit 2, stdout пуст.

Буфер проходит через команду **текстом UTF-8**, а не байтами:
структурный результат команды контракта — JSON-объект
(`platform/command-contract.md`), и байтового поля в нём нет. Для ворот
над JSON и текстовыми выгрузками это равнозначно; двоичный поток через
`mpu confirm` пропускать нельзя.

## Побочные эффекты

Ни файлов, ни сети, ни состояния: единственное обращение наружу —
открытие `/dev/tty` на чтение и запись ради вопроса. При `--yes` не
делается и оно.

Запись журнала вызовов у команды без секций вывода
(`platform/invoke-log.md`, пометка «без записи вывода»): вывод здесь
дословно равен вводу, а это чужой буфер конвейера — журналу он не
принадлежит и приходит через stdin, мимо маски аргументов. Сама запись
о вызове остаётся.

## Конфигурация

Своих ключей env-файла у команды нет.

Права сборки: чтение `/dev/tty` покрыто общим `--allow-read`, запись —
уже объявленным `--allow-write=…,/dev/tty` (его завёл буфер обмена,
`platform/clipboard.md`). Новых прав команда не потребовала.

## Инварианты

- Ответ читается только из терминала. Данные stdin на исход не влияют
  никогда — иначе ворота отвечали бы сами себе содержимым буфера.
- Буфер в stdout побайтно равен прочитанному (с точностью до
  UTF-8-перекодировки), в том числе без добавленного эхом перевода
  строки.
- Отказ и отсутствие терминала не печатают в stdout ничего.
- `--yes` не открывает терминал и не печатает эха.

## Граничные случаи и ошибки

- Терминала нет (пайп без tty, cron, вызов тула) → exit 2, stdout пуст,
  в stderr:

```
mpu confirm: терминал недоступен для подтверждения. Используй `--yes` или two-step (`<команда> > /tmp/x.json` → проверить → `mpu sheet set <ssid> < /tmp/x.json`).
--- tty диагностика (как запущен mpu) ---
/dev/tty: открыть не удалось
fd 0 (stdin): isatty=false
fd 1 (stdout): isatty=false
fd 2 (stderr): isatty=false
имя устройства: недоступно — ttyname в Deno нет
```

- Пустой stdin — не ошибка: вопрос задаётся и на пустом буфере, а «да»
  пропускает пустоту дальше. Ворота не решают за конвейер, что данных
  мало.
- Ответ `undefined` (терминал закрыли, не ответив) равнозначен «нет».

## Golden-примеры

- `fixtures/confirm/confirm-stdout.txt` — пропущенный буфер.
- `fixtures/confirm/err-cancelled-stderr.txt` — отказ человека.
- `fixtures/confirm/err-no-tty-stderr.txt` — отсутствие терминала
  вместе с диагностикой. В живом прогоне ему предшествует строка эха:
  буфер показывается раньше, чем выясняется, что спросить некого, — и
  человек видит, что именно осталось непропущенным.

Все поверхности оканчиваются одним переводом строки.

## Известные отклонения

- **preserve частично** — имя устройства в диагностике. Рабочая версия
  печатает у каждого fd имя из `ttyname`; в Deno такого вызова нет, а
  ради диагностики тащить FFI незачем. Печатается то, что доступно
  (`isatty` каждого из трёх fd), а отсутствие имени названо отдельной
  строкой `имя устройства: недоступно — ttyname в Deno нет` — молча
  укоротить вывод значило бы оставить читателя в догадках, искали имя
  или нет.
- **preserve** — точка в конце текста `отменено — pipe прерван.`
  сохранена от рабочей версии, хотя общее правило текстов ошибок
  (`ts/CLAUDE.md`) точки не ставит.
