# mpu telegram log

Статус: реализовано

## Назначение

Отправить себе заметку или уведомление в личного Telegram-бота. В отличие от
`send`, отправка идёт от имени бота (Bot API), а не от личного аккаунта: чат с
ботом не виден командам `telegram ls` и `telegram search`, а текст сообщения не
попадает в журнал вызовов.

## CLI-контракт

```
mpu telegram log MESSAGE [-f PATH]
```

- `MESSAGE` — позиционный, обязателен. Значение `-` означает «весь stdin» и
  работает только в CLI-вызове: у вызова тула MCP-сервером stdin нет по
  построению, и `-` там даёт ошибку ввода `stdin у вызова тула нет — передай
  значение аргументом` (`platform/mcp-server.md`). Пустой (или состоящий из
  одних пробельных символов) `MESSAGE` допустим только вместе с `-f`.
- `-f/--file PATH` — вложение: **ровно один** файл. Флаг не повторяется, и
  повтор — ошибка ввода, exit 2, своим текстом
  (`option --file may be given only once`), а не «последний побеждает». Причина
  в протоколе: `sendDocument` Bot API несёт ровно один документ, а альбом —
  это уже `sendMediaGroup` с другой формой ответа. Путь в текст ошибки не
  попадает: ввод помеченной команды не эхо-печатается (см. «Инварианты»).
  У вызова тула путь приходит обычной строкой поля `file`; `-` там
  по-прежнему ошибка ввода, и относится она только к `MESSAGE`.
- Опции выбора адресата нет. Адресат единственный, из `TELEGRAM_BOT_ID`;
  опции его выбора нет намеренно: динамический адресат означал бы, что
  сообщение может уйти постороннему, написавшему боту. Вложение адресата не
  меняет.

`mpu telegram` без подкоманды печатает справку и завершается кодом 2 (общее
правило групп, `platform/registry.md`).

## Ввод/вывод

stdin читается целиком тогда и только тогда, когда `MESSAGE` равен `-`; с
`-f` это сочетается — текст из stdin становится подписью документа.

Без `-f` уходит текстовое сообщение. С `-f` уходит документ: файл под своим
базовым именем, без превью, а `MESSAGE` становится его **подписью**;
отдельного сообщения рядом с документом не отправляется — то же правило, что
у `telegram send`. Пустой `MESSAGE` при этом означает документ без подписи.

stdout — одна строка JSON, за ней один перевод строки; пробел после двоеточия
входит в форму:

```
{"id": 5000001}
```

Источник значения: `id` — `result.message_id` ответа Bot API. `chat_id` в вывод
не идёт намеренно: секция `out` пишется в журнал, и адресат оказался бы в ней.

## Побочные эффекты

Один POST на `https://api.telegram.org` — и с вложением он остаётся одним:
меняется метод. Без `-f` это `sendMessage` с телом JSON, с `-f` —
`sendDocument` с телом `multipart/form-data` (поля `chat_id`, `caption` —
только при непустой подписи, — и файловая часть `document`). Апдейты не
читаются, состояние не пишется, файлы не создаются; файл вложения только
читается.

## Конфигурация

Значения читаются из env-файла (слой — `platform/env-file.md`).

- `TELEGRAM_BOT_TOKEN` — обязателен. Токен бота от BotFather.
- `TELEGRAM_BOT_ID` — обязателен. `chat_id` получателя.
- `TELEGRAM_BOT_NAME` — необязателен. Username бота; попадает только в
  подсказку при отказе доставки. Пустое значение равнозначно незаданному.

Ключи сеанса MTProto (`TELEGRAM_API_ID`, `TELEGRAM_API_HASH`,
`TELEGRAM_SESSION`) команде не нужны: неавторизованный `mpu init` её не
блокирует.

Прокси берётся из первого непустого источника: `TELEGRAM_PROXY`, затем
`HTTPS_PROXY`, затем `https_proxy` — те же источники и то же старшинство, что
у сеанса MTProto (`platform/telegram-mtproto.md`). Канал другой, но сеть до
Telegram одна, и настраивать её дважды оператор не должен.

Набор схем **уже**, чем у MTProto: `http`, `https`, `socks5`, `socks5h`.
`socks4` и `socks4a` HTTP-клиент не принимает, хотя `mpu telegram send` через
них работает; отказ приходит до сети и называет причину (см. «Граничные
случаи»).

Пределы времени вызова — 15 s на заголовки и 30 s на весь вызов, шире
умолчания транспорта (3 s/10 s): умолчание отмерено на стенд в локальной сети,
а здесь внешний узел, обычно через прокси.

## Инварианты

- Адресат сообщения равен `TELEGRAM_BOT_ID` при любом вводе: другого источника
  адресата у команды нет — вложение адресата не меняет.
- Апдейты Bot API (`getUpdates`, webhook) не запрашиваются ни при каком исходе.
- Запись журнала вызовов не содержит ни текста сообщения, ни пути вложения ни
  в каком виде (`platform/invoke-log.md`). Аргументы в строке `$ mpu …`
  заменены маской, сообщения разбора argv ввод не эхо-печатают, а секция `err`
  записи с кодом выхода 2 заменяется маской целиком — иначе путь из текста
  `файл-вложение не найден: <путь>`, названного оператору на экране, вернулся
  бы в запись через неё. Секция `err` кода 1 (отказ Bot API, отказ
  конфигурации) при этом сохраняется дословно: ввода в ней нет.
- Значение `TELEGRAM_BOT_TOKEN` не появляется ни в stdout, ни в stderr, ни в
  журнале.
- Сеанс MTProto не открывается: отказ входа `mpu init` на команду не влияет.

## Граничные случаи и ошибки

- `MESSAGE` пуст либо состоит только из пробельных символов — как аргументом,
  так и через `-` из stdin — **и `-f` не задан** → `telegram: нужен непустой
  MESSAGE`, exit 2. С `-f` тот же ввод означает документ без подписи и ошибкой
  не является.
- Подпись длиннее предела Bot API (1024) → `telegram: подпись длиннее предела
  Bot API: <сколько> символов, можно 1024`, exit 2, до сети. Единица счёта —
  кодовые единицы UTF-16 (`string.length`): чем меряет сам Telegram, не
  проверено, а UTF-16 — граница консервативная (для всего BMP совпадает с
  кодовыми точками, расходится только на emoji и прочем astral) и ошибается в
  сторону понятного локального отказа, а не невнятного отказа после сети.
  Предел проверяется только у подписи: у текста сообщения он свой, 4096.
- Файл `-f` отсутствует, нечитаем либо это каталог → `mpu telegram log:
  файл-вложение не найден: <путь>`, exit 2, до сети. Префикс здесь общий, от
  точки входа: это отказ разбора аргументов, у него своя рамка
  (`telegram-send.md`, «Известные отклонения»). Порядок проверок — предел
  подписи раньше чтения файла: он не стоит обращения к диску.
- Повтор `-f` → `mpu telegram log: option --file may be given only once`,
  exit 2, до сети.
- У помеченной аргументами команды сообщения разбора ввода не эхо-печатают
  введённое: лишний позиционный аргумент даёт `unexpected argument REDACTED`,
  неизвестная опция — `unknown option REDACTED`. Иначе текст заметки попал бы в
  секцию `err` журнала (`platform/invoke-log.md`).
- `TELEGRAM_BOT_TOKEN` или `TELEGRAM_BOT_ID` отсутствует либо пуст → сообщение
  слоя env-файла с именем ключа и путём файла, exit 1.
- `TELEGRAM_BOT_ID` — не число → `telegram: TELEGRAM_BOT_ID должен быть числом,
  получено '<строка>'`, exit 1. Ведущий минус допустим: так выглядят id групп и
  каналов.
- Прокси заданной схемы, которой клиент не понимает (`socks4`, `socks4a` и
  прочие вне списка) → `telegram: Bot API не умеет прокси <схема>;
  поддерживаются http/https/socks5/socks5h (у mpu telegram send прокси свой,
  через MTProto, и socks4 там работает)`, exit 1, до сети.
- Прокси-URL без `host:port` → `telegram: в прокси-URL нужен host:port —
  '<url>'`, exit 1. Неразбираемый URL → `telegram: прокси-URL неразбираем —
  '<url>'`, exit 1.
- Ответ с `ok: false` → `telegram: bot API <error_code> <description>`, exit 1.
- Описание отказа содержит `chat not found` либо `bot was blocked` → тот же
  текст плюс `; напиши боту @<name> /start`; часть `@<name>` присутствует
  только при заданном `TELEGRAM_BOT_NAME`.
- Тело ответа не разбирается как JSON → `telegram: bot API вернул не JSON:
  <первая строка тела>`, exit 1.
- Ответ с `ok: true` без `result.message_id` → `telegram: bot API не сообщил
  номер сообщения`, exit 1.
- Сбой вызова (сеть, предел времени) → `telegram: bot API недоступен: <причина
  одной строкой>`, exit 1.

## Golden-примеры

- `fixtures/telegram-log/log-stdout.txt` — успешная отправка.
- `fixtures/telegram-log/err-empty-text-stderr.txt` — пустой `MESSAGE`.
- `fixtures/telegram-log/err-caption-long-stderr.txt` — подпись длиннее
  предела.
- `fixtures/telegram-log/err-file-missing-stderr.txt` — файл `-f` не найден.

Все поверхности оканчиваются одним переводом строки.
