# mpu-task — оркестратор ролей (порция T3)

Статус: к реализации — порция T3 серии оркестратора (после T1 `task.md` и
T2 `task-roles.md`). Написана хостом 2026-09-25 по дизайну оркестратора и
по механике, отработанной руками в сериях 157–169 (запуск окна, `/clear`,
ожидание простоя); полная проверка — автором по списку.

## Назначение

Работа по плану идёт порция за порцией без человека: хост принимает отчёт и
кладёт следующую постановку, исполнитель берёт её с чистым контекстом.
Человек нужен только там, где правила проекта не решают. Сейчас эту работу
руками делает хост: открывает окно, чистит контекст, ждёт простоя, будит.
`mpu-task` делает её сам и переживает падение окон, перезагрузку и закрытие
терминала.

## Процесс

`mpu-task` — третий ребёнок `mpu-supervisor` рядом с `back` и `mcp`: та же
служба, тот же перезапуск с паузами, строки лога с префиксом `[task] `
(`platform/supervisor-install.md`). Каждые 5 с — **шаг** по каждому проекту,
у которого есть хотя бы один профиль роли (`task-roles.md`) и который не
остановлен.

## CLI-контракт

```
mpu task stop project: <имя> [text: ^причина^]
mpu task resume project: <имя>
```

`stop` пишет в журнал сообщение вида `stop` (тело — причина, умолчание
`стоп`) и останавливает шаги проекта; `resume` — вид `resume`, шаги идут.
Остановлен ли проект — вывод журнала (последнее из `stop`/`resume`), в
`status` (`task.md`) ход такого проекта — `остановлен`. Виды `stop` и
`resume` добавляются к списку `kind:` у `read`/`wait` и к тексту отказа
T17 `task.md`. Посев: `stop` —
`allow` (хост останавливает на блокере), `resume` — `ask` (решает человек).

## Решения хоста по вопросам исполнителя T3 (2026-09-26)

1. Супервизор: `mpu-supervisor --back <п> --mcp <п> --task <п>`, флаг
   обязательный; эталон `fixtures/supervisor-install/mpu.service` и
   `platform/supervisor-install.md` поправлены. У `mpu-task` аргументов нет.
2. Хода нет (журнал пуст или последний `task` прочитан) — «Что делать
   сейчас»: `дела нет — жди: mpu task wait project: <п> kind: task` (у хоста —
   `kind: report`).
3. `claude` не запускается процессом: строка набирается в оболочке окна tmux.
   Права: `--allow-run=/usr/bin/tmux,/usr/bin/notify-send` абсолютными путями
   (снято: `tmux` — `/usr/bin/tmux`); `notify-send` на машине нет —
   уведомление остаётся строкой лога `[task] …`.
4. `stop`/`resume` в проекте без порций — пишутся в порцию 0, без отказа.
5. Ожидания (проверка запуска, простой после `/clear`, `busy` после
   сообщения) — состояние роли со сроком, проверяется на каждом шаге; шаг их
   не ждёт; пауза 2 с перед Enter — внутри шага через порт часов.
   Транзакция — только на снимок журнала и отметок, не на нажатия.
6. Три неудачи очистки (нет `busy` за 60 с после сообщения) — как у запуска:
   роль остановлена до перезапуска службы, одно уведомление `[task] <п> <р>:
   не будится (3 попытки) — вернуть: systemctl --user restart mpu`; иначе
   `/clear` раз в минуту без конца.
7. `install.sh`: изменился только `mpu-task` — перезапуск службы целиком, как
   при изменении супервизора (сигнала для третьего ребёнка нет).
8. (приёмка T3) Признак модели — строка баннера, `/model` не шлётся (см.
   «Шаг проекта», п. 2; сценарии O11, O11b).
9. (приёмка T3) Чистка журнала не удаляет действующий `stop` (последнее из
   `stop`/`resume` — `stop`), как правило и открытый `owner`.
10. (приёмка T3) `Capacity` может посчитать роль дважды (отметка `busy` в
    фазе ожидания) до следующего шага — осторожно, оставлено.
11. Литерал O4 — с хвостом `— вернуть: systemctl --user restart mpu`.

## Шаг проекта

В этом порядке, до первого действия:

1. **Окно.** Нет окна роли (`<сессия>:<окно>` профиля) или в нём не
   Claude (текущая команда панели не `claude`) — **запуск** роли.
2. **Модель.** Строка баннера окна (вторая строка логотипа, снято
   2026-09-26 на Claude Code 2.1.283: `▝▜██████▀  Sonnet 5 · Claude Max`)
   называет модель не из профиля — в простое закрыть окно; следующий шаг
   запустит его с `--model`. `/model` оркестратор **не шлёт**: снято, что
   `/model opus` сохраняет модель умолчанием для всех новых сессий
   пользователя (`Set model to Opus 5.5 and saved as your default for new
   sessions`), а баннер после него не меняется. Признак — только строка
   баннера: имя модели в тексте роли на экране признаком не служит. Баннер
   остаётся на экране после `/clear` (снято там же).
3. **Ход** по журналу канала (`task.md`):
   - последний `report` не прочитан и хост `idle` → **очистка** хоста,
     первое сообщение — «прими порцию N по отчёту; спека и постановка N+1 по
     плану; положи `mpu task post`»;
   - последний `task` не прочитан и исполнитель `idle` → **очистка**
     исполнителя, первое сообщение — «прочитай `mpu task read project: <п>`
     и выполняй»;
   - последний `question` не отвечен и хост `idle` → очистка хоста, вопрос в
     первом сообщении; хост `busy` — ничего (он видит канал сам).
4. **Стоп.** Последнее сообщение `owner` без ответа дольше часа — одно
   уведомление; `mpu task stop project:` — проект замирает до `mpu task
   resume project:`, уведомление.

**Отметки, а не экран.** Занята ли роль, шаг узнаёт по отметке
(`task busy|idle`); экран читается только для «окно живо, в нём Claude,
модель». `busy` без нового сообщения в журнале дольше часа — уведомление,
очистки нет. Очистка — только при `idle`.

## Запуск роли

1. Сессия профиля есть — окно в ней; нет — создать сессию.
2. Файл первого сообщения `$XDG_RUNTIME_DIR/mpu-task/<проект>/<роль>.md`
   (состав — ниже).
3. `claude "Прочитай файл <путь> целиком и выполняй его." --permission-mode
   <режим> --model <модель> --name <окно> [--add-dir <каталог>]…` в каталоге
   профиля: **сообщение первым аргументом** — `--add-dir` вариадический и
   съедает строку после себя (поймано живьём 15.09.2026). Enter — отдельным
   нажатием через 2 с.
4. Проверка до 60 с: на экране строка `❯ Прочитай файл <путь>`, модель
   профиля в баннере, `auto mode on` (у режима `auto`). Не сошлось — закрыть
   окно, повторить; три неудачи подряд — роль остановлена, уведомление.
   Экран «Do you trust the files in this folder?» — уведомление «подтвердите
   доверие в окне <окно>», повторов нет.

## Очистка роли

Только при `idle`: `/clear` (Enter отдельно) → до 60 с экран без «esc to
interrupt» → проверка модели → «Прочитай файл <первое сообщение> целиком и
выполняй его.» (Enter отдельно) → до 60 с отметка роли `busy`. Нет `busy` —
повтор; три — уведомление.

**Упавшая роль** (окно умерло при `busy`): запуск с тем же первым
сообщением и строкой «продолжай с первого незакрытого раздела, сверяясь с
`git log` и `git status`».

## Первое сообщение

Файл в `$XDG_RUNTIME_DIR/mpu-task/<проект>/<роль>.md`, markdown, разделы в
порядке:

1. `# Роль: <host|exec> проекта <проект>` и полномочия профиля дословно.
2. `## Канал` — `mpu task … project: <проект>`; «сразу после начала работы —
   `mpu task busy project: <п> role: <р>`, по окончании — `idle`»; вопрос
   хосту — `mpu task question`, владельцу (хост) — `mpu task owner`.
3. `## Что делать сейчас` — строка хода (раздел «Шаг проекта»).
4. `## Прочитать первым` — пути `read:` профиля.
5. `## Правила и решения` — вывод `mpu task decisions project: <п>` (правила,
   решения последних порций, открытые ответы владельца).

## Уведомления

Строка в лог службы `[task] <проект> <роль>: <что>` и
`notify-send "mpu task" "<проект> <роль>: <что>"`, если `notify-send` есть
(`platform/claude-hook-notification.md` — тот же способ). Одно уведомление на
событие: повтор того же события на следующих шагах — молча.

## Параллельные проекты

- Шаг проекта — транзакция SQLite с блокировкой проекта; ожидания (простой,
  60 с проверки) — отдельные задачи со сроком, шаг их не ждёт.
- Предел одновременно `busy` ролей по всем проектам — ключ конфига
  `task.max_busy` (int, 4); сверх него очистка и запуск ждут следующего шага.

## Порты и права

Окна (`tmux`), запуск `claude`, часы, уведомления — порты `mpu-task`, в
тестах подменяются. Права Deno задачи `task` (и `compile:task`): запуск
`tmux`, `claude`, `notify-send`; кэш-БД; запись
`$XDG_RUNTIME_DIR/mpu-task/` — каждое строкой с обоснованием и проверкой
(`ts/CLAUDE.md`, «Права Deno»).

## Сценарии

Стенд: поддельный tmux в памяти (окна, панели, текущая команда, экран) и
поддельная роль-программа вместо `claude`: печатает баннер с моделью и `❯
<первый аргумент>`, ставит отметки настоящим `mpu task busy|idle` на стенде
канала, умеет «упасть», «зависнуть», «показать не ту модель», «показать
диалог доверия». Часы — порт. Проект `demo`: профили `host` и `exec` (T2),
`dir:` — временные каталоги.
