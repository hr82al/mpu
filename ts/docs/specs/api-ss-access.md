# mpu api ss-access — доступ к таблице клиента

**Статус:** к реализации (2026-08-28). Контракт неймспейса — `api.md`,
обвязка — `platform/slback-http.md`.

## Назначение

Первая из трёх кастомных групп остатка `api`: четыре команды над доступом к
Google-таблице клиента. Механика своя, и потому группа отдельная — авто-тело
из умолчаний кнопки sl-front плюс резолв идентификатора выдачи **прямо из
main-БД**, а не из ответа сервера.

```
mpu api ss-access request ТАБЛИЦА [--role R] [--reason T] [--template U] [-b JSON|@файл]
mpu api ss-access status  ТАБЛИЦА
mpu api ss-access revoke  ТАБЛИЦА [--grant-id G] [--reason T]
mpu api ss-access reset   ТАБЛИЦА [--reason T] [--role R] [--template U]
```

Получатель доступа всегда — владелец токена (`TOKEN_EMAIL`), как у кнопки:
эндпоинт выдаёт доступ тому, чьим токеном ходят. Своего параметра у этого нет
и быть не должно.

## Механики группы

1. **Авто-тело.** `request` без опций отправляет умолчания кнопки:
   роль `editor`, обоснование по умолчанию, шаблон `null`. Точечные опции
   (`--role`, `--reason`, `--template`) правят поля; `--body` заменяет тело
   целиком и отменяет их. `@файл` читает тело из файла.

2. **Резолв идентификатора выдачи из main-БД.** `revoke` без `--grant-id`
   ищет выдачи в `public.spreadsheets_access_grants` со статусами `created`,
   `permission_added`, `applied` — теми, что входят в частичный уникальный
   индекс активной выдачи. То есть команда знает про схему базы, а не только
   про HTTP. Запрос дословно:

   ```sql
   SELECT grant_id FROM public.spreadsheets_access_grants
   WHERE spreadsheet_id = $1 AND grantee_email = $2
     AND status IN ('created', 'permission_added', 'applied')
   ```

   **Схема — такой же стык, как форма ответа службы, и снимается так же.**
   Голден состава колонок — `fixtures/api/schema/spreadsheets_access_grants.columns`,
   снят со стенда `information_schema.columns` 2026-08-28. Ключ выдачи зовётся
   `grant_id`, не `id`; колонки `id` в таблице нет вовсе.

   Голден проверяем **без доступа к базе только на состав**; при поднятом
   стенде его надо сверять с живым `information_schema.columns` — расхождение
   красит проверку. Это дешевле, чем сверять реализацию с реализацией.

3. **Ожидание с пределом.** `reset` = отозвать все найденные выдачи →
   **дождаться их исчезновения из индекса** → выдать заново. Опрос с
   интервалом и предельным сроком; истёк — код 1 с подсказкой, что конвейер
   отзыва сломан.

## Литералы и пути, снятые с объекта

Дословно, чтобы авто-тело совпадало с кнопкой sl-front, а не с догадкой:

| что | значение |
|---|---|
| умолчание `--reason` у `request` и `reset` | `Диагностика проблемы по обращению клиента` |
| умолчание `--role` | `editor` |
| умолчание `--reason` у `revoke` | `revoke via mpu` |
| причина отзыва внутри `reset` | `reset via mpu` (не берётся из `--reason`) |
| интервал опроса у `reset` | 3 секунды |
| предел ожидания у `reset` | 60 секунд |

Пути:

- `request` → `POST /admin/ss/<ss>/my-access/request`, тело
  `{"googleSheetsRole": …, "reason": …, "accessTemplateId": …}`;
- `status` → `GET /admin/ss/<ss>/my-access`;
- `revoke` → **своего эндпоинта нет**: ставится job через
  `POST /admin/jobs/ss` с телом
  `{"type": "accessGrantRevoke", "data": {"grantId": …, "revokedByUserId": null, "reason": …}}`.
  Тот же путь, что у переехавшей `ss-jobs-submit`.

Обратить внимание на две пары, которые легко слить в одну:

1. **умолчание `--reason` у `revoke` и причина внутри `reset` — разные
   строки** (`revoke via mpu` против `reset via mpu`). Внутри `reset` причина
   не берётся из `--reason`: та относится к последующей выдаче, а не к отзыву;
2. **`--reason` у `reset` — это обоснование выдачи**, и его умолчание равно
   умолчанию `request`, а не отзыва.

## Инварианты

1. **Ожидание не бесконечно и не молчаливо.** У опроса есть предел; при
   исчерпании — код 1, текст называет предел в секундах и то, что выдача
   осталась в индексе. Молчаливый успех после истечения запрещён.

2. **Величина берётся из работы.** Строка «отозвано N выдач» печатает число
   **найденных и отозванных**, а не число попыток и не длину входа
   (`CLAUDE.md`, «Величина берётся там, где совершается работа»). При нуле
   найденных строки нет вовсе — отзывать было нечего, и это отличается от
   «отозвали ноль».

3. **`--body` отменяет точечные опции, а не смешивается с ними.** Иначе у
   одного поля два источника и неявный порядок старшинства.

4. **Отказ базы отличается от отказа сервера.** Недоступная main-БД при
   резолве — код 2 с указанием, что упал резолв, а не запрос к sl-back:
   иначе оператор чинит не то.

5. **Статус читает, а не меняет.** `status` — только чтение.

6. **Активная выдача единственна, и это допущение проверяется.** Единственность
   держит не наш код, а частичный уникальный индекс базы:

   ```sql
   CREATE UNIQUE INDEX idx_spreadsheets_access_grants_unique_active_grant
     ON public.spreadsheets_access_grants (spreadsheet_id, grantee_email)
     WHERE status = ANY (ARRAY['created','permission_added','applied'])
   ```

   Уникальность идёт по паре (таблица, почта) ровно по тем статусам, по
   которым ищет резолв, — значит выдач не может быть больше одной. На этом
   допущении стоит вся группа: цикл на одну строку, `reset` без выбора «какую
   из», ожидание одной выдачи.

   Поэтому резолв **отбивается**, найдя больше одной: индекс — внешняя вещь,
   его могут снять или добавить четвёртый статус, и тогда молчаливая работа по
   неверной картине мира отозвала бы лишнее. Отказ называет индекс поимённо и
   говорит, что схема разошлась со снимком.

   Сторожить обратное — обрабатывать «частичный отзыв N из M» — не нужно:
   код, стерегущий невозможное состояние, читается как утверждение, что оно
   бывает (замер 2026-08-28: вставка второй активной выдачи отбивается самим
   индексом).

## Граничные случаи и ошибки

- `--body` с невалидным JSON → код 2, назвать позицию ошибки;
- `--body @файл`, файла нет → код 2 с путём;
- `revoke`, выдач не найдено и `--grant-id` не задан → код 0 и сообщение,
  что отзывать нечего (не отказ: состояние уже целевое);
- main-БД недоступна → код 2 (инвариант 4);
- `reset`, предел ожидания истёк → код 1 с подсказкой про ручное истечение
  застрявшей строки.

## Проверка — только на локальном стенде

Как и весь `api` (указание владельца 2026-08-28), **включая читающий
`status`**. Стенд: `mp-api` на `127.0.0.1:5000`, базовый путь `/api`, вход
`admin@test.com`; направляется подменным `XDG_CONFIG_HOME`.

Ограничение стенда, которое надо учесть заранее: клиентов на нём завести
нельзя (`no instance servers available to place client`), поэтому таблицу с
выдачей придётся либо готовить вставкой в main-БД стенда, либо признать
непроверяемым и сказать это прямо, а не выдать за проверенное.

## Приёмка

- `request` без опций отправляет умолчания кнопки — сверка тела запроса;
- `--body` отменяет точечные опции;
- `revoke` без выдач — код 0 и сообщение, что отзывать нечего;
- резолв идёт по трём статусам индекса, а не по всем;
- `reset` при неисчезающей выдаче упирается в предел и даёт код 1;
- недоступная main-БД даёт код 2 с указанием на резолв.
