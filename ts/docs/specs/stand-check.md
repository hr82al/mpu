# mpu stand check --shell

Статус: черновик (2026-09-10 — постановка по живым случаям; к реализации — после ответа на
«Открытые вопросы»)

## Назначение

Диагноз, почему конкретный экран не открывается в оболочке локального стенда (`sw.localhost`):
пройти цепочку «оболочка → sw-back → инстанс sl-N пространства → инструмент вертикали» и назвать
первое звено, которое рвётся, — погашенный контейнер, гейт онбординга, незарегистрированный
инструмент, фрейм, который не дорисовался. Только чтение; починку предлагает текстом.

**Живые случаи (2026-09-10).**

- Новая вкладка `http://sw.localhost/ozon/checklist/54` висела на спиннере: консоль — 502 на
  `/api/v2/subscriptions/workspaces/54/statuses` с текстом sw-back `"sl-1" did not answer at its
  last known address mp-sl-1-i-internal-api:5100: getaddrinfo`. Весь стек `sl-1` был погашен
  (`sl-1-cli`, `sl-1-pg`, `sl-1-redis` — `Exited`, `internal-api` не было вовсе). Лечение —
  подъём стека `sl-1`.
- После подъёма тот же адрес давал 404 на статусах подписок, а iframe инструмента появлялся через
  ~7,5 с после загрузки (режим разработки): проба «сразу после `networkidle`» видела пустую
  страницу, хотя экран работал.
- `http://sw.localhost/ozon/fin-report/54` показывал модалку «OZON ещё не подключён»: гейт
  онбординга оболочки (`sw-front`, страница `ozon/[screen]/[id]`, набор инструментов, пропускаемых
  мимо гейта). Локально Ozon у пространства не «подключён» — экран закрыт не поломкой, а гейтом.
- Раньше в поставке: инструмент `checklist` не открывался в оболочке, пока его не
  зарегистрировали в списке инструментов домена Ozon (`sw-front`, модель доменов маркетплейса);
  браузер служебного Playwright ходит через прокси VPN-контейнера, и после перезапуска контейнера
  в его hosts пропадала запись `sw.localhost`.

Смежный инструмент рабочей области (`mp-stand check`) проверяет коды ответа фиксированного набора
адресов (оболочка, один инструмент, health инстансов), но не ведёт цепочку от конкретного экрана и
пространства и не видит гейт, регистрацию и позднюю отрисовку; дублем команда не является —
см. «Открытые вопросы» о месте.

## CLI-контракт

`mpu stand check --shell <URL> [--wait SEC] [--json]`

- `URL` — адрес экрана в оболочке (`http://sw.localhost/ozon/checklist/54`); из него берутся
  вертикаль (`ozon`), инструмент (`checklist`) и пространство (`54`).
- `--wait` — сколько ждать отрисовки фрейма инструмента; дефолт 40 с (живой замер — 7,5 с в режиме
  разработки).
- `--json` — вместо отчёта JSON-массив звеньев.

Политика — `ro`: HTTP-запросы на чтение, `docker ps`, чтение исходников оболочки.

## Ввод/вывод

### Звенья по порядку (первое упавшее — диагноз; последующие проверяются и печатаются)

1. **Имя** — `sw.localhost` разрешается там, откуда ходит браузер (хост и прокси-контейнер VPN);
   нет → `hosts`.
2. **Оболочка** — `GET http://sw.localhost/` → 2xx.
3. **Инструмент зарегистрирован** — идентификатор инструмента есть в списке инструментов домена
   вертикали в исходнике оболочки; нет → `not-registered`.
4. **Гейт онбординга** — инструмент не входит в набор пропускаемых мимо гейта, а статус
   онбординга пространства не «подключён» → `onboarding-gate` (экран закроется модалкой).
5. **Инстанс пространства** — какой sl-инстанс держит пространство (источник — открытый вопрос),
   его контейнеры в `docker ps` (`sl-N-*`, `internal-api`); погашены → `instance-down` с именем
   стека.
6. **Статусы подписок** — `GET /api/v2/subscriptions/workspaces/<ws>/statuses` через оболочку (с
   сессией пользователя): 502 → смотрится тело ответа; текст `did not answer at its last known
   address` → `instance-down`; 404 → `subscriptions-404` (живьём было после подъёма стека — причина
   не выяснена, см. «Открытые вопросы»).
7. **Сервис вертикали** — для `ozon`: контейнеры `ozon-front`, `ozon-datacore` в `docker ps`;
   health.
8. **Фрейм** — страница экрана в headless-браузере: iframe инструмента появился за `--wait` и в нём
   есть узел готовности (для таблиц — ячейка с датой `ДД.ММ.ГГГГ`); не появился → `frame-timeout`
   со временем ожидания.

### Звено

`{ step, ok, code, detail, fix }` — `code` из названных выше, `fix` — текст починки
(`поднять стек sl-1`, `добавить sw.localhost в hosts прокси-контейнера`, `добавить инструмент в
набор пропускаемых мимо гейта — правка sw-front, для локальной сверки временно`,
`зарегистрировать инструмент в домене вертикали`).

Отчёт: строка на звено `✓`/`✗` `<step>: <detail>`, под упавшими — `  починка: <fix>`; последняя
строка — `диагноз: <code первого упавшего>` или `экран открывается`.

## Побочные эффекты

Нет: команда ничего не поднимает, не правит и не регистрирует.

## Конфигурация

Сессия пользователя для звена 6 — открытый вопрос (браузерная сессия служебного Playwright или
токен sw-back).

## Инварианты

- Диагноз — первое упавшее звено по порядку; поздние звенья печатаются, но диагнозом не становятся.
- «Экран закрыт гейтом» и «экран сломан» — разные коды.

## Граничные случаи и ошибки

- URL не из оболочки → exit 2.
- Exit 0 — экран открывается; 1 — есть упавшее звено.

## Golden-примеры

Нет — снимаются при реализации: стенд с погашенным стеком инстанса (502 с текстом sw-back), стенд
с инструментом вне набора гейта, стенд в порядке.

## Открытые вопросы

- Место команды: `mpu stand …` или расширение `mp-stand check` в `ai-tools`, где уже лежат подъём
  стенда и соседние проверки. Решение владельца не принималось.
- Откуда брать соответствие «пространство → sl-инстанс» (PG sw-back, ответ API оболочки, конфиг
  стенда) — факта о каноническом источнике в этой сессии нет.
- Причина 404 на статусах подписок после подъёма `sl-1` — не выяснялась; экран при этом работал.
- Сессия пользователя для звена 6: чем авторизоваться без браузера — не проверялось.
