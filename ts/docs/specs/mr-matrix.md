# mpu mr matrix

Статус: черновик (2026-09-10 — постановка по живому случаю; к реализации — после ответа на
«Открытые вопросы»)

## Назначение

Все мои открытые MR одной таблицей — состояние, которое сегодня собирается руками из пяти
источников: конфликт с целевой веткой, конвейер, открытые обсуждения, стек веток (MR стоит на
другом MR) и невыгруженные локальные коммиты. Только чтение: ни GitLab, ни локальные ветки команда
не меняет.

**Живой случай (2026-09-10).** Перед выгрузкой трёх MR поставки «Чек-лист» в `wb/ozon` состояние
собиралось так:

- список — `glab mr list --author=@me` → `!556`, `!558`, `!559`;
- по каждому — `glab mr view <iid> -F json` → `detailed_merge_status: conflict`,
  `head_pipeline.status: success`, `blocking_discussions_resolved: true`;
- конфликт с целевой — `git fetch` и `git merge-tree --write-tree --name-only origin/main
  origin/<source>` в локальном чекауте: у всех трёх `CONFLICT (content)` в `docs/decisions.md`, у
  `!559` ещё в `docs/structure.md`; конфликты только в документах — это видно лишь по списку
  файлов, флаг `conflict` GitLab этого не говорит;
- стек — `git merge-base --is-ancestor origin/<source !558> origin/<source !559>` → `!559` стоит
  на `!558`, `!558` на `!556` — нет;
- невыгруженное — `git status -sb` в worktree ветки `!559` → `ahead 10`.

Итог таблицы для владельца складывался из этих пяти ответов вручную. Смежная команда
`glab-status.md` отвечает на другой вопрос — до каких веток деплой-пайплайна доехал MR — и
конфликтов, обсуждений, стека и локальных коммитов не показывает; дублем эта команда не является.

Авторизация, HTTP-клиент, пагинация и формы ответов GitLab — `platform/gitlab-api.md` (далее —
атом); рабочая область и её репозитории — `platform/code-analyzer.md`, раздел «Ввод/вывод».

## CLI-контракт

`mpu mr matrix [--repos REPOS] [--no-fetch] [--json]`

- `--repos` — репозитории: повторяемый флаг и/или значения через запятую; имя без `/` получает
  префикс `wb/` (как в `glab-status.md`). Дефолт — **все** репозитории, где у меня есть открытые
  MR (фильтра по списку нет).
- `--no-fetch` — не обновлять удалённые ветки в локальных чекаутах перед сравнением; колонка
  `conflict` тогда считается по уже имеющимся `origin/*` и помечается `(устар.?)`, если последний
  fetch старше часа (время — mtime `FETCH_HEAD`).
- `--json` — вместо таблицы JSON-массив строк.

Политика — `ro`: GitLab только читается; локально выполняется лишь `git fetch` удалённых веток
(обновляет `refs/remotes/*` чекаута, рабочее дерево и локальные ветки не трогает) и
`git merge-tree` (ничего не пишет в рабочее дерево и индекс). См. «Побочные эффекты».

## Ввод/вывод

### Источники

1. Список — GET `/merge_requests?scope=created_by_me&state=opened` (пагинация — атом); project
   восстанавливается из `web_url`, как в `glab-status.md`.
2. По каждому MR — GET `/projects/{project}/merge_requests/{iid}` → `detailed_merge_status`,
   `head_pipeline.status` (нет конвейера → `null`), `blocking_discussions_resolved`, `sha`,
   `source_branch`, `target_branch`.
3. Обсуждения — GET `/projects/{project}/merge_requests/{iid}/discussions` (атом): число тредов с
   `resolvable: true` и `resolved: false`.
4. Локальный чекаут — репозиторий рабочей области с тем же именем, что последний сегмент project
   (`wb/ozon` → `<рабочая область>/ozon`). Нет такого каталога → колонки `conflict`, `stack`,
   `local` = `(нет чекаута)`, остальное печатается.
5. Конфликт — `git merge-tree --write-tree --name-only origin/<target> origin/<source>` в чекауте:
   код выхода 1 и строки `CONFLICT (…): Merge conflict in <path>` → список путей; код 0 → пусто.
6. Стек — MR A стоит на MR B, если оба в одном project, `origin/<source B>` — предок
   `origin/<source A>` (`git merge-base --is-ancestor`) и `origin/<source B>` не предок
   `origin/<target A>` (иначе B уже влит и стеком это не считается).
7. Невыгруженное — по всем worktree чекаута (`git worktree list --porcelain`) и по самому чекауту:
   локальная ветка с именем `source_branch` → ahead/behind против `origin/<source>`
   (`git rev-list --left-right --count`); путь worktree, где она выписана.

### Строка результата (одна на MR; `--json`)

`repo`, `iid`, `title`, `source_branch`, `target_branch`, `web_url` — из API;
`pipeline` — `head_pipeline.status` | null;
`gitlab_merge_status` — `detailed_merge_status` как есть;
`unresolved_threads` — число (источник 3);
`conflict_files` — массив путей (источник 5) | null без чекаута;
`stacked_on` — iid MR, на котором стоит этот | null;
`local` — `{ worktree, ahead, behind }` | null (локальной ветки нет);
`fetched_at` — ISO-время последнего fetch чекаута.

### Таблица (без `--json`)

Колонки: `repo`, `MR`, `ветки` (`source → target`), `конвейер`, `конфликт`, `треды`, `стек`,
`локально`. Ячейка `конфликт`: пусто → `—`; иначе число файлов и первые два пути
(`2: docs/decisions.md, docs/structure.md`). `стек`: `на !558` | пусто. `локально`: `+10 −0
(wt/ozon/checklist-k4)` | `нет ветки`. Порядок строк — (repo, iid). Таблица оканчивается переводом
строки; после неё — строка-подвал `обновлено: <fetched_at>` для каждого чекаута, если был fetch.

## Побочные эффекты

`git fetch origin` в каждом задействованном чекауте (кроме `--no-fetch`): меняет только
`refs/remotes/origin/*` и `FETCH_HEAD`. Больше ничего: ни веток, ни рабочего дерева, ни стеша, ни
GitLab.

## Конфигурация

Нет своей. Токен GitLab — атом; рабочая область — сентинел `.mp-workspace-root`.

## Инварианты

- Команда не пишет в GitLab и не меняет ни одной локальной ветки и рабочего дерева.
- `conflict_files` берётся из `merge-tree`, а не из `detailed_merge_status`: флаг GitLab
  говорит «есть конфликт», но не где он.
- Отсутствие чекаута — не ошибка: строка печатается с пометками.

## Граничные случаи и ошибки

- Нет открытых MR → stderr `(нет моих открытых MR)`, exit 0; `--json` → `[]`.
- `git fetch` упал (сеть, права) → строка печатается по старым `origin/*`, ячейка `конфликт`
  получает `(fetch не удался)`; exit 0, в stderr — текст ошибки git один раз на чекаут.
- Source-ветки нет на origin (удалена) → `conflict` = `(нет ветки на origin)`.
- Ошибка API списка → exit 1 с сообщением атома.

## Golden-примеры

Нет — снимаются при реализации с живого набора (`wb/ozon` 2026-09-10: три MR, у всех
`conflict_files` непуст, `!559` стоит на `!558`, у `!559` `+10`). Голден обезличивается по правилам
атома.

## Открытые вопросы

- Имя чекаута: всегда ли совпадает с последним сегментом project? В рабочей области так у всех
  известных репозиториев; исключений не наблюдалось, но и не проверялось перечнем.
- Нужен ли режим `--mine=false` (все открытые MR проекта, не только мои) — случая не было.
- Стек через `merge-base` не отличает «B стоит под A» от «A и B содержат общий сторонний коммит».
  В живом случае ветки `!558` и `!559` отведены одна от другой; проверить на ложное срабатывание при
  реализации.
