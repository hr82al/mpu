`fixtures/sql-ro/`. Маршрут sw вынесен в `specs/sql-sw.md` и едет

это время. 2026-08-05, вторая правка: исполнение текста переведено на
обёртку транзакцией с меткой — замер показал, что одна опция сессии

## Назначение

Ad-hoc SQL по селектору в enforced read-only PG-сессии — безопасный
дефолт для диагностического чтения: запрет записи гарантирует сам
PostgreSQL, не анализ текста SQL. Write-вариант — `specs/sql.md`.

## CLI-контракт

`mpu sql-ro SELECTOR [SQL] [--server sl-N] [--dry] [--json] [--md]
[-v/--verbose]`

`SELECTOR` — client_id / spreadsheet_id substring / title substring /
`sl-N` / sw-алиас / `dev:<client_id>`; `SQL` — необязательный второй
аргумент; `--server sl-N` — override резолва; `--dry` — только
meta-блок, без единого подключения, exit 0; `--json` / `--md` — формат
результата; `-v/--verbose` — печатать meta-блок; `-h/--help`. Без
аргументов — справка, exit 2. `--json` вместе с `--md` → exit 2,
`mpu sql-ro: --json и --md взаимоисключающие` — проверяется первым, до
чтения SQL и до резолва селектора.

Источник SQL, первый непустой (после trim) побеждает: (1) аргумент;
(2) stdin целиком, если stdin не терминал, — без приглашения;
(3) интерактивный ввод до EOF, в stderr приглашение
`-- enter SQL, end with EOF (Ctrl+D):`. Итог пуст (после trim) →
exit 2, `mpu sql-ro: empty SQL`, без подключения к БД.

Три маршрута по селектору, первое совпадение побеждает; `--server`
совместим только с обычным, с dev-селектором → exit 2 до чтения SQL:
`mpu sql-ro: --server не сочетается с dev-селектором`.

1. **dev** — префикс `dev:`; подключение к dev-PG. Хвост-число →
   client_id (ставится search_path), иначе client_id нет (не ошибка).
2. **sw** — алиас из `{sw, sw-pg, swpg, sw-back, swback, ws,
   workspaces}` без учёта регистра и краевых пробелов: SQL исполняется
   в БД воркспейсов — `specs/sql-sw.md`. До реализации той спеки вызов
   с sw-алиасом целиком делегируется прежней реализации (подпроцесс по
   маршруту `legacy`, `platform/registry.md`): argv передаётся как есть,
   stdin/stdout/stderr и код выхода проходят насквозь, разбора вывода
   нет. Наблюдаемое поведение sw-вызова этой порцией не меняется —
   включая проверку `--json`/`--md` и текст
   `mpu sql-ro: --server не сочетается с sw-селектором`.
3. **обычный** — резолв селектора (`platform/selector.md`, выполняется
   до чтения SQL) → номер сервера + кандидаты. Среди кандидатов ровно
   один различный client_id → search_path на его схему; иначе (0 или
   больше одного) search_path не ставится — запрос идёт в дефолтный
   search_path сервера. При `--server` резолв не выполняется: селектор
   игнорируется (несуществующий — не ошибка), search_path не ставится.

Выполнение (dev/обычный): сессия открывается с серверной опцией
`default_transaction_read_only=on` и до первого пользовательского SQL
проверяется на самом соединении (`platform/readonly-default.md`); при
заданном search_path перед SQL отдельно выполняется
`SET search_path TO "schema_<client_id>", public`; затем весь текст SQL
уходит серверу одним вызовом внутри обёртки транзакцией с меткой
(форма и отказы — `platform/readonly-default.md`) — без параметризации,
разбиения и модификации самого текста.

## Ввод/вывод

stdout — только данные результата; stderr — meta-блок, приглашение и
ошибки, без трейсбеков. Exit: 0 — успех (включая `--dry` и запрос без
result set); 1 — ошибка исполнения (read-only отказ, ошибка БД); 2 —
ошибки ввода и конфигурации (пустой SQL, конфликт флагов, `--server` с
dev, резолв, нет адреса/кредов PG).

Meta-блок (stderr; печатается ⇔ `--verbose` или `--dry`); строки
`search_path` и `mode` — только при действующем search_path/read-only:

    server: sl-<N>
    pg_host: <host>
    pg_port: <port>
    database: <db>
    search_path: schema_<client_id>, public
    mode: read-only
    sql:
    <текст SQL как есть>

Маршрут dev: первая строка `server: dev`, host/port/db — dev-стенда.

Печатается результат **первого оператора текста пользователя**;
операторы обёртки в счёт не идут. У `;`-склейки последующие операторы
сервер выполняет, но их результаты не печатаются, и на выбор формы
вывода они не влияют (`SET …; SELECT …` → `OK (rowcount=-1)` первого
оператора, не таблица второго).

Результат (stdout):

- запрос без result set → `OK (rowcount=<N>)`; с `--json` — одна строка
  `{"ok": true, "rowcount": <N>}`. `<N>` — число строк, затронутых
  оператором, как его сообщает сервер; для операторов, не затрагивающих
  строк (`SET`, `DISCARD`), это `-1`. На read-only-сессии положительное
  `<N>` недостижимо;
- result set, default — ASCII-таблица: шапка, строка `-`-разделителей,
  строки; колонки через два пробела, каждая дополнена пробелами справа
  до max(длина имени, длины значений) — включая последнюю в строке;
  NULL — пустая строка; последняя строка `(<N> rows)` при любом `<N>`,
  включая 1; 0 строк → шапка + `(0 rows)` без разделителя;
- `--json` — одна строка: массив объектов `{колонка: значение, …}`,
  не-ASCII без экранирования; значение без JSON-представления (дата и
  т.п.) сериализуется его текстовой формой; 0 строк → `[]`;
- `--md` — markdown-таблица `| col | … |` / `| --- | … |` / строки;
  экранирование значений: `\` → `\\`, `|` → `\|`, перевод строки →
  `<br>`; NULL — пустая ячейка; 0 строк → шапка + разделитель.

Ошибки исполнения: пишущий SQL → отказ сервера, stderr
`` mpu sql-ro: запрос пытается писать — заблокировано read-only сессией. Для записи используйте `mpu sql`. ``,
exit 1, stdout пуст; текст сам завершил транзакцию вызова → stderr
`mpu sql-ro: текст завершил транзакцию вызова — гарантия только-чтения
снята, результат не печатается`, exit 1, stdout пуст; любая другая
ошибка БД → stderr `db error: <текст ошибки сервера>`, exit 1. Текст
сервера печатается как есть, включая многострочный (позиция и указатель
на место ошибки). Классы различаются по SQLSTATE
(`platform/readonly-default.md`), не по тексту сообщения.

## Побочные эффекты

Одно TCP-подключение к PG; записи в пределах сессии не бывает, границы
гарантии — `platform/readonly-default.md`. Резолв
читает локальную кэш-БД; результаты не кэшируются; файлов команда не
пишет. Журнал вызовов — обвязка (`platform/invoke-log.md`).

## Конфигурация

Адреса `pg_<N>`, порт/БД/креды PG и dev-стенд — `platform/env-file.md`.
Путь прежней реализации для sw-моста — `mcp.legacy_bin`
(`platform/config.md`).

## Инварианты

- Запись отклоняет сервер, а не разбор текста запроса; переключить режим
  из самого SQL нельзя. Что этой гарантией НЕ закрыто — названо в
  `platform/readonly-default.md`, «Инварианты».
- `--dry` не открывает соединений; meta-блок в stderr ⇔ `--verbose` или
  `--dry`, при успехе без них stderr пуст.
- search_path ставится ⇔ ровно один различный client_id (dev-хвост-число
  либо единственный client_id кандидатов резолва).
- NULL в таблице и markdown — всегда пустая строка/ячейка, никогда
  текст `None`/`NULL`; в JSON — `null`.
- Пользовательский SQL уходит серверу одной строкой, байт в байт как
  введён; конфликт `--json`/`--md` валидируется до чтения SQL.
- Форма вывода определяется первым оператором SQL и только им; печать
  начинается лишь после успешного выполнения всего переданного текста.

## Граничные случаи и ошибки

- SQL-аргумент из одних пробелов → как незаданный: fallback на
  stdin/интерактив, не «empty SQL» сразу (источники — «CLI-контракт»).
- `sl-N` (сервер целиком) → кандидатов нет → без search_path;
  `dev:<нечисло>` → dev-PG без search_path, не ошибка.
- Многострочное значение в ASCII-таблице печатается как есть, без
  экранирования: строка результата разрывается, выравнивание соседних
  колонок ломается; ширина колонки при этом считается по полной длине
  значения. Экранирование переводов строк — только у `--md`.
- Ошибка любого оператора `;`-склейки — в том числе не первого
  (`SELECT 1 AS a; SELECT 1/0`) → `db error: <текст>`, exit 1, stdout
  пуст: result set первого оператора не печатается, хотя сервер его
  отдал. Печать начинается после того, как весь текст выполнен.
- Попытка снять режим только-чтения, `COMMIT`/`ROLLBACK` внутри текста,
  оператор, запрещённый в блоке транзакции (`VACUUM`, `ANALYZE`,
  `CREATE INDEX CONCURRENTLY`) — случаи обёртки, перечислены в
  `platform/readonly-default.md`; здесь поведение то же, exit 1.
- Ошибка резолва селектора → exit 2 до чтения SQL, тексты —
  `platform/selector.md`.
- Нет адреса `pg_<N>` / кредов → `mpu sql-ro: <причина>`, exit 2, без
  подключения (см. «Известные отклонения»).
- sw-алиас, а прежней реализации по пути нет → exit 1 и текст маршрута
  `legacy` (`platform/registry.md`), собственного текста команда не
  добавляет.

## Известные отклонения

- **fix** — ошибка конфигурации PG (нет `pg_<N>`, нет кредов) в
  оригинале — сырой трейсбек и exit 1; правильно — `mpu sql-ro:
  <причина>`, exit 2, без трейсбека (`platform/readonly-default.md`).
- **fix** — оригинал открывает сессию одной опцией
  `default_transaction_read_only=on`, и запрет снимается из самого
  текста SQL (замер 2026-08-05 на PostgreSQL 16: `SET
  transaction_read_only = off; INSERT …` в одном вызове запись
  выполняет). Новая реализация исполняет текст в обёртке транзакцией с
  меткой (`platform/readonly-default.md`). Наблюдаемая цена: оператор,
  запрещённый внутри блока транзакции, перестаёт проходить — в
  оригинале `VACUUM` на read-only сессии выполнялся. Обмен принят:
  `sql-ro` — команда диагностического чтения, а не обслуживания.
- **fix** — шапка таблицы при 0 строк в оригинале печатается с
  табуляцией между именами колонок, непустая — с двумя пробелами и
  выравниванием; правильно — единый формат шапки в обоих случаях.
  Golden `table-empty-stdout.txt` записан в целевой форме, а не в
  оригинальной.
