## Назначение

Логи сервисов стенда: по умолчанию — запрос в Loki (история по всем хостам,
фильтры, слежение); `--via portainer` — legacy-снимок одного контейнера из
Docker API через Portainer.

## CLI-контракт

`mpu logs [SELECTOR] [SERVICE] [флаги]`. `-h` = `--help`. Совсем без
аргументов — **не справка**: выполняется обычный Loki-запрос без фильтра по
хосту за дефолтное окно (проверено прогоном живой версии: exit 0, вывод —
строки логов всех хостов).

- `SELECTOR` — `ls` | прямой хост (`sl-N`, `wb-N`, `dt-N`, `wb-clusters`,
  `wb-positions`) | селектор клиента/таблицы (`platform/selector.md`) | имя
  сервиса (п. 2 ниже). Не задан — запрос без фильтра по хосту.
- `SERVICE` — `ls` | Loki: точное значение сервиса (label `compose_service`) |
  portainer: подстрока имени контейнера.

Флаги: `--via loki|portainer` (default `loki`); `--tail/-n N` (default 200);
`--since STR`; `--timestamps/-t`; `--no-stdout`; `--no-stderr`; `--grep S` и
`--grep-regex S` (повторяемые; у второго алиас-написание `--grep_regex`);
`--level S`; `--client INT`; `--follow/-f` (только Loki).

Порядок разбора:

1. `ls`-режимы — раньше всего (не требуют `LOKI_URL` и валидного `--via`):
   `SELECTOR` == `ls` → хосты из кэш-БД (`SERVICE` игнорируется); иначе
   `SERVICE` == `ls` → сервисы хоста `SELECTOR` (значение литерально, без
   резолва). По одному на строку, сортировка; exit 0; пусто → exit 2.
2. Трактовка первого аргумента как сервиса: `SELECTOR` задан, `SERVICE` нет,
   `--via` не `portainer`, значение не матчит
   `^(sl-\d+|wb-\d+|dt-\d+|wb-clusters|wb-positions)$` и есть среди сервисов
   кэш-БД → это `SERVICE`, фильтра по хосту нет (`mpu logs wb-loader` —
   сервис со всех хостов).
3. `--via portainer`: обязательны оба аргумента; несовместим с `--follow` и с
   `--grep`/`--grep-regex`/`--level`/`--client` («Известные отклонения»,
   fix) — нарушение → exit 2; при нескольких нарушениях сразу побеждает
   первый отказ в порядке этого текста: селектор → контейнер →
   `--follow` → фильтры. Прочие значения `--via` → exit 2.
4. Loki-путь: сначала проверка `LOKI_URL`; хост: `SELECTOR` матчит regex
   прямого хоста (п. 2) → значение как есть, иначе резолв селектора
   (`platform/selector.md`) в номер сервера `N` → хост `sl-N` (до клиента не
   сужается); `--follow` → слежение, иначе разовый запрос.

`--since`: одни цифры → абсолютный Unix-ts; `<число>` + единица `s|m|h|d` →
`now − число·единица`; иначе exit 2. Дефолт: разовый Loki-запрос — 5 минут до
now; слежение — 10 секунд; portainer — без нижней границы (не передаётся).

LogQL (порядок частей фиксирован, стык — один пробел; label-блок — через
запятую без пробелов):

    {host="H" | host=~".+"[,compose_service="S"][,stream!="stdout"]
    [,stream!="stderr"]} [|= `G`]… [|~ `R`]… [|= `CLIENT`]
    [| detected_level="LEVEL"]

`|=` — на каждый `--grep` в порядке ввода; `|~` — на каждый `--grep-regex`;
затем `--client` как `|=` с десятичной записью числа; затем `--level` в
нижнем регистре. Label-значения: `\` → `\\`, `"` → `\"`; значение line-filter
в backtick-кавычках; содержит backtick → в двойных кавычках с тем же
экранированием, что у label.

Разовый Loki-запрос: окно `[since .. now]`, лимит `--tail`, направление
backward (последние N записей окна); печать всегда по возрастанию ts. Строка:
текст записи без хвостового `\n` (снимается ровно один хвостовой перевод
строки, остальные — данные записи), плюс `\n`; с `--timestamps` — префикс
`YYYY-MM-DDThh:mm:ss.mmmZ ` (UTC, миллисекунды из ts записи).

Слежение (`--follow`): начальная порция — окно `[since | now−10s .. now]`,
forward, лимит `--tail`; далее опрос каждые 2 секунды: окно
`[последний_увиденный_ts + 1нс .. now]`, forward, лимит 1000; печать по
возрастанию. Ошибка начального запроса — как у разового (exit 1); ошибка на
опросе → в stderr тот же текст, что у разового запроса (в форме точки
входа), с ведущим переводом строки, и продолжение с тем же курсором;
пустой опрос курсор не двигает. Выход — Ctrl+C: `\n` в stdout, exit 0.
Слежение — только CLI: вызов `logs` как MCP-тула с `follow: true` →
ошибка ввода `--follow доступен только в CLI` (слежение живёт до
Ctrl+C, которого у MCP-вызова нет). Ограничение названо и в текстах:
описание входа `follow` в схеме тула и абзац справки о `--follow`
содержат «только CLI» — читатель узнаёт о запрете из справки, а не
пробой.

Portainer-путь: печать байтов как есть, без построчной обработки и сортировки
(порядок между потоками — как демультиплексировано): stdout-часть → stdout,
stderr-часть → stderr; `--timestamps` отдаёт Docker'у добавление меток.

## Ввод/вывод

stdout — строки логов (или списки `ls`); stderr — ошибки с префиксом
`mpu logs: ` (в текстах ниже опущен), без трейсбеков. Exit: 0 — успех
(включая пустой результат: 0 строк); 2 — ошибка аргументов, конфигурации или
резолва; 1 — ошибка внешней системы после валидной конфигурации.

## Побочные эффекты

Только чтение: HTTP GET и SELECT из кэш-БД; никакой записи, кэш не мутируется.

Граница Loki — атом `platform/loki-http.md` (эндпоинт `query_range`, набор
параметров, отсутствие авторизации, проверка TLS, таймаут, игнорирование
прокси); здесь только то, что задаёт команда: `query` — LogQL выше,
`start`/`end` — границы окна в наносекундах, `limit` — `--tail`,
`direction` — `backward` у разового запроса и `forward` у слежения.
Ответ 200:

    {"data":{"result":[{"stream":{"host":"sl-1", …},
      "values":[["<ts_ns>","<строка>"], …]}, …]}}

Записи собираются из `values` всех элементов `result` (`ts_ns` — строка с
целым числом наносекунд). Терпимость к мусору: верхний уровень не по схеме →
0 записей, не ошибка; элемент `result` не по схеме → пропуск только его; пара
`values` не-массив / короче двух / нестроковая / ts не целое → пропуск пары
(элементы после второго игнорируются).

Граница Portainer: цель `(base_url, endpoint_id)` — из кэш-БД, при
отсутствии — legacy-ключ env `sl_<N>_portainer=<base_url>/<endpoint_id>`
(невалидный формат = отсутствие цели). Заголовок
`X-API-Key: <PORTAINER_API_KEY>`; TLS-сертификат проверяется только при
`PORTAINER_VERIFY_TLS=true` (без учёта регистра); прокси игнорируется. Два
запроса:

1. `GET {base_url}/api/endpoints/{endpoint_id}/docker/containers/json?all=true`
   → JSON-массив; из каждого объекта берутся строки `Names[]`, ведущий `/`
   отрезается. Точное совпадение `SERVICE` побеждает; иначе подстрочные
   совпадения: ноль или больше одного → exit 2.
2. `GET {base_url}/api/endpoints/{endpoint_id}/docker/containers/{имя}/logs` с
   параметрами `stdout=true|false`, `stderr=true|false` (инверсии
   `--no-stdout`/`--no-stderr`), `tail=<N>`, `follow=false`,
   `timestamps=true|false`, `since=<unix_ts>` (лишь при `--since`). Тело —
   мультиплексированный Docker-поток: кадры с 8-байтовым заголовком (байт 0 —
   поток: 0=stdin, 1=stdout, 2=stderr; байты 4–7 — big-endian длина payload);
   кадры потока 1 → stdout-часть, 2 → stderr-часть, 0 и неполный хвостовой —
   отбрасываются; первый же байт потока вне {0,1,2} → фрейминга нет
   (TTY-контейнер), весь ответ целиком — stdout-часть.

## Конфигурация

Env (`platform/env-file.md`): `LOKI_URL` — обязателен для Loki-пути;
`PORTAINER_API_KEY` — обязателен для portainer-пути; `PORTAINER_VERIFY_TLS`;
`sl_<N>_portainer` — legacy-fallback цели. Кэш-БД: таблицы `loki_hosts(host)`
и `loki_services_by_host(host, service)` — здесь только читаются; заполняются
обновлением кэша (`mpu init`/`mpu update`); отсутствие схемы = пустой кэш.

## Инварианты

- Команда ничего не пишет: ни в кэш-БД, ни в PG, ни в файлы; `ls`-режимы не
  ходят в сеть.
- Loki-вывод всегда хронологический по возрастанию ts записи, независимо от
  направления запроса; повторный вызов с теми же аргументами и тем же ответом
  Loki даёт побитово тот же вывод.
- Слежение не дублирует и не теряет записи между опросами (forward + курсор
  последнего увиденного ts, следующее окно с `ts+1`).

## Граничные случаи и ошибки

- Первый аргумент — имя сервиса, но кэш сервисов пуст → трактуется как
  селектор → ошибка резолва, exit 2 (`platform/selector.md`).
- `mpu logs ls <что-угодно>` → `ls` первым аргументом побеждает: хосты.
- Пустой кэш хостов → exit 2:
  ``кэш hosts пуст. Запусти `mpu init` или `mpu update`.``
- Нет сервисов для хоста `X` → exit 2: ``для host='X' нет services в кэше.
  Проверь host через `mpu logs ls` или обнови кэш через `mpu update`.``
- `LOKI_URL` пуст (Loki-путь, до любой сети) или `PORTAINER_API_KEY` пуст
  (portainer-путь) → exit 2: `<ИМЯ> не задан в ~/.config/mpu/.env`.
- `--since 5x` → exit 2:
  `--since: ожидается <число>{s|m|h|d} или unix-ts, получено '5x'`;
  `--since 60` → абсолютный Unix-ts 60, не «60 секунд назад».
- `--via x` → exit 2: `--via 'x', ожидается 'loki' или 'portainer'`.
- `--via portainer` без `SELECTOR` → exit 2: `--via portainer требует
  <selector>`; без `SERVICE` → `--via portainer требует <container>
  (2-й позиционный аргумент)`; с `--follow` →
  `--follow не поддерживается с --via portainer`.
- `--tail 0` или отрицательный → exit 2, ошибка ввода: значение не доходит
  ни до сети, ни до сборки запроса (замерено). Байтовый текст не
  фиксируется — он принадлежит слою разбора аргументов.
- Абсолютный `--since` больше текущего времени (окно `start > end`) → запрос
  уходит и отвергается источником: exit 1, `loki HTTP 400: end timestamp
  must not be before or equal to start time` + строка `  query: <LogQL>`.
- Строка лога печатается как есть, включая управляющие последовательности
  цвета, которые пишет сам сервис: команда их не удаляет и не добавляет.
- Loki ответил не-2xx → exit 1: `loki HTTP <код>: <тело без крайних пробелов,
  максимум 500 символов>` + вторая строка `  query: <LogQL>`; прочая сетевая
  ошибка → exit 1: `loki error: <описание>`.
- Цель portainer не найдена → exit 2: ``для sl-N не найден portainer-target
  (SQLite после `mpu init` или sl_N_portainer в ~/.config/mpu/.env)``.
- Контейнер не найден → exit 2: `контейнер 'X' не найден на sl-N` + строка
  `  подсказка: mpu ps sl-N`; неоднозначная подстрока → exit 2: `подстрока
  'X' даёт несколько контейнеров на sl-N:` + `  <имя>` на строку (сортировка).
- HTTP-ошибка запроса логов portainer → exit 1: `portainer error: <описание>`.

## Golden-примеры

Сняты с живой версии 2026-08-05, `fixtures/logs/`:

- `ls-hosts-stdout.txt` — `mpu logs ls`: хосты по одному на строку, exit 0;
- `ls-services-stdout.txt` — `mpu logs sl-1 ls`: сервисы хоста, exit 0;
- `err-services-empty.txt` — `mpu logs sl-99 ls`: хоста нет в кэше, exit 2;
- `err-since-bad.txt` — `--since abc`, exit 2, без сети;
- `err-via-unknown.txt` — `--via docker`, exit 2;
- `err-portainer-no-selector.txt` / `err-portainer-no-container.txt` /
  `err-follow-portainer.txt` — три отказа валидации portainer-пути, exit 2.

Голденов на строки логов нет намеренно: живая строка несёт данные клиента,
а формат печати фиксирован текстом выше (запись без хвостового перевода
строки, при `--timestamps` — префикс). Голдена на вывод неоднозначного
селектора нет по той же причине: его строки кандидатов содержат названия и
идентификаторы клиентов — форма списка задана `platform/selector.md`.
Справка голденом не сверяется: она рендерится из объявления команды и
обязана отличаться от оригинала (`platform/registry.md`).

## Известные отклонения

- **preserve** — слежение: пустой опрос не продвигает курсор — окно запроса
  растёт, пока источник молчит. Причина: иначе терялись бы записи, доезжающие
  в Loki с опозданием; вывод корректен (forward + лимит дочитывают без дублей).
- **preserve** — `--client N` — line-filter подстроки: подойдёт любое
  вхождение числа в строку (порт, id заказа), не только client_id. Причина:
  label с client_id в потоке нет; подстрока — единственный механизм
  cross-service поиска, и справка флага это заявляет.
- **fix** — оригинал молча игнорирует `--grep`/`--grep-regex`/`--level`/
  `--client` при `--via portainer` (вывод выглядит отфильтрованным). Правильно:
  exit 2, `--grep/--grep-regex/--level/--client поддерживаются только с --via loki`.
- **fix** — оригинал игнорирует `--tail` при `--follow` (лимит начальной
  порции всегда 500); правильное поведение — в контракте: лимит = `--tail`.
- **fix** — оригинал при ненайденном контейнере подсказывает `mpu p ps sl-N` —
  команды `mpu p ps` не существует; правильная подсказка — в контракте: `mpu ps sl-N`.
- **fix** — алиас-написание `--grep_regex` — отдельный вход схемы, а не
  алиас разбора: оба написания видны в справке и схеме тула, значения
  складываются (сначала все `--grep-regex`, затем все `--grep_regex`),
  взаимный порядок при смешивании написаний в одном вызове не
  сохраняется. Причина: разбор argv выводит флаги из имён схемы
  один-в-один; смешивание двух написаний в одном вызове — вырожденный
  случай, стоимость алиасного слоя платформы им не оправдана.
