# mpu init

Статус: реализовано (2026-08-06: принята доработка «down-endpoint'ы»
— пропуск без опроса и реконсиляция кэша; порции А и Б приняты
2026-08-05, маршрут переключён на `native`; goldens —
`fixtures/init/`; границы прогревов — атомы `platform/loki-http.md` и
`platform/kaiten-http.md`, кэш-БД — `platform/store.md`)

## Назначение

Первичная инициализация локальной кэш-БД: создание схемы, discovery
контейнеров стенда через Portainer, прогрев кэшей Loki и Kaiten,
авторизация Telegram. Запускается вручную на новой машине и после
изменения стенда; повторный запуск безопасен и догоняет пропущенное.

## CLI-контракт

`mpu init [--portainer TEXT] [--dry-run] [--reset]`

Пять шагов. Модель исполнения: шаг 1 выполняется первым; шаги 2–4
независимы и могут исполняться конкурентно; шаг 5 (единственный
интерактивный) начинается строго после завершения 2–4 — терминал к
этому моменту свободен. Порядок вывода детерминирован: блоки строк
шагов печатаются в порядке 1…5 независимо от порядка завершения.
Прервать команду могут только шаги 1–2; исходы шагов 3–5 (best-effort)
не меняют код выхода.

«Шаги 3–5 не выполняются» при сбое шага 2 означает отсутствие
наблюдаемых следов: ни их строк в выводе, ни записей в кэш-БД; шаг 5
не стартует вовсе. Прогревы 3–4 стартуют не раньше успешного получения
списка endpoints (при его сбое — не стартуют) и могут идти конкурентно
с обходом контейнеров; уже ушедшие при сбое обхода сетевые чтения
допустимы — их результат не записывается.

**Шаг 1 — схема кэш-БД.** Явный идемпотентный bootstrap
(`platform/store.md`); существующие данные не затрагиваются.
stderr: `# bootstrap: схема в <путь к кэш-БД> готова`.

**Шаг 2 — discovery контейнеров (Portainer).** Подключение — из
env-файла: `PORTAINER_API_KEY` обязателен; базовый URL — `--portainer`,
иначе `PORTAINER_URL`; `PORTAINER_VERIFY_TLS`, без учёта регистра
равный `true`, включает проверку TLS-сертификата — незаданная
переменная или любое иное значение оставляют её выключенной (см.
отклонения). Обмен:

- `GET {base}/api/endpoints` — список environment'ов; используются
  поля `Id`, `Name`, `Status` (контракт Portainer CE: 1 — доступен,
  2 — недоступен; любое значение, кроме 1, трактуется как недоступен);
- на каждый **доступный** endpoint —
  `GET {base}/api/endpoints/{id}/docker/containers/json?all=true` —
  все контейнеры, включая остановленные; обход endpoints допускает
  конкурентность.

Недоступный endpoint (`Status` ≠ 1) не опрашивается вовсе — запрос
контейнеров не отправляется, его таймаут не тратится; в блоке шага 2
печатается stderr `mpu init: endpoint <id> (<имя>): down — пропущен`.

Ошибка обработки одного endpoint'а (включая таймаут) → stderr
`mpu init: endpoint <id> (<имя>): <причина>`, обход продолжается по
остальным. Сбой самого списка endpoints → stderr
`mpu init: portainer: <причина>`, exit 1, без трейсбека (см.
отклонения). `<причина>` в обеих формах — одна из: `no response
headers within <N>ms` (таймаут заголовков), `no response within <N>ms`
(таймаут всего вызова), `HTTP <код>` (ответ вне 2xx), либо первая
строка системной ошибки сети. Если после обхода не найдено ни одного контейнера —
stderr `mpu init: ни одного контейнера не найдено`, exit 1, шаги 3–5
не выполняются.

Сводка в stdout: `# найдено sl-N контейнеров: <count>`; далее по строке
на каждый CLI-контейнер, по возрастанию номера сервера:
`sl-<N>: <container_name> [<state>] @ endpoint <endpoint_id>
(<endpoint_name>) -> <portainer_url>/<endpoint_id>`; затем
`# прочих контейнеров: <count>`.

`--dry-run` — только сводка: данные кэша не изменяются (bootstrap
схемы шага 1 к этому моменту уже выполнен), шаги 3–5 не выполняются,
exit 0. Без `--dry-run` выполняется запись: при `--reset` сначала
удаляются все записи кэша контейнеров
(stderr `# --reset: удалено <N> старых записей`), затем upsert каждой
найденной строки по ключу (portainer_url, endpoint_id, container_id) и
итог stderr `# записано <N> контейнеров в <путь к кэш-БД>`.

Запись реконсилирует кэш с авторитетными данными оркестратора — в той
же транзакции, что и upsert, удаляются записи текущего
`portainer_url` (записи других URL не затрагиваются):

- всех endpoint'ов со `Status` ≠ 1 (down);
- всех endpoint'ов, отсутствующих в успешно полученном списке
  endpoints;
- контейнеров, отсутствующих в успешно полученном списке контейнеров
  своего endpoint'а.

Записи endpoint'а, обход которого сорвался (ошибка, таймаут), не
удаляются и не обновляются. Суммарное число удалённых реконсиляцией
записей, если оно больше нуля, печатается stderr-строкой
`# удалено устаревших записей: <K>` перед итогом `# записано …`.

Строка кэша контейнеров (таблица `portainer_containers`, DDL —
фикстура `platform/store.md`): portainer_url, endpoint_id,
endpoint_name, container_id, container_name (первое из имён контейнера
без ведущего `/`), server_number (номер по `^/?(?:mp-)?sl-(\d+)-cli$`
из любого из имён, включая 0; у прочих контейнеров номера нет), state,
image, discovered_at (unix-время, секунды).

**Шаг 3 — прогрев Loki.** Best-effort; контракт вызова и записи —
`platform/loki-http.md`. Успех → stderr
`# loki: <H> hosts, <P> (host, service) пар`; любая ошибка (в т.ч.
незаданный `LOKI_URL`, таймаут) → `# loki: пропущено (<причина>)`.
`<причина>` — текст ошибки атома без префикса (`HTTP 503`,
`LOKI_URL не задан`); префикс `loki:` принадлежит только этой строке.

**Шаг 4 — прогрев справочников Kaiten.** Best-effort; четыре части и
их независимость — `platform/kaiten-http.md`, раздел «Прогрев
справочников». Ошибка части 1 → stderr `# kaiten: пропущено
(<причина>)`, части 2–3 не выполняются; иначе сводка stderr
`# kaiten: <S> spaces, <B> boards, <L> lanes, <C> columns, <R> roles`,
где счётчик полностью упавшей части — `?`. Пропуск отдельной доски в
частях 2–3 — отдельной stderr-строкой
`# kaiten: доска <id>: пропущена (<причина>)`; уже собранные доски
записываются (см. отклонения). Незаданный `KITEN_API_KEY` → причина
`KITEN_API_KEY не задан` — без подсказки «попробуй: …» (она — контракт
подкоманд `kiten`, не пропуска init). Порядок строк внутри блока шага:
строки 429-повторов атома → пропуски досок по возрастанию id → сводка.

**Шаг 5 — авторизация Telegram.** Тот же вход, что у команды
`mpu telegram login` (`telegram-login.md`), **вызываемый напрямую**, а не
подпроцессом: реализация одна, семантика её — идемпотентность при непустой
`TELEGRAM_SESSION`, пропуск без TTY, интерактив, запись `TELEGRAM_*` в
env-файл. Сообщения идут пользователю как есть; код выхода `init` шаг не
меняет ни при каком исходе (все ветки входа завершаются нулём —
`telegram-login.md`, инвариант 3).

Прежняя редакция описывала запуск подпроцесса `mpu telegram login` с
проброшенным терминалом и целый набор причин пропуска — `код возврата <N>`,
`legacy-реализация не найдена по пути "<путь>"`, первая строка системной
ошибки. Всё это исчезает вместе с подпроцессом: своей реализации у шага нет,
и ломаться на запуске больше нечему.

Причина правки не в красоте. Вход переехал порцией 90, но `init` продолжал
звать Python-версию — две реализации одного шага жили рядом, и разойтись
они могли молча: у `init` не было ни одной проверки, сверяющей их поведение.

## Ввод/вывод

stdout — discovery-сводка шага 2; stderr — служебные строки `# …` всех
шагов (включая строки записи шага 2 — `--reset`/`записано`), интерактив
шага 5 и ошибки формата
`mpu init: <причина>`, без трейсбеков. Exit: 0 — успех (включая
пропуски best-effort шагов); 2 — ошибки конфигурации Portainer;
1 — сбой списка endpoints или discovery без единого контейнера.

## Побочные эффекты

Сеть: HTTPS к Portainer API, Loki и Kaiten; Telegram — только на шаге 5.
Запись: кэш-БД (схема; кэш контейнеров; кэши Loki и Kaiten), env-файл —
только шагом 5. Интерактивный
stdin — только шаг 5 и только при TTY. Внешние системы не мутируются:
все обращения — чтение (Telegram-логин создаёт сессию на стороне
Telegram).

## Конфигурация

Env-файл (`platform/env-file.md`): `PORTAINER_URL` (или `--portainer`),
`PORTAINER_API_KEY`, `PORTAINER_VERIFY_TLS`; `LOKI_URL` (опционален);
креды Kaiten — `platform/kaiten-http.md`; `TELEGRAM_*` — шаг 5
(`telegram-login.md`). Кэш-БД — `platform/store.md`. Дефолты таймаутов — решение
реализации (см. инварианты), задокументированы в `--help`.

## Инварианты

Устойчивость (главная цель переработки):

- Каждый сетевой вызов ограничен таймаутом; вызова, ждущего
  неограниченно, не существует.
- Молчащий или зависший источник (endpoint Portainer, Loki, Kaiten,
  отдельная доска) не блокирует ни другие источники, ни завершение
  команды дольше своего таймаута.
- Обрыв по таймауту не теряет уже собранное: данные завершившихся
  источников записываются; частично обойдённые множества пишутся в
  объёме успешно собранного (scoped-замена — по обойдённым доскам).
- Молчаливых потерь нет: каждый пропущенный источник виден отдельной
  строкой или `?`-счётчиком сводки.
- Повторный запуск догоняет пропущенное: идемпотентные записи по
  ключу, дубликаты не появляются.
- Конкурентность ненаблюдаема ничем, кроме времени: порядок блоков
  вывода фиксирован, записи шагов не конфликтуют (разные таблицы).
- Кэш реконсилируется только авторитетными данными: удаление записей
  происходит лишь на основании успешного ответа оркестратора (список
  endpoints, обход endpoint'а); сбой обхода не удаляет ничего.
- Числа таймаутов — дефолты реализации (выбираются эмпирически),
  видны в `--help`; спека их не фиксирует. К ним относится и
  таймаут-бюджет шага прогрева целиком (сверх пределов на заголовки и
  на вызов): исчерпан → недообойдённое попадает в пропуски, счётчик
  части — `?`.

Прочие:

- `--dry-run` не пишет данных никуда: ни в кэш контейнеров, ни в
  env-файл, и не запускает шаги 3–5; bootstrap схемы (шаг 1)
  выполняется всегда, в том числе при `--dry-run`.
- Секреты (API-ключи, сессия Telegram) не печатаются ни в одной
  строке.
- Шаг 5 не начинается до завершения шагов 2–4: интерактив не смешан с
  их выводом.

## Граничные случаи и ошибки

- Нет `PORTAINER_API_KEY` → stderr
  `mpu init: в ~/.config/mpu/.env нет PORTAINER_API_KEY`, exit 2.
- Нет ни `--portainer`, ни `PORTAINER_URL` → stderr `mpu init: укажите
  --portainer <url> либо PORTAINER_URL в ~/.config/mpu/.env`, exit 2.
- URL Portainer без схемы `http://`/`https://` → stderr `mpu init:
  некорректный URL Portainer: '<значение>' — нужна схема http:// или
  https://`, exit 2; проверка выполняется до какого-либо сетевого
  вызова (это ошибка конфигурации, симметричная отсутствию URL).
- Сбой списка endpoints (сеть, таймаут, HTTP-ошибка) → exit 1 (см.
  шаг 2), шаги 3–5 не выполняются.
- Все endpoints упали или контейнеров нет → exit 1 (см. шаг 2).
- 0 sl-контейнеров при непустом списке прочих → не ошибка: сводка с
  нулём, шаги 3–5 выполняются.
- Endpoint down (`Status` ≠ 1) → строка пропуска, контейнеры не
  запрашиваются; при записи его записи в кэше удаляются
  (реконсиляция).
- Endpoint исчез из списка endpoints → при записи его записи в кэше
  удаляются (реконсиляция).
- Контейнер удалён на endpoint'е, обойдённом успешно → при записи его
  запись удаляется (реконсиляция).
- Обход endpoint'а сорвался (ошибка, таймаут) → его записи в кэше
  остаются нетронутыми (см. отклонения).
- Kaiten отвечает 429 → retry-контракт атома
  (`platform/kaiten-http.md`); паузы retry не отменяют таймаут-бюджет
  шага — при исчерпании часть помечается `?`.
- Запуск без TTY (CI/cron) → шаг 5 сам печатает пропуск с подсказкой,
  остальные шаги отрабатывают полностью.
- Legacy-реализация (`mpu telegram login`) недоступна → `# telegram:
  пропущено (<причина>)`, exit 0.

## Golden-примеры

Сняты с живой версии (`fixtures/init/`): `err-no-api-key.txt` — exit 2
без API-ключа; `err-no-url.txt` — exit 2 без URL (в обоих строка
шага 1 предшествует отказу: bootstrap успевает выполниться; путь к
кэш-БД в фикстурах заменён плейсхолдером `<путь к кэш-БД>` —
подстановка реального пути — обязанность теста). DDL схемы — фикстура
`platform/store.md`; формы ответов прогревов — фикстуры атомов.

Остальные классы закрепляются контрактными тестами реализации на
фейковых HTTP-серверах (без живых систем): happy path (discovery +
запись + сводки прогревов); exit 1 при сбое списка endpoints; exit 1
при пустом discovery; ошибка одного endpoint'а с продолжением; таймаут
молчащего endpoint'а (строка ошибки + продолжение + время завершения
ограничено); down-endpoint (строка пропуска, запрос контейнеров не
отправляется, его записи удалены, чужие целы); endpoint исчез из
списка (записи удалены); контейнер исчез с успешно обойдённого
endpoint'а (запись удалена); сорвавшийся endpoint (записи целы,
реконсиляция его не касается); пропуск одной доски Kaiten (строка +
scoped-запись остальных); `--dry-run` (кэш не изменён — в т.ч. ничего
не удалено, шаги 3–5 не вызваны); `--reset`; повторный запуск
(обновление без дублей); `--help` (дефолты таймаутов видны).

## Известные отклонения

- **preserve** — проверка TLS-сертификата Portainer по умолчанию
  выключена: включает её только явное `PORTAINER_VERIFY_TLS=true` (без
  учёта регистра). Причина: стенд живёт на self-signed сертификатах —
  «безопасный» дефолт сломал бы каждую машину, где ключ не задан;
  контракт ключа общий с Python-реализацией.
- **fix** — оригинал копит мёртвые записи вечно: down-endpoint'ы
  опрашиваются (init тормозит на их таймаутах), а кэш никогда не
  чистится, кроме явного `--reset` — записи down/удалённых
  endpoint'ов и исчезнувших контейнеров остаются целями резолва.
  Правильное поведение — пропуск down-endpoint'ов без опроса и
  реконсиляция кэша авторитетными данными (см. шаг 2). Прежняя
  осторожность сохранена в узкой форме: сбой обхода endpoint'а
  (ошибка, таймаут) не удаляет его записи — резолв по кэшу продолжает
  работать.
- **fix** — сбой списка endpoints в оригинале не обработан: команда
  падает трейсбеком, нарушая собственный контракт вывода. Правильное
  поведение — `mpu init: portainer: <причина>`, exit 1.
- **fix** — `<причина>` в строке ошибки endpoint'а у оригинала
  многострочная (HTTP-клиент дописывает второй строкой ссылку на MDN) —
  шум в stderr, наблюдался живьём на 502. Правильное поведение:
  причина — одной строкой, первая строка сообщения об ошибке.
- **fix** — вызовы Kaiten в оригинале без таймаута: висящий сервер
  блокирует init неограниченно. Все вызовы ограничены (инварианты).
- **fix** — исполнение в оригинале строго последовательное; шаги 2–4 и
  обходы внутри них допускают конкурентность. Наблюдаемое следствие —
  только время; порядок вывода сохранён.
- **fix** — молчаливый пропуск доски и потеря собранного при обрыве
  обхода — отклонения атома (`platform/kaiten-http.md`), здесь их
  наблюдаемая форма: строка пропуска и scoped-запись собранного.
- **fix** — шаг 5 в оригинале — встроенный код init; теперь общая
  реализация с командой `mpu telegram login`, вызываемая напрямую.
  Промежуточная редакция звала её подпроцессом: MTProto тогда оставался
  в Python, и `init` переезжал не дожидаясь. После порции 90 вход стал
  своим, и подпроцесс исчез вместе с причиной.

## Открытые вопросы

- Значения `Status` (1 — доступен, 2 — недоступен) взяты из контракта
  Portainer CE API; живой замер down-endpoint'а на стенде отложен —
  на 2026-08-06 оркестратор недоступен по VPN. Подтвердить при первой
  возможности; спека уже защищена трактовкой «всё, кроме 1, —
  недоступен».

(числа таймаутов — осознанно делегированы реализации, см. инварианты;
эмпирический материал — профилирование живого init).
