# mpu sql / sql-ro — маршрут sw

Статус: черновик (выделен из `specs/sql-ro.md` 2026-08-05; реализуется
после `platform/exec-transport.md`. До тех пор вызов с sw-алиасом
делегируется прежней реализации — мост описан в `specs/sql-ro.md`)

## Назначение

Третий маршрут селектора команд `sql` и `sql-ro`: SQL к БД воркспейсов
(sw-back). Прямого доступа к этой БД снаружи нет, поэтому запрос
исполняется изнутри контейнера приложения. Маршрут общий для обеих
команд: отличаются только префикс ошибок (имя вызванной команды) и
установка read-only.

## CLI-контракт

Собственных флагов нет: маршрут выбирается селектором — алиас из
`{sw, sw-pg, swpg, sw-back, swback, ws, workspaces}` без учёта регистра
и краевых пробелов. Синопсис, источники SQL, форматы вывода и коды
выхода — `specs/sql-ro.md`. `--server` с sw-селектором → exit 2 до
чтения SQL: `mpu <команда>: --server не сочетается с sw-селектором`.

Выполнение: в контейнере (target) запускается `node --input-type=module
-` со скриптом на stdin. Скрипт берёт DSN, вычищает из его query-string
параметры `schema`, `connection_limit`, `pool_timeout`, `pgbouncer`,
`socket_timeout`, для `sql-ro` первым делом выполняет
`SET default_transaction_read_only = on`, затем пользовательский SQL
одним вызовом — без параметризации, разбиения и модификации. Результат
(колонки, строки, rowcount, признак result set) возвращается через вывод
exec и печатается в форматах `specs/sql-ro.md`.

Target: `sl-N` → штатный контейнер сервера N, иначе — контейнер с этим
именем из кэша. Доставка команды в контейнер и код выхода —
`platform/exec-transport.md`.

## Ввод/вывод

Meta-блок (stderr; печатается ⇔ `--verbose` или `--dry`); строка `mode`
— только у `sql-ro`:

    server: sw-pg (база sw-back)
    run_target: <target>
    dsn_source: env <VAR> (коннект изнутри контейнера)
    mode: read-only
    sql:
    <текст SQL как есть>

где `<VAR>` — имя env-переменной с DSN; при литеральном override —
`dsn_source: SW_PG_DSN (override) (коннект изнутри контейнера)`.

Печатается результат первого оператора переданного SQL — то же правило,
что на остальных маршрутах (`specs/sql-ro.md`, «Известные отклонения»).

Ошибки:

- контейнер не резолвится → exit 2, stderr:
  `mpu <команда>: контейнер '<target>' не резолвится (<причина>).` плюс
  строка-подсказка с отступом в два пробела:
  ``Нужен Portainer endpoint sw-хоста в кэше `mpu init`, либо задай
  SW_PG_RUN_TARGET (sl-N / имя контейнера).``;
- exec завершился ненулевым кодом или результат в выводе не распознан →
  stderr/stdout контейнера пробрасываются в stderr, затем
  `mpu <команда>: выполнение не удалось (<причина>)`, причина —
  `результат не найден в выводе` либо `exit=<код>`; exit 1.

## Побочные эффекты

Exec в контейнер приложения + TCP-подключение к PG изнутри него. Для
`sql-ro` записи не бывает ни при каких входах; для `sql` мутируется БД
воркспейсов. Файлов маршрут не пишет, результаты не кэшируются.

## Конфигурация

Env-файл (`platform/env-file.md`): `SW_PG_RUN_TARGET` — target exec
(дефолт `sw-api`); `SW_PG_DSN_ENV` — имя env-переменной с DSN в
контейнере (дефолт `DATABASE_URL`); `SW_PG_DSN` — литеральный override
DSN (коннект всё равно изнутри контейнера).

## Инварианты

- Подключение к БД воркспейсов всегда изнутри контейнера: прямого
  TCP-соединения с sw-PG команда не открывает ни при каких входах, в том
  числе при `SW_PG_DSN`.
- `sql-ro` на этом маршруте не может выполнить запись: опция read-only
  устанавливается до пользовательского SQL, гарантия серверная
  (`platform/readonly-default.md`).
- `--dry` не выполняет exec и не открывает соединений.
- DSN, его пароль и содержимое env контейнера в вывод, ошибки и журнал
  вызовов не попадают: печатается только имя переменной.
- Форма вывода одинакова с остальными маршрутами при одинаковом
  результате запроса — маршрут виден только в meta-блоке.

## Граничные случаи и ошибки

- Пустой DSN в контейнере (нет env и нет override) → диагностика
  контейнера в stderr + `mpu <команда>: выполнение не удалось (результат
  не найден в выводе)`, exit 1.
- `SW_PG_RUN_TARGET=sl-N` → штатный контейнер сервера N, кэш контейнеров
  не опрашивается.
- Селектор — sw-алиас в другом регистре или с пробелами по краям
  (` SW-PG `) → тот же маршрут.
- Ошибка транспорта (нет доступа к хосту, контейнер остановлен) → текст
  транспорта в stderr + `mpu <команда>: выполнение не удалось
  (exit=<код>)`, exit 1.

## Golden-примеры

`fixtures/sql-sw/`:

- `dry-v-stderr.txt` — `sw` с `--dry -v` у `sql-ro`: meta-блок целиком,
  stdout пуст, exit 0;
- `err-container-unresolved.txt` — target не найден в кэше: две строки
  stderr (сообщение + подсказка), exit 2. Записан в оригинальной форме,
  с префиксом `mpu sql sw:`; целевая форма — префикс вызванной команды
  (см. «Известные отклонения»).

Снять при переводе в «к реализации»: живой `SELECT` (таблица /`--json`),
`;`-склейку, отказ read-only на `sql-ro`, `SW_PG_DSN`-override в
meta-блоке.

## Известные отклонения

- **fix** — ошибки маршрута в оригинале имеют префикс `mpu sql sw:`
  независимо от вызванной команды; правильно — префикс имени команды
  (`mpu sql:` / `mpu sql-ro:`), тексты причин и подсказок — без
  изменений.
- **fix** — у `;`-склейки оригинал этого маршрута печатает результат
  последнего оператора, остальные маршруты — первого; правильно — единое
  правило «результат первого оператора» на всех маршрутах.

## Открытые вопросы

- Разделение спеки при реализации: маршрут описан для двух команд сразу
  (`sql` и `sql-ro`) и переезжает одной порцией; если к тому моменту
  `specs/sql.md` останется незамороженной, порция берёт только
  `sql-ro`-половину — read-only-часть контракта от write-части здесь не
  зависит.
