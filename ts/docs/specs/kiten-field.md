# mpu kiten field

Статус: черновик

## Назначение

Скалярные кастомные поля карточки Kaiten (MR / гипотеза / что сделано /
результат) с локальной историей значений — журналом полей: `set` пишет
поле и историю, `ls` читает историю, `update`/`rm` правят её с
пере-синхронизацией поля. Отдельная подгруппа `artefact` — файловое
поле «9. AI-артефакт» (md-вложение, без истории). Тем же механизмом
записи полей пользуется `mpu kiten close` (`kiten-close.md`).

Обвязка Kaiten — `platform/kaiten-http.md`; кэш-БД — bootstrap схемы:
`init.md`.

## CLI-контракт

`KIND` — закрытый список: `mr`, `hypothesis`, `done`, `result`; иное
значение — ошибка ввода CLI-слоя, exit 2, без сети. Соответствие
kind → кастомное поле инстанса Kaiten фиксировано:

| KIND | id поля | название |
| --- | --- | --- |
| mr | 398965 | «Ссылка на Merge Request» (тип url) |
| hypothesis | 291984 | «6. Причина/гипотеза» |
| done | 291985 | «7. Что сделано» |
| result | 291990 | «8. Результат» |
| (artefact) | 610303 | «9. AI-артефакт» (тип attachment) |

Ключ поля в теле PATCH — `id_<id>`.

Модель: журнал полей — история значений, несколько записей на пару
(карточка, KIND); поле карточки всегда равно последней записи пары —
максимальный момент создания, при равенстве — максимальный id записи.

- `mpu kiten field set SELECTOR KIND VALUE` — добавить запись истории
  (безусловно, без дедупа и проверки «уже задано») и установить поле
  карточки в последнюю запись (= только что добавленную).
- `mpu kiten field ls [--card SELECTOR] [--kind KIND] [--json]` —
  история, новые сверху; read-only, без сети и без токена.
- `mpu kiten field update RECORD_ID VALUE` — изменить значение записи
  (момент создания не меняется), затем установить поле карточки этой
  пары в её текущую последнюю запись.
- `mpu kiten field rm RECORD_ID` — удалить запись, затем так же
  пере-синхронизировать; записей не осталось → поле очищается.
- `mpu kiten field artefact set SELECTOR PATH` — загрузить md-файл в
  поле «9. AI-артефакт» и привязать к нему. `PATH` обязан существовать
  и быть обычным читаемым файлом (иначе ошибка ввода CLI-слоя,
  exit 2); имя файла обязано оканчиваться на `.md` без учёта регистра,
  иначе exit 2: `артефакт должен быть .md-файлом, получен '<имя>'` —
  проверка по имени, не по содержимому. Журнал полей не пополняется.
- `mpu kiten field artefact rm SELECTOR` — удалить все файлы карточки,
  привязанные к полю (идемпотентно); файлы комментариев и файлы
  карточки вне поля не трогаются.
- `mpu kiten field` (и `mpu kiten field artefact`) без подкоманды —
  справка, exit 2.

Живые сценарии: `mpu kiten field set 12345678 mr
https://gitlab.example.com/team/repo/-/merge_requests/999`;
`mpu kiten field ls --card 12345678 --json`;
`mpu kiten field artefact set 12345678 razbor.md`.

## Ввод/вывод

HTTP-граница (формы — `platform/kaiten-http.md`):

- установка поля (`set`/`update`/`rm`, включая очистку):
  `PATCH /cards/{id}` body
  `{"properties": {"id_<NNN>": <значение | null>}}`;
- `artefact set`: `PUT /cards/{id}/custom-properties/610303/files` —
  multipart, единственная файловая часть в поле `file`, имя части —
  базовое имя файла. Именно этот эндпоинт привязывает файл к полю;
  обычная загрузка файла карточки поле не заполняет;
- `artefact rm`: `GET /cards/{id}`; на каждый файл карточки с
  привязкой к полю 610303 — `DELETE /cards/{id}/files/{file_id}`;
  удаление привязанного файла очищает значение поля на сервере,
  отдельный PATCH не отправляется.

stdout:

- `set`: `ok: {kind} → {значение} · {url карточки}`;
- `update`: `ok: #{RECORD_ID} {kind} → {применённое} · {url}` —
  применённое = значение последней записи пары после правки; при
  правке не-последней записи оно отличается от введённого;
- `rm`: `ok: удалена #{RECORD_ID} {kind} → {применённое} · {url}`; при
  опустевшей истории — `ok: удалена #{RECORD_ID} {kind} (очищено) ·
  {url}`;
- `ls --json`: массив `{"id","card_id","field","value","created_at"}`
  (`created_at` — epoch-секунды), отступ 2, юникод как есть; порядок —
  новые сверху (момент создания, затем id, по убыванию);
- `ls` без `--json`: таблица с колонками `id, card, field, when,
  value` (оформление — свобода реализации), `when` —
  `YYYY-MM-DD HH:MM` по МСК; нет записей → `(пусто)`;
- `artefact set`: `ok: артефакт {имя} → {url карточки} (файл {url
  файла})` — имя и url файла из ответа сервера;
- `artefact rm`: `ok: удалено из «AI-артефакт»: {имя1, имя2} · {url}`;
  поле уже пусто → `ok: поле «AI-артефакт» уже пусто · {url}`.

Exit: 0 — успех; 2 — ошибки ввода (KIND, селектор, PATH, не-md имя);
1 — ошибки API (`mpu kiten field <sub>: kaiten error: <текст>`, где
`<sub>` — `set` / `update` / `rm` / `artefact set` / `artefact rm`) и
отсутствующий RECORD_ID.

## Побочные эффекты

Kaiten: PATCH поля (`set`/`update`/`rm`), PUT загрузки и DELETE файлов
(`artefact`). Локально: журнал полей в кэш-БД — добавление (`set`),
правка (`update`), удаление (`rm`); `ls` только читает; `artefact` к
журналу не обращается. Пустая/несозданная кэш-БД инициализируется на
месте. Локальная запись фиксируется до PATCH и при его сбое не
откатывается (см. «Известные отклонения»).

## Конфигурация

`KITEN_API_KEY`, `KITEN_BASE_URL` — `platform/kaiten-http.md` (для
`ls` не нужны). Кэш-БД — `platform/env-file.md`.

## Инварианты

- После любой успешной мутации поле карточки равно последней записи
  журнала пары; пустая история — поле очищено (null). Правило выбора
  последней записи одно и для журнала, и для сервера.
- `set` только добавляет записи: прошлые не редактируются и не
  удаляются.
- `ls` не выполняет сетевых запросов и работает без `KITEN_API_KEY`.
- Артефактное поле не касается журнала полей ни в одной операции.
- `artefact rm` идемпотентен и не трогает файлы вне поля 610303.

## Граничные случаи и ошибки

- `update`/`rm` с несуществующим RECORD_ID → exit 1:
  `mpu kiten field update: записи #{N} нет` /
  `mpu kiten field rm: записи #{N} нет`; сетевых запросов нет.
- `update` не-последней записи пары → история изменена, поле карточки
  осталось значением последней записи — его и печатает `ok`-строка.
- `rm` единственной записи пары → PATCH null, `(очищено)`.
- PATCH упал после локальной записи → журнал изменён, поле карточки
  нет, exit 1; следующая успешная мутация пары доводит поле.
- `ls` на пустой/новой кэш-БД → `(пусто)` / `[]`, exit 0.
- `ls --card abc` (нет числового сегмента) → exit 2
  (`platform/kaiten-http.md`, «Селектор карточки»).
- `artefact set x.MD` → проходит (регистр расширения не значим);
  markdown-файл с именем `x.txt` → exit 2.
- `artefact rm`: сбой DELETE в середине списка → уже удалённые файлы
  не восстанавливаются, exit 1.

## Golden-примеры

Снять при переводе в «к реализации» (тестовая карточка, синтетический
журнал): `field ls --json` (happy path), `field ls` на пустом журнале
(`(пусто)`), `field set <id> mr <url>` + повторный `set` (две записи в
`ls`), `field rm <RECORD_ID единственной записи>` (`(очищено)`),
`field update 999999 x` (нет записи, exit 1), `field set <id> badkind
x` (exit 2), `field artefact set <id> файл.txt` (exit 2).

## Известные отклонения

- **preserve** — локальная запись журнала коммитится до PATCH и при
  его сбое не откатывается (журнал и поле временно расходятся).
  Причина: журнал — история намерений; откат терял бы введённое
  значение, а следующая успешная мутация пары доводит поле до
  последней записи автоматически.
- **fix** — `ls --json` печатает компактный однострочный JSON;
  правильно — отступ 2, юникод как есть, как во всех `--json` дерева
  `kiten`.
- **fix** — `when` в таблице `ls` рендерится по UTC; правильно — по
  МСК, как во всех остальных выводах `kiten`.

## Открытые вопросы

- Журнал полей пишет и читает не только эта команда (`close` до своего
  переезда, `ls` из обеих реализаций): совпадение физической схемы
  таблицы кэш-БД со старой реализацией — решение владельца переезда
  при переводе спеки в «к реализации».
