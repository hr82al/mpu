# mpu backup-wb-unit-proto | backup-ozon-unit-proto | backup-wb-unit-manual-data

Статус: реализовано

## Назначение

Снять копию таблицы клиента в схему `backups` перед тем, как её менять.
Три команды одной формы, различаются только таблицей-источником:

| Команда | Площадка | Таблица-источник |
| --- | --- | --- |
| `backup-wb-unit-proto` | `wb` | `wb_unit_proto` |
| `backup-ozon-unit-proto` | `ozon` | `ozon_unit_proto` |
| `backup-wb-unit-manual-data` | `wb` | `wb_unit_manual_data` |

Это **не** обёртка семейства `platform/portainer.md`: ход прямым
соединением с PostgreSQL, без `docker exec` и без Portainer.

## CLI-контракт

```
mpu backup-<X> SELECTOR [--date YYYYMMDD] [--schema-id N]
               [--server sl-N] [--dry]
```

- `SELECTOR` — базовый резолв `platform/selector.md`; `--server sl-N` —
  override сервера.
- `--schema-id N` — номер схемы клиента явно. Без него он выводится:
  единственный `client_id` среди кандидатов селектора; кандидатов нет, а
  селектор — чистое число → само число.
- `--date YYYYMMDD` — суффикс имени копии; ровно восемь цифр. По
  умолчанию — сегодняшняя дата **по Москве**.
- `--dry` — показать мета-блок и запрос, не подключаясь.
- Политика — `rw`: команда создаёт таблицу. `--dry` — режим флага, а не
  отдельная читающая команда: класс объявляется командой и от аргументов
  не зависит (`platform/command-contract.md`). Отдельного `ro`-тула у
  неё нет; тулом публикуется в профиле `rw` вместе с прочими
  мутирующими.
- В секцию `destructive` закрытого списка команды **не** входят:
  `CREATE TABLE` только добавляет таблицу и обратим одним `DROP`,
  данных источника он не трогает. Решение записано здесь, чтобы
  отсутствие пометки читалось как выбор, а не как пропуск
  (`platform/mcp-server.md`).

## Ввод/вывод

stdin не читается. Мета-блок и запрос идут в **stderr**; stdout не
используется вовсе. Порядок и имена полей сохранены от рабочей версии:

```
marketplace: wb
source_table: schema_777.wb_unit_proto
date_suffix: 20260827
server: sl-9
pg_host: 10.9.9.9
pg_port: 5432
database: mp
sql:
CREATE TABLE backups.wb_unit_proto_777_20260827 AS
SELECT * FROM schema_777.wb_unit_proto;
```

Поле `source_table` несёт таблицу **вместе со схемой**
(`schema_777.wb_unit_proto`): блок читают глазами перед тем, как
создать копию, и «из какой схемы» там важнее самого имени.

Тот же блок печатается и при `--dry`, и после выполнения: в первом
случае это то, что ушло бы серверу, во втором — то, что ушло. Отличает
их поле `dry` структурного результата.

Форма запроса дословная, включая перевод строки перед `SELECT`:

```
CREATE TABLE backups.<таблица>_<schema_id>_<YYYYMMDD> AS
SELECT * FROM schema_<schema_id>.<таблица>;
```

## Побочные эффекты

Без `--dry` — одно соединение с PostgreSQL сервера клиента и один
`CREATE TABLE` в схеме `backups`. Транзакция обычная, пишущая: сессия
открывается в режиме `write` (`specs/sql.md`), иначе сервер отбил бы
запрос сам. С `--dry` — ни соединения, ни сети.

Данные источника не меняются и не удаляются: копия только читает
таблицу клиента.

## Конфигурация

Адрес сервера и креды — тем же слоем, что у `mpu sql`
(`specs/sql.md`, `platform/env-file.md`): `pg_<N>` — хост, `PG_PORT` —
порт (по умолчанию 5432), `PG_DB_NAME` — база, личные
`PG_MY_USER_NAME`/`PG_MY_USER_PASSWORD` старше общих
`PG_MAIN_USER_*`. Своих ключей у команд нет.

Кэш-БД (`platform/store.md`) читается ради резолва селектора; при
`--server sl-N` он не нужен.

## Инварианты

- Имя копии полностью определяется тремя вещами: таблицей, `schema_id` и
  суффиксом даты. Ничего из окружения в него не попадает.
- `--dry` не открывает соединения ни при каком вводе.
- Всё, что решается без сети, решается до неё: неверная дата и
  неоднозначный клиент отбиваются раньше соединения.
- Сессия закрывается при любом исходе запроса, включая отказ сервера.
- Креды в вывод не попадают: мета-блок несёт хост, порт и базу, но не
  имя пользователя и не пароль.

## Граничные случаи и ошибки

- `--date` не из восьми цифр → `mpu backup-<X>: bad --date '<D>',
  expected YYYYMMDD`, exit 2, до соединения.
- `schema_id` не выводится (кандидаты дают разные `client_id` либо
  кандидатов нет, а селектор не число) → `mpu backup-<X>: cannot derive
  client_id from selector '<S>'; pass --schema-id explicitly` + список
  кандидатов в stderr, exit 2.
- Селектор пуст либо неоднозначен → тексты и кандидаты
  `platform/selector.md`, exit 2.
- Ключа `pg_<N>` нет в env-файле → сообщение слоя env-файла, exit 2.
- Отказ PostgreSQL (таблица уже есть, нет схемы, нет прав) → текст
  сервера, exit 1. Повторный вызов с тем же суффиксом даты — как раз
  такой отказ: имя копии занято.

## Известные отклонения

- **preserve** — порядок и имена полей мета-блока (`marketplace`,
  `source_table`, `date_suffix`, `server`, `pg_host`, `pg_port`,
  `database`, затем `sql:`) сохранены от рабочей версии, хотя у
  соседнего `mpu sql` блок начинается с `server`. Причина: блок
  копируют в переписку как есть, и переставленные строки в нём
  выглядели бы другим отчётом.
- **preserve** — `source_table` в мета-блоке несёт схему
  (`schema_777.wb_unit_proto`), а не одно имя таблицы: так печатает
  рабочая версия, и это верно по существу — блок читают перед тем, как
  создать копию, и «из какой схемы» там важнее имени.
- **preserve** — дата суффикса берётся по Москве, а не по часовому
  поясу машины. Причина: имя копии читают люди, у которых рабочий день
  по Москве; на машине в другом поясе суффикс разъезжался бы с их
  календарём.

## Известные отклонения

- **fix** — состав блока при выполнении. У оригинала безусловны три строки
  (`marketplace`, `source_table`, `date_suffix`), а `server`, `pg_host`,
  `pg_port`, `database` и текст запроса печатаются только при `--dry` либо
  `--verbose`; у нас блок всегда полный, и флага `--verbose` у этих команд
  нет вовсе. Оставлено полным намеренно, решение 2026-08-31: запись о том,
  **куда именно ушла копия**, нужна как раз при выполнении, а не при
  предпросмотре, и она же попадает в журнал вызовов — то есть остаётся у
  оператора, когда терминал закрыт. Секретов в блоке нет: креды в него не
  входят (см. инварианты).

- **fix** — мета-блок печатался в stdout, а у оригинала он в stderr
  (замер 2026-08-31, пара на `--dry`). Правильно — stderr, и не ради
  паритета: это наша же конвенция, по которой stdout несёт только
  результат, а всё служебное уходит в stderr (`sql-ro.md`: «stdout —
  только данные результата; stderr — meta-блок»; `d2-miro.md`: «stdout
  — только план `--dry-run`, всё служебное — stderr»). У `backup`
  результата на stdout нет вовсе, поэтому там должно быть пусто.

  Цена ошибки наблюдаемая: `mpu backup-… --dry > file` у оригинала даёт
  пустой файл, у переноса — мета-блок; `2>/dev/null` ведёт себя
  зеркально. Конвейер, написанный под одну версию, у другой молча
  меняет смысл.
