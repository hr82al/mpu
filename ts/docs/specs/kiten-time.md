# mpu kiten time

Статус: черновик

## Назначение

Учёт времени карточки Kaiten: записи (`ls`/`add`/`edit`/`rm`) и личный таймер
(`start`/`status`/`stop`/`discard`). Остановка таймера с этой же семантикой
переиспользуется `mpu kiten close` — контракт остановки здесь. Обвязка Kaiten (base URL
и токен, HTTP-слой и его ошибки, селектор карточки, роли) — `platform/kaiten-http.md`.

## CLI-контракт

Общее: `SELECTOR` — ID карточки или её URL (`platform/kaiten-http.md`); обязателен
везде, кроме `ls`/`status`. `DURATION` → целые минуты: `3h` | `1h15m` | `1:15` | `90`
(голое число = минуты) | `2.5h`; единицы `h`/`m`/`ч`/`м` (каждая не чаще раза), регистр
и внутренние пробелы не значимы, дробь с `.`/`,` округляется ВВЕРХ до минуты; итог —
1..1440. Даты — строго `YYYY-MM-DD`; дата по умолчанию — сегодня по МСК (UTC+3), не по
локальной зоне машины. `--role REF` — ID или подстрока названия роли (числовой → ID как
есть, иначе точное совпадение названия без регистра, иначе подстрока); действующая роль:
явный `--role` → env `KITEN_TIME_ROLE` (нерезолвимое значение — ошибка с префиксом
`KITEN_TIME_ROLE:`, без отката) → роль 12058 («Техподдержка»). `--dry-run`
(`add`/`edit`/`rm`/`stop`) — печать плана `dry-run: <действие> · <URL карточки>` тем же
расчётом, что боевой прогон: чтения выполняются, мутаций и записи подсказки нет.
Длительность в выводе — `1 ч 15 мин` / `2 ч` / `45 мин`; счётчик записей: «1 запись» /
«2 записи» / «5 записей».

`ls [SELECTOR] [--all] [--date-from D] [--date-to D] [--role REF] [--json]` — записи
карточки; по умолчанию только записи владельца токена (API отдаёт записи всей компании —
фильтр клиентский), `--all` — всех; фильтры дат по дате записи, границы инклюзивные.
Вывод: таблица `ID ДАТА ВРЕМЯ РОЛЬ [ПОЛЬЗОВАТЕЛЬ при --all] КОММЕНТАРИЙ` + `итого:
<длительность> (N записей)`; нет записей → `(пусто)`. `--json`: `{"total_minutes": int,
"logs": [...]}`; запись — плоский объект `{id, card_id, for_date, minutes, role_id,
role, user_id, user, comment}`. Без `SELECTOR` — сводка за период, `--date-from`
обязателен; кандидаты — карточки, где пользователь участник и обновлявшиеся в окне,
плюс карточки из локальных подсказок (карточку вне обоих источников сводка не увидит).
Сортировка — (дата, карточка, id записи). Вывод: как выше, но первые колонки `ДАТА
КАРТОЧКА`, итог — `итого: <длительность> (N записей, просмотрено карточек: M)`, пусто →
`(пусто) · просмотрено карточек: M`; `--json` — плюс `"scanned_cards": M`.

`add SELECTOR DURATION [--date D] [--role REF] [--comment/-m TEXT] [--dry-run]` —
создать запись; пустой `--comment` (дефолт) = без комментария. Дата в будущем не
блокируется: stderr `внимание: дата <D> в будущем`. Успех: `ok: +<длительность> · <дата>
· <роль> · запись <id> · <URL>` — из ответа сервера.

`edit SELECTOR LOG_ID [--time DURATION] [--date D] [--role REF] [--comment/-m TEXT]
[--force] [--dry-run]` — частичное обновление: тело только из явно заданных осей;
`--comment ''` очищает комментарий — иное, чем отсутствие флага. Успех: `ok: запись <id>
· <только изменённые оси> · <URL>` (очистка — `комментарий очищен`).

`rm SELECTOR LOG_ID [--force] [--dry-run]` — удалить запись; печатает удалённую целиком
(`ok: удалена запись <id> · <дата> · <длительность> · <роль>[ · «комментарий»] · <URL>`)
— страховка от опечатки в ID.

`start SELECTOR [--role REF] [--comment/-m TEXT] [--force]` — запустить таймер. Роль API
таймера не хранит (принимает и теряет) и в запрос не идёт — запоминается в локальной
подсказке для `stop`. Перед стартом — свежее чтение карточки; конфликты — см. «Граничные
случаи»; `--force` игнорирует таймер на другой карточке. Успех: `ok: таймер запущен
<ЧЧ:ММ МСК> · <роль> · <URL>`.

`status [SELECTOR] [--json]` — чтение без мутаций. Без `SELECTOR` карточка берётся из
локальной подсказки о запущенном таймере; подсказки нет → stdout `таймер: не знаю ни об
одном запущенном (подскажи карточку)` / `--json` `{"card_id": null, "timer": null}`,
exit 0. С карточкой: `таймер: идёт <длительность> (с <ЧЧ:ММ МСК>)[ · «комментарий»]`
либо `таймер: не запущен`, затем `всего по карточке: <длительность>`. `--json`:
`{"card_id", "timer": null | {id, started_at, elapsed_minutes, comment}, "total_minutes"}`.

`stop SELECTOR [--time DURATION] [--role REF] [--comment/-m TEXT] [--dry-run]` —
остановить таймер, создав запись. Роль записи: явный `--role` → роль из подсказки от
`start` → env/дефолт. Комментарий: явный `-m` → описание от `start` (передаётся в запрос
обязательно — сервер сам его из таймера не переносит). Без `--time` начало не
передаётся, финиш = «сейчас». С `--time N`: начало = старт таймера, усечённый до целой
минуты, финиш = начало + N; финиш попал бы в будущее (N больше натёкшего) → финиш =
«сейчас», усечённое до минуты, начало = финиш − N, плюс предупреждение. Созданная запись
перечитывается из списка записей карточки: `ok: таймер остановлен · записано
<длительность>[ (по факту <длительность>) при --time ≠ факту] · <дата> · <роль> · запись
<id> · <URL>`; сервер не вернул id записи → `ok: таймер остановлен · запись <id> ·
<URL>`.

`discard SELECTOR` — сбросить таймер без создания записи. Таймер идёт → `ok: таймер
сброшен без записи (шёл <длительность>) · <URL>`; нет → `ok: таймера нет — нечего
сбрасывать · <URL>`, exit 0 (идемпотентно — в отличие от `stop`, где тихий успех
означал бы потерянную работу).

Живые сценарии: `time status`; `time ls 1234567`; `time stop 1234567 --role Диагностика
-m 'разбор жалобы'`; `time add <URL карточки> 1h30m -m 'фикс'`.

## Ввод/вывод

stdout — данные и `ok:`-строки; stderr — предупреждения `внимание: …` и ошибки `mpu
kiten time <sub>: <причина>[; попробуй: <подсказка>]`, без трейсбеков. Exit: 0 — успех;
2 — ошибки ввода (длительность, дата, роль, пустое обновление, сводка без
`--date-from`, нераспарсенный селектор); 1 — доменные и сетевые. Не-2xx ответ Kaiten →
exit 1, `… kaiten error: <текст HTTP-ошибки, platform/kaiten-http.md>`; обрамление
ошибок ввода (usage-блок) задаёт общий CLI-слой.

## Побочные эффекты

HTTP Kaiten (обвязка, формы ответов, пагинация — `platform/kaiten-http.md`):

- `ls`: `GET /cards/{id}/time-logs`; без `--all` — плюс `GET /users/current`. Сводка
  дополнительно: `GET /cards?member_ids=<я>&updated_after=
  <D0>T00:00:00Z&updated_before=<D1>T23:59:59Z` (ось без флага не фильтруется), затем
  `GET /cards/{id}/time-logs` на кандидата.
- `add`: `POST /cards/{id}/time-logs` body `{for_date, time_spent, role_id, comment}`
  (минуты — единица API).
- `edit`/`rm`: `GET /cards/{id}/time-logs` (+`GET /users/current` для проверки
  владельца) → `PATCH /cards/{id}/time-logs/{logId}` body `{time_spent?, for_date?,
  role_id?, comment?}` (пустое тело не отправляется никогда) / `DELETE
  /cards/{id}/time-logs/{logId}`.
- `start`: `GET /cards/{id}` (+ по карточкам подсказок) → `POST /user-timers` body
  `{card_id[, comment]}`; ответ без `id` (тело `{"message": "User timer already
  created"}`, не обязательно HTTP-ошибка) = таймер уже создан.
- `status`/`stop`/`discard`: `GET /cards/{id}` — поле `timer`, единственный источник
  истины о таймере (глобального списка таймеров в API нет); `stop` далее `PATCH
  /user-timers/{timerId}` body `{finished_at[, started_at][, comment][, role_id]}`
  (`finished_at` обязателен; ответ несёт id созданной записи) и `GET
  /cards/{id}/time-logs`; `discard` — `DELETE /user-timers/{timerId}`. Отправляемые
  метки времени — ISO 8601 в зоне старта таймера, миллисекунды всегда `.000` (сервер
  округляет `finished − started` вверх до минуты).

Локально — подсказки таймера в кэш-БД (bootstrap — `init.md`), строка на карточку: id
карточки и таймера, роль, комментарий, метка старта, момент последнего списания. Пишут:
`add` (роль), `start` (всё), `stop`/`discard`/`status` (очистка таймерной части; роль
остаётся). Читают: `stop`, `start`, `status` без селектора, `ls`-сводка.

## Конфигурация

Env `KITEN_TIME_ROLE` — роль по умолчанию (ID или подстрока названия). Base URL и токен
Kaiten, кэш ролей — `platform/kaiten-http.md`.

## Инварианты

- Единица длительности — целые минуты, округление вверх; секунд нет нигде.
- «Сегодня» и часы-минуты в выводе — по МСК.
- Фильтр «только мои записи» — всегда клиентский, по id владельца токена.
- Блокирующие решения о таймере — только по свежему чтению карточки; локальная подсказка
  — эвристика, сама ничего не запрещает.
- `stop` печатает перечитанную с сервера запись, а не свои вычисления.
- `ls`/`status` без мутирующих HTTP-вызовов; единственная локальная запись в read-пути —
  самоочистка протухшей подсказки.
- Чужая запись не меняется и не удаляется без `--force`; запись без владельца (`user_id`
  = null) — без ограничений.

## Граничные случаи и ошибки

- `DURATION` (причина с префиксом `'<вход>': `, всё exit 2): ноль/отрицательное →
  `нулевая длительность бессмысленна`; > 1440 → `больше 24 ч в одной записи; заведите
  записи по дням через --date`; `1h15` → `после числа нужна единица измерения —
  вероятно, вы имели в виду '1h15m'`; `1:60` → `минуты в форме Ч:ММ должны быть 00–59`;
  мусор → `неразобранная длительность; ожидается <перечень форм>`.
- Невалидная дата → exit 2 `<флаг>='<значение>': ожидается YYYY-MM-DD`.
- `--role` без совпадений → exit 2 `role '<ref>' не найден — см. `mpu kiten roles``;
  несколько → exit 2 `role '<ref>' неоднозначен (<N> совпадений):` + до 10 кандидатов
  `id (название)`.
- `ls` без селектора и `--date-from` → exit 2 `без карточки нужен период: --date-from
  YYYY-MM-DD (иначе пришлось бы опросить все карточки подряд)`.
- `edit` без единой оси → exit 2 `нужно хотя бы одно из --time / --date / --role / --comment`.
- `edit`/`rm`: `LOG_ID` не с карточки → exit 1 `записи <id> нет на карточке <card_id>` +
  подсказка `time ls <card_id>`; чужая запись без `--force` → exit 1 `запись <id>
  принадлежит другому пользователю (user_id=<их>, я <мой>); повтори с --force`.
- `start`: таймер на этой карточке → exit 1 `таймер на карточке <id> уже запущен (с
  <ЧЧ:ММ МСК>)` + подсказки `time stop`/`time discard`; на другой (по подсказке,
  подтверждённой свежим чтением; протухшая молча чистится, недоступная не блокирует) →
  exit 1 `таймер уже идёт на карточке <other> (с <ЧЧ:ММ МСК>)` + подсказки `time stop
  <other>`/`--force`; ответ «уже создан» без id → exit 1 `Kaiten сообщает, что таймер …
  уже создан` + `time stop`.
- `stop` без запущенного таймера → exit 1 `таймер на карточке <id> не запущен` +
  подсказка `time start <id>`.
- `stop --time` больше натёкшего → stderr `внимание: --time <X> больше фактических <Y> —
  начало сдвинуто назад`, запись создаётся.
- Дата созданной `stop` записи ≠ московскому дню финиша (сервер берёт её от финиша в
  UTC; расходятся в 00:00–03:00 МСК) → stderr-предупреждение с готовой командой `time
  edit <карточка> <id> --date <мск-день>`.
- Сбой чтения списка карточек-кандидатов сводки → сводка не падает: кандидаты только из
  подсказок; счётчик просмотренных отражает факт.

## Golden-примеры

Кандидаты (снять с живой версии при переводе в «к реализации»; карточка и записи —
синтетические, на тестовой карточке): `time ls <card>` и с `--json`; `time status
<card>` и с `--json` (оба состояния таймера); `time status --json` без селектора и
подсказки (`card_id: null`); `time add <card> 0 --dry-run` (exit 2); `time edit <card>
<log_id>` без осей (exit 2); `time ls --date-from <D> --json` (сводка; дорого — запрос
на карточку, окно брать узкое).

## Известные отклонения

- **fix** — в `add` текст ошибки разбора длительности начинается с `--time`, хотя
  `DURATION` у `add` — позиционный аргумент и флага `--time` там нет. Правильное
  поведение: причина называет аргумент `DURATION` (у `edit`/`stop` — флаг `--time`).
- **preserve** — best-effort сводка `ls`: сбой чтения списка карточек или отдельной
  карточки не роняет команду, выдаётся частичный результат. Причина: частичный отчёт
  полезнее отказа, неполнота видна по счётчику «просмотрено карточек».
- **preserve** — `status` чистит протухшую таймерную подсказку в read-пути. Причина: без
  самоочистки мёртвая подсказка навсегда блокировала бы `start` на других карточках.
