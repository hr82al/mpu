# mpu mp-clone

Статус: к реализации (2026-09-24). Требования сняты живым подъёмом рабочей области с нуля на чистой
машине 2026-09-24: каталоги субрепо были пустышками с одними env-файлами, ключа GitLab не было в
`known_hosts`, личности git не было. Порядок ниже — тот, что сработал руками.

## Назначение

Развернуть рабочую область `mp` из GitLab одной командой: склонировать каждый субрепо, которого нет,
рядом с корнем `mp`, и не тронуть ни один, который уже есть. Повторный вызов на готовой области —
ноль мутаций. Команда готовит область для `mpu mp-init` (`mp-init.md`), контейнеры не трогает.

## CLI-контракт

`mpu mp-clone` · `mpu mp-clone dry`

- `dry` — напечатать план (что клонируется, что пропускается и почему) без мутаций; probe'ы
  (`git ls-remote`, проверка каталогов) выполняются.
- Строка может дойти до записи на диск, поэтому путь — `ask` (`mpu ask mp-clone`).

Коды выхода: 0 — область готова (в том числе когда какого-то субрепо нет на сервере, см. ниже);
2 — не найден корень `mp` или `mp.code-workspace`; 1 — упал `git clone` субрепо, который на сервере
есть; 3 — ключ хоста GitLab не в `known_hosts` (см. «Граничные случаи»).

## Что клонируется

Список субрепо = объединение двух источников, без повторов, в порядке первого появления:

1. `folders[].path` из `<корень mp>/mp.code-workspace`, кроме `"."` (сам `mp`).
2. Служебные субрепо, без которых не поднимается стенд и не работает тулинг, даже если их нет в
   workspace: `mp-config-local` (compose и алиасы стенда), `ai-tools` (`mp-stand`, диагностика),
   `opiu-service`.

Адрес: `ssh://git@gitlab.btlz-api.ru:2222/wb/<имя>.git`. HTTPS не используется: без кред он отвечает
`could not read Username`, а ssh-ключ пользователя на машине есть (проверено 2026-09-24: ssh работает,
https нет). `mpu` (`github`), `10x-ozon` и прочие каталоги, у которых уже есть свой `.git`, не трогаются.

## Состояние каталога → действие

| Состояние `<корень>/<имя>` | Действие |
| --- | --- |
| нет каталога | `git clone <url> <имя>` |
| каталог с собственным `.git` (`git -C <имя> rev-parse --show-toplevel` = сам каталог) | пропуск, строка `уже есть: <имя> (<ветка> <sha>)` |
| каталог БЕЗ своего `.git` (git отвечает корнем `mp`) — пустышка с локальными файлами | клонировать поверх, сохранив локальные файлы (ниже) |
| на сервере нет репозитория (`ls-remote` не находит) | предупреждение `нет на сервере: <имя>`, пропуск, exit не меняется |

**Клон поверх пустышки** — живой случай 2026-09-24: `sw-back`, `sw-front`, `sl-front`, `10x-ozon`,
`mp-config-local`, `ai-tools`, `opiu-service` были каталогами с `.env`, `.env.example`,
`.env.development` и пустыми подкаталогами. `git clone` в непустой каталог отказывает. Порядок:

1. Копия каталога целиком в `~/tmp/mp-clone-backup/<дата-время>/<имя>` (до любой записи).
2. `git clone --no-checkout <url> <временный каталог>` и перенос `<временный>/.git` в `<имя>/.git`.
3. `git -C <имя> checkout -f HEAD -- .` — неотслеживаемые локальные файлы (`.env`) остаются.
4. Каждый файл из копии, который отличается от файла в каталоге после checkout, вернуть из копии:
   это отслеживаемый файл, который владелец правил локально (2026-09-24: `sw-front/.env.example`,
   `opiu-service/.env.example`). В `git status` он станет `M` — так и должно быть, правка его.
   Строка вывода: `восстановлен локальный: <путь>`.

## Предусловия и побочные эффекты

1. **Ключ хоста GitLab.** Первый ssh к `gitlab.btlz-api.ru:2222` на чистой машине падает `Host key
   verification failed`. Команда НЕ принимает ключ сама и не пишет в `~/.ssh`: принять ключ хоста —
   решение человека. Проверка: `ssh-keygen -F '[gitlab.btlz-api.ru]:2222'`. Нет ключа — отказ exit 3 с
   отпечатком, снятым `ssh-keyscan -p 2222 gitlab.btlz-api.ru` (печатать `ssh-keygen -lf -`), и готовой
   строкой для человека: `ssh-keyscan -p 2222 gitlab.btlz-api.ru >> ~/.ssh/known_hosts`.
2. **Сентинел корня** `<корень>/.mp-workspace-root` — создать пустым, если его нет. Без него
   `ai-tools/bin/*` (`mp-stand`) падают `mp-root: cannot locate workspace` (живой случай 2026-09-24).
   Файл в `.gitignore` `mp`.
3. **`.gitignore` и workspace `mp`.** Каждый склонированный субрепо должен стоять в `.gitignore`
   корня строкой `/<имя>/` (иначе внешний `mp/.git` видит его как неотслеживаемый каталог). Нет
   строки — дописать в блок «Detected subrepos». В `mp.code-workspace` команда ничего не пишет:
   это её вход. Изменения `mp` не коммитит — строка `в mp не закоммичено: .gitignore`.
4. **Личность git.** Нет `user.name`/`user.email` ни глобально, ни в субрепо — предупреждение с
   подсказкой `git config --global user.name … && git config --global user.email …`. Сама не
   задаёт: живой случай 2026-09-24 — коммит изолированной сессии упал без личности, имя пришлось
   брать из истории GitLab (`hr82al <hr82al@gmail.com>`), а не из email пользователя.

## Ввод/вывод

stderr — строка на субрепо: `склонирован: <имя> (<ветка> <sha>)`, `уже есть: …`, `поверх пустышки:
<имя>, копия <путь>`, `восстановлен локальный: <путь>`, `нет на сервере: <имя>`. Итог — `mp-clone:
N склонировано, M уже было, K нет на сервере`. stdout пуст. `dry` — те же строки с префиксом
`план:` и финал `dry-run: ничего не выполнено`.

## Инварианты

- Идемпотентность: второй прогон подряд — ноль `git clone`, ноль записей на диск, exit 0.
- Каталог с собственным `.git` не трогается никогда: ни fetch, ни checkout, ни смена ветки.
- Локальные файлы пустышки не теряются: копия снимается до первой записи, отличающиеся файлы
  возвращаются.
- `~/.ssh` и глобальный git-конфиг команда не пишет.
- Ветка — дефолтная ветка репозитория на сервере (`main` / `trunk` / `dev` по субрепо), без `-b`.

## Граничные случаи и ошибки

- Нет `mp.code-workspace` → exit 2 с путём.
- `git ls-remote` отвечает не «нет репозитория», а ошибкой сети/ключа → это не «нет на сервере»:
  exit 1 с текстом git (иначе падение сети выглядело бы как отсутствие репо).
- Упал `git clone` посреди пустышки после переноса `.git` → каталог восстанавливается из копии,
  exit 1.
- `mp-support-scripts-old` в workspace есть, на сервере нет (2026-09-24) — ожидаемое предупреждение.
