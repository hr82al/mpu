# mpu sql

Статус: реализовано

## Назначение

Write-capable SQL по селектору: реальная мутация БД (INSERT / UPDATE /
DELETE / DDL). Контракт целиком общий с `specs/sql-ro.md`; здесь —
только отличия. Для любого чтения используется `mpu sql-ro`.

## CLI-контракт

`mpu sql SELECTOR [SQL] [--server sl-N] [--dry] [--json] [--md]
[-v/--verbose]`

Синопсис, маршруты селектора (dev / обычный), источники SQL,
search_path, форматы вывода, meta-блок и коды выхода — идентичны
`specs/sql-ro.md`; маршрут sw — `specs/sql-sw.md` (общий для обеих
команд). Отличия:

- сессия открывается пишущей: без опции
  `default_transaction_read_only=on` (обычный/dev маршруты) и без
  `SET default_transaction_read_only = on` в скрипте маршрута sw;
  пишущий SQL исполняется и фиксируется;
- в meta-блоке нет строки `mode: read-only`;
- префикс ошибок — `mpu sql:` (тексты — те же, что в sql-ro);
- подтверждения внутри команды нет: защита записи — внешний
  permissions-слой запускающего окружения, паттерн 1
  `platform/readonly-default.md`. `--dry` — превью, не защита.

## Ввод/вывод

Как в `specs/sql-ro.md`. Успешная мутация без result set →
`OK (rowcount=<N>)` (с `--json` — `{"ok": true, "rowcount": <N>}`),
exit 0. Отказ read-only-сессии (`запрос пытается писать …`) из
`mpu sql` недостижим: сессия пишущая.

## Побочные эффекты

Как в `specs/sql-ro.md`, плюс главное: команда мутирует удалённую БД
(прод-данные клиента/сервера), если SQL пишущий — включая
data-modifying CTE, пишущие функции и DDL. Вся строка SQL исполняется
в одной транзакции: успех фиксируется целиком, ошибка любого оператора
откатывает всё — частичной записи не бывает, **пока текст пользователя
сам не управляет транзакцией**. Собственный `COMMIT` внутри текста
закрывает транзакцию вызова, и написанное до него остаётся в БД, даже
если следующий оператор упадёт. Ловить это нечем: у read-only-сессии
такой обход упирается в метку сервера (`25P01`/`3B001`), у пишущей
метки нет по построению. Оригинал ведёт себя так же (неявная транзакция
драйвера с фиксацией на выходе), и переезд её не меняет.

## Конфигурация

Как в `specs/sql-ro.md` (env-переменных, специфичных только для
`mpu sql`, нет).

## Инварианты

- Для читающего SQL вывод и коды выхода побитово совпадают с
  `mpu sql-ro` (отличие только в meta-блоке: нет `mode: read-only`).
- Одна транзакция на вызов: наблюдаемое состояние БД после ошибки — как до
  вызова, если сам текст не закрыл транзакцию своим `COMMIT`
  («Побочные эффекты»). Проверяется **последовательностью операторов, ушедших драйверу**:
  открытие транзакции, текст пользователя, фиксация; при ошибке вместо
  фиксации — откат. Живая мутация для этого не нужна и в тестах не ставится.
- `--dry` не открывает ни одного соединения и не выполняет exec —
  единственный режим, безопасный по построению.
- Мутация происходит только по явно переданному SQL; никаких скрытых
  записей (кэша, файлов) команда не делает.

## Граничные случаи и ошибки

Общие — `specs/sql-ro.md` (пустой SQL, конфликт флагов, `--server` с
dev/sw, резолв, конфигурация — с префиксом `mpu sql:`). Специфичные:

- пишущий SQL, затронувший 0 строк (`UPDATE … WHERE 1=0`) →
  `OK (rowcount=0)`, exit 0;
- ошибка БД посреди многооператорной записи → `db error: <текст>`,
  exit 1, транзакция откачена целиком;
- нарушение констрейнта / синтаксическая ошибка → `db error: <текст>`,
  exit 1, записи нет.

## Golden-примеры

`fixtures/sql/`. Meta-блок и ошибка БД сняты живым прогоном рабочей версии
2026-08-17; адрес и номер сервера заменены плейсхолдерами, как в
`fixtures/sql-ro/`. Две строки успеха записи — синтетические: живой голден
на них требует настоящей мутации, а dev-маршрут в окружении не настроен
(`DEV_PG_HOST` не задан), прод же для этого не используется.

- `dry-v-server-stderr.txt` — `--dry -v`: тот же meta-блок, что у
  `sql-ro`, **без строки** `mode: read-only`. Это и есть единственное
  наблюдаемое отличие на читающем SQL.
- `ok-rowcount-stdout.txt` — запись без result set: `OK (rowcount=0)`.
- `ok-rowcount-json-stdout.txt` — то же с `--json`, одной строкой.
- `db-error-stderr.txt` — синтаксическая ошибка: `db error:` и текст
  сервера как есть, включая строку с указателем. Форма общая с `sql-ro`.

Каждый файл оканчивается одним переводом строки. Голдена на транзакционность
нет по построению — см. «Инварианты»: она проверяется последовательностью
операторов, ушедших драйверу, а не живой мутацией.

## Известные отклонения

Отклонения `specs/sql-ro.md` действуют и здесь (ошибка конфигурации →
exit 2 без трейсбека; единая шапка таблицы при 0 строк), отклонения
маршрута sw — `specs/sql-sw.md`. Свои:

- **preserve** — `PGOPTIONS` из окружения доезжает до сервера. Опций
  стартового пакета у пишущей сессии нет, а драйвер подставляет туда
  переменную окружения, если своих опций ему не дали; у `sql-ro`
  фолбэк закрыт побочно — непустой строкой `-c
  default_transaction_read_only=on`. Закрыть симметрично можно только
  нейтральным параметром в стартовом пакете, то есть добавив пишущей
  сессии то, чего у неё по контракту нет, и приняв цену «отказ пулера»
  (`platform/readonly-default.md`). Оригинал ведёт себя ровно так же:
  разница между командами — его свойство, а не дефект переезда.
- **preserve** — собственный `COMMIT` в тексте пользователя разрывает
  транзакцию вызова («Побочные эффекты»).

## Открытые вопросы

Нет. Оба закрыты 2026-08-17:

- **транзакционность** проверяется последовательностью операторов, ушедших
  драйверу («Инварианты»), а не живой мутацией: голден на неё не заводится;
- **единый контракт подтверждения мутаций не вводится.** Своего подтверждения
  у команды нет и не появляется: запись защищает внешний слой разрешений
  запускающего окружения (паттерн 1 `platform/readonly-default.md`), а `--dry`
  остаётся превью. Причина — требование поведенческой нейтральности переезда:
  общий контракт флагов менял бы поверхность сразу четырёх команд, у которых
  в оригинале нет общего решения. Вопрос вернётся отдельной задачей, если
  когда-нибудь понадобится, — и уже не как условие переезда.
