# mpu api

Статус: к реализации (заморожена 2026-08-28; формы читающих команд сняты
живьём, открытый вопрос снят решением о переносе группы целиком)

## Назначение

Неймспейс HTTP-клиентов sl-back: `mpu api <команда>` — тонкая обёртка
одного admin-эндпоинта (декларативный эндпоинт, `EndpointSpec`) либо
кастомная команда с резолвом селектора (семейство `wb-loader-*` и
другие). Обвязка (URL, токен, транспорт) — `platform/slback-http.md`.

Правило переезда: единица переезда — группа эндпоинтов. Эндпоинт едет
только после дословной фиксации в `api-<группа>.md` (метод + путь +
path-параметры + поля тела + форма вывода + ошибки); первая группа —
`api-wb-loader.md`. Команда, не зафиксированная ни в одной
`api-*.md`, остаётся за маршрутом `legacy`
(`platform/registry.md`) и ведёт себя как раньше; список в
`mpu api --help` покрывает команды обеих сторон.

## CLI-контракт

`mpu api <команда> [ARGS…]`

- `mpu api --help` / `-h` — справка со списком всех команд (одна
  строка на команду), stdout, exit 0. `mpu api` без подкоманды — та
  же справка в stderr, exit 2, без трейсбека (оригинал ведёт себя
  иначе — см. «Известные отклонения»). `mpu api <неизвестное>` →
  stderr содержит Usage-строку, подсказку `Try 'mpu api -h' for
  help.` и текст `No such command '<имя>'.`, exit 2 (оформление не
  фиксируется — см. «Известные отклонения»). `--help`/`-h` работает у
  каждой команды, exit 0.

### Декларативные команды

`mpu api <имя> [PATH_ARGS…] [--<поле> <значение>]… [--body/-b JSON]`

- Path-параметры эндпоинта → обязательные позиционные аргументы в
  порядке появления в пути; значение подставляется в путь
  URL-экранированным целиком (включая `/`).
- Поля тела → опции `--<поле> <значение>`; имя опции — точное имя
  поля (регистр значим: `--newPassword`). Типизация по объявленному
  типу поля:
  - string — как есть;
  - number — строка с `.` или `e`/`E` → дробное, иначе целое; не
    число → ошибка `--<поле>: ожидается число, получено '<значение>'`;
  - boolean — `true`/`yes`/`1`/`on` → истина, `false`/`no`/`0`/`off`
    → ложь (без учёта регистра); иначе ошибка `--<поле>: ожидается
    boolean (true/false/yes/no/1/0), получено '<значение>'`;
  - json — JSON-литерал; невалидный → ошибка `--<поле>: ожидается
    JSON, получено '<первые 60 символов>...': <детали>`.
- Обязательное поле без значения → ошибка `--<поле> обязателен`.
- Незаданные поля в тело не входят; ни одного заданного поля →
  запрос без тела.
- `--body/-b` (у эндпоинтов, принимающих произвольное тело):
  значение `@<путь>` → JSON из файла (файл не читается → ошибка
  `--body @<путь>: <причина>`), иначе значение — сам JSON-литерал
  (невалидный → `--body: невалидный JSON: <детали>`). Заданный
  `--body` полностью замещает собранные `--<поле>`.
- Все ошибки выше — ошибки ввода: stderr, exit 2, до сети.
- Query-параметров у декларативных команд нет.
- `--help` команды: summary (метод + путь), описание, список
  path-аргументов и полей тела с типами и признаком required.

### get-token / auth-login

- `mpu api get-token [--email E] [--password P]` — печатает в stdout
  ровно accessToken (одна строка), без JSON-обёртки. Без явных кред —
  cache-first: токен-кэш валиден → печать без сети; иначе логин на
  кредах из env, запись кэша, печать. Оба флага заданы → кэш при
  чтении игнорируется: всегда свежий логин, кэш перезаписывается под
  нового пользователя. Ответ логина без `accessToken` → stderr
  `mpu api get-token: нет accessToken в ответе sl-back`, exit 1.
- `mpu api auth-login --email E --password P` — печатает полный JSON
  ответа `/auth/login` (accessToken + user); оба флага обязательны.
- Прочие `/auth/*` (logout / refresh / verify / resend-email /
  change-password) — обычные декларативные команды.

## Ввод/вывод

- stdout — данные: JSON-ответ сервера как получен, pretty-print
  (indent 2, unicode как есть); пустой ответ → пустой stdout, exit 0.
- stderr — ошибки:
  `mpu api <имя>: <причина>[; попробуй: <подсказка>]` одной строкой;
  сохранённое тело ответа сервера (обрезано до 500) — отдельной
  строкой следом, если непусто.
- Exit: 0 — успех; 2 — ошибки ввода (валидация до сети); 1 — сеть,
  HTTP ≥ 400, невалидный ответ, отсутствие env-конфигурации.

## Побочные эффекты

- 0–2 HTTP-запроса на вызов: логин при холодном/просроченном
  токен-кэше + сам эндпоинт (`get-token` при горячем кэше — 0).
- Запись файла токен-кэша (`platform/slback-http.md`).
- Запись в журнал вызовов (`platform/invoke-log.md`); вывод
  `get-token` в журнал не перехватывается (живой токен), секретные
  аргументы командной строки маскируются.

## Конфигурация

`BASE_API_URL`, `NEXT_PUBLIC_SERVER_URL`, `TOKEN_EMAIL`,
`TOKEN_PASSWORD` — контракт и тексты ошибок в
`platform/slback-http.md`; своих env-переменных у неймспейса нет.

## Инварианты

- Декларативная команда ничего не добавляет к ответу: stdout — сырой
  JSON сервера без обёрток и переименований.
- stdout `get-token` — только токен; JSON-ключей и лишних строк нет.
- Валидация ввода всегда предшествует первому сетевому обращению.
- Пароль не попадает ни в stdout, ни в stderr, ни в журнал; токен —
  в stdout только у `get-token` / `auth-login` (их назначение), в
  stderr — никогда.
- `--body` и `--<поле>` не смешиваются: приоритет у `--body` целиком.

## Граничные случаи и ошибки

- Ошибка обвязки (нет базового URL / кред) →
  `mpu api <имя>: <текст из platform/slback-http.md>`, exit 1.
- HTTP ≥ 400 → `mpu api <имя>: <METHOD> <путь> failed: HTTP <код>` +
  тело отдельной строкой, exit 1.
- 2xx не-JSON → `mpu api <имя>: <METHOD> <путь>: non-JSON response:
  <тело до 200>`, exit 1.
- `get-token`: задан лишь один из `--email`/`--password` → работает
  как без явных кред (cache-first); при логине заданный флаг
  побеждает env по своему полю.
- Непредвиденная ошибка исполнения →
  `mpu api <имя>: unexpected error: <причина>`, exit 1, без
  трейсбека.

## Golden-примеры

Сняты 2026-08-28 с рабочей версии на живом клиенте (только читающие вызовы),
обезличены: идентификатор клиента → 777, заголовок и сервер заменены, отметки
времени приведены к постоянным.

- `fixtures/api/get-client.json` — `api get-client <id>`: объект клиента с
  полями `id`, `created_at`, `updated_at`, `data_loaded_at`, `is_active`,
  `server`, `is_locked`, `is_deleted`, `title`, `is_web`, `archived_at`;
- `fixtures/api/list-client-modules.json` — `api list-client-modules <id>`:
  массив `{client_id, module, is_active, last_activation_date, datasets}`.

Пишущих голденов с боевого контура нет и не будет: **на проде не меняется
ничего** (правило владельца 2026-08-28), а запись у этого семейства — создание
и удаление клиентов, токенов и таблиц. Снимать их можно только на локальном
sl-back: он поднимается вместе со стендом (`mpu mp-init` — контейнеры `sl-0` и
`sl-1`) и несёт те же админские эндпоинты. Пока стенд недоступен, пишущая
половина закрывается тестами на подставном сервере, и это записывается в отчёте
прямо, а не подразумевается.

## Известные отклонения

- **fix** — ошибки декларативных команд печатаются с легаси-префиксом
  `mpuapi-<имя>:` (имена бывших отдельных бинарей), кастомных — с
  `mpu api <имя>:`. Правильное поведение — единый префикс
  `mpu api <имя>:` (раздел «Ввод/вывод») у всех команд.
- **fix** — вывод `auth-login` (содержит accessToken) перехватывается
  в журнал вызовов; правильное поведение — не перехватывать, как у
  `get-token`.
- **fix** — оригинал при `mpu api` без подкоманды справку не
  печатает: stdout пуст, stderr — необработанный трейсбек, exit 1;
  текст справки виден лишь внутри сообщения исключения в последних
  строках трейсбека. Правильное поведение — справка в stderr, exit 2,
  без трейсбека (раздел «CLI-контракт», как у `mpu` без аргументов).
- **fix** — байтовый паритет stderr при `mpu api <неизвестное>` не
  требуется: в оригинале сообщение обёрнуто в рамку из псевдографики.
  Оформление не воспроизводится; фиксируется структурный контракт —
  Usage-строка, подсказка `Try 'mpu api -h' for help.`, текст
  `No such command '<имя>'.` в stderr, exit 2. Differential по этому
  случаю сравнивать структурно.
- **fix** — ответы `list-client-wb-tokens` и `list-client-ozon-keys` несут
  чужие секреты клиента (WB-токены, Ozon-ключи), и оригинал пишет их в секцию
  `out` журнала вызовов. Правильное поведение — вывод этих двух команд в журнал
  не пишется (`logsOutput: false`): на stdout секрет остаётся, за ним команду и
  зовут, а на диск в журнал не ложится. Инвариант «пароль и токен sl-back не
  попадают в журнал» этого случая не покрывал — он про наши креды, а не про
  чужие.
- **improve** — опция сырого тела в оригинале называется `body_raw` и короткой
  формы не имеет; здесь она `--body` с короткой `-b` (раздел «Декларативные
  команды»). Имя `body_raw` не принимается: у одного значения было бы два имени.
- **improve** — позиционные path-аргументы в оригинале названы в нижнем
  регистре (`userid`, `clientid`, `spreadsheetid`, `sheetname`); здесь они
  зовутся так же, как параметр в пути (`userId`, `clientId`, `spreadsheetId`,
  `sheetName`). На вызов из CLI это не влияет — аргументы позиционные; имя
  видно в справке, схеме тула и дополнении, и там оно читается.
