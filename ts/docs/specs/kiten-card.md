# mpu kiten card

Статус: к реализации (2026-08-14: вывод всех трёх видов сверен с рабочей
версией; голдены сняты дважды — живым прогоном на тестовой карточке
Kaiten и на синтетическом входе. Живой прогон поправил четыре
утверждения: `properties` — всегда объект и значение бывает массивом,
порядок комментариев в ответе сервера не хронологический, недоступная
карточка даёт 403 с пустым телом, а не 404, и чек-листы карточки в
выводе команды не показываются вовсе)

## Назначение

Прочитать одну карточку Kaiten целиком — шапка, свойства, описание,
файлы, комментарии — в одном из трёх видов: наглядный терминальный,
чистый GFM-markdown для LLM, сырой JSON. Только чтение.

## CLI-контракт

`mpu kiten card SELECTOR [--md] [--json] [--images/--no-images]
[--comments/--no-comments]`

- `SELECTOR` — ID карточки или её URL (короткий/глубокий); разбор — по
  `platform/kaiten-http.md` («Селектор карточки»).
- `--md` — чистый GFM markdown (без ANSI-оформления и картинок).
- `--json` — сырой JSON (карточка + комментарии).
- `--images/--no-images` (дефолт `--images`) — инлайн-картинки в
  наглядном режиме; на `--md`/`--json` не влияет.
- `--comments/--no-comments` (дефолт `--comments`) — включать
  комментарии; `--no-comments` отключает и сам запрос комментариев.

Выбор вида, по убыванию приоритета: `--json` → `--md` ЛИБО stdout не
терминал → наглядный терминальный рендер. Пайп без флагов отдаёт
markdown: `mpu kiten card 123 | <потребитель>` — чистый GFM.

Примеры из практики (обезличены):

    mpu kiten card 65634936 --json
    mpu kiten card https://btlz.kaiten.ru/65634936 --md
    mpu kiten card 65634936 --no-comments

## Ввод/вывод

Внешняя граница — `platform/kaiten-api-cards.md` (карточка, комментарии)
и `platform/kaiten-api-refs.md` (кастомные поля компании). Комментарии
запрашиваются только при включённом `--comments`. Имена кастомных полей
для markdown/наглядного вида — один живой запрос справочника полей
компании, best-effort: сбой → в выводе сырые ключи, команда не падает.
На `--json` имена не нужны — этот запрос не выполняется (см. «Известные
отклонения»).

Метка этапа (`state`) во всех видах: 1 → `queued`, 2 → `in progress`,
3 → `done`; иное число → само число строкой; значения нет → пустая
строка.

`--json` — объект (отступ 2, юникод как есть):
`id` (число), `key`, `title`, `state` (метка), `condition` (число:
1 активная, 2 архив), `due_date`, `board`, `column`, `lane` (названия),
`size_text`, `created`, `updated`, `type`, `tags` (массив строк),
`url`, `owner` (объект `{id, full_name, email, username}` либо null),
`members` (массив таких же объектов), `properties` (объект
`ключ "id_NNN" → значение` — ключи сырые, без резолва имён; всегда
объект, полей нет → `{}`, никогда не null; поле с null-значением из
ответа API в объект не попадает; значение — строка ЛИБО массив строк:
файловое поле несёт массив uid привязанных файлов и остаётся в JSON
массивом, см. «Известные отклонения»),
`description`, `files` (массив
`{id, name, url, mime_type, comment_id, card_cover}`), `comments`
(массив `{id, author, created, text}`). Отсутствующее строковое
значение — null.

Markdown (`--md` / пайп):

- `# {title}`;
- строки `- **Key**: …`, `- **URL**: …`, `- **Этап**: {метка}`,
  `- **Доска**: {доска · колонка · дорожка}` (непустые через ` · `),
  `- **Владелец**: …`, `- **Участники**: …` (через запятую),
  `- **Дедлайн**: {YYYY-MM-DD}`, `- **Теги**: …` — каждая строка
  печатается только при непустом значении; `URL` и `Этап` — всегда;
- `## Свойства` (если есть): `- {имя поля}: {значение}`; имя — по
  справочнику кастомных полей (`id_NNN` → имя), не резолвится → сырой
  ключ; значение-массив (файловое поле) печатается элементами через
  `, ` — без скобок и кавычек, см. «Известные отклонения»;
- `## Описание` — всегда; пустое описание → `_нет описания_`;
- `## Файлы` (если есть): `- [{имя, иначе url}]({url})`;
- `## Комментарии` (если есть): на каждый —
  `### {автор} · {YYYY-MM-DD HH:MM}` (автора нет → `—`; даты нет —
  только автор), пустая строка, текст комментария дословно (GFM,
  включая `![](url)`); порядок — по возрастанию `created`, при равных
  `created` — по возрастанию `id`. Порядок ответа сервера не годится:
  он не упорядочен (`platform/kaiten-api-cards.md`, вызов 3);
- вывод завершается ровно одним `\n`.

Наглядный режим (stdout — терминал): та же информация — шапка,
свойства, описание, комментарии, вложения-картинки; терминальное
оформление и способ отрисовки картинок — свобода реализации.
`--images` управляет только загрузкой и отрисовкой картинок.

Exit: 0 — успех; 2 — ошибки ввода (селектор); 1 — ошибки API.

## Побочные эффекты

Только чтение внешней системы. Локального состояния нет: на диск
команда не пишет ничего. В наглядном режиме с `--images` —
дополнительные HTTP-запросы за байтами картинок по их `url`; это
загрузка файлов с файлового хоста Kaiten, а не вызовы API, и в каталоге
внешней границы она не значится.

## Конфигурация

`KITEN_API_KEY`, `KITEN_BASE_URL` — по `platform/kaiten-http.md`.

## Инварианты

- Kaiten не мутируется ни при каких флагах.
- `--json`-вывод не зависит от справочника кастомных полей (ключи
  `properties` сырые) и от `--images`.
- `--no-comments` → запрос комментариев не выполняется, в JSON
  `comments: []`, раздела `## Комментарии` нет.
- Ключ JSON присутствует всегда; отсутствие значения — null (не
  пропуск ключа).

## Граничные случаи и ошибки

- Невалидный селектор (нет числового сегмента) → exit 2,
  `не удалось извлечь id карточки из '<строка>'`.
- Несуществующая либо недоступная карточка → exit 1, stderr
  `mpu kiten card: kaiten error: kaiten GET /cards/{id} -> 403: ` —
  именно **403 с пустым телом**, а не 404: существование чужой карточки
  сервер не раскрывает, и подставлять в сообщение после двоеточия
  нечего (замер 2026-08-14, голден
  `fixtures/kiten-card/err-not-found-stderr.txt`).
- Карточка с чек-листами → в выводе их нет ни в одном виде: ни ключа в
  JSON, ни раздела в markdown. Чек-листы читает `mpu kiten checklist ls`
  (`kiten-checklist.md`); эта команда о них молчит намеренно.
- Описание или комментарий с GFM-чекбоксами (`- [ ]`, `- [x]`) →
  печатаются дословно, как любой другой markdown: Kaiten их
  интерактивными не делает нигде в тексте (`platform/kaiten-api-cards.md`,
  «Инварианты»), и команда ничего с ними не делает тоже.
- Карточка без описания → JSON `description: null`, markdown
  `_нет описания_`.
- Комментариев нет → JSON `comments: []`, раздела `## Комментарии` нет.
- Справочник кастомных полей не отвечает → markdown печатает сырые
  ключи `id_NNN`, команда не падает.

## Golden-примеры

Два комплекта: живой — снят целиком через CLI на тестовой карточке
Kaiten и обезличен; синтетический — собран вручную ради ветвей, которых
на живой карточке не устроить.

**Живой** (`fixtures/kiten-card/live-*`, снят 2026-08-14). Вход — ответы
внешней границы: `live-raw-card.json` (`GET /cards/{id}` целиком, как
пришёл: сервер несёт девять десятков полей) и `live-raw-comments.json`
(`GET /cards/{id}/comments` — на нём и виден неупорядоченный ответ).
Выводы: `live-json-stdout.json`, `live-md-stdout.md`,
`live-md-no-comments-stdout.md`. Отдельно — пустая карточка сразу после
создания: `live-empty-json-stdout.json` и `live-empty-md-stdout.md`;
на ней закреплены `properties: {}`, `key: null`, `_нет описания_` и то,
что строки шапки без значения не печатаются, а `URL` и `Этап` есть
всегда. Живая карточка покрывает: теги, дедлайн, размер, четыре
кастомных поля, три файла (два принесены комментарием), шесть
комментариев, markdown-чекбоксы в описании и в комментарии.

**Синтетический** (`fixtures/kiten-card/synthetic-*`). Вход —
`synthetic-card-detail.json` и `synthetic-comments.json`, выводы —
`synthetic-json-stdout.json`, `synthetic-md-stdout.md`,
`synthetic-md-no-comments-stdout.md` (сняты прогоном рендера рабочей
версии на этом входе). Он нужен ради четырёх ветвей, которых на живой
карточке нет: непустой `key`, непустые `members`, свойство `id_999999`,
которого нет в справочнике (печатается сырым ключом), и файл,
привязанный к комментарию. Справочник имён при съёме —
`{398965: «Ссылка на Merge Request», 291984: «6. Причина/гипотеза»}`.

Значение-массив (файловое поле) в выводах-голденах не встречается
намеренно: рабочая версия печатает его питоновским представлением
списка, а это отклонение с вердиктом **fix** — голден с таким значением
был бы ловушкой. Сама форма значения закреплена входом каталога
`fixtures/kiten-card/raw-card-file-property.json` (та же живая карточка
с заполненным файловым полем), требуемый вывод — текстом выше.

Ошибочные ветви: `err-not-found-stderr.txt` (403, exit 1 — снят целиком,
это `die`-сообщение без обрамления) и `err-selector-message.txt`
(exit 2 — только текст сообщения: обрамление, в которое его заворачивает
CLI-фреймворк рабочей версии, оформление, а не контракт). Проверяемое в
обоих: exit-код, пустой stdout, текст на stderr.

## Известные отклонения

- **fix** — прежняя реализация запрашивала справочник кастомных полей и
  на `--json`, хотя JSON-вывод имена полей не использует. Правильное
  поведение — запрос только для markdown/наглядного вида.
- **fix** — значение файлового кастомного поля приходит массивом uid, а
  прежняя реализация печатала его питоновским представлением списка:
  в markdown `- 9. AI-артефакт: ['99536012-…']`, в JSON — та же строка
  со скобками и апострофами вместо массива. Это форма чужого языка, а не
  контракт. Правильное поведение: в JSON массив остаётся массивом, в
  markdown печатаются его элементы через `, `.
- **fix** — прежняя реализация печатала комментарии в порядке ответа
  сервера, а он не упорядочен: замер 2026-08-14 дал шесть комментариев,
  где созданный последним стоял третьим. Правильное поведение —
  сортировка по `created`, при равных — по `id`.

Общие — в `platform/kaiten-http.md`.
