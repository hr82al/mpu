# mpu kiten — справочники: whoami / spaces / boards / lanes / columns / roles

Статус: черновик

## Назначение

Справочные подкоманды `mpu kiten`: кто я по токену и живые списки
пространств, досок, дорожек, колонок и ролей компании. Каждая делает
живой запрос к Kaiten и попутно обновляет локальный кэш справочников —
на нём работают резолв `REF`-опций и автодополнение во всех командах
`kiten-*`.

## CLI-контракт

- `mpu kiten whoami [--json]` — текущий пользователь по токену.
- `mpu kiten spaces [--all] [--json]` — пространства; архивные скрыты
  без `--all`.
- `mpu kiten boards [--space REF] [--json]` — доски всех пространств
  плоско; `--space` фильтрует.
- `mpu kiten lanes [--space REF] [--board REF] [--json]` — дорожки
  досок скоупа: `--board` → одна доска, `--space` → доски
  пространства, без фильтров — все доски.
- `mpu kiten columns [--space REF] [--board REF] [--json]` — колонки
  досок скоупа (скоуп как у `lanes`).
- `mpu kiten roles [--all] [--json]` — роли компании («типы работ»
  учёта времени); роли с неположительным ID (системная Employee)
  скрыты без `--all`.

`REF` — ID или подстрока названия; резолв — `platform/kaiten-http.md`
(«Резолв справочной ссылки») по кэшу, который команда обновила в
начале собственного запуска.

## Ввод/вывод

HTTP-граница:

- `whoami`: `GET /users/current`.
- `spaces` и `boards`: `GET /spaces` — доски вложены в каждое
  пространство массивом `boards[]` и собираются из него (отдельного
  глобального списка досок у API нет: такой запрос отвечает 405).
- `lanes` / `columns`: сначала `GET /spaces` (список досок скоупа),
  затем `GET /boards/{id}/lanes` / `GET /boards/{id}/columns` по
  каждой доске скоупа. Доска, ответившая ошибкой (нет доступа и
  т.п.), молча пропускается — обход продолжается (best-effort).
- `roles`: `GET /user-roles`.

Вывод `--json` (отступ 2, юникод как есть), порядок строк — порядок
ответа API (для `lanes`/`columns` — в порядке обхода досок):

- `whoami` — объект `{id, full_name, username, email}`;
- `spaces` — массив `{id, title, archived}`;
- `boards` — массив `{id, space_id, title}`;
- `lanes` / `columns` — массив `{id, board_id, title}`;
- `roles` — массив `{id, name}`.

Вывод без `--json` — человекочитаемый. `whoami` — четыре строки:

    id:    {id}
    name:  {full_name}
    login: {username}
    email: {email}

Остальные — таблица (оформление — свобода реализации) с колонками
`ID, TITLE, ARCHIVED` (spaces; ARCHIVED — `yes` или пусто),
`ID, SPACE, TITLE` (boards), `ID, BOARD, TITLE` (lanes/columns),
`ID, NAME` (roles) и итогом `({N} spaces)` / `({N} boards)` /
`({N} lanes)` / `({N} columns)` / `({N} roles)`. Пустой список →
`(нет пространств)` / `(нет досок)` / `(нет дорожек)` /
`(нет колонок)` / `(нет ролей)` без таблицы.

Фильтры `--all` / `--space` применяются после получения ответа и на
запись кэша не влияют (кэшируется полный ответ).

Exit: 0 — успех (в т.ч. пустая выдача); 2 — ошибки ввода (`REF`);
1 — ошибки API.

## Побочные эффекты

Чтение Kaiten (только GET). Запись локального кэша справочников в
кэш-БД (`platform/kaiten-http.md`, «Побочные эффекты»): `spaces` и
`boards` полностью заменяют таблицы пространств и досок; `roles` —
таблицу ролей; `lanes` / `columns` заменяют дорожки/колонки только
обойдённых досок. Сбой записи-обнаружения не роняет команду с
трейсбеком — превращается в ошибку API (см. ниже).

## Конфигурация

`KITEN_API_KEY`, `KITEN_BASE_URL` — `platform/kaiten-http.md`. Других
env-переменных нет.

## Инварианты

- Каждая подкоманда делает живой запрос: кэш обновляется ответом, но
  никогда не подменяет его (выдача — из ответа API, не из кэша).
- Kaiten не мутируется; единственная запись — локальная кэш-БД.
- `--json`-вывод не зависит от состояния кэша до запуска.
- Скрытые по умолчанию строки (`archived` без `--all`, роли с ID ≤ 0)
  отфильтровываются только из вывода — в кэш попадают.

## Граничные случаи и ошибки

- `KITEN_API_KEY` не задан → exit 2, формат —
  `platform/kaiten-http.md` («Конфигурация»).
- Ошибка API (сеть, не-2xx) → exit 1, stderr
  `mpu kiten <sub>: kaiten error: <текст ошибки>` — например
  `mpu kiten spaces: kaiten error: kaiten GET /spaces -> 500: <тело>`.
- `lanes`/`columns`: часть досок скоупа отдала ошибку → эти доски
  пропущены, остальные в выдаче, exit 0; все доски отдали ошибку →
  пустая выдача, exit 0.
- Пустой ответ `/spaces` → пустые таблицы кэша и `(нет пространств)` /
  `[]`, exit 0.
- Нерезолвящийся `--space`/`--board` → exit 2
  (`platform/kaiten-http.md`).

## Golden-примеры

Снять при переводе в «к реализации» (свой тестовый инстанс, без
клиентских данных): `whoami --json`, `spaces --json`, `boards --json`,
`lanes --board <id> --json`, `roles --json`, `roles --all --json`
(разница — системная роль). Случай «`KITEN_API_KEY` не задан» с живой
версии не снимается — там поведение отклонения (см. ниже); эталон
задаёт раздел «Граничные случаи».

## Известные отклонения

- **fix** — при отсутствии `KITEN_API_KEY` оригинал не даёт exit 2:
  `whoami` обрывается трейсбеком необработанного исключения (exit 1),
  остальные подкоманды печатают одну строку
  `mpu kiten <sub>: kaiten error: KITEN_API_KEY не задан` и завершаются
  exit 1. Правильное поведение — ошибка ввода exit 2 в формате
  `platform/kaiten-http.md` («Конфигурация»), как в разделе «Граничные
  случаи».
- **fix** — при ошибке API оригинал печатает удвоенный префикс:
  `mpu kiten spaces: kaiten error: kaiten: kaiten GET /spaces -> 500:
  …`. Правильное поведение — одинарный префикс, как в разделе
  «Граничные случаи».
- **fix** — `whoami --json` оригинал печатает компактным однострочным
  JSON, тогда как все остальные подкоманды `kiten` — с отступом 2.
  Правильное поведение — единый формат (отступ 2, юникод как есть).
