# mpu glab-status

Статус: к реализации (заморожена 2026-08-28; формы сняты живьём, голдены
обезличены)

## Назначение

Прохождение GitLab MR по веткам деплой-пайплайна одной таблицей:
строка — MR, шесть колонок-веток пайплайна `trunk / main / dev / qa /
predprod / prod`, галочка `✅` в колонке ⇔ ветка содержит
landing-коммит MR. Авторизация, HTTP-клиент, формы MR-селектора,
ответов и ошибок API — `platform/gitlab-api.md` (далее — атом).

## CLI-контракт

`mpu glab-status [MR]... [--since SINCE] [--repos REPOS] [--branches]
[--json]`

`[MR]...` — MR-селекторы: URL | `'group/repo!iid'` | iid (формы и
разбор — атом; голый iid берёт project из `git remote get-url origin`
текущего каталога; деривация iid из текущей ветки не используется).
Селектор с ведущим `-` отделяется `--`. `--json` (оба режима) —
вместо таблицы JSON-массив строк.

### Строка результата (одна на MR)

- `repo` — короткое имя репозитория (последний сегмент project);
- `iid`, `title`, `state`, `web_url`, `source_branch`,
  `target_branch` — из ответа API;
- `project` — путь `group/repo`; не определился → null;
- `landed` — ветки пайплайна, содержащие landing-коммит, всегда в
  порядке колонок;
- `other_branches` — остальные ветки с landing-коммитом, без
  source-ветки самого MR, отсортированы; null — refs не запрашивались
  либо данных нет (отличается от `[]` — «запросили, пусто»).

Landing-коммит — первый непустой из `merge_commit_sha`,
`squash_commit_sha`, `sha` ответа MR. Ветки, содержащие коммит, —
GET `/projects/{project_id}/repository/commits/{sha, URL-encoded}/refs?type=branch`
(пагинация — атом); ответ — массив объектов, имя ветки — поле `name`:
`[{"type": "branch", "name": "trunk"}, …]`. Запрос выполняется только
когда `state == merged` И landing-коммит есть И `project_id` известен,
иначе `landed` пуст и `other_branches` null без сетевого вызова. 404
этого запроса → то же состояние «нет данных» (см. «Известные
отклонения»).

### Режим «мои MR» (без аргументов)

- `--since` — окно по `updated_at`: `<число>{s|m|h|d}` (отсчёт от
  «сейчас») либо чистое число — unix-ts как есть; дефолт `7d`.
- HTTP: GET `/merge_requests?scope=created_by_me&updated_after=<окно
  ISO8601 UTC 'YYYY-MM-DDTHH:MM:SSZ'>&order_by=created_at&sort=asc`
  (пагинация — атом). Глобальный эндпоинт project не отдаёт: project
  восстанавливается из `web_url` — путь до маркера `/-/` без крайних
  `/`; маркера нет → project не определён.
- Фильтр: `state` ∈ {`opened`, `merged`} И project ∈ выбранным
  репозиториям (MR с неопределённым project отпадает).
- `--repos` — повторяемый флаг и/или значения через запятую; пустые
  сегменты отбрасываются; имя без `/` получает префикс `wb/`; с `/` —
  как есть. Дефолт: `wb/sw-front`, `wb/sl-front`, `wb/sw-back`,
  `wb/sl-back`, `wb/mp-config-local`.
- Порядок строк: (короткое имя репо, iid).
- Пустой результат: stderr
  `(нет моих MR за интервал в выбранных репозиториях)`, exit 0;
  с `--json` — `[]` в stdout.

### Режим селекторов MR (аргументы заданы)

- Ровно перечисленные MR, любых авторов и репозиториев; окно и фильтр
  репо не действуют. Порядок строк — порядок аргументов; повторы
  одного (project, iid) схлопываются до первого вхождения, в том числе
  заданные разными формами селектора.
- На каждый MR — GET `/projects/{project, URL-encoded}/merge_requests/{iid}`
  (атом).
- Вывод без `--json`: шапка на каждый MR, пустая строка, одна общая
  таблица на все MR, подвал «прочие ветки».
- Шапка: `{project}!{iid} · {state} · {source_branch} → {target_branch}`;
  пустой `state` → `?`; оба branch пусты → сегмент веток опущен целиком.
- Подвал: один MR — `прочие ветки: {ячейка}`; несколько —
  `прочие ветки:` и на каждый MR строка `  {project}!{iid}: {ячейка}`
  (отступ два пробела). Ячейка: null → `(MR не смержен)` при
  `state` ≠ `merged`, иначе `(нет данных)`; `[]` → `(нет)`; с
  `--branches` — имена через `, `; без — `{N} (показать: --branches)`.
- `--branches` — печатать «прочие ветки» полным списком; только этот
  режим. С `--json` допустим и на вывод не влияет (JSON всегда несёт
  полный `other_branches`).

### Таблица (оба режима, без `--json`)

Колонки: `repo`, `id`, `title` и шесть колонок веток; в ячейке ветки
`✅`, если она в `landed`, иначе пусто; рамки и выравнивание не
фиксируются. При нехватке ширины терминала усекается только `title`
(хвост `…`; счёт в терминальных ячейках: emoji/CJK — две), колонки
веток не скрываются; места нет вовсе → `title` пуст (не `…`).

## Ввод/вывод

stdout — данные; stderr — ошибки в формате
`mpu glab-status: <причина>[; попробуй: <подсказка>]`, без трейсбеков.
JSON: отступ 2, не-ASCII-символы как есть, завершающий перевод строки.
Exit: 0 — успех (включая пустой список «мои MR»); 1 — все ошибки
команды; 2 — ошибки разбора argv (неизвестный флаг).

Конфликты режимов валидируются до чтения `GLAB_TOKEN` и до сети:

- `--since` и/или `--repos` при селекторах MR → exit 1:
  `mpu glab-status: --since — только для режима «мои MR», с адресом MR
  не сочетается; попробуй: убрать --since либо вызвать mpu glab-status
  без адресов MR` (для `--repos` аналогично; заданы оба — в обеих
  позициях `--since/--repos`);
- `--branches` без селекторов MR → exit 1:
  `mpu glab-status: --branches применяется только с адресом MR;
  попробуй: указать адрес MR либо убрать флаг`.

## Побочные эффекты

Только чтение: три GET-эндпоинта выше; git-подпроцесс
`git remote get-url origin` — только при голом iid. Ни записи в
БД/файлы, ни кэша; stdin не читается.

## Конфигурация

`GLAB_TOKEN` (обязателен), `GITLAB_BASE_URL` (дефолт
`https://gitlab.btlz-api.ru`) — атом. Ширина терминала — из TTY / env
`COLUMNS`.

## Инварианты

- Ни одного пишущего HTTP-запроса ни в одном режиме.
- `landed` ⊆ шести веток пайплайна и всегда в порядке колонок,
  независимо от порядка ответа refs.
- `landed` пуст у несмерженного MR — корректные данные, не ошибка;
  `other_branches` null ⇔ данных о ветках нет.
- Source-ветка MR никогда не попадает в `other_branches`.
- `--json` несёт `landed` и `other_branches` полностью; таблица всегда
  показывает все шесть колонок веток.
- Повторный вызов с теми же входами при неизменном состоянии GitLab —
  побитово тот же вывод (включая порядок `other_branches`).
- `closed`/`locked` MR не появляются в «моих MR»; по явному селектору
  closed MR показывается (state как есть), refs не запрашиваются.
- Ошибка → stdout пуст: вывод печатается только после успешного
  построения всех строк.
- Токен не попадает ни в stdout, ни в stderr.

## Граничные случаи и ошибки

- Нет `GLAB_TOKEN` → exit 1, ошибка env-слоя с именем переменной и
  путём env-файла (атом).
- `--since` не парсится → exit 1 до сети:
  `mpu glab-status: --since: ожидается <число>{s|m|h|d} или unix-ts,
  получено '<значение>'`.
- `--repos` только из запятых/пробелов → пустой фильтр → пустой
  результат, не ошибка.
- Мусорный селектор → exit 1:
  `не удалось разобрать MR '<селектор>'; формы: URL | 'group/repo!iid' | iid`.
- URL чужого хоста → exit 1:
  `хост MR-URL '<хост>' != '<ожидаемый>' (GITLAB_BASE_URL)`.
- Голый iid, а cwd не git-репозиторий / git не найден / remote чужого
  хоста → exit 1: текст ошибки атома с префиксом `MR '<селектор>': `,
  подсказка в нём — `укажи MR как 'group/repo!iid' или полным URL`
  (флага `--mr` у команды нет, селектор позиционный).
- HTTP-ошибки → exit 1: `gitlab error: <сообщение атома>`; при 401
  добавляется `; проверь GLAB_TOKEN в <путь env-файла>`, при 404 от
  GET MR (только режим селекторов) — `; проверь адрес MR (URL |
  'group/repo!iid' | iid)`; прочие — без подсказки.
- MR без коммитов (обе ветки пусты) → шапка `group/repo!1 · merged`.
- Смерженный MR без `project_id` → refs не запрашиваются, в подвале
  `(нет данных)` — отличается от `(MR не смержен)`.
- Длинный `title` на узком терминале → усечён с `…`, полный текст в
  stdout не встречается.

## Golden-примеры

Сняты 2026-08-28 с рабочей версии на живом MR (только чтение), затем
обезличены: проект → `group/repo`, хост → `gitlab.example.test`, заголовок и
ветка заменены.

- `fixtures/glab-status/single-mr.json` — `glab-status '<MR>' --json`: массив
  объектов `{repo, iid, title, state, web_url, landed, project, source_branch,
  target_branch, other_branches}`; `landed` пуст у несмерженного MR,
  `other_branches` там `null`;
- `fixtures/glab-status/single-mr.stdout` — тот же вызов без `--json`: строка
  шапки `<проект>!<iid> · <состояние> · <ветка> → <цель>`, таблица с колонками
  `repo`, `id`, `title` и колонкой на каждую ветку деплой-пайплайна (`trunk`,
  `main`, `dev`, `qa`, `predprod`, `prod`), затем строка `прочие ветки:` с
  пояснением, если MR не смержен.

Ширина таблицы зависит от терминала, поэтому побайтно сверяется только
json-форма; у текстовой проверяются состав и порядок колонок, шапка и хвостовая
строка. Пустой результат (`glab-status` без аргументов, когда своих MR за окно
нет) печатает одну строку `(нет моих MR за интервал в выбранных репозиториях)`
— снято тем же прогоном.

## Известные отклонения

- **fix** — в оригинале 404 от запроса refs landing-коммита (коммит
  недоступен на хосте, например после переписывания истории)
  трактуется как пустой список веток: галочек нет, в подвале `(нет)` —
  неотличимо от «коммит реально ни в одной ветке». Правильное
  поведение (в контракте выше): 404 → «нет данных» (`landed` пуст,
  `other_branches` null, `(нет данных)` в подвале).
- **preserve** — принадлежность колонке определяется только именем
  ветки репозитория MR: ветка `qa`, заведённая в репозитории под
  другую задачу, неотличима от пайплайновой. Причина: колонки и есть
  имена веток; другого признака «ветка пайплайна» в GitLab нет,
  валидация по семантике невозможна.
