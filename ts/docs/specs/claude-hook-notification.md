# mpu claude-hook notification

Статус: реализовано

## Назначение

Доставить уведомление хука Claude Code в личного Telegram-бота. Claude Code
зовёт внешнюю команду на событии `Notification` (запрос разрешения, простой в
ожидании ввода и прочее); без адаптера оператор узнаёт об этом, только глядя в
терминал. Канал «себе» тот же, что у `mpu telegram log`: Bot API, чат с ботом не
виден командам `telegram ls` и `telegram search`.

Отдельной командой, а не флагом `telegram log`: у того контракт «MESSAGE
аргументом, `-` — весь stdin», а у хука stdin всегда JSON и всегда единственный
вход. Общий у них только слой отправки, и он переиспользуется целиком.

## CLI-контракт

```
mpu claude-hook notification
```

- Аргументов и опций нет. Весь stdin — JSON-объект payload'а хука.
- Тулом MCP-сервера команда **не публикуется**: закрытый список публикации
  (`fixtures/mcp-server/tool-policies.json`) её не содержит, и правило
  fail-closed делает из этого отсутствие тула (`platform/mcp-server.md`).
  Причин две: у вызова тула stdin нет по построению, а вне хука команда
  бессмысленна.
- Политика — `rw`: наружу уходит сообщение.

`mpu claude-hook` без подкоманды печатает справку и завершается кодом 2 (общее
правило групп, `platform/registry.md`).

## Ввод/вывод

stdin читается целиком и всегда. Разбор терпимый: незнакомые поля игнорируются,
отсутствующие и поля не того типа считаются незаданными. Обязательное требование
ровно одно — stdin разбирается как JSON-**объект**.

Живое событие `idle_prompt`, снято хуком 2026-08-27 (голден
`fixtures/claude-hook-notification/live-payload-idle-prompt.json`; перенос строк
и сокращение значений — для чтения, событие целиком лежит в голдене,
идентификаторы сессии и путь журнала в нём обезличены):

```json
{
  "session_id": "00000000-…-000000000001",
  "transcript_path": "/home/user/.claude/projects/…/00000000-….jsonl",
  "cwd": "/home/user/mr/mp/ozon",
  "prompt_id": "00000000-…-000000000002",
  "hook_event_name": "Notification",
  "message": "Claude is waiting for your input",
  "notification_type": "idle_prompt"
}
```

Наблюдение шире одного события: живьём снято десять событий трёх типов —
`idle_prompt`, `permission_prompt`, `auth_success` (2026-08-27). Набор полей у
всех трёх одинаковый и равен показанному выше. Дока Claude Code
(`code.claude.com/docs/en/hooks`, читана в тот же день) описывает событие иначе,
и расхождения зафиксированы наблюдением, а не пересказом:

- текст уведомления живой хук кладёт в `message`; дока называет это поле
  `notification_message`. Команда читает **оба**: сперва `message`, затем
  `notification_message`. Порядок не произволен — первое подтверждено пробой на
  всех трёх типах, второе известно только по доке;
- `permission_mode` и `notification_data` дока называет, а живой хук не прислал
  их ни разу — ни на одном из десяти событий. Команда их и не читает, так что
  проверить их форму неоткуда;
- `session_id`, `prompt_id`, `transcript_path`, `cwd`, `hook_event_name` и
  `notification_type` совпали с докой.

Тексты `message` у снятых типов: `idle_prompt` — «Claude is waiting for your
input», `permission_prompt` — «Claude needs your permission», `auth_success` —
«Claude Code login successful». Команда их не разбирает и ни на что по ним не
решает: это чужой текст, который она доставляет как есть.

Расхождение кода не переписывает: разбор терпимый ровно за этим. Незнакомое
поле игнорируется, отсутствующее не ломает отправку, поле не того типа
считается незаданным — единственное жёсткое требование по-прежнему одно, и оно
про JSON-объект.

`notification_type` — строка, а не закрытый union: список типов меняется вместе
с Claude Code, и незнакомый тип обязан доезжать, а не отбиваться — уведомление
важнее строгости. Типы команда не фильтрует: отбор делает `matcher` в настройке
хука, второе место отбора означало бы два источника правды.

Текст сообщения — две строки, вторая только при непустом тексте события:

```
Claude · <проект> · <notification_type>
<message, иначе notification_message>
```

- `<проект>` — базовое имя каталога `cwd`; завершающие слэши снимаются. `cwd`
  нет либо он пуст — часть опускается вместе с разделителем, а не печатается
  пустой.
- `notification_type` нет — `notification`.
- Текст берётся из `message`; поля нет, оно пусто либо не строка — из
  `notification_message`.
- `cwd` и `notification_type` пусты, текста события нет — уходит одна строка
  `Claude · notification`: это успешная отправка, а не отказ, сам факт события
  уже сигнал.
- `session_id`, `prompt_id`, `permission_mode`, `transcript_path` и
  `notification_data` в текст не идут: первые два бесполезны на телефоне,
  третий и четвёртый — про машину, у пятого форма произвольна.

Предел текста `sendMessage` — 4096. Длиннее → текст **усекается** до предела
(многоточие входит в предел, а не добавляется сверх), а не отбивается ошибкой.
Осознанное отличие от подписи в `telegram log`: там отказ видит оператор на
экране, здесь отказ не видит никто (см. «Побочные эффекты»), а усечённое
уведомление доходит. Единица счёта та же — кодовые единицы UTF-16
(`string.length`); суррогатная пара на месте среза выбрасывается целиком,
поэтому усечённый текст бывает на единицу короче предела, но половины
пары в нём не остаётся.

stdout — одна строка JSON, за ней один перевод строки; пробел после двоеточия
входит в форму:

```
{"id": 5000001}
```

Источник значения: `id` — `result.message_id` ответа Bot API. `chat_id` в вывод
не идёт: секция `out` пишется в журнал, и адресат оказался бы в ней.

## Побочные эффекты

Ровно один POST `sendMessage` на `https://api.telegram.org` с телом JSON.
Апдейты не читаются, состояние не пишется, файлы не создаются и не читаются.

Наблюдаемого эффекта в самом Claude Code у вызова нет: у события `Notification`
он игнорирует stdout, stderr, JSON-вывод и код выхода (0, 2 и любой другой
равнозначны), заблокировать или изменить поведение хук не может. Повтора у
команды нет: одно событие — один POST, ретраев она не делает. Таймаут команды
хука — 600 s по умолчанию, и вызов Bot API в него укладывается своими пределами
(см. «Конфигурацию»).

## Конфигурация

Целиком та же, что у `mpu telegram log`, и той же реализацией: ключи env-файла
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_ID` (обязательны), `TELEGRAM_BOT_NAME`
(необязателен, идёт в подсказку при отказе доставки); прокси — `TELEGRAM_PROXY`,
иначе `HTTPS_PROXY`, иначе `https_proxy`, схемы `http`/`https`/`socks5`/
`socks5h`; пределы времени вызова 15 s на заголовки и 30 s на весь вызов. Своей
копии этих правил у команды нет — расхождению взяться неоткуда.

Ключи сеанса MTProto команде не нужны: неавторизованный `mpu init` её не
блокирует.

Вторая половина настройки — сам вызов: команду зовёт Claude Code, и включается
она сниппетом в `~/.claude/settings.json`. Тип событий отбирает `matcher`, а не
команда:

```json
{
  "hooks": {
    "Notification": [
      {
        "matcher": "permission_prompt|idle_prompt|agent_needs_input",
        "hooks": [
          { "type": "command", "command": "mpu claude-hook notification" }
        ]
      }
    ]
  }
}
```

Известные значения `matcher` — по доке Claude Code
(`code.claude.com/docs/en/hooks`), снято 2026-08-27: `permission_prompt`,
`idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`,
`elicitation_complete`, `elicitation_response`, `agent_needs_input`,
`agent_completed`, `quota_auto_resume_fired`, `quota_auto_resume_stale`,
`quota_auto_resume_disabled`. Список меняется вместе с Claude Code и с этой
датой устаревает — сверяться с ним стоит по источнику, а не по спеке. Команде
он не известен и знать его она не обязана: типы она не фильтрует.

## Инварианты

- Адресат сообщения равен `TELEGRAM_BOT_ID` при любом payload'е: другого
  источника адресата у команды нет.
- Фильтра типов уведомлений у команды нет: любой `notification_type`, включая
  незнакомый и отсутствующий, приводит к отправке.
- Апдейты Bot API (`getUpdates`, webhook) не запрашиваются ни при каком исходе.
- Содержимое stdin не попадает в текст ошибки ни куском, ни первой строкой —
  иначе оно вернулось бы на диск секцией `err` записи журнала
  (`platform/invoke-log.md`). Тот же довод, что у `telegram log`.
- Значение `TELEGRAM_BOT_TOKEN` не появляется ни в stdout, ни в stderr, ни в
  журнале.
- Тула у команды нет ни в одном профиле MCP-сервера.
- Сеанс MTProto не открывается.

## Граничные случаи и ошибки

- stdin пуст, не разбирается как JSON либо разбирается не в объект (массив,
  число, строка, `null`) → `mpu claude-hook notification: stdin хука
  разбирается как JSON-объект`, exit 2, до сети и до чтения конфигурации.
- `TELEGRAM_BOT_TOKEN` или `TELEGRAM_BOT_ID` отсутствует либо пуст → сообщение
  слоя env-файла с именем ключа и путём файла, exit 1.
- `TELEGRAM_BOT_ID` — не число → `telegram: TELEGRAM_BOT_ID должен быть числом,
  получено '<строка>'`, exit 1.
- Прокси непонятной схемы, прокси-URL без `host:port` либо неразбираемый URL →
  тексты `telegram log`, exit 1, до сети.
- Ответ с `ok: false` → `telegram: bot API <error_code> <description>`, exit 1;
  при `chat not found` и `bot was blocked` — плюс `; напиши боту @<name>
  /start`.
- Тело ответа не JSON → `telegram: bot API вернул не JSON: <первая строка
  тела>`, exit 1. Ответ без `result.message_id` → `telegram: bot API не сообщил
  номер сообщения`, exit 1.
- Сбой вызова (сеть, предел времени) → `telegram: bot API недоступен: <причина
  одной строкой>`, exit 1.

Коды выхода обычные, mpu-шные: «проглотить любую ошибку и выйти 0» команда не
делает. Но на экран они не попадают — вызывает её хук, а он вывод и код выхода
игнорирует (см. «Побочные эффекты»). Единственная поверхность, где отказ виден,
— журнал вызовов: `mpu log --failed --since 1h`. Лечить «невидимый exit code» не
нужно, его никто не читает.

## Golden-примеры

- `fixtures/claude-hook-notification/notify-stdout.txt` — успешная отправка.
- `fixtures/claude-hook-notification/err-bad-json-stderr.txt` — stdin не
  разбирается как JSON-объект.
- `fixtures/claude-hook-notification/live-payload-idle-prompt.json` — живое
  событие `idle_prompt` целиком, одной строкой, как его отдаёт хук;
  идентификаторы сессии и путь журнала обезличены, форма и порядок ключей —
  как в снятом событии. Не поверхность команды, а её вход: голден нужен, чтобы
  разбор сверялся с бинарём Claude Code, а не с докой. Второго типа рядом нет
  намеренно: набор полей у трёх снятых типов совпал дословно, и второй файл
  стерёг бы то же самое.

Все поверхности оканчиваются одним переводом строки.

## Открытые вопросы

Живой пробой (2026-08-27) проверены три типа: `idle_prompt`,
`permission_prompt`, `auth_success` — набор полей у них один и тот же, текст
везде в `message`, отправка на живом `permission_prompt` дошла. Остальные девять
типов из списка `matcher` известны только по доке; разойдись и они — это
обнаружится тем же способом, образцом события, а не чтением доки.
