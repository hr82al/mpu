# mpu kiten comment

Статус: к реализации (2026-08-14: CLI-поверхность, вывод, коды выхода и
состав внешних вызовов сверены с рабочей версией; голдены всех ветвей
сняты живым прогоном на тестовой карточке. Живой прогон опроверг одно
обещание спеки — комментарий из одних вложений внешняя система не
принимает, см. «Известные отклонения». Внешняя граница вынесена в
каталог `platform/kaiten-api-cards.md` правкой 2026-08-06)

## Назначение

Комментарий к карточке Kaiten от имени владельца токена: текст
(markdown), файлы-вложения, адресаты первой строкой; `@all`
разворачивается во владельца карточки. Обвязка —
`platform/kaiten-http.md`.

## CLI-контракт

`mpu kiten comment SELECTOR [-m/--message TEXT | -F/--body-file PATH]
[-f/--file PATH]... [--to HANDLES]...`

- Текст — из ровно одного источника: `-m TEXT` либо `-F PATH` (`-` —
  stdin). Оба сразу → exit 2: `нельзя одновременно -m/--message и
  -F/--body-file`. Ни одного и нет вложений/адресатов → exit 2:
  `нужно ровно одно из -m/--message и -F/--body-file`. Обязательный
  текст из одних пробелов → exit 2: `пустой текст комментария`.
- **Итоговый текст комментария не бывает пустым.** Адресаты дают текст
  сами (строка адресатов становится первой строкой), поэтому `--to` без
  `-m`/`-F` проходит. А вот вложения текста не дают: комментарий «только
  из файлов» внешняя система не принимает — `POST` с пустым `text`
  отвечает 400 (`platform/kaiten-api-cards.md`, вызов 5). Поэтому
  `-f` без текста и без адресатов → **exit 2 до сети**:
  `нужен текст комментария: вложения без текста Kaiten не принимает`.
  С `-f` вместе с `-m`/`-F` либо с `--to` — проходит.
- `-f PATH` (повторяемый) — вложение: прикрепляется сам файл, не его
  содержимое. Путь обязан быть существующим обычным файлом, иначе
  exit 2: `файл-вложение не найден: {путь}`; ошибка чтения → exit 2:
  `не удалось прочитать вложение {путь}: <причина>`. Имя вложения в
  Kaiten — базовое имя файла, без каталога.
- `--to HANDLES` (повторяемый; значение делится по пробелам на
  токены) — адресаты. Токен без ведущего `@` получает его; дубликаты
  убираются без учёта регистра, порядок и регистр первого вхождения
  сохраняются. Строка адресатов (через пробел) ставится самой первой
  строкой комментария, затем пустая строка, затем текст; текст пуст →
  комментарий состоит из одной строки адресатов.
- `@all` (в `--to` или самостоятельным токеном в тексте:
  регистронезависимо, не часть слова или email) → `@{username
  владельца карточки}`. Владельца/username нет → предупреждение в
  stderr, литеральный `@all` остаётся (и в тексте, и среди адресатов),
  команда продолжается.

Живые сценарии: `mpu kiten comment 12345678 -m 'Готово, проверьте'`;
`mpu kiten comment 12345678 --to '@all' -F -`;
`mpu kiten comment 12345678 -f отчёт.xlsx -m 'файл во вложении'`.

## Ввод/вывод

Внешняя граница — `platform/kaiten-api-cards.md`:

- чтение карточки — только когда нужен владелец: заданы адресаты либо в
  тексте есть токен `@all`; иначе карточка не читается;
- без вложений — создание комментария в JSON-форме;
- с вложениями — одно создание комментария в multipart-форме: Kaiten
  создаёт один комментарий и привязывает файлы к нему.

stdout успеха:

    ok: комментарий {id} → {url карточки}
       вложения: {имя1, имя2}          ← если были вложения
       адресаты: {@a @b}               ← если кто-то реально упомянут

`адресаты` — реально упомянутые логины (литеральный `@all` не входит),
без дублей.

Источники значений: `{id}` — из ответа создания комментария;
`{url карточки}` — строится как `{базовый URL}/{id карточки}`, не из
ответа; `{имя1, имя2}` — базовые имена приложенных файлов в порядке
флагов `-f`, через `, `; `{@a @b}` — раскрытые адресаты через пробел, в
порядке первого вхождения. Дополнительные строки печатаются с отступом
в три пробела и только когда есть что показать.

Вывод оканчивается одним `\n`; пустых строк в нём нет.

Exit: 0 — успех (в том числе с предупреждением про владельца); 2 —
ошибки ввода (источники текста, вложение, селектор, ненастроенный
`KITEN_API_KEY`); 1 — ошибки API. Префикс всех сообщений — полный путь
команды: `mpu kiten comment: …`; у ошибок внешней системы после него
идёт `kaiten error: <текст>`.

## Побочные эффекты

Один POST в Kaiten (комментарий, при вложениях — вместе с файлами);
GET карточки — только при необходимости владельца. Локальных записей
нет.

## Конфигурация

`KITEN_API_KEY`, `KITEN_BASE_URL` — `platform/kaiten-http.md`. Других
нет.

## Инварианты

- Текст и вложения уходят одним запросом — один комментарий, частичной
  публикации не бывает.
- `@all` — клиентская текстовая подстановка; сервер получает обычный
  текст, токена `@all` как механизма в запросе нет.
- Без адресатов и без `@all` в тексте карточка не читается — ровно
  один HTTP-запрос.
- Валидация текста и вложений — до первого сетевого запроса.
- Отсутствие владельца не превращается в ошибку.

## Граничные случаи и ошибки

- `-f <каталог>` → exit 2: `файл-вложение не найден: {путь}`.
- `-F <нечитаемый путь>` → exit 2:
  `не удалось прочитать {путь}: <причина>`.
- Только `--to`, без `-m`/`-F` → комментарий из одной строки адресатов,
  exit 0 (голден `ok-recipients-only-stdout.txt`).
- Только `-f`, без `-m`/`-F` и без `--to` → exit 2 до сети (см.
  CLI-контракт). Прежняя реализация запрос всё-таки отправляла и
  получала 400 — голден
  `err-attachment-without-text-stderr.txt` сохранён как свидетельство
  отклонения, воспроизводить его не нужно.
- `-f` вместе с `--to`, без `-m`/`-F` → проходит: текстом становится
  строка адресатов (голден `ok-attachment-recipients-stdout.txt`).
- Несколько вложений → в выводе `вложения: {имя1, имя2}` через запятую,
  в порядке флагов (голден `ok-attachment-two-stdout.txt`).
- `--to '@all'`, владельца нет → stderr `mpu kiten comment: у карточки
  нет владельца с username — оставляю '@all' как есть`; `@all`
  остаётся первой строкой; строки `адресаты:` в выводе нет; exit 0.
- `--to 'ivan @Ivan'` → один адресат `@ivan` (дедуп без учёта
  регистра, первое вхождение побеждает).
- Невалидный селектор → exit 2 (`platform/kaiten-http.md`,
  «Селектор карточки»).
- Ошибка API → exit 1, локальных следов нет.

## Golden-примеры

Сняты живым прогоном на тестовой карточке Kaiten 2026-08-14 и
обезличены; лежат в `fixtures/kiten-comment/`.

Успех — по одному файлу на ветвь: `ok-message-stdout.txt` (`-m`),
`ok-stdin-stdout.txt` (`-F -`), `ok-recipients-stdout.txt` (`--to '@all
@teststub'` вместе с `@all` в тексте — видно и раскрытие в строке
адресатов, и раскрытие внутри текста), `ok-recipients-only-stdout.txt`
(`--to` без текста), `ok-recipients-dedup-stdout.txt` (`--to '@Teststub
@teststub'` → один адресат, регистр первого вхождения),
`ok-attachment-stdout.txt` (одно вложение с текстом),
`ok-attachment-two-stdout.txt` (два вложения — виден разделитель),
`ok-attachment-recipients-stdout.txt` (вложение и адресаты без своего
текста).

Ошибки: `err-no-text-message.txt`, `err-both-sources-message.txt`,
`err-file-not-found-message.txt` — тексты сообщений ветвей exit 2 (сети
не касаются; обрамление рабочей версии — оформление её CLI-фреймворка, не
контракт, проверяются exit-код, пустой stdout и текст на stderr).
`err-attachment-without-text-stderr.txt` — ответ внешней системы на
комментарий из одних вложений (exit 1, 400); он снят как свидетельство
отклонения и в новой реализации недостижим: см. «Известные отклонения».

## Известные отклонения

- **fix** — прежняя реализация обещала комментарий «только из вложений»
  (текст необязателен, если есть файлы) и отправляла запрос с пустым
  `text`. Kaiten такой запрос не принимает: 400,
  `{"message":"Comment-public-api.text should be string"}` — пустой
  текстовый part для него равен отсутствующему полю (замер 2026-08-14,
  голден `err-attachment-without-text-stderr.txt`). Правильное
  поведение — не отправлять заведомо отвергаемый запрос: `-f` без текста
  и без адресатов отбивается на входе, exit 2, до сети.
