# `mpu-back`: строка простым HTTP

Статус: реализовано — порция 143 (`48ff986`, `3b2315b`, `9d751f7`); принято 2026-09-18: гейты зелёные (тестов 2135, smoke 21/1), живой прогон хостом `curl` — поток, собранный JSON, вопрос с номером → `y` → записано, повтор номера 404, чужой `Accept` 406, токена в выводе нет. Эталоны — `fixtures/back-http-line/`, схема кадров обновлена в `fixtures/back-rpc/schema.json`.

## Назначение

Строку `mpu-back` можно исполнить без WebSocket: одним `POST` из `curl`,
встроенного `http` оболочки nu или клиента на C. Длинный вывод при этом идёт
потоком — те же кадры, что у WebSocket (`platform/back-rpc.md`), по одному
JSON-объекту на строку ответа (NDJSON), по мере появления. Кому поток не нужен,
просит один JSON в конце.

Подтверждение — вторым запросом: вместо вопроса посреди соединения сервер
завершает ответ кадром с вопросом и одноразовым номером, клиент присылает
ответ новым запросом, и строка продолжается уже в его ответе.

WebSocket-вход, `mpu-next` и всё прочее не меняются.

## Ввод/вывод

### `POST /line` и `POST /agent/line`

Двери, токены, `Origin`, `human` — те же, что у WebSocket с тем же путём
(`platform/back-rpc.md`, «Доступ»; `cli-client.md`, «Канал и токен»). Токен —
только заголовком `Authorization: Bearer`.

Тело запроса — первый кадр строки: `{"words": [...], "cwd": "...", "human": …}`.

Форма ответа — по заголовку `Accept`:

| `Accept` | Ответ |
|---|---|
| `application/x-ndjson` | 200, `Content-Type: application/x-ndjson`; тело — кадры сервера по одному на строку, каждая строка оканчивается `\n`, отдаются по мере появления |
| `application/json` | 200, `Content-Type: application/json`; тело — один объект, собранный из тех же кадров (ниже) |

Заголовок разбирается по правилам HTTP: из двух поддерживаемых форм берётся та,
у которой вес `q` выше; при равенстве — NDJSON. Заголовка нет, `*/*` или
`application/*` — NDJSON. Ни одна из двух форм не допустима — 406.

Кадры потока — те же `{"out": …}`, `{"err": …}`, `{"exit": N}`. Вместо
`{"ask": …}` WebSocket'а поток получает:

```json
{"ask": "выполнить mpu kiten comment 1 x? [y/N] ", "ticket": "<номер>"}
```

и **на этом кадре ответ заканчивается** (кадра `exit` в нём нет). Номер —
случайная строка из 32 шестнадцатеричных знаков, действует 120 секунд и один
раз.

Собранный ответ (`application/json`):

```json
{"stdout": "<все out подряд>", "stderr": "<все err подряд>", "exit": 0}
```

или, если строка упёрлась в вопрос:

```json
{"stdout": "…", "stderr": "…", "ask": "…", "ticket": "<номер>"}
```

### `POST /line/answer` и `POST /agent/line/answer`

Тело: `{"ticket": "<номер>", "answer": "y"}`. Путь и токен обязаны быть те же,
что у запроса, выдавшего номер. Ответ — продолжение той же строки в той же
форме (`Accept` нового запроса): кадры после вопроса, до `exit` или до
следующего вопроса с новым номером.

## Правила

| Дано | Ожидается |
|---|---|
| тело не JSON или нет `words`/`cwd` | 200, поток `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}` (так же, как у WebSocket) |
| номер неизвестен, истёк или уже использован | 404, тело `{"error": "номер подтверждения недействителен"}` |
| номер выдан на другой двери или другим токеном | 404, тот же текст |
| на номер не ответили за 120 секунд | строка кончается ответом «нет», как у WebSocket; вывод отбрасывается; номер недействителен |
| клиент оборвал поток до `exit` | исполнение доходит до конца (строки не прерываются), вывод отбрасывается |
| в той же строке второй вопрос (после ответа на первый) | ответ `…/answer` кончается новым кадром `ask` с новым номером |
| сервер останавливается, пока строка ждёт ответа по номеру | строка не исполняется (ответ «нет»), номер недействителен; открытого ответа у неё нет — клиент узнаёт по 404 на `…/answer` |
| сервер останавливается во время потока | как у WebSocket: в поток `{"err": "mpu-back: остановлен\n"}`, `{"exit": 1}` |
| `Accept` другой | 406, тела нет |

Очередь исполнения, окружение строки, пустой stdin и не-терминальные потоки —
как у WebSocket (`platform/back-rpc.md`). Вопрос и ожидание ответа — до
очереди.

## Инварианты

- Кадры потока для одной строки — те же, что у WebSocket, в том же порядке;
  отличие одно — `ask` несёт `ticket` и завершает ответ.
- Собранный ответ равен склейке кадров потока.
- Итог строки (stdout, stderr, код) равен итогу через WebSocket на тех же
  словах, правилах и ответе.
- Номер подтверждения не принимается на другой двери и с другим токеном.
- `GET` (WebSocket) и `POST` (эта спека) на одном пути `/line` и `/agent/line`
  сосуществуют: ни один не перехватывает другой; прочие методы — 405 с
  `Allow: GET, POST`.
- Остановка сервера не оставляет ни ожидающих номеров, ни открытых потоков без
  `exit`.
- Токен не появляется ни в одном ответе.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| `curl -N -H "Authorization: Bearer <токен>" -d '{"words":["version"],"cwd":"/"}' …/line` | две строки: `{"out":"0.1.0\n"}`, `{"exit":0}` |
| то же с `Accept: application/json` | `{"stdout":"0.1.0\n","stderr":"","exit":0}` |
| `["allow:","kiten ls"]` на `/line`, `human: true` | ответ кончается `{"ask": "изменить правило: kiten ls → allow? [y/N] ", "ticket": …}`; `POST /line/answer` с `y` → данные и `{"exit":0}`; правило записано |
| то же, ответ `n` | `{"err": "mpu allow: kiten ls: не подтверждено\n"}`, `{"exit":1}` |
| тот же номер второй раз | 404 |
| номер с `/line` отправлен в `/agent/line/answer` | 404 |
| строка с выводом ≥ 1 МБ | кадры `out` приходят по мере появления, склейка равна выводу |
