# Ввод клиента — по запросу строки

Статус: к реализации — порция 165c.

## Назначение

Клиент `mpu` сейчас читает не-терминальный stdin до конца **до** первого кадра
(`call-context.md`, «Сторона клиента»). Если stdin — открытый канал или сокет,
который никто не закрывает (фоновая задача, унаследованный дескриптор), любая
строка молча висит — даже `mpu version`: живьём поймано установкой 165b
(`install.sh`, «проверка cli: mpu version не отвечает»). Строка, которой ввод не
нужен, читать его не должна; строка, которой нужен, получает его как прежде.

## Контракт

Клиент с не-терминальным stdin ввод **не читает**, а объявляет, что он есть:

```json
{"words": ["kiten", "comment", "id:", "5", "text:", "stdin"], "cwd": "/home/user/mr/mp",
 "human": true, "stdinOnRequest": true, "tty": {"stdin": false, "stdout": true, "stderr": true}}
```

Когда строке впервые нужен ввод (значение `stdin` — `value-expression.md`;
чтение `-` прежних подстановок), сервер шлёт кадр и ждёт ответа:

| Кадр | Направление | Что |
|---|---|---|
| `{"stdinRequest": true}` | сервер → клиент | ввод нужен; не чаще одного раза за строку |
| `{"stdin": "<весь ввод>"}` | клиент → сервер | клиент читает stdin до конца и шлёт одним кадром |

Второе и следующее чтения в той же строке берут то же содержимое без нового
кадра (ввод — значение, `call-context.md`).

## Правила

- `stdinOnRequest` — булево; вместе со строковым `stdin` в первом кадре —
  `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}`.
- Поле есть только на WebSocket (`/line`, `/agent/line`); `POST /line` (curl,
  фронт) и MCP передают ввод прежним полем `stdin` или не передают вовсе.
- Предел 8 МиБ — у клиента при чтении по запросу: больше — клиент печатает
  в stderr прежний отказ о пределе ввода (тот же текст, что до порции),
  закрывает сокет, код 2; сервер видит
  обрыв как отмену строки. У сервера — прежний отказ на кадр `stdin` сверх
  предела.
- `POST /line` и `/agent/line` поле `stdinOnRequest` не читают: игнорируется
  любым значением, как незнакомое поле, ввода нет.
- Кадр `stdin` сверх 8 МиБ после запроса: `{"err": "mpu-back: ввод больше 8
  МиБ\n"}`, команду останавливают (как при обрыве), её дальнейший вывод
  клиенту не идёт, итог — `{"exit": 2}`.
- Кадр `stdin` без запроса или второй — игнорируется (как лишний `answer`,
  `back-rpc.md`).
- Строка, подтверждённая вопросом двери, запрашивает ввод при исполнении — после
  ответа, тем же сокетом.
- Клиент после `{"exit": …}` stdin не читает.
- Терминальный stdin — как прежде: поля нет, ввода нет, кадра запроса нет.

## Инварианты

- Итог строки, читающей ввод, побайтово равен итогу до порции (голдены
  `call-context/` не меняются, кроме первого кадра клиента).
- Строка, не читающая ввод, завершается, не касаясь stdin клиента.

## Граничные случаи

| Дано | Ожидается |
|---|---|
| `sleep 999 \| mpu version` | версия печатается сразу, код 0 (stdin не читался) |
| `mpu version` со stdin — открытым сокетом, в который никто не пишет | то же |
| `printf 'ok' \| mpu kiten comment id: 5 text: stdin` (локальный стек) | кадр `stdinRequest`, текст `ok` доходит до команды |
| `mpu confirm …` с `-` дважды из пайпа | один `stdinRequest`, оба чтения — тот же текст |
| `mpu kiten ls` из пайпа | кадра `stdinRequest` нет |
| первый кадр `{"stdinOnRequest": true, "stdin": "x", …}` | `mpu-back: плохой кадр строки`, код 2 |
| первый кадр `{"stdinOnRequest": "yes", …}` | то же |
| ввод 8 МиБ + 1 байт из пайпа, строка читает `stdin` | прежний отказ клиента о пределе ввода, код 2 |
| ввод 8 МиБ + 1 байт, строка ввод не читает | строка исполняется, код 0 |
| кадр `{"stdin": "x"}` без запроса | игнорируется |
