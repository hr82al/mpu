# Тесты на Vitest — порция V1 (этап 1 перехода)

Статус: к реализации (2026-10-07). План —
`docs/plans/2026-10-06-bun-tslibs-objects-plan.md`, этап 1. Правило —
`CLAUDE.md` mpu, «Код без привязки к рантайму».

## Кто и зачем

Разработчик mpu хочет, чтобы тесты шли на широко используемом раннере,
одинаковом под Bun, Deno и Node, и при переходе не потерялся ни один случай.
V1 — основа (зависимости, раннер, гейт) и перевод одного каталога
`back/src/objects` целиком; остальные каталоги — следующими порциями тем же
способом.

## Основания (пробы хоста 2026-10-07, `mp/tmp/vitest-deno-probe`, `mp/tmp/deno-sanitizer-golden`)

- Vitest 3.2.4 исполняется под Node 24.21, Bun 1.4.2 (`bun --bun`) и Deno
  2.9.7 (`deno run -A npm:vitest@3.2.4`); под Deno код с `Deno.*` и
  `vi.useFakeTimers` работают.
- Vite не читает карту `imports` из `deno.jsonc`: модуль с `@zod/zod`
  не грузится («Failed to load url @zod/zod»); с npm `zod@4.4.3` грузится.
- Санитайзеры `Deno.test` в Deno 2.9.7 по умолчанию проверяют только выход
  из процесса; таймеры, файлы, сокеты, подпроцессы — лишь при явном
  `sanitizeOps`/`sanitizeResources`, а их в репозитории нет. Выход Vitest
  ловит сам под всеми тремя: `process.exit unexpectedly called with "3"`,
  остальные тесты файла идут дальше. Своей библиотеки санитайзеров нет
  (решение владельца 2026-10-07).
- Покрытие — `@vitest/coverage-istanbul` (решение владельца 2026-10-07):
  одинаковые цифры под тремя рантаймами; `coverage-v8` расходится (ветви:
  Bun 60 %, Node и Deno 50 % на одном файле).
- Модель прав Deno не воспроизводится ни в коде, ни в тестах (решение
  владельца 2026-10-07): опция `permissions` у `Deno.test` уходит без замены.

## Сценарии [S.n]

Число случаев «до» снимается с текущего `main` один раз, до правок
(`deno test --reporter=junit back/src/objects`), и становится литералом в
отчёте; ниже `N` — это число.

1. `deno task test` на ветке после V1 → зелёно; в выводе нет ни одного файла
   из `back/src/objects`; число файлов = число на `main` минус 8.
2. `deno task vitest` → зелёно; вывод оканчивается строками
   ` Test Files  8 passed (8)` и ` Tests  N passed (N)` и временем прогона.
3. Список листовых случаев `back/src/objects` до (junit `deno test`: путь
   «тест > шаг > шаг») и после (junit Vitest: «describe > it») совпадает
   строка в строку, кроме одного переименования из [S.10].
4. В `back/src/objects` после V1: `rg -c 'Deno\.test|@std/assert|@std/testing'`
   → пусто; файлы названы `*.test.ts`, `*_test.ts` там нет.
5. Случай эталона: `случаи эталона объектов > <имя случая>` — 43 строки,
   по одной на случай `testdata/objects/cases.json`; плюс
   `в эталоне объектов 43 случая`.
6. Переведённый тест, утверждение которого нарушено (проба: ожидаемое `43`
   заменено на `44`) → `deno task vitest` красный, строка
   ` FAIL  back/src/objects/cases.test.ts > в эталоне объектов 43 случая`,
   код выхода 1; вернули `43` → зелёно.
7. Утверждение старого вида и его перевод краснеют на одних и тех же
   данных: для каждого вида утверждения, встреченного в каталоге, — пара
   «зелёный / красный» вход, прогнанная до (`@std/assert`) и после
   (Vitest), записана в `.tmp/design-V1.md`.
8. Тест, вызвавший `process.exit(3)` (проба, не коммитится) → красный с
   `process.exit unexpectedly called with "3"`, соседние тесты файла
   исполнились.
9. `deno task vitest --coverage` → таблица istanbul по затронутым модулям
   `back/src/objects`; каталог отчёта не попадает в git.
10. Тесты с `permissions` прав больше не ограничивают; имя, обещавшее
    проверку прав, меняется на то, что проверяется:
    `исполнение не трогает окружение, файлы и сеть и повторяется` →
    `исполнение повторяется` (`chain`); `случаи эталона объектов` — имя то
    же, ограничение `read: [helpDir]` снято. (`шаг не трогает окружение,
    файлы и сеть и повторяется` в `back/src/messages/read_test.ts` — не в
    этой порции, переименуется своей.)
11. `deno check .` → зелёно, включая `*.test.ts`.
12. Импорты `@zod/zod` во всём `ts/` (кроме `web/`) → `zod`; `@hono/hono` →
    `hono`; `@std/text/levenshtein-distance` → `fastest-levenshtein`
    (решение владельца 2026-10-07). `deno task test`
    и `deno task vitest` зелёные после замены.
13. Чистый клон: одна команда установки из `ts/CLAUDE.md` → `deno task test`
    и `deno task vitest` зелёные без ручных шагов.
14. `deno task smoke` → зелёно (бинарь собран на тех же зависимостях).
15. `web/` — его тесты идут своим прежним путём (`deno task web:test`),
    корневой `deno task vitest` их не исполняет.

## Инварианты

- Ни один случай не исполняется двумя раннерами и ни один — ни одним.
- Каждый переведённый случай краснеет на тех же данных, что и до перевода.
- Список случаев каталога после перевода = до, кроме переименований,
  названных в спеке.

## Правила

Какой раннер исполняет файл:

| Файл | `deno task test` | `deno task vitest` |
|---|---|---|
| `back/src/objects/cases.test.ts` | нет | да |
| `back/src/kiten/cmd_status_test.ts` | да | нет |
| `supervisor/src/install_test.ts` | да | нет |
| `cli/src/tasks_test.ts` | да | нет |
| `mod_test.ts` (корень `ts/`) | да | нет |
| `web/src/vitest_test.ts` | да (как сегодня) | нет |
| `web/src/**/*.test.tsx` | нет | нет (их зовёт `web:test`) |
| `back/src/objects/testtree.ts` | нет | нет |
| `back/src/objects/testdata/objects/cases.json` | нет | нет |
| файл `*.test.ts` в `node_modules` | нет | нет |

Перевод случая:

| До | После |
|---|---|
| `Deno.test("a", fn)` без шагов | `it("a", fn)` |
| `Deno.test("a", async (t) => { …t.step("b") })` | `describe("a")` с `it("b")` |
| шаг с вложенными шагами | вложенный `describe` |
| общий код теста до шагов (с `await`) | подготовка `describe` (`beforeAll`) |
| `t.step` в цикле по эталону | цикл, порождающий `it` при сборе |
| `Deno.test({ name, permissions, fn })` | `it(name, fn)`, права — нет |
| `Deno.test({ name, only: true })` | нет в репозитории |
| `FakeTime` (`@std/testing/time`) | `vi.useFakeTimers` / `vi.useRealTimers` |
| `assertEquals` и прочие `@std/assert` | `expect` — таблица видов в `.tmp/design-V1.md` с парами [S.7] |
| `Deno.exit` в тесте | ловит Vitest (`process.exit`); код с `Deno.exit` — после этапа 3 |

## Границы

- Каталоги, кроме `back/src/objects`, не переводятся (кроме замены импортов
  [S.12]).
- Код с `Deno.*` не переписывается (этап 3); исключение — `nearest.ts`
  (замена `@std/text`).
- Biome, `bun:test`, своя библиотека санитайзеров, воспроизведение прав
  Deno — нет.
- Прогон под Bun и Node не требуется: код каталога ещё на `Deno.*`.
- `web/` и его раннер не трогаются.

## Свойства решения

- Какой раннер исполняет файл — выводится из имени файла и только из него
  (одно место правды; списков путей в двух конфигах нет).
- Версии зависимостей зафиксированы точно; файл блокировки коммитится;
  у каждой зависимости строка «зачем» (`ts/CLAUDE.md`, «Зависимости»).
- Установка с нуля — одна команда, повторный запуск ничего не меняет.

## Устройство [D.n]

- **[D.1] Раннер по имени.** `*_test.ts` — `deno test` (исключить
  `*.test.ts` из его выборки: по умолчанию он берёт оба вида), `*.test.ts` —
  Vitest; `web/` исключён из корневого Vitest.
- **[D.2] Зависимости — один источник.** Пакеты, нужные Vitest и коду
  (`zod`, `hono`, `fastest-levenshtein`, `vitest`,
  `@vitest/coverage-istanbul`), — в `package.json` `ts/`; код импортирует
  голые имена npm; в `deno.jsonc` остаются только `jsr:`-записи старых
  тестов (`@std/assert`, `@std/testing`) до конца этапа 1. Эти зависимости
  разрешены владельцем (2026-10-07), прочие новые — нет. Псевдонимов
  `@zod/zod → zod` в конфиге Vitest нет.
- **[D.3] Задача `vitest`.** `deno task vitest` исполняет Vitest под Deno
  (под Bun и Node — после этапа 3, той же конфигурацией).
- **[D.4] Правила `ts/CLAUDE.md` — под переход** (файл ведёт исполнитель):
  «Шаг 1 — гейты» и «Команды» — обе задачи тестов и покрытие istanbul;
  «TDD» и «Асинхронность» — новый тест пишется на Vitest (`*.test.ts`),
  `vi.useFakeTimers` вместо `FakeTime`, временный каталог — через `node:fs`;
  строки про санитайзеры `Deno.test` и права тестов заменить фактом из
  «Оснований»; «Зависимости» — `package.json` рядом с `deno.jsonc`.
- **[D.5] Перевод механический**, скриптом во временном каталоге (не
  коммитится); ручные правки — только где скрипт не справился, перечислены
  в отчёте.

## Пункты чек-листа

`design.md`:
1. примитивы — раннер по имени файла и одна таблица перевода; всё прочее
   (гейт, выборка, покрытие) выведено из них;
2. особые случаи — `web/`, тесты с шагами, тесты с правами — строки таблицы
   перевода, не ветки в конфиге;
3. `null` и типы — ничего (порция не вводит логики);
4. кто решает — раннер решает имя файла; зависимость решает `package.json`;
5. память приватна — ничего;
6. голые данные — ничего;
7. основание проверкой — [S.3] список случаев до = после, [S.7] пары
   «зелёный / красный» на каждый вид утверждения.

`design-mpu.md`: 1–3 — ничего (команд нет); 4 один источник — [D.1], [D.2];
5 — ничего; 6 права Deno — снимаются в тестах по решению владельца, у
`compile:*` не меняются; 7 границы модулей — ничего; 8 внешнее — ничего;
9 голдены — junit «до» снимается с `main`; 10 пропускаемая проверка — нет.
