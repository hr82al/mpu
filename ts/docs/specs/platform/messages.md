# Разбор строки вызова в цепочку сообщений

Статус: к реализации

## Назначение

Строка вызова `mpu` — это не команда с аргументами, а цепочка сообщений:
первое уходит корневому объекту `mpu`, каждое следующее — результату
предыдущего. Эта спека задаёт, как слова строки делятся на сообщения. Что
сообщения делают, решают объекты (следующая порция); здесь их нет.

Разбор — новый модуль в `ts/back/`. Нынешний разбор аргументов команд и точка
входа CLI не меняются и к новому разбору не подключаются.

## CLI-контракт

Нет: наружу разбор в этой порции не выходит.

## Ввод/вывод

**Вход одного шага разбора:** оставшиеся слова строки (массив строк, как их
отдала оболочка) и описание текущего приёмника:

- `unary` — унарные селекторы, которые приёмник объявил;
- `keyword` — ключевые методы; у каждого — ключи с видом (`value` — ключ
  берёт значение, `flag` — ключ-флаг) и список обязательных ключей.

**Выход шага:** одно сообщение и оставшиеся слова — либо ошибка разбора.
Следующий шаг получает оставшиеся слова и описание **следующего** приёмника:
кто он, станет известно только после исполнения сообщения, поэтому цепочка
разбирается по шагу, а не целиком заранее.

**Сообщение** — одно из двух:

- унарное: `{ "unary": "<слово>" }`;
- ключевое: `{ "keyword": { "<ключ>": <значение>, … } }`; значение ключа вида
  `value` — строка как есть, вида `flag` — `true` или `false`.

Сравнение ключевых сообщений — по набору пар, порядок ключей не важен.

**Ошибка разбора** — текст из таблицы «Граничные случаи и ошибки»; код выхода
вызывающего, когда он появится, — 2.

Эталон — `fixtures/messages/cases.json`: описания приёмников и 30 случаев
(слова, приёмники по шагам, ожидаемые сообщения или текст ошибки). Тест
прогоняет все случаи; `receivers[i]` — описание приёмника для шага `i`.
Разбор случая идёт шагами до конца слов или до первой ошибки; ошибка шага
обрывает цепочку, сообщения до неё в эталоне ошибки не сравниваются. Описаний
в `receivers` может быть больше, чем шагов, — лишние не используются.

## Правила

Слово строки — одно из:

| Слово | Что это |
|---|---|
| `имя:` | ключ `имя` в ключевой форме; следующее слово — его значение |
| `--имя значение` | ключ `имя` в форме оболочки; следующее слово — его значение |
| `--имя=значение` | ключ `имя` со значением в том же слове |
| `--имя` у ключа вида `flag` | флаг `имя` = `true`, значение не берётся |
| `--имя=true` / `--имя=false` у ключа вида `flag` | флаг с явным значением; другое значение — ошибка «ключ … ждёт true или false» |
| ключ, которого нет ни у одного метода приёмника | считается ключом вида `value` |
| `имя: true` / `имя: false` у ключа вида `flag` | флаг с явным значением |
| `--help` | унарное сообщение `help` текущему приёмнику |
| `.` | явная граница между сообщениями |
| `--` | следующее слово берётся буквально: как значение ключа, если ключ ждёт значения, иначе как унарное сообщение |
| любое другое | унарное сообщение с этим словом |

Деление на сообщения:

| Положение | Итог |
|---|---|
| строка пуста | одно сообщение: унарное `help` корню |
| очередное слово — не ключ | унарное сообщение текущему приёмнику, даже если такого селектора у него нет (что делать с непонятым, решает приёмник) |
| очередное слово — ключ | начинается ключевое сообщение текущему приёмнику |
| в ключевом сообщении следующий ключ принимает хотя бы один ключевой метод приёмника, содержащий все уже набранные ключи | ключ входит в текущее сообщение |
| следующий ключ такому методу не принадлежит | текущее сообщение закончено; ключ начинает сообщение следующему приёмнику |
| следующее слово — не ключ | текущее сообщение закончено |
| `.` сразу за законченным сообщением | точку забирает шаг, который это сообщение сформировал; после неё есть слово — оно начинает следующий шаг; слов нет — ошибка «после точки нет сообщения» |
| шаг начинается с `.` (первое слово строки или вторая точка подряд) | ошибка «перед точкой нет сообщения» |
| `--help` внутри ключевого сообщения | текущее сообщение закончено; `help` — унарное сообщение следующему приёмнику |
| `--` внутри ключевого сообщения не сразу за ключом, ждущим значения | текущее сообщение закончено; слово за `--` — унарное сообщение следующему приёмнику |
| ни один метод приёмника не содержит первый ключ сообщения | сообщение формируется из подряд идущих ключей до не-ключа или `.`; проверки обязательности нет (непонятое — дело приёмника) |
| сообщение закончено, есть метод с его набором ключей, но у всех таких методов не хватает обязательного ключа | ошибка «не хватает ключа …» |
| значение ключа начинается с `--`, оканчивается на `:` или равно `.` без предшествующего `--` | это не значение: ошибка «у ключа … нет значения» |

## Инварианты

- Разбор не исполняет ничего и не обращается ни к чему, кроме переданных ему
  слов и описания приёмника.
- Один и тот же вход даёт один и тот же выход.
- Разбор не решает, существует ли селектор: неизвестное слово — всё равно
  сообщение.
- Порядок ключей в строке не влияет на сообщение.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| ключ дважды в одном сообщении | `ключ seller-id указан дважды` |
| ключ в конце строки | `у ключа card нет значения` |
| за ключом идёт другой ключ | `у ключа seller-id нет значения` |
| не хватает обязательного ключа | `не хватает ключа query` |
| у флага значение не `true`/`false` | `ключ check ждёт true или false` |
| за точкой, закончившей сообщение, слов нет | `после точки нет сообщения` |
| шаг начинается с точки: точка первым словом строки или две точки подряд | `перед точкой нет сообщения` |
| `--` последним словом | `после -- нет слова` |

В текстах ошибок имя ключа — без двоеточия и без `--`. Если отсутствуют
несколько обязательных ключей — называется первый по алфавиту.

   единственный примитив; разбор строки целиком выводится из него повтором
   с приёмником, который дал исполнитель [D.1].
2. Особые случаи → получатели — изменил: сообщение двух видов (унарное,
   ключевое) — на границе контракта (сериализация в эталон) это данные;
   поведение над видом слова (ключ, флаг, точка, экранирование) — решение
   исполнителя, `switch` по виду слова внутри разбора — находка [D.2].
3. Проверка `null` — изменил: «приёмник без ключевых методов» — обычное
   описание с пустыми списками, не отсутствие [D.3].
4. Кто решает — изменил: существует ли селектор, решает приёмник, не разбор
   [D.4]; обязательность ключей — описание метода.
5. Память приватна — ничего: разбор не хранит состояния между шагами,
   остаток слов возвращается явно.
6. Голые данные → протокол — изменил: вид ключа — `value`/`flag` на границе
   описания приёмника; внутри — решение исполнителя [D.2].
