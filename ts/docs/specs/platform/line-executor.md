# Исполнитель строк и сторож памяти

Статус: к реализации — порция 166a (серия языка, после установки 158–165).

## Назначение

Одна строка, съевшая память, сейчас роняет `mpu-back` целиком — вместе со
всеми идущими строками и висящими вопросами. Строка переезжает в отдельный
процесс-исполнитель; `back` остаётся лёгким ядром; при нехватке памяти убивают
исполнителя-виновника, а не ядро. Своих пределов у строки нет (решение
владельца: без лимитов) — защищает сторож по свободной памяти машины.

## Что где живёт

| `mpu-back` (ядро) | `mpu-worker` (исполнитель) |
|---|---|
| двери `/line`, `/agent/line`, `/rpc`, web | исполнение одной команды (`runCommand`) |
| решение правил, дверь `ask` | порты команды: кэш-БД, файлы, сеть, подпроцессы |
| вопросы человеку и билеты | — (вопрос — запросом к ядру) |
| журнал вызовов, `it`, отбор и форматы результата | структурный результат и потоки вывода — кадрами ядру |
| пул исполнителей | — |

Исполнитель — отдельная программа `mpu-worker` из тех же исходников `back`
(задача `compile:worker`, права — как у `compile:back`).

## Пул и протокол

- Ядро держит **тёплый пул**: 2 запущенных простаивающих исполнителя
  (параметр). Строка берёт исполнителя из пула; пул доливается сразу.
- Исполнитель исполняет **ровно одну строку** и завершается — память
  гарантированно возвращается.
- Все заняты — строка ждёт свободного (новый запускается сверх пула, если
  занятых меньше предела одновременных строк `line-concurrency.md`); отмена
  ожидания работает.
- Связь — кадры NDJSON по stdin/stdout исполнителя (stderr исполнителя — в
  журнал службы с префиксом `[worker <pid>]`):

| Кадр | Направление | Что |
|---|---|---|
| `run` | ядро → исп. | строка прежней диспетчеризации и контекст вызова (`call-context.md`: stdin, tty, env, cwd) |
| `out`, `err` | исп. → ядро | куски stdout/stderr команды по мере появления |
| `ask` | исп. → ядро | вопрос человеку (`prompt` порта команды); ядро задаёт его своим каналом; `copy` порта — `ask` вида `copy` с пустым `answer` |
| `note` | исп. → ядро | заметка журнала вызова (`io.note`) |
| `answer` | ядро → исп. | ответ человека |
| `stdin` | исп. → ядро | запрос ввода; ядро отвечает содержимым, запросив его у клиента по `stdin-on-request.md` (165c) |
| `result` | исп. → ядро | структурный результат (для отбора, `it`, значения ключа) и код выхода |
| `stop` | ядро → исп. | отмена (обрыв клиента, Ctrl+C); затем `SIGTERM`, через 5 с `SIGKILL` |

## Защита от нехватки памяти

- Исполнитель получает `oom_score_adj` = `1000` (повышать можно без
  привилегий): ядро запускает его через `/bin/sh -c 'echo 1000 >
  /proc/self/oom_score_adj && exec "$0" "$@"' <mpu-worker> …` — значение
  наследуется через `exec`. Deno не пускает к `/proc` ни при каком списке
  путей (`NotCapable … --allow-all`, замер исполнителя на Deno 2.9.4), поэтому
  нового права нет; права `compile:worker` = права `compile:back`.
- Путь исполнителя — `mpu-back --worker <путь>`; умолчание — `mpu-worker`
  рядом с `Deno.execPath()`. `install.sh` собирает и ставит `mpu-worker`,
  перезапуск — вместе с `back`.
- **Сторож — в супервизоре**: раз в секунду снимает `MemAvailable`
  (`/usr/bin/cat /proc/meminfo`) и память исполнителей (`/usr/bin/ps -e -o
  pid=,ppid=,rss=,comm=`: потомки `mpu-back` с `comm` `mpu-worker`); убивает
  `/usr/bin/kill -KILL <pid>`. Права супервизора: `--allow-run` на эти три
  программы, `--allow-write=$XDG_RUNTIME_DIR/mpu/killed`; у `back` — чтение
  `XDG_RUNTIME_DIR` в `--allow-env`. Причина подпроцессов — та же: `/proc` и
  `Deno.kill` чужого pid Deno пускает только без списков.
  `MemAvailable` ниже порога (умолчание — меньшее из 10 % памяти и 1 ГиБ) →
  убить `SIGKILL` **самого большого** исполнителя, если он больше 256 МиБ;
  иначе ничего (память ест не `mpu`).
- Перед убийством сторож пишет отметку `$XDG_RUNTIME_DIR/mpu/killed/<pid>` с
  размером; ядро, увидев смерть исполнителя сигналом, читает отметку и
  отвечает строке «строка остановлена: машине не хватает памяти, строка
  заняла N МиБ», код 1. Без отметки — «исполнитель строки упал (сигнал N)»,
  код 1.
- **Пояс**: служба `mpu.service` получает `MemoryMax=80%` (единица systemd).
- Пороги — параметры супервизора.

## Инварианты

- Строка через исполнителя даёт тот же stdout, stderr и код, что до порции
  (голдены серии 158–165 не меняются).
- Смерть исполнителя не трогает ядро, соседние строки и висящие вопросы.
- Исполнитель не держит состояния между строками.
- Вопрос человеку задаёт только ядро.

## Граничные случаи

| Дано | Ожидается |
|---|---|
| `mpu kiten ls` | итог как прежде; в шапке записи журнала вызовов (`invoke-log.md`) `pid=` и хвост `run=` — `pid` исполнителя, он ≠ `pid` ядра |
| после строки | исполнитель завершён, в пуле снова 2 простаивающих |
| тестовая строка ест память до порога | исполнитель убит, «строка остановлена: машине не хватает памяти, строка заняла N МиБ», код 1; ядро и соседняя строка живы, `pid` ядра прежний |
| памяти мало, но исполнители ≤ 256 МиБ | сторож ничего не убивает |
| два исполнителя, 300 и 900 МиБ, памяти мало | убит 900 |
| все исполнители заняты | строка ждёт; Ctrl+C во время ожидания — код 130 |
| ядро перезапустилось, исполнители работают | исполнители видят закрытый stdin, завершаются; вызывающий — код 1 прежним текстом: штатная остановка — «mpu-back: остановлен», ядро убито — «сервер оборвал строку» клиента; при штатной остановке ядро шлёт исполнителям `stop` и ждёт их |
| вопрос `ask` внутри строки | вопрос человеку от ядра, ответ доходит до исполнителя |
| `cat /proc/<pid исполнителя>/oom_score_adj` | `1000` |
