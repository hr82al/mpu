# platform/store — локальная кэш-БД

Статус: к реализации (2026-08-05; создана 2026-08-04 при переработке
init — доступ к кэш-БД выделен в атом, DDL-фикстура снята с живого
bootstrap; журнальный режим закрыт: WAL; права файла БД 0600 добавлены
2026-08-05 до запуска порции А; реализуется порцией А init)

## Назначение

Единая точка доступа к локальной служебной SQLite-БД
`~/.config/mpu/mpu.db`: открытие, идемпотентный bootstrap схемы,
транзакции. Доменные таблицы, их запросы и политика записей — в спеках
доменов (снапшот — `update.md`, кэш контейнеров — `init.md`, справочник
Kaiten — `platform/kaiten-http.md`, …); атом о содержимом таблиц не
знает.

БД — общая граница двух реализаций: пока жив маршрут `legacy`, тот же
файл читает и пишет Python-версия. Схема заморожена (эталон —
`fixtures/platform/store/schema.sql`); изменение схемы запрещено до
вывода Python из эксплуатации.

## Ввод/вывод

- Путь БД: литеральный `~/.config/mpu/mpu.db`; `XDG_CONFIG_HOME` НЕ
  учитывается (поведение оригинала; путь — контракт общего файла).
  Каталог создаётся при первом обращении на запись.
- Открытие БД на **чтение** схему не создаёт: на чистой машине
  читающая возможность падает ошибкой отсутствующей таблицы (тексты —
  в спеках потребителей), а не тихо создаёт пустую схему.
- Открытие устанавливает журнальный режим WAL
  (`PRAGMA journal_mode=WAL`): конкурентные вызовы `mpu` — в том числе
  конкурентные шаги init и параллельно работающая Python-реализация —
  читают и пишут без взаимной блокировки; рядом с файлом БД появляются
  служебные `-wal`/`-shm`. Режим персистентен в самом файле и совпадает
  с режимом оригинала — обе реализации работают в одном режиме.
- Bootstrap схемы — отдельная операция: идемпотентно создаёт
  недостающие таблицы и индексы (`CREATE … IF NOT EXISTS`-семантика),
  существующие данные не затрагивает. **Любая запись в кэш-БД
  предваряется bootstrap** — гарантия схемы и self-heal старой БД без
  части таблиц (поведение оригинала). Шаг 1 `init.md` вызывает
  bootstrap явно — единственное место, где схема создаётся без
  последующей записи.
- Эталон схемы — фикстура `fixtures/platform/store/schema.sql`: дамп
  `sqlite_master` БД сразу после bootstrap живой Python-версии. Это
  эталон для СВЕРКИ итогового состояния, не исполняемый скрипт: строка
  `sqlite_sequence` появляется автоматически (AUTOINCREMENT), её не
  создают руками.
- Запись — в транзакциях; прерывание не оставляет частичного состояния
  той операции, которую прервали (границы транзакций — в спеках
  потребителей: у снапшота — одна транзакция на всё, у upsert-кэша —
  на строку/пачку).
- Bootstrap приводит права файла БД к `0600` (создаваемого и уже
  существующего): в БД лежат токены доступа. Чтение прав не меняет.

## Инварианты

- Bootstrap идемпотентен: повторный вызов на живой БД ничего не меняет
  и данных не трогает.
- После bootstrap на чистой БД `sqlite_master` совпадает с фикстурой
  (с точностью до автоматической `sqlite_sequence`).
- Чтение не создаёт ни таблиц, ни частичной схемы; записи без
  предварительного bootstrap не существует.
- Реализация не выполняет `DROP`/`ALTER` объектов схемы ни на одном
  пути (заморозка до вывода Python).
- После любой записи права файла БД — `0600`.
- Конкурентный доступ двух реализаций к одному файлу не ломает БД:
  запись — через транзакции SQLite, длительных эксклюзивных блокировок
  вне транзакций нет.

## Граничные случаи и ошибки

- Чистая машина, чтение без предшествовавших записей → ошибка
  отсутствующей таблицы у первого же запроса потребителя.
- БД от старой версии без части таблиц → bootstrap досоздаёт
  недостающие, остальные не трогает (self-heal — см. `update.md`).
- Файл повреждён → ошибка SQLite пробрасывается потребителю (свой
  текст — его спека); атом не пытается «лечить» файл.

## Golden-примеры

## Известные отклонения

- **fix** — оригинал права файла БД не выставляет: файл создаётся с
  umask-правами (обычно `0644`), при том что в БД хранятся токены
  доступа. Новая реализация приводит права к `0600` при bootstrap;
  для Python-версии это прозрачно (владелец тот же).

(путь без `XDG_CONFIG_HOME` — поведение оригинала, зафиксировано
контрактом: файл общий, обе реализации обязаны находить его одинаково).
