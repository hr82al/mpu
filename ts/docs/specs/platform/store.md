# platform/store — локальная кэш-БД

Статус: реализовано (2026-08-05, порцией А init; приёмка — гейты и
контрактные точки перепроверены спецификатором. Создана 2026-08-04 при
переработке init; журнальный режим WAL и права 0600 закрыты
2026-08-05; каноничное имя в коде — `CacheDb`, см. glossary)

## Назначение

Единая точка доступа к локальной служебной SQLite-БД
`~/.config/mpu/mpu.db`: открытие, идемпотентный bootstrap схемы,
транзакции. Доменные таблицы, их запросы и политика записей — в спеках
доменов (снапшот — `update.md`, кэш контейнеров — `init.md`, справочник
Kaiten — `platform/kaiten-http.md`, …); атом о содержимом таблиц не
знает.

БД — общая граница двух реализаций: пока жив маршрут `legacy`, тот же
файл читает и пишет Python-версия. Схема заморожена (эталон —
`fixtures/platform/store/schema.sql`); изменение схемы запрещено до
вывода Python из эксплуатации.

## CLI-контракт

нет (платформенная возможность).

## Ввод/вывод

- Путь БД: литеральный `~/.config/mpu/mpu.db`; `XDG_CONFIG_HOME` НЕ
  учитывается (поведение оригинала; путь — контракт общего файла).
  Каталог создаётся при открытии БД (само открытие уже пишет:
  журнальный режим персистентен в файле).
- Открытие БД на **чтение** схему не создаёт: на чистой машине
  читающая возможность падает ошибкой отсутствующей таблицы (тексты —
  в спеках потребителей), а не тихо создаёт пустую схему.
- Открытие устанавливает журнальный режим WAL
  (`PRAGMA journal_mode=WAL`): конкурентные вызовы `mpu` — в том числе
  конкурентные шаги init и параллельно работающая Python-реализация —
  читают и пишут без взаимной блокировки; рядом с файлом БД появляются
  служебные `-wal`/`-shm`. Режим персистентен в самом файле и совпадает
  с режимом оригинала — обе реализации работают в одном режиме.
- Bootstrap схемы — отдельная операция: идемпотентно создаёт
  недостающие таблицы и индексы (`CREATE … IF NOT EXISTS`-семантика),
  существующие данные не затрагивает. **Любая запись в кэш-БД
  предваряется bootstrap** — гарантия схемы и self-heal старой БД без
  части таблиц (поведение оригинала). Шаг 1 `init.md` вызывает
  bootstrap явно — единственное место, где схема создаётся без
  последующей записи.
- Эталон схемы — фикстура `fixtures/platform/store/schema.sql`: дамп
  `sqlite_master` БД сразу после bootstrap живой Python-версии. Это
  эталон для СВЕРКИ итогового состояния, не исполняемый скрипт: строка
  `sqlite_sequence` появляется автоматически (AUTOINCREMENT), её не
  создают руками.
- Запись — в транзакциях; прерывание не оставляет частичного состояния
  той операции, которую прервали (границы транзакций — в спеках
  потребителей: у снапшота — одна транзакция на всё, у upsert-кэша —
  на строку/пачку).
- Файл БД создаётся сразу с правами `0600` (в БД лежат токены
  доступа); служебные `-wal`/`-shm` появляются при первой настоящей
  записи и наследуют права файла — окна с широкими правами нет. Уже
  существующий файл с иными правами bootstrap приводит к `0600`.
  Чтение прав не меняет.

## Инварианты

- Bootstrap идемпотентен: повторный вызов на живой БД ничего не меняет
  и данных не трогает.
- После bootstrap на чистой БД `sqlite_master` совпадает с фикстурой
  (с точностью до автоматической `sqlite_sequence`).
- Чтение не создаёт ни таблиц, ни частичной схемы; записи без
  предварительного bootstrap не существует.
- Реализация не выполняет `DROP`/`ALTER` объектов схемы ни на одном
  пути (заморозка до вывода Python).
- После любой записи права файла БД — `0600`.
- Конкурентный доступ двух реализаций к одному файлу не ломает БД:
  запись — через транзакции SQLite, длительных эксклюзивных блокировок
  вне транзакций нет.

## Граничные случаи и ошибки

- Чистая машина, чтение без предшествовавших записей → ошибка
  отсутствующей таблицы у первого же запроса потребителя.
- Путь БД неопределим (`HOME` не задана) → отказ доменной ошибкой
  `путь к кэш-БД не определён: HOME не задан` (префикс — имя команды,
  рендер — её спека), exit 1.
- БД от старой версии без части таблиц → bootstrap досоздаёт
  недостающие, остальные не трогает (self-heal — см. `update.md`).
- Файл повреждён → ошибка SQLite пробрасывается потребителю (свой
  текст — его спека); атом не пытается «лечить» файл.

- **fix** — оригинал права файла БД не выставляет: файл создаётся с

## Изоляция через XDG_CONFIG_HOME — половинчатая

Замер 2026-08-28. `XDG_CONFIG_HOME` подменяет **только env-файл**
(`src/env/mod.ts`). Кэш-БД, журнал вызовов и файл токена берутся через
`defaultConfigDir()` (`src/runtime/mod.ts`), который смотрит **исключительно
`HOME`**. Токен-кэш sl-back тогда же лежал в каталоге состояния — вопреки
`slback-http.md` и вопреки оригиналу; порция 87 вернула его к env-файлу.

Наблюдаемо так: с подменным `XDG_CONFIG_HOME` команда берёт чужой адрес
сервера и креды из подменного `.env`, но резолв читает основной кэш, а записи
о вызовах ложатся в основной журнал. Базы в подменном каталоге не появляется
вовсе.

Правило коротко: **состояние адресуется `HOME`, конфигурация —
`XDG_CONFIG_HOME`; подмена второго не изолирует первое.**

Комментарий у `openCacheDb` при этом **верен**, и править его не надо: он про
параметр каталога, из которого собираются пути состояния (`mpu.db`, `token`),
— тест, подставив его, изолирует всё сразу: второй каталог у `makeDenoIo` по
умолчанию равен первому, и разводит их только точка входа. Дефект в том,
что у оператора такой ручки снаружи нет: бинарь зовёт
`makeDenoIo(defaultConfigDir())`, то есть `HOME`.

**Рабочий приём изоляции — подменять `HOME`**, а не `XDG_CONFIG_HOME`: он
уводит и кэш, и журнал, и токен. Замер 2026-08-28: с подменным `HOME` резолв
селектора отвечает «кэш-БД не инициализирована», а команда, не требующая
резолва, работает — то есть недоступность кэша проверяема, и граница «не
открывает кэш» доказывается, а не декларируется.

Решено порцией 87 — вторая форма: **расхождение намеренное и названо в
справке** (`mpu --help`, раздел «Окружение:»). Первая форма отвергнута, и
довод сильнее удобства: пока Python-версия жива, файлы состояния у неё общие
с нашими и адресуются литеральным `~/.config/mpu` (см. выше «Ввод/вывод»).
Научи `defaultConfigDir()` читать `XDG_CONFIG_HOME` — и у оператора, которому
переменную задала графическая сессия, две реализации молча разъедутся по
разным базам и разным журналам. Это хуже той половинчатости, которую первая
форма лечит.

Граница проведена так: **чем адресованы креды, тем адресовано и выведенное из
них.** `XDG_CONFIG_HOME` уводит env-файл и токен-кэш sl-back, выведенный из
его кред; `HOME` уводит кэш-БД, журнал вызовов и токен MCP-сервера — последний
не выведен из кред и не предпочтение, а локальный секрет машины. Замер
2026-08-31 у оригинала: `py/src/mpu/lib/slapi.py:34-41`,
`token_cache_path()` = `XDG_CONFIG_HOME/mpu/.api-token.json` — при подменной
переменной `/tmp/podmena/mpu/.api-token.json`. То есть переезд токен-кэша не
наше решение о вкусе, а совпадение с оригиналом.

Изолировать разом и состояние, и конфигурацию можно только подменой `HOME`.
