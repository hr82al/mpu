# platform/selector — резолв селектора

Статус: к реализации (2026-08-05; goldens сняты с живой версии —
`fixtures/platform/selector/`; вопрос неинициализированной кэш-БД
закрыт fix-отклонением; тексты ошибок и формат кандидатов — дословно)

## Назначение

Единый резолв строки-селектора (`sl-N`, client_id, email, IP,
spreadsheet_id, sid, заголовок таблицы) в номер сервера и список
кандидатов; вторая ступень — сужение до единственного client_id.
Используется всеми native-командами, адресующими сервер или клиента:
строка-селектор разбирается единой платформенной возможностью — команды
селектор сами не трактуют (legacy-командам селектор разбирает их
Python-реализация, реестр аргументы не трогает).

## CLI-контракт

нет (платформенная возможность; синтаксис селектора — ниже).

## Ввод/вывод

Вход: строка-селектор `value`; опционально override `--server sl-N`.
Выход: `(номер сервера: int, кандидаты: список строк
{client_id, spreadsheet_id, title, server, server_number, sids})` либо
ошибка резолва с приложенными кандидатами.

Порядок разбора:

1. Задан override `--server`: обязан матчить `sl-N`, иначе ошибка
   `bad --server: '<значение>' (expected sl-N)`. Override полностью
   замещает value при определении сервера (кандидаты пусты).
2. value сам матчит `sl-N` → короткий цикл `(N, [])`; кэш не читается,
   даже если в нём есть одноимённые записи. Диапазон N не ограничен —
   несуществующий N падает позже, на этапе подключения («pg_N не задан»).
3. Иначе — однопроходный поиск по локальной кэш-БД, первый непустой
   предикат побеждает, в порядке: email (только из кэша email→клиент;
   сеть не трогается) → точный client_id (целое число, включая
   отрицательное) → IPv4-паттерн (ищется в конфиг-файле серверов, не в
   кэш-БД) → WB sid (точный, затем substring) → spreadsheet_id
   substring → title substring (только если по spreadsheet_id пусто).
4. Вердикт по множеству различных server_number среди кандидатов
   (кандидаты без сервера в множестве не участвуют):
   - кандидатов нет → `nothing matched: '<value>'`; для email —
     `email '<value>' не в кэше; сначала запусти: mpu search <value>`;
   - кандидаты есть, серверов нет →
     `matched but no server resolvable: '<value>'`;
   - серверов больше одного → `ambiguous selector '<value>' —
     <N> candidates on different servers`;
   - иначе успех: единственный номер + все кандидаты.

Ошибка резолва: команда печатает stderr `<команда>: <сообщение>`, затем
список кандидатов (если есть), и завершается exit 2 — один код для всех
подтипов. Формат списка кандидатов — по строке на кандидата с отступом
в два пробела, поля разделены двумя пробелами:
`  client_id=<v>  server=<v>` + `title="<v>"` (если непустой) +
`spreadsheet_id=<v>` (если непустой); server_number и sid'ы не
печатаются.

Вторая ступень (командам, которым нужен один клиент): кандидаты пусты →
`selector '<v>' resolved to sl-<N> but does not point to a specific
client; pass client_id / spreadsheet / title`; ни у одного кандидата
нет client_id → `selector resolved to a server but no client_id; use a
selector that points to a specific client` + кандидаты; больше одного
различного client_id → `selector matches <n> clients — narrow it down`
+ кандидаты; иначе — client_id. Всё — exit 2.

Командные расширения, перехватываемые ДО базового резолва (дословные
тексты их ошибок — в спеках соответствующих команд):

- `dev:<хвост>` — селектор dev-стенда. Семантику хвоста задаёт команда:
  для SQL-команд хвост = client_id (одна общая dev-БД, схема
  `schema_<client_id>`); для ssh/exec-команд хвост = номер sl-сервера
  на dev-ноде. Это осознанный контракт, не непоследовательность —
  воспроизводить как есть.
- sw-алиасы `{sw, sw-pg, swpg, sw-back, swback, ws, workspaces}`
  (без учёта регистра) — БД воркспейсов; несовместимы с `--server`
  (exit 2), как и dev-селектор.
- Точное имя контейнера (ssh/exec-команды): проверяется между `sl-N` и
  базовым резолвом; ровно одно совпадение → контейнер; больше одного →
  exit 2 со списком совпадений, БЕЗ проваливания в базовый резолв
  (опечатка не должна проглатываться клиент-селектором); ноль — базовый
  резолв.

## Побочные эффекты

Сам резолв — только чтение локальной кэш-БД и env-файла;
ни внешней сети, ни PG, ни записи. Резолв никогда не запускает синк
кэша сам: полный синк при пустом результате — поведение команды поиска
(гейтится её флагом и не срабатывает на IP-подобных значениях; email
идёт точечным синком) — контракт в её спеке. Секреты в кандидатах и
текстах ошибок не выводятся.

## Конфигурация

Env-файл (`platform/env-file.md`): `sl_<N>`/`pg_<N>` — адреса,
`sl_<N>_portainer` — legacy-fallback оркестратора; параметры PG
(порт, пользователь, пароль, имя БД с дефолтом `wb`); dev-хост/порт/БД
с дефолтами и отдельными кредами. Кэш-БД (`platform/store.md`): таблицы
клиентов, таблиц, sid'ов, контейнеров, email→клиент; схему создаёт
только явная инициализация.

## Инварианты

- Резолв идемпотентен и не мутирует состояние.
- `sl-N` короткий цикл строго приоритетнее поиска по кэшу.
- Override `--server` побеждает безусловно; value тогда не влияет на
  выбор сервера.
- Однозначность считается по различным серверам, не по числу
  кандидатов: несколько кандидатов на одном сервере — успех.
- Email внутри резолва — только из кэша; сетевой резолв email не
  запускается никогда.
- Все native-команды обязаны трактовать селектор идентично — логика
  одна, платформенная, по командам не дублируется.

## Граничные случаи и ошибки

- `sl-0` — обычный сервер (main), особых веток нет.
- Отрицательное целое → поиск как client_id → обычно `nothing matched`
  (отдельной валидации нет).
- IPv4-подобное значение без совпадений в конфиге → `nothing matched`,
  синк кэша не запускается.
- Клиент найден, но server пуст → `matched but no server resolvable`
  (не «ambiguous», не «nothing matched»).
- Один client_id с таблицами на разных серверах (перенос клиента) →
  `ambiguous …` — реальный сценарий, не теория.
- Кэш-БД не инициализирована (нет таблиц) → единая ошибка с подсказкой
  (см. «Известные отклонения»), не трейсбек.

## Golden-примеры

Сняты с живой версии 2026-08-05 (`fixtures/platform/selector/`; префикс
`mpu sql-ro:` — имя вызвавшей команды, для других команд — их имя):

- `err-nothing-matched.txt` — несуществующий селектор, stderr, exit 2;
- `err-email-not-cached.txt` — email вне кэша: подсказка запустить
  поиск, stderr, exit 2;
- `err-bad-server.txt` — невалидный `--server`, stderr, exit 2;
- `dry-v-client-stderr.txt` — SQL-команда `--dry -v` по client_id:
  мета-блок с `search_path: schema_<client_id>, public` (значения
  заменены плейсхолдерами `sl-<N>`/`<pg_host>`/`<client_id>` —
  подстановка — обязанность теста);
- `dry-v-sl0-stderr.txt` — то же по `sl-0`: мета-блок без search_path.

Остальные классы — контрактные тесты реализации на синтетическом кэше:
ambiguous (клиент на двух серверах); matched-but-no-server; вторая
ступень (все три отказа + успех); порядок предикатов (sid раньше
spreadsheet_id, title только при пустом spreadsheet_id); кандидаты без
сервера не участвуют в вердикте.

## Известные отклонения

- **preserve** — кандидаты с пустым server выпадают из проверки
  неоднозначности: 2 кандидата на sl-1 + 1 без сервера = однозначный
  успех со всеми тремя кандидатами в выдаче. Закрепить тестом при
  портировании, чтобы поведение было явным, а не унаследованным.
- **fix** — противоречивый конфиг серверов (один IP у разных ключей)
  резолвится в generic `nothing matched`, маскируя битый конфиг.
  Правильное поведение: явная ошибка конфигурации с указанием
  конфликтующих ключей. Расхождение ожидаемо только на битом конфиге.
- **preserve** — `sl-<огромное N>` проходит резолв и падает позже
  понятной ошибкой «pg_<N> не задан» — дополнительная валидация не
  нужна.
- **fix** — неинициализированная кэш-БД (нет таблиц) у оригинала ведёт
  себя противоречиво: пути client_id/spreadsheet_id/title падают сырым
  трейсбеком «no such table», email-путь молча глотает отсутствие
  таблицы и отвечает «email не в кэше». Правильное поведение — единая
  ошибка резолва для всех путей: `<команда>: кэш-БД не
  инициализирована; попробуй: mpu init`, exit 2, без трейсбека.
