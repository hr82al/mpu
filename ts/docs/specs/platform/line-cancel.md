# Отмена строки и бесконечный вывод

Статус: к реализации (порция 13 переключения).

## Назначение

Две вещи, которых не хватает тонкому клиенту, чтобы заменить старый `mpu`:

- **Отмена.** Сегодня Ctrl+C у клиента закрывает канал, а строка на сервере
  доходит до конца, и её вывод отбрасывается (`platform/back-rpc.md`). У
  старого `mpu` тот же Ctrl+C останавливал работу: сигнал приходил тому самому
  процессу, который её делал. Долгая выгрузка, `ssh`, запрос к базе —
  продолжаются, хотя их уже никто не ждёт.
- **Бесконечный вывод.** `mpu logs --follow` сегодня отвергается вне
  терминала («`--follow` доступен только в CLI»), потому что ответ собирается
  целиком. Слежение за логами — обычная работа человека, и без неё
  переключение неполно.

Обе решаются одним: у строки появляется **владелец**, который её остановит, и
вывод уходит клиенту по мере появления, а не по завершении.

## Отмена — это обрыв канала, а не новое сообщение

Отдельной команды «отменить» нет: отменяет тот, кто перестал слушать.

| Канал | Что считается отменой |
|---|---|
| WebSocket (`/line`, `/agent/line`) | клиент закрыл сокет |
| `POST /line` (NDJSON) | клиент оборвал чтение ответа |
| MCP | клиент прислал отмену вызова, и `mpu-mcp` оборвал свой запрос к `back` |

Причина такого выбора: новый вид сообщения потребовал бы имени строки, а
имени у неё нет ни у одного из трёх клиентов. Обрыв канала виден всем трём
одинаково и подделать его нельзя.

## Что происходит при отмене

1. Строка получает сигнал отмены; команда прекращает работу на ближайшей
   точке ожидания.
2. Подпроцессы строки (`ssh`, `docker`, внешние программы) получают `SIGTERM`;
   не завершились за **5 секунд** — `SIGKILL`.
3. Сигнал отмены доходит до ожиданий строки. В этой порции он проведён до
   слежения за логами (единственная бесконечная работа); остальные сетевые
   вызовы и клиент базы получат его по мере надобности — см. «Известные
   отклонения».
4. Запись журнала вызовов закрывается кодом **130**; словесную пометку
   журнал выводит из кода сам — второго факта об отмене никто не пишет.
   Потерянной записи не бывает.
5. Соседние строки не затрагиваются, а место в пределе одновременности
   освобождается сразу (`platform/line-concurrency.md`): отменённая строка не
   держит его до конца работы команды.

После отмены у сервера не остаётся ни одного процесса, порождённого этой
строкой: проверяется тем, что список потомков сервера пуст.

## Вывод — по мере появления

- Кадры `out` и `err` уходят клиенту, как только появились, и не ждут конца
  строки. Проверяется на команде с бесконечным выводом: первый кадр приходит
  до того, как команда кончилась (она не кончается вовсе).
- `--follow` разрешён на всех дверях; отказ «только в CLI» снимается.
  Остановка слежения — отмена, то есть обрыв канала.
- Клиент читает медленнее, чем команда печатает, — сервер притормаживает
  чтение вывода команды, а не копит его в памяти без предела. Проверяется на
  `POST /line`: там медленный читатель виден сервером как событие. У
  WebSocket такого события нет (см. «Известные отклонения»).

## Инварианты

- Отменённая строка не оставляет процессов, открытых файлов и соединений.
- Отмена одной строки не меняет итог соседних.
- Строка, кончившаяся сама, и строка, отменённая ровно в тот же момент, дают
  разные записи журнала (код команды против 130) и не дают двух записей.
- Клиент, не оборвавший канал, поведения не меняет: итог строки тот же, что до
  порции.
- Вывод не теряется: то, что команда напечатала до отмены, доходит до клиента.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| Ctrl+C у `mpu-next` во время долгой строки | клиент печатает `mpu-next: прервано`, код 130; строка на сервере остановлена |
| отмена, пока строка ждёт ответа на вопрос | вопрос снимается, строка не исполняется: stderr `…: не подтверждено`, код 1; записи журнала нет, как у любого отказа правил |
| отмена после `exit` (гонка) | итог строки прежний, второй записи журнала нет |
| подпроцесс не реагирует на `SIGTERM` 5 секунд | `SIGKILL`, строка закрыта кодом 130 |
| `mpu-next logs -f` | записи идут по мере появления; Ctrl+C останавливает и слежение, и строку |
| `logs --follow` через MCP | разрешён; отмена вызова у агента останавливает строку |
| `POST /line` с `logs -f`, клиент читает и рвёт соединение | поток кадров идёт, обрыв останавливает строку |
| клиент читает медленно, команда печатает быстро (`POST /line`) | память сервера не растёт неограниченно; вывод доезжает целиком |
| отмена строки, которая ничего не начинала (ждала места в пределе 16) | строка не исполняется, записи журнала нет |

## Известные отклонения

- Старый `mpu` останавливался сигналом процесса, и команда могла ничего не
  узнать об остановке; здесь отмена доходит до команды явно. Вердикт —
  **fix**: команда обязана прибрать за собой.
- **Давление у WebSocket не передаётся.** У сокета нет события «буфер
  отправки опустел», а опрос поля буфера — это синхронизация по таймеру,
  запрещённая правилами модуля. Поэтому медленный читатель по сокету копит
  вывод в буфере сокета; у `POST /line` давление честное. Снимется, когда у
  канала появится событие.
- **Отказ «`--follow` только в CLI» снимается только у дверей `mpu-back`.** У
  старого `mpu mcp` он остаётся: тот копит вывод целиком и отмены не имеет
  вовсе, так что бесконечный вызов агенту там нечем остановить. Уйдёт вместе
  со старым сервером.
- **Отмена проведена до слежения за логами, а не до каждого сетевого
  вызова.** Прочие `fetch` и клиент базы сигнала пока не принимают: строка
  остановится на ближайшей своей точке ожидания, а начатый запрос доживёт до
  ответа. Расширяется по мере надобности, отдельными порциями.

## Открытые вопросы

- Что делает Claude Code при отмене вызова тула: снимает ли он заодно висящий
  запрос подтверждения. Снимается живой пробой в MCP-клиенте (делает хост при
  приёмке); до пробы поведение MCP-стороны не фиксируется, на остальные двери
  вопрос не влияет.

## Пункты чек-листа

`design.md`:

1. Примитивы — изменил: примитив — «строка, у которой есть чем её
   остановить»; поток вывода и отмена выводятся из него [D.1].
2. Особые случаи → получатели — изменил: «клиент слушает» и «клиент ушёл» —
   два получателя вывода, а не проверка обрыва у каждой печати [D.2].
3. Проверка `null` — изменил: ушедший клиент — получатель, который вывод
   отбрасывает и просит остановиться, а не `null` вместо канала [D.2].
4. Кто решает — изменил: останавливаться решает сама строка, получив просьбу;
   сервер не убивает её снаружи [D.1].
5. Память приватна — изменил: подпроцессы и открытые соединения знает сама
   строка и закрывает их, кончаясь любым способом [D.3].
6. Голые данные → протокол — изменил: `--follow` перестаёт быть флагом,
   которому отказывают по виду канала: бесконечный вывод — такой же вывод
   [D.4].

`design-mpu.md`:

1. Команда — сообщение объекту — ничего: новых команд нет.
2–3 — ничего.
4. Один факт — один источник — изменил: причина конца строки называется один
   раз — кодом записи журнала (130 у отменённой) [D.5].
5. Величина из результата — изменил: «отменена» ставится по факту остановки,
   а не по факту обрыва канала: обрыв мог прийти после конца [D.5].
6. Права Deno — ничего: новых прав не нужно.
7. Границы модулей — изменил: отмена доходит до команд тем же портом, что и
   остальное, без глобального обработчика сигналов [D.1].
8. Внешнее ссылкой — изменил: срок между `SIGTERM` и `SIGKILL` — параметр
   [D.3].
9. Голден снятый — изменил: кадры слежения и отмены снимаются прогоном [D.6].
10. Пропускаемая проверка — изменил: проверка «после отмены не осталось
    процессов» не пропускается: нечего проверить — значит ошибка [D.3].

[D.1] Строку останавливает она сама. [D.2] Ушедший клиент — получатель.
[D.3] Подпроцессы знает строка. [D.4] Бесконечный вывод — обычный вывод.
[D.5] Причина конца — одна. [D.6] Голдены сняты прогоном.
