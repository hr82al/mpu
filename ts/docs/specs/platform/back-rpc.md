# `mpu-back`: сервер строк и запросов

Статус: к реализации

## Назначение

Долгоживущий процесс, который исполняет строки `mpu-next` для клиентов:
будущих `cli`, `mcp` и фронта. Строка идёт по WebSocket — только так сервер
может посреди исполнения спросить подтверждение (`platform/policy.md`) и
отдавать вывод по мере появления. Запросы без исполнения (снимок дерева,
список правил, здоровье, схема) — обычный HTTP.

Порция добавляет сервер и задачу его запуска. Клиентов ещё нет (порции 6, 7,
10); нынешний `mpu`, `mpu mcp` и `mpu-next` не меняются.

## CLI-контракт

Задача `deno task back` из `ts/` (в `~/.local/bin` не ставится):

```
deno task back [--port <число>]
```

- слушает только `127.0.0.1`; порт по умолчанию `7338`, `--port 0` — порт
  выдаёт ОС;
- после того как сокет слушает, печатает в stdout одну строку
  `mpu-back: http://127.0.0.1:<порт>` и перевод строки;
- SIGTERM и SIGINT — закрывает сокет и открытые строки (исход открытых —
  `{"exit": 1}` с `{"err": "mpu-back: остановлен\n"}` перед ним), код 0;
- порт занят — stderr `mpu-back: порт <порт> занят`, код 1.

Права задачи — права `next` (в них уже есть `--allow-net` без списка: оно
покрывает и слушание петли) плюс запись в `$HOME/.cache/mpu` (снимок дерева);
новое право — строкой с обоснованием. Права `back` ⊇ права `next`, разница —
ровно каталог снимка (проверяется тестом).

## Доступ

| Условие | Ответ |
|---|---|
| `GET /health` | 200, `{"ok": true, "version": "<версия сборки>"}`, без токена |
| любой другой путь без `Authorization: Bearer <токен>` (у WebSocket — либо заголовок, либо подпротокол `bearer.<токен>`) или с неверным | 401, тела нет |
| `Origin` есть, и его хост не `127.0.0.1`, `localhost`, `[::1]`, `mpu.localhost` | 403, тела нет (проверяется до токена) |
| путь неизвестен | 404, тела нет |
| метод HTTP не тот, что у пути | 405, тела нет |

**Подпротокол WebSocket.** Сервер никогда не выбирает подпротокол
`bearer.*`: выбранный подпротокол возвращается заголовком ответа, и токен
оказался бы в ответе. Если клиент предложил ещё один подпротокол, выбирается
первый не-`bearer`; иначе ответ без подпротокола. Браузер без выбранного
подпротокола соединение не откроет — клиенты предлагают
`["mpu", "bearer.<токен>"]`.

Токен — тот же файл, что у нынешнего MCP-сервера (`platform/mcp-server.md`,
«Конфигурация»); путь передаётся серверу, не читается по месту. Ни один
ответ и ни одна строка лога сервера не содержат токена. `mpu.localhost` в
списке `Origin` — ради фронта (порция 10, открывается по
`http://mpu.localhost:7338`); у нынешнего MCP-сервера список не меняется.

**Граница доверия.** Владелец токена — доверенная сторона: сервер не может
отличить человека от программы, которая прочла файл токена и подключилась к
`/line`, назвалась `"human": true` и сама ответила `y`. Правила
подтверждения защищают от агента, который ходит **через MCP** (у него есть
только `/agent/line` через `mpu-mcp`, а вопрос уходит человеку в интерфейс
клиента). Агент с собственной оболочкой и правом читать файл токена эту
защиту обходит — это закрывается не сервером, а запретом агенту читать
файл токена (правило разрешений клиента агента; решение владельца).

## Строка: `GET /line` и `GET /agent/line` (WebSocket)

Путь задаёт **канал вызова** (`platform/policy.md`): `/line` — клиент с
человеком (он отвечает на вопросы), `/agent/line` — агент. На канале агента
изменение правил всегда отказывает `изменить правила может только человек`
(код 1), вопрос о правиле ему не задаётся. Вопрос о решении `ask` задаётся
обоим каналам.

Кадры — текстовые, каждый — один JSON-объект.

Клиент → сервер, первым кадром:

```json
{"words": ["kiten", "ls"], "cwd": "/home/user/mr/mp", "human": true}
```

- `words` — слова строки как есть; `cwd` — каталог клиента, абсолютный;
- `human` — есть ли у клиента, кого спросить (у `cli` — терминал). На `/line`
  с `"human": false` вопрос не задаётся, решение `ask` отказывает как у канала
  без человека. На `/agent/line` поле читается так же — для решения `ask`.

Сервер → клиент, сколько угодно раз, в порядке появления:

```json
{"out": "<кусок stdout>"}
{"err": "<кусок stderr>"}
{"ask": "выполнить mpu kiten comment 1 x? [y/N] "}
```

На кадр `ask` клиент отвечает кадром `{"answer": "<строка ответа>"}`; толкование
ответа — как в `platform/policy.md` (`y`/`yes` в любом регистре — «да»).

Последний кадр сервера, после него сервер закрывает сокет с кодом 1000:

```json
{"exit": 0}
```

Правила кадров:

| Дано | Ожидается |
|---|---|
| первый кадр не разбирается или нет `words`/`cwd` | `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}` |
| клиент закрыл сокет, не ответив на `ask` | исполнение не начинается; ответ «нет» |
| клиент не ответил на `ask` за 120 секунд | ответ «нет»: `…: не подтверждено`, `{"exit": 1}` |
| после первого кадра клиент прислал что-то, кроме `answer` на заданный вопрос | кадр игнорируется |
| `cwd` не существует | `{"err": "mpu-back: нет каталога <cwd>\n"}`, `{"exit": 2}` |

**Исполнение** строк идёт по одной: вторая ждёт конца исполнения первой
(исполнение меняет текущий каталог процесса на `cwd` строки). Разбор, решение
правил и вопрос `ask` — **до** очереди: строка, ждущая ответа человека,
других не держит. Ожидание не видно клиенту, кроме задержки. Запросы
`/rpc` и `/health` от очереди не зависят и от текущего каталога не зависят.
Окружение процесса — самого сервера: переменные клиента не передаются;
stdin у строки пуст (конец ввода сразу); стандартные потоки строки не
терминалы (см. «Известные отклонения»).

Итог строки — тот же, что у `mpu-next` с тем же набором правил и тем же
ответом человека: те же байты stdout и stderr, в том же порядке внутри
каждого потока, тот же код (`platform/registry-objects.md`, «`mpu-next`»).
Журнал вызовов пишется так же.

## Запросы: `POST /rpc` (JSON-RPC 2.0)

| Метод | Параметры | Результат |
|---|---|---|
| `tree.snapshot` | нет | снимок дерева (ниже) |
| `policy.list` | нет | то же, что данные строки `policy` (`platform/policy.md`) |
| `schema` | нет | JSON Schema кадров строки и методов `/rpc` (голден) |

Ошибки — по JSON-RPC: неизвестный метод — `-32601`, тело не JSON — `-32700`
без `id`, сбой — `-32603`. Изменения правил через `/rpc` нет — только
строкой.

**Снимок дерева** — узлы дерева `mpu-next` в порядке обхода в глубину, дети
по алфавиту:

```json
{"version": "<версия>", "nodes": [
  {"path": [], "summary": "…", "selectors": ["allow:", "…"], "tail": null},
  {"path": ["kiten"], "summary": "…", "selectors": ["card", "…"], "tail": null},
  {"path": ["kiten", "card"], "summary": "…", "selectors": [], "tail": "args"}
]}
```

При старте сервер записывает снимок в `$HOME/.cache/mpu/tree.json` атомарно
(временный файл рядом и переименование). Каталога нет — создаётся. Записать
не удалось — строка в stderr `mpu-back: снимок дерева не записан: <причина>`,
сервер работает дальше.

## Инварианты

- Сервер слушает только `127.0.0.1`.
- Итог строки по WebSocket равен итогу `mpu-next` на тех же словах, правилах
  и ответе.
- На `/agent/line` изменить правило нельзя ни при каком ответе.
- Строка, ждущая ответа, не задерживает исполнение других строк.
- Строки не исполняются одновременно.
- Токен не появляется ни в одном ответе, кадре и выводе.
- Остановка сервера не оставляет незакрытых сокетов и незавершённых строк без
  кадра `exit`.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| `GET /health` без токена | 200, `{"ok": true, …}` |
| `POST /rpc` `tree.snapshot` без токена | 401 |
| `GET /line` с `Origin: http://evil.localhost` | 403 |
| `GET /line` с `Origin: http://mpu.localhost:7338` и токеном в подпротоколе | подключение |
| строка `["version"]` | `{"out": "<версия>\n"}`, `{"exit": 0}` |
| строка `["kitn"]` | `{"err": "mpu: не понимает kitn; ближайшие: kiten\n"}`, `{"exit": 2}` |
| строка `["allow:", "kiten ls"]` на `/line`, ответ `y` | кадр `ask` с текстом `изменить правило: kiten ls → allow? [y/N] `, затем данные, `{"exit": 0}`; правило записано |
| та же строка на `/agent/line` | `{"err": "изменить правила может только человек\n"}`, `{"exit": 1}`; кадра `ask` нет; файл правил не изменён |
| решение `ask`, `"human": false` | `{"err": "… нужно подтверждение, а спросить некого\n"}`, `{"exit": 1}` |
| две строки одновременно | вторая начинает исполнение после кадра `exit` первой |
| строка A ждёт ответа на `ask`, приходит строка B с решением `allow` | B исполняется, не дожидаясь ответа A |
| SIGTERM во время строки | у открытой строки `err` и `{"exit": 1}`; процесс — код 0 |
| `POST /rpc` с телом `{` | `-32700` без `id` |

## Известные отклонения

- Окружение строки — окружение сервера, не клиента. `COLUMNS`, `NO_COLOR`,
  `TMUX`, `PG*` клиента на строку не действуют. Передача окружения клиента —
  по нужде, отдельной порцией.
- Строки исполняются по одной: смена текущего каталога — на весь процесс.
- Stdin у строки пуст: команда, читающая `-`, получает пустой ввод. Потоки
  строки не терминалы: команда, выбирающая вид вывода по терминалу, выводит
  как в канал. Передача stdin клиента — по нужде, отдельной порцией.
- Токен в подпротоколе WebSocket может осесть в журнале прокси, если его
  поставить перед сервером; сейчас прокси нет.
- Токен у WebSocket в подпротоколе — ради браузера (заголовок там не задать);
  как фронт его получает — порция 10.

## Пункты чек-листа

`design.md`:

1. Примитивы — изменил: у сервера два примитива — исполнить строку в канале и
   ответить на запрос; всё остальное (здоровье, схема, снимок) — запросы
   [D.1].
2. Особые случаи → получатели — изменил: канал человека и канал агента — две
   реализации протокола канала `platform/policy.md`, выбранные путём, а не
   флаг в кадре [D.2].
3. Проверка `null` — изменил: клиент без человека — канал «спросить некого»,
   а не отсутствие канала [D.2].
4. Кто решает — изменил: можно ли менять правило — канал, по пути
   подключения; клиент заявить себя человеком на `/agent/line` не может [D.2].
5. Память приватна — ничего: очередь строк держит сервер, снаружи —
   только сокет.
6. Голые данные → протокол — изменил: кадр — данные на границе; внутри —
   объекты строки и канала [D.3].

`design-mpu.md`:

1. Команда — сообщение объекту — ничего: сервер исполняет те же строки.
2. Вид метода — реализация — ничего.
3. Решение политики у владельца — изменил: решение принимает тот же набор
   правил, что у `mpu-next`; сервер только передаёт вопрос [D.4].
4. Один факт — один источник — изменил: итог строки — тот же код, что у
   `mpu-next`, эталон — прогон `mpu-next` в тесте [D.4].
5. Величина из результата — ничего.
6. Права Deno — изменил: слушание петли и запись снимка — новые строки прав
   задачи `back` [D.5].
7. Границы модулей — изменил: сервер — отдельный модуль поверх `next`;
   `next`, `objects`, `policy` о транспорте не знают [D.6].
8. Внешнее ссылкой — изменил: порт, путь токена, путь снимка, каталог
   состояния — параметры [D.5].
9. Голден снятый — изменил: кадры сравниваются с живым `mpu-next` в том же
   тесте [D.4].
10. Пропускаемая проверка — ничего.
