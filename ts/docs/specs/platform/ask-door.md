# Дверь `ask`: строки под подтверждением — отдельным адресом

Статус: реализовано — порция 157 (`ab4955b`); принято 2026-09-22 хостом: гейты зелёные (тестов 2168), голдены справок двери сверены с таблицей, `tools.json` и `frames-clip.json` заморожены. Живая проба (терминал, MCP, правило из web) — после установки, в конце порции 163 (решение владельца: установка по окончании серии).

## Назначение

Строка, которую правила решают `ask` (`platform/policy.md`), вызывается
только через сообщение корню `ask`: `mpu ask sql sl-1 "update …"`. Та же строка
без `ask` отказывает с подсказкой, куда её звать. Строка с решением `allow`
вызывается только без `ask`. Строка с решением `deny` не исполняется ни одним
адресом и не показывается ни в одном списке справки.

Состав двери — живой: он выводится из действующих решений той же книги правил,
а она перед каждым решением сверяется с файлом (`policy.md`, «Хранение»).
Поставил в web (`web.md`) на узле `ask` — со следующей строки узел доступен
только под `ask`; поставил `allow` — ушёл из-под `ask`. Перезапуск `back`,
`mcp` и CLI не нужен.

Зачем: адрес строки сам говорит, что она спросит человека. Агент и человек
видят список таких строк одним вызовом `mpu ask`, а правила разрешений
клиента (`Bash(mpu ask *)`) могут отличать строки с подтверждением от
прочих по тексту команды.

## Термины

- **Взгляд** — как дерево объектов показывается и исполняется с данного
  адреса. Взглядов два: **обычный** (корень `mpu`) и **дверь** (`mpu ask`).
  Дерево, команды, их справки и книга правил у взглядов общие.
- **Действующее решение узла** — то же, что `verdict` в `policy.tree`
  (`web.md`): решение, которое получила бы строка, дошедшая до узла.

## Как устроено

- `ask` — метод корня с видом результата «объект» (`platform/objects.md`).
  Объект — дверь над корнем. Слово, которое дверь понимает, возвращает
  ребёнка того же узла **в том же взгляде**: `mpu ask kiten` — объект `kiten`
  в двери. [D.1]
- Кого понимает взгляд (селекторы, дополнение, «ближайшие» в
  `doesNotUnderstand`), вычисляется на каждой строке по действующим решениям:

  | Узел | Обычный взгляд | Дверь |
  |---|---|---|
  | команда с решением `allow` | понимает | не понимает |
  | команда с решением `ask` | не понимает | понимает |
  | команда с решением `deny` | не понимает | не понимает |
  | группа, которая сама не исполняется (плоская: `kiten`, `code`, `xlsx`) | понимает, если у потомка решение `allow` | понимает, если у потомка решение `ask` |
  | группа, которая исполняется сама (селектор впереди: `ozon-jobs`, `wb-jobs`, …; путь `<группа> <args>`) | понимает, если у неё или у потомка решение `allow` | понимает, если у неё или у потомка решение `ask` |

  Своё решение у плоской группы в расчёт не идёт: правила на ней обычно нет,
  и наследуемое `ask` корня затянуло бы в дверь группу, все дети которой
  `allow` (`code`).

  «Не понимает» в таблице касается **списков** (справка, дополнение,
  «ближайшие»). Исполнение по слову, которого нет в списке, не превращается в
  `не понимает …`: строка доходит до конца и получает отказ с подсказкой по
  таблице исходов ниже. Иначе агент, помнящий старый адрес, не узнает новый.
- **Исход в конце строки** решает пара «решение × взгляд»; решение по-прежнему
  одно, из одной точки для любого канала (`policy.md`, «Инварианты»):

  | Решение | Обычный взгляд (`mpu <путь>`) | Дверь (`mpu ask <путь>`) |
  |---|---|---|
  | `allow` | исполнение | отказ `mpu ask <путь>: вопроса не требует — вызывай mpu <путь>`, код 2 |
  | `ask` | отказ `mpu <путь>: требует подтверждения — вызывай mpu ask <путь>`, код 2 | вопрос каналу, как сегодня; «да» — исполнение |
  | `deny` | отказ `mpu <путь>: запрещено правилом «<путь правила>»`, код 1 | тот же текст (без `ask` в пути), код 1 |

  `<путь>` — текст пути строки без звена `ask` (`objects.md`, «Путь в
  тексте»). Код 2 у двух адресных отказов — ошибка адреса, как у
  `doesNotUnderstand`: ничего не исполнено и не спрошено. Отказы — до вопроса
  каналу и до исполнения. [D.2]
- Вопрос каналу, отказ «не подтверждено», «спросить некого», elicitation в
  MCP — **без изменений**, дословно те же тексты, что давала строка без `ask`
  до этой порции. Дверь вопроса не заменяет и не добавляет. [D.3]
- **Путь правила** строки под дверью — путь без звена `ask`: `mpu ask sql
  sl-1 …` решается правилом пути `sql <args>`. `ask` — не узел дерева
  правил: не сеется, отсутствует в `policy`, `policy.tree` и web; правило
  `deny: "ask"` — правило на пути `ask`, ни на что под дверью не действует.
  Журнал вызовов (`invokelog`) пишет строку как она набрана (со словом `ask`)
  — как сегодня пишет любую строку. [D.4]
- Сообщения корня `policy`, `allow:`, `ask:`, `deny:`, `forget:`, `help`,
  `version`, `web`, `web-logout`, `ask` — только у обычного взгляда. Дверь их не
  понимает: `mpu ask allow: kiten` → `mpu ask: не понимает allow:`. Жёсткий
  запрет изменения правил (`policy.md`) обходного пути не получает. Сообщение
  корня, которое решается правилом (`policy`, `version`), при решении `ask`
  получает обычный адресный отказ и через дверь не вызывается: дверь не
  понимает корневых сообщений. (Следствие: `ask: "policy"` делает `policy`
  недоступным, пока правило не сменят в web или `forget:`.)

## Справка

- `mpu ask`, `mpu ask --help`, `mpu help ask` — справка объекта-двери по форме
  `objects.md` («Текст справки»): `Использование: mpu ask <сообщение>`,
  назначение, текст, раздел «Сообщения» — только то, что дверь понимает
  сейчас, с назначениями узлов.
- Однострока `ask`: `строки, которые спрашивают подтверждение человека`.
  Первый абзац текста (`registry.md`, «Что говорит справка»): звать, когда
  нужна команда, которая пишет или трогает чужое, — под `ask` лежат ровно те
  строки, на которые правила сейчас требуют «да» человека; список живой и
  меняется правилами (`mpu ask:` / `mpu allow:` в терминале или в web), а
  грепом по коду его не получить.
- `mpu ask kiten` — справка `kiten` в двери: только ask-дети.
  `mpu kiten` — справка `kiten` в обычном взгляде: только allow-дети.
- Справка команды не зависит от адреса и правил не спрашивает (`policy.md`,
  «Когда проверяется»): `mpu sql --help` и `mpu ask sql --help` — справка
  `sql`, код 0, вопроса нет. Строка `Использование:` у справки объекта
  несёт путь того взгляда, в котором её запросили.
- Справка корня: строка `ask` в «Сообщениях» есть всегда (даже если дверь
  пуста); команды с решением `ask` и `deny` в корне не перечислены.

## MCP

Список тулов не меняется (`help`, `mpu`). Дверь — те же слова:
`{"words": ["ask", "sql", "sl-1", "update …"]}`, `help` с
`{"path": ["ask"]}`. Описание тула `mpu` дополняется одной фразой: строки,
требующие подтверждения человека, начинаются словом `ask`, их список —
`help` с `path: ["ask"]`. Ограничение 2048 байт в силе. Голден
`fixtures/mcp-objects/tools.json` меняется: составляет исполнитель,
замораживает хост при приёмке.

## Дополнение

`complete` строится из снимка дерева (`complete.md`), а снимок решений не
знает. В этой порции дополнение не меняется: `mpu ask <Tab>` может не
предлагать ничего. Дополнение по взглядам — отдельная порция.

## Инварианты

- Строка с решением `ask` исполняется только через дверь и только после «да»
  канала.
- Строка с решением `allow` исполняется только без двери.
- Строка с решением `deny` не исполняется ни одним адресом, вопроса не
  задаёт и ни в одном списке справки не показывается.
- Состав двери и обычного взгляда — функция действующих решений в момент
  строки; изменение правила любым процессом (терминал, web) действует на
  следующую строку любого процесса.
- Дверь не меняет ни пути правила, ни текста вопроса, ни дерева
  `policy.tree`.
- Имя `ask` не совпадает ни с одной командой верхнего уровня реестра —
  проверяется тестом (к списку `policy.md`).

## Граничные случаи и ошибки

Правила по умолчанию — посев (`policy.md`); в строках — нужные решения.

| Дано | Ожидается |
|---|---|
| `sql` — `ask`; `mpu sql sl-1 "select 1"` | stderr `mpu sql sl-1 select 1: требует подтверждения — вызывай mpu ask sql sl-1 select 1`, код 2; вопроса нет, запроса к БД нет |
| `sql` — `ask`; `mpu ask sql sl-1 "select 1"` из терминала, ответ `y` | вопрос `выполнить mpu sql sl-1 select 1? [y/N] ` (как сегодня), затем итог `sql` |
| то же, ответ `n` | `mpu sql sl-1 select 1: не подтверждено`, код 1 (как сегодня) |
| то же без tty | `… спросить некого`, код 1 (как сегодня) |
| `sql-ro` — `allow`; `mpu ask sql-ro sl-1 "select 1"` | `mpu ask sql-ro sl-1 select 1: вопроса не требует — вызывай mpu sql-ro sl-1 select 1`, код 2 |
| `sql-ro` — `allow`; `mpu sql-ro sl-1 "select 1"` | исполнение, как сегодня |
| `deny: "kiten close"`; `mpu kiten close 1` и `mpu ask kiten close 1` | оба: `mpu kiten close 1: запрещено правилом «kiten close»`, код 1; вопроса нет |
| `deny: "kiten close"`; `mpu kiten --help`, `mpu ask kiten --help` | `close` нет ни в одном разделе «Сообщения» |
| `mpu ask` при посеве | справка двери; в «Сообщениях» есть `sql`, `kiten`, `ozon-jobs`; нет `sql-ro`, `ps`, `log`, `code` |
| `mpu ask kiten` при посеве | «Сообщения» — `checklist`, `close`, `comment`, `field`, `move`, `ready`, `review`, `time`; нет `ls`, `card`, `boards` |
| `mpu kiten` при посеве | нет `close`, `comment`, `move`, `ready`, `review`; есть `ls`, `card`, `checklist`, `time` (у них есть allow-дети) |
| `ask: "kiten ls"`, затем `mpu kiten ls` | `mpu kiten ls: требует подтверждения — вызывай mpu ask kiten ls`, код 2 |
| то же, затем `mpu ask kiten ls` | вопрос → исполнение |
| то же, затем `allow: "kiten ls"` (или `allow` в web), затем `mpu kiten ls` | исполнение; `mpu ask kiten ls` — адресный отказ |
| то же, затем `forget: "kiten ls"` | посеянный путь заново не сеется (`policy.md`): решение — наследуемое `ask`, `mpu kiten ls` — адресный отказ |
| процесс `back` работает; правило изменено из web; следующая строка через MCP | новое решение, без перезапуска |
| `mpu ask ask sql …` | `mpu ask: не понимает ask; ближайшие: …`, код 2 |
| `mpu ask allow: kiten` | `mpu ask: не понимает allow:`, код 2; правило не изменено, вопроса нет |
| `mpu ask kitn` | `mpu ask: не понимает kitn; ближайшие: kiten`, код 2 |
| `mpu ask:` `"kiten ls"` | как сегодня: правило, вопрос изменения |
| `mpu ask sql --help` и `mpu sql --help` | справка `sql`, код 0, вопроса нет |
| `mpu ask ozon-jobs sl-2 show` (`ozon-jobs` — `ask`) | вопрос → исполнение; правило — путь `ozon-jobs <args>` |
| `mpu ask` при посеве | `code` нет (все дети `allow`) |
| MCP `mpu` `["sql", "sl-1", "select 1"]` | `isError`, stderr с подсказкой `вызывай mpu ask sql …`, elicitation нет |
| MCP `mpu` `["ask", "sql", "sl-1", "select 1"]`, accept | исполнение, как сегодня без `ask` |
| `policy.tree` после любой строки через дверь | без узла `ask`; как до порции |
| `deny: "ask"` | правило на пути `ask`; `mpu ask sql …` решается правилом `sql` |

Тексты `<путь>` в таблице — по правилу «Путь в тексте»; точное написание
значения с пробелами берётся оттуда, таблица показывает звенья.

## Golden-примеры

- `fixtures/mcp-objects/tools.json` — перезамораживается (описание `mpu`).
- Справки двери и `kiten` в двух взглядах — снимает исполнитель прогоном на
  посеве во временном `HOME`, хост сверяет с таблицей выше.

## Известные отклонения

- Дополнение (`complete`) взглядов не различает — отдельная порция.
- Документы вне `ts/` (правила агентов, навыки) вызывают `mpu sql`, `mpu kiten
  comment` без двери; после порции такие вызовы получают адресный отказ с
  подсказкой. Обновление документов — за хостом после приёмки.

## Пункты чек-листа

`design.md`:

1. Примитивы — изменил: у взгляда два примитива — «понимаю ли я узел с
   этим действующим решением» и «исход для решения в конце строки»;
   справка, «ближайшие», отказы выводятся из них [D.1].
2. Особые случаи → получатели — изменил: взгляд — две реализации одного
   протокола (обычный, дверь); исход — двойная диспетчеризация «решение
   спрашивает взгляд» (`allow` → `onAllow` взгляда и т. д.), не ветка по
   флагу «пришла через дверь» в `Ruling.settle` / `Report` [D.2].
3. Проверка `null` — ничего нового: «нет правила» уже null-объект «наследуемое
   правило» (`policy.md` [D.4]); отсутствующего взгляда нет — корень всегда
   обычный.
4. Кто решает — изменил: исполнять ли — решение правил; где исполнять —
   взгляд; вопрос — канал, как прежде [D.2], [D.3].
5. Память приватна — изменил: взгляд не хранит список своих команд, спрашивает
   книгу правил на каждой строке [D.1].
6. Голые данные → протокол — изменил: «через дверь / без» — объект-взгляд, не
   булево поле строки [D.2].

`design-mpu.md`:

1. Команда — сообщение объекту — изменил: `ask` — метод корня с результатом
   «объект» [D.1].
2. Вид метода — реализация, не флаг — изменил: «под подтверждением» —
   действующее решение правил, а не признак команды; адрес — взгляд [D.2].
3. Решение политики у владельца — изменил: взгляд решения не вычисляет, берёт
   у книги (как `policy.tree`) [D.1].
4. Один факт — один источник — изменил: принадлежность двери — только
   действующее решение; строка «Использование», списки справки, отказы
   выводятся из него [D.1].
5. Величина из результата — ничего: печатаемых чисел нет.
6. Права Deno — ничего: новых ресурсов нет.
7. Границы модулей — изменил: взгляды — рядом с мостом правил (модуль
   `line`), `objects`/`policy` о двери не знают [D.2].
8. Внешнее ссылкой — ничего нового: канал и файл правил уже переданы.
9. Голден снятый — изменил: `tools.json` и справки — снятые прогоном [D.5].
10. Пропускаемая проверка — ничего.

`statement-mpu.md` п. 3: список публикации `fixtures/mcp-server/tool-policies.json`
относится к прежнему MCP-серверу; новый переводчик (`mcp-objects.md`) публикует
два тула и видимость решает правилами — новых записей в список не нужно.

[D.1] Взгляд вычисляет состав по книге. [D.2] Исход — пара «решение ×
взгляд». [D.3] Вопрос без изменений. [D.4] Путь правила без `ask`.
[D.5] Голдены снятые.
