# Вопросы владельцу в Telegram

Статус: черновик (серия R, порция R1; постановка —
`telegram-relay-statement.md`, её сценарии здесь — `[S.n]`)

## Назначение

Ядро `mpu-back` получает возможность задать владельцу вопрос в его чате с
ботом и дождаться ответа кнопкой или текстом. Первый потребитель —
`claude-hook-permission-request.md`; следующие порции серии (R2–R4) задают
вопросы того же вида, не меняя ни отрисовки, ни приёма ответов. Поэтому всё
ниже говорит о **форме вопроса**, а не о видах вопросов Claude Code.

Чат с ботом тот же, что у `telegram log` (Bot API, `TELEGRAM_BOT_TOKEN`,
адресат `TELEGRAM_BOT_ID`).

## Форма вопроса и исход

Форма — то, что потребитель передаёт ядру; ядро ничего не знает о том, откуда
вопрос. Части формы:

| Часть | Что это | Пример |
|---|---|---|
| заголовок | одна строка, первая в сообщении | `🔐 Bash · ozon · w:2 claude` |
| шаги | 1–4 шага; у каждого — текст, варианты, вид выбора | AskUserQuestion с двумя вопросами — два шага |
| текст шага | строки тела под заголовком | `Create probe file` / `touch /tmp/x1.txt` |
| вариант | подпись кнопки, ≤ 60 символов после обрезки | `Yes, always: Bash(touch /tmp/x1.txt)` |
| вид выбора | один вариант / несколько (галочки и `Готово`) | `multiSelect: true` — несколько |
| свой текст | принимается ли текст владельца как ответ шага | право — да (пояснение отказа), AskUserQuestion — да |

Исход вопроса — ровно один из:

- **ответ** — по каждому шагу: номер выбранного варианта, набор номеров
  (несколько) либо текст владельца; ядро отдаёт его потребителю целиком после
  последнего шага [S12];
- **снят** — потребитель сам сообщил, что вопрос решён в другом месте
  (`решено в терминале` — текст снятия даёт потребитель);
- **истёк** — потребитель отключился (обрыв строки), вышел срок ожидания
  потребителя, или ядро перезапущено, пока сообщение было в чате.

Подпись варианта длиннее 60 символов обрезается до 59 и `…`; номер варианта
при этом тот же. Подписи и тексты — данные формы: новый вид вопроса не требует
изменений здесь (инвариант постановки §3).

## Порядок вопросов [S13–S15]

- Ожидающие вопросы образуют один ряд по времени прихода, общий для всех
  потребителей и сессий.
- В чате действующие кнопки есть ровно у одного сообщения — у вопроса,
  пришедшего раньше всех из ещё не решённых.
- Под текстом активного вопроса — строка `ещё ждут: N`, где N — число
  остальных ожидающих; при N = 0 строки нет. N меняется правкой того же
  сообщения при каждом приходе и уходе ожидающего.
- После исхода активного вопроса следующий в ряду отправляется **новым**
  сообщением (чтобы телефон уведомил), а не правкой.
- Ожидающий, не показанный ещё вопрос, снятый или истёкший, из ряда уходит
  молча: в чат по нему ничего не отправляется [S14].

## Сообщение

Текст сообщения активного вопроса, построчно:

```
<заголовок>[ <k>/<n>, если шагов больше одного, после первого слова-значка и имени]
<текст шага>
[• <подпись> — <описание>   — по строке на вариант, если у вариантов есть описания]
[ещё ждут: N]
```

Кнопки — по одной на вариант, по две в ряд; у вида «несколько» подпись
начинается с `☐ ` или `☑ `, последней отдельным рядом — `Готово`. Отметка
варианта правит кнопки того же сообщения, ответа ещё нет [S10]. `Готово` без
отмеченных — подсказка `отметьте хотя бы один вариант`, вопрос остаётся.

После исхода сообщение правится: кнопки сняты, последней строкой дописан
исход, строка `ещё ждут` убрана:

| Исход | Последняя строка |
|---|---|
| ответ кнопкой | `✅ <подпись> — из чата` (несколько — подписи через `, `) |
| ответ текстом | `✅ <текст> — из чата`; потребитель может задать свою строку (право: `❌ No: <текст> — из чата`) |
| снят | `✅ <текст снятия>` (`✅ решено в терминале`) |
| истёк | `⌛ истёк — ответьте в терминале` |

Значок и текст строки ответа задаёт потребитель вместе с формой (у права
`No` — `❌`); умолчание — `✅`.

Длина текста сообщения — не больше 4096 (единица — кодовые единицы UTF-16,
как у `telegram log`): длиннее — усекается текст шага, строки вариантов,
заголовок и строка `ещё ждут` не усекаются.

## Ответы владельца

- **Кнопка.** Нажатие подтверждается Telegram'у сразу, до любого другого
  действия (`answerCallbackQuery`): подтверждение, отправленное позже срока,
  Telegram отвергает — `400 Bad Request: query is too old and response timeout
  expired or query ID is invalid` (голден `bot-api/answerCallbackQuery-too-old.json`),
  а у владельца кнопка «не реагирует». Подсказка подтверждения пуста при
  принятом нажатии и несёт текст при отвергнутом (ниже).
- **Текст.** Обычное сообщение владельца боту (reply не нужен) — ответ
  активному вопросу на его текущем шаге, если у шага «свой текст — да»
  [S5, S11]. Нет активного вопроса — бот отвечает `сейчас вопросов нет`. Шаг без
  своего текста — бот отвечает `ответьте кнопкой`.
- **Нажатие не активного вопроса** (кнопка старого сообщения, повторная
  доставка того же нажатия) — ничего не решает, подсказка
  `вопрос уже решён` [S7].
- **Не владелец** (`from.id` ≠ `TELEGRAM_BOT_ID`) — ничего не решает;
  на нажатие подсказка `не ваш вопрос`, на текст — молчание [S19].

Кнопка несёт в себе метку запуска ядра и номер вопроса: нажатие кнопки,
отправленной до перезапуска ядра, — «вопрос уже решён». Метка, номер и номер
варианта вмещаются в 64 байта (предел Telegram на данные кнопки).

## Приём апдейтов

- Пока у конфигурации есть `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_ID`, ядро
  постоянно ждёт апдейтов бота долгим опросом `getUpdates` (`timeout` 25 с,
  `allowed_updates` — `message`, `callback_query`), каждый апдейт
  подтверждается следующим `offset`. Ключей нет — опроса нет, вопросы
  отвечаются отказом «бот не настроен» (см. «Ошибки»).
- Апдейты, полученные первым опросом после старта ядра и датированные раньше
  старта, отбрасываются без действия: накопленное до запуска — не ответы.
- Сбой опроса (сеть, 5xx, 409 — второй читатель того же бота) не роняет ядро:
  следующая попытка через 5 с; при 409 в журнал службы — одна строка
  `telegram: у бота другой читатель (409)` на серию отказов.
- Живые формы апдейтов — `bot-api/getUpdates-callbacks-and-text.json` (пять
  нажатий и одно текстовое сообщение; id и имена обезличены).

## Перезапуск

Сообщения с действующими кнопками переживают процесс ядра в кэш-БД
(`platform/store.md`; новая таблица — миграцией, без правки замороженного
прежде эталона). При старте ядро правит каждое такое сообщение в исход
«истёк» и забывает его [S17]. Ряд ожидающих при этом пуст: их потребители —
строки, оборвавшиеся вместе с ядром.

## Ошибки

Вопрос не удалось показать — потребитель получает отказ с причиной, и ни одно
сообщение в чате кнопок по нему не держит:

| Случай | Причина отказа |
|---|---|
| нет `TELEGRAM_BOT_TOKEN` или `TELEGRAM_BOT_ID` | `бот не настроен` |
| сеть, прокси, срок вызова | `бот недоступен: <первая строка ошибки транспорта>` |
| ответ Bot API `ok: false` | `бот недоступен: <error_code> <description>` |

Токен не появляется ни в причине, ни в журнале службы: адрес вызова с токеном
в текст ошибки не попадает (как у `telegram log`).

Сбой правки уже показанного сообщения (`editMessageText`) исход не меняет:
исход доставлен потребителю, неудача правки пишется строкой в журнал службы.

## Стык Bot API

Методы и формы — дословно по голденам `fixtures/telegram-relay/bot-api/`:

| Метод | Когда | Голден |
|---|---|---|
| `sendMessage` + `reply_markup.inline_keyboard` | показ вопроса | `sendMessage.json` |
| `editMessageText` (с `reply_markup` или без) | отметка, счётчик, исход | `editMessageText.json` |
| `answerCallbackQuery` | каждое нажатие | `answerCallbackQuery-too-old.json` (отказ); успех — `{"ok":true,"result":true}`, **догадка**, снять при приёмке |
| `getUpdates` | опрос | `getUpdates-callbacks-and-text.json` |
| `sendMessage` без кнопок | `сейчас вопросов нет`, `ответьте кнопкой` | как `sendMessage.json` |

Транспорт, прокси и пределы времени вызова — как у `telegram log`
(`telegram-log.md`, «Конфигурация»); у долгого опроса предел вызова —
`timeout` опроса плюс 10 с.

## Инварианты

- У вопроса ровно один исход; второй (нажатие после снятия, повтор апдейта)
  ничего не меняет.
- Решить вопрос может только владелец.
- В чате не больше одного сообщения с действующими кнопками.
- Ожидание вопроса не занимает исполнителя строк (`line-executor.md`).
- Токен не появляется ни в одной поверхности.

## Открытые вопросы

- Успешный ответ `answerCallbackQuery` не снят (в пробе подтверждение
  опоздало) — снять при приёмке; до того голден помечен догадкой.
