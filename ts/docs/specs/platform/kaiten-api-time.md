# platform/kaiten-api-time — учёт времени и таймеры Kaiten

Статус: черновик

## Назначение

Каталог внешнего API Kaiten для учёта времени и личных таймеров: девять
вызовов — записи времени карточки, записи пользователя за окно, жизненный цикл
личного таймера и справочник ролей («типов работ»). Резолв аргументов, рендер и
локальное хранилище сюда не входят — это дело командных спек.

Слой каталога — порт к внешней системе: полнота порта — требование, а не
спекулятивная гибкость. Вызов без вызывающего кода в первой волне команд —
норма для этого слоя.

## Ввод/вывод

Транспорт общий (`platform/kaiten-http.md`): подстановка пути, заголовки,
обработка не-2xx, ретрай 429. Ниже — только специфика каждого вызова.

### 1. GET /cards/{card_id}/time-logs

Записи учёта времени карточки, всех пользователей карточки, а не только
текущего. Query и тело запроса — нет. Пагинации нет — полный список одним
ответом.

Ответ — массив объектов: `id` (число, id записи), `card_id` (число),
`user_id` и `author_id` (число или `null`), `role_id` (число или `null`),
`role_name` (строка или `null` — сервер несёт вложенный объект `role`,
значимо только его `name`), `user_name` (строка или `null` — сервер несёт
вложенный объект `user`/`author` с base64-аватаркой, значимо только
отображаемое имя, сам объект не входит в форму ответа), `time_spent` (целое
число — списанная длительность **в минутах**), `for_date` (строка
`YYYY-MM-DD` — календарный день записи), `comment` (строка, `""` если
комментарий отсутствует). Ошибок сверх общих нет.

### 2. POST /cards/{card_id}/time-logs

Создать запись времени. Тело — все четыре поля:
- `for_date` (строка `YYYY-MM-DD`, обязательно);
- `time_spent` (целое число, минуты, обязательно);
- `role_id` (число, обязательно);
- `comment` (строка; пустая строка, если без комментария).

Ответ — форма вызова 1: созданная запись со своим `id`. Неочевидности:
`time_spent` — минуты, не часы и не секунды; `for_date` в ответе на POST и на
PATCH (вызов 3) приходит полной ISO-меткой (`2026-07-20T00:00:00.000Z`), а не
чистой датой, как в ответе GET (вызов 1) — значим только календарный день.
Ошибок сверх общих нет.

### 3. PATCH /cards/{card_id}/time-logs/{log_id}

Частичное обновление. Тело — любое непустое подмножество `time_spent`,
`for_date`, `role_id`, `comment`: заданы только меняющиеся поля, остальные не
трогаются. Пустая строка в `comment` очищает комментарий — сервер
нормализует её в `null`, последующее чтение снова отдаёт `""`. Ответ — форма
вызова 1 целиком, включая не изменившиеся поля. Ошибок сверх общих нет.

### 4. DELETE /cards/{card_id}/time-logs/{log_id}

Удалить запись. Тело запроса и ответа нет — успех подтверждается статусом
2xx с пустым телом. Ошибок сверх общих нет.

### 5. GET /users/{user_id}/time-logs

Записи пользователя за окно времени по всем карточкам, где он списывал время —
включая карточки без его членства. Query: `from`, `to` — обе строки
**обязательны и передаются всегда**; без них сервер отвечает 500 вместо «за
всё время». Пагинации нет — объём ответа режется только шириной окна.

Ответ — массив объектов формы вызова 1 плюс поле `card`: вложенная карточка
целиком или `null`, все поля опциональны — `id`, `title`, `state`,
`condition`, `due_date`, `updated`, `board_id`, `column_id`, `lane_id`,
`archived` (булево), `last_moved_at`, `time_spent_sum` (число или `null` —
сумма минут по карточке ВСЕМИ участниками, не только этим пользователем),
`board_title`, `space_title`, `column_title`, `lane_title`, `type_name`.
Неочевидность: запрос без `from`/`to` возвращает HTTP 500 в общем формате
ошибки транспорта — квирк валидации параметров сервером, не отдельный код
обработки.

### 6. POST /user-timers

Запустить личный таймер на карточке. Тело: `card_id` (число, обязательно),
`comment` (строка, необязательно — ключ отсутствует в теле, если комментарий
не задан). Роль в теле передавать бессмысленно: API принимает `role_id`, но
не сохраняет его — тип работы выбирается только при остановке (вызов 7).

Ответ — одна из двух форм, различаемых **по составу тела, не по
HTTP-статусу**: успех — объект таймера (`id` число, `card_id`, `card_title`
строка, `comment` строка, `started_at` строка ISO 8601, `finished_at` `null`,
`card_time_log_id` `null`); конфликт (у пользователя уже есть таймер на
карточке, названной в `card_id`) — тело `{"message": "User timer already
created"}`, **без поля `id`**, статус не обязательно не-2xx. Случай «таймер
идёт на другой карточке» — см. «Открытые вопросы». Ветвление — по наличию
`id` в разобранном JSON, не по статусу.

### 7. PATCH /user-timers/{timer_id}

Остановить таймер; сервер создаёт запись учёта времени. Тело: `finished_at`
(строка ISO 8601, **обязательно**), `started_at` (строка, опционально —
переопределяет фактическое время старта), `comment` (строка, опционально),
`role_id` (число, опционально — здесь роль впервые применяется и
сохраняется).

Метки времени — ISO 8601 в часовом поясе момента старта таймера, миллисекунды
всегда `.000`. Длительность записи сервер считает как
`finished_at − started_at`, округляя результат **вверх** до целой минуты.
Ответ — объект таймера (форма вызова 6) с заполненным `finished_at` и
`card_time_log_id` (число — id созданной записи времени). Неочевидности:
запрос без обеих меток времени отвечает 500; `finished_at: null` отвечает
400.

### 8. DELETE /user-timers/{timer_id}

Сбросить таймер **без** создания записи учёта времени — в отличие от вызова 7.
Тело запроса и ответа нет. Ошибок сверх общих нет.

### 9. GET /user-roles

Роли компании — «типы работ», используемые как `role_id` в вызовах 2, 3, 7.
Query и тело — нет. Ответ — массив `{id: число, name: строка}`. Пагинации нет.

## Побочные эффекты

Мутирующие вызовы (2, 3, 4, 6, 7, 8) создают, изменяют или удаляют состояние в
Kaiten — записи учёта времени и личные таймеры. Локального состояния (кэш,
журнал, SQLite) каталог не ведёт и не читает; вся история — только на сервере
Kaiten.

## Инварианты

- `time_spent` во всех формах записи — целое число **минут**; секунды и часы
  каталог не использует.
- `for_date` значим только как календарный день — час, минута и часовой пояс
  внутри значения не несут смысла.
- Личный таймер не хранится своим списком: единственный способ узнать про
  идущий таймер — поле `timer` ответа `GET /cards/{card_id}` (вызов другого
  каталога) либо тело, которое возвращают вызовы 6 и 7 этого каталога;
  отдельного списка запущенных таймеров в API нет.
- Комментарий таймера хранится на сервере и переживает вызовы каталога; роль
  таймера — нет: `role_id`, переданный в вызове 6, не сохраняется, тип работы
  фиксируется только вызовом 7.
- Роль записи времени (вызовы 2, 3, 7) — целое число `role_id`; резолв
  названия роли в число каталогу не принадлежит.

## Граничные случаи и ошибки

- `GET /users/{id}/time-logs` без `from`/`to` → HTTP 500 в общем формате
  ошибки транспорта.
- `POST /user-timers` на карточке с уже идущим личным таймером → тело
  `{"message": "User timer already created"}` без `id`; HTTP-статус не
  обязательно не-2xx.
- `PATCH /user-timers/{id}` без `finished_at` и без `started_at` → HTTP 500.
- `PATCH /user-timers/{id}` с `finished_at: null` → HTTP 400.
- `PATCH /cards/{id}/time-logs/{log}` с `comment: ""` → успех; сервер
  нормализует пустую строку в `null`, последующий `GET` отдаёт `""`.
- Округление длительности вверх до минуты выполняет только вызов 7 (по разнице
  меток времени); вызовы 2 и 3 записывают `time_spent` как передано.

## Golden-примеры

Пары «запрос → ответ» на синтетических данных, по одной на класс:

- **успех** — вызов 2 (`POST /cards/{id}/time-logs`): тело с четырьмя полями
  → созданная запись со своим `id`.
- **успех** — вызов 7 (`PATCH /user-timers/{id}`): `started_at`/`finished_at`
  с разницей, не кратной минуте → ответ с `time_spent` округлённым вверх.
- **ошибка** — вызов 5 без `from`/`to` → HTTP 500.
- **ошибка** — вызов 7 без `finished_at` → HTTP 500.
- **граница** — вызов 6 на карточке с уже идущим таймером → тело без `id`.
- **граница** — вызов 3 с `comment: ""` → ответ с `comment: ""`, несмотря на
  внутреннюю нормализацию сервера в `null`.

## Открытые вопросы

- Поведение `POST /user-timers`, когда у пользователя уже идёт таймер на
  **другой** карточке (не на той, что указана в `card_id`): из наблюдаемого
  поведения не выведено, вернёт ли сервер ту же форму-конфликт без `id` или
  какую-то ещё. Закрывается прямым пробным вызовом на синтетической тестовой
  карточке до перевода этой спеки в статус «к реализации»; предположением не
  закрывается.
