# Контекст вызова: stdin, терминал и окружение клиента

Статус: к реализации (порция 11 переключения).

## Назначение

Сейчас строка исполняется в окружении сервера: stdin пуст, потоки не
терминалы, переменные клиента не видны (`platform/back-rpc.md`, «Известные
отклонения»). Из-за этого тонким клиентом нельзя заменить старый `mpu`: не
работают `-F -` и прочее чтение `-`, таблицы верстаются под чужую ширину, цвет
выбирается не по терминалу человека.

Порция закрывает три пробела разом: **что подал клиент на вход**, **какой у
него терминал**, **какие переменные окружения он принёс**. Потоковый ввод и
вывод, отмена и интерактивный ввод пароля — следующие порции переключения, их
здесь нет.

## Контракт первого кадра

Первый кадр строки (`platform/back-rpc.md`, «Кадры»; то же тело у `POST /line`,
`platform/back-http-line.md`) получает три необязательных поля:

```json
{"words": ["kiten", "comment", "123", "-F", "-"],
 "cwd": "/home/user/mr/mp",
 "human": true,
 "stdin": "текст сообщения\n",
 "tty": {"stdin": false, "stdout": true, "stderr": true, "columns": 120},
 "env": {"COLUMNS": "120", "NO_COLOR": "1"}}
```

- `stdin` — весь ввод строкой; поля нет — ввода нет (как сегодня).
- `tty` — терминальность трёх потоков у клиента и ширина его консоли.
  Поля нет — все три `false`, ширины нет (как сегодня). `columns`
  необязателен и только при `stdout: true`.
- `env` — переменные окружения клиента; поля нет — окружение сервера как есть.

Поля независимы: любое можно прислать без остальных.

## Что видит исполняемая строка

| Что спрашивает команда | Откуда берёт |
|---|---|
| чтение `-` (весь stdin) | `stdin` кадра; поля нет — пустой ввод, конец сразу |
| повторное чтение `-` в той же строке | то же содержимое: ввод — значение, а не поток с позицией |
| «stdin/stdout/stderr — терминал?» | `tty` кадра, а не файловые дескрипторы сервера |
| ширина консоли | `tty.columns`; его нет — ширины нет (вывод без ограничения) |
| переменная окружения | `env` кадра, а при отсутствии имени там — окружение сервера |

`env` действует **только на свою строку**: окружение процесса сервера не
меняется, соседняя строка чужих переменных не видит. Переменные сервера,
которых нет в `env`, остаются видны — иначе строка потеряет доступ к
конфигурации службы.

## Вопрос подтверждения: контекст живёт до конца строки

У WebSocket контекст лежит в открытом сокете. У `POST /line` вопрос уходит
номером, а ответ приходит **другим** запросом (`…/answer`,
`platform/back-http-line.md`), и тело ответа несёт только номер и `y`/`n`.
Поэтому контекст вызова хранится **рядом с номером**, как и сама строка:
исполнение после подтверждения видит тот же `stdin`, ту же терминальность и
те же переменные, что пришли первым запросом. Контекст в `…/answer` не
принимается: поля `stdin`, `tty`, `env` там — отказ как у плохого тела.

## Какие переменные принимаются

Закрытый список — подмножество имён, которые читает сам `mpu` (`deno.jsonc`,
права задачи `back`):

```
COLUMNS NO_COLOR TERM TERM_PROGRAM COLORTERM TMUX WT_SESSION OS
```

Список — только про **вид вывода**. Всё, что меняет, куда строка пойдёт и
откуда возьмёт состояние, не принимается:

- `HOME`, `XDG_CONFIG_HOME` — каталоги токенов, кэш-БД и журнала вызовов;
- `PG*` (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`) — цель
  подключения к базе. Команда выбирает базу селектором, и правило
  подтверждения решается по словам строки; принятая от клиента `PGHOST`
  увела бы ту же самую разрешённую строку в другую базу, не изменив ни одного
  слова. Это прямо противоречит правилу «пишущее проверяем на локальном
  стенде, не в проде» (`ts/CLAUDE.md`). Понадобится — отдельным решением
  владельца, с названным способом отличить локальный стенд от боевого.

Имя вне списка — отказ, а не молчаливый пропуск (ниже, «Граничные случаи»).

## Предел размера ввода

`stdin` больше **8 МиБ** (в байтах UTF-8) — отказ с кодом 2; потоковый ввод —
следующая порция. Предел проверяется до исполнения строки.

## Сторона клиента

`mpu-next` (`cli-client.md`) заполняет поля сам:

- `stdin` — читает свой stdin **целиком, только если это не терминал**; stdin
  терминал — поле не отправляется (иначе клиент повис бы, ожидая ввод, которого
  никто не даёт);
- `tty` — `Deno.stdin.isTerminal()` и то же для двух других потоков;
  `columns` — из `Deno.consoleSize()`, когда stdout терминал;
- `env` — имена из списка выше, которые есть у клиента.

Клиент читает stdin до конца **до** отправки первого кадра. Ввод больше предела
— клиент не шлёт ничего и печатает в stderr `mpu-next: ввод больше 8 МиБ`,
код 2.

## Инварианты

- Первый кадр без новых полей ведёт себя ровно как до порции: пустой ввод,
  потоки не терминалы, окружение сервера. Прежние клиенты (`mcp`, `curl`,
  фронт) не меняются.
- `env` строки не переживает строку: следующая строка видит окружение сервера.
- Каталоги состояния (токены, кэш-БД, журнал вызовов) не зависят ни от одного
  поля кадра.
- Итог строки с контекстом равен итогу той же команды у старого `mpu`,
  запущенного с тем же stdin, тем же терминалом и теми же переменными: те же
  байты stdout и stderr, тот же код.
- Ни ввод, ни **значения** `env` не попадают в журнал вызовов и в сообщения об
  ошибках: в них бывают тексты комментариев и секреты. В отказе по имени вне
  списка печатаются только имена.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| `stdin` — не строка | `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}` |
| `stdin` 8 МиБ + 1 байт | `{"err": "mpu-back: ввод больше 8 МиБ\n"}`, `{"exit": 2}` |
| `stdin` пустая строка | ввод есть и он пуст (чтение `-` даёт пустое значение) |
| поля `stdin` нет, команда читает `-` | как сегодня: пустой ввод |
| `tty` не объект или поле не булево | `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}` |
| `tty.columns` не целое от 1 до 10000 | то же (предел — параметр, не литерал по коду) |
| `tty.columns` при `stdout: false` | `{"err": "mpu-back: ширина без терминала\n"}`, `{"exit": 2}` |
| `env` с именем вне списка | `{"err": "mpu-back: переменная вне списка: HOME\n"}`, `{"exit": 2}` (имена через запятую, в порядке прихода) |
| `env` со значением не строкой | `{"err": "mpu-back: плохой кадр строки\n"}`, `{"exit": 2}` |
| `env` пустой объект | как отсутствие поля |
| `PGHOST` или `PGPASSWORD` в `env` | `{"err": "mpu-back: переменная вне списка: PGHOST\n"}`, `{"exit": 2}` |
| строка А с `env`, следом строка Б без него | Б видит окружение сервера |
| команда читает `-` дважды в одной строке | оба чтения дают то же содержимое |
| `POST /line/answer` с полем `stdin`, `tty` или `env` | 400, тело как у плохого тела запроса |
| строка через `POST /line` с `stdin`, подтверждённая номером | исполнение видит тот же `stdin` |
| `mpu-next … -F -` из пайпа | текст пайпа доходит до команды |
| `mpu-next … -F -` с терминала | поля `stdin` нет, команда получает пустой ввод |
| `mpu-next` в пайпе (stdout не терминал) | `tty.stdout: false`, `columns` не отправляется |

## Golden-примеры

`fixtures/call-context/`:

- `frames-stdin.json` — кадры строки, читающей `-`: первый кадр с `stdin`,
  ответ команды;
- `frames-env-reject.json` — отказ на имя вне списка;
- `pairs.json` — пары «старый `mpu` / строка с контекстом» на одних и тех же

  читающей `-`. Эталон снимает исполнитель прогоном обеих сторон, хост
  замораживает при приёмке.

в `testdata` модуля обязана совпасть с каналом.

## Известные отклонения

- Ввод передаётся целиком, а не потоком: команда, которой нужен
  бесконечный ввод, этой порцией не поддерживается.
- Повторное чтение `-` даёт то же содержимое, а у старого `mpu` второе чтение
  того же дескриптора давало пустоту. Вердикт — **fix**: ввод строки
  описывается значением, и команда, читающая его дважды, ведёт себя
  одинаково оба раза.
- Буфер обмена (`OSC 52`, `wl-copy`) остаётся на стороне сервера и в терминал
  клиента не попадает — следующая порция.

## Пункты чек-листа

`design.md`:

1. Примитивы — изменил: один примитив — «описание вызывающего», из которого
   строка берёт ввод, терминальность и переменные [D.1].
2. Особые случаи → получатели — изменил: «ввод есть» и «ввода нет» — две
   реализации ввода строки, а не проверка поля на каждом чтении; так же и
   окружение: «правило клиента» и «правило сервера» — две реализации чтения
   переменной, а не `if (имя в env)` у каждого потребителя [D.2].
3. Проверка `null` — изменил: отсутствие `tty` — описание «не терминал»
   (null-объект), не `undefined` в полях [D.1].
4. Кто решает — изменил: терминальность и ширину решает клиент; сервер их не
   вычисляет и своими дескрипторами не подменяет [D.3].
5. Память приватна — изменил: контекст живёт ровно одну строку и наружу не
   виден [D.4].
6. Голые данные → протокол — изменил: `env` — не мешок строк, а список
   разрешённых имён со своим отказом [D.5].

7. Границы модулей — изменил: контекст разбирается на границе кадра и дальше

8. Внешнее ссылкой — изменил: предел ввода — параметр, не литерал по коду

9. Голден снятый — изменил: пары снимаются прогоном обеих сторон [D.7].
