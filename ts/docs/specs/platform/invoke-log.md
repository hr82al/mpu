# platform/invoke-log — журнал вызовов

Статус: черновик (адаптирована 2026-08-04 под один бинарь: журнал снова
локальный, формат записей оригинала восстановлен дословно — включая
`pid=`/`cwd=`)

## Назначение

Каждое исполнение команды — маршрут `native` или `legacy`, включая
завершившееся ошибкой, — оставляет ровно одну запись: что запускали,
вывод, ошибки, код, длительность. Журнал — память оператора («что я уже
прогонял и почему упало») и источник частот. Обе точки входа бинаря
журналируются: CLI-вызов и вызов тула MCP-сервером — это вызовы одних и
тех же команд. Реестровые поверхности — справка, `version`, completion,
ошибки маршрутизации — не журналируются: по `registry.md` это чистая
печать (его единственное исключение, `--install-completion`, пишет
только rc-файл shell — записи журнала тоже не оставляет; см. отклонения).

## CLI-контракт

нет (механизм обвязки. Чтение — команда `mpu log` с фильтрами
`--tail/--failed/--cmd/--since/--run`; её спека — при переезде команды).

## Ввод/вывод

Формат записи — текстовый, унаследован от оригинала дословно; секция с
пустым содержимым не печатается:

```
### <YYYY-MM-DD HH:MM:SS.mmm> <+HH:MM> run=<id> pid=<pid> cwd=<каталог>
$ mpu <argv после маскирования>
--- note run=<id> ---      # диагностика обвязки, если была
--- out run=<id> ---       # stdout verbatim
--- truncated run=<id> stream=out dropped=<байт> ---
--- err run=<id> ---       # stderr / текст ошибки
--- end run=<id> exit=<код> dur=<сек, 3 знака>s ---
<пустая строка>
```

`run_id` = `YYYYMMDD-HHMMSS.mmm-<pid>`. Границы записи при чтении
определяются только шапкой и `--- end` с тем же run_id — похожие маркеры
внутри чужого вывода запись не рвут. Строка `$ mpu …` всегда начинается
литеральным `mpu`, независимо от argv[0]. Код в записи: exit-код
команды/подпроцесса; внутренняя ошибка обвязки → 1, детали в err-секции.

## Побочные эффекты

Пишет файл журнала (дефолт — `~/.config/mpu/mpu.log`) + соседний
lock-файл; оба 0600, права выравниваются при каждой записи; каталог
создаётся. Перехват вывода — на уровне файловых дескрипторов 1/2: вывод
дочерних процессов тоже попадает в запись. Сети нет.

Маршрут `legacy`: запись делает обвязка бинаря, а собственный журнал
Python-подпроцесса отключается окружением — иначе записей было бы две.
Shell-completion записей не оставляет (правило оригинала).

## Конфигурация

`MPU_LOG_ENABLED` (выкл: 0/off/false/no, любой регистр),
`MPU_LOG_FILE`, `MPU_LOG_MAX_OUTPUT_BYTES` (дефолт 8 МиБ на поток,
0 = без обрезки), `MPU_LOG_MAX_BYTES` (порог ротации, дефолт 50 МБ,
0 = не ротировать), `MPU_LOG_KEEP` (архивов, дефолт 5, 0 = ротация без
архивов) — env-слой (`platform/env-file.md`). Битое числовое
значение → дефолт + note в текущую запись.

## Инварианты

- Ровно одна запись на вызов — и для native, и для legacy; append
  атомарен на локальной ФС, параллельные записи не смешиваются.
- Fail-open: любая ошибка журнала (права, диск, лок) не меняет
  результат и код команды; журнал работает на копии перехваченных
  байт и не может исказить проброшенный вывод.
- Мимо журнала не проваливается ничего: ошибка на любом этапе
  обработки вызова, включая инициализацию обвязки, попадает в запись
  (детали в err-секции).
- Секреты маскируются до записи, необратимо: значения опций, чьё имя
  содержит password/token/secret/api-key/session (без учёта регистра,
  раздельная и `=`-форма), и такие же ключи рекурсивно внутри JSON-тел
  (`@file`-индирекция не разворачивается; невалидный JSON не трогается).
- Команды, помеченные в своих спеках «без записи вывода» (`log`,
  `confirm`, `search`, `api get-token`), пишутся без секций out/err —
  перехват для них не включается вовсе. (`confirm` не переезжает, но
  пока жив Python — исполняется маршрутом `legacy`: перехват её пайпа
  продублировал бы payload и сломал бы промпт в /dev/tty.)
- Перехват сохраняет TTY-природу дескрипторов: команда и её подпроцессы
  видят isatty ровно как при прямом вызове без журнала — прогресс-бары
  и интерактивные подтверждения (в т.ч. legacy-команд) не ломаются.
- Ротация ждёт лок не дольше 0,5 с: не успела — запись пишется без
  ротации; запись при неудачной ротации никогда не теряется.

## Граничные случаи и ошибки

- Перехват вывода не удался → команда исполняется без перехвата,
  запись без out/err.
- Вывод сверх лимита → маркер `truncated` с числом байт; неполный
  хвостовой UTF-8-символ дорезается.
- Пустой (0 байт) файл журнала не ротируется никогда — первая запись
  любой величины ложится целиком.
- Журнал выключен (`MPU_LOG_ENABLED`) → команды работают, записей нет.

## Golden-примеры

Снять с живой Python-версии при переводе в «к реализации»: одна полная
запись happy path; запись упавшей команды (err-секция, exit≠0); запись
с маскированным секретом в argv. Пользовательская поверхность чтения
(`mpu log` и фильтры) снимет свои golden при переезде команды `log`.

## Известные отклонения

- **fix** — оригинал журналировал и вызовы без исполнения команды
  (справка, `version`, опечатки имени); новая обвязка журналирует только
  исполнение команд. Причина: реестровые поверхности — чистая печать без
  побочных эффектов (`registry.md`), а опечатки — шум журнала.

## Открытые вопросы

- Шапка записи для вызова через MCP-сервер: pid долгоживущего процесса
  постоянен — уникальность суффикса `run_id`, содержимое `cwd=`, а также
  рендер строки `$ mpu …` и маскирование для вызова тула с
  JSON-аргументами — решить при реализации журналирования MCP-вызовов.
- Детекция «команд без перехвата» — по реестру команд, а не по argv
  (устраняет открытый вопрос оригинала про флаг перед именем команды);
  закрепить тестом при реализации.
