# Правила подтверждения

Статус: к реализации

## Назначение

Перед исполнением строки решается, можно ли её исполнить: выполнить сразу,
спросить человека или отказать. Решение берётся из правил, заданных на пути
сообщений (`platform/objects.md`, «Выход»: `path`). Правила хранятся в SQLite,
меняются сообщениями корню и с фронта (позже) и действуют со следующей строки
без перезапуска.

Порция подключает правила к `mpu-next` (`platform/registry-objects.md`).
Нынешний `mpu`, MCP-сервер и их профили `ro`/`rw` не меняются.

## Термины

- **Путь правила** — звенья пути через пробел: `kiten card <args>`,
  `sql-ro <args>`, `policy`. Пустой путь (корень) пишется `*`. Хвостовое
  ` *` у пути — то же, что путь без него: `kiten *` ≡ `kiten`.
- **Решение** — `allow` (выполнить), `ask` (спросить), `deny` (отказать).

## Как находится решение

Правило на пути действует на этот путь и на всё под ним. Для строки берётся
правило с **самым длинным** путём, который является началом её пути (по
звеньям, не по буквам). Совпавших нет — решение `ask`.

Эталон — `fixtures/policy/cases.json`: наборы правил, путь строки, ожидаемое
решение и путь выигравшего правила (`*`, если выиграл корень; `null`, если не
совпало ни одно). Коротко:

| Правила | Путь строки | Решение |
|---|---|---|
| — | `kiten ls` | `ask` (ни одно не совпало) |
| `* allow` | `kiten ls` | `allow` |
| `* allow`, `sql-ro ask` | `sql-ro <args>` | `ask` |
| `* allow`, `sql-ro ask` | `kiten ls` | `allow` |
| `kiten ask`, `kiten ls allow` | `kiten ls` | `allow` |
| `kiten ask`, `kiten ls allow` | `kiten card <args>` | `ask` |
| `kiten card deny` | `kiten card <args>` | `deny` |
| `kiten card deny`, `kiten card <args> allow` | `kiten card <args>` | `allow` |
| `kiten allow` | `kitenx ls` | `ask` (не начало пути по звеньям) |

## Когда проверяется

- Один раз на строку — перед исполнением, которое даёт итог (конец строки у
  объекта команды или группы, `platform/registry-objects.md`), по полному
  пути строки.
- Режим справки, итог-объект (справка группы) и отказ до исполнения правил не
  спрашивают: ничего не исполняется.

Исход:

| Решение | Что происходит |
|---|---|
| `allow` | исполнение |
| `ask` | вопрос каналу вызова; «да» — исполнение; «нет» — отказ `<путь>: не подтверждено`, код 1 |
| `ask`, а спросить некого (канал без человека: нет tty) | отказ `<путь>: нужно подтверждение, а спросить некого`, код 1 |
| `deny` | отказ `<путь>: запрещено правилом «<путь правила>»`, код 1 |

**Канал вызова `mpu-next`.** Канал с человеком — только когда и stdin, и
stderr — терминалы: вопрос печатается в stderr без перевода строки, ответ —
одна строка из stdin. Иначе — канал без человека (`/dev/tty` не открывается:
это потребовало бы прав шире задачи `build`).

`<путь>` — текст пути строки (`platform/objects.md`, «Путь в тексте»).
Вопрос каналу — одна строка: `выполнить <путь>? [y/N] `; «да» — ответ `y`
или `yes` в любом регистре, всё прочее — «нет».

## Сообщения корню

Корень дерева `mpu-next` получает пять собственных методов рядом с командами
реестра (имена с командами не пересекаются). Они видны в `selectors` и
справке корня.

| Сообщение | Итог |
|---|---|
| `policy` | данные: список `{ "path": "<путь правила>", "verdict": "<решение>" }`, по пути правила по алфавиту (`*` первым) |
| `allow: <путь правила>` | правило записано (заменяет прежнее на том же пути); данные: `{ "path": …, "verdict": "allow" }` |
| `ask: <путь правила>` | то же с `ask` |
| `deny: <путь правила>` | то же с `deny` |
| `forget: <путь правила>` | правило удалено, путь снова наследует; данные: `{ "path": …, "verdict": null }`; правила не было — то же, без ошибки |

Путь правила в значении — одно слово оболочки: `mpu allow: "kiten card"`.
Значение ключа — не сообщение: режим справки его не смотрит
(`allow: -- --help` — правило на пути `--help`, а не справка).
Лишние пробелы между звеньями и хвостовое ` *` нормализуются; пустое
значение — отказ `путь правила пуст`, код 2.

**Жёсткий запрет, вне правил.** Сообщения `allow:`, `ask:`, `deny:`,
`forget:` правилами не решаются: они **всегда** спрашивают канал, текст
вопроса — `изменить правило: <путь правила> → <решение>? [y/N] `
(`… → forget` для `forget:`). Канал без человека отвечает отказом
`изменить правила может только человек`, код 1, база не меняется. Канал MCP
(порция 7) — всегда такой.

`policy` — обычная строка: её решает правило пути `policy` (посев — `allow`).

## Хранение

- Файл `policy.db` в каталоге состояния `mpu` (`$HOME/.config/mpu`, тот же,
  что у кэш-БД и журнала; путь передаётся, не читается по месту). Новых прав
  Deno не нужно.
- Правила читаются при старте процесса; запись правила и обновление
  прочитанного — одна операция: следующая строка того же процесса видит новое
  правило.
- **Перед каждым решением** набор правил сверяется с файлом: если файл
  изменил другой процесс (например, правило записано из терминала, а решение
  принимает уже работающий MCP-сервер), правила перечитываются до решения.
  Устаревшее прочитанное решения не даёт ни в одном процессе.
- Файл нельзя открыть или прочитать (повреждён, не SQLite) — строка
  отказывает `правила подтверждения: <причина>` с кодом 1 до разбора;
  молча считать «всё разрешено» нельзя.

## Посев

При каждом старте каждый путь, который посев ещё **ни разу** не видел,
получает правило. Посеянный и потом удалённый (`forget:`) или изменённый путь
заново не сеется. Корневое правило посев не ставит.

| Путь | Посевное решение |
|---|---|
| команда реестра (путь без `<args>`) | `ro` — `allow`, `rw` — `ask` |
| группа с `bare` (`mcp`) | `ask` — у исполнения группы признака `ro`/`rw` нет |
| группа с селектором перед подкомандой (`ozon-jobs`) | самое строгое из посевных решений её детей: хоть один `rw` — `ask`, иначе `allow` |
| `policy` | `allow` |

Правило на такой группе действует и на вызов с селектором впереди
(`ozon-jobs sl-2 show` — путь `ozon-jobs <args>`, `platform/registry-objects.md`,
«Известные отклонения»), и на всех детей, у которых своего правила нет.
Поэтому `allow: "ozon-jobs"` открывает все её подкоманды, включая пишущие; в
вопросе подтверждения такого правила после стрелки добавляется
` (группа: подкоманды с записью — <имена через запятую>)`, если такие есть.

## Инварианты

- Решение принимается в одном месте для любого канала.
- Строка с решением не `allow` не исполняется, пока канал не ответил «да».
- Изменить правило без ответа человека «да» нельзя ни одним сообщением.
- После `allow:`/`ask:`/`deny:`/`forget:` следующая строка видит новое
  правило без перезапуска.
- Файл правил, недоступный для чтения, никогда не даёт `allow`.
- Правило, изменённое любым процессом, действует на следующую строку любого
  процесса.
- Имена `policy`, `allow:`, `ask:`, `deny:`, `forget:` не совпадают ни с одной
  командой верхнего уровня реестра — проверяется тестом.

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| пустой файл правил, первый старт | посев: `kiten card` — `allow` (`ro`), `kiten comment` — `ask` (`rw`) |
| `forget: "kiten card"`, перезапуск | правило не вернулось; `kiten card 1` — `ask` |
| `allow: ""` | `путь правила пуст`, код 2 |
| `allow: "kiten  card *"` | записано как `kiten card` |
| `deny: "*"`, затем `policy` | `policy` сеян `allow` — список правил показан |
| `deny: "*"`, затем `kiten ls` | отказ `mpu kiten ls: запрещено правилом «*»`, код 1 |
| `kiten card 1 --help` при `deny: "*"` | справка, код 0 (режим справки правил не спрашивает) |
| изменение правила из канала без человека | `изменить правила может только человек`, код 1, база не изменена |
| файл `policy.db` — мусор | `правила подтверждения: …`, код 1, до разбора |
| процесс A прочитал правила; процесс B записал `deny: "kiten ls"`; A решает `kiten ls` | `deny` — A перечитал файл до решения |
| первый старт: `ozon-jobs` (есть `rw`-дети) | посеян `ask`; `ozon-jobs sl-2 show` — `ask` |
| `allow: "ozon-jobs"` | вопрос: `изменить правило: ozon-jobs → allow (группа: подкоманды с записью — …)? [y/N] ` |

## Известные отклонения

От раздела 5 архитектуры (`mpu/docs`, исполнителю не виден — суть здесь):
свёртка «самое строгое решение по звеньям цепочки» не делается. Она
противоречит правилу «самое конкретное побеждает»: при `kiten ask`,
`kiten ls allow` строка `kiten ls` получила бы `ask`. Правило на пути
действует на всё ниже, побеждает самое длинное совпадение — этого хватает.
Файл правил — в каталоге состояния `$HOME/.config/mpu`, а не
`~/.local/state/mpu`: там уже лежат кэш-БД и журнал, и новых прав не нужно.
