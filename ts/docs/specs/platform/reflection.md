# Протокол отражения и дополнение сообщениями

Статус: к реализации — порция 160.

## Назначение

Любой объект `mpu` рассказывает о себе сообщениями: какие сообщения понимает,
какие ключи и форматы у команды, какие значения подходят ключу. На этих
сообщениях работают дополнение оболочки, справка агенту и дерево web — один
источник вместо снимка с отдельными полями. Имена сообщений выбраны слепым
замером двух агентов `sonnet` (ru/en): 5 из 9 совпали дословно.

## Общий протокол — понимает любой объект

| Сообщение | Ответ (данные; `… end json` — структура) |
|---|---|
| `messages` | `[{ "selector": "ls", "kind": "unary", "purpose": "…" }, { "selector": "id:", "kind": "keyword", "purpose": "…" }]` — собственные сообщения, по алфавиту |
| `understands: <сообщение>` | `true` / `false`; ключевое пишется за `--`: `understands: -- id:` |
| `keys` | `[{ "name": "id", "kind": "value", "required": true, "purpose": "…", "reason": null }]` — ключи ключевого сообщения команды; `kind` — `value`, `flag`, `list`; `reason` — причина ключа вне словаря (`keys-translation.md`); у объекта без ключей — `[]` |
| `formats` | `["json", "md"]` — форматы результата; у команды — без исполнения; у результата — его же |
| `variants` | `[]` — варианты команды (появятся отдельной порцией) |
| `help` | как в 158 |

Протокол — общий для всех объектов (композиция, одна реализация на модуль
объектов), не перечисляется в `messages`, но разбирается у каждого. Прежние
имена `selectors`, `respondsTo:` сняты: отказ «`selectors` — теперь `messages`»
с готовой строкой, код 2.

Ни одно сообщение протокола ничего не исполняет, правил не спрашивает и не
пишет журнал вызовов (как `help`). Текстовый вид — строки `<selector>\t<purpose>` (`messages`),
`<name>\t<kind>\t<обязателен|->\t<purpose>` (`keys`), по строке на формат
(`formats`); в конце — перевод строки.

## Значения ключа — `candidates: … like: …`

Объект команды понимает `candidates: <ключ> like: <начало>` → список
`{ "value": "…", "purpose": "…" }`, не больше 20, по алфавиту:

- `target` — из кэш-БД: номера и имена клиентов (`purpose` — имя клиента и
  сервер), серверы `sl-N`, dev-клиенты `dev:N`; совпадение — начало значения
  или подстрока имени без учёта регистра; сети нет;
- прочие ключи — `[]` (свои значения объявит команда позже).

## Дополнение — `complete: <строка>`

Корень понимает `complete: <набранная строка>` (строка — одно слово: всё, что
набрано после `mpu`, последнее слово — дописываемое, может быть пустым) →
список `{ "word": "…", "purpose": "…" }` следующего слова:

| Где стоит курсор | Кандидаты |
|---|---|
| после унарных звеньев | `messages` получателя (унарные словом, ключевые — первым ключом: первый обязательный в порядке входов, обязательных нет — первый по порядку; `sql-ro` → `target:`, `kiten card` → `id:`) |
| внутри ключевого сообщения, после значения | ключи методов получателя, содержащих уже набранные, ещё не набранные (и ключ-список — снова) |
| за ключом, ждущим значения | `candidates: <ключ> like: <начало>` |
| после `end` | `formats` результата |
| за `--` | ничего |

Дополнение исполняет только протокол отражения: ни команды, ни `ask`-вопроса,
ни записи в журнал вызовов. Ответ `back` — за 50 мс без сети.

## `mpu-complete`

- Спрашивает `back` сообщением `complete:` (по `/line`, основной токен);
  варианты печатает прежним форматом `<вариант>\t<описание>`, код всегда 0.
- `back` не ответил за 150 мс, не запущен или нет основного токена — снимок
  `tree.json`, как сейчас. Снимок — вывод того же протокола: узел `path`,
  `summary`, `tail` (его читают правила и дерево политики), `messages`,
  `keys`, `formats`; поля `selectors`, `flags`, `summaries` сняты. Без `back`
  значения ключей (`candidates`) не предлагаются.
- Права задачи `complete`: `--allow-net=127.0.0.1` (запрос к `back`),
  `--allow-read=$HOME/.config/mpu/token` (основной токен),
  `--allow-env=MPU_BACK_URL` (адрес, как у `cli`) — каждое строкой с
  обоснованием и проверкой, краснеющей без него. Агентский токен не читается.
- Скрипты `init bash|fish|nu` не меняются.

## Инварианты

- Протокол отражения ничего не исполняет.
- `mpu-complete` при живом `back` берёт ответ `back`, не снимок; снимок и
  ответ `back` на одном дереве дают одинаковые сообщения и ключи.
- `keys` и справка команды не расходятся: оба из объявления команды.

## Граничные случаи

| Дано | Ожидается |
|---|---|
| `mpu kiten card keys` | `id	value	обязателен	id или URL карточки`, `no-comments	flag	-	…`, `no-images	flag	-	…` |
| `mpu kiten card keys end json` | JSON-массив ключей |
| `mpu sql-ro formats` | `json`, `md`; запроса к БД нет |
| `mpu kiten messages` | `boards	…` … `whoami	…`, по алфавиту |
| `mpu kiten understands: ls` / `understands: nope` | `true` / `false` |
| `mpu kiten selectors` | `mpu kiten: selectors — теперь messages: mpu kiten messages`, код 2 |
| `mpu sql-ro candidates: target like: ром` | клиенты, чьё имя содержит «ром», с сервером в `purpose` |
| `mpu complete: "kiten ca"` | `card	…` |
| `mpu complete: "sql-ro target: 54 "` | `sql:	…` (и ключи-флаги) |
| `mpu complete: "sql-ro target: ром"` | кандидаты `target` на «ром» |
| `mpu complete: "kiten card id: 1 end "` | `json`, `md` |
| `mpu-complete -- kiten ca` при погашенном `back` | `card	…` из снимка, за ≤ 150 мс |
| `mpu complete: "ask sql target: 1 sql: x "` | ключи; вопроса нет, запроса нет |
