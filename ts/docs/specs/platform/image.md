# Образ: методы пользователя в `image.db`

Статус: к реализации — порция 168 (после 167).

## Назначение

Строку, которую пишут снова и снова, можно сохранить методом получателя:
`kiten cardsIn: review` вместо `kiten ls where: column is: review`. Метод
образа неотличим от команды: отвечает на протокол отражения, виден в
справке, дополнении и web, решается правилами. Хранится сразу в SQLite, не в
памяти процесса.

## Хранение

- Файл `image.db` рядом с `policy.db` (`policy.md`, «Хранение»); нет файла —
  образ пуст, файл создаётся первой записью.
- Метод: путь получателя (`kiten`), имя (`cardsIn:`), исходник — текст блока
  определения (`do :column … done`) словами через пробел, назначение, описание
  ключей (может быть пустым), автор — канал (`human`, `agent`, `web`), время
  (ISO UTC), хэш sha256 нормализованного исходника (слова через один пробел).
- `define:` и `forget:` пишутся сразу, транзакцией.
- Перед каждым поиском метода — `PRAGMA data_version`; изменилось с прошлого
  чтения — прочитанное забывается. Правка из другого процесса видна
  следующей строке.

## Определение

`ask kiten define: cardsIn purpose: ^мои карточки в колонке^ do :column kiten
ls where: column is: @column done`

| Правило | Итог |
|---|---|
| имя — следующее слово после `define:` как есть; `cardsIn` ≡ `cardsIn:` | |
| частей имени через `:` столько, сколько параметров блока: 1 параметр — `cardsIn:`, 2 — `cardsIn:since:` (записывается `cardsIn:since` или `cardsIn:since:`), 0 — унарный `myCards` | вызов: `kiten cardsIn: review since: 1d` |
| `purpose:` — обязателен | нет — отказ «метод без назначения: purpose: ^…^», код 2 |
| `keys: ^…^` | описание ключей для справки; необязателен |
| тело — блок `do … done` | иначе отказ «тело метода — блок do … done», код 2 |
| частей имени ≠ параметров | отказ «имя cardsIn:since: ждёт 2 параметра, у блока 1», код 2 |
| имя — команда, группа или вариант получателя, сообщение корня (`it`, `ask`, `help`), сообщение протокола отражения | отказ «`ls` у `kiten` уже есть», код 2 |
| имя склеивает сообщение получателя и сообщение вида его результата (`greater:ifTrue:` у числа) | отказ «имя делится на greater: и ifTrue: — выбери другое», код 2 |
| метод с тем же именем есть | заменяется (новые исходник, время, автор, хэш) |
| получатель — не команда и не группа дерева | отказ «метод — только у команды или группы», код 2 |

Определение — строка под правилами: путь `<получатель> define:` (посев
`ask`); без начального `ask` — адресный отказ двери.

## Правило метода — посев обходом

При определении обход тела (`ask-composite.md`) собирает достижимые команды:
все `allow` — правило метода `allow`; иначе — `ask`. Правило пишется в
`policy.db` путём `<получатель> <имя>` источником «посев»; человек меняет его
как любое (`policy.md`). Вызов метода решается своим правилом, а команды тела
— своими при отправке (167).

## Удаление

`ask kiten forget: cardsIn` — метод и его правило посева удалены; нет метода
— отказ «у kiten нет метода cardsIn:», код 1.

## Вызов и отражение

- `kiten cardsIn: review` — тело исполняется с `column` = `review`; итог —
  итог тела. Параметры — ключами по частям имени.
- Метод отвечает протоколу корня: `kiten messages` перечисляет его рядом с
  командами (метка `образ`); `kiten cardsIn: help` — назначение, ключи,
  исходник, автор, время; `kiten understands: cardsIn:` → `true`;
  `complete:` предлагает его наравне с командами.
- Снимок дерева (`tree.json`, `reflection.md`) — узел метода с полем
  `image: {author, time, source}`.

## Решено по ходу 168

- Метка в `messages` — назначение с префиксом `образ: ` (`образ: мои в
  колонке`); новых полей нет, голдены прежних узлов не меняются.
- Правило метода при вызове: обход до исполнения (167) — `deny` → отказ,
  код 1; `ask` без начального `ask` → адресный отказ, код 2. Если правило
  метода — `ask` (посевом или человеком), вопрос человеку задаётся **на каждый
  вызов** в момент отправки (цикл из пяти вызовов — пять вопросов), текстом
  строки вызова со значениями; «нет» — вызов не исполнен, «не подтверждено»,
  код 1. Исполнитель шлёт ядру обычный кадр `line` со строкой вызова; узел
  метода в ядре исполнения не имеет — решает правило пути и пишет журнал;
  тело исполняет исполнитель. Вопросы команд тела — как прежде.
- Итог `define:` — видом изменения правила: `{"path": "kiten cardsIn:",
  "verdict": "allow"}`; у `forget:` — `verdict: null`.
- Параметры метода — объекты программы (число остаётся числом); тело —
  блок `value:…` в программе. Строка с вызовом метода — программа; справка
  метода — прежним путём по дереву.

## Инварианты

- Строка без методов образа ведёт себя как до порции.
- Метод не переживает `forget:` ни в одном месте: отражение, дополнение,
  снимок, правила.
- Встроенная команда не переопределяется никаким `define:`.

## Граничные случаи

| Дано | Ожидается |
|---|---|
| `ask kiten define: cardsIn purpose: ^мои в колонке^ do :column kiten ls where: column is: @column done`, «да» | метод записан, правило `kiten cardsIn:` — `allow` (посев) |
| затем `kiten cardsIn: review end size` | число карточек в `review` |
| `kiten messages` | среди прочих `cardsIn:` с меткой `образ` |
| `kiten cardsIn: help` | назначение «мои в колонке», ключ `cardsIn:`, исходник |
| `ask kiten define: cardsIn do :c … done` | «метод без назначения: purpose: ^…^», код 2 |
| `ask kiten define: ls purpose: ^x^ do … done` | «`ls` у `kiten` уже есть», код 2 |
| `ask kiten define: pingAll purpose: ^пинг^ do kiten ls each: do :c kiten comment id: @c id text: ping done done` | правило `kiten pingAll` — `ask` |
| `kiten pingAll` без `ask` | адресный отказ двери, код 2 |
| `kiten define: cardsIn purpose: ^x^ do :c … done` без `ask` | адресный отказ двери, код 2 |
| второй процесс определил метод, первый вызывает его следующей строкой | метод найден (сверка `data_version`) |
| `ask kiten forget: cardsIn` → `kiten cardsIn: review` | `doesNotUnderstand` с ближайшими, код 2 |
| `image.db` — мусор | «образ: …», код 1, до разбора (как `policy.db`) |
