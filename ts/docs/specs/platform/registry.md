## Назначение

Реестр команд Deno-CLI — единственная точка маршрутизации и все справочные
поверхности: общая справка (`--help`), команда `mpu help`, `mpu version`,
shell-completion, ошибки неизвестной команды. Здесь — решение «куда» и контракт
каждого маршрута; что именно делает команда — её собственная спека.

## CLI-контракт

- `mpu <cmd> [args…]` — единственная форма вызова. Установка — один бинарь
  `~/.local/bin/mpu` (`deno compile`). Ни `mpu2`, ни env-переключателей
  реализации.
- Запись реестра: имя команды и однострока-summary. Все команды исполняются
  кодом CLI и подчиняются `platform/command-contract.md`.

  Маршрутов было два — `native` и `legacy`, второй отдавал команду
  подпроцессу установленной Python-реализации. **Маршрут снят целиком порцией
  97** (2026-08-31) вместе с последними двумя именами, и вместе с ним ушли
  ключ `mcp.legacy_bin`, проброс stdin/stdout/stderr сквозь подпроцесс, отказ
  `legacy-реализация не найдена по пути "<путь>"` и сверка версий при старте
  MCP-сервера. Имена, которые решено не переносить, перечислены отдельно, с
  причиной на каждое, — «ещё не переехало» и «не переедет никогда» разные
  вещи, и по слепку их не различить.
- Имя,
  которого нет в реестре, — ошибка на CLI, без сети: stderr
  `No such command '<имя>'.` + подсказка `Try 'mpu -h' for
  help.`, exit 2.
- Запись группы несёт раскладку argv уровня. Умолчание — имя подкоманды
  идёт сразу за именем группы. Признак `layout: "selector-first"` означает
  другую форму: `<группа> [флаги] SELECTOR <подкоманда> [флаги]` — селектор и
  режимы печати набираются до имени подкоманды (семейство обёрток,
  `specs/portainer-wrappers.md`). Точка входа опознаёт имя подкоманды с
  пропуском: среди **позиционных** токенов уровня (значение флага позиционным
  не считается — какие флаги его берут, известно из схем подкоманд группы).
  Своей схемы аргументов у группы при этом нет, и разбирает вход всё та же
  схема листа; лишний токен уровня для такой группы даёт не
  `No such command`, а индекс уровня в stdout и exit 2 — отличить забытую
  подкоманду от опечатки в ней при этой раскладке нельзя, а индекс называет
  доступные.
- `mpu --help` ≡ `mpu -h` (байт-в-байт, exit 0); `mpu` без аргументов — тот же
  текст без финальной пустой строки, **exit 2** (вызов без команды — ошибка, см.
  отклонения). Всё в stdout: Usage, описание CLI («Monorepo Python utilities —
  multi-purpose CLI for ad-hoc operations.»), панель Options (completion-опции,
  `--help -h`), одна плоская панель Commands. Порядок команд — порядок реестра,
  не алфавит; строка команды = её собственная однострока-summary. После панели
  Commands — хвост «Окружение:»: какая переменная какие файлы уводит
  (`platform/store.md`). Хвост есть только у корня; у промежуточных уровней его
  нет — там он повторялся бы на каждом шаге, ничего не добавляя.
- `-h`/`--help` первым аргументом работают одинаково на любом уровне
  вложенности, включая passthrough-команды (`mpu ssh --help` и
  `mpu run-js --help` рендерят справку, exit 0). Судьба
  `--help` среди произвольных аргументов после позиционных — контракт конкретной
  команды, не обвязки.
- `mpu help` (подкоманда): заголовок `Available commands:`, затем по строке
  `mpu <kebab><выравнивание><описание>` (одна колонка описаний), футер
  `Run \`<command> --help\` for detailed usage.`; exit 0.
- `mpu help <имя>` — аргумент это ПОЛНОЕ имя (`mpu help "mpu search"`, не голый
  kebab); рендерит справку целевой команды, prog-имя в Usage = переданное имя;
  exit 0. Неизвестное имя
  (включая пустую строку и голый kebab) → stderr
  `mpu help: unknown command '<имя>'` + `Known commands: <список>`, exit 2.
- `--json` — общий параметр точки входа, принимаемый с любой командой на любом
  уровне вложенности: вместо текстового рендера печатается результат команды
  как JSON. В схему аргументов команды не входит и в её справке не
  перечисляется. Исключение — команда, объявившая
  собственный вход с этим именем (`platform/command-contract.md`): у неё
  параметр разбирается её же схемой, перечисляется в её справке, а точка входа
  его не перехватывает и не добавляет вторым в режиме дополнения. Признак —
  имя входа, а не имя команды. Второе исключение — команда, чей хвостовой вход
  забирает неопознанные токены (`platform/command-contract.md`, инвариант 4): у
  неё параметр не распознаётся вовсе и уходит в этот вход как обычный токен, а
  режим дополнения его не предлагает. Код выхода такой команды при этом всегда
  её собственный: подменять его нулём формы вывода нечему — структурной формы у
  неё нет. Оба исключения действуют **после имени команды**: до него чужой
  командной строки ещё нет, поэтому параметр снимается всегда, и попасть во
  вход он не может. Снятый до имени параметр у команды-исключения второго вида
  — ошибка ввода: stderr `mpu: --json не применяется к команде '<путь>'`,
  exit 2. Молчаливое игнорирование запрещено (пользователь ждёт JSON и не
  получит его), печать JSON невозможна (stdout уже занят байтами чужой
  команды).
- `mpu version` — одна строка версии в stdout, без префиксов, exit 0. Версия —
  константа сборки; подпроцессу команда не уходит. Версия установленной
  реализации отдельной поверхностью не публикуется: её показывает диагностика
  расхождения при старте сервера, и до появления спроса второй величине места в
  выводе нет. Флага `--version` на корне нет: `mpu --version` → ошибка
  `No such option`, exit 2.
- `--install-completion` / `--show-completion` — установка/печать
  completion-скрипта текущего shell. Shell определяется по ближайшему известному
  shell в дереве процессов-предков; env `SHELL` не участвует (при bash-родителе
  `SHELL=/bin/zsh` всё равно даёт bash-скрипт).

## Режим дополнения

Установленный скрипт — только обвязка: он зовёт бинарь со служебной переменной
`_MPU_COMPLETE` и подставляет ответ. Формат ответа зависит от shell, потому что
bash собирает из него массив, а zsh **исполняет** его как код:

- `complete_bash` — по варианту на строку, без описаний
  (`fixtures/platform/registry/completion-out-bash.txt`);
- `complete_zsh` — вызов `_arguments` с парами «вариант : описание»; двоеточие
  внутри описания экранируется, описание обрезается по длине
  (`completion-out-zsh.txt`, вложенный уровень — `completion-out-zsh-nested.txt`).

Разбираемый вход: `COMP_WORDS` и `COMP_CWORD` для bash, `_TYPER_COMPLETE_ARGS`
для zsh; конец слова определяется хвостовым пробелом.

Предлагаются имена того уровня дерева, до которого дошёл ввод: после `mpu xlsx`
— его подкоманды, а не имена верхнего уровня. Слово, начинающееся с `-`,
дополняется флагами этого уровня, включая `--help`
(`completion-out-bash-flags.txt`, для zsh — `completion-out-zsh-flags.txt`: тот
же `_arguments`, описание флага рядом с ним). Значения перечислений не
дополняются: после `--render ` вывод пуст.

**Порядок флагов не фиксируется** — фиксируются состав и формат ответа. У
переехавшей команды флаги идут в порядке её схемы, а общий `--json` — после них,
тогда как эталон снят на порядке объявления оригинала. Требовать совпадения
порядка значило бы переснимать эталоны дополнения после каждого переезда ради
величины, которая не меняет ни поведения дополнения, ни того, что видит человек.

## Источник записей реестра

Записи берутся из машинного слепка дерева
`fixtures/platform/registry/tree.json`: массив узлов, у каждого — путь (сегменты
после `mpu`), однострока, подробная справка и параметры. Слепок снят с
установленной Python-реализации служебной командой дампа и несёт её версию;
обновляется пересъёмом целиком, правка руками — недопустима. Формат слепка несёт
собственную версию `manifestVersion`: незнакомая — отказ с внятным текстом, а не
попытка разобрать.

Узлы двух видов. **Составное имя** (`kiten`, `xlsx alias`, ещё двадцать)
помечено `group` и несёт собственные однострокѝ и справку. **Лист** — исполнимая
команда, признака `group` у него нет. Всего 272 записи: 22 группы и 250 листьев.
Однострока составного имени берётся из его записи, а не собирается
перечислением подкоманд: перечисление — суррогат, который расходится с тем, что
показывает живой CLI.

Версия сборки бинаря равна `mpuVersion` слепка: реестр и описания тулов
порождены из него, и расхождение означало бы, что бинарь описывает не то дерево,
которое исполняет. Инвариант действует, пока реестр порождается слепком, — то
есть до конца переезда.

Сверка версии сборки с версией установленной прежней реализации снята вместе с
маршрутом (порция 97): сверять больше нечего — ни одна команда к ней не
обращается.

Слепок — единственный источник однострок. Golden-файлы `help-list.txt` и
`help-root.txt` для этого не годятся: первый несёт дрейф оригинала (54 записи
вместо 57), во втором описания перенесены по ширине рамки и обрезаны. Они
остаются эталонами наблюдаемой поверхности, а не источником данных.

В реестр попадает **верхний уровень** — 57 имён, и сверх них те листья, что уже
переехали внутрь ещё не переехавшей группы. Маршрут решается по **самому
длинному известному реестру пути**: argv разбирается слева направо, побеждает
самая длинная совпавшая запись, остальные аргументы уходят команде как есть.
Правило имело смысл, пока внутри группы соседствовали переехавшие и
непереехавшие листья (первым таким был `kiten card`); теперь все листья свои,
и «самая длинная» совпадает с «по первому сегменту». Почему правило всё же
осталось записанным — раздел о частично переехавших группах ниже.

Полное дерево прежней реализации (250 листьев) живёт в слепке. Публикации
тулов он больше не нужен: описания и параметры берутся из объявлений команд,
а состав публикуемого задан закрытым списком (`platform/mcp-server.md`).
Слепок остался свидетельством того, что было в Python-версии, и опорой для
списка выброшенных имён.

## Ввод/вывод

Справка, `version`, completion и ошибки маршрутизации — чистая печать: без сети,
подпроцессов и записи файлов (исключение — `--install-completion`, пишущий в
rc-файл shell). Исполнение самих команд — их спеки.

## Побочные эффекты

нет (кроме `--install-completion`, см. выше). Completion-режим (служебная
env-переменная) не порождает подпроцессов и не создаёт записей журнала.

## Конфигурация

нет (версия — константа сборки; shell для completion определяется по дереву
процессов, не по конфигурации и не по env).

## Инварианты

- Реестр один: `--help`, `mpu help`, completion и маршрутизация читают один и
  тот же список команд — рассинхрон списков невозможен по построению.
- Состав реестра равен множеству первых сегментов слепка (57 имён) плюс
  собственные поверхности новой реализации, которых в оригинале не было
  (`mcp`). Список собственных перечислен явно: имя, отсутствующее и в слепке, и
  в этом списке, в реестре не появляется.
- Маршрутизация детерминирована: один **полный путь команды** — один маршрут
  (не «один первый сегмент»: внутри группы соседние листья могут идти разными
  маршрутами). Состояние между вызовами не живёт (единственное персистентное —
  локальные предпочтения, `platform/config.md`).
- Дополнение внутри группы, переехавшей частично, перечисляет только известные
  реестру листья — то есть уже нативные. Список неполон по построению, и это
  ожидаемое состояние переезда, а не дефект: соседи исполняются как прежде,
  просто не подсказываются. Подавлять дополнение до переезда всей группы не
  нужно — пустая подсказка не лучше неполной.
- Неизвестность имени решается реестром, без исполнения чего бы то ни было.
- Справочные поверхности (`--help`, `mpu help`, completion) перечисляют все
  команды реестра.
- Присутствие в реестре не определяет, публикуется ли команда тулом: состав
  публикуемого задан закрытым списком (`platform/mcp-server.md`). Реестр
  отвечает за то, «что исполняется», а не за то, «что видно агенту».
- Порядок команд стабилен между вызовами и одинаков во всех поверхностях.
- `mpu help <имя>` для каждого зарегистрированного имени даёт exit 0 и непустой
  вывод (закрепить тестом по всему реестру).
- `mpu help "mpu help"` рендерит собственную справку без рекурсии.
- `mpu version` идемпотентна, побочных эффектов нет.

## Граничные случаи и ошибки

- Строковый аварийный выход любой команды → exit 1, текст в stderr.
- Необработанное падение команды → exit 1, пользователю — стандартное
  сообщение об ошибке, не сырой трейс.
- `mpu totally-bogus-command` → `No such command`, exit 2 (см. golden).
- `mpu --version` → `No such option`, exit 2.
- `mpu help ""` → unknown, exit 2 (не путается с вызовом без аргумента).
- `mpu help <голый-kebab>` → unknown (частая ошибка ввода; список Known commands
  подсказывает полную форму).

## Golden-примеры

Фикстуры в `fixtures/platform/registry/` (`err-*` — stderr, остальное — stdout).
Сняты с живой Python-версии 0.1.0, 2026-07-29:

| Вызов                                   | Эталон                                      | exit |
| --------------------------------------- | ------------------------------------------- | ---- |
| `mpu --help` ≡ `mpu -h`                 | `help-root.txt`                             | 0    |
| `mpu`                                   | `help-root.txt` без финальной пустой строки | 2    |
| `mpu help`                              | `help-list.txt`                             | 0    |
| `mpu help --help`                       | `help-help.txt`                             | 0    |
| `mpu help "mpu sheet"`                  | `help-named-sheet.txt`                      | 0    |
| `mpu help "mpu help"`                   | `help-named-self.txt`                       | 0    |
| `mpu help does-not-exist`               | `err-help-unknown.txt`                      | 2    |
| `mpu help ""`                           | `err-help-empty.txt`                        | 2    |
| `mpu help search` (голый kebab)         | `err-help-bare-kebab.txt`                   | 2    |
| `mpu totally-bogus-command`             | `err-unknown-command.txt`                   | 2    |
| `mpu --version`                         | `err-version-flag.txt`                      | 2    |
| `mpu version`                           | `version.txt` — эталон формата              | 0    |
| `mpu version --help` (односоставная)    | `version-help.txt`                          | 0    |
| `mpu sheet get --help` (многосоставная) | `subcmd-help.txt`                           | 0    |
| `mpu --show-completion` (bash-родитель) | `completion-bash.txt`                       | 0    |
| `mpu --show-completion` (zsh-родитель)  | `completion-zsh.txt`                        | 0    |
| режим дополнения (4 случая)             | `completion-out-*.txt`                      | 0    |

`version.txt` закрепляет **форму**, а не значение: одна строка, без префиксов,
без завершающего текста. Значение в нём — версия оригинала на день съёма, а
`mpu version` печатает версию сборки; сверять его байтами нельзя.

Списки команд в `help-list.txt` и в `Known commands:` err-фикстур несут дрейф
оригинала (нет `api`, `init`, `version` — см. отклонения); вывод новой
реализации на этих поверхностях сравнивать по единому реестру, не байтами с
фикстурой. `help-named-*.txt` несут квирк именованного рендера (см. отклонения)
— сравнивать по prog-имени и exit-коду. Для completion «родитель» = shell, из
которого mpu форкнут: снимать как `bash -c 'mpu --show-completion; :'` — голый
`bash -c 'mpu …'` exec'ает mpu, и родителем остаётся внешний shell.
**Эталон теряет байтовую силу в момент переезда своей команды.** Все эталоны
сняты с прежней реализации. Когда команда переезжает, её справка рендерится из
объявления и обязана отличаться
— байтовая сверка становится проверкой прошлого. С этого момента эталон
проверяет состав и ключевые фразы; паритет к тому времени подтверждён
differential-сверкой, а не golden. Снимок новой поверхности, если он нужен для
регрессии, снимается заново и эталоном оригинала уже не является. Правило
избавляет от разбора «почему этот golden красный» в каждой следующей задаче.

`help-named-sheet.txt` и `subcmd-help.txt` — эталоны того, как сквозную
справку печатала прежняя реализация: flag-level текст она поставляла сама,
реестр хранил только однострокѝ. Обе команды (`search`, `sheet`) с тех пор
переехали, и по правилу выше эти эталоны проверяют состав и ключевые фразы, а
не байты.

## Известные отклонения

- **preserve** — голый `mpu` печатает справку в stdout и завершается exit 2,
  тогда как явные `-h`/`--help` — exit 0. Причина: скриптовая проверка «команда
  не указана» отличима от запроса справки; на код полагаются вызывающие.
- **fix** — в оригинале порядок списка `mpu help` определялся алфавитом
  внутренних имён модулей и расходился с порядком `--help`; в новой реализации
  обе поверхности используют порядок единого реестра. Расхождение с оригиналом —
  только порядок строк `mpu help`.
- **fix** — рукописный список `mpu help` дрейфанул от реестра (подтверждено при
  съёме golden): в нём и в `Known commands:` ошибок нет `api`, `init`, `version`
  — 54 команды против 57 в `--help`. Следствие проверено вживую при съёме:
  `mpu help "mpu version"` → stderr `mpu help: unknown command 'mpu version'`,
  exit 2 (фикстура не снималась — тот же класс unknown, что
  `err-help-unknown.txt`). В новой реализации все поверхности читают единый
  реестр — состав всегда полный.
- **fix** — именованный рендер `mpu help "mpu <cmd>"` в оригинале собирает
  справку заново и расходится с собственной `mpu <cmd> --help`: в панель Options
  добавляются `--install-completion`/`--show-completion`, пропадает алиас `-h` у
  `--help`, меняется разбивка колонок (видно по `help-named-self.txt` против
  `help-help.txt`). В новой реализации `mpu help <имя>` выдаёт ровно тот же
  текст, что `<имя> --help`.
- **fix** — байтовый паритет оформления справки и текстов ошибок не требуется:
  рамки/цвета оригинала не воспроизводятся; фиксируются состав, порядок, тексты
  однострок, ключевые фразы ошибок (`No such command '<имя>'.`,
  `No such option`) и exit-коды. Differential по этим поверхностям сравнивать
  структурно.
- **fix** — `--install-completion` идемпотентен: если функция дополнения в
  rc-файле уже есть, вторая копия не дописывается, а печатается сообщение об
  этом. Оригинал дописывал безусловно, и повторный вызов оставлял в rc-файле
  дубликаты. Наблюдаемая разница — только при повторной установке.
- **fix** — в оригинале `mpu --help` платит цену загрузки всех модулей
  (~секунда); новая справка мгновенна. Наблюдаемая разница — только время.

## Частично переехавших групп больше нет — и покрытие вместе с ними

Свойство «маршрут решается по самому длинному известному пути» появилось
2026-08-14 ради групп, где часть подкоманд уже native, а остальные ещё
подпроцессные. Такая группа была последней — `telegram`; порция 95 увела её
целиком, а порция 97 сняла и сам маршрут вместе с двумя оставшимися именами
(`iu-wb`, `ozon-fix-fo-tax` — выброшены, см. список выброшенных).

Отсюда прямое следствие, названное реализующей стороной 2026-08-31 и
записанное здесь, чтобы не потеряться: **проверки этого свойства удалены
вместе с предметом**, а не оставлены зелёными на выдуманном входе. Сегодня
свойство не проверяется нигде. Это сознательный размен: проверка на входе,
которого в реестре нет, зеленела бы, ничего не подтверждая, — тот же
вакуум, что мы чинили в 91 и 94.

Вернуть проверки обязана та порция, которая заведёт следующую частично
переехавшую группу. После 97 такой порции взяться неоткуда: маршрута, по
которому уходила бы вторая половина группы, больше нет — правило про самый
длинный путь осталось описанием того, как реестр устроен, а не того, что он
сегодня различает.

## Открытые вопросы

- Completion-опции в оригинале — автоматика CLI-фреймворка, не осознанный
  дизайн. Решить: сохранять ли обе опции (штатный completion Deno-фреймворка
  CLI) и не добавить ли заодно `--version` — любое отличие фиксируется как
  принятое расхождение в журнале переезда (его ведёт сессия-спецификатор вне
  этого канала).
- Поведение completion при неопределимом shell (в дереве предков нет известного
  shell) не снято — в реальном окружении недостижимо, у mpu предком всегда
  является shell. Зафиксировать при реализации, если фреймворк потребует явного
  решения.
