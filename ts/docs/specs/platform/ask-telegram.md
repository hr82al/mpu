# Подтверждение `ask` — и в Telegram

Статус: к реализации (серия R, порция R3; постановка —
`telegram-relay-r3-statement.md`, сценарии `[S.n]`)

## Назначение

Вопрос подтверждения строки (`ask` вида `line` с вопросом `[y/N]`:
решение правил `ask` — `platform/policy.md`, и ворота `mpu confirm` —
`confirm.md`) ядро задаёт **одновременно** своему каналу с человеком
(терминал клиента — `platform/line-prompt.md`; форма MCP —
`platform/mcp-objects.md`) и владельцу в Telegram
(`platform/telegram-questions.md`). Решает первый ответ; проигравшая
сторона снимается.

## Вопрос в чате

- Вид — срочный (как право, R1): обгоняет «ждёт ввода».
- Заголовок: `❓ mpu ask` + ` (MCP)` для двери агента + ` — <окно>` по
  `TMUX`/`TMUX_PANE` клиента (как у хука R1b); без окна — без части.
- Текст шага — вопрос без хвоста ` [y/N] ` (`выполнить mpu kiten comment?`).
- Кнопки `Да` / `Нет`; свой текст — нет (`ответьте кнопкой`).
- Исход: `✅ Да — из чата`, `❌ Нет — из чата`, `✅ решено в терминале`
  (ответил канал строки), `⌛ истёк — ответьте в терминале` (строка
  оборвалась, ядро перезапущено).

## Кто задаёт и кто снимается [D.1]

| Событие | Строка | Канал строки | Чат |
|---|---|---|---|
| вопрос поставлен | ждёт | вопрос как сегодня | вопрос |
| `Да` в чате | ответ `y` | снят: терминал — stderr `mpu: решено в Telegram — да`, ввод не ждётся; MCP — форма закрыта отменой запроса | `✅ Да — из чата` |
| `Нет` в чате | ответ `n` | снят (`… — нет`) | `❌ Нет — из чата` |
| ответ в канале строки | ответ | — | `✅ решено в терминале` |
| строка оборвалась | — | — | `⌛ истёк …` |
| бот не настроен / недоступен | ждёт | вопрос как сегодня | ничего |

Снятие в терминале — новый кадр ядра клиенту
`{"settled": "решено в Telegram — да"}` (`да`/`нет`): клиент прекращает
чтение терминала, печатает `mpu: <текст>` в stderr и ждёт кадров строки
дальше. Клиент, не знающий кадра, его игнорирует (тогда ввод ждётся до
Enter; ответ уже принят ядром — что ни введи, второго ответа нет). [D.2]

Снятие формы MCP — переводчик `mpu-mcp` шлёт Claude Code
`notifications/cancelled` с `requestId` своего `elicitation/create` и
продолжает вызов тула. **Номер запроса формы не равен 0**: Claude Code
пропускает отмену с `requestId: 0` — форма остаётся на экране (снято
2026-10-06, проба R3-2, голден `live-elicitation-cancel-id0-ignored.jsonl`);
переводчик тратит номер 0 на другой запрос сессии или начинает нумерацию с 1.
Снято живьём 2026-10-06 (проба R3-1, голден
`fixtures/telegram-relay/r3/live-elicitation-cancel-exchange.jsonl`): форма
исчезла, Claude продолжил ход с результатом тула. [D.3]

## Что не уходит в чат [S6]

- `ask` вида `secret` (пароль) — никогда.
- `ask` вида `line`, чей вопрос не оканчивается на `[y/N] ` — только канал
  строки (вопросы-строки с произвольным ответом).
- Строка без человека («спросить некого») — как сегодня: отказ, в чат
  ничего (у неё нет канала, который снимать; ответ из чата не задуман для
  строк без человека).

## Известные отклонения

- Гонка Enter в терминале одновременно с кнопкой в чате: запоздалый ответ
  терминала может достаться следующему вопросу той же строки (номера вопроса
  в кадрах `ask`/`answer` нет). Окно — доли секунды; вердикт — принять, номер
  вопроса в кадрах — отдельной порцией при надобности.
- Брошенное чтение настоящего `/dev/tty` после `settled` закрытием не
  прерывается: первый Enter следующего вопроса того же клиента может уйти
  брошенному читателю. Подтверждается живьём хостом.
- Форма MCP с более чем 4 полями — только `Decline` / `В терминале`;
  `oneOf`, `format`, `minimum`/`maximum`, `default` — поле как текст. Принять.
- Вопрос изменения правила (`изменить правило: …? [y/N]`) тоже уходит в чат:
  отвечает только владелец (`from.id`), это и есть человек. Принять.
- Номер двери агента решён в чате, а переводчик решение не забрал за 120 с →
  строка истекает «нет», в чате остаётся `✅ Да — из чата`. Принять (крайний
  случай: переводчик ждёт `/settled` всё время формы).

## Инварианты

- На вопрос — один ответ; второй (из проигравшего канала) не принимается.
- Ответ из чата действует только на свой вопрос (номер вопроса в данных
  кнопки, R1a).
- Пароль не попадает в Telegram ни в каком виде.

## Пункты чек-листа

`design.md`: 1 — примитив «вопрос строки» один, каналов два, гонка в одном
месте (ядро); 2 — канал строки «терминал / MCP» снимается своей реализацией
(кадр / отмена формы), не веткой у ядра; 3 — бот без ключей — существующий
`NO_BOT`, вопрос просто не уходит; 4 — решает ядро (первый ответ), каналы
только снимаются; 5–6 — кадр `settled` — протокол контракта кадров; 7 —
«отмена формы закрывает её» — проба R3-1, голден.
`design-mpu.md`: 4 — текст вопроса один (из правила), чат и терминал его не
переписывают; 8 — бот, часы, канал — параметры.
