# Команды реестра как объекты; точка входа `mpu-next`

Статус: реализовано — порция 139 (`5a039c8`, `36d4933`, `89bdfba`, `fa86d80`; модуль `back/src/next`, задача `next`); принято 2026-09-17: гейты зелёные (тестов 2039, smoke 21/1), парный тест — 20 строк.

## Назначение

Все нынешние команды становятся доступны через модель объектов
(`platform/objects.md`) без изменения своего поведения. Новая точка входа
`mpu-next` исполняет строку цепочкой сообщений; её вывод, stderr и коды
выхода для команд совпадают с нынешним `mpu` (`runCli`).

Порция — мост, а не перепроектирование команд. Цепочка решает только три
вещи: до какого узла реестра дошла строка, нужна ли справка и есть ли отказ.
**Исполняет** узел нынешняя диспетчеризация пути (та, что внутри `runCli`),
получая **исходную строку целиком** — поэтому короткие флаги, повторы, `-`,
`--`, чужой хвост `mpu ssh`, правила `--json`, `bare` групп и группы с
селектором перед подкомандой работают как сейчас, по построению.
Перевод семейств в объекты со своими сообщениями
(`mpu kiten card 123 comment "x"`) — следующие порции, по семейству.

Старая точка входа, реестр и MCP-сервер не меняются.

## Расширение разбора: хвост

`platform/messages.md` дополняется. Описание приёмника может объявить
**хвост** — имя вида звена (например `args`):

| Положение | Итог |
|---|---|
| у приёмника есть хвост, очередное слово — его собственный унарный селектор | обычное унарное сообщение |
| у приёмника есть хвост, очередное слово — любое другое | шаг забирает **все** оставшиеся слова одним сообщением-хвостом `{ "tail": [<слова как есть>] }`; остаток пуст |

Внутри хвоста слова не толкуются: `.`, `--`, `имя:` и `--имя` — просто
слова. Исключение одно — режим справки (ниже). Эталон разбора дополняется
случаями хвоста (`fixtures/messages/cases.json`).

## Дерево

| Реестр | Объект |
|---|---|
| корень | корень `mpu`: унарные методы — команды и группы верхнего уровня |
| группа (`kiten`, `kiten field`, …) | вид объекта; унарные методы — дети группы (вид результата — объект); назначение и справка — из объявления группы |
| группа с собственным исполнением без подкоманды (`bare`) | то же плюс хвост `args`: слова, не совпавшие с детьми |
| группа с селектором перед подкомандой (`layout: "selector-first"`: `wb-jobs`, `ozon-jobs`, …) | то же плюс хвост `args`: `ozon-jobs show sl-2` — унарное `show`; `ozon-jobs sl-2 show` — хвост `["sl-2","show"]`, подкоманду найдёт диспетчеризация |
| лист (команда) | метод родителя с видом результата «объект команды»; объект команды объявляет только хвост `args` |

Назначение и справка метода — из объявления команды (однострока и текст
справки). Звено пути у хвоста — `<args>`: путь `mpu kiten card 123` —
`["kiten", "card", "<args>"]`.

## Итог строки

Объект команды и группа отвечают на конец строки (`final`,
`platform/objects.md`) по-своему:

| Приёмник в конце строки | Итог |
|---|---|
| объект команды | исходная строка целиком уходит нынешней диспетчеризации пути; итог — её stdout, stderr и код |
| группа с `bare` или с селектором перед подкомандой, получившая хвост | то же |
| группа с `bare` без хвоста | то же (диспетчеризация исполнит `bare`) |
| группа без хвоста и без `bare`, корень | итог-объект: справка в формате `platform/objects.md` |

Что именно сделает диспетчеризация с исходной строкой — её дело: `mcp port: 1`
у неё даёт `No such command 'mcp port:'` и код 2, `sql-ro 54 "select 1"
--json` — форму JSON команды. Цепочка этого не повторяет и не предсказывает.

Так команда исполняется только в конце строки: сообщения до конца её не
запускают, а режим справки не исполняет последнее сообщение
(`platform/objects.md`) — справка к команде её не запускает.

## Режим справки и `--json`

- Дополнение к шагу 1 режима справки (`platform/objects.md`): сообщение-хвост
  тоже проверяется — слово `help` или `--help` в хвосте до первого `--`
  включает режим справки и убирается из хвоста; хвост, ставший пустым,
  убирается из цепочки (`kiten card --help` — путь
  `["help", "kiten", "card"]`). За `--` слова хвоста не проверяются.
- `--json` для обхода цепочки убирается из строки везде, где он стоит не
  внутри хвоста (иначе корень получил бы непонятое сообщение); в исполнение
  уходит исходная строка с ним, и форму вывода решает диспетчеризация.

## `mpu-next`

Точка входа в `back/` и задача `deno task next` **сняты порцией 154** вместе с
монолитом: строку исполняет сервер, а зовёт её тонкий клиент `mpu`
(`cli-client.md`). Таблица ниже описывает итог цепочки, и он тот же — меняется
только то, кто её запускает:

| Итог цепочки | stdout | stderr | код |
|---|---|---|---|
| команда исполнена | как у `runCli` | как у `runCli` | как у `runCli` |
| итог-данные (режим справки) | текст справки | — | 0 |
| итог-объект | текст справки | — | 2 |
| отказ | — | текст отказа как есть и перевод строки | 2 |

Журнал вызовов пишется так же, как у `runCli`.

## Инварианты

- Для любого пути реестра и любых аргументов, на которых `runCli` исполняет
  команду, `mpu-next` даёт тот же stdout, stderr, код и запись журнала.
- Каждый путь реестра достижим в дереве объектов; `selectors` группы —
  ровно имена её детей (плюс ничего).
- Команда не исполняется ни в режиме справки, ни посреди строки.
- Старая точка входа, реестр, `mpu mcp`, модули `messages` и `objects` —
  без изменения поведения (кроме расширения разбора хвостом).

## Граничные случаи и ошибки

| Дано | Ожидается |
|---|---|
| `kiten card 123` | диспетчеризация получает `["kiten","card","123"]` |
| `kiten card --help` | справка метода `card`, команда не исполнена, код 0 |
| `kiten card 123 --help` | справка команды `kiten card`, команда не исполнена, код 0 |
| `ssh sl-1 -- ls --help` | диспетчеризация получает строку целиком; `ssh` — argv `["sl-1","--","ls","--help"]` |
| `mcp port: 1` | как `runCli`: `No such command 'mcp port:'.`… и код 2 |
| `ozon-jobs sl-2 show` | как `runCli` |
| `--json kiten ls` | как `runCli` |
| `kiten` | справка группы, код 2 |
| `kitn` | `mpu: не понимает kitn; ближайшие: kiten`, код 2 |
| `kiten nope` | `mpu kiten: не понимает nope; ближайшие: move`, код 2 — подсказка по правилу `platform/objects.md` (расстояние до `move` равно 2) |
| `version extra` | как `runCli` |
| `mcp` (группа с `bare`) | как `runCli` для `mpu mcp` |
| `sql-ro 54 "select 1" --json` | как `runCli` с тем же argv |

## Golden-примеры

- Расширение разбора — новые случаи в `fixtures/messages/cases.json`.
- Равенство с `runCli` — парный тест: одна и та же строка через `runCli` и
  через `mpu-next` с одними подменами окружения. Строки выбирает исполнитель,
  но набор обязан покрыть: короткий флаг, повтор флага, `-` (stdin), `--`,
  хвост `ssh` с чужими флагами, позиционный `rest`, группу с `bare`, `--json`
  до и после пути, ошибку ввода команды (код 2 с текстом нынешнего разбора),
  доменную ошибку команды (код 1), по одной команде из каждого семейства
  верхнего уровня, у которого есть офлайн-тест через `runCli`.

## Известные отклонения

Намеренно отличаются от `runCli` (сравнение с ним не делается):

- справка: формат `platform/objects.md` вместо нынешнего;
- неизвестная команда: отказ `doesNotUnderstand` вместо нынешнего текста;
- команда `mpu help …` — заменена режимом справки;
- `--help` не первым словом аргументов (`kiten card 123 --help`) — у
  `mpu-next` справка без исполнения, у `runCli` слово уходит разбору команды;
- путь для правил подтверждения у групп с селектором перед подкомандой
  грубее: `ozon-jobs sl-2 show` — `["ozon-jobs", "<args>"]`;
- группа без `bare` и без селектора перед подкомандой отказывает по-своему:
  `wb-loader 777 cards` — `mpu wb-loader: не понимает 777` вместо
  `No such command 'wb-loader 777'`; обе формы — отказ с кодом 2;
- строка, чей хвост состоял бы из одного `--json`, доходит до другого узла:
  флаг снимается со слов обхода до первого `--`, а где начнётся хвост,
  известно только по ходу разбора;
- `--version`, режим дополнения оболочки — не поддерживаются `mpu-next`
  (дополнение — порция 9);
- текст отказа разбора (`у ключа card нет значения`) печатается без пути и
  без префикса; формат ошибок клиента решается в порции 6.
