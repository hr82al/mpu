# platform/kaiten-api-cards — карточка и её содержимое

Статус: к реализации (2026-08-14: закрыт единственный открытый вопрос —
ответ вызова 12 несёт обновлённый «Пункт чек-листа»)

## Назначение

Каталог вызовов внешнего API Kaiten, работающих с карточкой и вложенными в
неё сущностями: описание, файлы, комментарии, положение на доске, кастомные
поля, чек-листы, история перемещений. Транспорт (базовый URL, заголовки,
формат ошибок, повтор на 429, пагинация вообще, разбор селектора карточки) —
`platform/kaiten-http.md`, здесь не повторяется. Каталог — порт к внешней системе:
полнота обязательна для всех 14 вызовов независимо от того, есть ли на
вызов в первой волне вызывающий код команд.

## CLI-контракт

нет (платформенная возможность; поверхность появляется в командных спеках
`kiten-card.md` / `kiten-comment.md` / `kiten-field.md` / `kiten-checklist.md`

## Ввод/вывод

### Вызовы

| # | Метод и путь | Query / тело запроса | Ответ |
| - | - | - | - |
| 1 | `GET /cards` | query: `limit`, `offset`, `member_ids`, `responsible_id`, `condition`, `states`, `space_id`, `board_id`, `lane_id`, `column_id`, `updated_after`, `updated_before` — все необязательные фильтры | массив «Карточка (список)» |
| 2 | `GET /cards/{card_id}` | путь: id карточки | «Карточка (полная)» |
| 3 | `GET /cards/{card_id}/comments` | путь: id карточки | массив «Комментарий» |
| 4 | `POST /cards/{card_id}/comments` | тело JSON: `{text}` | «Комментарий» |
| 5 | `POST /cards/{card_id}/comments` | тело multipart: поле `text` + один part `files[]` на файл | «Комментарий»; файлы привязаны к нему (`file.comment_id` = id комментария) |
| 6 | `PATCH /cards/{card_id}` | тело JSON: подмножество `{board_id, column_id, lane_id}` — только заданные оси | «Карточка (полная)» |
| 7 | `PATCH /cards/{card_id}` | тело JSON: `{description}` — GFM markdown, заменяет целиком | «Карточка (полная)» (тот же путь и метод, что вызов 6) |
| 8 | `PATCH /cards/{card_id}` | тело JSON: `{properties: {"id_NNN": value}}`; `value: null` — очистить поле | «Карточка (полная)» (тот же путь и метод, что вызов 6) |
| 9 | `GET /cards/{card_id}/location-history` | путь: id карточки | массив «Перемещение» |
| 10 | `POST /cards/{card_id}/checklists` | тело JSON: `{name}` | «Чек-лист» (`items` — пустой массив) |
| 11 | `POST /cards/{card_id}/checklists/{checklist_id}/items` | тело JSON: `{text, checked}` + опциональный `sort_order` | «Пункт чек-листа» |
| 12 | `PATCH /cards/{card_id}/checklists/{checklist_id}/items/{item_id}` | тело JSON: `{checked}` | «Пункт чек-листа» — обновлённый, с новым значением `checked` |
| 13 | `PUT /cards/{card_id}/custom-properties/{property_id}/files` | тело multipart: одно поле `file` | «Файл» |
| 14 | `DELETE /cards/{card_id}/files/{file_id}` | путь: id карточки + id файла | пустое тело (см. транспорт: пустое тело успешного ответа — не ошибка) |

Пагинация: только вызов 1 — offset-режим транспорта (`limit=100`, конкатенация
страниц до первой короче 100); см. `platform/kaiten-http.md`. Остальные 13 вызовов —
без пагинации, один ответ на один запрос.

### Query вызова 1 — смысл параметров

`member_ids` — CSV id участников карточки (роль «участник»). `responsible_id`
— id ОТВЕТСТВЕННОГО, отдельная от `member_ids` ось: участник и ответственный —
разные роли карточки, сервер фильтрует по ним независимо, значение одной оси
не подставляется в другую. `condition` — целое, закрытый список: `1` активные,
`2` архивные. `states` — CSV чисел из закрытого списка состояния карточки
(`1` queued, `2` in progress, `3` done) — фильтр по полю `state`. `space_id`,
`board_id`, `column_id` — целые id соответствующих сущностей. `lane_id` —
**единственного числа**; плюральный `lane_ids` сервер принимает без ошибки,
но молча игнорирует — фильтр не применяется. `updated_after`/`updated_before`
— строки ISO-8601 (`YYYY-MM-DDThh:mm:ssZ`), окно по полю `updated` карточки;
неизвестные имена параметров сервер молча игнорирует, поэтому имена точны.

### Формы данных

- **Карточка (список)** — элемент ответа вызова 1: `id` (целое), `title`
  (строка), `state` (целое, закрытый список 1/2/3), `condition` (целое),
  `due_date` (строка|null), `updated` (ISO-8601|null), `board_id`/`column_id`/
  `lane_id` (целое|null), `archived` (булево), `last_moved_at` (строка|null),
  `time_spent_sum` (целое|null, минуты — сумма по карточке всеми участниками);
  вложенные `board {id, title, spaces: [{title, …}]}`, `column {title}`,
  `lane {title}`, `type {name}` — источник подписи места и типа карточки.
- **Карточка (полная)** — ответ вызовов 2/6/7/8: `id`, `key` (строка|null —
  человекочитаемый код карточки), `title`, `state`, `condition`, `due_date`,
  `size_text` (строка|null), `created`, `updated` (ISO-8601|null), `description`
  (строка|null, GFM markdown), `time_spent_sum` (целое|null, минуты); вложенные
  `board {id, title}`, `column {id, title}`, `lane {title}`, `type {name}`,
  `owner` («Участник»|null), `timer` («Таймер»|null — ТОЛЬКО таймер текущего
  пользователя по токену, не любой запущенный на карточке; null = не запущен),
  `tags` (массив имён тегов), `members` (массив «Участник»), `files` (массив
  «Файл»), `properties` (объект строка→строка, ключи вида `id_NNN`),
  `checklists` (массив «Чек-лист»).
- **Комментарий** — ответ вызовов 3/4/5: `id`, `text` (строка, GFM markdown),
  `created` (ISO-8601|null); вложенный `author {id, full_name, username}`.
- **Файл** — ответ вызова 13, элемент `files[]` карточки: `id`, `url`, `name`,
  `mime_type` (строка|null), `comment_id` (целое|null — null = файл уровня
  карточки, иначе id комментария-владельца), `card_cover` (булево),
  `custom_property_id` (целое|null — null = не привязан к полю, иначе id
  кастомного файлового поля).
- **Участник** — `id`, `full_name`, `email`, `username`.
- **Таймер** — `id`, `card_id` (целое|null), `card_title`, `comment`,
  `started_at`/`finished_at` (строка|null), `card_time_log_id` (целое|null —
  заполняется только после остановки таймера).
- **Чек-лист** — ответ вызова 10: `id`, `name`, `items` (массив «Пункт
  чек-листа»).
- **Пункт чек-листа** — ответ вызовов 11 и 12: `id`, `text`, `checked` (булево),
  `sort_order` (дробное|null — вес сортировки среди пунктов чек-листа). Сверх
  этой формы сервер несёт служебные поля пункта (моменты создания и изменения,
  автор отметки, момент отметки, признак удаления, срок, ответственный); в форму
  каталога они не входят — ни один из 14 вызовов их не задаёт.
- **Перемещение** — элемент ответа вызова 9: `card_id`, `column_id`
  (целое|null), `lane_id` (целое|null), `author_id` (целое|null), `author_name`
  (строка|null), `changed` (строка ISO-8601 UTC|null) — момент смены.

## Побочные эффекты

Сеть — только Kaiten API, эндпоинты из таблицы выше. Вызовы 4/5/6/7/8/10/11/
12/13/14 мутируют состояние карточки на стороне Kaiten. Локального состояния
(SQLite, файлы) каталог не пишет и не читает — кэш справочников и журналы
действий ему неизвестны.

## Инварианты

- `lane_id` в фильтре вызова 1 — единственного числа; `lane_ids` сервер молча
  игнорирует, фильтр по дорожке в этом случае не применяется.
- `responsible_id` — отдельная ось от `member_ids`, не синоним и не альтернатива.
- Файл привязывается к файловому (attachment) кастомному полю ТОЛЬКО вызовом
  13; обычная загрузка файла карточки поле не заполняет.
- Замена описания (вызов 7) — полная замена содержимого, не патч фрагмента.
- Kaiten-редактор описания не поддерживает интерактивные GFM-чекбоксы: `- [ ]`
  в `description` рендерится обычным текстом списка, не отмечаемым пунктом.
  Единственная сущность с интерактивными чекбоксами в Kaiten — чек-лист
  карточки (вызовы 10–12).
- Вызов 8: `value: null` в `properties` — валидная операция очистки поля, не
  ошибка ввода.
- Вызов 11: `sort_order` не передан — сервер ставит пункт в конец списка;
  явное значение фиксирует позицию.
- Удаление файла (вызов 14), привязанного к кастомному полю, автоматически
  очищает значение этого поля на карточке — отдельного вызова на очистку
  поля не требуется.

## Граничные случаи и ошибки

- Ни один из 14 вызовов не имеет кодов ошибок сверх общего формата не-2xx
  (см. «Retry и ошибки» в `platform/kaiten-http.md`).
- Вызов 1 с `lane_ids` (множественное число) вместо `lane_id` → ответ 200,
  но фильтр по дорожке не применяется — результат как без него.
- Карточка без комментариев / без истории перемещений → вызовы 3/9 отвечают
  пустым массивом, не ошибкой.
- Чек-лист сразу после создания (вызов 10) → `items` пуст; пункты добавляются
  отдельными вызовами 11.

## Golden-примеры

Успех — по одной паре «запрос → ответ» на каждый из 14 вызовов, синтетические
данные (вымышленные id/имена):

| # | Вызов | Фикстура демонстрирует |
| - | - | - |
| 1 | `GET /cards` | страница с фильтрами `member_ids`+`states`, вложенные `board`/`column`/`lane` |
| 2 | `GET /cards/{id}` | полная карточка с непустыми `members`, `files`, `properties`, `checklists`, `timer` не null |
| 3 | `GET /cards/{id}/comments` | 2+ комментария хронологически, `text` с GFM-разметкой |
| 4 | `POST /cards/{id}/comments` (JSON) | комментарий без вложений |
| 5 | `POST /cards/{id}/comments` (multipart) | комментарий с двумя файлами, `comment_id` у обоих файлов |
| 6 | `PATCH /cards/{id}` (перемещение) | тело только с `column_id`+`lane_id`, без `board_id` |
| 7 | `PATCH /cards/{id}` (описание) | тело с `- [ ]` в `description` |
| 8 | `PATCH /cards/{id}` (свойство) | `value: null` — очистка |
| 9 | `GET /cards/{id}/location-history` | 2+ записи разных авторов |
| 10 | `POST /cards/{id}/checklists` | ответ с пустым `items` |
| 11 | `POST .../items` | вызов без `sort_order` и вызов с явным `sort_order` |
| 12 | `PATCH .../items/{id}` | `checked: true` в запросе, ответ — тот же пункт с `checked: true` и неизменным `sort_order` |
| 13 | `PUT .../custom-properties/{id}/files` | ответ с `custom_property_id`, равным id поля |
| 14 | `DELETE .../files/{id}` | пустое тело ответа |

Ошибка — одна пара на класс: `PATCH /cards/{id}` на несуществующий `card_id` →
404 в общем формате транспорта.

Граница — вызов 1 с `lane_ids` вместо `lane_id` (фильтр молча не применяется,
раздел «Граничные случаи»); вызов 11 без `sort_order` (пункт в конце списка).
