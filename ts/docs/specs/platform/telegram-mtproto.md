# platform/telegram-mtproto

Статус: реализовано — в «RPC error» оформляется только отказ клиента, классификация одна на сеанс и вход («Ошибки и коды выхода», порция 135, `f9824eb`+`07628f0`; живьём: ls/search/send — код 0, несуществующий чат — прежний текст, мёртвый прокси — код 1 за 20 с); предел первого ответа у входа 60 с (порция 133, `b1993f4`; живой вход со сменой DC не проверялся — отзывает сессию); предел первого ответа после соединения 20 с у сеанса, гашение клиента после отказа — реализовано (порция 132, `b6fe5af`, принято живьём: молчащий узел за туннелем — код 1 за 20,26 с); предел соединения 20 с и логи клиента не в stdout — реализовано (порция 131, `a8ada35`, принято живьём); код выхода отдельного входа при сбое — порции 129–130 (`fe06bcb`, `bee48de`). 2026-09-14: wasm из бинаря (порция 124, `9c3361b`), сбой криптографии в сеансе не «не авторизован» (порция 126, `7131b7e`), текст сбоя криптографии при входе (порция 128, `2771212`).

## Назначение

Сеанс Telegram от имени личного аккаунта (протокол MTProto, не бот) — общая
часть всех подкоманд `telegram`: конфигурация, строка сессии, прокси, открытие
и закрытие соединения, приведение адресата к виду, понятному клиенту, и
раскладка ошибок по кодам выхода. Своей CLI-поверхности у слоя нет.

## Возможность

- **Открыть сеанс**: конфигурация → подключённый авторизованный клиент.
  Закрытие — обязанность вызывающего и происходит в любом исходе.
- **Резолв адресата**: строка пользователя → адресат, пригодный для операции.
- **Классификация ошибки**: отказ → текст одной строкой и код выхода.

## Конфигурация

Значения читаются из env-файла (слой — `platform/env-file.md`).

- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — обязательны. Отсутствие любой:
  stderr начинается с `telegram: environment variable <ИМЯ> is not set.` (далее
  в тексте — путь env-файла), exit 1. Нечисловой `TELEGRAM_API_ID` →
  `telegram: TELEGRAM_API_ID должен быть числом, получено '<строка>'`, exit 1.
- `TELEGRAM_SESSION` — строка сессии (см. ниже). Пустая или не принятая
  клиентом → до любой операции `` telegram: не авторизован; запусти `mpu init` ``,
  exit 1. Тот же текст и тот же код даёт **отозванная** сессия: строка разбирается,
  но учётной записи за ней больше нет. Различать эти два случая пользователю
  незачем — действие одно и то же.
- Сбой, не относящийся к сессии, — прежде всего не поднялась криптография
  клиента (встроенный модуль не найден в сборке, нет права его прочитать), —
  «не авторизован» **не** печатает: совет пройти вход здесь вреден, вход
  отзывает действующую сессию. Текст — `telegram: криптография клиента не
  поднялась: <первая строка причины>`, exit 1. «Не авторизован» остаётся
  только для строки сессии, которую клиент не принял, и отозванной сессии.
  Текст одинаков для всех подкоманд, включая вход (`mpu telegram login`): там
  сбой криптографии тоже печатается этим текстом, а не обёрткой ошибки
  операции (`telegram: RPC error: …` — замер отчёта порции 126). Код выхода
  у входа свой: сбой входа — это «пропущено» с кодом 0
  (`telegram-login.md`, инвариант 3), и текст идёт в скобки:
  `# telegram: пропущено (telegram: криптография клиента не поднялась: …)` —
  и у отдельного `mpu telegram login`, и у шага `mpu init`. «exit 1» выше —
  для `send`/`ls`/`search`/`status`. (Исправлено 2026-09-14: прежняя редакция
  этого пункта называла exit 1 и для отдельного входа, что противоречило
  инварианту 3.)
- `TELEGRAM_DEFAULT_CHAT` — адресат по умолчанию для подкоманд, которые кому-то
  пишут. Пустое значение равнозначно незаданному.
- `TELEGRAM_PROXY` — прокси, применяемый только к Telegram. Не задан → берётся
  `HTTPS_PROXY`, затем `https_proxy`.

## Строка сессии — внешняя граница

`TELEGRAM_SESSION` — не внутреннее представление, а разделяемое значение: её
пишет шаг входа `mpu init` (`init.md`), и пока переезд не закончен, одну и ту же
строку читают обе реализации команды. Отсюда два обязательных требования:

- строка принимается **как есть**, без повторного входа оператора;
- команда её **не переписывает**: после любой операции значение в env-файле
  побайтово прежнее.

Оба требования проверяемы: снять значение до вызова и после, сравнить; вызов на
строке, записанной входом, обязан дойти до операции.

## Прокси

Значение — URL. Схема задаёт вид туннеля: `http`, `https` — CONNECT; `socks5`,
`socks5h` — SOCKS5; `socks4`, `socks4a` — SOCKS4. Схемы с `h`/`a` — синонимы
основных: они означают резолв имён на стороне прокси, а адреса узлов Telegram
приходят числовыми, поэтому наблюдаемой разницы нет.

- `host:port` обязателен; порт отсутствует → `telegram: в прокси-URL нужен
  host:port — '<url>'`, exit 1.
- Учётные данные — в форме `user:pass@`; percent-последовательности
  декодируются (`%40` → `@`).
- Иная схема → `telegram: неподдерживаемая схема прокси '<схема>'; попробуй:
  http/https/socks5/socks4`, exit 1.

Ловушка, которую слой обязан оставить видимой: `HTTPS_PROXY`, заданный в
env-файле, проксирует не только Telegram, а весь инструмент; `TELEGRAM_PROXY`
такого действия не имеет.

**Соединение с Telegram ограничено по времени.** Если соединение с узлом
Telegram (через прокси или напрямую) не установлено за **20 с**, операция
отказывает: `telegram: нет соединения с Telegram за 20 с: <первая строка
причины>` (причина — последний отказ соединения, например
`ConnectionRefused`), exit 1; у входа (`mpu telegram login`, шаг `mpu init`)
это сбой самого входа — пропуск с этим текстом, код 0
(`telegram-login.md`, инвариант 3). Бесконечные переподключения без
предела недопустимы: вызов через MCP-службу иначе не отвечает никогда.
Замер 2026-09-14 (установленный бинарь `2771212`, `TELEGRAM_PROXY` на
закрытый порт петли): `mpu telegram ls --limit 1` висит, снят через 40 с.
Реализовано порцией 131 (`a8ada35`): тот же замер — код 1 за 20,25 с, stdout
пуст; живой сеанс — код 0 за 0,7 с.

- Если за 20 с не пришло ни успеха, ни отказа соединения, `<первая строка
  причины>` — `узел не ответил`.
- **Первый ответ после соединения тоже ограничен.** Узел или прокси, принявший
  соединение и молчащий (или рвущий его) до первого ответа, иначе держит
  вызов без конца (замер разбора 131: `openSession` висит > 30 с, stderr —
  `unhandled error` каждые 3–5 с). Первый ответ — у сеанса ответ на запрос
  собственного пользователя (`getMe`), у входа — ответ на первый запрос
  входа, до вопроса кода. Не пришёл за **20 с** после установки соединения →
  `telegram: нет ответа от Telegram за 20 с: <первая строка причины или
  «узел не ответил»>`, exit 1; у входа — пропуск с этим текстом, код 0.
  Ожидание ввода человеком (код, пароль) под предел не попадает.
  **У входа предел — 60 с**, текст соответственно `… за 60 с: …`: цепочка до
  вопроса кода при первом входе включает смену DC (`PHONE_MIGRATE` /
  `USER_MIGRATE` / `NETWORK_MIGRATE` — новый сокет, обмен ключами, повтор
  запроса) и встроенное ожидание flood-wait клиента (до 10 с, до 5 повторов);
  Telegram на этих шагах отвечает, но время идёт, и 20 с дали бы ложное «нет
  ответа» у законного входа (разбор порции 132). Вход редок, запас дешевле
  ложного пропуска. Предел сеанса (`getMe`) остаётся 20 с.
- После отказа по любому из пределов клиент погашен: попыток соединения и
  таймеров от этого вызова не остаётся — это существенно для службы MCP,
  исполняющей вызовы в долгоживущем процессе.
- **Известное ограничение (preserve):** обрыв соединения посреди уже идущей
  операции после первого ответа (многостраничный `search`, отправка файлов)
  этими пределами не ограничен — клиент переподключается сам; предел на всю
  операцию спека не вводит.

**Логи клиента не попадают в stdout.** stdout подкоманд — данные (JSON,
таблица, текст); сообщения библиотеки клиента (`[ERR] [client] …`) туда не
пишутся — либо в stderr, либо подавляются. Замер того же прогона: в stdout
оказалась строка `… [ERR] [client] [USER n/a] unhandled error:
ConnectionRefused…`.

**Во время работы сеть — только узлы Telegram (через прокси, если он задан).**
Код и двоичные модули клиента (в том числе `mtcute.wasm` криптографии) лежат в
собранной программе; открытие сеанса не скачивает ничего ни с реестров
пакетов (`jsr.io`, `deno.land`, `npm`), ни откуда-либо ещё, и не зависит от
переменных прокси окружения процесса. Наблюдаемо: запуск с очищенным
окружением (`env -i HOME=… PATH=…`) и заданным в env-файле `TELEGRAM_PROXY`
открывает сеанс, а TCP-соединения процесса идут только на хост:порт прокси
(без прокси — только на адреса узлов Telegram).

Замер 2026-09-14 (установленный бинарь, `TELEGRAM_PROXY=http://127.0.0.1:8888`
в env-файле): `env -i … mpu telegram ls --limit 1` висит (снят через 60 с), и
всё время у процесса одно соединение — на `104.21.7.32:443` (`jsr.io`), до
прокси он не доходит; тот же вызов с `HTTPS_PROXY` в окружении — 1,1 с,
соединения на `127.0.0.1:8888`. Причина: клиент грузит `mtcute.wasm` через
`fetch(new URL('./mtcute.wasm', import.meta.url))`, а у собранной программы
`import.meta.url` зависимости — адрес на `jsr.io`. Следствие для оператора:
служба MCP (окружение без прокси) не могла ни отправить, ни прочитать
сообщения, пока терминал с прокси в окружении работал. Бот (`telegram log`,
Bot API) wasm не грузит и не страдал. Вердикт — **fix**; к порции 111 не
относится (бинарь до неё ведёт себя так же). Реализовано порцией 124
(`9c3361b`, wasm встроен `--include` и читается из бинаря); принято живым
замером 2026-09-14: собранный бинарь с `env -i` — `telegram ls` за 1,1 с,
TCP только на `127.0.0.1:8888`.

## Резолв адресата

Вход — строка. Нормализация, по порядку: префикс `t.me` (со схемой `https://`,
`http://` или без неё) срезается, остаётся хвост без крайних `/` — пустой хвост
означает, что строку берут целиком; ведущий `@` срезается; строка из цифр с
необязательным ведущим минусом — это числовой id, не название; всё прочее идёт
как строка.

Строка из цифр длиннее безопасного целого числа (более 15 знаков) числовым
идентификатором **не** считается и идёт строкой: разбор такой строки в число
округлил бы её молча, и сообщение ушло бы в чужой чат. Отказ приходит от
резолва, а не от округления.

`me` — «Избранное», собственный чат пользователя. Ему предшествует определение
себя: адресат `me` резолвится только после того, как сеанс узнал собственную
учётную запись.

Явно указанный адресат всегда приоритетнее значения из env-файла.

Порядок резолва строки — **две попытки, а не одна**:

1. штатный резолв клиентом: `me`, числовой id, имя пользователя, ссылка `t.me`,
   телефон;
2. **если он не удался** — поиск чата по названию (`telegram-ls.md`, «Резолв по
   названию»).

Вторая попытка обязательна и для строки, которая выглядит именем пользователя:
`news` — валидное имя пользователя по форме, но если такого имени нет, это
скорее всего название чата, и отказ на первой попытке останавливать команду не
должен.

Исключение — строка, где пользователь **объявил вид сам**; на ней второй
попытки нет, а отказ резолва так и остаётся отказом резолва:

- ведущий `@` и ссылка `t.me` — объявлено имя пользователя;
- ведущий `+` перед цифрами — объявлен телефон. Чат с названием-номером —
  редкость, а подмена ответа Telegram («номер не найден») на «не удалось найти
  чат '+79990000000': совпадений нет» уводит от настоящей причины. Строка из
  одних цифр сюда не относится: она разбирается как числовой id ещё
  нормализацией.

Сам поиск по названию живёт в `telegram-ls.md`.

## Инварианты

- Один вызов — один сеанс: соединение открывается заново и закрывается в любом
  исходе, включая отказ авторизации и ошибку операции.
- Авторизация проверяется до операции; ошибки ввода (код 2) обнаруживаются до
  открытия соединения, то есть без единого сетевого обращения.
- Секреты не попадают ни в stdout, ни в stderr: `TELEGRAM_API_HASH`, строка
  сессии, пароль прокси не появляются в выводе ни при каком отказе, включая
  сообщения об ошибках разбора URL прокси — в них остаётся URL без учётных
  данных.

## Ошибки и коды выхода

- **2** — ошибки ввода: отсутствующий или пустой адресат, невалидные значения
  флагов. Обнаруживаются до сети.
- **1** — конфигурация (см. выше) и Telegram: rate-limit → `telegram:
  rate-limit, подожди <N>s`; прочий отказ протокола → `telegram: RPC error:
  <текст>`.
- **1** — сбой вне Telegram и слоя клиента: дефект собственного кода
  (например `TypeError`), отказ записи файла вложения и т. п. — **исходным
  текстом ошибки**, без переоформления в `telegram: RPC error: …`
  (`mpu: unexpected error: <текст>` точки входа).
- **0** — успех.

**Что считается отказом Telegram / слоя клиента (2026-09-14).** В строку
`telegram: …` (rate-limit, `RPC error`) оформляется только отказ, пришедший
от клиента Telegram: ошибка протокола (`tl.RpcError` клиента), ошибка
библиотеки клиента (`MtcuteError` и наследники), сбой криптографии,
отказ по пределам соединения/первого ответа, уже оформленные слоем строки.
Всё прочее — не отказ Telegram и не переоформляется. Правило одно для всех
подкоманд: `send`, `ls`, `search`, `status`, резолв адресата, вход
(`telegram-login.md`, «Что считается сбоем самого входа»). Различение — по
типу ошибки, а не по тексту; решает его модуль, который сам загружает
клиент Telegram (сеанс и вход), — лёгкий слой ошибок, общий для всех команд,
библиотеку клиента не загружает (иначе старт каждой команды тянул бы клиент
с модулем криптографии). Причина правила — та же, что у входа: ошибка
программы, выданная за «Telegram отказал», прячет дефект (отчёт порции 130:
`telegramOperation` переоформлял любой не-Verbatim отказ, в том числе
дефект своего кода).

Формат строки ошибки — `telegram: <причина>[; попробуй: <подсказка>]`, одна
строка, без трейсбеков.

## Известные отклонения

- **preserve** — у объявленного вида (`@`, ссылка, телефон) отказ первой
  попытки печатается с причиной, как её назвал клиент Telegram: строка
  английская и для телефона говорит про `username`
  (`не удалось найти чат '+79990000000': Peer with username +79990000000 was
  not found`). Своего текста здесь нет намеренно: причина приходит от внешней
  системы и различает случаи точнее, чем любая наша замена. Цена названа
  замером 2026-08-17.
- **fix** — ошибки ввода прежняя реализация завершает кодом 1, не отличая их от
  отказов Telegram. Правильно — код 2 и проверка до сети; тексты неизменны.
- **fix** — при отказе резолва прежняя реализация имеет два разных пути с
  похожим текстом: собственно неудачу резолва (с подсказкой) и исключение,
  выброшенное уже самой операцией отправки, которое оформляется как «не удалось
  найти чат» без подсказки. Второй путь маскирует ошибку операции под ошибку
  адресата. Правильно — резолв один: если адресат получен, отказ операции
  сообщается как отказ операции.
- **preserve** — прокси задаётся одним URL, а не набором полей: это формат,
  который уже лежит в env-файлах операторов, и менять его переезд не вправе.

## Открытые вопросы

Замечания исполнителя порции 135 (поведение было до порции, код не менялся):

- Rate-limit при резолве объявленного вида адресата (`@имя`, телефон)
  выходит текстом «не удалось найти чат 'x': Telegram API error 420:
  FLOOD_WAIT_%d; …» — срок ожидания теряется. Отличать ли rate-limit от «не
  найден»?
- Адресат без идентификатора в «не удалось найти» даёт двойной префикс
  «…: telegram: Telegram вернул адресата без идентификатора…».
- Сбой криптографии в резолве попал бы в «не удалось найти» многострочной
  причиной; живьём недостижим (криптография поднимается при входе в сеанс).
- Ветка альбома `send` (несколько вложений) тестом места вызова
  классификатора не исполняется.
