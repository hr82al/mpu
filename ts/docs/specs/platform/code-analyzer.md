# platform/code-analyzer — разбор кода рабочей области

Статус: реализовано (2026-09-09, порции 99–104; ответ сверен живым прогоном по рабочей области. Заморожена 2026-09-08; дерево-фикстура и голдены —
`fixtures/code/`, факты сняты оракулом полноты на самом дереве)

## Назначение

Общий слой команд семейства `mpu code`: из чего строится ответ о связях
кода, какую гарантию он несёт и чем эта гарантия проверяется.
Поверхности команд — `specs/code-refs.md`, `specs/code-twins.md`,
`specs/code-name.md`, `specs/code-mentions.md`.

Смысл слоя один: **ответ полон либо назван неполным**. Ссылка, которую
разобрать не удалось, попадает в отдельный раздел с причиной; молча
выпасть она не может. Инструмент, тихо выбрасывающий неразобранное,
выдаёт уверенный неверный ответ.

## CLI-контракт

нет (общий слой; флаги — в спеках команд).

## Ввод/вывод

**Рабочая область** — ближайший каталог-предок текущего рабочего
каталога, содержащий файл-сентинел `.mp-workspace-root`. Ключа конфига у
неё нет: сентинел уже лежит в корне и служит той же цели соседнему
тулингу, а новый ключ пришлось бы вносить в замороженный реестр
(`platform/config.md`) и пересобирать его голдены. Сентинела нет ни у
одного предка — отказ.

Её **репозитории** — подкаталоги первого уровня, содержащие `.git`.
Список нигде не зашит: он снимается с диска на каждый вызов.

Обход состава проекта не заходит в каталоги, начинающиеся с точки, и в
`node_modules`. Правило нужно явно: у проекта вида Deno отсечь их иначе
нечем, а в кэше (`.deno`) лежат тысячи `.ts`, и попади они в программу —
ответ стал бы неверным молча. Полагаться на то, что репозиторий сам
перечислил их в `exclude`, нельзя: это совпадение, а не устройство.

**Проект** внутри репозитория — одно из двух, вне `node_modules` и
`dist`:

- файл `tsconfig.json` (ровно это имя), у которого разрешается непустой
  список файлов. Имена вида `*.base.json`, `*.build.json`,
  `*.spec.json` проектами не считаются: они либо не перечисляют
  исходников, либо сужают уже покрытый набор;
- файл `deno.json` или `deno.jsonc` — корень конфигурации Deno.
  Опции разбора такому проекту задаёт сам слой (модули `ESNext`,
  резолвинг `bundler`, импорт с расширением `.ts` разрешён), состав —
  все `.ts`/`.tsx` его каталога вне `exclude` конфигурации.

Второй вид обязателен, а не удобство: без него репозиторий на Deno
целиком не имеет проектов, и команда отказывает по нему на любой вопрос
о символе — проверено живым прогоном. Разбор при этом работает: внешние
пакеты (`jsr:`, `npm:`, `@std`) не разрешаются и попадают в «не
разрешено» поимённо, а внутренний граф относительных импортов
разрешается целиком, и перечень совпадает с ответом `deno check`
(замер 2026-09-08).

Файл репозитория, не попавший ни в один проект, обслуживается
текстовым анализатором.

**Исключения тестов снимаются.** Список файлов проекта берётся из его
конфигурации, после чего `exclude` заменяется фиксированным списком
`["**/node_modules/**", "<outDir>/**"]`, где `outDir` — значение из
конфигурации проекта, по умолчанию `dist`. Пустым `exclude` не
заменяется: проект с `include: ["**/*"]` затянул бы в программу
зависимости. Снимаются, таким образом, все исключения кода — и никакие
исключения артефактов.

Причина измеримая: на дереве-фикстуре ответ по штатной конфигурации даёт
**шесть** файлов-потребителей `addDays`, а со снятыми исключениями —
**семь**;
разница ровно `src/report.spec.ts`, отсечённый шаблоном `**/*.spec.ts`.
Имена тестов при этом никуда не зашиваются: `src/seed_test.ts` тем же
шаблоном не описывается вовсе, а потребителем является.

### Анализатор

Анализатор отвечает за один репозиторий и умеет ровно четыре вещи:

| Операция | Что возвращает |
| --- | --- |
| отметка дерева | репозиторий, ветка, коммит, признак незакоммиченных изменений |
| объявления файла | имя, сигнатура, строка, область видимости (ниже) |
| потребители цели | места использования + ссылки, которые не разрешились |
| тела | тело каждого объявления-функции с его нормализованной формой |

Всё остальное выводится из них и **ровно в одном месте**: читатели
модуля — потребители цели-модуля; близнецы — группировка тел; занятость
имени — отбор объявлений; упоминания пути — потребители у текстового
анализатора.

**Форма получения символа значения не имеет.** Потребителем считается
файл, который переименование символа ломает, — чем именно он символ
получил, вопрос второго порядка: статический `import`, `export … from`,
алиас конфигурации, динамический `import()`, `import x = require()`.
Перечень, собранный по перечислению форм импорта, теряет остальные
молча — под шапкой «ответ полон». Замер на дереве-фикстуре: без
динамического импорта оракул даёт семь файлов, а такой перечень — шесть.

Обратное тоже верно: файл, который символа не берёт, в перечень не
попадает, даже если модуль импортирует. Голый `import "./a.ts"` имён не
приносит; `import * as A` считается по обращениям `A.имя`, а не по
самому импорту.

**Область видимости** объявления — одно из четырёх значений, и
печатается оно одной строкой, не двумя:

- `экспортируется из модуля и из входа проекта`;
- `экспортируется из модуля; из входа проекта не реэкспортируется`;
- `экспортируется из модуля; входа у проекта нет`;
- `приватное в модуле`.

Ещё два значения появляются, когда вход **не определён**: манифест не
разобрался либо разобрался не в объект. Они не сливаются с «входа нет» —
это разные ответы, и причина называет, что именно не так, а не подменяет
одно другим. Различаются они кодом диагностики, не текстом сообщения.

Пустой, пробельный и состоящий только из комментариев манифест — это
**не** третий случай: он разбирается в `{}`, то есть читается и полей
входа не объявляет, и ответ тот же, что у пакета без манифеста вовсе —
`входа у проекта нет`. Названо здесь, чтобы молчание спеки не читалось
как пропуск.

**Вход проекта** — объявленный входом файл, **входящий в программу
проекта**. Поля просматриваются в порядке `types`, `exports`, `main`
(`package.json`) либо `exports` (`deno.json`/`deno.jsonc`); ни одно не
указывает на файл программы — `index.ts` в общем корне исходников; нет
и его — входа у проекта нет, и второе значение области видимости
принимает вид `экспортируется из модуля; входа у проекта нет`.

Оговорка «входящий в программу» не формальность: у живого пакета `main`
указывает на `dist/index.js` — артефакт сборки, которого в программе
нет. Правило «берём поле входа» без этой оговорки объявляло вход
отсутствующим у пакета, где он есть, и символ, реэкспортированный
наружу, выглядел видимым только из своего модуля (проверено живым
прогоном).

Реализаций две, с одним набором операций и разной гарантией:

| Вид репозитория | Анализатор | Гарантия |
| --- | --- | --- |
| есть хотя бы один проект | по типам | полная: перечень равен оракулу |
| проектов нет; файл вне всех проектов | текстовый | неполная, помечена в каждом разделе |

Анализатор, который не удалось построить, отвечает на все четыре
операции отказом с причиной — он не отсутствует и не подменяется
пустым результатом.

**Двух операций у текстового анализатора нет вовсе.** Объявления и тела
он выдать не может: выделить тело без разбора — угадывание по
скобкам, а объявление, записанное стрелкой, текстовый поиск не находит
(в дереве-фикстуре это `src/span.ts`). Обе операции отвечают у него
**названным незнанием**, и команда превращает его в отказ с причиной
(exit 1), а не в пустой раздел: пустые разделы читались бы как
«потребителей нет», «близнецов нет» и «имя свободно», а это другие
ответы. Протокол при этом
цел — незнание есть ответ операции, а не её отсутствие.

Отсюда следствие, которое стоит назвать прямо: **объявления текстовый
анализатор не печатает никогда**. Все три поверхности, которым они
нужны — потребители символа, близнецы, занятость имени, — отвечают в
таком репозитории отказом. Печатать «сигнатуры нет» и «область видимости
неизвестна» негде и не нужно: строка символа в этих ответах не
появляется вовсе.

Что текстовому анализатору доступно — читатели модуля (адрес без строки)
и упоминания пути: и то и другое выводится из текста честно, с
пониженной гарантией.

### Отметка дерева

Отметка — отдельная операция, и её источник задаётся при создании
анализатора. Рабочий источник — git; в тестах подставляется постоянная
отметка.

Шапка раздела — поля через ` · `:

    РЕПОЗИТОРИЙ · ВЕТКА · КОММИТ · СОСТОЯНИЕ · ГАРАНТИЯ
    РЕПОЗИТОРИЙ · вне git · ГАРАНТИЯ

- **ВЕТКА** — имя текущей ветки; голова отделена — слово `detached`;
- **КОММИТ** — первые восемь знаков полного хэша. Длина фиксирована:
  сокращение средствами git плавает от репозитория к репозиторию, а
  вывод обязан быть детерминированным;
- **СОСТОЯНИЕ** — `дерево чистое` либо
  `дерево содержит незакоммиченные изменения`;
- **ГАРАНТИЯ** — `разбор по типам — ответ полон` либо
  `текстовый разбор — ответ неполон`.

Дерево вне git — отметка `вне git` вместо трёх полей; это ответ, а не
отказ. Примеры обеих форм:

    ozon · feat/checklist/serving/screen-data-endpoint · 989c0bf9 · дерево чистое · разбор по типам — ответ полон
    fixture · вне git · разбор по типам — ответ полон

Ответ читается **с рабочего дерева**, а не из объектов git: правка, ещё
не закоммиченная, видна в ответе. Поэтому отметка обязательна и печатается
в шапке каждого раздела; дерево с незакоммиченными изменениями помечается,
но ответ выдаётся.

### Стоимость ответа

Кэша у слоя нет, и два правила держат цену без него.

**Репозитории обходятся параллельно.** Они независимы, разделы ответа
раздельные, и вопрос по всей рабочей области стоит не сумму, а максимум
по самому тяжёлому репозиторию. Замер последовательного обхода —
**19.3 с** на тринадцати репозиториях: без параллельности порог не
держится с двукратным запасом.

Параллельность здесь — отдельные потоки исполнения, и это замер, а не
предпочтение: построение программы синхронно от начала до конца, поэтому
промисы совмещают только походы за отметкой. Три репозитория по 575
файлов: последовательно **2.97 с**, промисами **2.67 с**, потоками
**1.66 с**; через команду целиком — **3.65 с** против **1.78 с**. Реализация
на промисах даёт зелёные тесты и несобранный порог, поэтому число стоит
здесь, а не в отчёте.

**Один репозиторий считается на месте.** Цена потока — не его запуск, а
загрузка компилятора в него: `mentions` четырьмя потоками стоит 0.06 с
против 0.00 с на месте, `name` по одному репозиторию — 1.31 с на месте
против 1.78 с потоками. Вопрос с окном `--in РЕПОЗИТОРИЙ` этих полсекунды
не платит.

**У `name` и `mentions` строятся только проекты, покрывающие окно.**
Ответ на эти вопросы лежит внутри окна, соседние проекты ему не нужны;
`mentions` не строит программ вовсе. Следствие, наблюдаемое в ответе:
раздел «не разрешено» у `name --in РЕПОЗИТОРИЙ:КАТАЛОГ` описывает окно, а
не репозиторий целиком — ссылок из проектов вне окна в нём нет. Окно,
покрытое построенными проектами не полностью, достраивается пропущенными:
файл окна может не значиться ни в одном списке состава и попадать в
программу соседа импортом, и без этой достройки ответ был бы неполон
молча. У `refs` и `twins` так нельзя:
потребитель и близнец живут в любом проекте репозитория, и сужение
обхода там теряло бы их молча.

Порог — не «до 1.5 с»: это замеренная цена построения программы над
тысячами файлов, и укладкой она не убирается. Ожидание такое: вопрос по
малому репозиторию — до 2 с, по большому — **до 8 с**, по всей рабочей
области — **до 9 с** за счёт параллельного обхода.

**Сколько репозиториев в рабочей области, спека не знает и знать не
должна** — список снимается с диска. Замер 2026-09-09: их оказалось
**тринадцать**, а не восемь, как предполагала постановка по таблице
документации монорепо; пять (`code-index`, `mp-support-scripts`,
`mp-web-app`, `opiu-service`, `sl-front`) в ней не описаны вовсе.
Поэтому ни одно правило здесь не опирается на число.

Числа сняты живыми прогонами 2026-09-08/09 (24 проекта в описанных
репозиториях: `10x-ozon` 10, `ozon` 8, `sw-back` и `sw-front` по 2,
`sl-back` 1, `mpu` 1 вида Deno):

| Вопрос | Время |
| --- | ---: |
| `mentions` (программа не строится вовсе) | 0.39 с |
| `name --in mpu` (1 проект, 575 файлов) | 1.8 с |
| `refs` по символу `ozon` | 5.2 с |
| `name --in ozon:packages/contracts` (окно — пакет) | 5.4 с |
| `name --in sl-back` (1 проект, 4047 файлов, `checkJs`) | 6.8 с |
| `name --in ozon` (репозиторий целиком) | 7.4 с |
| `name` без окна, вся рабочая область, обход последовательный | 19.3 с |

После порции 104 (параллельный обход и построение только проектов окна),
замер 2026-09-09 на тех же вопросах:

| Вопрос | Было | Стало |
| --- | ---: | ---: |
| `name --in ozon:packages/contracts` | 5.4 с | **1.2 с** |
| `name` без окна, вся рабочая область | 19.3 с | **8.4 с** |
| `refs` по символу `ozon` | 5.2 с | 5.3 с — не меняется, и не должно: сужать обход у `refs` нельзя |

Порог по всей рабочей области назван по замеру — **до 9 с**: получилось
8.4 с, три прогона подряд в пределах 0.2 с. Обещать «до 8» значило бы
подогнать порог под красивое число вместо измеренного. Дальше без кэша не сжимается — это цена построения программ
самого тяжёлого репозитория, а он строится всегда.

Решающая строка — две последние: **сужение окна по каталогу стоимость
почти не снижает**, потому что платится построение программ всех
проектов репозитория, а не размер ответа. Отсюда и оба правила выше.

Кэша у слоя нет. Ответ строится на каждый вызов из текущего состояния
файлов: индекс, собранный на одной ветке и прочитанный на другой,
уверенно врёт, а репозитории рабочей области со своими ветками делают
его инвалидацию дороже самого ответа.

### Форма ответа

Всякий ответ состоит из трёх частей, и ни одна не опускается:

1. **отметка дерева** — шапка раздела;
2. **найденное** — разделы своей команды;
3. **не разрешено** — по строке на ссылку, которую не удалось
   разрешить, с причиной; пусто — печатается `не разрешено: 0`.

Раздел «не разрешено» печатается **всегда**, в том числе нулевой:
его отсутствие читалось бы как «всё разрешилось».

Пустой раздел найденного означает «совпадений нет» и остаётся ответом.
Невозможность ответить — другой вид: отказ с причиной, разделов
найденного у него нет.

**Отказавший раздел печатается без гарантии.** Гарантия — свойство
ответа: она говорит, насколько полон перечень. Там, где перечня нет,
заявлять о его полноте нечего, а «текстовый разбор» было бы неправдой —
текстового разбора там тоже не было. Отметка дерева при этом остаётся:
её снимает git, а не анализатор.

    РЕПОЗИТОРИЙ · ВЕТКА · КОММИТ · СОСТОЯНИЕ
      отказ: <причина>

Ни разделов найденного, ни «не разрешено» у такого раздела нет — их дать
нечему.

**Запись** — одна найденная вещь: потребитель, тело, объявление,
упоминание. Сколькими строками она печатается, зависит от поверхности:
у `name` запись занимает две строки, у прочих — одну. Предел `--limit`
и счётчик `усечено: показано N из M` считают **записи**, а не строки:
предел в строках означал бы право оборвать запись на половине.

Порядок строк задаёт слой: `(репозиторий, путь, строка)`. Времени в
выводе нет ни в каком виде.

Каждая поверхность stdout оканчивается **одним переводом строки**.

## Побочные эффекты

Чтение файлов рабочих деревьев и вызовы `git` только для чтения
(`rev-parse`, `symbolic-ref`, `status --porcelain`). Сети нет. Ни один
репозиторий не изменяется — ни файлами, ни индексом git. Артефактов
внутри репозиториев рабочей области слой не создаёт.

## Кто спрашивает и как он узнаёт про команды

Главный потребитель семейства — агент, правящий код: три вопроса, ради
которых слой заведён, возникают именно у того, кто собирается
переименовать символ, внести новую функцию или перенести файл. Отсюда два
требования, без которых команда есть, а пользы от неё нет.

**Все четыре публикуются тулами в профиле `ro`.** Список публикации
закрыт и fail-closed (`platform/mcp-server.md`), поэтому отсутствие
записи в нём — не нейтральное умолчание, а решение «агент этих команд не
увидит». Ничего опасного в публикации нет: слой только читает, ответ
детерминирован, объём режется `--limit`. Замер 2026-09-09: в списке их не
было, и сессия, работающая через сервер, пользовалась текстовым поиском
там, где у неё был исчерпывающий ответ.

**Однострочник и первый абзац справки называют повод звать, а не состав
ответа.** Описание тула собирается из них (`summary` плюс текст справки),
и по ним читающий решает, брать ли инструмент. «Связи кода рабочей
области: ссылки, близнецы, имена, упоминания» перечисляет части и повода
не называет; называть надо момент работы — перед переименованием,
удалением, переносом, внесением нового имени — и то, чем ответ отличается
от текстового поиска: он либо полон, либо сам говорит, где неполон.
Остальная справка уже написана по составу и переписывания не требует.

## Конфигурация

Своих ключей у слоя нет, и реестр конфига (`platform/config.md`)
остаётся замороженным: корень рабочей области находится по сентинелу
`.mp-workspace-root`, а не настраивается. Разбор кода выполняет
компилятор TypeScript, версия закреплена в зависимостях — **ветка 5.x**.
Это не отставание: в 7.x компилятор переписан нативно и отдаёт
JavaScript'у только `version` и `versionMajorMinor` — ни построения
программы, ни разбора конфигурации там нет (замер 2026-09-08 на
`npm:typescript@7.0.2`). Обновление на 7.x сломает слой целиком, и
поднимать версию можно только после проверки, что нужный разбор снова
доступен.

Отдельный языковой сервер не нужен и не устанавливается: это обёртка над
тем же разбором.

## Инварианты

- Ответ полон либо назван неполным; неразрешённая ссылка попадает в свой
  раздел с причиной и не выпадает молча.
- «Не знаю» и «нет» — разные ответы: пустой раздел против отказа с
  причиной.
- Каждый раздел несёт отметку дерева, на котором получен, — включая
  отказавший: отметку снимает git, а не анализатор, и отказ без неё не
  отвечает на вопрос «на каком дереве».
- Гарантия анализатора печатается у каждого **ответившего** раздела, а
  не только когда пониженная; у отказавшего её нет — заявлять полноту
  нечего.
- Отказ раздела и отказ команды — разное: `exit 1` только если не
  ответил ни один раздел. С окном из одного репозитория они совпадают.
- Исключения проекта снимаются перед разбором; имена тестов не зашиты.
- Результаты разных репозиториев не смешиваются никогда — ни при
  совпадении имён, ни в режиме всей рабочей области.
- Отказ одного репозитория не отменяет ответы остальных: он печатается
  вместо перечня в своём разделе. Замер 2026-09-08: один репозиторий без
  установленных зависимостей (`tsconfig` наследует пакет, которого нет)
  обнулял ответ по всем восьми.
- Два вызова на неизменном дереве дают побайтово одинаковый вывод.
- Слой только читает; мутирующего варианта у него нет.

## Граничные случаи и ошибки

| Вход | Ожидаемое поведение |
| --- | --- |
| Сентинела `.mp-workspace-root` нет ни у одного предка | отказ, `mpu code: рабочая область не найдена: сентинела .mp-workspace-root нет ни у одного предка <путь>` |
| В рабочей области нет ни одного репозитория | отказ, `mpu code: в рабочей области нет репозиториев` |
| Репозиторий без единого проекта, вопрос о читателях модуля или об упоминаниях | ответ текстового анализатора, гарантия «неполная», причина названа |
| Репозиторий без единого проекта, вопрос об объявлениях, потребителях символа или телах | отказ **его раздела** с причиной: этих операций у текстового анализатора нет вовсе |
| Проекты есть, но ни одна программа не собралась непустой | отказ раздела, и причина называет **это** условие, а не «нет ни одного проекта» |
| Каталог окна не существует в репозитории без проектов | exit 2, ошибка ввода: она решается **раньше** отказа раздела — опечатку в окне надо отличать от «репозиторий не может ответить» |
| Проект есть, но программа не строится | отказ **того раздела**, чьего репозитория это касается, с причиной; остальные разделы отвечают |
| Ни один раздел не ответил | exit 1; иначе exit 0 с названными отказами разделов |
| Дерево вне git | ответ, отметка `вне git` |
| У проекта нет входа | ответ; область видимости экспортированного символа — `экспортируется из модуля; входа у проекта нет` |
| Дерево с незакоммиченными изменениями | ответ, отметка несёт признак изменений |
| Импорт не разрешился | строка в разделе «не разрешено» с указателем и причиной |
| Ссылка на внешний пакет не разрешилась | там же; на перечень потребителей внутреннего символа не влияет |

## Golden-примеры

`fixtures/code/tree/` — дерево-фикстура: пятнадцать файлов с
расширением `.txt`, которое тестовое окружение снимает при
материализации во временный каталог. Расширение не украшение: файлы
`.ts` в канале спецификаций попали бы под гейты модуля.

Каждый файл несёт комментарий «зачем он здесь» и закрывает ровно одну
ловушку:

| Файл | Что проверяет |
| --- | --- |
| `tsconfig.json` | `exclude: **/*.spec.ts` и алиас `#/*` |
| `src/days.ts` | символ `addDays` с потребителями; `spanDays` с `+1` |
| `src/span.ts` | тёзка `spanDays` стрелкой и без `+1` |
| `src/window.ts`, `src/grid.ts`, `src/seed_test.ts` | три побайтово равных тела под разными именами; последний — тестовая обвязка вне шаблона `*.spec.ts` |
| `src/report.spec.ts` | потребитель, отсекаемый штатным `exclude` |
| `src/aliased.ts` | потребитель через алиас `#/` |
| `src/dynamic.ts` | потребитель через динамический `import()` |
| `src/loaderA.ts`, `src/loaderB.ts` | тела, различающиеся комментарием и литералом |
| `src/broken.ts` | импорт несуществующего модуля |
| `src/orphan.ts` | экспортируемый символ без потребителей |
| `src/index.ts` | вход проекта: реэкспорт части символов |
| `docs/guide.md` | путь, упомянутый в документации и отсутствующий в коде |

Факты дерева сняты оракулом (ниже) и механизмом разбора; оба дали одно и
то же. Голдены самих поверхностей — в спеках команд.

### Дерево-фикстура вида Deno

`fixtures/code/deno-tree/` — семь файлов, тем же способом с расширением
`.txt`. Материализуется под именем `deno-fixture` и закрывает то, чего в
первом дереве нет по устройству:

| Файл | Что проверяет |
| --- | --- |
| `deno.json` | проект второго вида; вход объявлен полем `exports`, а не найден по `index.ts` |
| `mod.ts` | вход проекта, реэкспортирующий символ |
| `src/days.ts` | тот же `addDays`, что и в первом дереве, — ответы двух видов сравнимы |
| `src/window.ts` | импорт с расширением `.ts` — форма, которой на tsconfig-дереве нет |
| `src/seed_test.ts` | тестовая обвязка Deno, шаблоном `*.spec.ts` не описанная |
| `src/broken.ts` | импорт несуществующего модуля |
| `src/ext.ts` | внешний пакет: в «не разрешено» поимённо, на перечень потребителей не влияет |

**Свой `deno.json` у фикстуры обязателен**, и не для красоты: без него
разбор поднялся бы вверх по каталогам за чужой конфигурацией. Замер
2026-09-08: один и тот же оракул, прогнанный в каталоге модуля и вне
его, дал одинаковый перечень — потому что ближайшей конфигурацией
оказывалась фикстурная. Уберут конфиг — прогон начнёт зависеть от места.

### Дерево-фикстура нечитаемой конфигурации

`fixtures/code/broken-tree/` — два файла, материализуется под именем
`broken-fixture`. `tsconfig.json` наследует пакет, которого нет;
`src/a.ts` разбираем сам по себе. Дерево закрывает класс, у которого до
сих пор не было ни одного голдена: раздел, которому нечего ответить.
Текст причины — дословная диагностика компилятора (`TS6053`), снятая
прогоном, а не пересказанная.

### Оракул полноты

Полнота не заявляется, а измеряется. Эталон один:

> Полный список потребителей символа `S` — множество мест, где сборка
> ломается, если `S` переименовать.

Оракул исполним и служит тестом канала: переименовать объявление в
материализованном дереве, проверить типы, вычесть список ошибок базового
прогона. На дереве-фикстуре он даёт по `addDays` семь файлов —
`src/aliased.ts`, `src/dynamic.ts`, `src/grid.ts`, `src/index.ts`,
`src/report.spec.ts`, `src/seed_test.ts`, `src/window.ts` — и ни одного
лишнего:
`src/broken.ts` даёт ошибку и в базовом прогоне, поэтому в разность не
попадает.

**Оракул гоняется по обоим видам проекта**, и это единственное, чем
закрывается полнота у проекта на Deno: правило «исключения кода
снимаются» там почти ничего не снимает, и частные мутации вокруг
`exclude` на нём краснеть не будут. Эталон берётся родной: для
`tsconfig.json` — проверка типов компилятором, для `deno.json` —
`deno check`. Замер 2026-09-08 показал, что оба дают один и тот же
перечень.

На дереве вида Deno оракул `deno check` даёт по `addDays` **три**
потребителя — `mod.ts`, `src/seed_test.ts`, `src/window.ts`; `src/days.ts`
из перечня исключается как файл самого объявления, а `src/broken.ts` и
`src/ext.ts` ошибочны и в базовом прогоне.

Приёмка любой команды семейства — совпадение её ответа с оракулом на
дереве соответствующего вида. Тест обязан краснеть от снятия любого из трёх условий:
не снимать `exclude` — пропадает `src/report.spec.ts`; не читать
`paths` — пропадает `src/aliased.ts`; считать потребителей перечислением
статических форм импорта — пропадает `src/dynamic.ts`.

## Открытые вопросы

нет. Три вопроса закрыты владельцем 2026-09-09 по замерам выше.

- **Стоимость.** Принято: параллельный обход репозиториев и построение
  только нужных проектов у `name`/`mentions`; порог переписан по факту
  (до 8 с на большом репозитории вместо обещанных 1.5 с).
  **Резидентный режим не заводится** — вводить его пришлось бы против
  довода, записанного в этой спеке: кэша нет по построению, а индекс,
  собранный на одной ветке, на другой уверенно врёт. Пересмотр — только
  если живая работа покажет, что окно всей рабочей области вообще
  спрашивают.
- **Границы `10x-ozon`.** Принято: из рабочей области не исключается.
  Его раздел-отказ несёт настоящую и устранимую причину (зависимости не
  установлены, конфигурация наследует отсутствующий пакет), а исключение
  репозитория вернуло бы в инструмент ровно то, ради чего он заводился —
  молча неполный ответ. Удвоение ответов по перенесённому коду полезно:
  для задачи переноса «символ есть и там, и там» — сигнал, а не шум.
- **Обязательность.** Принято: в гейт и pre-commit команда не
  встраивается. Гейт проверяет инвариант и отвечает «да/нет», а команда
  отвечает перечнями — сравнивать перечень в гейте не с чем; цена вызова
  для pre-commit тоже не годится. Обязательной может стать **другая**
  проверка поверх этого слоя (например «нет побайтовых близнецов между
  модулями» или «нет двух объявлений одного имени с разными типами
  возврата в одном пакете»), и какая именно — видно только после того,
  как командой начнут пользоваться.
