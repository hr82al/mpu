# platform/code-analyzer — разбор кода рабочей области

Статус: к реализации (2026-09-08; дерево-фикстура и голдены —
`fixtures/code/`, факты сняты оракулом полноты на самом дереве)

## Назначение

Общий слой команд семейства `mpu code`: из чего строится ответ о связях
кода, какую гарантию он несёт и чем эта гарантия проверяется.
Поверхности команд — `specs/code-refs.md`, `specs/code-twins.md`,
`specs/code-name.md`, `specs/code-mentions.md`.

Смысл слоя один: **ответ полон либо назван неполным**. Ссылка, которую
разобрать не удалось, попадает в отдельный раздел с причиной; молча
выпасть она не может. Инструмент, тихо выбрасывающий неразобранное,
выдаёт уверенный неверный ответ.

## CLI-контракт

нет (общий слой; флаги — в спеках команд).

## Ввод/вывод

**Рабочая область** — ближайший каталог-предок текущего рабочего
каталога, содержащий файл-сентинел `.mp-workspace-root`. Ключа конфига у
неё нет: сентинел уже лежит в корне и служит той же цели соседнему
тулингу, а новый ключ пришлось бы вносить в замороженный реестр
(`platform/config.md`) и пересобирать его голдены. Сентинела нет ни у
одного предка — отказ.

Её **репозитории** — подкаталоги первого уровня, содержащие `.git`.
Список нигде не зашит: он снимается с диска на каждый вызов.

**Проект** внутри репозитория — файл `tsconfig.json` (ровно это имя) вне
`node_modules` и `dist`, у которого разрешается непустой список файлов.
Имена вида `*.base.json`, `*.build.json`, `*.spec.json` проектами не
считаются: они либо не перечисляют исходников, либо сужают уже покрытый
набор. Файл репозитория, не попавший ни в один проект, обслуживается
текстовым анализатором.

**Исключения тестов снимаются.** Список файлов проекта берётся из его
конфигурации, после чего `exclude` заменяется фиксированным списком
`["**/node_modules/**", "<outDir>/**"]`, где `outDir` — значение из
конфигурации проекта, по умолчанию `dist`. Пустым `exclude` не
заменяется: проект с `include: ["**/*"]` затянул бы в программу
зависимости. Снимаются, таким образом, все исключения кода — и никакие
исключения артефактов.

Причина измеримая: на дереве-фикстуре ответ по штатной конфигурации даёт **пять**
файлов-потребителей `addDays`, а со снятыми исключениями — **шесть**;
разница ровно `src/report.spec.ts`, отсечённый шаблоном `**/*.spec.ts`.
Имена тестов при этом никуда не зашиваются: `src/seed_test.ts` тем же
шаблоном не описывается вовсе, а потребителем является.

### Анализатор

Анализатор отвечает за один репозиторий и умеет ровно четыре вещи:

| Операция | Что возвращает |
| --- | --- |
| отметка дерева | репозиторий, ветка, коммит, признак незакоммиченных изменений |
| объявления файла | имя, сигнатура, строка, область видимости (ниже) |
| потребители цели | места использования + ссылки, которые не разрешились |
| тела | тело каждого объявления-функции с его нормализованной формой |

Всё остальное выводится из них и **ровно в одном месте**: читатели
модуля — потребители цели-модуля; близнецы — группировка тел; занятость
имени — отбор объявлений; упоминания пути — потребители у текстового
анализатора.

**Область видимости** объявления — одно из трёх значений, и печатается
оно одной строкой, не двумя:

- `экспортируется из модуля и из входа проекта`;
- `экспортируется из модуля; из входа проекта не реэкспортируется`;
- `приватное в модуле`.

**Вход проекта** — файл, на который указывает поле входа его пакета
(`exports` либо `main` в `package.json`, `exports` в `deno.json`/
`deno.jsonc`). Поля нет — `index.ts` в общем корне исходников проекта.
Нет и его — у проекта входа нет, и второе значение принимает вид
`экспортируется из модуля; входа у проекта нет`.

Реализаций две, с одним набором операций и разной гарантией:

| Вид репозитория | Анализатор | Гарантия |
| --- | --- | --- |
| есть хотя бы один проект | по типам | полная: перечень равен оракулу |
| проектов нет; файл вне всех проектов | текстовый | неполная, помечена в каждом разделе |

Анализатор, который не удалось построить, отвечает на все четыре
операции отказом с причиной — он не отсутствует и не подменяется
пустым результатом.

**Чего текстовый анализатор не знает — он называет.** Сигнатуры и
области видимости у него нет: типов он не разбирает. Вместо них
печатается именованное незнание, а не пустое место и не молчание:

    addDays — сигнатуры нет: текстовый разбор
    область видимости неизвестна: текстовый разбор

Правило то же, что и у раздела «не разрешено»: пропуск строки читался бы
как «сигнатуры у символа нет» и «символ приватный», а это другой ответ.

### Отметка дерева

Отметка — отдельная операция, и её источник задаётся при создании
анализатора. Рабочий источник — git; в тестах подставляется постоянная
отметка.

Шапка раздела — поля через ` · `:

    РЕПОЗИТОРИЙ · ВЕТКА · КОММИТ · СОСТОЯНИЕ · ГАРАНТИЯ
    РЕПОЗИТОРИЙ · вне git · ГАРАНТИЯ

- **ВЕТКА** — имя текущей ветки; голова отделена — слово `detached`;
- **КОММИТ** — первые восемь знаков полного хэша. Длина фиксирована:
  сокращение средствами git плавает от репозитория к репозиторию, а
  вывод обязан быть детерминированным;
- **СОСТОЯНИЕ** — `дерево чистое` либо
  `дерево содержит незакоммиченные изменения`;
- **ГАРАНТИЯ** — `разбор по типам — ответ полон` либо
  `текстовый разбор — ответ неполон`.

Дерево вне git — отметка `вне git` вместо трёх полей; это ответ, а не
отказ. Примеры обеих форм:

    ozon · feat/checklist/serving/screen-data-endpoint · 989c0bf9 · дерево чистое · разбор по типам — ответ полон
    fixture · вне git · разбор по типам — ответ полон

Ответ читается **с рабочего дерева**, а не из объектов git: правка, ещё
не закоммиченная, видна в ответе. Поэтому отметка обязательна и печатается
в шапке каждого раздела; дерево с незакоммиченными изменениями помечается,
но ответ выдаётся.

Кэша у слоя нет. Ответ строится на каждый вызов из текущего состояния
файлов: индекс, собранный на одной ветке и прочитанный на другой,
уверенно врёт, а восемь независимых репозиториев со своими ветками делают
его инвалидацию дороже самого ответа.

### Форма ответа

Всякий ответ состоит из трёх частей, и ни одна не опускается:

1. **отметка дерева** — шапка раздела;
2. **найденное** — разделы своей команды;
3. **не разрешено** — по строке на ссылку, которую не удалось
   разрешить, с причиной; пусто — печатается `не разрешено: 0`.

Раздел «не разрешено» печатается **всегда**, в том числе нулевой:
его отсутствие читалось бы как «всё разрешилось».

Пустой раздел найденного означает «совпадений нет» и остаётся ответом.
Невозможность ответить — другой вид: отказ с причиной, разделов
найденного у него нет.

Порядок строк задаёт слой: `(репозиторий, путь, строка)`. Времени в
выводе нет ни в каком виде.

Каждая поверхность stdout оканчивается **одним переводом строки**.

## Побочные эффекты

Чтение файлов рабочих деревьев и вызовы `git` только для чтения
(`rev-parse`, `symbolic-ref`, `status --porcelain`). Сети нет. Ни один
репозиторий не изменяется — ни файлами, ни индексом git. Артефактов
внутри репозиториев рабочей области слой не создаёт.

## Конфигурация

Своих ключей у слоя нет, и реестр конфига (`platform/config.md`)
остаётся замороженным: корень рабочей области находится по сентинелу
`.mp-workspace-root`, а не настраивается. Разбор кода выполняет
компилятор TypeScript, версия закреплена в зависимостях — **ветка 5.x**.
Это не отставание: в 7.x компилятор переписан нативно и отдаёт
JavaScript'у только `version` и `versionMajorMinor` — ни построения
программы, ни разбора конфигурации там нет (замер 2026-09-08 на
`npm:typescript@7.0.2`). Обновление на 7.x сломает слой целиком, и
поднимать версию можно только после проверки, что нужный разбор снова
доступен.

Отдельный языковой сервер не нужен и не устанавливается: это обёртка над
тем же разбором.

## Инварианты

- Ответ полон либо назван неполным; неразрешённая ссылка попадает в свой
  раздел с причиной и не выпадает молча.
- «Не знаю» и «нет» — разные ответы: пустой раздел против отказа с
  причиной.
- Каждый раздел несёт отметку дерева, на котором получен.
- Гарантия анализатора печатается всегда, а не только когда пониженная.
- Исключения проекта снимаются перед разбором; имена тестов не зашиты.
- Результаты разных репозиториев не смешиваются никогда — ни при
  совпадении имён, ни в режиме всей рабочей области.
- Два вызова на неизменном дереве дают побайтово одинаковый вывод.
- Слой только читает; мутирующего варианта у него нет.

## Граничные случаи и ошибки

| Вход | Ожидаемое поведение |
| --- | --- |
| Сентинела `.mp-workspace-root` нет ни у одного предка | отказ, `mpu code: рабочая область не найдена: сентинела .mp-workspace-root нет ни у одного предка <путь>` |
| В рабочей области нет ни одного репозитория | отказ, `mpu code: в рабочей области нет репозиториев` |
| Репозиторий без единого проекта | ответ текстового анализатора, гарантия «неполная», причина названа |
| Проект есть, но программа не строится | отказ с причиной; разделов найденного нет |
| Дерево вне git | ответ, отметка `вне git` |
| У проекта нет входа | ответ; область видимости экспортированного символа — `экспортируется из модуля; входа у проекта нет` |
| Дерево с незакоммиченными изменениями | ответ, отметка несёт признак изменений |
| Импорт не разрешился | строка в разделе «не разрешено» с указателем и причиной |
| Ссылка на внешний пакет не разрешилась | там же; на перечень потребителей внутреннего символа не влияет |

## Golden-примеры

`fixtures/code/tree/` — дерево-фикстура: четырнадцать файлов с
расширением `.txt`, которое тестовое окружение снимает при
материализации во временный каталог. Расширение не украшение: файлы
`.ts` в канале спецификаций попали бы под гейты модуля.

Каждый файл несёт комментарий «зачем он здесь» и закрывает ровно одну
ловушку:

| Файл | Что проверяет |
| --- | --- |
| `tsconfig.json` | `exclude: **/*.spec.ts` и алиас `#/*` |
| `src/days.ts` | символ `addDays` с потребителями; `spanDays` с `+1` |
| `src/span.ts` | тёзка `spanDays` стрелкой и без `+1` |
| `src/window.ts`, `src/grid.ts`, `src/seed_test.ts` | три побайтово равных тела под разными именами; последний — тестовая обвязка вне шаблона `*.spec.ts` |
| `src/report.spec.ts` | потребитель, отсекаемый штатным `exclude` |
| `src/aliased.ts` | потребитель через алиас `#/` |
| `src/loaderA.ts`, `src/loaderB.ts` | тела, различающиеся комментарием и литералом |
| `src/broken.ts` | импорт несуществующего модуля |
| `src/orphan.ts` | экспортируемый символ без потребителей |
| `src/index.ts` | вход проекта: реэкспорт части символов |
| `docs/guide.md` | путь, упомянутый в документации и отсутствующий в коде |

Факты дерева сняты оракулом (ниже) и механизмом разбора; оба дали одно и
то же. Голдены самих поверхностей — в спеках команд.

### Оракул полноты

Полнота не заявляется, а измеряется. Эталон один:

> Полный список потребителей символа `S` — множество мест, где сборка
> ломается, если `S` переименовать.

Оракул исполним и служит тестом канала: переименовать объявление в
материализованном дереве, проверить типы, вычесть список ошибок базового
прогона. На дереве-фикстуре он даёт по `addDays` шесть файлов —
`src/aliased.ts`, `src/grid.ts`, `src/index.ts`, `src/report.spec.ts`,
`src/seed_test.ts`, `src/window.ts` — и ни одного лишнего:
`src/broken.ts` даёт ошибку и в базовом прогоне, поэтому в разность не
попадает.

Приёмка любой команды семейства — совпадение её ответа с оракулом на
этом дереве. Тест обязан краснеть от снятия любого из двух условий:
если `exclude` не снимать, пропадает `src/report.spec.ts`; если не
читать `paths`, пропадает `src/aliased.ts`.

## Открытые вопросы

- **Резидентный режим.** Сборка программы одного проекта занимает
  сотни миллисекунд, и на большой рабочей области счёт идёт на секунды.
  Проекты независимы и обходятся параллельно; если этого окажется мало,
  единственный оставшийся ход — процесс, живущий дольше вызова и
  держащий разобранные программы. Это выводит слой из-под общего
  контракта команды (`platform/command-contract.md`) и заводит вопрос
  инвалидации, которого сейчас нет. Заводить ли — решает владелец, и
  после того, как замер на живой работе покажет, что такое окно вообще
  спрашивают.
