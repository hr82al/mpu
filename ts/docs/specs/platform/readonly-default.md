## Назначение

Инвариант mpu: диагностическое чтение безопасно по построению, мутация —
явная. Два универсальных enforced-механизма: read-only PG-сессия
(гарантия сервера БД) и закрытый список публикации MCP-тулов —
мутирующие команды не публикуются в `ro`-профиле, а необратимые вне
этой машины — несут в `rw`-профиле аннотации подтверждения (критерий и
состав — `platform/mcp-server.md`; локальные мутации аннотаций не
несут). Подтверждения записи в CLI — per-команда UX
(карта ниже). У каждой мутирующей команды обязан быть enforced read-only
вариант или dry-режим.

## Ввод/вывод

Read-only PG-сессия: подключение открывается с серверной опцией
`default_transaction_read_only=on`, а пользовательский текст исполняется
одним вызовом внутри обёртки фиксированной формы — три оператора до него
и два после:

    BEGIN READ ONLY;
    SELECT current_setting('transaction_read_only');
    SAVEPOINT <метка>;
    <текст пользователя>
    ;
    ROLLBACK TO SAVEPOINT <метка>;
    ROLLBACK

Перевод строки перед замыкающей `;` — часть формы, а не вёрстка примера:
текст, оканчивающийся хвостовым `--`-комментарием (`SELECT 1 -- зачем`),
на одной строке с терминатором проглотил бы и его, и снятие метки, то
есть обход через `COMMIT` перестал бы обнаруживаться. Метка — имя
реализации, из пользовательского ввода не строится.

Обёртка нужна там, где текст запроса приходит **снаружи** — от человека
или агента. Команде с фиксированным набором собственных запросов
(`specs/update.md`) достаточно опции сессии: снимать режим в её запросах
некому, и оборачивать их не требуется.

Обёртка — сам механизм запрета, а не оформление. Одной опции сессии
недостаточно: `transaction_read_only` переключается из самого SQL, пока в
транзакции не взят снимок, и текст `SET transaction_read_only = off;
INSERT …` в одном вызове запись выполняет. Каждый оператор обёртки
закрывает свою часть: `BEGIN READ ONLY` задаёт режим явно, не полагаясь
на то, что опция подключения доехала до сервера; второй оператор берёт
снимок (проверка действующего режима — отдельное обращение ДО обёртки,
иначе она проверяла бы саму себя); `SAVEPOINT` открывает
подтранзакцию, внутри которой переход в read-write сервер отклоняет
безусловно; `ROLLBACK TO SAVEPOINT` не находит метки, если текст сам
завершил транзакцию вызова, и превращает такой обход в отказ вместо
тихой записи. Текст пользователя при этом не разбирается и не
фильтруется по содержимому — запрет держит сервер.

Отказы различаются по SQLSTATE, не по тексту сообщения:

- `25006` — пишущий оператор (включая data-modifying CTE, пишущие
  функции и триггеры): команда печатает
  `mpu sql-ro: запрос пытается писать — заблокировано read-only сессией.
  Для записи используйте `mpu sql`.` → exit 1;
- `25P01` и `3B001` — метку снять не удалось. Оба кода дают один текст
  `mpu sql-ro: метка транзакции вызова не снята — гарантия только-чтения
  не подтверждена, результат не печатается` → exit 1. Разные коды —
  разные пути, замерено: `COMMIT` внутри текста закрывает транзакцию
  (`25P01`), а `COMMIT; BEGIN …` открывает вместо неё чужую, где метки
  нет (`3B001`). Формулировка намеренно говорит о неподтверждённой
  гарантии, а не о снятой: тем же кодом `3B001` сервер отвечает и на
  ссылку самого текста на не открывавшуюся точку сохранения
  (`ROLLBACK TO SAVEPOINT bar`), когда транзакция вызова цела. Отличаются
  эти случаи только именем метки внутри сообщения сервера — позиции у
  ошибки нет ни в одном из них (замерено), а разбирать текст сообщения
  запрещено. Собственное имя метки в вывод не попадает ни по одному пути;
- прочие — текстом сервера, `db error: <текст>` → exit 1. Сюда попадает
  и `25001`: этим кодом сервер отвечает и на попытку снять режим, и на
  оператор, запрещённый внутри блока транзакции, — различать их по коду
  нельзя, а собственного текста они не требуют.

Для БД воркспейсов (sw), куда снаружи прямого доступа нет и SQL
исполняется изнутри контейнера (атом exec-transport), тот же контракт
обеспечивается той же обёрткой вокруг текста.

Агентная точка входа (MCP): `ro`-профиль публикует только читающие
команды, мутирующие живут в `rw`-профиле; состав задан закрытым списком,
fail-closed. Интерактивные подтверждения на этой точке входа исполняет
клиент агента по аннотациям тула — сам сервер диалогов не ведёт.

Карта паттернов подтверждения — UX-паттерны команд CLI (фиксируется как
есть; деталь — в спеке каждой команды):

1. **Пара read/write команд** — `sql-ro` (только чтение, авторазрешаема)
   / `sql` (пишет сразу, без вопросов; защита — ask-разрешение
   запускающего харнесса). Общий `--dry` печатает мету и SQL без
   подключения, exit 0 — превью, не защита.
2. **`--dry-run` opt-in** (дефолт — писать немедленно): мутации Kaiten
   (перемещения, таймер), пакетная запись листов, exec-обёртки.
3. **Инвертированный `--yes`** (дефолт — только сухой прогон): редкие
   деструктивные локальные операции (снос локальных клиентских схем);
   такие команды физически подключаются только к локальным адресам и до
   прода не достают по построению.
4. **Интерактивный y/N** — единично (удаление ноты MR): без TTY и без
   `--yes` — немедленный отказ с подсказкой `добавь --yes` (не зависает
   на чтении несуществующего ввода).

Отдельная утилита `mpu confirm` — y/N-шлюз для пайплайнов: читает весь
stdin, показывает его в stderr, спрашивает через терминал напрямую
(stdin занят данными); `y`/`yes` → буфер целиком в stdout; любой другой
ответ/EOF → exit 1 `отменено — pipe прерван.`, в stdout не уходит
ничего; нет терминала и нет `--yes` → exit 2 с подсказкой и
диагностикой. Частичного пропуска данных не бывает. Подробности —
`specs/confirm.md`; команда переехала маршрутом `native`.

## Побочные эффекты

Политика сама по себе эффектов не имеет; она ограничивает эффекты
команд: read-вариант не пишет ничего в пределах своей сессии (границы
этой гарантии — «Инварианты»), мутирующий — пишет туда, куда заявлено
его спекой.

## Конфигурация

Креды и адреса PG — `platform/env-file.md`. Env-переключателей поведения
подтверждений нет — только CLI-флаги.

## Инварианты

- Запись отклоняет сервер, а не разбор текста запроса: содержимое
  пользовательского SQL не анализируется ни на каком шаге.
- Переключение режима из самого SQL (`SET transaction_read_only`,
  `SET TRANSACTION READ WRITE`, `BEGIN READ WRITE` и прочие формы)
  невозможно: внутри подтранзакции обёртки сервер отклоняет его
  безусловно, независимо от того, взят ли снимок.
- Текст, завершивший транзакцию вызова, не остаётся незамеченным:
  вызов падает на потерянной метке, exit 1, результат не печатается.
- Гарантия проверяется на самом соединении, а не предполагается по
  факту отправки опции: соединение, на котором запрет транзакционной
  записи не действует (опция потеряна пулером, переопределена ролью
  или сервером), к работе не допускается — вызов отказывает вместо
  того, чтобы исполнить запрос на пишущей сессии. Цена — одно
  дополнительное обращение на соединение, принято осознанно.
- Режим задаётся **параметром стартового пакета** подключения. Отсюда
  ограничение, названное явно: пулер соединений отвергает такое
  подключение целиком (замер 2026-08-05: pgbouncer в transaction-режиме
  отвечает `unsupported startup parameter in options`). Механизм требует
  прямого подключения к PostgreSQL; сегодня стенд такой и есть, но при
  переводе адреса на пулер перестанут открываться сессии всех команд,
  которым эта спека предписывает запрет записи.
- Гарантия ограничена сессией и названа так честно. Запись, идущая мимо
  неё — через второе соединение изнутри запроса (`dblink`,
  `postgres_fdw`), выполнением программы или записью файла сервером,
  изменением конфигурации сервера, — этим механизмом не ограничивается
  и держится только правами роли. Полный запрет даёт лишь роль без прав
  записи либо реплика; ни того, ни другого в распоряжении нет (решение
  оператора 2026-08-05).
- Оператор, запрещённый внутри блока транзакции (`VACUUM`, `ANALYZE`,
  `CREATE INDEX CONCURRENTLY`, `ALTER SYSTEM`), обёрткой отклоняется —
  до неё `VACUUM` на read-only сессии проходил.
- Тул мутирующей команды не публикуется в `ro`-профиле MCP; состав
  профилей — закрытый список, fail-closed
  (`platform/mcp-server.md`).
- Опция сессии действует одинаково на один оператор и на многооператорный
  блок в одном вызове.
- `--dry`/`--dry-run`-режимы не открывают мутирующих соединений.
- Деструктивные локальные команды не принимают селектор прод-сервера —
  изоляция по построению подключения, не по флагу.
- Новая мутирующая команда без read-only/dry-варианта в дерево не
  попадает (правило ревью).

## Граничные случаи и ошибки

- Пишущий SQL под read-only → перехваченный отказ сервера, exit 1,
  без трейсбека и без частичного выполнения.
- Data-modifying CTE (`WITH x AS (DELETE …) SELECT …`) → тот же отказ.
- `SET transaction_read_only = off; INSERT …` (в любой форме записи
  значения) → отказ `25001` текстом сервера, exit 1, записи нет.
- `SET TRANSACTION READ WRITE; …` и `BEGIN READ WRITE; …` → тот же отказ.
- `COMMIT; BEGIN READ WRITE; INSERT …` без собственного `COMMIT` →
  отката достаточно: записи нет, вызов падает на потерянной метке.
- `COMMIT; …; COMMIT` — запись доходит до БД (единственный обход,
  который механизм не предотвращает), но вызов падает `25P01`, результат
  не печатается. Молчаливого обхода не остаётся.
- Сервер сообщил позицию ошибки внутри операторов обёртки (не в тексте
  пользователя) → печатается одно сообщение сервера, без строки `LINE`
  и указателя: операторы обёртки в вывод не попадают ни при каких
  ошибках.
- Ошибка конфигурации (нет кредов) → exit 2; ошибка БД → `db error: …`,
  exit 1.

## Golden-примеры

Сняты с живой версии 2026-08-05 (`fixtures/platform/readonly-default/`):

- `select1-stdout.json` — `SELECT 1` read-вариантом с `--json`:
  stdout-данные, stderr пуст, exit 0;
- `dry-v-stderr.txt` — `--dry -v`: мета-блок целиком в stderr со
  строкой `mode: read-only`, без подключения; stdout пуст, exit 0
  (адрес хоста заменён плейсхолдером `<pg_host>` — подстановка —
  обязанность теста);
- `write-refused-stderr.txt` — пишущий запрос под read-вариантом:
  отказ одной строкой в stderr, stdout пуст, exit 1.
