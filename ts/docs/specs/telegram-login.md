# mpu telegram login — вход от имени пользователя

**Статус:** к реализации — 2026-09-14 сообщение библиотеки об отправке кода не в stdout («stdout входа», порция 133); прочее реализовано — отказ входа у отдельной команды — «пропущено» с кодом 0 (порция 129, `fe06bcb`); пропуск только за отказ Telegram/слоя, дефект кода и сбой терминала — код 1, коды 0/2/1 в справке (порция 130, `bee48de`; установлено и сверено по `mpu telegram login --help`). Предел соединения при входе — `platform/telegram-mtproto.md` (порция 131); прочее реализовано — сверено 2026-09-10 по `mpu telegram login --help` (команда в справке; поверхность флагов построчно не сверялась). Ранее: к реализации (2026-08-28). Последняя непереехавшая команда
семейства: `send`, `ls`, `search`, `status`, `log` уже native.

## Назначение

Интерактивный вход в Telegram: сохранить пользовательскую сессию в env-файл,
чтобы остальные команды семейства работали без повторного входа. Та же
реализация — шаг входа в `mpu init`.

```
mpu telegram login
```

Опций нет.

## Сценарий

1. **Сессия уже есть** → печатает «уже авторизован», код 0, вход не
   запускается. Идемпотентность здесь не удобство, а защита: повторный вход
   отзывает прежнюю сессию.
2. **Нет TTY** → пропуск с подсказкой заполнить ключи вручную, **код 0**.
   Не отказ: команда общая с шагом `mpu init`, а тот не должен падать в
   неинтерактивном запуске.
3. **Нет ключей приложения** → спрашивает согласие завести их, с указанием,
   где взять; отказ пользователя — выход без записи.
4. Телефон берётся из env-файла либо спрашивается и **сохраняется**.
5. Код из Telegram — обычный ввод; пароль второго фактора — **скрытый**.
6. Успех: сессия и телефон записаны в env-файл, сообщение об этом.

## Инварианты

1. **Секреты не печатаются.** Строка сессии — полноценный доступ к аккаунту:
   она не идёт ни в stdout, ни в stderr, ни в журнал вызовов, ни в текст
   ошибки. Пароль второго фактора вводится скрыто и не сохраняется вовсе.

2. **Единственное место записи — env-файл.** Ни временных файлов, ни копий
   рядом; при отказе на любом шаге частично записанного состояния не
   остаётся, кроме телефона и ключей приложения — они не секреты доступа и
   переживают неудачный вход намеренно.

3. **Ни один отказ сценария не даёт ненулевого кода.** Нет TTY, отказ
   заводить ключи, согласие с пустым вводом, **сбой самого входа**
   (неверный код, недоступная служба, битый прокси) — всё это «пропущено»
   с кодом 0. У оригинала это названо прямо: «ошибка входа не считается
   фатальной — печатается в stderr, команда завершается кодом 0».

   Инвариант исправлен 2026-08-31: прежняя редакция требовала кода 2 при
   пустом вводе ключей. Замер оригинала (подменный `XDG_CONFIG_HOME`, пустой
   env-файл) показал обратное:

   ```
   api_id (integer): api_hash (32 hex chars): # telegram: пропущено (api_id/api_hash пустые)
   КОД=0
   ```

   Требование кода 2 было моей выдумкой и противоречило назначению команды:
   та же реализация — шаг `mpu init`, и падение на ней сломало бы bootstrap
   у того, кто просто не хочет настраивать Telegram. Пропуск здесь — не
   снисходительность, а контракт: команда сообщает, чего не сделала, и не
   мешает остальному.

   Сбой криптографии клиента при входе (встроенный модуль не найден или не
   принят, `platform/telegram-mtproto.md`, «Конфигурация») — тоже сбой
   самого входа: `# telegram: пропущено (telegram: криптография клиента не
   поднялась: <первая строка причины>)`, код 0.

   **Что считается сбоем самого входа, а что — нет (2026-09-14).** Пропуск
   с кодом 0 — только отказ, пришедший от Telegram или от слоя клиента и уже
   оформленный им текстом: отказ протокола (неверный код, отозванный
   запрос, недоступная служба), непригодный прокси, сбой криптографии
   клиента. **Не** сбой входа и **не** пропуск — код 1 с исходным текстом,
   без переоформления в `telegram: RPC error: …`: дефект собственного кода
   (например `TypeError` при сборке клиента или строки сессии), отказ
   терминала (не удалось прочитать ответ на вопрос), отказ записи env-файла,
   отказ закрытия клиента. Иначе ошибка программы маскируется под «Telegram
   отказал», и её никто не увидит (разбор порции 129: `TypeError` в сборке
   клиента давал `# telegram: пропущено (Cannot read properties of
   undefined …)`, код 0).

   Коды отдельной команды: 0 — успех и любой пропуск; 2 — неверный вызов
   (лишняя опция, `unknown option`); 1 — сбой вне сценария (перечень выше).
   Справка команды называет все три.

   **Исправленное отклонение (было fix, закрыто порциями 129 `fe06bcb` и 130
   `bee48de`, 2026-09-14).** Отдельный `mpu telegram login`
   при отказе клиента на шаге входа выходит с кодом 1 (трасса отчёта порции
   128: `runLogin` отказ клиента не ловит), а справка команды называет код 1
   «отказом Telegram». По инварианту — «пропущено» с кодом 0 и у отдельной
   команды, и у шага `mpu init`; справка приводится к этому же контракту.

   **stdout входа (2026-09-14).** Сообщения клиента о ходе входа (например
   «код подтверждения отправлен через …») не печатаются в stdout напрямую
   библиотекой: ход входа команда пишет своими строками, а служебные
   сообщения библиотеки идут в stderr (`platform/telegram-mtproto.md`, «Логи
   клиента не попадают в stdout»). Замер отчёта порции 132: `start` клиента
   без обработчика отправки кода делает `console.log("The confirmation code
   has been sent via …")` мимо платформы клиента — в stdout команды.

4. **Годность сессии не проверяется — проверяется наличие.** Непустая
   строка в env-файле означает «авторизован», и вход не запускается.

   Инвариант исправлен 2026-08-31 по замечанию реализующей стороны: прежняя
   редакция требовала распознавать негодную сессию, а это сетевой вызов —
   ровно то, чего шаг 1 обещает не делать. Оригинал проверяет только
   наличие; при этом его собственная справка говорит «если
   `TELEGRAM_SESSION` уже **валидна**» — то есть документация оригинала
   обещает больше, чем делает код. Повторять эту неточность в спеке
   незачем.

   Негодная сессия обнаруживается не здесь, а при первом же вызове
   `send`/`ls`/`search` — там сеть и так нужна.

## Проверка — и её честная граница

**Полный вход живьём непроверяем и проверяться не должен:** он требует
настоящего телефона, кода из Telegram и отзывает действующую сессию
владельца. Прогон «до конца» сломал бы рабочий доступ.

Проверяемо без входа:

- ветка «уже авторизован» — сессия в env-файле есть;
- ветка «нет TTY» — запуск с перенаправленным вводом, код 0 и подсказка;
- ветка «нет ключей приложения» — на подменном env-файле без них;
- что строка сессии не появляется ни в одном выводе и ни в журнале.

Что непроверяемо — говорить прямо, а не выдавать за проверенное. Живой вход
выполняет владелец вручную, если сессия когда-нибудь истечёт.

## Дословные тексты веток — снято 2026-08-31

Живая пара обеих реализаций (перенос — бинарь из `e7f8133`, оригинал — под
тем же подменным `XDG_CONFIG_HOME`):

```
уже авторизован:   # telegram: уже авторизован
нет TTY:           # telegram: пропущено (нет TTY; заполни TELEGRAM_API_ID/HASH в .env вручную)
отказ настраивать: # telegram: пропущено (позже: заполнить TELEGRAM_API_ID/HASH в .env и `mpu telegram login`)
пустой ввод:       # telegram: пропущено (api_id/api_hash пустые)
```

Все четыре — код 0; env-файл после трёх последних остаётся нулевого
размера, после первой не переписан (сверено по отметке времени).

Два расхождения с оригиналом приняты, дефектами не считаются:

- у оригинала первая строка — `# telegram: уже авторизован, пропускаю`;
  хвост потерян при переносе. Смысл тот же, и спека не задавала дословной
  формы, поэтому текст переноса и есть теперь норма — зафиксирован здесь,
  чтобы не плавал дальше;
- вступление про ключи приложения у оригинала — три строки с инструкцией
  (где на my.telegram.org, какие поля заполнять), у переноса одна со
  ссылкой `https://my.telegram.org/apps`. Требование спеки — «с указанием,
  где взять» — выполнено, а формат значений подсказывают сами вопросы
  (`api_id (integer)`, `api_hash (32 hex chars)`).

## Приёмка

- на основном конфиге: «уже авторизован», код 0, сессия не переписана
  (сверить env-файл до и после — по отметке времени, не по содержимому);
- ввод не с терминала → код 0 и подсказка;
- подменный env-файл без ключей → сценарий согласия; и отказ, и согласие с
  пустым вводом дают код 0 и не пишут в env-файл ни байта (проверено на
  оригинале 2026-08-31: файл остался нулевого размера);
- `mpu log` после всех прогонов не содержит строки сессии.
