# mpu init

Статус: черновик

## Назначение

Первичная инициализация локальной кэш-БД: создание схемы, discovery
контейнеров стенда через Portainer, прогрев кэшей Loki и Kaiten,
интерактивная авторизация Telegram. Запускается вручную на новой машине
и после изменения стенда; повторный запуск безопасен. Без init у кэш-БД
нет схемы и резолв селектора неработоспособен (`platform/selector.md`).

## CLI-контракт

`mpu init [--portainer TEXT] [--dry-run] [--reset]`

Пять шагов строго последовательно. Прервать команду могут только шаги
1–2; ошибки шагов 3–5 (best-effort) печатаются и не меняют код выхода.

**Шаг 1 — схема кэш-БД.** Идемпотентное создание всех таблиц и индексов
(`CREATE … IF NOT EXISTS`); существующие данные не затрагиваются.
stderr: `# bootstrap: схема в <путь к кэш-БД> готова`.

**Шаг 2 — discovery контейнеров (Portainer).** Подключение — из
env-файла: `PORTAINER_API_KEY` обязателен; базовый URL — `--portainer`,
иначе `PORTAINER_URL`; `PORTAINER_VERIFY_TLS`, не равный строке `true`,
отключает проверку TLS-сертификата. Обмен:

- `GET {base}/api/endpoints` — список environment'ов (Id, Name);
- на каждый endpoint —
  `GET {base}/api/endpoints/{id}/docker/containers/json?all=true` —
  все контейнеры, включая остановленные.

Ошибка обработки одного endpoint'а → stderr
`mpu init: endpoint <id> (<имя>): <причина>`, обход продолжается по
остальным. Если после обхода не найдено ни одного контейнера — stderr
`mpu init: ни одного контейнера не найдено`, exit 1, шаги 3–5 не
выполняются.

Сводка в stdout: `# найдено sl-N контейнеров: <count>`; далее по строке
на каждый CLI-контейнер, по возрастанию номера сервера:
`sl-<N>: <container_name> [<state>] @ endpoint <endpoint_id>
(<endpoint_name>) -> <portainer_url>/<endpoint_id>`; затем
`# прочих контейнеров: <count>`.

`--dry-run` — только сводка: кэш-БД не изменяется, шаги 3–5 не
выполняются, exit 0. Без `--dry-run` выполняется запись: при `--reset`
сначала удаляются все записи кэша контейнеров
(`# --reset: удалено <N> старых записей`), затем upsert каждой
найденной строки по ключу (portainer_url, endpoint_id, container_id) и
итог `# записано <N> контейнеров в <путь к кэш-БД>`.

Строка кэша контейнеров (таблица `portainer_containers`):
portainer_url, endpoint_id, endpoint_name, container_id, container_name
(первое из имён контейнера без ведущего `/`), server_number (номер по
`^/?mp-sl-(\d+)-cli$` из любого из имён, включая 0; у прочих
контейнеров номера нет), state, image, discovered_at (unix-время).

**Шаг 3 — кэш Loki.** Best-effort прогрев кэша хостов/сервисов Loki.
Успех → stderr `# loki: <H> hosts, <P> (host, service) пар`; любая
ошибка (в т.ч. незаданный `LOKI_URL`) → `# loki: пропущено (<причина>)`.

**Шаг 4 — справочники Kaiten.** Best-effort загрузка справочников
(spaces, boards, lanes, columns, роли) в кэш-БД. Ошибка верхнего
уровня → stderr `# kaiten: пропущено (<причина>)`; иначе stderr-сводка
`# kaiten: <S> spaces, <B> boards, <L> lanes, <C> columns, <R> roles`,
где счётчик упавшей части (lanes/columns/roles) печатается как `?`.

**Шаг 5 — авторизация Telegram** (единственный интерактивный):

- `TELEGRAM_SESSION` уже в env-файле → stderr
  `# telegram: уже авторизован, пропускаю`;
- stdin не TTY → stderr `# telegram: пропущено (нет TTY; заполни
  TELEGRAM_API_ID/HASH в .env вручную)`;
- иначе интерактив: при отсутствии `TELEGRAM_API_ID`/`TELEGRAM_API_HASH`
  печатается инструкция про my.telegram.org и вопрос
  `Set up Telegram now? [y/N]` (отказ или пустой ответ → пропуск с
  подсказкой); телефон — `TELEGRAM_PHONE` либо запрос
  `Telegram phone (e.g. +79991234567): `; далее логин: код
  подтверждения — видимый ввод, пароль 2FA — скрытый (если скрытый
  ввод недоступен — видимый). Успех →
  `TELEGRAM_API_ID/HASH/PHONE/SESSION` записываются в env-файл, stderr
  `# telegram: авторизован, сессия записана в .env`. Любая ошибка
  логина → `# telegram: пропущено (<причина>)`, код выхода остаётся 0.

## Ввод/вывод

stdout — discovery-сводка шага 2; stderr — служебные строки `# …`
остальных шагов, интерактивные подсказки и ошибки формата
`mpu init: <причина>`, без трейсбеков. Exit: 0 — успех (включая
пропуски best-effort шагов); 2 — ошибки конфигурации Portainer;
1 — discovery без единого контейнера.

## Побочные эффекты

Сеть: HTTPS к Portainer API, Loki и Kaiten; Telegram (MTProto) — только
при интерактивном логине. Запись: кэш-БД (схема; кэш контейнеров; кэши
Loki и Kaiten), env-файл (`TELEGRAM_*` при успешном логине; атомарная
запись — `platform/config.md`). Интерактивный stdin — только шаг 5 и
только при TTY. Внешние системы не мутируются: все обращения — чтение
(Telegram-логин создаёт сессию на стороне Telegram).

## Конфигурация

Env-файл (`platform/config.md`): `PORTAINER_URL` (или `--portainer`),
`PORTAINER_API_KEY`, `PORTAINER_VERIFY_TLS`; `LOKI_URL` (опционален);
креды Kaiten (контракт — спеки Kaiten-команд); `TELEGRAM_API_ID`,
`TELEGRAM_API_HASH`, `TELEGRAM_PHONE`, `TELEGRAM_SESSION`.
Кэш-БД — `~/.config/mpu/mpu.db`.

## Инварианты

- Схему кэш-БД создают только init и полный синк снапшота (одна и та
  же идемпотентная инициализация — `specs/update.md`); простое открытие
  БД прочими командами схему не создаёт.
- Повторный запуск идемпотентен: записи контейнеров обновляются по
  ключу, дубликаты не появляются; шаг 5 при живой сессии — no-op.
- Discovery обходит все endpoints и все их контейнеры; не-CLI
  контейнеры тоже сохраняются (без номера сервера).
- `--dry-run` не пишет никуда: ни в кэш-БД, ни в env-файл.
- Секреты (API-ключи, сессия Telegram) не печатаются ни в одной строке.

## Граничные случаи и ошибки

- Нет `PORTAINER_API_KEY` → stderr
  `mpu init: в ~/.config/mpu/.env нет PORTAINER_API_KEY`, exit 2.
- Нет ни `--portainer`, ни `PORTAINER_URL` → stderr `mpu init: укажите
  --portainer <url> либо PORTAINER_URL в ~/.config/mpu/.env`, exit 2.
- Все endpoints упали или контейнеров нет → exit 1 (см. шаг 2).
- 0 sl-контейнеров при непустом списке прочих → не ошибка: сводка с
  нулём, шаги 3–5 выполняются.
- Контейнер удалён в Portainer → его запись остаётся в кэше до
  `--reset` (см. «Известные отклонения»).
- Запуск без TTY (CI/cron) → шаг 5 пропущен с подсказкой, остальные
  шаги отрабатывают полностью.

## Golden-примеры

Снять при переводе в «к реализации» на фейковом Portainer (без живых
систем): happy path (discovery + запись + пропуски шагов 3–5); exit 2
без API-ключа; exit 2 без URL; exit 1 при пустом discovery; ошибка
одного endpoint'а с продолжением; `--dry-run` (кэш не изменён, шаги
3–5 не вызваны); `--reset`; повторный запуск (обновление без дублей,
stale остаётся). Отдельно — DDL всей схемы кэш-БД как фикстура (общая
граница с Python-веткой диспетчера на одном файле БД).

## Известные отклонения

- **preserve** — кэш контейнеров не перезаписывается целиком: upsert
  оставляет записи об исчезнувших из Portainer контейнерах до явного
  `--reset`. Причина: сбой одного endpoint'а при очередном init не
  должен вычищать живые контейнеры из кэша — резолв по кэшу продолжает
  работать; очистка stale — только явным решением пользователя.

## Открытые вопросы

- Механика discovery Loki и Kaiten здесь не зафиксирована — только
  последовательность, best-effort и формат строк сводки; границы самих
  систем фиксируются спеками соответствующих команд (ещё не написаны).
  До их появления шаги 3–4 дословно нереализуемы.
- Telegram (MTProto) может не переезжать с Python; как Go-версия
  выполняет шаг 5 — делегирует Python-ветке диспетчера или печатает
  «пропущено» — решить при реализации.
- Выборочные шаги (только discovery без Telegram и т.п.) флагами не
  выражаются — кроме `--dry-run`, отсекающего 3–5. Идея флагов шагов —
  кандидат в журнал переезда, differential не затрагивает.
