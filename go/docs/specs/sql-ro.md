# mpu sql-ro

Статус: черновик

## Назначение

Ad-hoc SQL по селектору в enforced read-only PG-сессии — безопасный
дефолт для диагностического чтения: запрет записи гарантирует сам
PostgreSQL, не анализ текста SQL. Write-вариант — `specs/sql.md`.

## CLI-контракт

`mpu sql-ro SELECTOR [SQL] [--server sl-N] [--dry] [--json] [--md]
[-v/--verbose]`

`SELECTOR` — client_id / spreadsheet_id substring / title substring /
`sl-N` / sw-алиас / `dev:<client_id>`; `SQL` — необязательный второй
аргумент; `--server sl-N` — override резолва (маршрут 3); `--dry` —
только meta-блок, без единого подключения/exec, exit 0; `--json` /
`--md` — формат результата; `-v/--verbose` — печатать meta-блок;
`-h/--help`. Без аргументов — справка, exit 2. `--json` вместе с
`--md` → exit 2, `mpu sql-ro: --json и --md взаимоисключающие` —
проверяется первым, до чтения SQL и до резолва селектора.

Источник SQL, первый непустой (после trim) побеждает: (1) аргумент;
(2) stdin целиком, если stdin не терминал, — без приглашения;
(3) интерактивный ввод до EOF, в stderr приглашение
`-- enter SQL, end with EOF (Ctrl+D):`. Итог пуст (после trim) →
exit 2, `mpu sql-ro: empty SQL`, без подключения к БД.

Три маршрута по селектору, первое совпадение побеждает; `--server`
совместим только с обычным, с dev-/sw-селектором → exit 2 до чтения
SQL: `mpu sql-ro: --server не сочетается с dev-селектором` /
`mpu sql-ro: --server не сочетается с sw-селектором`.

1. **dev** — префикс `dev:`; подключение к dev-PG. Хвост-число →
   client_id (ставится search_path), иначе client_id нет (не ошибка).
2. **sw** — алиас из `{sw, sw-pg, swpg, sw-back, swback, ws,
   workspaces}` без учёта регистра и краевых пробелов: SQL исполняется
   изнутри контейнера sw-back (ниже).
3. **обычный** — резолв селектора (`platform/selector.md`, выполняется
   до чтения SQL) → номер сервера + кандидаты. Среди кандидатов ровно
   один различный client_id → search_path на его схему; иначе (0 или
   больше одного) search_path не ставится — запрос идёт в дефолтный
   search_path сервера. При `--server` резолв не выполняется: селектор
   игнорируется (несуществующий — не ошибка), search_path не ставится.

Выполнение (dev/обычный): сессия открывается с серверной опцией
`default_transaction_read_only=on`; при заданном search_path перед SQL
отдельно выполняется `SET search_path TO "schema_<client_id>", public`;
затем весь текст SQL уходит серверу одним вызовом — без параметризации,
разбиения и модификации.

## Ввод/вывод

stdout — только данные результата; stderr — meta-блок, приглашение и
ошибки, без трейсбеков. Exit: 0 — успех (включая `--dry` и запрос без
result set); 1 — ошибка исполнения (read-only отказ, ошибка БД,
sw-exec); 2 — ошибки ввода и конфигурации (пустой SQL, конфликт флагов,
`--server` с dev/sw, резолв, sw-контейнер, нет адреса/кредов PG).

Meta-блок (stderr; печатается ⇔ `--verbose` или `--dry`); строки
`search_path` и `mode` — только при действующем search_path/read-only:

    server: sl-<N>
    pg_host: <host>
    pg_port: <port>
    database: <db>
    search_path: schema_<client_id>, public
    mode: read-only
    sql:
    <текст SQL как есть>

Маршрут dev: первая строка `server: dev`, host/port/db — dev-стенда. Маршрут sw:

    server: sw-pg (база sw-back)
    run_target: <target>
    dsn_source: env <VAR> (коннект изнутри контейнера)
    mode: read-only
    sql:
    <текст SQL как есть>

где `<VAR>` — имя env-переменной с DSN; при литеральном override —
`dsn_source: SW_PG_DSN (override) (коннект изнутри контейнера)`.

Результат (stdout):
- запрос без result set → `OK (rowcount=<N>)`; с `--json` — одна строка
  `{"ok": true, "rowcount": <N>}`;
- result set, default — ASCII-таблица: шапка, строка `-`-разделителей,
  строки; колонки через два пробела, каждая дополнена пробелами справа
  до max(длина имени, длины значений); NULL — пустая строка; последняя
  строка `(<N> rows)`; 0 строк → шапка + `(0 rows)` без разделителя;
- `--json` — одна строка: массив объектов `{колонка: значение, …}`,
  не-ASCII без экранирования; значение без JSON-представления (дата и
  т.п.) сериализуется его текстовой формой; 0 строк → `[]`;
- `--md` — markdown-таблица `| col | … |` / `| --- | … |` / строки;
  экранирование значений: `\` → `\\`, `|` → `\|`, перевод строки →
  `<br>`; NULL — пустая ячейка; 0 строк → шапка + разделитель.

Ошибки исполнения: пишущий SQL → отказ сервера, stderr
`` mpu sql-ro: запрос пытается писать — заблокировано read-only сессией. Для записи используйте `mpu sql`. ``,
exit 1, stdout пуст; любая другая ошибка БД → stderr
`db error: <текст ошибки сервера>`, exit 1.

**Маршрут sw.** Прямого доступа к БД воркспейсов снаружи нет: в
контейнере (target) запускается `node --input-type=module -` со
скриптом на stdin. Скрипт берёт DSN, вычищает из его query-string
Prisma-параметры `schema`, `connection_limit`, `pool_timeout`,
`pgbouncer`, `socket_timeout`, при read-only первым делом выполняет
`SET default_transaction_read_only = on`, затем пользовательский SQL
одним вызовом; результат (колонки, строки, rowcount, признак result
set; у `;`-склейки — последний result set) возвращается через вывод
exec и печатается в форматах выше. Target вида `sl-N` → штатный
контейнер сервера N, иначе — контейнер с этим именем из кэша. Ошибки:

- контейнер не резолвится → exit 2, stderr:
  `mpu sql-ro: контейнер '<target>' не резолвится (<причина>).` плюс
  строка-подсказка с отступом в два пробела:
  ``Нужен Portainer endpoint sw-хоста в кэше `mpu init`, либо задай
  SW_PG_RUN_TARGET (sl-N / имя контейнера).``;
- exec завершился ненулевым кодом или результат в выводе не распознан →
  stderr/stdout контейнера пробрасываются в stderr, затем
  `mpu sql-ro: выполнение не удалось (<причина>)`, причина —
  `результат не найден в выводе` либо `exit=<код>`; exit 1.

## Побочные эффекты

Обычный/dev: одно TCP-подключение к PG; записи не бывает ни при каких
входах. Маршрут sw: exec в контейнер + TCP к PG изнутри него. Резолв
читает локальную кэш-БД; результаты не кэшируются; файлов команда не
пишет. Журнал вызовов — обвязка (`platform/invoke-log.md`).

## Конфигурация

Адреса `pg_<N>`, порт/БД/креды PG и dev-стенд — `platform/config.md`.
Маршрут sw (env-файл): `SW_PG_RUN_TARGET` — target exec (дефолт
`sw-api`); `SW_PG_DSN_ENV` — имя env-переменной с DSN в контейнере
(дефолт `DATABASE_URL`); `SW_PG_DSN` — литеральный override DSN
(коннект всё равно изнутри контейнера).

## Инварианты

- Запись невозможна ни при каких входах на всех трёх маршрутах:
  гарантия серверная (`platform/readonly-default.md`).
- `--dry` не открывает соединений и не выполняет exec; meta-блок в
  stderr ⇔ `--verbose` или `--dry`, при успехе без них stderr пуст.
- search_path ставится ⇔ ровно один различный client_id (dev-хвост-число
  либо единственный client_id кандидатов резолва).
- NULL в таблице и markdown — всегда пустая строка/ячейка, никогда
  текст `None`/`NULL`; в JSON — `null`.
- Пользовательский SQL уходит серверу одной строкой, байт в байт как
  введён; конфликт `--json`/`--md` валидируется до чтения SQL.

## Граничные случаи и ошибки

- SQL-аргумент из одних пробелов → как незаданный: fallback на
  stdin/интерактив, не «empty SQL» сразу (источники — «CLI-контракт»).
- `sl-N` (сервер целиком) → кандидатов нет → без search_path;
  `dev:<нечисло>` → dev-PG без search_path, не ошибка.
- Ошибка резолва селектора → exit 2 до чтения SQL, тексты —
  `platform/selector.md`.
- Нет адреса `pg_<N>` / кредов → `mpu sql-ro: <причина>`, exit 2, без
  подключения (см. «Известные отклонения»).
- Пустой DSN в контейнере sw (нет env и нет override) → диагностика
  контейнера в stderr + `mpu sql-ro: выполнение не удалось (результат
  не найден в выводе)`, exit 1.

## Golden-примеры

Кандидаты (снять при переводе в «к реализации»; входы синтетические):
`mpu sql-ro <client_id> 'SELECT 1' --dry -v` (meta с search_path и
`mode: read-only`, без сети); то же с `sl-1`, `dev:<client_id>`, `sw`;
`echo 'SELECT 1' | mpu sql-ro <client_id> --dry -v` (stdin-источник);
`--json --md` вместе (конфликт, exit 2); живой SELECT c NULL-колонкой
(таблица / `--json` / `--md`) и с 0 строк; `UPDATE … WHERE 1=0` (текст
отказа read-only, exit 1); `SELECT 1 AS a; SELECT 2 AS b` (вопрос о
`;`-склейке); первый пример с `--server sl-<N>` (meta без search_path).

## Известные отклонения

- **fix** — ошибка конфигурации PG (нет `pg_<N>`, нет кредов) в
  оригинале — python-трейсбек и exit 1; правильно — `mpu sql-ro:
  <причина>`, exit 2, без трейсбека (`platform/readonly-default.md`).
- **fix** — ошибки маршрута sw в оригинале имеют префикс `mpu sql sw:`
  независимо от вызванной команды; правильно — префикс имени команды
  (`mpu sql-ro:`), тексты причин и подсказок — без изменений.
- **fix** — шапка таблицы при 0 строк в оригинале печатается с
  табуляцией между именами колонок, непустая — с двумя пробелами и
  выравниванием; правильно — единый формат шапки в обоих случаях.

## Открытые вопросы

- `;`-склейка: маршрут sw печатает последний result set; для
  обычного/dev маршрута выбор result set тестами оригинала не
  зафиксирован. Снять golden (`SELECT 1 AS a; SELECT 2 AS b`) до
  перевода в «к реализации» и закрепить контракт «результат последнего
  оператора» либо записать отклонение.
- Транспорт exec маршрута sw (Portainer/ssh+docker, кэш контейнеров) —
  отдельная платформенная спека, ещё не снята; здесь — только контракт
  вызова и тексты ошибок.
