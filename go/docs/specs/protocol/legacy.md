# protocol/legacy — операция делегации и стриминговые ответы

Статус: к реализации (утверждена 2026-07-29; проектная спека новой
поверхности — оригинала нет, эталоны авторские. Вводит стриминговую
форму ответа — расширение транспорта `protocol/core.md`)

## Назначение

Домен `legacy`: исполнение не переехавшей команды установленным рядом с
брокером Python-mpu (серверная механика — `platform/legacy-delegation.md`
канала брокера). Здесь — протокольная форма: операция `legacy.run` и
общий для будущих длинных операций **стриминговый ответ**.

## CLI-контракт

нет (протокол; пользовательская поверхность — реестр CLI и сами
legacy-команды).

## Ввод/вывод

### Стриминговый ответ (расширение транспорта)

Операция, помеченная своей спекой как **стриминговая**, отвечает не
одним JSON-RPC Response, а потоком `Content-Type: application/x-ndjson`:
последовательность строк-JSON («кадров»), по одному объекту на строку.
Клиент различает форму ответа по `Content-Type`; нестриминговые
операции отвечают как в `protocol/core.md`.

Кадры, в порядке появления:

- `{"stream": "out", "data": "<текст>"}` — кусок stdout исполняемого
  процесса; `{"stream": "err", "data": …}` — кусок stderr. Данные —
  UTF-8; кусок, не режущийся по границе UTF-8 (бинарный вывод),
  передаётся как `{"stream": …, "b64": "<base64>"}` — в кадре ровно
  одно из полей `data`/`b64`.
- `{"keepalive": true}` — пульс при молчании процесса (интервал —
  конфигурация брокера); клиент игнорирует, в вывод не попадает.
- Последняя строка потока — **стандартный JSON-RPC 2.0 Response** с
  `id` запроса: `result` при завершении процесса, `error` при отказе
  операции. После неё поток закрывается.

Порядок кусков одного потока (`out` отдельно, `err` отдельно) совпадает
с порядком вывода процесса; взаимный порядок `out`/`err` — порядок
наблюдения брокером. CLI печатает куски немедленно в свои
stdout/stderr, ничего не буферизуя.

### `legacy.run` (стриминговая)

- Запрос — стандартный JSON-RPC Request (`protocol/core.md`), с Bearer:
  `params = {"argv": [<имя команды>, <аргументы…>], "stdin":
  <строка|null>}`. `argv` — как получил CLI, без ведущего `mpu`.
  `stdin` — содержимое стандартного ввода одним куском, UTF-8
  (не-UTF-8 ввод CLI отклоняет до сети); `null` ≡ пустой ввод, процесс
  сразу видит EOF. Интерактивного канала ввода нет: stdin передаётся
  один раз, дальше только чтение потока.
- Маркер `confirmed` **не требуется**: операция не классифицирует
  legacy-команды на читающие/мутирующие — защита остаётся на
  собственных механизмах самих команд (read-only-варианты,
  y/N-подтверждения), как в оригинале.
- `result` финального кадра: `{"exit": <int>}` — код возврата
  Python-процесса; CLI завершает себя этим кодом.
- Ошибка операции (финальный кадр `error`): код `2000`
  (`legacy unavailable`) — Python-mpu не установлен/сломан; `message` —
  безопасное описание с именем команды. CLI печатает `message` в
  stderr и завершается exit 1. Кадры `out`/`err`, успевшие прийти до
  ошибки, уже напечатаны — это нормально.

## Побочные эффекты

Один вызов — одна запись в журнале брокера: строка `$ mpu <argv…>`
(литеральный `mpu`), перехваченные потоки, exit; маскирование и
лимиты — `platform/invoke-log.md`. Кадры `keepalive` в журнал не
попадают.

## Конфигурация

Интервал `keepalive` и путь Python-установки — конфигурация брокера
(`platform/config.md`). Лимит размера тела запроса из
`protocol/core.md` действует и на `stdin` — больший ввод отклоняется
транспортом до исполнения.

## Инварианты

- Прозрачность: байты `out`/`err` и exit-код доходят до CLI без
  изменений и переупорядочивания внутри каждого потока; журнал и его
  лимиты не влияют на проброс (fail-open).
- Ровно один финальный кадр; после него кадров нет.
- `keepalive` не влияет на вывод и exit-код.
- Обрыв соединения клиентом (включая Ctrl+C в CLI) → брокер завершает
  Python-процесс (SIGTERM, при игнорировании — SIGKILL); осиротевших
  процессов не остаётся; запись в журнале помечается обрывом.
- Секреты в argv/stdin не логируются сверх правил маскирования
  `platform/invoke-log.md`.

## Граничные случаи и ошибки

- Неизвестная Python-mpu команда в `argv` → это НЕ ошибка операции:
  Python-mpu сам печатает свой отказ в stderr и возвращает свой exit —
  пробрасываются как есть.
- Python недоступен → финальный кадр `error 2000`, журнал получает
  запись с ошибкой.
- Пустой `argv` → `-32602` (invalid params) обычным нестриминговым
  Response.
- Обрыв соединения во время исполнения → см. инварианты (процесс
  завершается, ответа нет).

## Golden-примеры

Оригинала нет — эталоны авторские: `fixtures/protocol/legacy/`, один
JSON-файл на класс. Формат — как у `protocol/core` (`request`,
`authorization`, `note`), но для стриминговых ответов вместо
`response` — `responseStream`: массив кадров в порядке следования,
последний элемент — финальный Response. Все argv синтетические.

| Класс | Фикстура |
| --- | --- |
| happy-стрим: чередование out/err + `result.exit` | `run-ok.json` |
| stdin одним куском, ненулевой exit | `run-stdin.json` |
| бинарный кусок → кадр `b64` | `frame-b64.json` |
| молчание процесса → `keepalive` | `frame-keepalive.json` |
| Python недоступен → `error 2000` | `err-legacy-unavailable.json` |
| пустой `argv` → `-32602` (нестриминговый Response) | `err-empty-argv.json` |
