# protocol/core — транспорт, аутентификация, ядро JSON-RPC

Статус: к реализации (утверждена 2026-07-29; повторно — в тот же день,
после оговорки о стриминговых ответах и решений по учёткам/TTL.
Проектная спека новой поверхности — оригинала нет, эталоны авторские.
Видна и Go-, и ts-сессиям — самодостаточна)

## Назначение

Единый контракт обмена Deno-CLI ↔ Go-брокер: кадрирование JSON-RPC 2.0
поверх HTTPS, аутентификация (login → временный JWT), формат ошибок,
операции ядра (`auth.login`, `core.version`). Прикладные словари
операций — отдельные спеки `protocol/<домен>.md`, появляются вместе с
переездом команд.

## CLI-контракт

нет (протокол; пользовательская поверхность — спеки команд CLI).

## Ввод/вывод

- Транспорт: HTTPS, один endpoint `POST /rpc`. Тело запроса — ровно
  один JSON-RPC 2.0 Request (UTF-8, `Content-Type: application/json`);
  тело ответа — ровно один Response (`application/json`). Исключение —
  **стриминговые** операции (помечены своей спекой домена): их ответ —
  NDJSON-поток кадров, завершающийся тем же стандартным Response;
  форма — `protocol/legacy.md`. Batch-массивы не поддерживаются:
  JSON-массив в теле → ошибка `-32600`.
- Request: `{"jsonrpc": "2.0", "id": <строка|число>, "method":
  "<домен>.<действие>", "params": {<объект>}}`. Нотификации (запрос без
  `id`) не используются: каждый запрос получает ответ.
- Имена операций — `<домен>.<действие>`: `auth.login`, `core.version`,
  `legacy.run`, далее по доменам. Словарь закрытый: неизвестный
  `method` → `-32601`.
- Response — по JSON-RPC 2.0: `result` при успехе, `error` при ошибке.
  Транспортный HTTP-статус при валидном JSON-RPC-обмене всегда 200;
  ошибки — только внутри JSON-RPC. HTTP-статус ≠ 200 клиент трактует
  как ошибку транспорта/инфраструктуры (не брокера).
- Коды ошибок: стандартные JSON-RPC (`-32700` parse, `-32600` invalid
  request, `-32601` unknown method, `-32602` invalid params, `-32603`
  internal) + прикладные ядра: `1000` unauthorized (нет/просрочен/
  невалиден JWT; неверная пара login/password), `1002`
  confirmation_required. Доменные коды — в спеках доменов, диапазон
  `2000+`. `error.message` — безопасное для клиента сообщение;
  внутренние детали (пути, SQL, stack) остаются в логах брокера.
- Аутентификация: HTTP-заголовок `Authorization: Bearer <JWT>` на
  каждой операции, кроме `auth.login`. Отсутствие, просрочка или
  неверная подпись → error `1000`.
- `auth.login`: params `{"login": <строка>, "password": <строка>}` →
  result `{"token": <JWT>, "expires_at": <ISO-8601 UTC>}`. Неверная
  пара → error `1000` с message `invalid credentials` (без уточнения,
  какое из полей неверно). Учётки — `.env` брокера: **хэш пароля**
  (bcrypt или argon2id — выбор реализации), не открытый текст;
  заведение пары — утилита брокера, генерирующая хэш. TTL токена —
  конфигурация брокера, дефолт **7 дней**; по истечении — повторный
  интерактивный login.
- `core.version`: params `{}` → result `{"version": <строка>}` (версия
  брокера — константа сборки). Требует аутентификации, как и все
  операции кроме `auth.login`.
- Мутирующие операции (признак — спека операции): обязательное поле
  `params.confirmed = true`, иначе error `1002`. Это enforcement
  брокера; интерактивное подтверждение — UX CLI.
- Разбор защитный: неизвестное поле верхнего уровня Request →
  `-32600`; неизвестное или отсутствующее обязательное поле `params` →
  `-32602`. Лимит размера тела и таймауты чтения/записи — конфигурация
  брокера.

## Побочные эффекты

Каждая принятая операция — включая завершившуюся ошибкой и неизвестный
`method` — оставляет ровно одну запись в журнале брокера
(`platform/invoke-log.md`). Пароль из `auth.login` и выданный токен не
попадают ни в журнал, ни в логи ни в каком виде.

## Конфигурация

- Брокер (`.env`): учётные пары login/password, секрет подписи JWT,
  TTL токена, лимит размера тела, таймауты. Детали — при пересмотре
  `platform/config.md`.
- CLI: адрес брокера — локальная настройка; полученный токен
  сохраняется между вызовами в локальном файле с правами 0600. Пароль
  CLI **не хранит**: `login` выполняется командой с интерактивным
  вводом, наружу уходит только по HTTPS, на диске остаётся только
  токен. Истёкший/отсутствующий токен → понятная ошибка CLI с
  подсказкой выполнить login.

## Инварианты

- Секреты не пересекают границу наружу: пароль и JWT-секрет не
  появляются ни в ответах (единственное исключение — `token` в result
  `auth.login`), ни в журнале, ни в логах брокера.
- Один Request → один Response → одна запись журнала; порядок полей и
  повторные вызовы не меняют semantику (идемпотентность — свойство
  конкретных операций, фиксируется их спеками).
- `error.message` безопасен для показа пользователю as-is.
- JWT stateless: брокер не хранит выданные токены; повторный login
  выдаёт новый токен, прежний действует до своего истечения.
- Разбор params строгий: неизвестное поле — ошибка, не молчаливый
  игнор.

## Граничные случаи и ошибки

- Тело не парсится как JSON → `-32700`.
- JSON-массив (batch) или неизвестное верхнеуровневое поле → `-32600`.
- Неизвестный `method` → `-32601` (+ запись в журнале).
- Лишнее/отсутствующее поле `params` → `-32602`.
- Bearer отсутствует/просрочен/подпись неверна (любая операция, кроме
  `auth.login`) → `1000`.
- Мутирующая операция без `confirmed: true` → `1002`.
- Внутренняя ошибка брокера → `-32603`, детали — только в его логах.

## Golden-примеры

Оригинала нет — эталоны авторские: пары Request → Response в
`fixtures/protocol/core/`, один JSON-файл на класс (поля: `request` —
или `rawRequest` для невалидного тела, `response`, `authorization` —
`null` | `"valid"`, `note`). Значения в угловых скобках (`"<jwt>"`,
`"<iso-8601-utc>"`, `"<semver>"`) — плейсхолдеры: контрактный тест
сравнивает форму, не значение. Точные тексты `error.message` — часть
контракта, закреплены в фикстурах (стиль: строчные, без точки на
конце). Эти пары — общие контрактные тесты обеих сторон.

| Класс | Фикстура |
| --- | --- |
| happy path `auth.login` | `login-ok.json` |
| happy path `core.version` | `version-ok.json` |
| не-JSON тело → `-32700` | `err-parse.json` |
| batch-массив → `-32600` | `err-batch.json` |
| неизвестный `method` → `-32601` | `err-unknown-method.json` |
| неизвестное поле `params` → `-32602` | `err-invalid-params.json` |
| без Bearer → `1000` | `err-unauthorized.json` |
| неверная пара login → `1000` | `err-invalid-credentials.json` |
| внутренняя ошибка → `-32603` (форма ответа) | `err-internal.json` |
| мутация без `confirmed` → `1002` | фикстура — в спеке первой мутирующей операции |

## Открытые вопросы

- Авто-повтор login CLI при error `1000` (сейчас — явная подсказка
  пользователю, без авто-релогина).
- Ревокация токенов: stateless без отзыва принят до появления
  требования; при компрометации — смена секрета подписи.
- Источник TLS-сертификата брокера (внутренний CA / публичный) —
  вопрос развёртывания, не протокола.
