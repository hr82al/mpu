# platform/readonly-default — политика чтения/записи

Статус: черновик

## Назначение

Инвариант mpu: диагностическое чтение безопасно по построению, мутация —
явная. Единственный универсальный enforced-механизм — read-only
PG-сессия; подтверждения записи — per-команда (карта ниже). У каждой
мутирующей команды обязан быть enforced read-only вариант или dry-режим.

## CLI-контракт

нет (политика; флаги — в спеках команд).

## Ввод/вывод

Read-only PG-сессия: подключение открывается с серверной опцией
`default_transaction_read_only=on` — запрет записи гарантирует сам
PostgreSQL, не разбор текста запроса. Любой пишущий SQL (включая
data-modifying CTE, пишущие функции и триггеры) отклоняется сервером
(SQLSTATE 25006); команда перехватывает это и печатает:
`mpu sql-ro: запрос пытается писать — заблокировано read-only сессией.
Для записи используйте `mpu sql`.` → exit 1. Для БД воркспейсов (sw),
куда снаружи прямого доступа нет и SQL исполняется изнутри контейнера,
тот же контракт обеспечивается установкой той же опции в начале сессии.

Карта паттернов подтверждения (фиксируется как есть; деталь — в спеке
каждой команды):

1. **Пара read/write команд** — `sql-ro` (только чтение, авторазрешаема)
   / `sql` (пишет сразу, без вопросов; защита — ask-разрешение
   запускающего харнесса). Общий `--dry` печатает мету и SQL без
   подключения, exit 0 — превью, не защита.
2. **`--dry-run` opt-in** (дефолт — писать немедленно): мутации Kaiten
   (перемещения, таймер), пакетная запись листов, exec-обёртки.
3. **Инвертированный `--yes`** (дефолт — только сухой прогон): редкие
   деструктивные локальные операции (снос локальных клиентских схем);
   такие команды физически подключаются только к локальным адресам и до
   прода не достают по построению.
4. **Интерактивный y/N** — единично (удаление ноты MR): без TTY и без
   `--yes` — немедленный отказ с подсказкой `добавь --yes` (не зависает
   на чтении несуществующего ввода).

Отдельная утилита `mpu confirm` — y/N-шлюз для пайплайнов: читает весь
stdin, показывает его в stderr, спрашивает через терминал напрямую
(stdin занят данными); `y`/`yes` → буфер целиком в stdout; любой другой
ответ/EOF → exit 1 `отменено — pipe прерван`, в stdout не уходит ничего;
нет терминала и нет `--yes` → exit 2 с подсказкой. Частичного пропуска
данных не бывает. (Команда решена к невыезду — контракт здесь
справочный, пока Python-версия жива.)

## Побочные эффекты

Политика сама по себе эффектов не имеет; она ограничивает эффекты
команд: read-вариант не может писать ни при каких обстоятельствах,
мутирующий — пишет туда, куда заявлено его спекой.

## Конфигурация

Креды и адреса PG — `platform/config.md`. Env-переключателей поведения
подтверждений нет — только CLI-флаги.

## Инварианты

- Read-only вариант не может выполнить запись НИ ПРИ КАКИХ входах:
  гарантия серверная, а не текстовый анализ запроса.
- Опция сессии действует одинаково на один оператор и на многооператорный
  блок в одном вызове.
- `--dry`/`--dry-run`-режимы не открывают мутирующих соединений.
- Деструктивные локальные команды не принимают селектор прод-сервера —
  изоляция по построению подключения, не по флагу.
- Новая мутирующая команда без read-only/dry-варианта в дерево не
  попадает (правило ревью).

## Граничные случаи и ошибки

- Пишущий SQL под read-only → перехваченный отказ сервера, exit 1,
  без трейсбека и без частичного выполнения.
- Data-modifying CTE (`WITH x AS (DELETE …) SELECT …`) → тот же отказ.
- Ошибка конфигурации (нет кредов) → exit 2; ошибка БД → `db error: …`,
  exit 1.

## Golden-примеры

Снять при переводе в «к реализации»: `SELECT 1` через read-вариант
(`--json`); `--dry -v` (строка `mode: read-only` в мете); заведомо
безопасный пишущий запрос с `WHERE 1=0` под read-вариантом (точный
текст отказа, exit 1).

## Открытые вопросы

- Го-порт: унифицировать ли четыре паттерна подтверждения под единый
  контракт флагов (`--dry-run`/`--yes`) — в оригинале осознанного
  общего контракта нет, это независимые решения команд. Решить до
  переезда первой мутирующей команды; сам переезд каждой команды при
  этом обязан остаться поведенчески нейтральным.
