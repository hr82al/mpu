# mpu kiten move / ready / review

Статус: черновик

## Назначение

Перемещение карточки Kaiten по трём независимым осям (доска / дорожка /
колонка) и две фиксированные цели поверх него: `ready` — в колонку
«Готово», `review` — в колонку «Код-ревью». Каждое успешное перемещение
записывается в локальный журнал перемещений — по нему другие команды
mpu строят дневную сводку «что я двигал».

Обвязка Kaiten (токен, base URL, формат HTTP-ошибок, разбор селектора
карточки, резолв `REF`-ссылок) — `platform/kaiten-http.md`.

## CLI-контракт

`mpu kiten move SELECTOR [--lane REF] [--column REF] [--board REF]`

- Нужна хотя бы одна ось, иначе exit 2:
  `нужно хотя бы одно из --lane / --column / --board`.
- `REF` — ID или подстрока названия (`platform/kaiten-http.md`,
  «Резолв справочной ссылки»). `--lane`/`--column` резолвятся в скоупе
  целевой доски: явный `--board`, иначе текущая доска карточки —
  одноимённые дорожки/колонки чужих досок не конфликтуют. При переносе
  на другую доску заданные дорожка/колонка должны принадлежать ей.
- Незаданные оси не меняются.

`mpu kiten ready SELECTOR [--column REF] [--note TEXT] [--dry-run]`
`mpu kiten review SELECTOR [--column REF] [--note TEXT] [--dry-run]`

- Перевод в целевую колонку на текущей доске карточки; дорожка и доска
  не меняются. Целевая колонка, по убыванию приоритета: `--column` →
  env `KITEN_READY_COLUMN` / `KITEN_REVIEW_COLUMN` → «Готово» /
  «Код-ревью».
- `--note` — заметка, сохраняется в строку журнала перемещений.
- `--dry-run` — печать намерения без единой мутации.

Релог: Kaiten молча игнорирует PATCH, не меняющий колонку карточки,
поэтому релог-bump выполняется, когда запрошенное перемещение сводится
к переводу в текущую колонку — задана колонка, равная текущей, и
остальные заданные оси не меняют положения: PATCH в соседнюю колонку,
затем PATCH обратно — Kaiten фиксирует перемещение. Соседняя колонка —
предыдущая по порядку колонок доски (sort_order, при равенстве — ID);
целевая крайняя левая → следующая справа.

Живые сценарии: `mpu kiten ready 12345678`;
`mpu kiten review 12345678 --note 'MR !999'`;
`mpu kiten move 12345678 --column Очередь --board 'Доска поддержки'`.

## Ввод/вывод

HTTP-граница (формы — `platform/kaiten-http.md`):

- `GET /cards/{id}` — положение «до»;
- релог: `GET /boards/{board_id}/columns` (колонки текущей доски) и два
  `PATCH /cards/{id}` (`{"column_id": <сосед>}`, затем
  `{"column_id": <цель>}`); иначе один `PATCH /cards/{id}` — только
  заданные оси: `{"board_id"?, "column_id"?, "lane_id"?}`;
- `GET /cards/{id}` — положение «после»: PATCH-ответ не несёт названий
  доски/колонки/дорожки, только id.

stdout успеха (все три команды):
`ok: {до} → {после}{ (релог)} · {url карточки}`, где положение —
непустые из `{Доска}`, `{Колонка}`, `{Дорожка}` через ` · `; все
пусты → `—`.

`--dry-run` (`ready`/`review`): выполняется только `GET /cards/{id}` и
резолв цели, затем stdout
`dry-run: {релог (влево→обратно) | перемещение} → «{имя цели}»
(колонка {id цели}); сейчас {положение}; PATCH не отправлен` — exit 0,
без PATCH и без записи в журнал.

Exit: 0 — успех; 2 — ошибки ввода (оси не заданы, нерезолвящийся
`REF`, селектор); 1 — ошибки API
(`mpu kiten <sub>: kaiten error: <текст>`).

## Побочные эффекты

Kaiten — PATCH-перемещение (выше). Локально — строка журнала
перемещений (кэш-БД, `platform/config.md`) после каждого успешного
перемещения; состав строки: id карточки, заголовок, url, колонка-куда
(название; пустое → `—`), дорожка, доска — по состоянию «после»,
колонка-откуда — по состоянию «до», заметка (`--note` у
`ready`/`review`; у `move` пусто), момент записи (epoch-секунды).
Журнал только пополняется; пустая/несозданная кэш-БД инициализируется
на месте.

## Конфигурация

`KITEN_READY_COLUMN`, `KITEN_REVIEW_COLUMN` — ID или имя целевой
колонки `ready`/`review`. Токен и base URL — `platform/kaiten-http.md`.

## Инварианты

- Оси независимы: незаданная ось не попадает в тело PATCH.
- Вывод и поля «после» строки журнала строятся по свежему GET после
  перемещения, не по PATCH-ответу; колонка-откуда — по GET «до».
- Строка журнала соответствует зафиксированному сервером перемещению:
  релог гарантирует, что перевод в текущую колонку тоже фиксируется
  (см. «Известные отклонения»).
- `--dry-run` не выполняет мутирующих запросов и не пишет в журнал.
- `ready`/`review` меняют только колонку — дорожка и доска карточки
  сохраняются.

## Граничные случаи и ошибки

- Ни одной оси у `move` → exit 2 (текст выше), без сетевых запросов.
- `move --column <текущая>` без других осей → релог-bump, суффикс
  ` (релог)` в выводе.
- `ready`/`review`, карточка уже в целевой колонке → релог-bump.
- Релог на доске с одной колонкой → exit 2:
  `на доске одна колонка — релог невозможен`.
- Релог: список колонок доски пуст → exit 2:
  `не удалось получить колонки доски для релога`; целевой колонки нет
  в списке → exit 2: `целевая колонка не найдена на доске карточки`.
- Сбой второго PATCH релога → карточка остаётся в соседней колонке
  (отката нет), exit 1, строки журнала нет.
- Нерезолвящийся/неоднозначный `REF` → exit 2
  (`platform/kaiten-http.md`).
- Ошибка API на любом шаге → exit 1; журнал не пополняется (запись —
  только после успешного финального GET).

## Golden-примеры

Снять при переводе в «к реализации» (своя тестовая карточка):
`ready <id> --dry-run` (оба варианта строки — перемещение и релог),
`move <id>` без осей (exit 2), `move <id> --column <текущая>` (релог,
`ok`-строка), `ready <id>` (happy path + строка журнала),
`move abc` (селектор, exit 2).

## Известные отклонения

- **fix** — решение о релоге оригинал принимает по набору флагов, а не
  по значениям: `--column <текущая>` вместе с `--lane <текущая>` или
  `--board <текущая>` уходит одним PATCH, который Kaiten молча
  игнорирует — перемещение не фиксируется, но команда печатает `ok` и
  пишет строку журнала. Правильное поведение — правило из
  «CLI-контракта»: релог-bump по сравнению значений осей.
- **fix** — в ошибках API `ready`/`review` печатают префикс
  `mpu kiten: kaiten error: …` без имени подкоманды. Правильно —
  `mpu kiten ready: …` / `mpu kiten review: …`
  (`platform/kaiten-http.md`).

## Открытые вопросы

- Журнал перемещений читают ещё не переехавшие команды mpu (дневная
  сводка перемещений): совпадение физической схемы таблицы кэш-БД со
  старой реализацией — решение владельца переезда при переводе спеки
  в «к реализации».
