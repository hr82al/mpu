# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Главное: качество и читаемость кода

Это основной приоритет проекта, важнее скорости получения результата. Код читают
чаще, чем пишут — оптимизировать нужно под чтение.

### Принципы, которые соблюдаются обязательно

- **KISS** — самое простое решение, которое работает. Умный код, требующий
  объяснений, хуже скучного очевидного кода.
- **YAGNI** — не закладывать абстракции «на будущее». Обобщать по факту третьего
  повторения, а не в ожидании второго. Один вызов — не повод для интерфейса.
- **DRY** — но не в ущерб ясности: два похожих куска с разными причинами
  изменения дублированием не являются, а их преждевременное слияние создаёт
  ложную связанность.
- **Минимум абстракций** — абстракция вводится только когда убирает уже
  существующую боль. Интерфейс с одной реализацией, фабрика ради фабрики, слой
  «на всякий случай» — не архитектура, а лишний уровень чтения. Конкретный тип
  по умолчанию; абстракция — по факту второй реализации или реальной границы
  тестирования.
- **Low coupling** — пакет знает о соседях минимум: узкие интерфейсы вместо
  общих типов, передача данных вместо разделяемого состояния, никаких глобалов и
  синглтонов. Изменение внутри пакета не должно требовать правок в вызывающих.
- **High cohesion** — в одном пакете/типе лежит то, что меняется по одной
  причине и вместе. Если файл описывается через «и» («парсинг **и** HTTP **и**
  метрики») — он разъезжается на части.
- **Явность** — никакой магии: явные зависимости, явные параметры, явный
  порядок инициализации. Не `init()`, не рефлексия, не скрытые побочные эффекты
  импорта. Поведение читается из кода вызова, а не выводится из соглашений.
- **SOLID** — прикладной минимум для Go: одна причина изменения на тип;
  расширение через новые реализации, а не правку `switch`; интерфейсы узкие и
  объявленные **на стороне потребителя** (1–3 метода); зависимости передаются
  явно (конструктор/параметр), а не берутся из глобалов.
- **Composition over inheritance** — встраивание и делегирование вместо
  наследования иерархий; в Go это естественно, не бороться с этим.
- **Явные ошибки** — никаких проглоченных `_ = err`; паника только на невозможных
  состояниях программы, а не на ожидаемых ошибках. Подробности — ниже.

### Читаемость: что проверять в каждом изменении

- Имена сообщают о назначении, а не о типе. Короткие для короткой области
  видимости, развёрнутые для экспортированного API.
- Функция делает одну вещь и укладывается на экран; ранние `return` вместо
  вложенных `if`; счастливый путь — по левому краю.
- Комментарии объясняют **почему**, а не **что**. Комментарий, пересказывающий
  код, удаляется. Экспортированные сущности документируются в стиле godoc
  (`// Имя …`).
- Никакого «мёртвого» кода, закомментированных блоков, отладочных `fmt.Println`
  и TODO без объяснения.
- Плотность комментариев, стиль именования и идиомы — как в окружающем коде.

### Библиотеки и приёмы

Если задача решается чище и короче с подходящей библиотекой или известным
паттерном — **предлагать это явно**, с обоснованием и альтернативой из стандартной
библиотеки. Стандартная библиотека — предпочтение по умолчанию; новая зависимость
требует аргумента «что она устраняет». Решение о добавлении зависимости
принимает пользователь.

### Типы и API

- **Принимать интерфейсы, возвращать структуры.** Функция объявляет в параметре
  ровно тот минимум поведения, который использует; наружу отдаётся конкретный
  тип, чтобы вызывающий видел полный набор возможностей и не терял их при
  расширении.
- Нулевое значение по возможности рабочее (`var b Builder` пригоден сразу).
  Конструктор появляется тогда, когда есть что валидировать или чем владеть, а не
  «потому что тип экспортирован».
- Аргументов у функции немного; если их больше трёх-четырёх и часть
  необязательна — структура параметров с говорящими полями, а не позиционный
  список, где на месте вызова видны голые `true, false, nil`.
- Возвращаемые срезы и карты, за которые тип отвечает, копируются перед выдачей —
  иначе внутреннее состояние правится извне незаметно.

### Ошибки

- Текст ошибки — с маленькой буквы, без точки на конце и без «failed to»:
  `fmt.Errorf("read config %s: %w", path, err)`. Обёртки складываются в читаемую
  цепочку, поэтому каждая добавляет только свой слой контекста.
- Sentinel-ошибки сравниваются через `errors.Is` / `errors.As`, никогда по тексту.
- Отменяемые и длительные операции принимают `context.Context` **первым**
  параметром. Контекст не хранится в структурах и не передаётся в поле.
- Ошибка `Close` у писателя обрабатывается: там теряется запись. У читателя
  допустимо `defer f.Close()`, но с явным комментарием, почему ошибка не важна.
- `defer` в цикле — сигнал ошибки: тело выносится в функцию, иначе ресурсы
  держатся до конца всего цикла.
- После итерации по `sql.Rows`/`bufio.Scanner` проверяется `.Err()` — молчаливый
  выход из цикла означает потерянные данные.

### Логирование

- Логгер (`log/slog`) передаётся явно параметром или полем конструктора.
  Глобального логгера в библиотечных пакетах нет — это скрытая зависимость.
- Сообщение — короткая постоянная строка, переменные уходят в пары
  ключ-значение: `slog.Error("read config", "path", path, "err", err)`, а не
  форматная строка со склейкой.
- Ошибку либо логируют, либо возвращают. Оба сразу — это одна и та же проблема,
  напечатанная в трёх местах по пути наверх.
- Секреты, токены, пароли и персональные данные в логи не попадают ни в каком
  виде.

### Конкурентность

Главный источник неявной сложности в Go, поэтому правила жёсткие:

- У каждой горутины есть понятный владелец и способ остановки (контекст или
  закрытие канала). «Висящих» горутин не бывает.
- Канал закрывает только отправитель. Синхронизация — `sync.WaitGroup` или
  `errgroup`, но не `time.Sleep`.
- Любое изменение, добавляющее горутины, проверяется `go test -race`.

### Производительность

Читаемость не разменивается на догадки. Оптимизация начинается с `testing.B` или
профиля, показывающего проблему, и сопровождается цифрами «было/стало» в
описании изменения. Без измерения ручной пулинг, микрооптимизации аллокаций и
`unsafe` не появляются. Предварительное выделение ёмкости среза, когда размер
известен, — не оптимизация, а обычный стиль.

### Границы пакетов

- Публичная поверхность минимальна; всё, что не является контрактом для внешнего
  потребителя, живёт в `internal/`.
- Пакетов `utils`, `common`, `helpers` не существует — имя пакета называет
  предметную область.
- Циклических зависимостей нет.
- `cmd/<binary>` содержит только разбор флагов и склейку зависимостей. Логика — в
  библиотечных пакетах, чтобы тестировалась без запуска бинаря.

### Проверка каждого изменения

Обязательный прогон перед сообщением о готовности:

```bash
gofmt -l . && go vet ./... && staticcheck ./... && go test -race -count=1 ./...
```

Пока это не зелёное, работа не считается выполненной — и об этом не сообщается.

Затем — разбор фактического диффа (`git diff -- go/`, `git diff --stat -- go/`;
без pathspec диff зашумлён, см. раздел об изоляции) по списку выше с
**конкретными** предложениями: файл, строка, в чём нарушение, как переписать.
Если нарушений нет — сказать это прямо. Замечания к соседнему коду, не
затронутому задачей, озвучивать отдельно, а не править по ходу.

## Процесс разработки

### TDD

Цикл: **красный → зелёный → рефакторинг**.

1. Тест, описывающий требуемое поведение, пишется первым и **запускается**, чтобы
   увидеть его падение по ожидаемой причине.
2. Минимальная реализация, доводящая тест до зелёного.
3. Рефакторинг под раздел о качестве — при зелёных тестах.

Тесты проверяют поведение и контракт, а не внутреннее устройство. Табличные тесты
(`t.Run` по случаям) — форма по умолчанию. Багфикс начинается с теста,
воспроизводящего баг.

Что считать хорошим тестом:

- Синхронизация — фейковые часы и каналы, никогда `time.Sleep`.
- `t.Helper()` в хелперах, `t.Cleanup()` вместо `defer` в setup, `t.TempDir()`
  вместо самодельных путей.
- Сравнение через `reflect.DeepEqual` (или `cmp.Diff`, если зависимость будет
  добавлена) с выводом `got`/`want` — падение теста должно читаться без отладчика.
- Внешние зависимости — за узким интерфейсом на стороне потребителя. Ручной
  заглушки достаточно; mock-фреймворки не добавляются.

### Контроль покрытия

Покрытие измеряется и не должно падать от изменения:

```bash
go test -cover ./...
go test -coverprofile=coverage.out ./... && go tool cover -func=coverage.out
go tool cover -html=coverage.out          # построчно, что не покрыто
```

Покрытие — инструмент поиска непроверенных ветвей, а не самоцель: непокрытыми не
должны оставаться ветви обработки ошибок и граничные случаи. Отчёт по покрытию
затронутых пакетов сообщать вместе с результатом.

### Атомарность изменений

- Одно изменение — одна задача. Рефакторинг, багфикс и новая функциональность не
  смешиваются в одном коммите.
- Правки хирургические: минимальный диff, решающий задачу. Не переформатировать,
  не переименовывать и не «попутно улучшать» несвязанные участки — это скрывает
  суть изменения в шуме.
- Каждый коммит оставляет дерево в рабочем состоянии: сборка проходит, тесты
  зелёные.
- Сообщения коммитов: Conventional Commits со скоупом (`feat(dt-host): …`,
  `fix(go): …`, `refactor(layout): …`), тема — на русском, в императиве.

### Зависимости

Каждая прямая зависимость сопровождается строкой «зачем» — комментарием в
`go.mod` рядом с `require`. После `go get` в том же коммите выполняется
`go mod tidy`; `go.sum` коммитится.

### Что не делать без спроса

- Не создавать каркас пакетов заранее (см. YAGNI) — структура растёт из задач.
- Не добавлять зависимости, не менять `module`/версию `go` в `go.mod`.
- Не трогать `.claude/`, `.gocache/`, `.gopath/`, `.gotmp/`.
- Не переписывать существующие тесты «под новый стиль» и не рефакторить код,
  которого задача не касается.

### Формат отчёта о выполнении

1. Что изменено — список файлов и в чём смысл каждого изменения.
2. Почему именно так, если решение неочевидно.
3. Вывод `gofmt`/`go vet`/`go test -race` и покрытие затронутых пакетов.
4. Замечания к соседнему коду — отдельным списком, без правок.

## Команды

```bash
go build ./...                        # сборка
go test ./...                         # все тесты
go test ./path/to/pkg -run TestName   # один тест (-run принимает regexp)
go test -race ./...                   # детектор гонок
go test -count=1 ./...                # без кэша результатов
gofmt -s -l .                         # что не отформатировано/не упрощено
go vet ./...                          # штатный статический анализ
staticcheck ./...                     # расширенный анализ

git status --short -- go/             # состояние; pathspec обязателен
git diff -- go/                       # дифф перед завершением задачи
git add go/…                          # только явные пути
git commit -m "…" -- go/              # коммит с pathspec
```

`go`, `gofmt` и `git` разрешены без запроса подтверждения.

Инструменты берутся из общего `~/go/bin` (он в `PATH`): `staticcheck`, `gopls`,
`dlv`. `staticcheck` ловит существенно больше, чем `go vet`, и входит в
обязательную проверку. Установка чего-то ещё:

```bash
CGO_ENABLED=0 go install <module>@latest
```

`CGO_ENABLED=0` нужен потому, что cgo пишет во временный каталог мимо `TMPDIR`.
Прокси `proxy.golang.org` открыт, поэтому ставится любой инструмент,
распространяемый как Go-модуль. Установка в общий `~/go/bin` затрагивает
окружение пользователя — спрашивать перед этим.

## Состояние проекта

**Greenfield-модуль Go**: исходного кода ещё нет — только `go.mod`
(`module mpu`, go 1.25.10) и инфраструктура `.claude/`. Каталог создан как цель
переноса Python-реализации из `../py` на Go.

Переносится **поведение, а не структура**: классы-неймспейсы, `**kwargs`-сигнатуры,
динамическая диспетчеризация и питоновское деление на модули не калькируются —
пакеты и типы проектируются заново по правилам выше. Паритет с `py/`
подтверждается тестом на одинаковых входных данных, а не построчным сравнением
кода.

Архитектуры, которую можно описать, пока не существует. Структуру пакетов
(`cmd/`, `internal/`, …) закладывает первая реальная задача — по YAGNI не
создавать каркас заранее. Раздел дописывается сюда по факту появления кода.

Конвенции репозитория: комментарии и документация — на русском, идентификаторы и
код — на английском. `vendor/` не используется, зависимости фиксируются через
`go.sum`. `go.work` локальный и не коммитится.

## Изоляция окружения

Рабочая область — каталог `go/`. Практические последствия:

- Соседние проекты в `/home/user/mr/mp/` (`sl-back`, `sw-back`, `wiki`, …)
  закрыты полностью.
- Внутри `mpu/` песочница открыта на чтение и запись целиком — это нужно git.
  Но `py/`, `docs/`, `CLAUDE.md` и `.claude/` запрещены правилами
  `permissions.deny`: инструменты Read/Edit туда не идут. Родительский
  `mpu/CLAUDE.md` вдобавок отключён через `claudeMdExcludes` — этот файл
  единственный источник контекста. Работать с `py/` без явной просьбы не следует.
- Git доступен: `Bash(git:*)` разрешён, история, диффы и коммиты делаются внутри
  сессии — **но только с pathspec**, см. ниже.
- Сеть открыта только для Go-прокси (`proxy.golang.org`, `sum.golang.org`,
  `storage.googleapis.com`): `go get` работает, прочие хосты — нет.
- `~/go` открыт: используется штатный `GOPATH` с общим кэшем модулей
  (`~/go/pkg/mod`) и общим `~/go/bin` в `PATH`.
- Через `env` в `.claude/settings.json` внутрь каталога перенаправлены только
  `GOCACHE=go/.gocache` (системный `~/.cache` закрыт) и `GOTMPDIR`/`TMPDIR` =
  `go/.gotmp` (системный `/tmp` закрыт). Оба в `.gitignore`.
- Временные файлы — в `$TMPDIR` (то есть `go/.gotmp`), не в `/tmp`.

### Git: обязательно работать через pathspec

Запрет на `py/`, `docs/`, `CLAUDE.md` и `.claude/` реализован подменой
содержимого: `py/` виден как пустой каталог, `CLAUDE.md` — как символьное
устройство. Git считает эти файлы **удалёнными и изменёнными**, хотя на диске они
целы. Поэтому:

- Смотреть состояние только с ограничением области: `git status --short -- go/`,
  `git diff -- go/`. Массовый `git status` покажет ~50 ложных удалений.
- Индексировать только явными путями: `git add go/…`. Коммитить с pathspec:
  `git commit -m "…" -- go/`.
- `git add -A|--all|-u`, `git commit -a|-am`, `git stash` **запрещены** — они
  закоммитят удаление `py/`. Это не рекомендация: их блокирует `PreToolUse`-хук
  в `.claude/settings.json`, который проверяет git-команды перед запуском.

`git push` не настроен: сеть открыта только на Go-прокси, `~/.ssh` закрыт.
Отправка в remote — из внешнего терминала.

`.claude/lock.sh on|off|status` — тумблер права на запись в
`.claude/settings.json`. Запускается **только из внешнего терминала**: в положении
`on` каталог `.claude/` read-only и запись падает с Errno 30.
