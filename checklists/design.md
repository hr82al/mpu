# Чек-лист проектирования (универсальный, TypeScript)

Модели: постановка и рецензия — сильная модель; проектирование — сильная, или слабая при
обязательной рецензии сильной; доводка и код по spec — любая.

Каждый пункт — триггер → действие → обязательный артефакт в spec.md.
Пункт без артефакта не считается выполненным. «Рассмотрел и отверг» — не ответ:
нужна строка с конкретной причиной по конкретному случаю.

Словарь: «сообщение» — вызов метода или функции, HTTP-ручка, событие; «получатель» — объект,
у которого есть и память, и поведение над ней; «владелец данных» — тот, кто держит состояние.
Запись (`interface` с полями) плюс свободные функции над ней — это НЕ получатель, а данные с
процедурами; в этом чек-листе такое считается отсутствием объекта.

1. **Примитивы.** Найди минимальный набор операций, которые нельзя выразить через другие
   (обычно 2–4). Всё остальное — выводится из них ровно один раз, **в одном месте**: в общем
   предке, в одной функции над протоколом или в одном методе базового объекта — а не по копии в
   каждой реализации. Артефакт: список примитивов и для каждой производной операции — через что
   и ГДЕ выведена (одно место).

2. **Особые случаи → получатели.** Выпиши ВСЕ места, где внутри функции есть ветка по виду,
   состоянию, «особому случаю» или по значению чужого поля (пустой, вырожденный, отсутствует,
   первый/не первый, локальный/удалённый, есть/нет, пришёл/ещё едет, отпущен/жив). Для каждого:
   отдельная **реализация с тем же протоколом** (класс или объект-литерал с методами), которая
   отвечает по-своему — либо одна строка, почему нет. Размеченное объединение с `switch` —
   допустимый ответ только для данных на границе внешнего контракта (сериализация, DTO), не для
   поведения внутри модуля; «свести к switch, чтобы не плодить классы» — не причина. Артефакт:
   таблица «ветка → реализация | причина».

3. **Проверка типа и `null`/`undefined` — нигде, включая равенство.** `typeof`, `instanceof`,
   `in`, `as`-приведение, type predicate с последующим ветвлением вне владельца; `=== undefined`,
   `?.`, `??`, `!`, `if (x)` с последующей веткой → вызов у получателя; отсутствие / ошибка /
   вырожденность / «уже отпущено» → объект, отвечающий на ВЕСЬ протокол настоящего (не флаг и не
   `null`), **один экземпляр на модуль**, если у него нет своей памяти (не создавать новый `Error`
   на каждое обращение). `null` на границе внешнего контракта допустим только как названный вид
   пустоты. Артефакт: список таких мест → имя объекта, которым заменено.

4. **Кто решает.** Таблица: каждое сообщение протокола → кто принимает решение. Если решение
   принимается по данным другого объекта (его поле, его тип, ответ его getter'а) → перенести к
   владельцу данных. Отдельно: у каждого модульного или глобального состояния (реестр, счётчик,
   `WeakMap` уровня модуля) — назван владелец-объект, либо строка, почему оно вне объекта.
   Артефакт: таблица «сообщение → решает → перенесено?» + список модульного состояния с владельцем.

5. **Память приватна.** Ни одна операция не отдаёт состояние ради чужого решения; никто не
   опирается на представление другого (порядок ключей, формат строки, коллекция внутри, индекс
   кортежа, `parts[i]` чужого узла). Запись с открытыми полями, которые правят снаружи
   (`rec.count++`, `cell.holders += 1`, `entry.seen.set(...)`) → объект с методом-намерением;
   экспорт из модуля или getter, чей результат используется снаружи для `if` → операция-намерение.
   Артефакт: список записей и getter'ов — что стало объектом, что оставлено и почему.

6. **Голые данные → протокол.** Строка-код, булев аргумент, выбирающий поведение, кортеж, словарь
   с известными ключами, `any`/`unknown`, доезжающий до `as` → тип с протоколом (объект с
   методами, брендированный тип; для набора значений — literal union с одним `switch` у владельца).
   DTO на границе контракта — данные, не нарушение. Артефакт: список.

7. **Основание решения — проверкой, а не текстом.** Решение, которое держится на свойстве системы
   («у строк дня один штамп», «вход не бывает пустым», «вызывается только из X», «ключ уникален»),
   закрепляет само это свойство тестом или `assert`; удаление кода «как недостижимого» — тоже решение
   такого рода, и его тест заменяется тестом на свойство, из которого следует недостижимость.
   Позднее решение, ломающее свойство, тогда краснеет само, а не ждёт перечитывания spec. Артефакт:
   у каждого такого решения строка «держится на: <свойство> → <тест>».

8. **Жизненный цикл носителя состояния.** Триггер: решение заводит или дописывает место, где
   состояние переживает процесс, — таблица или колонка PG/CH, ключ Redis, запись очереди, файл,
   строка кэша. Для каждого — четыре ответа: (а) кто и когда СНИМАЕТ запись — операция или срок
   числом; «никто» и «потом» — не ответ, отложить можно только словом владельца; (б) потолок роста
   числом: записей в сутки × срок хранения; (в) запись, не доходящая до конечного состояния (вечная
   ошибка, оборванный протокол): через сколько и чем она снимается ВИДИМО (строка лога + счётчик),
   повтор по ней — с растущей паузой и потолком; (г) что с записями при выключении флага, откате,
   смене режима. Артефакт: таблица «носитель → кто снимает → потолок → конечное состояние → откат».
   ⚠️ Живьём (T3, ozon !773, 07.10.2026): леджер требований прошёл design-check и мультиагентное
   ревью без очистки и без предела возраста долга; оба пробела нашёл владелец вопросом «а PG не
   забьётся?».

9. **Лимит — против числа нагрузки.** Триггер: решение вводит лимит — размер пачки, потолок
   просмотра, таймаут, паузу, срок, размер окна. Каждый такой лимит выбран против числа нагрузки, на
   которой он работает (объём очереди, число строк, поток событий в час — из плана, замера, прода).
   Артефакт: строка «лимит N — против нагрузки M (источник)»; лимит без числа нагрузки — основание без
   проверки (п. 7). Нагрузка больше лимита — показать, что обходит хвост за пределом.
   ⚠️ Живьём (T3, ozon !773, 08.10.2026): потолок просмотра 1000 принят без хвоста прода 1755–2569
   ключей из того же плана — долги за хвостом не просматривались часами; нашёл живой ревьюер.

10. **Значение — через его потребителя.** Триггер: решение хранит или отдаёт значение (колонка, ключ,
   метка времени, метрика, поле события). Названо, кто его читает и что по нему решает или меряет:
   критерий приёмки, очистка, панель, алерт, другой сервис. Если потребитель применяет порог — один
   числовой сценарий через него в spec («после двух прогонов метка = X, порог 30 мин → вывод»).
   Семантика, взятая из чужого документа, проверяется против СВОЕГО потребителя. Артефакт: таблица
   «значение → потребитель → что решает → сценарий с числами».
   ⚠️ Живьём (T3, ozon !773, 08.10.2026): «метка долга при долге сохраняется» перенесена из спеки
   гистерезиса; критерий лага ≤ 30 мин по ней показал бы 35 мин при фактических 17–18; тест закрепил
   неверную семантику.

Только потом — код, по протоколам из п. 4. Ограничитель — внутри: перед кодом напиши сценарий
использования как рассказ (последовательность вызовов с конкретными данными) и убедись, что после
проектирования он не длиннее черновика; отдельным пунктом это не считается и «ничего» здесь не
пишется. В конце spec — раздел «Пункты чек-листа»: для КАЖДОГО из десяти пунктов — что он заставил
изменить, или «ничего».

После него — `design-<проект>.md`, если есть.
