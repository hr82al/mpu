# Чек-лист проверки кода (универсальный, TypeScript)

Модели: постановка и рецензия — сильная модель; проектирование — сильная, или слабая при
обязательной рецензии сильной; доводка и код по spec — любая.

Пройди по коду сверху вниз. Для каждого пункта найди ВСЕ вхождения; для каждого запиши: место
(файл, функция, строка), что нарушено, как исправить. Помечай находки, меняющие структуру
(появление/исчезновение объекта, модуля, варианта union), словом «структура». Потом
отранжируй по вреду.

1. Проверка типа / `null` / `undefined` снаружи владельца с последующим ветвлением — **включая
   равенство** (`typeof`, `instanceof`, `in`, `as`, type predicate, `=== undefined`, `?.`, `??`,
   `!`); сюда же обход диспетчеризации: вызов по вычисленному ключу (`obj[name]()`), склейка имён.
2. Ветвление по значению поля или ответа другого объекта; размеченное объединение с `switch`
   по тегу там, где поведение могло жить в реализациях одного протокола (запись + свободные
   функции над ней вместо объекта).
3. Данные без протокола: кортежи, словари с известными ключами, строки-коды, флаги, булевы
   аргументы, выбирающие поведение; `any`/`unknown`, размазанные по вызывающим.
4. Getter или экспорт, чей результат используется для принятия решения не владельцем.
5. `null`/`undefined` как ответ или состояние; булев флаг «жив/отпущен/готов» вместо подмены
   получателя; новый экземпляр «отсутствия» на каждое обращение вместо одного на модуль; `throw`
   там, где объект мог бы ответить тотально (значением-исходом).
6. Одно знание в двух местах (формула, правило, константа, тот же union-литерал).
7. Глобальный/статический доступ вместо переданной ссылки (`process.env`, синглтон-импорт,
   `Date.now()` / таймеры без инъекции, модульная переменная состояния).
8. Изменение чужого состояния извне (мутация аргумента, `push` в чужой массив, запись в поле
   другого объекта).
9. Опора на внутреннее представление другого объекта (порядок ключей, формат строки, индекс
   кортежа, форма ошибки по тексту).
10. **Кто решает.** Для каждой публичной операции: решение принимает получатель? Если отправитель
    решает по данным получателя — находка «структура»: перенести к владельцу.

Правило для автора при доводке: находку «структура» нельзя отклонить без встречного дизайна —
либо исправить, либо предложить другой объект, который снимает нарушение.

В конце review — раздел «Пункты чек-листа»: для КАЖДОГО пункта — сколько находок и какие,
или «ничего».

После него — `review-<проект>.md`, если есть.
