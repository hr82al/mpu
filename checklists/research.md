# Как подбирались TS-чек-листы — запись эксперимента (2026-09-08)

Цель: перенести чек-листы zel (постановка, проектирование, проверка кода) на TypeScript так,
чтобы каждый пункт был подтверждён замером: слепые решатели с чек-листом и без против эталонов,
судьи по списку решений эталона. Всё ниже — замеры, не мнения. Метод — zel
`docs/research/checklists-experiment.md`, отличия названы.

## Метод

- **Эталоны** — фрагменты живых TS-проектов, отобранные по признакам принципов (одна поверхность —
  несколько реализаций; отсутствие как объект; получатель решает; позднее связывание), а не по
  именам. Каждый кандидат до постановки проходил **квалификацию**: судья читает только фрагмент и
  цели кода (`code-quality.md` §1), отдаёт `kay` 0..10 со строками-доказательствами, `goals`,
  хрестоматийность, число проектных выборов; порог эталона — `kay ≥ 7`, не хрестоматийный.
- **Постановка**: аналитик пишет «решения и почему» + слепую постановку по `statement.md`;
  судья утечки (эталон не видел) → при `leak ≥ 3` или `completeness ≤ 6` переписка;
  **контрольный пилот** (сильная модель, без чек-листа) + два судьи — задача берётся, если пилот
  далёк от эталона (`closeness ≤ 6` у обоих).
- **Решатели** получают ТОЛЬКО постановку и чек-лист; пишут `spec.md` с пометками `[D.n]` и
  разделом «Пункты чек-листа», `code.ts` 100–300 строк, `code.test.ts` по сценариям. Модели —
  opus и sonnet. Рецензия по `review.md` (opus), доводка автором.
- **Гейт формы до судей**: `tsc --strict` + `node --test` на каждой работе (все 40 работ прошли).
- **Судьи** ×2, анонимные буквы, три оценки 0..10: близость к решениям эталона · принципы ·
  цели кода. Отличие от zel — третья шкала. Согласие судей ±0.5–1; разница < 1 — шум.

| effection · слабая | | 5/5/5.5 | 6.5/6.5/8 | 5.5/5.75/6.25 | 6.5/7.5/7.25 |

Направление совпадает у обоих судей:

- **Сильная модель**: чек-лист даёт +1…+4.5 к близости и +2…+3 к принципам против пилота на всех
  пяти задачах. v1 и v2 на ней различаются в пределах шума. Рецензия добавляет ещё +0.5…+1.75;
  после неё принципы 8.75–9.25 везде, кроме `dataflow` v1 (9) — то есть потолок достигается
  рецензией, а не версией чек-листа.
- **Слабая модель**: v1 одна оставляет её на уровне пилота (4.5–7 против 3.5–7.75). v2 поднимает
  принципы на +1.75…+2.25 на трёх задачах из пяти (`stubhook`, `dataspace`, `transport`),
  на `effection` +0.75, на `dataflow` −0.5 (шум). После рецензии сильной моделью v2 даёт близость
  6.5–7.75 и принципы 6.75–8.75 — уровень пилота сильной модели или выше на четырёх задачах.
- **Цели кода**: у сильной модели v2 + рецензия не ниже v1 + рецензии на всех пяти задачах
  (`transport` 8.25 против 7.75, `dataflow` 8.5 против 7.5).
- **`dataflow` — исключение и оно объяснимо**: единственная задача, где пилот сильной модели уже
  6.25–7.75 по близости (область предписывает устройство, см. таблицу постановок). Там чек-лист
  близости не добавляет, добавляет только рецензия; слабая модель на v2 просела в пределах шума.

## Правки v1 → v2

v1 (перевод zel на TS-словарь): `design` п.7 «сценарий и мера» — «ничего» в 5 из 6 ячеек →
снят, ограничитель оставлен фразой перед кодом. Системные промахи по судьям: у sonnet ×3 —
«размеченные объединения вместо реализаций, null-объектов нет, записи с открытыми полями и
свободные функции над ними»; причина — v1 п.2 разрешал «discriminated union с одним switch» как
замену получателю. У opus ×2 — новый `Error` на каждое «отпущено» вместо одного экземпляра;
производная операция выведена в каждой реализации, а не в предке.

v2: п.2 — реализация с тем же протоколом, union + `switch` только для данных на границе
контракта; п.3 — один экземпляр null-объекта на модуль; п.1 — «в одном месте» = предок или одна
функция; п.4 — плюс владелец модульного состояния; п.5 — плюс записи, правимые снаружи; словарь —
«запись + свободные функции = не получатель». `review` v2: п.2 и п.5 уточнены теми же признаками.
Абляция v2: все шесть пунктов `design` дают изменения во всех ячейках (п.5 — «ничего» 2/6); все
десять пунктов `review` дают находки.

## Что не подтвердилось / оговорки

- n = 1 работа на ячейку, 2 судьи; выводы только там, где направление совпадает.
- Пилот — opus; «sonnet против пилота» = sonnet против сильной модели без чек-листа.
- Ozon-файлы (`proc-ozon-cl/checklists/*-ozon.md`) экспериментом не проверялись: выведены из документов вертикали;
  абляция по правилу «три карточки подряд “ничего” → удалить».

## Техническое (пригодится при повторе)

- `pipeline()` в workflow ждёт массив: `args.problems`, а не голый `args` — иначе TypeError.
- Гейт формы: Node в strip-only режиме не принимает parameter properties →
  `--experimental-transform-types`; без `package.json` файл считается CJS и top-level await в
  тестах падает у `tsc` → `--module esnext --moduleResolution bundler`.
- Анонимизатор режет разделы «Пункты чек-листа» и «Что изменено по рецензии» и заменяет метки
  `[D.n]`/`[R.n]` на `[П]`; порядок букв — по хешу от имени ячейки.
- Материалы — `~/tmp/ts-checklists-research/` (не в репозитории): `samples/`, `originals/`,
  `problems/`, `checklists/`, `results/`, скрипты `wf-*.js`, `anon.py`, `ablate.py`, `check.sh`,
  `decode.py`, заметки `results/notes.md`.
