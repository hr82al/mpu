# CLAUDE.md — `@mpu/command`

Слой команд `mpu`: контракт команды и порт io, env-файл, ворота
`mpu confirm`, метка `mpu jsdate`, резолв селектора, атом кэш-БД,
локальные предпочтения и `mpu config`, правила подтверждения, помощники
тестов потребителя. Ставится архивом из `release/`.

Спеки — в `ts/docs/specs/` mpu: порция `platform/tslibs-n3.md`, договор
пакета `platform/tslibs-package.md`; поведение — `platform/command-contract.md`
и спеки, на которые ссылаются шапки модулей (`platform/env-file.md`,
`confirm.md`, `jsdate.md`, `platform/selector.md`, `platform/store.md`,
`platform/config.md`, `platform/policy.md`). Ссылки на спеки в комментариях
— от `ts/docs/specs/`.

## Поверхность — девять точек входа

- `@mpu/command` (`index.ts`) — контракт команды: объявление, порт io,
  разбор аргументов, ошибки ввода и предметной области, кэш-БД как порт.
- `@mpu/command/env` (`env.ts`) — env-файл сессии.
- `@mpu/command/confirm` (`confirm.ts`) — команда `mpu confirm` и правило
  согласия `isYes`.
- `@mpu/command/jsdate` (`jsdate.ts`) — команда `mpu jsdate`.
- `@mpu/command/selector` (`selector.ts`) — резолв селектора по кэш-БД.
- `@mpu/command/store` (`store.ts`) — открытие кэш-БД, схема, транзакции.
- `@mpu/command/config` (`config.ts`) — предпочтения, реестр ключей и
  команда `mpu config`.
- `@mpu/command/policy` (`policy.ts`) — правила подтверждения.
- `@mpu/command/testing` (`testing.ts`) — подставное io и спрошенный,
  временная кэш-БД, запуск модуля `.ts` текущим рантаймом. `vitest` вход
  не тянет: потребитель грузит его и из генераторов эталонов, запущенных
  без Vitest (там импорт `vitest` падает). Области `describe` и
  поддельные часы — у потребителя.

Поверхность входа — `mod.ts` его каталога (`export *`); имя попадает
наружу, только если его экспортирует `mod.ts`. Два исключения: у
`config.ts` — ещё `configCommand` (реэкспорт из `mod.ts` замкнул бы цикл),
`testing.ts` собирает три модуля `src/testing/` — по модулю на вид
помощника. Пакет не
импортирует доменные модули `ts/` (`kiten`, `sheet`, …); реестр ключей
`config/registry.ts` их ключи называет данными.

## Команды

```bash
bun install
VITEST_MAX_FORKS=2 bun run gate   # biome → tsc → тесты Bun, Node, Deno → check:release
bun run build                     # dist/<вход>.js, куски chunk-*.js, .d.ts
bun run release                   # release/mpu-command-<версия>.tgz
bun run check:release             # сборка и упаковка = архив в release/
```

Рантаймы гейт гонит по одному. Поменялись исходники или `package.json` —
`bun run release` и архив в тот же коммит, иначе `check:release` красный.
Любое изменение `dist/` — новая версия: `version` в `package.json` и новый
архив одним коммитом, прежний удаляется.

Сборка — с `--splitting`: общие модули входов лежат в одном куске. Без него
у каждого входа своя копия `DomainError`, `UsageError`, `NO_ONE`, и
`instanceof`/сравнение по ссылке между входами молча лжёт.

Под Vitest+Bun `zod` идёт через преобразование Vite
(`vitest.config.ts`, `server.deps.inline`): родной импорт внешнего модуля
теряет реэкспорт `z`.

## Раскладка

- Корневые `index.ts` … `testing.ts` — поверхности; `src/<каталог>/` —
  устройство и тесты `*.test.ts` рядом с кодом.
- `src/{env,confirm,selector,store,config,policy}/testdata/` — копии
  эталонов канала `ts/docs/specs/fixtures/` байт-в-байт. Сверить их с
  каналом не может ни пакет (канал вне его папки), ни `ts/` (папку пакета
  он не читает), поэтому правило: копия меняется только переносом файла из
  канала тем же коммитом, что и эталон, никогда правкой по месту; Biome их
  не форматирует (`biome.json`, `!**/testdata`).
- `release/` — архивы версий, коммитятся; `dist/` — нет.

## Порядок изменения

Гейт зелёный → разбор итогового диффа субагентом со свежим контекстом (не
автор) по чек-листам `../../ts/docs/checklists/review.md` + `review-mpu.md`
(сессию библиотеки запускают с `--add-dir` на этот каталог; копий нет) →
исправление найденного → гейт зелёный повторно → коммит. Ядро чек-листов:
объект держит свою память (запись + свободные функции над ней — не объект);
особый случай — отдельная реализация, а не ветка по виду; позднее связывание
и один null-объект на модуль вместо проверок `typeof`/`instanceof`/`null`;
голые данные (строка-код, булев флаг, кортеж) — протоколом.

## Правила кода

Действуют правила `ts/CLAUDE.md` mpu; главное из них:

- Ничего специфичного для рантайма: ни `Deno.*`, ни `Bun.*` — только `node:*`
  и npm. Тесты — Vitest, зелёные под Bun, Node и Deno.
- Функция ≤ 40 строк, вложенность ≤ 3; ранние выходы. JSDoc на каждом
  экспорте; комментарий объясняет «почему».
- Строгий TypeScript, без `any`; `as` и `!` — с обоснованием рядом.
- Бросаются только `Error` и подклассы; обёртка — через `cause`.
- Никакой работы при импорте. Синхронизация сном в тестах запрещена.
- Линтер — рекомендованный без выключений; исключение по месту —
  `biome-ignore` с причиной в той же строке; на файл (`biome-ignore-all`)
  — только когда причина — природа всего файла (`command/schema.ts`:
  ключи JSON Schema — данные чужого документа).

## Зависимости

Версии точные, без `^`; `bun.lock` коммитится. Библиотеки `tslibs/*` —
необязательные `peerDependencies` плюс `devDependencies` архивом
(договор [S.9]): потребитель ставит их сам, копия на граф одна.

- `zod` 4.4.3 — объявление схемы аргументов и результата команды
  (`platform/command-contract.md`). **Обязательный** peer: схемы
  пересекают границу пакета — `z.ZodType` в публичных типах объявления
  команды, `z.toJSONSchema` пакета над схемами потребителя, — поэтому тип
  и рантайм должны быть одного `zod` потребителя (`dist/` его не
  бандлит); вход `.` и ещё шесть входов (все, кроме `/store` и
  `/policy`) грузят его при импорте.
- `@mpu/language` (архивом) — объекты цепочки и картинка ответа
  (`/objects`, `/picture`) в контракте команды.
- `@mpu/base` (архивом) — ошибки ОС по коду (`/oserror`) при открытии
  кэш-БД.
- `vitest` 3.2.4 (dev) — тесты пакета под тремя рантаймами.
- `@mpu/testing` (архивом, dev) — `thrown`, `rejected` в тестах.
- `@biomejs/biome` — формат и линт; `typescript`, `@types/node` — проверка
  типов и `.d.ts` сборки.
