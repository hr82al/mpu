# CLAUDE.md

Overview дерева `mpu` целиком. Корневой CLAUDE.md монорепо (`../CLAUDE.md`)
применяется как есть.

`mpu` (monorepo python utilities) — multi-purpose CLI для вспомогательных операций
над данными монорепо. Отдельный `.git` (этот каталог) — версионируется независимо
от `sl-back` / `sw-back` / `sw-front`. Ветки/MR не создавать, коммитить прямо в
`main` (как и `mp`; см. корневой Git & MR workflow).

## Чек-листы качества — обязательно, без напоминания

Любая работа с кодом mpu — постановка, спека, досыл, рецензия — идёт по
чек-листам `proc-ak-ts` и их проектному слою `*-mpu.md`. Изолированная сессия
skill не видит, поэтому набор лежит двумя одинаковыми копиями: `checklists/` в
корне (для сессии из корня и подпроектов вне `ts/`) и `ts/docs/checklists/`
(канал `ts/`). Порядок, роли, ядро и две команды проверки совпадения —
`checklists/mpu.md`. Правка универсального набора — в skill, проектного слоя — в
`checklists/`; затем копирование в обе точки. Каждый `post` в ячейку несёт сценарии, ядро дословно,
требование артефактов design/review и раздел о трате контекста — состав в
`ts/docs/CLAUDE.md`, «Что несёт каждая постановка». Приоритет — у чек-листов:
правило `ts/CLAUDE.md` «данные + функции, расширение через `switch`» заменено
2026-09-17.

## Структура

- `ts/` — **единственная реализация на сегодня** (разъезжается на подпроекты по
  `docs/2026-09-17-mpu-objects-design.md`): один бинарь, две точки входа к одним и
  тем же командам — CLI для человека (`~/.local/bin/mpu`, `deno compile`) и
  MCP-сервер для агента (Streamable HTTP, Hono). Правила качества и тулинга
  модуля — `ts/CLAUDE.md`.
- Каталога `py/` больше нет (2026-08-31): Python-реализация выведена из
  эксплуатации, когда CLI перестал к ней обращаться. Что переживает удаление и
  что потеряно — `docs/plans/command-migration.md`. Установленная версия могла
  остаться в `~/.local/share/uv/tools/mpu/`; работой CLI она не используется.
- Каталога `go/` больше нет (2026-08-04): спеки отменённой Go-редакции
  адаптированы под один бинарь и переехали в `ts/docs/specs/`, план — в
  `docs/plans/command-migration.md`, журнал — в `docs/migration-log.md`.
  `docs/go-migration.md` и `docs/broker-architecture.md` оставлены как история
  решений — не развивать.

## Роли сессий

Переезд вёлся тремя ролями, и граница между ними была не формальностью, а
способом не дать реализации подсмотреть в Python-код вместо спеки. Кода
больше нет, а роли остались: спека по-прежнему пишется отдельно от
реализации, и это единственное, что удерживает их от срастания.

- **Спецификатор** — эта сессия (из `mpu`). Пишет **только** `ts/docs/`: спеки,
  golden-фикстуры, план. Кода в `ts/src/` не трогает.
- **Изолированная Deno-сессия** — пишет код `ts/`. Ей не видны ни `docs/`, ни
  этот файл: знание о требуемом поведении доходит до неё исключительно через
  `ts/docs/specs/` по правилам `ts/docs/CLAUDE.md`.
- **Оператор** — человек: запускает изолированные сессии и принимает результат.

Практическое следствие для этой сессии: внутри `ts/` менять можно `ts/docs/`;
исходники и тесты — читать, чтобы принять работу, но не править.

Граница держится и для `ts/CLAUDE.md`: его ведёт изолированная сессия, а
спецификатор правит его только по явному разрешению пользователя и разово
(так было 2026-08-14 — правило передачи работы и устаревшее «Состояние
проекта»). Разрешение не превращается в постоянное: следующая правка того же
файла — снова через постановку порции, а не своей рукой.

**Постановка и отчёт ходят через `ts/.tmp/buf.txt`** — один файл, доступный
обеим сессиям (вне git). Ходить в него обе роли должны задачей
`deno task handoff` из каталога `ts/` (`status`/`read`/`post`/`report`/`wait`,
код — `ts/handoff/`): она пишет атомарно, не даёт затереть неотработанное и умеет
ждать нужный маркер. Спецификатор кладёт туда постановку порции и забирает
оттуда отчёт; изолированная сессия читает постановку и перезаписывает файл
отчётом. Первая строка — маркер `# ЗАДАНИЕ` либо `# ОТЧЁТ`: по нему любая из
сессий на голое «go» сама понимает, читать ей постановку или писать отчёт.
**Каждая роль, записав своё, сама встаёт на ожидание встречного маркера**
(`wait task` / `wait report`, фоном) — оператор сообщений между сессиями не
носит и «готово» никому не передаёт; его дело — запустить сессию однажды.
Ячейка одна, и запись в неё — всегда полная перезапись: новое кладётся
вместо старого, дописывать в конец нельзя. Перед перезаписью прочитать лежащее и
перенести всё ценное в долговечное место — спеку, план, `docs/migration-log.md`,
сообщение коммита. Подробности для обеих ролей — `ts/docs/CLAUDE.md`, раздел
«Передача работы».

**Перед каждой новой постановкой — чистый контекст исполнителя.** Порция
получает всё нужное из спеки и постановки; хвост прошлых порций дорожает на
каждом ходу и мешает: исполнитель сверяется с памятью о старых текстах спек, а
не с файлом. Знание, которое должно пережить порцию, идёт разделом «что
разбору знать». Порядок — чтобы ожидание не разбудило исполнителя раньше
очистки (гонка ловилась живьём):

1. Отчёт забран (приёмка — по нему), в ячейке `# ОТЧЁТ`, исполнитель стоит
   на `wait task`.
2. `bash ~/mr/mp/.claude/skills/proc-isolated-tmux-sessions/clear.sh <окно>
   ts/.tmp/buf.txt` — ждёт простоя, `/clear`, «прочитай ячейку»: там отчёт,
   исполнитель по правилу «go» снова встаёт на ожидание — уже с чистым
   контекстом.
3. Только теперь `deno task handoff post`.

## Справка — часть контракта команды, а не оформление

У справки два читателя, и второй решает по ней, существует ли инструмент:
описание тула для агента собирается из однострокѝ и текста справки, другого
источника у него нет. Отсюда порядок, обязательный для каждой команды:
**однострока называет вопрос, на который команда отвечает; первый абзац
справки — момент работы, в который её зовут, и чем её ответ отличается от
подручного средства (грепа, чтения глазами); дальше — состав** (аргументы,
границы, разделы вывода, коды выхода, примеры). Перечень частей ответа вместо
повода звать — самая частая форма промаха: читается как оглавление и не
объясняет, зачем брать инструмент.

Правило целиком, вместе с проверкой, которой оно снимается с автора, —
`ts/docs/specs/platform/registry.md`, раздел «Что говорит справка». Спека
команды задаёт **состав** справки и требует повода в первом абзаце; сам текст
живёт в коде рядом с командой, поэтому в постановке порции это отдельное
требование, а не подразумеваемое.

Второе следствие того же: команда, не внесённая в закрытый список публикации
(`ts/docs/specs/fixtures/mcp-server/tool-policies.json`), агенту не видна
вовсе — список fail-closed. Для read-only команды отсутствие в нём — решение
«агент этого не увидит», и принимать его надо осознанно, а не умолчанием.

## Язык строки — инварианты

Строка `mpu` — Smalltalk на словах: всё — объект и сообщение (дизайн —
`docs/2026-09-22-mpu-language-design.md`, серии — `docs/plans/`). Любая новая
команда и любая правка языка держат:

1. **Значение — только ключом**, ключи из словаря: `target` (где исполнить —
   клиент, сервер, dev), `id` (номер главной сущности команды), `text`,
   `query`, `since`/`until`, `limit`. Для прочего — свой описательный ключ с
   причиной (`warehouse:`); словарь не растягивать на чужой смысл. Голое
   слово — всегда сообщение, не значение.
2. **Не флаги, а сообщения**: формат вывода — сообщение результату (`… end
   csv`), способ исполнения — вариант до ключей (`process dry target: 54`),
   отбор — сообщения результата (`… end where: … is: …`).
3. **Порядок строки**: команда → варианты → ключи → `end` → сообщения
   результату.
4. **Ничего не терять**: каждый прежний вход получает новый адрес; снятое
   написание — громкий отказ с готовой исправленной строкой, не тишина.
5. **`ask` — первым словом**, если строка может дойти до записи; вопрос
   человеку — на каждую запись.
6. **Одно правило вместо двух**; слова грамматики — одна константа.
7. **Справка**: однострока → когда звать → примеры → состав; описание тула
   ≤ 2048 байт.

## Синтаксис языка — решает слепой замер на `sonnet`

Строка `mpu` — простой Smalltalk на словах, который модель пишет верно с первой
попытки. Развилку синтаксиса (слово, знак, порядок, правило разбора) решает
замер, а не вкус:

1. **Проходимость.** Каждый токен проходит параметром bash, fish и nu без
   кавычек — проверить прогоном в трёх оболочках скрипта, печатающего
   `[слово]` на аргумент. Кавычки, скобки, `# * ? ; | < > $ & ~` — нельзя.
2. **Генерация.** Два свежих агента `sonnet` (промпт по-русски и по-английски),
   без инструментов, получают принятую грамматику, ограничения и 6–10 задач и
   придумывают запись сами. Их совпадения — кандидаты.
3. **Слепой замер.** На кандидата — свежий агент; описания отличаются только
   проверяемым местом, задачи одни. Ответ — массивы слов JSON и «Где
   сомневался». Порог — 9/10 с первой попытки.
4. Ошибка **по пропуску** (в описании нет примера) — добавить пример на это
   место. Ошибка **вопреки примеру** — менять язык под интуицию модели, а не
   множить примеры.
5. Описание — строгое правило; неверная строка — громкий отказ с готовой
   исправленной строкой. Терпимость получателя — только там, где замер показал,
   что она не создаёт второго смысла.

Промпты, ответы и итог — `docs/probes/<дата>-<тема>/`; решение в спеке —
со ссылкой на замер.
