# Архитектура: один бинарь Deno/TS — CLI для человека и MCP-сервер для агента

Статус: принятые решения 2026-08-03.

**Заменяет** `broker-architecture.md` (Go-брокер отменён) и отменяет
`go-migration.md` вместе с каталогом `go/`. Разворот относительно обеих
предыдущих редакций: не «CLI + удалённый доверенный брокер», а одна
программа с двумя режимами вызова.

## Замысел

`mpu` — один самодостаточный бинарь (`deno compile`), работающий в двух
режимах над **одним** реестром команд:

- `mpu <cmd> …` — one-shot вызов человеком, в своём процессе, как
  сегодня. Поднятый сервер для этого не нужен;
- `mpu mcp --profile ro|rw` — долгоживущий MCP-сервер для Claude Code:
  транспорт **Streamable HTTP** на `127.0.0.1`, роутер — Hono.

Обе точки входа — тонкие склейки над общим реестром; код команд
слинкован в них одинаково, второго источника истины нет.

**Демон существует только на стороне агента.** Человек в него не ходит:
иначе `mpu` перестал бы работать без поднятого сервера, маршрут `legacy`
стал бы недостижим (legacy — не тул), локальные команды ходили бы по
сети ради файла на диске, относительные пути разрешались бы от `cwd`
сервера, а пайпы и интерактивные подтверждения потребовали бы отдельного
механизма. Выгоды «единого исполнителя» достигаются дешевле: журнал —
слой запуска команды, а не сервера, и обе точки входа пишут в один файл;
политика объявлена в самой команде, а enforcement живёт внутри `run`.

```
                mpu  (один бинарь, deno compile)
                        │
        ┌───────────────┴───────────────┐
   режим CLI                       режим MCP
   mpu <cmd> …                     mpu mcp --profile ro|rw
   (человек, в процессе)           (Claude Code, HTTP 127.0.0.1)
        │                               │
        │   argv → args.parse           │  tools/call → args.parse
        │   run → render → stdout       │  run → structuredContent
        └───────────────┬───────────────┘
                        ▼
                 реестр команд
                 ┌──────┴──────┐
              native         legacy
                 │        spawn python mpu
                 ▼
          домены: sql / kiten / sheet / …
                 ▼
          io: PG · HTTP · ssh · docker · fs
```

## Принятые решения

| # | Развилка | Решение | Почему |
|---|---|---|---|
| 1 | Процессная модель | Один бинарь, два режима. Долгоживущий процесс — только режим MCP; человек исполняет в своём процессе | Человеческий путь не должен зависеть от поднятого сервера, а транспорт для агента и способ вызова для человека — независимые вещи |

| 2 | Непереехавшие команды | Маршрут `legacy` в реестре → подпроцесс Python-`mpu` | Перевод команды и откат — правка одной строки; переезд идёт поштучно без простоя |

ORM отвергнут: зрелые (knex/MikroORM/Prisma/Sequelize) проваливают зависимости или compile, чистые (drizzle/kysely) — вечные 0.x; DDL кэш-БД заморожен (общий с Python до фазы 4), пересмотр — после вывода Python |
| 7 | Доступ к кэш-БД | Две двери: атом store (файл, bootstrap, транзакции, WAL — спека `platform/store.md`) и модуль-владелец на семейство таблиц с узким типизированным интерфейсом; SQL к кэш-БД в коде команд не существует. Универсальная кэш-библиотека / общий API поверх всех таблиц не строится; общие хелперы паттернов (снапшот, scoped-замена, upsert, TTL-чтение — словарь в `ts/docs/glossary.md`) извлекаются по факту 2–3-го владельца | Принято 2026-08-05 по инвентарю всех потребителей py-версии: под «кэшем» шесть семантик (generic KV, снапшоты без TTL, upsert-реестр, TTL-payload с вытеснением, журналы append-only, долговечные данные) — единый API был бы god-object'ом и прятал бы границу «кэш vs данные», на которой уже случались инциденты. Generic `cache`-таблица в схеме была всегда — домены всё равно вырастили реляционные таблицы: по ним ищут по полям, джойнят и агрегируют. В py дисциплина протекла (SQL прямо в командах search/sheet/cli_wrap) — в TS запрет структурный. Эвристика KV vs таблица и кандидаты ревизии схемы — фаза 4 мастер-плана |
| 8 | Служебная запись на диск | Кэш-БД + журнал вызовов; ровно два исключения — env-файл (человекоправимый конфиг) и файл MCP-токена (0600, решение спеки `platform/mcp-server.md`). Новые файловые кэши не заводятся; существующие (`.api-token.json`, `.wb-loader-servers.json`) втягиваются ключами в `cache`-таблицу при переезде своих команд — новые ключи схему не меняют, фазы 4 не ждут. Файл БД — права 0600 (приводит bootstrap) | Принято 2026-08-05. Журнал остаётся файлом не из лени: он оборачивает весь процесс и обязан фиксировать в том числе поломку самой кэш-БД, плюс append из параллельных процессов и tail/grep. Токены в БД (x10-сессии уже там) требуют 0600 на файле БД — оригинал прав не выставляет, файл живёт с umask-правами; фикс не меняет схему и Python не ломает (владелец тот же) |

## Контракт команды

Команда — единица системы. Она объявляет всё, что о ней нужно знать
обоим режимам:

```ts
interface Command<A, R> {
  readonly path: readonly string[]      // ["kiten","field","artefact","set"]
  readonly summary: string              // однострока для индекса родителя
  readonly help: LeafHelp               // подробная справка
  readonly policy: "ro" | "rw"          // объявляется, не выводится
  readonly args: z.ZodType<A>           // → inputSchema (io:"input")
  readonly result: z.ZodType<R>         // → outputSchema (io:"output")
  readonly cli: CliMeta<A>              // позиционные/короткие — по keyof A
  run(a: A, io: Io): Promise<R>         // ничего не печатает
  render(r: R, a: A): string            // чистая; только для режима CLI
}
```

### Инварианты

Каждый — проверка (типов или теста), а не дисциплина:

- **`run` не знает, кто его вызвал.** Единственный канал побочных
  эффектов — `io`. Отсюда фейковый `io` в тестах бесплатно; паттерн уже
  работает в `XlsxIo`.
- **`render` чистая, `R → string`.** Golden-фикстуры проверяют её без
  сети, отдельно от `run`.
- **`policy` в типе.** `rw`-команда не может попасть в ro-профиль —
  ошибка типов, а не забытая строка конфига.
- **CLI-метаданные — отдельным полем, не в схеме.** `.meta({cli:…})`
  протекает в JSON Schema посторонним ключом и уезжает в контекст
  модели (проверено). `CliMeta<A>` типизирован по `keyof A`, поэтому
  «позиционный аргумент, которого нет в схеме» ловит компилятор.

### Следствие: флаги формата исчезают

`R` сериализуем, значит JSON-вывод обслуживает слой CLI одинаково для
всех команд — командам не нужен собственный `--json`. В нынешнем
Python-дереве это 38 параметров формата на 30 листьях в восьми разных
написаниях (`json_out`, `md_out`, `out_json`, …); все они пропадают.

### Следствие: `--print` становится отдельной командой

46 листьев Python-дерева меняют мутирующесть в зависимости от флага
`--print`, ещё 21 — от `--dry`. Флаг, меняющий политику, несовместим с
двухпрофильной раскладкой: тул объявлен один, а ведёт себя как два.

Поэтому read-вариант становится **отдельной командой со своим путём** и
`policy: "ro"`. Это ровно правило §7 `py/CLAUDE.md` («мутирующая команда
обязана иметь enforced read-only вариант»), выраженное в имени.

## Реестр и маршрутизация

Реестр — единственная точка маршрутизации и все справочные поверхности
(`--help` на любом уровне, `mpu help`, `mpu version`, completion, ошибка
неизвестной команды). Контракт CLI-поверхности сохраняется целиком из
`ts/docs/specs/platform/registry.md`, кроме маршрута `брокер`, который
исчезает.

Запись реестра: путь, summary, маршрут (`native` | `legacy`), для
`native` — сама команда.

### Маршрут `legacy`

Исполнение — подпроцесс установленного Python-`mpu` с тем же argv;
stdout/stderr/exit-код прокидываются насквозь, наблюдаемое поведение не
отличается от прямого вызова.

Установка: `~/.local/bin/mpu` сейчас — **симлинк** на
`~/.local/share/uv/tools/mpu/bin/mpu` (реальный console-script uv-тула).
Deno-бинарь встаёт на место симлинка и зовёт Python по абсолютному
пути; путь берётся из конфига, дефолт — тот самый.
`--allow-run` пинится ровно на этот путь.

**Ловушка:** `uv tool upgrade mpu` пересоздаёт симлинк и затирает
Deno-бинарь. Штатная команда обновления, поэтому её нужно либо не
запускать, либо всегда сопровождать пересборкой.

## MCP-поверхность

| | режим CLI | режим MCP |
|---|---|---|
| имя | `mpu kiten field artefact set` | `kiten_field_artefact_set` (`path.join("_")`) |
| вход | argv → `cli` + `args` | `params` → `args.parse` |
| выход | `render(r, a)` → stdout | `structuredContent` + `outputSchema` |
| ошибка | stderr + exit-код | результат с `isError: true` |

Замерено на текущем Python-дереве: коллизий имён **0**, самое длинное
имя — 37 символов (`ozon_loader_campaign_daily_statistics`).

### Тулом становится только `native`

`legacy`-команда есть в `mpu --help` и `mpu help` (паритет CLI-поверхности),
но отсутствует в `tools/list`: типизированной схемы у неё нет и быть не
может. Это тестируемый инвариант и естественный гейт — переезд команды
означает появление тула, промежуточных состояний не бывает.

### Два профиля

```json
{"mcpServers": {
  "mpu_ro": {"type": "http", "url": "http://127.0.0.1:7337/ro",
             "headersHelper": "mpu mcp token"},
  "mpu_rw": {"type": "http", "url": "http://127.0.0.1:7337/rw",
             "headersHelper": "mpu mcp token"}}}
```

```
allow: ["mcp__mpu_ro__*"]     ask: ["mcp__mpu_rw__*"]
```

**Один процесс, два endpoint'а.** Гранулярность прав даёт имя сервера в
`.mcp.json`, а не URL, поэтому две записи могут указывать в один
процесс на разные пути. Профиль выбирается путём (`/ro`, `/rw`);
`--profile` у `mpu mcp` определяет, какие профили процесс вообще
поднимает.

**Профили не пересекаются.** `mpu_ro` регистрирует только `policy: "ro"`,
`mpu_rw` — только `policy: "rw"`. Каждый тул существует ровно в одном
профиле: иначе читающая команда была бы видна и как `mcp__mpu_ro__x`, и
как `mcp__mpu_rw__x`, модель выбирала бы из двух одинаковых имён, а
половина выборов упиралась бы в лишний промпт.

ro-профиль **физически не регистрирует** мутирующие тулы — не «запрещает
правилом», а не объявляет.

Имена серверов пишутся сразу через `_`, а не через дефис: Claude Code
нормализует небуквенно-цифровые символы имени сервера (видно на
`claude.ai Google Drive` → `mcp__claude_ai_Google_Drive__`), и `mpu_ro`
не оставляет вопроса, во что превратится `mpu-ro`.

### Server instructions ≤ 2 КБ

Claude Code режет описания тулов и server instructions на 2 КБ каждое.
Инструкции сервера поэтому не перечисляют команды (их сотни), а
объясняют **когда искать** тулы этого сервера — как описание skill'а.

### Лимит вывода

Вывод MCP-тула: предупреждение с 10 000 токенов, потолок по умолчанию
25 000 (`MAX_MCP_OUTPUT_TOKENS`). Команды, которые по природе отдают
много (`sql-ro`, `logs`, `sheet get`), обязаны иметь в `A` ограничитель
(`limit`/`tail`) с разумным дефолтом; для действительно больших
результатов — `_meta["anthropic/maxResultSizeChars"]` (потолок 500 000
символов).

### Чего не делаем

- **Не мапим дерево в тулы «на будущее»**: тул появляется вместе с
  переехавшей командой.
- **Не делаем generic-тул с `argv`**: одно имя на все мутирующие
  команды — permission-wildcard по природе, точечно ужесточить нельзя.
- **Не используем `anyOf`/`oneOf` в корне `inputSchema`**: Claude API
  их в корне не принимает, Claude Code сплющивает схему, а `required`
  веток переезжает в текст описания и перестаёт проверяться.
- **Не закладываем elicitation** (YAGNI): в ревизии 2026-07-28
  server-initiated requests заменены паттерном MRTR; понадобится —
  добавим тогда.

## Транспорт: Streamable HTTP

### Ядро не знает о транспорте

Диспетчер — чистая функция `handle(req: JsonRpcRequest) => Promise<JsonRpcResponse>`
над реестром. Ввод-вывод живёт в адаптере, как и в контракте команды,
где `run` не печатает. Практическое следствие: HTTP-адаптер на Hono —
единственное место, знающее про заголовки и статусы, а тесты
диспетчера идут таблицей «запрос → ответ» без сокета.

### Что обязана делать реализация

Ревизия 2026-07-28 предъявляет к HTTP-биндингу заметно больше
требований, чем stdio. Обязательное:

- один path, **только POST**; `GET`/`DELETE` → `405 Method Not Allowed`;
- **валидация `Origin`**; присутствует и невалиден → `403` (защита от
  DNS rebinding); слушать только `127.0.0.1`, не `0.0.0.0`;
- на каждом POST обязательны `MCP-Protocol-Version` и `Mcp-Method`, а
  для `tools/call` / `resources/read` / `prompts/get` — ещё `Mcp-Name`;
- сервер **обязан сверять эти заголовки с телом**; расхождение или
  отсутствие → `400` + JSON-RPC `-32020 HeaderMismatch`. Значения в
  сентинеле `=?base64?…?=` перед сравнением декодируются. Оговорка
  2026-08-06: запрос без заголовка версии или со старой ревизией
  обслуживается классическим рукопожатием (`initialize`/`ping`) — живые
  клиенты `2026-07-28` ещё не говорят (спека `platform/mcp-server.md`,
  «Классическое рукопожатие»);
- неизвестный метод → `404` + JSON-RPC `-32601`;
- неподдерживаемая версия протокола → `400` +
  `UnsupportedProtocolVersionError` со списком поддерживаемых;
- нотификация → `202 Accepted` без тела;
- ответ на запрос — либо `Content-Type: application/json`, либо SSE-стрим,
  привязанный к этому запросу;
- `Mcp-Session-Id` и `Last-Event-ID` игнорировать; стримы не resumable;
- при SSE — заголовок `X-Accel-Buffering: no`, для долгих стримов —
  keep-alive комментарии; **отмена = клиент закрыл стрим**, сервер обязан
  прекратить работу и не слать больше ничего по этому запросу.

Опционально и не берём: `x-mcp-header` (зеркалирование параметров тула в
HTTP-заголовки) — для сервера это MAY.

### SSE в MVP не нужен

Спека требует вернуть **либо** JSON, **либо** SSE. Пока нет
`notifications/progress` и `subscriptions/listen`, законно всегда
отвечать `application/json`. Это убирает из MVP стриминг, keep-alive и
явную обработку отмены (остаётся разрыв соединения). SSE добавляется
тогда, когда появится первая долгая команда с прогрессом.

### Жизненный цикл и auth

- Процесс поднимается вручную (`mpu mcp --profile ro,rw --port 7337`) —
  для MVP этого достаточно и видно логи. Юнит `systemd --user` с
  `Restart=on-failure` — отдельный шаг после MVP.
- Аутентификация: статический Bearer-токен, файл 0600 в конфиг-каталоге,
  генерируется сервером. В `.mcp.json` не хранится: там `headersHelper`,
  который печатает заголовок при подключении.
- Версионный перекос — реальный риск этой схемы: пересобрал бинарь,
  забыл перезапустить сервер, агент работает со старым набором тулов.
  `mpu version` обязан отдавать версию сборки, а сервер — сообщать её в
  `server/discover`, чтобы расхождение было видно.

## Права, секреты и модель угроз

Это разворот, а не деталь, и его нужно зафиксировать честно.

Брокер существовал ради тезиса «CLI — недоверенная сторона, данные не
добывает, а запрашивает». Без брокера **недоверенной стороны не
остаётся**: бинарь сам держит секреты, ходит в прод-PG, запускает `ssh`
и `docker`.

| было (xlsx-профиль) | станет |
|---|---|
| `--allow-net` = хост брокера | широкий (адреса серверов приезжают из кэша селектора, аллоулист непрактичен) |
| `--allow-run=xdg-open,open` | `+ ssh, docker, python-mpu` |
| `--allow-write=~/.config/mpu` | `+ каталоги выгрузок` |
| `--allow-env=MPU_XLSX,HOME` | много |

Вывод: **permissions Deno перестают быть барьером безопасности и
становятся гигиеной.** Граница переезжает в два места, и оба реальные:

1. **ro-профиль — настоящий enforcement**, потому что read-only это
   свойство PG-сессии (`default_transaction_read_only=on`), а не флаг в
   коде: пишущий запрос отклоняет сам Postgres.
2. **Permission-правила Claude Code** на `mcp__mpu_rw__*`.

Секреты остаются в файле конфига с правами 0600; в argv, env, вывод и
сообщения об ошибках не попадают.

Разделы «Песочница и permissions» и «Секреты» в `ts/CLAUDE.md`
описывают несуществующую модель угроз и переписываются.

## Ошибки и подтверждения

Одна таксономия на оба режима; отображает её слой режима, а не команда.

| ошибка | CLI | MCP |
|---|---|---|
| `UsageError` (аргументы) | stderr, exit 2 | JSON-RPC error |
| нет такой команды / тула | stderr, exit 2 | JSON-RPC error |
| доменная (SQL упал, карточки нет, ssh недоступен) | stderr, exit 1 | результат с `isError: true` |

Различие в последней строке принципиальное: доменная ошибка приходит
модели **как содержимое результата**, чтобы она её прочитала и
исправилась, а не как транспортный сбой.

Подтверждения мутаций:

- CLI — интерактивный промпт, как сегодня;
- MCP — интерактива нет, промпт делает Claude Code по правилу `ask` на
  `mcp__mpu_rw__*`;
- на необратимое наружу (`telegram send`, `kiten comment`, `mr create`,
  `sql` на проде) дополнительно `_meta["anthropic/requiresUserInteraction"]:
  true` — форсирует промпт на каждый вызов, и его не обходят
  allow-правила.

**Выбрасывается:** `go/` целиком (кода нет — `CLAUDE.md` 33 КБ и docs);

## Известные ловушки

- `z.toJSONSchema(schema)` без опций кладёт поля с `default` в
  `required`. Для `inputSchema` обязателен `{ io: "input" }`, для
  `outputSchema` — `{ io: "output" }`.
- Целые числа порождают в схеме `minimum`/`maximum` на
  ±9007199254740991 — шум в контексте модели. Проверено: `z.int()` ведёт
  себя так же, как `z.number().int()`; убирает шум только явный
  `.min()/.max()`, который у CLI-аргументов (`limit`, `tail`) и так
  уместен.
- `.meta()` протекает в JSON Schema произвольным ключом; CLI-метаданные
  туда не класть.
- `uv tool upgrade mpu` затирает Deno-бинарь (см. маршрут `legacy`).
- Deno отказывается ставить зависимость моложе 24 часов (minimum
  dependency age — защита от supply chain). Проверено вживую: свежая
  `@hono/hono@4.12.34` была заблокирована. Версии пинить точно
  (`4.12.33`), а не через `^`, иначе сборка ломается в день релиза
  апстрима.
- Версионный перекос бинаря и запущенного сервера: пересобрал — перезапусти.

## Проверенные факты

Собраны 2026-08-03 из первоисточников; здесь, чтобы не переспорить их
заново.

### Протокол MCP

- Текущая ревизия — **2026-07-28**. Протокол стал stateless: handshake
  `initialize`/`notifications/initialized` и `Mcp-Session-Id` удалены,
  версия и capabilities едут в `_meta` каждого запроса, добавлен
  `server/discover` (`/specification/2026-07-28/changelog`).
- Server-initiated requests (`elicitation/create`, `sampling/createMessage`,
  `roots/list`) заменены паттерном **MRTR**; прежний способ объявлен
  breaking change (`/specification/2026-07-28/basic/patterns/mrtr`).
- `tools/list` — **плоский** массив; иерархии тулов протокол не задаёт.
  Поддерживает курсорную пагинацию.
- `annotations`: `readOnlyHint` (default false), `destructiveHint`
  (default true, осмысленно только при `readOnlyHint == false`),
  `idempotentHint`, `openWorldHint`. Клиент обязан считать аннотации
  недоверенными.
- `outputSchema` у тула и `structuredContent` у результата — с ревизии
  2025-06-18.
- `completion/complete` работает **только** для `ref/prompt` и
  `ref/resource`. Автодополнения аргументов тулов в протоколе нет.
- Ограничений на число тулов и размер `inputSchema` в спеке нет.

### Транспорты MCP

- Стандартных транспортов два: **stdio** («newline-delimited messages
  over the standard streams of a client-launched subprocess») и
  **Streamable HTTP** («each message is an HTTP POST to a single MCP
  endpoint; replies arrive as a JSON object or a request-scoped SSE
  stream»).
- Ревизия 2026-07-28 изменила Streamable HTTP: убраны GET-стрим и
  протокольные сессии (`Mcp-Session-Id`), стримы больше не resumable
  (`Last-Event-ID` игнорируется), сервер не шлёт собственные JSON-RPC
  запросы.
- Требования к локальному серверу: валидировать `Origin` (иначе `403`),
  слушать `127.0.0.1`, а не `0.0.0.0`, реализовать аутентификацию.
- Обязательные заголовки и сверка их с телом (`-32020 HeaderMismatch`),
  `405` на GET/DELETE, `404`+`-32601` на неизвестный метод,
  `202 Accepted` на нотификацию — см. раздел «Транспорт».
- Кастомные транспорты поверх байтового потока (unix-сокет, TCP)
  **SHOULD** переиспользовать stdio-фрейминг, а не изобретать свой.

### Hono и Deno

Проверено на Deno 2.9.4: `jsr:@hono/hono@4.12.33` работает —
роутинг по путям, чтение заголовков запроса, `405` на не-POST, SSE через
`@hono/hono/streaming`. `4.12.34` в тот же день была заблокирована
политикой minimum dependency age.

### Claude Code

- Правила permissions: `mcp__<server>__<tool>`. Дословно: «Allow rules
  accept tool-name globs only after a literal `mcp__<server>__` prefix.
  The server segment must be glob-free». Неякорный allow-глоб
  пропускается с предупреждением.
- **Tool search включён по умолчанию**: «Only tool names and server
  instructions load at session start… Claude Code doesn't impose a fixed
  per-server tool cap; the practical limit is your context window
  budget». Управление — `ENABLE_TOOL_SEARCH`; `alwaysLoad: true` в
  `.mcp.json` исключает сервер из отложенной загрузки.
- Описания тулов и server instructions режутся на **2 КБ** каждое.
- Стандартные MCP-аннотации (`readOnlyHint` и прочие) в документации
  Claude Code **не описаны** как источник авто-разрешения. Работают
  permission-правила по имени тула и собственные
  `_meta["anthropic/requiresUserInteraction"]` (форсирует промпт, не
  обходится allow-правилами) и `_meta["anthropic/maxResultSizeChars"]`
  (потолок 500 000 символов).
- Вывод тула: предупреждение с 10 000 токенов, потолок по умолчанию
  25 000 (`MAX_MCP_OUTPUT_TOKENS`).
- Корневые `anyOf`/`oneOf` в `inputSchema` Claude API не принимает; с
  v2.1.195 Claude Code сплющивает схему и переносит `required` веток в
  текст описания — «instead of enforced by the schema».
- Точность выбора тула деградирует после **30–50** загруженных тулов
  (`platform.claude.com/…/tool-search-tool`); при tool search точность
  держится «across thousands of tools», потому что загружаются не все.
