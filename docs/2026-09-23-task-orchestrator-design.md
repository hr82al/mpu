# `mpu task`: оркестратор сессий — роли, тик, решения

Дизайн 2026-09-23, решения владельца. Исполнителю не виден: рабочие части
переносятся в `ts/docs/specs/` порция за порцией. Хуки Claude Code — отдельный
дизайн и порция позже (надстройка для скорости, тик остаётся страховкой).

## Цель

Работа по плану идёт порция за порцией без человека, на чистом контексте
каждой роли, и переживает падения сессий, перезагрузку и закрытие окон. Для
любого проекта, а не только `mpu`; параллельные проекты друг другу не мешают.
Человек участвует только там, где правила проекта не решают: вопросом в
канале и уведомлением.

Опирается на `ts/docs/specs/task.md` — канал сообщений (`task`, `report`,
`question`, `answer`) в кэш-БД; он ещё не реализован, его заменяет
`deno task handoff` — первая порция серии реализует канал.

## 1. Роли и профили

Три роли проекта: **диалог** (человек и сессия-собеседник — оркестратор её не
трогает), **хост порции** (спецификатор на одну порцию), **исполнитель**.

Профиль роли в кэш-БД, по ключу проекта:

| Поле | Пример (`mpu`) |
|---|---|
| сессия tmux | `w` по умолчанию; проект, начатый в другой сессии (`a`), записывает её, и роли запускаются там |
| окно | `<проект>-<роль>`: `mpu-host`, `mpu-exec` |
| каталог | `~/mr/mp/mpu` (хост), `~/mr/mp/mpu/ts` (исполнитель) |
| модель | `opus` |
| режим разрешений | `auto` |
| `--add-dir` | каталоги вне каталога запуска |
| полномочия | текст: «субагенты — можно, модель явно; push своей ветки — можно; MR — спросить; мерж — никогда; прод — только чтение» |
| начальные файлы | пути, которые роль читает первыми (правила проекта, план) |

Профили меняет только человек (`mpu task role <проект> <роль> …` из
терминала, правка в web) — жёсткий запрет, как у правил подтверждения; агент
читает, но не пишет. Полномочия оркестратор вкладывает в каждое первое
сообщение роли дословно.

## 2. Тик и отметки ролей

Ребёнок `mpu-supervisor` — `mpu-task` (рядом с `back` и `mcp`, та же служба,
тот же перезапуск с паузами). Каждые 5 с по каждому проекту с профилями — один
шаг:

1. **Окна**: нет окна роли или в нём не Claude — запуск по профилю (раздел 3).
2. **Модель**: экран показывает модель не из профиля — `/model <модель>` в
   простое; не помогло — перезапуск окна с `--model`.
3. **Ход** по журналу канала:
   - `report` не прочитан, хост `idle` → очистить хоста, первое сообщение
     «прими порцию N по отчёту; спека и постановка N+1 по плану; положи»;
   - `task` положен, исполнитель `idle` → очистить исполнителя, первое
     сообщение — постановка;
   - `question` — хост в работе видит сам; хост `idle` — вопрос в его первом
     сообщении.
4. **Стоп**: `stop` в канале (конец плана, блокер) — проект замирает до
   `resume`, уведомление человеку.

**Отметки** вместо чтения экрана: роль пишет `mpu task busy|idle <проект>
<роль>`; тик верит отметке, экран проверяет только «окно живо, в нём Claude,
модель». `busy` без движения журнала дольше часа — уведомление, очистки нет.
Очистка — только при `idle`.

## 3. Запуск, очистка, восстановление

**Запуск**: окно в сессии профиля (нет сессии — создать) и каталоге профиля;
`claude --permission-mode <режим> --model <модель> --name <окно> [--add-dir …]`
с первым сообщением **первым аргументом** (`--add-dir` вариадический — съедал
постановку, ловилось живьём). Проверка за 60 с: `❯ Прочитай файл …`, модель в
баннере, `auto mode on`. Не сошлось — закрыть и повторить; три неудачи — стоп
роли, уведомление. Диалог доверия каталогу — уведомление «подтвердите
доверие», повторов нет.

**Первое сообщение** — файл (`$XDG_RUNTIME_DIR/mpu-task/<проект>/<роль>.md`):
роль и полномочия дословно; канал (проект, `busy`/`idle`, как спросить);
что делать сейчас; начальные файлы путями; правила проекта (`rule`),
решения последних порций (`decision`), открытые ответы владельца
(`owner-answer`).

**Очистка** при `idle`: `/clear` → проверка модели → «прочитай файл <первое
сообщение>» (Enter отдельно) → отметка `busy` в пределах 60 с, иначе повтор;
три — уведомление.

**Упавшая роль** (окно умерло при `busy`): новое окно, то же первое сообщение
и строка «продолжай с первого незакрытого раздела, сверяясь с `git log` и
`git status`».

**Права Deno** `mpu-task`: запуск `tmux` и `claude`; кэш-БД; запись в
`$XDG_RUNTIME_DIR/mpu-task/` — каждое строкой с обоснованием и проверкой.

## 4. Решения и вопросы — в канале

Два новых вида сообщений того же журнала, по порциям, без отдельных таблиц и
файлов:

| Вид | Пишет | Что |
|---|---|---|
| `decision` | хост, диалог | вопрос, решение, правило, по которому решено |
| `rule` | человек (через диалог) | правило выбора проекта; одна действующая редакция, старые — в истории |
| `owner` | хост | вопрос владельцу, не решённый правилами; открыт до ответа |
| `owner-answer` | человек | ответ; уходит в первое сообщение следующего хоста |

Чтение одним документом: `mpu task decisions <проект>` — правила, затем
решения последних N порций свёрнуто по порциям; `… query: <слово>` — поиск
прецедента. Хост получает в первом сообщении правила и последние порции, не
весь журнал. `rule` пишет только человек (хост предлагает строкой `owner`).

Хост порции: принять отчёт по правилам проекта; спека и постановка N+1 по
плану; положить `task`; отвечать исполнителю (решение — сперва в спеку и
`decision`, затем ответ); не решённое правилами — `owner` и порция пропущена
или на названном допущении.

## 5. Параллельные проекты

- Всё по ключу проекта: журнал, профили, отметки, файлы первого сообщения,
  окна `<проект>-<роль>` в сессии проекта.
- Шаг проекта — транзакция SQLite с блокировкой проекта; долгие действия
  (ожидание простоя) — отдельные задачи со сроком, тик их не ждёт.
- Роль видит только свой проект; `mpu task` без имени проекта в роли —
  отказ.
- Каталоги ролей разных проектов совпадать не могут — отказ запуска.
- Предел одновременно работающих ролей (умолчание 4) — остальные ждут.

## 6. Проверка

Порты — окна (tmux) и часы — параметры; в тестах поддельный tmux в памяти и
поддельная роль-программа (баннер с моделью, отметки через настоящий
`mpu task`, падение, зависание, не та модель). Сценарии: запуск в сессии
проекта; падение посреди работы; не та модель; диалог доверия; три неудачи;
очистка только при `idle` и порядок; `busy` без движения; два проекта не
пересекаются; предел ролей; `stop`/`resume`; полномочия дословно и
`owner-answer` в первом сообщении — каждый с мутацией.

Приёмка хостом: настоящий tmux и роль-скрипт — два цикла на игрушечном
проекте, падение окна, перезапуск службы; затем один настоящий цикл с
`sonnet` (баннер, `/model`, `/clear` живьём).

## 7. Порядок работ

| Порция | Что |
|---|---|
| T1 | канал `mpu task` по `task.md` (вместо `deno task handoff`), виды `decision`, `rule`, `owner`, `owner-answer`, `decisions` |
| T2 | профили ролей и отметки `busy`/`idle`; жёсткий запрет на правку профилей |
| T3 | `mpu-task`: тик, запуск, очистка, модель, восстановление, параллельность; ребёнок супервизора |
| T4 | перевод `mpu` на оркестратор: профили `mpu`, первые `rule`/`decision` из прецедентов серии 157–165 |
| T5 | хуки Claude Code (отдельный дизайн) |

Серия начинается после серии 158–165 и перед языком 166a — или по решению
владельца.
