# tslibs: протокол получателя — самоописание, конверт, интерфейс, соответствие

Статус: дизайн, согласован владельцем по частям 2026-10-06 (брейншторм).
Реализует параллельная ветка перехода (`docs/plans/2026-10-06-bun-tslibs-objects-plan.md`,
этапы 4 и 6), не серия R.

## Цель

Каждый домен `mpu/tslibs/<домен>` — граф объектов-получателей, которые сами
рассказывают о себе. Хост-сессия узнаёт интерфейс домена исчерпывающе и не
читая его код. Код — максимально объектный: всё — получатель и сообщение,
решает получатель, отсутствие — `doesNotUnderstand`, без проверок типа.

Решения владельца, на которых держится дизайн:

- интерфейс доступен двумя путями — живым запросом через mpu и
  сгенерированным файлом в корне домена, из одного источника;
- описание метода — данные рядом с методом (статическое поле), не декораторы
  и не JSDoc-генерация;
- граф объектов (как в Smalltalk), а не плоский список команд;
- тесты — Vitest на поверхности `describe`/`it`/`expect`; ничего
  специфичного для Bun или Deno.

## 1. Получатель

Получатель — класс домена. Описание — статическое поле `about`, проверяемое
типом:

```ts
class KaitenCard {
  static readonly about = {
    comment: "Карточка Kaiten: читать, комментировать, двигать по доске.",
    protocols: {
      reading: {
        show: { args: [], returns: "data", comment: "Карточка целиком.",
                examples: [{ call: [], answer: { id: 123, title: "…" } }] },
      },
      writing: {
        comment: { args: [{ name: "text", type: "string", required: true }],
                   returns: "data", effect: "write", raises: ["card-not-found"],
                   comment: "Комментарий от владельца.", examples: [...] },
      },
      navigation: {
        checklist: { args: [], returns: KaitenChecklist, comment: "Чек-лист карточки." },
      },
    },
  } satisfies About<KaitenCard>;
  // методы show(), comment(text), checklist()
}
```

Описание метода:

| Поле | Что | Обязательно |
|---|---|---|
| `comment` | что делает и когда звать — первым предложением | да |
| `args` | имя, тип, `required`, `default`; порядок = порядок параметров | да (пустой список — без аргументов) |
| `returns` | `"data"` или класс-получатель (следующий шаг графа) | да |
| `effect` | `read` (умолчание), `write`, `send` — наружу | нет |
| `raises` | виды отказов, которые метод отдаёт | нет |
| `examples` | вызов и ожидаемый ответ — исполняются тестом соответствия | да, хотя бы один у метода с `effect` |
| `deprecated` | `{ use: "<селектор>", since: "<версия>" }` | нет |

Протокол (`reading`, `writing`, `navigation`, …) — группировка методов, как
категории в Smalltalk; имена протоколов свободны.

`About<T>` — тип: ключи описаний в протоколах — ровно публичные методы `T`;
лишний или пропущенный — ошибка `tsc`. `numArgs` выводится из `args`, руками
не пишется (один источник).

Описание статично: читается без экземпляра, без сети и файлов.

Не описывается и наружу не отдаётся: поля, код, связи между методами,
состояние (`inspect` нет). Проверок типа у вызывающих нет (`isKindOf` нет):
вид результата — в описании метода.

## 2. Сообщения, которые понимает любой получатель

Отвечает конверт (раздел 3) по `about`; в классе их не пишут.

| Сообщение | Ответ |
|---|---|
| `describe()` | `about` целиком + путь получателя в графе |
| `selectors()` | имена методов по протоколам |
| `respondsTo(selector)` | понимает ли |
| `help(selector?)` | текст для человека и агента: однострока — когда звать — аргументы — пример (порядок `platform/registry.md`, «Что говорит справка») |
| `printString()` | как объект показывает себя (`KaitenCard 123`), без внутренностей |

## 3. Конверт (Proxy)

`envelope(receiver, { path, book, journal, asker, signal })` — Proxy вокруг
получателя; живёт в хосте, домен о нём не знает.

Ловушка `get` по селектору:

1. **описанный метод** → функция, которая:
   1. сверяет аргументы с `args` — нет обязательного, не тот тип → объект
      отказа (`ключ text обязателен`), метод не вызывается;
   2. спрашивает книгу правил по пути (`kaiten card comment`): `allow` →
      дальше; `ask` → вопрос человеку тем каналом, что у вызова (терминал,
      форма MCP, Telegram); `deny` → объект отказа;
   3. вызывает метод;
   4. пишет запись журнала: путь, аргументы с маской секретов, исход, время;
   5. результат, описанный как получатель, — заворачивает тем же конвертом с
      продолженным путём; данные — как есть;
2. **сообщение отражения** (раздел 2) → ответ по `about`;
3. **всё прочее**, включая публичный, но неописанный метод, →
   `doesNotUnderstand`: объект отказа с ближайшими селекторами
   (`понимаю: show, comment, checklist; ближе всего — comment`), не
   исключение. Единственная точка «нет такого».

Свойства:

- правило проверяется на каждом вызове цепочки; навигация (`returns`
  получатель, `effect` не задан) по умолчанию `allow`;
- посев правил — из `effect`: `read` → `allow`, `write`/`send` → `ask`;
  отдельной таблицы посева нет;
- зависимости (часы, окружение, HTTP, файлы) получатель получает в
  конструкторе; отмена — `signal` контекста;
- объект отказа — один протокол (`refusal-object.md`), печатает себя сам.

## 4. Файл интерфейса

`tslibs/<домен>/INTERFACE.md` и `tslibs/<домен>/interface.json`:

- генерируются одной командой из `about` обходом графа от корня
  (`returns: Класс`); руками не правятся;
- `INTERFACE.md`: однострока домена, как получить корень, по разделу на
  получателя — комментарий, протоколы, методы (арность, аргументы, результат,
  эффект, отказы, примеры, `deprecated → замена`);
- `interface.json` — те же данные для машины; из него хост строит справку,
  дополнение и схему MCP, не загружая код домена;
- живой запрос (`mpu kaiten describe`, `mpu kaiten card help`) отвечает тем
  же содержимым — источник один.

Хосту открыты только эти два файла домена (изоляция — этап 5 плана).

## 5. Тесты соответствия — `tslibs/conformance`

Один набор на все домены (Vitest), подключается доменом одной строкой со
своим корнем и фейками:

1. **Полнота:** у каждого достижимого получателя есть `comment`; публичные
   методы ⇔ описания (ловит и методы, добавленные мимо типа).
2. **Арность:** длина `args` = `Function.length` метода (с учётом `default`).
3. **Примеры:** каждый исполняется на фейках домена, ответ равен заявленному.
4. **Граф:** каждый `returns: Класс` — описанный получатель; недостижимых нет.
5. **Эффект:** метод с `read` за время своих примеров не пишет (фейки
   фиксируют вызовы).
6. **Снимок:** `interface.json` равен сгенерированному из кода; удалённый
   метод или новый обязательный аргумент без `deprecated` с заменой —
   красный.
7. **`doesNotUnderstand`:** неописанный селектор у каждого получателя —
   объект отказа с подсказкой, не исключение.

## Инварианты

- Снаружи достижимо только описанное.
- У одного факта один источник: арность, аргументы, эффект, примеры — в
  `about`; справка, файл интерфейса, схема MCP, посев правил — из него.
- Пример в описании всегда исполним и верен (тест 3).
- Домен не зависит от хоста: конверт, книга правил и журнал — в хосте.

## Открытые вопросы

- Валидация типов аргументов — своя по `type` или популярная библиотека
  схем (Zod уже в зависимостях `ts/`); решение владельца.
- Ближайшие селекторы — `@std/text/levenshtein-distance` сегодня; под правило
  «ничего специфичного» — npm-пакет (кандидат `fastest-levenshtein`).
- Имя команды генерации файла интерфейса и место в гейтах (до коммита
  домена).
- Как CLI и MCP отображают цепочку графа (D1 плана): `mpu kaiten card id:
  123 comment text: ок` — ключи на звене цепочки.

## Пункты чек-листа

`design.md`: 1 примитивы — `about` + конверт (отправка, отражение,
`doesNotUnderstand`); всё прочее (справка, файл, MCP, посев) выведено из
`about` в одном месте. 2 особые случаи — описанный метод / отражение / прочее
— три ответа конверта; вид результата — данные описания, не ветка у
вызывающего. 3 `null` и типы — отсутствие метода — объект отказа; проверок
типа нет. 4 кто решает — получатель (метод), конверт (политика, журнал,
отказ), книга правил (решение). 5 память приватна — состояние не
описывается и не отдаётся. 6 голые данные — путь, эффект, вид результата —
протокол описания, проверяемый типом. 7 основание проверкой — полнота,
арность, примеры, снимок — тесты соответствия.
