# Журнал переезда

Учёт решений переезда Python → Deno/TS: что умирает вместе с Python,
принятые расхождения differential-сверки, идеи улучшений из отчётов
изолированных сессий. План команд — `plans/command-migration.md`.

## Умрёт вместе с Python (решение 2026-07-27)

- **ozon-fix-fo-tax** — data-fix одного инцидента (источник 1 ₽ в
  ОПиУ/Фин отчёте SKU); сценарий исчерпан.
- **backup-wb-unit-proto**, **backup-ozon-unit-proto**,
  **backup-wb-unit-manual-data** — CTAS-бэкапы под конкретные
  ремедиации; при нужде бэкап делается штатным SQL (`CREATE TABLE … AS
  SELECT`), отдельные команды не оправданы.
- **wb-unit-proto-new** — разовая миграция старой
  `wb_unit_proto`-таблицы; выполнена.
- **sun** — восход/закат/зенит; вне домена mpu.
- **process, ss-load, ss-datasets, wb-unit-calc, wb-jobs, iu-wb,
  ozon-loader, ozon-jobs, data-loader-jobs, users, clients-migrations,
  datasets-migrations, app-migrations** — Portainer-обёртки над
  `node cli service:*` без вызовов за доступное окно журнала; при
  реальной нужде тот же вызов доступен как `node cli …` через `ssh`,
  отдельная команда на каждую не оправдана.
- **confirm** — вспомогательный pipe-фильтр подтверждения; без вызовов,
  шаблон использования не прижился.

## Заметки к будущим решениям

- PG-драйвер (решено 2026-08-05, живая проверка трёх кандидатов на
  PostgreSQL 16): взят `npm:pg` (node-postgres). Родной для Deno
  `jsr:@db/postgres` отвергнут не по вкусу, а по дефекту: на
  многооператорном тексте он не падает и не отдаёт наборы раздельно, а
  склеивает строки под именами колонок ПЕРВОГО оператора —
  «SELECT 1 AS a; SELECT 2 AS b» даёт `[{a:1},{a:2}]` при `rowCount:1`,
  то есть правдоподобную, но неверную таблицу. `npm:postgres`
  требованиям удовлетворяет (наборы раздельно, старт на ~40 мс быстрее),
  но многооператорный путь у него — отдельный метод `unsafe`, тогда как
  у `pg` это обычный `query()`. Общее для обоих npm-кандидатов: право на
  переменные окружения сужается до `--allow-env=PG*` (проверено), полный
  список PG-переменных стабильным контрактом не является.
- sql-ro (2026-08-05): при заморозке первой порции снят и закреплён
  контракт `;`-склейки — печатается result set **первого** оператора,
  причём печать начинается только после успешного выполнения всего
  текста (ошибка второго оператора гасит вывод первого). Маршрут sw
  оригинала печатает последний — расхождение помечено `fix` в
  `specs/sql-sw.md` и станет расхождением сверки, когда тот маршрут
  поедет. Там же — второй `fix`: префикс sw-ошибок в оригинале всегда
  `mpu sql sw:`, независимо от вызванной команды.
- telegram (обсуждено 2026-08-05, решение — при очереди команды): если
  Python выводится из эксплуатации целиком, замена Telethon —
  **`gramjs`** (npm-пакет `telegram`), прямой порт Telethon на TS с
  почти тем же API (`TelegramClient`, `StringSession`,
  `Api.contacts.Search`, `FloodWaitError`), поэтому 1204 строки нашего
  кода маппятся почти механически. Идея «взять нативные библиотеки
  Telethon» отпадает фактически: у Telethon их нет — зависимости
  `pyaes` и `rsa` чистый Python, MTProto реализован в самом пакете,
  нативный `cryptg` опционален и у нас не установлен. FFI к
  `libtdjson.so` (TDLib) снят с рассмотрения: `deno compile` не вшивает
  `.so` — бинарь перестаёт быть самодостаточным, `--allow-ffi` обходит
  всю модель прав, а переписывать пришлось бы с нуля (у TDLib своя
  модель авторизации и своя база на диске). Главный риск живучести — не
  библиотека, а TL-layer Telegram (меняется несколько раз в год),
  поэтому обязательна изоляция: команда ходит в Telegram только через
  атом `platform/telegram-mtproto`, смена библиотеки тогда стоит
  переписывания атома, а не команды. Отдельная разовая цена порта:
  StringSession Telethon и gramjs — разные форматы, потребуется
  повторная авторизация с телефоном и 2FA (человеком, не постановкой).
  Альтернатива решения — оставить команду на маршруте `legacy`
  навсегда; тогда она вычёркивается из плана переезда.
- env-file (2026-08-04): в собранном бинаре `--allow-env` перечисляет
  имена списком — чтение значений ключей слоя (`sl_<N>`, `pg_<N>`,
  `PG_*`, `DEV_*`, `MPU_LOG_*`) упрётся в право; запись при нестандартном
  `XDG_CONFIG_HOME` выйдет за `--allow-write=$HOME/.config/mpu`. Решение
  о форме прав — вместе с первой командой-потребителем слоя (sql-ro);
  напоминание — комментарием в `ts/deno.jsonc`.

## Платформенные факты (атомам не переоткрывать)

- **Клиент PostgreSQL (`npm:postgres` 3.4.x) безусловно читает
  `PGAPPNAME`** — до слияния своих умолчаний с переданными опциями, и
  без права на эту переменную не создаётся вовсе (`NotCapable`).
  Отсюда единственное имя вне служебного списка `--allow-env`; наш
  явный `application_name` перекрывает прочитанное, поэтому экспорт
  переменной в shell на поведение не влияет (проверено сверкой с
  исходником драйвера и smoke-сценарием, 2026-08-05). Прочие его
  переменные (`PGMAX`, `PGCONNECT_TIMEOUT`, …) подавлены передачей
  всех опций явно.
- **Пределы PG-обращений update (5000 ms соединение / 20000 ms
  запрос) выбраны без замера** — по аналогии с HTTP-пределами init и с
  запасом на тяжёлые выборки `public.clients`/`public.spreadsheets`.
  Уточнить замером на стенде при переезде `sql-ro`, где те же пределы
  окажутся на горячем пути (1225 вызовов/нед.).
- **Отключение проверки TLS-сертификата в Deno недостижимо через
  `fetch`**: у `Deno.createHttpClient` нет опции, гасящей проверку;
  `NODE_TLS_REJECT_UNAUTHORIZED` на `fetch` не влияет (проверено
  порцией А init, 2026-08-05). Рабочий путь — `node:https` с
  `rejectUnauthorized: false`, только для схемы `https:` и только при
  явно отключённой проверке (`PORTAINER_VERIFY_TLS`). Следующим
  HTTP-атомам (Loki, Kaiten) этот вопрос не переоткрывать.
