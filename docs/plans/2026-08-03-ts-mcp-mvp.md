# MVP: MCP-сервер и контракт команды на Deno/TS — план реализации

> **Для исполнителей:** план ведётся сессией-спецификатора **вне канала спек**
> (`ts/docs/CLAUDE.md`, строка 42). Задачи двух видов, они не смешиваются:
> **[С]** — сессия-спецификатор, пишет только в `ts/docs/`;
> **[D]** — изолированная Deno-сессия, пишет только код внутри `ts/`;
> **[O]** — оператор вне репозитория (конфиг Claude Code, запуск).
> Шаги отмечаются чекбоксами (`- [ ]`).

**Goal:** доказать конструкцию «один бинарь = CLI для человека + MCP-сервер для агента» насквозь на одной уже написанной вертикали (`xlsx`), ничего не добавляя к функционалу.

**Architecture:** команда объявляет схему аргументов, схему результата, политику `ro|rw` и рендер; `run` возвращает данные и ничего не печатает. Режим CLI рендерит их в текст, режим MCP отдаёт как `structuredContent`. Транспорт MCP — Streamable HTTP на `127.0.0.1`, роутер Hono, два непересекающихся профиля `/ro` и `/rw`. Непереехавшие команды исполняются подпроцессом Python-`mpu` по маршруту `legacy` и тоже становятся тулами: схемы для них берутся из машинного слепка дерева (`mpu manifest`), а состав публикации задан закрытым списком с политиками.

**Tech Stack:** Deno 2.x, TypeScript strict, `jsr:@zod/zod`, `jsr:@hono/hono`, `@std/assert`.

**Источник истины по архитектуре:** `mpu/docs/ts-mcp-architecture.md`. Этот план не повторяет её обоснований и не спорит с ней; расхождение = дефект плана.

## Global Constraints

Действуют в каждой задаче, повторно в задачах не перечисляются.

- **Протокол MCP — ревизия `2026-07-28`.** Stateless: нет `initialize`, нет `Mcp-Session-Id`, сервер не инициирует JSON-RPC-запросы.
- **Зависимости только с JSR, версии пинятся точно, не через `^`.** Deno блокирует пакеты моложе 24 часов (minimum dependency age): `jsr:@zod/zod@4.4.3`, `jsr:@hono/hono@4.12.33`. Каждая запись в `deno.jsonc` сопровождается комментарием «зачем». `npm:`-зависимостей нет.
- **Сервер слушает `127.0.0.1`, порт `7337`.** Не `0.0.0.0`.
- **Имена серверов в `.mcp.json` — `mpu_ro` и `mpu_rw`** (через `_`, не через дефис). Endpoint'ы — `/ro` и `/rw` одного процесса.
- **Имя тула = путь команды через `_`**, сегменты kebab тоже через `_`: `mpu kiten field artefact set` → `kiten_field_artefact_set`. Префикс `mpu_` не добавляется — имя сервера уже его несёт.
- **`z.toJSONSchema` вызывается с `{ io: "input" }` для схемы аргументов и `{ io: "output" }` для схемы результата.** Без этого поля с `default` попадают в `required`.
- **Гейты перед объявлением задачи готовой:** `deno fmt --check && deno lint && deno check . && deno test`. Пока не зелёные — работа не выполнена и об этом не сообщается.
- **Git:** только ветка `main`, веток не создавать. Коммит с pathspec: `git commit -m "…" -- ts/` (у задач [С] — `-- ts/docs`). `git add -A`, `git commit -a`, `git stash` запрещены (блокируются хуком).
- **Изолированная сессия запускается из КОРНЯ репозитория:** `claude`, не из `ts/`. Профиль изоляции — `mpu/.claude/settings.json`. Корень проекта обязан совпадать с корнем git-репозитория: иначе `.git` не попадает под дефолт «запись в рабочий каталог», а `allowWrite` на него не действует — песочница эмитит `denyWrite` последним и не знает правила «выигрывает более конкретный путь» для записи. Это подтверждённый баг (issues #26262, #25603); `excludedCommands` его не обходит.
- **Сообщения коммитов:** Conventional Commits со скоупом, тема на русском в императиве (`feat(mcp): добавить …`).
- **Ошибки:** exit 2 — ошибки ввода, exit 1 — инфраструктура; stderr без трейсбеков.
- **Язык:** комментарии и документация — русские, идентификаторы — английские.

## Ограничение формата

Skill `writing-plans` требует показывать в шагах готовый код. Здесь это **сознательно не соблюдается для задач [D]**: `ts/docs/CLAUDE.md` устанавливает, что типы и модули проектирует изолированная Deno-сессия, а спека фиксирует контракт возможности, а не API. Поэтому задачи [D] задают **вход, наблюдаемый результат, инварианты и команды проверки**, но не сигнатуры. Задачи [С] показывают содержание спеки полностью — там плейсхолдеров нет.

Контракт возможности «команда», из которого обе точки входа получают всё нужное. Формулировки — наблюдаемые и проверяемые; типов и модулей в спеке нет.

- [ ] **Шаг 1: написать спеку по скелету канала**

Разделы в порядке скелета (`Назначение / CLI-контракт / Ввод-вывод / Побочные эффекты / Конфигурация / Инварианты / Граничные случаи и ошибки / Golden-примеры / Известные отклонения / Открытые вопросы`). Обязательно зафиксировать:

*Контракт.* Каждая команда маршрута `native` объявляет: путь (сегменты после `mpu`); однострочное назначение; подробную справку; политику `ro|rw`; схему аргументов; схему результата; правило рендера результата в текст.

*Инварианты (каждый — проверяемый тестом).*
1. Исполнение команды ничего не печатает: весь вывод порождается рендером из результата. Проверка: прогон команды с подставленным приёмником вывода не даёт записей до вызова рендера.
2. Рендер — функция результата и аргументов, без обращений к сети, диску и часам. Проверка: рендер вызывается на литеральном результате без окружения.
3. Политика объявлена, а не выводится из значений аргументов. Проверка: у каждой команды реестра политика присутствует; команды, у которой мутирующесть зависела от флага, в реестре нет — вместо неё две команды с разными путями.
4. Множество имён параметров в схеме аргументов совпадает с множеством имён, принимаемых из argv. Проверка: обход реестра, сравнение множеств.
5. Обязательность параметра одинакова в обеих точках входа: параметр со значением по умолчанию не обязателен ни в argv, ни в схеме.
6. Результат сериализуем без потерь: рендер в JSON доступен для любой команды и не является её собственным флагом.

*Ошибки.* Ошибка ввода и доменная ошибка различимы по типу, а не по тексту. Отображение в exit-коды — `registry.md`; отображение в MCP — `mcp-server.md`.

*Известные отклонения.* **fix** — флаги формата вывода (`--json`, `--tsv`, `--raw`, `--md`) перестают быть параметрами команд: форма вывода — свойство точки входа. **fix** — флаг, меняющий политику команды (`--print`), упраздняется: read-вариант становится отдельной командой со своим путём.

## Task 4 [С]: Спека `platform/mcp-server.md`

**Files:**
- Create: `ts/docs/specs/platform/mcp-server.md`
- Create: `ts/docs/specs/fixtures/mcp-server/*.json` (golden-пары запрос/ответ)

- [ ] **Шаг 1: написать спеку**

*Контракт.* `mpu mcp [--profile ro|rw|ro,rw] [--port N]` — долгоживущий процесс, Streamable HTTP. Слушает `127.0.0.1`, порт из `--port`, иначе из ключа конфига `mcp.port`, иначе `7337`. Профиль `ro` обслуживается на пути `/ro`, `rw` — на `/rw`.

*Обязательное поведение транспорта (ревизия 2026-07-28).*
- Только `POST`. `GET`, `DELETE` и прочее → `405`.
- Заголовок `Origin` присутствует и не входит в разрешённый список → `403`.
- Отсутствует `Authorization: Bearer <токен доступа>` или токен неверен → `401`.
- На каждом POST обязательны `MCP-Protocol-Version` и `Mcp-Method`; для `tools/call` — ещё `Mcp-Name`. Отсутствие любого из них или расхождение с телом → `400` + JSON-RPC `-32020`. Значения в сентинеле `=?base64?…?=` декодируются перед сравнением.
- Версия протокола вне поддерживаемых → `400` + `UnsupportedProtocolVersionError` со списком поддерживаемых.
- Неизвестный метод → `404` + JSON-RPC `-32601`.
- Тело — JSON-RPC нотификация → `202` без тела.
- Ответ на запрос — всегда `Content-Type: application/json`. SSE в этой редакции не реализуется (спека требует «либо JSON, либо SSE»).
- `Mcp-Session-Id` и `Last-Event-ID` игнорируются.

*Методы.* `server/discover` — версии протокола, capabilities, идентичность и **версия сборки бинаря**. `tools/list` — тулы профиля этого пути. `tools/call` — исполнение.

*Отображение результатов.* Успех → `structuredContent` по схеме результата команды. Доменная ошибка → результат с `isError: true` и человекочитаемым текстом, **не** JSON-RPC error. Ошибка ввода (аргументы не прошли схему) и неизвестный тул → JSON-RPC error.

*Аннотации тулов.* `readOnlyHint: true` для профиля `ro`. Для команд с необратимым внешним эффектом — `_meta` с флагом обязательного подтверждения на каждый вызов.

*Инструкции сервера.* Каждый профиль объявляет текст инструкций, не длиннее **2048 байт** (клиент режет ровно на этом): он не перечисляет команды, а объясняет, для каких задач искать тулы этого сервера. Тот же предел — на описание одного тула. Проверка: длина обоих текстов измеряется тестом.

*Объём ответа.* Результат тула, чей размер не ограничен по построению (выборка строк, чтение диапазона, хвост лога), обязан иметь в схеме аргументов ограничитель со значением по умолчанию; в результате — признак усечения. Команда, у которой большой ответ осмыслен целиком, объявляет повышенный предел размера результата через `_meta`. Проверка: у каждого тула, помеченного как потенциально объёмный, ограничитель присутствует и имеет дефолт.

*Инварианты.*
1. Профили не пересекаются: множество имён тулов `/ro` и `/rw` не имеет общих элементов.
2. На `/ro` нет ни одного тула с политикой `rw`.
3. Имя тула однозначно восстанавливает путь команды и уникально в пределах профиля.
4. `tools/list` не содержит команд маршрута `legacy`.
5. Ни один ответ не содержит секретов: токен доступа не печатается и не возвращается.

*Конфигурация.* Токен доступа — файл 0600 в конфиг-каталоге, генерируется при первом запуске сервера. Подкоманда, печатающая заголовок авторизации для `headersHelper`, — часть контракта.

*Golden-примеры.* Минимум по одному на класс: успешный `tools/list`; успешный `tools/call`; `tools/call` с невалидными аргументами; `tools/call`, где команда упала доменной ошибкой; `400` при расхождении `Mcp-Name` с телом; `405` на GET.
