# Переработка спек `kiten`: ядро внешнего API и тонкие команды

Дата: 2026-08-06. Статус: принят пользователем в брейнсторме, спеки переписываются
по нему.

## Зачем

Десять черновиков спек `kiten-*.md` (1797 строк вместе с атомом) описывают
подкоманды, но нигде не описывают Kaiten API как целое: каждая командная спека
фиксирует «свой» кусок внешней границы. Отсюда два дефекта.

Первый: **ядра как отдельной сущности нет**, поэтому добавление `close`,
`status` или `checklist` неизбежно потребует править то, что уже реализовано под
`time` и `card`. Второй: **локальное состояние протекло в контракт** — из девяти
таблиц `kaiten_*` в SQLite три ведут журналы действий (подсказки таймера,
история значений полей, журнал перемещений), и командные спеки опираются на них
как на часть наблюдаемого поведения.

Решение: развести транспорт, каталог внешнего API и команды по трём ярусам;
ядром считать **полное** покрытие внешнего API, а не тот его срез, который нужен
командам первой волны.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Состав первой волны команд | `time`, `card`, `comment`, `field` — 483 из 619 вызовов (78 %) |
| Полнота ядра | Каталог покрывает все 29 вызовов внешнего API, а не срез под первую волну |
| Подсказки таймера (`kaiten_time_hints`) | Убрать целиком |
| Кэш справочников (6 таблиц) | Ядро о нём не знает; резолв имён — живым запросом. Кэш как ускоритель Tab — отдельная надстройка отдельной волной |
| История значений полей (`kaiten_card_links`) | Убрать; `field set` пишет переданное значение напрямую |
| Резолв роли по названию | Живой `GET /user-roles` при нечисловом значении; числовой id и дефолт — без запроса |
| Сводка `time ls` без селектора | Убрать из первой волны |
| `--dry-run` у мутаций `time` | Убрать |
| Проверка владельца записи + `--force` | Оставить — это сохранность данных, а не локальное состояние |
| Клиентский фильтр «только мои» в `time ls` | Оставить — иначе вывод замусорен записями всей компании |

## Три яруса

**Транспорт** — `platform/kaiten-http.md` (существует, реализован частично).
Базовый URL и токен, заголовки, единый формат ошибки не-2xx, ретрай только на
429, таймаут соединения, три режима пагинации, разбор селектора карточки. Ни
одного эндпоинта по имени не знает.

**Каталог API** — три новые спеки. Исчерпывающее описание внешней границы: путь,
query, тело, форма ответа, неочевидности. Ни рендера, ни SQLite, ни бизнес-логики.

**Команды** — резолв аргументов, вызов каталога, рендер. Составные сценарии
(`close`, `status`, `move` с релог-трюком, сводки) живут здесь же и ядру
неизвестны.

Проверяемый критерий расширяемости: **новая командная спека не порождает новой
платформенной**. Если для команды понадобился эндпоинт, которого нет в каталоге,
— каталог был неполон, и это дефект каталога, а не повод его «дорастить» под
команду.

## Ловушки внешней границы

Фиксируются в каталоге дословно — каждая из них уже стоила отладки и всплывёт
снова при первой же новой команде:

- глобального `GET /boards` не существует (405): доски приходят вложенными в
  `GET /spaces`, отдельного справочника досок нет;
- в фильтре карточек `lane_id` единственного числа; `lane_ids` сервер молча
  игнорирует;
- `GET /users/{id}/time-logs` требует `from`/`to`: без них отвечает 500, а не «за
  всё время»; пагинации у него нет, объём режется только шириной окна;
- `POST /user-timers` на занятой карточке отвечает телом `{"message": "User timer
  already created"}` **без** `id` и не обязательно HTTP-ошибкой — ветвление идёт
  по форме ответа, а не по статусу;
- файл привязывается к attachment-полю только через
  `PUT /cards/{id}/custom-properties/{prop}/files`; обычная загрузка файла к полю
  не цепляется;
- у таймера нет роли: `role_id` при старте API принимает, но не сохраняет — тип
  работы выбирается в момент остановки;
- комментарий таймера, наоборот, хранится на сервере и читается из
  `GET /cards/{id}` → `timer.comment`.

## Что уходит и с какими последствиями

**Подсказки таймера.** `time status` начинает требовать селектор. Кросс-карточный
guard (таймер идёт на другой карточке) снимается — ожидается, что о конфликте
сообщит сервер. Роль на `stop` берётся из `--role`/env вместо запомненной при
`start`; комментарий не теряется, он на сервере.

**История значений полей.** `field set` пишет переданное значение прямым PATCH.
`field ls`, `field update`, `field rm` исчезают вместе с журналом. Побочно
уходит ловушка: правка или удаление несвежей записи истории применяли к полю
карточки другое значение, а не то, которое трогали.

**Кэш справочников.** Резолв `--role`/`--column`/`--space` по названию перестаёт
зависеть от того, прогонялся ли `init`. Цена — сетевой запрос на резолв нечислового
значения и задержка Tab-дополнения до появления надстройки-ускорителя.

**Журнал перемещений (`kaiten_card_moves`) — решение отложено.** Его единственный
читатель — `mpu telegram status` (дневной отчёт), а не `kiten`. Убирая журнал, мы
меняем чужую команду. Живая замена существует —
`GET /cards?updated_after=…&updated_before=…` плюс `GET /cards/{id}/location-history`
— но она дороже и показывает перемещения кем угодно, а не только этим
инструментом. Решать вместе со спекой `move`, не в первой волне.

## Полнота ядра против YAGNI

Правила модуля (`ts/CLAUDE.md`) запрещают код «на будущее», и первая волна команд
зовёт 17 вызовов из 29. Остальные 12 будут реализованы без вызывающего кода — это
осознанное отступление, и в спеках каталога оно названо прямо: слой API — **порт к
внешней системе**, полнота порта является требованием, а не спекулятивной
гибкостью, иначе обещание «расширять, не залезая в ядро» не выполняется.

Отступление ограничено: полнота разрешена только каталогу. Ни рендер, ни команды,
ни надстройки права на код без вызывающего не получают. Непокрытость тестами
неиспользуемых эндпоинтов не допускается — каждый закрывается парой
«запрос → ответ» на синтетической фикстуре.

Двенадцать вызовов, у которых в первой волне вызывающего не будет: список
карточек, история перемещений, перемещение карточки, замена описания, три вызова
чек-листов, записи времени пользователя за окно, лента действий, пространства,
дорожки и колонки доски. Все они понадобятся волнам `ls`, `status`, `move`,
`close`, `checklist` и `refs`.

## Открытые вопросы

- **Поведение `POST /user-timers`, когда таймер идёт на другой карточке.** Из кода
  рабочей версии не следует: сообщение сервера может относиться только к текущей
  карточке. Закрывается живой пробой на тестовой карточке до перевода
  `kaiten-api-time.md` в «к реализации». Догадкой не закрывается.
- **Таймаут HTTP-соединения.** Унаследованный открытый вопрос
  `platform/kaiten-http.md`: оригинал не задаёт, зависшее соединение ждёт
  неограниченно. Закрывается числом в порции транспорта.

## Порядок порций

1. Транспорт (перенос из `init` + полный контракт запроса) **и** каталог
   времени, 9 вызовов — одной порцией.
2. Каталог: карточки и содержимое (14 вызовов) — с ним приходит multipart.
3. Каталог: справочники и пользователь (6 вызовов) — с ним приходят пагинация
   и живой резолв справочной ссылки.
4. Команда `time` (266 вызовов).
5. Команда `card` (77).
6. Команда `comment` (32).
7. Команда `field` (108).

Семь порций вместо привычной одной на команду. Транспорт не выделен в
отдельную порцию намеренно: методы запроса без единого вызывающего упёрлись бы
в запрет кода «на будущее», поэтому пломбирующие механизмы приходят вместе с
первым каталогом, который их зовёт, — multipart с карточками, пагинация со
справочниками. На каталоги как таковые это правило не распространяется: их
полнота оговорена выше отдельно.

## Критерии готовности волны

- Каталог сверен с инвентаризацией рабочей версии: 29 из 29, расхождений нет.
- Ни одна спека первой волны не упоминает SQLite, кэш справочников и локальные
  журналы.
- Спеки `time`, `card`, `comment`, `field` переведены в «реализовано».
- Ни одна из них не потребовала новой платформенной спеки.
