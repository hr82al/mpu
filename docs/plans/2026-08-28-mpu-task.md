# mpu task — план реализации

**Цель:** заменить файловый канал передачи работы командой `mpu task` поверх
кэш-БД: произвольное число проектов, четыре вида сообщений, журнал с чисткой,
самодостаточная инструкция для чистой машины.

**Устройство:** журнал сообщений — единственный источник правды; состояние
выводится из последнего сообщения проекта. Две таблицы в `mpu.db`
(`task_projects`, `task_messages`), чистка в одной транзакции с записью.

**Стек:** Deno/TS, тот же слой хранилища и контракта команд, что у остальных
команд `mpu`.

**Спека:** `ts/docs/specs/task.md` (заморожена 2026-08-28). Схема хранилища —
`ts/docs/specs/platform/store.md`.

**Адаптация шаблона:** код в задачах не приводится. Реализацию пишет
изолированная сессия по спеке; план задаёт границы порций, проверяемые
критерии и обязательные мутации — в той форме, в какой их читает исполнитель.

## Общие ограничения

- Имя проекта — первый позиционный аргумент, умолчаний нет.
- Состояние канала отдельно не хранится: выводится из журнала.
- Чистка — в одной транзакции с записью; текущая порция не удаляется никогда.
- `MPU_TASK_HISTORY` — единственная переменная окружения команды.
- Ни одна подкоманда не открывает сетевых соединений.
- Гейты порции: `deno fmt --check`, `deno lint`, `deno check .`,
  `deno task test`, `deno task smoke` — зелёные по строке с числом проблем.

## Порция 1. Схема хранилища

**Файлы:** `ts/src/store/schema.ts`; эталон
`ts/docs/specs/fixtures/platform/store/schema.sql`; копия в `testdata/`;
`ts/docs/specs/platform/store.md`.

**Даёт следующим порциям:** таблицы `task_projects(name, created_at, note)` и
`task_messages(id, project, portion, kind, body, created_at, read_at)` плюс
индекс по `(project, id)`.

- [ ] Тест: bootstrap на пустой базе создаёт обе таблицы и индекс; состав
      операторов совпадает с эталоном канала побайтно.
- [ ] Тест: bootstrap идемпотентен — второй прогон не меняет `sqlite_master`.
- [ ] Эталон схемы расширен; копия в `testdata/` синхронизирована.
- [ ] Замер (мой, спецификатора): рабочая Python-реализация продолжает
      работать на базе с новыми таблицами — проверяется командой, читающей
      кэш, а не рассуждением.
- [ ] Мутация: убрать индекс → контрактный тест краснеет.

## Порция 2. Слой журнала

**Файлы:** `ts/src/task/journal.ts` (доступ к таблицам), `ts/src/task/state.ts`
(вывод состояния из журнала), тесты рядом.

**Даёт следующим порциям:** запись сообщения, чтение последнего по проекту и по
виду, отметка прочитанным, номер текущей порции, чистка.

- [ ] Тест: `post` открывает порцию 1, следующий `post` — порцию 2.
- [ ] Тест: `report`/`ask`/`answer` прикрепляются к текущей порции.
- [ ] Тест: состояние «в канале постановка» выводится из последнего сообщения,
      а не из отдельного поля (проверяется через публичную функцию состояния).
- [ ] Тест: чистка оставляет три последние порции; текущая цела при `0`.
- [ ] Тест: чистка идёт в одной транзакции с записью — при ошибке записи
      журнал не меняется.
- [ ] Мутации: чистка вне транзакции; чистка удаляет текущую порцию; номер
      порции берётся `count(*)` вместо `max(portion)`.

## Порция 3. Команды записи

**Файлы:** `ts/src/task/cmd_post.ts`, `cmd_report.ts`, `cmd_ask.ts`,
`cmd_answer.ts`.

- [ ] Тест: `post` поверх непрочитанной постановки отвечает отказом и кодом 1;
      с `--force` заменяет её, не увеличивая номер порции.
- [ ] Тест: `report`/`ask`/`answer` в проекте без порций → код 2 с подсказкой
      про `post`.
- [ ] Тест: пустое тело (файл, stdin, `-m`) → код 2, запись не делается.
- [ ] Тест: тело возвращается побайтово равным поданному, включая хвостовые
      переводы строк.
- [ ] Тест: неизвестный проект → код 2 с подсказкой про `setup`.
- [ ] Мутации: `--force` увеличивает номер порции; пустое тело записывается;
      тело обрезается по краям.

## Порция 4. Команды чтения

**Файлы:** `ts/src/task/cmd_read.ts`, `cmd_status.ts`, `cmd_history.ts`.

- [ ] Тест: `read` печатает последнее сообщение и помечает прочитанным;
      `--keep-unread` не помечает.
- [ ] Тест: `read --kind` берёт последнее сообщение указанного вида.
- [ ] Тест: `read` в проекте без сообщений → пустой stdout, код 0.
- [ ] Тест: `status` без имени печатает строку на каждый проект; с именем —
      одну; признак непрочитанного соответствует журналу.
- [ ] Тест: `history -n` ограничивает вывод; `history clear` оставляет текущую
      порцию; без имени — по всем проектам.
- [ ] Мутации: `read` помечает прочитанным не то сообщение, что напечатал;
      `history clear` сносит текущую порцию.

## Порция 5. Ожидание

**Файлы:** `ts/src/task/cmd_wait.ts`.

- [ ] Тест: `wait` возвращается на непрочитанном сообщении нужного вида.
- [ ] Тест: `wait` не возвращается на **прочитанном** сообщении того же вида —
      ждёт следующего (проверяется на поддельных часах, без реального сна).
- [ ] Тест: истёкший предел → код 1 с текстом из спеки.

- [ ] Мутации: `wait` возвращается на прочитанном; предел игнорируется.

## Порция 6. Тексты: `setup` и `rules`

- [ ] `setup` печатает пять разделов в порядке спеки; с именем заводит проект,

- [ ] `rules` печатает десять правил и строку про порядок правки.
- [ ] Тест: оба текста сверяются с голденами побайтно.
- [ ] Тест: `rules` не читает и не пишет состояние (работает на пустой базе).
- [ ] Мутация: раздел `setup` переставлен местами → голден краснеет.

## Порция 7. Публикация и справка

**Файлы:** `ts/src/registry/mod.ts`, закрытый список тулов, снапшоты.

- [ ] Группа `task` зарегистрирована; `mpu task` без подкоманды печатает
      индекс, код 2.
- [ ] Публикация тулов: читающие (`status`, `history`, `read`, `rules`,
      `setup` без имени) — `ro`; пишущие (`post`, `report`, `ask`, `answer`,
      `setup` с именем, `history clear`) — `rw`. `wait` не публикуется:
      блокирующий вызов у тула не имеет смысла.
- [ ] Справка каждой подкоманды укладывается в предел описания тула.
- [ ] Мутация: пишущая подкоманда оказывается в `ro` → проверка краснеет.

## Порция 8. Проверка на чистой машине (моя, не исполнителя)

**Файлы:** рецепт `mpu/docs/task-vm/` (compose или скрипты подъёма, README).

- [ ] Гостевая система в qemu под KVM, образ Debian; **интернета нет**: весь
      выход только через прокси хоста, прописанный в системе и в apt.
- [ ] Проверка изоляции до теста: прямой запрос мимо прокси из гостя **падает**,
      через прокси — проходит. Без этого тест не начинается.
- [ ] В гостя доставляется **один файл** — собранный бинарь `mpu`.
- [ ] Полный цикл настоящими командами в двух терминалах: `setup` → `post` →
      `read` → `ask` → `answer` → `report` → `wait` → `history`.
- [ ] Четвёртая порция: первая исчезает по чистке; `MPU_TASK_HISTORY=all`
      её сохраняет.
- [ ] Критерий приёмки: после доставки одного бинаря цикл проходит **без
      единой ручной правки файлов**. Всё, что потребовало ручного шага, идёт
      в спеку строкой как ограничение.
- [ ] Виртуалка сносится; рецепт остаётся в репозитории.

## Порция 9. Живой прогон на паре сессий

- [ ] Игрушечный проект заводится через `mpu task setup`, одна маленькая
      порция проходит полный цикл с настоящей изолированной сессией.
- [ ] Файловый канал выводится из употребления: `ts/handoff/` удаляется,
      упоминания в инструкциях заменяются на `mpu task`.

## Порядок и зависимости

Порции 1 → 2 → 3 → 4 → 5 идут строго последовательно: каждая опирается на
предыдущую. Порция 6 не зависит от 3–5 и может идти раньше. Порции 7–9 — после
всех остальных; 9 закрывает переезд и удаляет старый канал.
