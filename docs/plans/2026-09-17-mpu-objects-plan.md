# mpu: объекты и живой бэкенд — план порций

> **Исполнение:** не субагентами основной сессии. Каждая порция — спека в
> `ts/docs/specs/` + постановка `~/tmp/prompt-<N>.txt`, которую оператор
> запускает в изолированной сессии (`mpu/CLAUDE.md`, «Роли сессий»). Код в
> плане не приводится: устройство проектирует исполнитель по чек-листам
> (`checklists/`), постановка его не выдаёт.

**Цель:** превратить один бинарь `mpu` в набор подпроектов вокруг живого
бэкенда с командами-сообщениями и политикой подтверждений, не ломая рабочий
`mpu` до переключения.

**Архитектура:** `ts/back` (Hono + JSON-RPC, объекты, политика, интеграции),
тонкие `ts/mcp`, `ts/cli`, `ts/complete`, `ts/supervisor`, фронт `ts/web`;
один юнит `mpu.service`.

**Стек:** Deno 2.9.x, TypeScript strict, Hono, zod, `node:sqlite`; фронт —
Vite, React 19, TanStack Router / Query / Table / Virtual, zustand, vitest.

**Спека:** `docs/2026-09-17-mpu-objects-design.md` (исполнителю не видна —
рабочие части переносятся в `ts/docs/specs/` порция за порцией).

## Общие ограничения

- Всё — в `mpu/ts/`; подпроекты — папки `ts/<имя>/` со своим `deno.jsonc`,
  объединённые workspace корневого `ts/deno.jsonc`.
- Сеть — только `127.0.0.1`. Порты целевые: `mcp` 7337, `back` 7338. До
  переключения (порция 8) новый `mcp` слушает **7339**, чтобы не мешать
  работающему `mpu-mcp.service` на 7337.
- Новый CLI до переключения ставится как `mpu-next`; `~/.local/bin/mpu` не
  трогается до порции 8.
- Зависимости, согласованные владельцем 2026-09-17: Hono (уже есть),
  `node:sqlite` (встроен), Vite, React 19, TanStack Router / Query / Table /
  Virtual, zustand, vitest. Каждая — строкой «зачем» в `deno.jsonc`. Прочие —
  только с разрешения.
- Go и C — не сейчас; после прототипа и замера (раздел 13 спеки).
- Каждая порция: сценарии «дано → ожидается», спека с разделом «Пункты
  чек-листа», рецензия исполнителя по `review.md` + `review-mpu.md`, отчёт с
  пунктами 4, 5, 8. Постановка несёт ядро и раздел о трате контекста полным
  текстом (`ts/docs/CLAUDE.md`, «Что несёт каждая постановка»).
- systemd, docker и живой MCP-клиент из изолированной сессии недостижимы:
  живые проверки этих порций делает спецификатор при приемке.
- Порядок — переукладка первой (memory: переукладку первым пунктом порции).
- **Рабочий `mpu` не ломается до порции 8.** Порции 2–7 добавляют новые
  модули и новые точки входа (`mpu-next`, `mcp` на 7339); прежние точка входа
  CLI, реестр и `mpu mcp` ведут себя как до порции 1 — их голдены и `smoke`
  зелёные в каждой порции, это пункт приёмки. Установленный
  `~/.local/bin/mpu` пересобирается из дерева в любой момент и должен остаться
  рабочим после любой принятой порции.
- Тесты и smoke не трогают настоящие systemd, `mpu-mcp.service`,
  `~/.local/bin` и порты 7337/7338: запуск процессов и юнитов подменяется,
  порты — выданные ОС (`port: 0`).

## Порция 2 (сквозной номер 137, принята 2026-09-17): разбор строки в цепочку сообщений

**Спека:** `ts/docs/specs/platform/messages.md` (раздел 2 спеки архитектуры).

**Сценарии (таблица ≥ 15 строк в спеке):**
- `kiten card: 123` → унарное `kiten`, ключевое `{card: "123"}`;
- `sql-ro --seller-id 54 query: "select 1"` → одно ключевое сообщение
  `{seller-id: "54", query: "select 1"}`;
- `seller-id: 5 seller-id: 6` → ошибка «ключ seller-id дважды», код 2;
- `kiten card: 123 comment: "x"`, где метод `card:` не принимает `comment:` →
  два сообщения; то же с `.` между ними → те же два сообщения;
- ключ, который принимают оба звена, без `.` → текущему сообщению;
- `note: -- "a:"` → значение `a:`;
- `card:` в конце строки → ошибка «у ключа card нет значения», код 2;
- пустая строка → сообщение `help` объекту `mpu`;
- `kiten card 123 comment "x"` → четыре унарных звена; что значат `123` и
  `"x"`, решают объекты порции 3, разбор слова не классифицирует;
- неизвестный ключ у последнего звена → `doesNotUnderstand` (порция 3).

**Свойства:** разбор детерминирован; схемы приёмников даются разбору извне
(тест подставляет свои).

## Порция 3a (138) и 3b (139), приняты 2026-09-17: объекты, рефлексия, справка; команды реестра как объекты и точка входа `mpu-next`

**Спека:** `ts/docs/specs/platform/objects.md` (разделы 3–4).

**Сценарии:**
- `mpu selectors` → список селекторов корня, отсортированный;
- `mpu kiten respondsTo: card:` → `true`; `respondsTo: nope:` → `false`;
- `mpu kitn` → `doesNotUnderstand`, в выводе «kiten» как ближайший, код 2;
- `mpu help kiten card` и `mpu kiten card: --help` → побайтово одинаковый текст;
- `mpu help kiten mr` → справка по двум узлам подряд;
- `mpu version name` → `doesNotUnderstand` с текстом «цепочка окончена»;
- `mpu kiten card 123` → объект карточек отвечает на `123` карточкой;
  `mpu kiten card abc` → `doesNotUnderstand` объекта карточек с его текстом;
- `mpu sql-ro 54 "select 1"` → результат запроса; путь для политики —
  `sql-ro <client> <query>`;
- все нынешние команды реестра доступны как сообщения через `mpu-next`:
  прежние строки вызова (`mpu kiten card 123`, `mpu sql-ro 54 "…"`) дают тот же
  результат, что голдены порции 1;
- замена модуля методов в работающем процессе: тест грузит версию A, вызывает,
  подменяет на B, вызывает → ответ B без перезапуска.


## Порция 4 (сквозной номер 140, принята 2026-09-18): политика

**Спека:** `ts/docs/specs/platform/policy.md` (раздел 5).

**Сценарии (таблица специфичности ≥ 12 строк):**
- `kiten card <card> comment → ask`; `mpu kiten card 123 comment "x"` → ask
  для любого номера;
- правила `* → allow`, `sql * → ask`; `mpu sql-ro …` → ask;
  `mpu kiten ls` → allow;
- `kiten * → ask`, `kiten ls → allow`; `mpu kiten ls` → allow;
  `mpu kiten card: 1` → ask;
- цепочка `kiten card: 1 comment: x` при `kiten card: → allow`,
  `kiten card: comment: → ask` → ask;
- любое звено `deny` → отказ, текст называет правило;
- пустая база → посев: нынешние ro → allow, rw → ask; повторный старт посев
  не повторяет;
- `mpu allow: "kiten *"` из tty после «да» → правило записано; следующий
  вызов видит его без перезапуска;
- то же через канал MCP → отказ «политику меняет только человек», база не
  изменилась;
- `mpu policy` → список правил, отсортированный по шаблону;
- база повреждена → старт `back` с ошибкой, называющей файл; молчаливого
  «всё разрешено» нет.

**Инвариант:** решение принимается в одной точке для любого канала.

## Мини-Smalltalk: адрес строки, грамматика, результат-объект (порции 17–23)

Решения владельца 2026-09-22. Порядок жёсткий: 18a меняет грамматику, 18b
переводит команды, 18c строит отражение и дополнение на ключах; 19–23 — после.

### Порция 17 (сквозной номер 157, принята 2026-09-22): дверь `ask`

**Спека:** `ts/docs/specs/platform/ask-door.md`. Строка с решением `ask`
вызывается только `mpu ask …`, `allow` — только без него, `deny` не
исполняется ни одним адресом и в списках не виден. Состав двери живой, из
действующих решений (web меняет его со следующей строки). `ask` — сообщение
корню с результатом «объект».

### Порция 18a (158, принята 2026-09-23): грамматика, справка-объект, результат-объект

Перевод на ключи в 18a — только на командах-образцах (`kiten card`,
`sql-ro`, `logs` — значение, формат, поток); остальные команды — 18b.

- Позиционных аргументов нет: значение — только ключом (`id: 123` ≡
  `--id 123`); ключевое сообщение составное (`--x a --y b` = `x:y:`). Голое
  слово — всегда унарное сообщение. Отменяет [D.5] архитектуры в части
  «произвольное слово как значение».
- Приоритет как в Smalltalk: унарное выше ключевого. Группа — слова `do` …
  `end` (решение владельца 2026-09-22; скобки без кавычек не проходят в
  bash/fish/nu, `do`/`end` проходят во всех трёх — замер; занятых имён в
  дереве нет). Разделитель — только слово целиком; литерал `do` / `end` —
  через `--`. `do` и `end` — зарезервированные слова: имя команды, группы или
  формата ими быть не может (тест). `.` уходит из грамматики.
- **Непарный `end` закрывает группу от начала строки** (начало строки —
  неявный `do`): `mpu kiten card id: 123 end md`. `do` нужен только внутри
  строки. Решено слепым замером: с обязательным `do` агент (`sonnet`) трижды
  из трёх писал `… end md` без `do`.
- Одно слово — одно значение, пробелы внутри можно (`sql: "select 1"`);
  кавычки литерала не делают, `--` нужен только для слов грамматики.
- Вариант после ключа — отказ с готовой строкой (варианты — до ключей);
  порядок не ослабляется.
- Словарь ключей, один на все команды: `target` (где), `id` (номер
  сущности), `text`, `query` (что искать), `since`/`until`, `limit`.
  Ключ вне словаря — только с записанной причиной (тест).
- `help` — последним словом объекту; `--help` — единственная флаговая форма
  унарного сообщения (≡ `help`). `--json` и прочие флаги формата — отказ с
  готовой строкой `… end json`.
- Справка команды: однострока → абзац «когда звать» → **два-три примера** →
  состав (ключи из словаря, варианты, форматы результата).
- Описание тула `mpu` — текст v3 из `docs/probes/2026-09-22-grammar/
  tool-desc-v3.txt` (1962 байта; слова группы подставляются из константы).
  Замер 2026-09-22 на `sonnet`: без описания — старые привычки (позиционные,
  `--json`); v1 (строгий `do`) — 5/10; v2 — 10/11; v3 — 12/12 с первой
  попытки. Приёмка 158 — тот же набор задач на собранном описании.
- Слова группы и знак литерала (`do`, `end`, `--`) — **один источник**: одна
  константа в модуле грамматики (владелец: «гибко, чтобы легко менялось»).
  Разбор, тест зарезервированных имён, справка корня, описание тула `mpu`,
  подсказки отказов и голдены справки берут слова из неё, а не пишут
  литералом. Приёмка — мутация: замена `do`/`end` на другую пару в
  константе даёт зелёные тесты разбора и новые слова в справке и описании
  тула без других правок кода (голдены пересобираются задачей).
- Результат команды — объект; форматы — его унарные сообщения, каждый вид
  результата отвечает на свои (`json`, `md`, `tsv`, `table`, `raw`, `csv`
  по тому, что команда умеет сегодня). Без сообщения — текстовый вид, как
  сейчас. `mpu kiten card id: 123 end md`.
- Флаги `--json`, `--md`, `--tsv`, `--table`, `--raw`, `--out` уходят
  (`telegram send --md` — не формат вывода, остаётся).
- Цель — аргумент ключевого сообщения, не объект и не унарное слово
  (владелец: значения заранее неизвестны). Один ключ `target:` ≡
  `--target`; значение — что угодно из прежнего селектора: номер клиента,
  имя или его часть, `sl-1`, `dev:54`; что это, система решает прежней
  логикой (`ts/docs/specs/platform/selector.md`), неоднозначность — прежний
  отказ со списком кандидатов. Имя выбрано под агента: «где исполнить»,
  без обещания, что там клиент (`by:` читается как способ, `on:` не
  подсказывает содержимое, `client:` неверно для `sl-1`). Описание тула и
  справка команды называют допустимые формы значения одной строкой.
  Примеры: `mpu sql-ro target: ромашка sql: "select 1"`,
  `mpu sql-ro --target 54 --sql "select 1" end json`.
- Код выхода отдаёт сам результат-объект, а не команда отдельно от него:
  у факта один источник (анти-пример `d2-miro`: код 0 при
  `shapes=0 skipped=10`).
- Справка — обычное сообщение `help` объекту (`mpu kiten card help`), режим
  разбора `--help` уходит. **Результат `help` — такой же объект-данные**, как
  результат команды: текстовый вид по умолчанию, `kiten comment help end
  json` — ключи, типы, обязательность, варианты, форматы структурой. Из той
  же структуры собираются описание тула MCP и тест словаря ключей: у факта
  один источник, текст справки обратно не разбирается.
- **Контракт потока.** Результат — вид с двумя реализациями: значение и
  поток; формат печатает запись (у потока `json` — строка на запись, `csv`
  — шапка один раз). Иначе первый `logs follow … end json` потребует
  переделать протокол результата у всех команд. Живой поток в 18a — у
  `logs`.
- Отказы подсказывают верную форму готовой строкой (голое значение →
  «значение — ключом …», `--json` → «… end json»).
**Приёмка 158 — сверка входов парой** (хост, до принятия): `sql`, `sql-ro`,
`kiten card` до и после порции, каждый прежний вход → новый. Отдельно живьём:
`--server sl-N` при клиентском селекторе против `target: sl-N` — снятие
`--server` обосновано справкой («резолв отменяет»), не прогоном.

### Порция 18b (159): перевод команд на словарь ключей

Все команды (~150; ~80 порождены эндпоинтами `api` по правилу «`:param`
пути → позиционный») — на ключи словаря; флаги формата сняты; хвост `ssh` —
значение `cmd:`. Перед спекой — инвентарь позиционных заново по коду
(черновик 2026-09-22 — в сессии хоста, не в канале).

**Функциональность не теряется** (риск уже срабатывал: первый вариант цели
разложил селектор на четыре точных ключа и потерял нечёткий поиск):

1. **Таблица соответствия на каждую команду** — каждый нынешний вход
   (позиционный, флаг, stdin, умолчание, формат, код выхода) → новый адрес или
   названная причина снятия. «Потеряно» без причины — дефект.
2. **Тест полноты, как `dropped.ts`:** каждый вход старой схемы есть в новой
   либо стоит в списке снятых с причиной.
3. **Проверка парой:** старая и новая строка на одном состоянии, сравнение
   stdout, stderr и кода (`ts/CLAUDE.md`, «Проверка — всегда парой»).
4. **Список «снято и заменено» — владельцу на вычитку до постановки.**

Известные места риска, каждое — строкой таблицы: сужение неоднозначного
селектора (`--client-id`, `--sid` у `make-schema`, `api wb-cards-reset`,
`api wb-loader-*`, обёрток nodecli) — ключом словаря, не потерей; короткие
флаги (`-v`, `-n`, `-t`); подстановки stdin (`sql`, `run-js`, `--from -`,
литерал `-`) — до перевода на `stdin`-выражение (порция 19) работают как
сейчас; чужой хвост `ssh`; режимы по умолчанию (`kiten card`: терминал —
наглядный, пайп — markdown).

### Порция 18c (160): протокол отражения и дополнение сообщениями

Общий протокол корневого объекта, который понимает **любой** объект (в коде —
композиция, не `extends`): `messages` (все сообщения), `understands: <сообщение>`,
`keys` (ключи ключевого сообщения: имя, вид, обязательность), `formats`
(форматы результата — у команды без исполнения и у результата), `variants`
(варианты до ключей; пусто до порции 22), `help`. Объект команды понимает
`candidates: <ключ> like: <начало>` (значения ключа, у `target:` — из
кэша клиентов/серверов). Корень понимает `complete: <набранная строка>` —
кандидаты следующего слова (сообщения, ключи с учётом уже набранных,
значения, форматы после `end`); на нём работает дополнение оболочки. `back`
недоступен — дополнение берёт снимок `tree.json` (≤ 150 мс, как сейчас),
снимок — вывод тех же сообщений, второго источника нет. `selectors` и
`respondsTo:` переименовываются в `messages` и `understands:` (один способ).
Имена — слепой замер двух агентов `sonnet` (ru/en), 5 из 9 совпали дословно:
`docs/probes/2026-09-22-grammar/reflect-answers.md`.

### Порция 19 (161): аргумент ключевого сообщения — выражение; `stdin`

`mpu kiten comment card: do kiten ls end first id text: готово`: на месте
значения может стоять группа, её результат — значение.

`stdin` — первичное выражение на месте значения (`ask sql target: sl-1 sql:
stdin`): одно правило вместо шести неявных подстановок (`sql`, `run-js`,
`--from -`, `--body-file -`, литерал `-`). Тем же правилом «что стоит на
месте значения» — поэтому здесь, а не отдельной порцией.

### Порция 20 (162): протокол коллекции у результата-данных

`size`, `first`, `last`, `pick: <поле>`, `where: <поле> is: <значение>` —
один раз у вида «данные», команды ничего не пишут. Цель — агент получает
только нужное, а не весь JSON.

### Порция 21 (163): `it` — последний результат

`back` держит результат последней строки вызывающего; `mpu it md`
перерисовывает его без повторного запроса.

### Порция 22 (164): флаги поведения — унарные варианты команды

`--dry-run`/`--print`, `--local`, `--all`, `--via <вид>`, `--out <вид>` и
подобные становятся унарными сообщениями объекту команды **до** ключевого:
вариант команды — отдельная реализация, ключевое исполняет его.
`mpu process dry target: 54`, `mpu copy-client local target: ромашка`,
`mpu kiten spaces all`, `mpu logs portainer target: sl-1 since: 1h`.
Порядок строки: слова до первого ключа — что делать; ключи — над чем;
после `end` — как показать. Перед спекой — инвентарь флагов поведения по
коду (как позиционных для 158).

### Порция 23 (165): отказ — объект

`doesNotUnderstand`, адресный отказ двери `ask`, «не хватает ключа»,
неоднозначная цель — объект с `reason`, `hint` (исправленная строка
целиком) и `candidates`. MCP кладёт его в `structuredContent`, агент берёт
`hint`, а не разбирает текст; печать CLI прежняя.
