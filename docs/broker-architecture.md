# Архитектура: Go-брокер + Deno/TS CLI

Статус: принятые решения 2026-07-29; открытые вопросы — внизу.

Поворот относительно `go-migration.md` (там CLI предполагался на Go) и
`go/CLAUDE.md` «Замысел: брокер и CLI» (там транспорт — unix-сокет).
Разделы этих документов, противоречащие настоящему, — на пересмотре; до
пересмотра источник истины по архитектуре — этот файл.

## Решения

- **Брокер — Go, удалённый сервис.** Доверенная сторона: секреты, доступ
  к PG и HTTP внешних систем, валидация каждого запроса как враждебного.
  Живёт на сервере, обслуживает несколько машин/пользователей.
- **CLI — Deno/TS.** Недоверенная сторона: парсинг аргументов, справка,
  рендер вывода. Данные не добывает — запрашивает у брокера. Песочница —
  штатными опциями Deno (permissions); зафиксировано как направление,
  на этом этапе НЕ планируется и не проектируется.
- **Транспорт — HTTPS, протокол — JSON-RPC 2.0.** Именованные операции с
  фиксированными параметрами (узкий словарь, как и раньше), не «прокинь
  произвольный запрос наружу».
- **Auth — временный JWT.** CLI получает токен операцией login по
  логину/паролю; дальше — Bearer JWT с ограниченным сроком жизни.
  Учётки — в `.env` брокера.
- **Python-делегация — в брокере.** На время переезда брокер исполняет
  ещё не переехавшие операции вызовом установленного Python-mpu; CLI не
  знает, какая реализация ответила. (В старом плане делегацию держал
  CLI-диспетчер — роль переезжает на сторону брокера.)

## Последствия для плана переезда

- Спеки `go/docs/specs/platform/registry.md` и `platform/dispatcher.md`
  возвращены в «черновик»: реестр/справка/маршрутизация — теперь
  поверхность Deno-CLI и/или брокера, дробление пересматривается.
  Снятые golden-фикстуры (2026-07-29) остаются эталоном наблюдаемой
  CLI-поверхности независимо от языка реализации.
- Спеки команд (`go/docs/specs/<command>.md`) описывают наблюдаемую
  CLI-поверхность — их контракт сохраняется; меняется адресат
  реализации (Deno-сессии), и добавляется второй контракт — операция
  брокера. Механика каналов спек (что остаётся в `go/docs`, что
  появляется для Deno) — открытый вопрос.
- Платформенные атомы делятся заново: selector, config (секреты),
  readonly-default, HTTP-клиенты внешних систем — сторона брокера;
  invoke-log — решить (журнал у CLI, у брокера или у обоих).

## Точка входа `mpu`: решено — прямой Deno (2026-07-29)

`mpu` и есть Deno-CLI: `deno compile` → один самодостаточный бинарь в
`~/.local/bin/mpu`, permissions зашиваются при сборке. Go-лончер
отклонён: его исторической ролью был strangler-диспетчер («команда →
Go | Python»), а с переносом делегации в брокер осталась только роль
лончера, обе выгоды которой (единый файл без установленного deno,
зашитая политика песочницы) штатно даёт `deno compile`. Возврат к
Go-обёртке — только если появится требование, которое `deno compile`
не закрывает (например, самообновление CLI-скриптов без раздачи
бинаря).

## Открытые вопросы

- Где живёт Deno-CLI в репо (`ts/`?) и как устроена изоляция сессий и
  канал спек для него (аналог `go/docs/`).
- `go/CLAUDE.md` «Замысел: брокер и CLI» (unix-сокет → HTTPS JSON-RPC):
  противоречит решениям, а правится только из изолированной Go-сессии.
- invoke-log: чей журнал (CLI, брокер, оба) и что с командой `mpu log`.
- Формат хранения учёток в `.env` (открытый текст или хэш), TTL и
  обновление JWT — при проектировании брокера.
