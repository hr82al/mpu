# mpu: объекты, сообщения и живой бэкенд — дизайн

Статус: согласовано с владельцем 2026-09-17. Заменяет `broker-architecture.md`
(Go-брокер) и `cli-extensibility-draft.md`: всё пишется на TS/Deno.

## Цель

Нынешний `mpu` — один Deno-бинарь, в котором CLI, реестр команд и MCP-сервер
(`mpu mcp`, юнит `mpu-mcp.service`, профили `/ro` и `/rw`) собраны вместе.
Любая пересборка перезапускает всё, включая MCP. Новый вид:

- живой локальный бэкенд, к которому обращаются CLI, MCP, веб-интерфейс и
  дополнение оболочки;
- команды — сообщения объектам в духе Smalltalk, с поздним связыванием;
- политика «выполнять без подтверждения / спрашивать / запрещать» хранится
  в SQLite, правится с фронта и из CLI без перезапуска;
- каждая часть — самодостаточный подпроект; запуск — один юнит systemd.

## 1. Подпроекты и процессы

Все подпроекты — отдельные папки в `mpu/`, каждая со своими `deno.jsonc`,
тестами и гейтами. Общий у них только контракт RPC, экспортируемый из `back/`.

| Папка | Бинарь | Роль |
|---|---|---|
| `supervisor/` | `mpu-supervisor` | единственное, что запускает systemd; порождает `back` и `mcp`, перезапускает упавший дочерний процесс по одному; кода — минимум |
| `back/` | `mpu-back` | Hono + JSON-RPC 2.0; объекты, разбор сообщений, политика, все интеграции (PG, Kaiten, GitLab, Sheets…); отдаёт статику `web` |
| `mcp/` | `mpu-mcp` | тонкий переводчик MCP ↔ JSON-RPC `back`; своих знаний о командах не имеет |
| `cli/` | `mpu` | тонкий клиент: отдаёт `back` сырые слова строки, рендерит ответ, подтверждение в tty |
| `complete/` | `mpu-complete` | дополнение в bash / fish / nu |
| `web/` | статика | Vite + React 19 |

Юнит один: `mpu.service` (`ExecStart=mpu-supervisor`). Перезапуск `back`
через супервизор не трогает `mcp`: `mcp` переживает рестарт `back`,
повторяя вызов до таймаута.

Сеть: всё слушает только `127.0.0.1`. Доступ — токен, как сейчас (`mpu mcp
token`). Фронт открывается по `http://mpu.localhost:<порт>`; браузеры
резолвят `*.localhost` в петлю сами. Порт 80 (через прокси) — не в этой
поставке. `Origin` для фронта принимается только `http://mpu.localhost:<порт>`.

## 2. Грамматика сообщений

Строка: `mpu <сообщение> <сообщение> …`. Приёмник первого сообщения — объект
`mpu`, приёмник каждого следующего — результат предыдущего.

- **Унарное сообщение** — одно слово: `kiten`, `ls`, `selectors`.
- **Ключевое сообщение** — набор пар «ключ — значение» в двух равноправных
  написаниях: `seller-id: 5` и `--seller-id 5`. Их можно смешивать.
  Порядок ключей не важен: селектор — множество ключей; обязательность и
  типы задаёт схема метода.
- **Бинарных сообщений и каскада `;` нет.**
- Позиционных аргументов нет: `mpu kiten card: 123`, а не `mpu kiten card 123`.
- Значение, которое само оканчивается двоеточием или начинается с `--`,
  экранируется предшествующим словом `--`.

Граница между сообщениями определяется схемой приёмника: ключи, которые
принимает метод текущего объекта, относятся к текущему сообщению; первый
непринятый ключ или унарный селектор адресуется результату. Если ключ
принимают оба, без явной границы он достаётся текущему сообщению. Явная
граница — отдельное слово `.`:

```
mpu kiten card: 123 comment: "текст"
mpu kiten card: 123 . comment: "текст"
```

Разбор выполняет только `back`: при позднем связывании схемы известны
только ему. `cli`, `mcp` и `complete` передают сырые слова.

Объекты-результаты живут в пределах одной строки; между вызовами они не
сохраняются.

Примеры:

```
mpu help kiten card
mpu kiten card: 123 --help
mpu sql-ro seller-id: 54 query: "select 1"
mpu sql-ro --seller-id 54 --query "select 1"
```

## 3. Объекты и позднее связывание

- Объект — таблица методов; `back` ищет метод в момент вызова.
- Метод объявляет схему ключей (как нынешний контракт команды), признак
  «возвращает объект» и тело.
- Нет метода — `doesNotUnderstand`: ответ с ближайшими селекторами, не падение.
- Модуль с методами перезагружается динамическим импортом с новым URL —
  метод меняется в живом `back` без рестарта. Deno не выгружает старую
  версию модуля; рост памяти для локального сервиса допустим. Если станет
  заметен — модуль в своём Worker, Worker пересоздаётся.
- Рефлексия — тоже сообщения: `selectors`, `respondsTo: <селектор>`,
  `help`. Дерево на фронте и дополнение строятся из них; отдельного API для
  браузера объектов нет.
- `complete: <ключ>` — необязательный метод объекта для умных значений
  (клиенты для `seller-id:`, свои карточки для `card:`). Результат
  кэшируется в `back` с коротким временем жизни.

## 4. Справка

`mpu help <путь…>` и `mpu <путь…> --help` выдают одно и то же: описание
узла, схему ключей, примеры (содержание нынешнего `--help`). Несколько путей
— справка по каждому. В MCP это тул `help` с путём в аргументе.

## 5. Политика

Решение на сообщение: `allow` (выполнить без подтверждения), `ask`
(спросить), `deny` (отказать).

- Правила задаются шаблонами пути селекторов: `*`, `kiten *`,
  `sql *`, `kiten card: comment:`.
- Выигрывает самое конкретное правило: точный путь сильнее шаблона,
  длинный префикс сильнее короткого.
- Для цепочки проверяется каждое звено, побеждает самое строгое
  (`deny` > `ask` > `allow`). В подтверждении показывается вся цепочка со
  значениями.
- Правила меняются сообщениями объекту `mpu`: `mpu allow: <шаблон>`,
  `mpu ask: <шаблон>`, `mpu deny: <шаблон>`, `mpu policy` (список).
- **Жёсткий запрет вне политики:** сообщения, меняющие политику, всегда
  требуют подтверждения человека и через MCP не исполняются вовсе — только
  из tty `cli` или с фронта. Иначе агент выдаёт права себе сам.
- Хранение: SQLite (`node:sqlite`), `~/.local/state/mpu/policy.db`.
  `back` держит политику в памяти и единственный пишет в базу; запись и
  обновление кэша — одна операция, действует со следующего вызова.
- Начальное наполнение: нынешние ro-команды — `allow`, rw — `ask`.
- Условия на значения (`sql * seller-id: dev:*`) — возможное расширение, не
  в этой поставке.

Проверку политики делает `back` в одной точке перед диспетчеризацией —
одинаково для `cli`, `mcp` и `web`.

## 6. Подтверждение

- `cli`: вопрос в tty. Нет tty — отказ.
- `mcp`: запрос yes/no клиенту (elicitation). Нет ответа или «нет» —
  отказ. Какой механизм реально поддерживает Claude Code (elicitation или
  MCP Apps) — проверяется живым прогоном **до** реализации шага 2.
- `web`: модальное окно.

## 7. MCP

Два тула вместо профилей `/ro` и `/rw`:

- `help(path?)` — дерево подкоманд, описание узла, схема ключей;
- `mpu(words)` — сообщение в виде слов строки.

Схемы `mcp` берёт у `back` на каждый вызов `help` — новый метод виден агенту
без перезапуска `mcp`.

## 8. CLI

- Отдаёт `back` слова, cwd, нужные переменные окружения, признак tty.
- Если `back` не отвечает: пишет `mpu.service`, делает
  `systemctl --user enable --now mpu`, ждёт готовности. Отключается
  переменной `MPU_NO_AUTOSTART=1` (CI, песочница, изолированные сессии).
- Стримы (логи) и интерактив — WebSocket от `back`.

## 9. Дополнение оболочки

`mpu-complete` — отдельный бинарь со своими правилами:

- никаких побочных эффектов: не поднимает юнит, не спрашивает, не пишет в
  журнал вызовов;
- бюджет ~150 мс; не успел `back` — ответ из снимка
  `~/.cache/mpu/tree.json`, который `back` перезаписывает при каждом
  изменении дерева;
- вход — слова строки и позиция курсора; выход — строки
  `значение\tописание`;
- `mpu-complete init bash|fish|nu` печатает скрипт подключения:
  - bash: `complete -C mpu-complete mpu`; `:` входит в `COMP_WORDBREAKS` —
    скрипт склеивает `seller-id:` обратно;
  - fish: `complete -c mpu -f -a '(mpu-complete --fish (commandline -cp))'`;
  - nu: внешний completer, записи `{value, description}`.

## 10. Фронт

Vite, React 19, TanStack Router, TanStack Query, TanStack Table + Virtual,
vitest — та же семья, что во фронте `ozon`, без Next.

- Серверное состояние — только TanStack Query.
- Клиентское общее состояние — zustand, заводится при первой реальной нужде;
  локальное — `useState`; фильтры, которыми делятся ссылкой, — search params
  роутера.
- Первый экран: дерево объектов и селекторов (из рефлексии) с выбором
  `allow` / `ask` / `deny` на узле, частичным состоянием у родителя и
  сбросом к наследуемому значению. Изменение применяется сразу.
- Сборка — `deno run -A npm:vite build`; Node на хосте не нужен.

## 11. Установка: `mpu/install.sh`

Чистый shell; нужны только `deno` и `systemctl`. Запущенный `mpu` не нужен.

1. Собирает подпроекты (`deno compile`; `web` — Vite). `--only back,web` —
   выборочно.
2. Ставит бинари в `~/.local/bin` атомарно: временный файл рядом + `mv`.
   Статику `web` — в новый каталог и переключает симлинком.
3. Нет `mpu.service` или он отличается от эталона в репо — пишет,
   `daemon-reload`, `enable --now`.
4. Изменился `supervisor` — `systemctl --user restart mpu`; изменились
   только дочерние — просит супервизор перезапустить именно их.
5. Проверяет: health каждого процесса с таймаутом; `mpu help` отвечает;
   MCP отдаёт тулы `help` и `mpu`; `mpu.localhost:<порт>` отдаёт страницу.
   Провал — ненулевой код и имя шага.
6. После успешной проверки выключает старый `mpu-mcp.service`.
7. Повторный запуск без изменений ничего не перезапускает.

## 12. Порядок переезда

Каждый шаг — отдельная порция; старый `mpu mcp` работает, пока новый не
прошёл живую проверку.

1. `back`: RPC, объекты, разбор сообщений, политика в SQLite; перенос
   команд из `ts/src`.
   Проверка: `mpu help`, цепочка `kiten card: … comment:`, `doesNotUnderstand`,
   смена политики действует со следующего вызова.
2. `mcp` (после живой пробы подтверждения).
   Проверка: в Claude Code видны тулы `help` и `mpu`; `ask` спрашивает;
   сообщение `allow:` через MCP отклонено; рестарт `back` при живом `mcp`.
3. `cli`.
   Проверка: оба синтаксиса ключей дают одно сообщение; автоподъём юнита и
   его отключение `MPU_NO_AUTOSTART`.
4. `supervisor` + `install.sh`.
   Проверка: перезапуск одного дочернего не трогает другой; идемпотентность.
5. `complete`.
   Проверка: bash / fish / nu; ответ из снимка при остановленном `back`.
6. `web`.
   Проверка: смена галочки без перезапуска видна в следующем вызове CLI.

## Будущее, без решений
