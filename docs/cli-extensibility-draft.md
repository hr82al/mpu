# CLI extensibility — черновик (`help/` + `commands/` + транспорт)

Статус: **черновик, не согласован**. Не связан с `go-migration.md`, `go/CLAUDE.md`,
`go/docs/plan.md` — ничего из них не меняет, пока явно не решено внедрять.

## Брокер

- Go, обычный host-процесс, **без изоляции** — доверенная сторона, нечего от
  себя защищать.
- Один листенер: HTTP на `127.0.0.1` + токен. Один протокол для скомпилированных
  примитивов (`sql-ro`, `kiten`, …) и для `commands/` — не два транспорта.
- Токен — файл `~/.config/mpu/broker.token` (0600), генерирует и хранит брокер.
  Передаётся заголовком `Authorization`, не через argv/env (видно в
  `ps`/`/proc/*/environ`).
- Каждый запрос валидируется как враждебный независимо от источника.
- Новая именованная операция в протоколе — только через штатный gate-процесс
  Go (`go-migration.md` §3). `commands/` комбинирует уже одобренный словарь,
  сам новых возможностей не заводит.

## `help/`

- `go/help/<зеркало дерева команд>.txt`, читается с диска на каждый вызов
  (не `go:embed` — снова требует пересборки).
- Первая строка файла = блёрб для индекса родителя.
- Нет файла у зарегистрированной команды → ошибка при старте, не пустой вывод.
- Синопсис флагов — авто-генерируется из регистрации в Go-коде (единственная
  compiler-гарантированная защита от дрейфа); файл несёт только прозу
  (описание, примеры, грабли).

## `commands/`

- `go/commands/<name>.ts` — TypeScript, исполняется **Deno**:
  `deno run --allow-net=127.0.0.1:<port> --allow-read=<нужные пути> script.ts -- <args>`.
  Права запрашиваются явно и точечно на каждый вызов, по умолчанию — ничего
  не разрешено (сеть/файлы/env/subprocess).
- Barrier — на уровне рантайма Deno, не ОС: работает одинаково на
  Linux/macOS/Windows. На Linux дополнительно оборачивается в
  `bwrap --ro-bind <те же пути>` как второй слой defense-in-depth (без
  сетевого namespace — сеть уже ограничена самим Deno, поднимать `lo` вручную
  не нужно). На других ОС — только Deno-флаги, тот же барьер без bwrap.
  Список путей для `--allow-read` и `--ro-bind` общий — резолвится один раз.
- Версия Deno фиксируется рядом (`go/commands/.deno-version`), диспетчер
  сверяет при запуске — защита от тихого дрейфа поведения без Docker
  (тот же принцип, что даёт `uv.lock` питоновской части).
- Токен брокера — файлом (тот же файл, что у примитивов), путь входит в
  `--allow-read`; не через argv/env.
- Первая строка скрипта = блёрб для индекса (та же конвенция, что в `help/` —
  отдельного help-файла не нужно, скрипт самодокументируется).
- Остальные языки (например, bash для тривиальных цепочек в 2-3 вызова)
  остаются доступны через шебанг, но получают защиту только от bwrap
  (Linux-only), без рантайм-permission-модели Deno.

## Governance над `commands/`

- Обычные git-коммиты в `main`, без формального gate — та же дисциплина, что
  у skills сегодня.
- Проверка при старте (то же сканирование, что ищет блёрб): импорты в `*.ts`
  — только относительные пути и стандартная библиотека Deno, никаких
  `npm:`-спецификаторов и remote-URL импортов сторонних пакетов. Иначе «без
  внешних зависимостей» — устная договорённость, а не свойство дерева.

## Открытое

1. Резолв пути `go/help/` и `go/commands/` относительно установленного
   бинаря `~/.local/bin/mpu` — фиксированный путь к чекауту репозитория,
   переменная окружения, или через `os.Executable()`?
2. Конкурентность/rate-limit в брокере для параллельных вызовов из
   Workflow-агентов — не проектировать заранее (YAGNI), пока не станет
   наблюдаемой проблемой.
3. Кроссплатформенность — архитектурное свойство (Deno-permissions не
   привязаны к ОС), не активная цель сейчас: текущее окружение — Linux,
   macOS/Windows не тестируются и не проектируются целенаправленно, пока не
   появится реальная потребность.
