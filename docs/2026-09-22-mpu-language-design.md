# mpu: язык целиком — блоки, условия, циклы, образ, исполнители строк

Дизайн 2026-09-22, решения владельца по итогам обсуждения и слепых замеров на
агенте `sonnet` (`docs/probes/2026-09-22-grammar/`,
`docs/probes/2026-09-22-blocks/`). Исполнителю не виден: рабочие части
переносятся в `ts/docs/specs/` порция за порцией.

Опирается на серию 158–165 (`docs/plans/2026-09-17-mpu-objects-plan.md`,
«Мини-Smalltalk»): грамматика-выражение, `do … end`, ключи, результат-объект,
отражение и дополнение сообщениями. Эта серия начинается после установки
158–165 и имеет свою установку в конце.

## Цель

Строка `mpu` — программа на маленьком Smalltalk, где всё — объект и
сообщение: блоки-замыкания, переменные, условия и циклы — сообщения
объектам, пользовательские методы хранятся в образе и неотличимы от команд.
Для человека и агента одинаково, в CLI, MCP и web. Критерий: слепой замер
`sonnet` на описании тула — 9 из 10 задач с первой попытки.

## Ограничение оболочек

Всё, что пишется в строке, проходит параметрами bash, fish и nu без кавычек и
одинаково читается из файла программы, делённого по пробелам. Запрещены
`( ) [ ] { } < > | ; $ & ' " # * ?` и одиночное `~`; символьных бинарных
операторов нет — только слова. Проверено прогоном всех конструкций ниже в трёх
оболочках. Кавычки оболочки остаются нужны только тексту со скобками и
подобным внутри значения (SQL) — это свойство оболочки, в файле их нет.

## 1. Синтаксис

| Что | Запись | Замер |
|---|---|---|
| унарное / ключевое | `kiten ls`, `kiten card id: 123` ≡ `--id 123` | 158 |
| выражения в строке | через `.` | ru-генерация |
| переменная | в начале выражения — голое имя (`c title print`), в значении ключа — `@c` (`id: @c id`); голое связанное имя в значении — отказ «`@c` или `-- c`»; имя, совпадающее с сообщением корня, не связывается | v7: без `@` в начале агент пишет вопреки примеру |
| присвоить | `x := <выражение>` | обе генерации |
| блок / группа | блок `do :a :b … done` (как в bash); группа `do … end`; внутри блока `end` закрывает выражение от начала блока | К1 7/9 против К2 2/9; v5 (группа в блоке явная) 3/6, v6 (`done`) — интуиция агента верна |
| поле записи | унарное: `@c title`; `@c.title` — отказ с подсказкой | замер строк |
| текст из нескольких слов | `^готово к ревью, проверь тесты^` — `^` приклеен к краям | В1 7/7 |
| комментарий | `rem … end` | обе генерации |
| литерал служебного слова | `--` перед словом (`text: -- end`) | 158 |
| сравнение и арифметика | `greater:`, `less:`, `equals:`, `plus:`, `minus:`, `times:`, `div:` | en-генерация |
| обход и отбор | `each:`; `where: <поле> is:|less:|greater:|includes: <значение>` | `each:`/`do:` 6/6 и 6/6; `where:less:` агент пишет сам |

Правила разбора сверх 158:

- Значение ключа — первичное (литерал, `@x`, текст `^…^`, блок). Унарное после
  `@x` — ей; **после литерала — результату всего ключевого сообщения**
  (`sql: ^…^ first n`, `id: 123 md`): литерал-аргумент сообщений не ждёт
  (v8 6/10 → v9 9/10). Ключевой вызов внутри значения — только в `do … end`.
- Слово после `done` блока-аргумента — сообщение результату **всего**
  ключевого сообщения (`kiten ls collect: do :c c id done print`); блоку
  отдельно шлют `@b value`.
- `done` в значении вне открытого блока — литерал (`inColumn: done`).
- **Ключи подряд — одно ключевое сообщение**; следующее — результату после
  `end` (так пишет описание: `kiten ls where: column is: review end each: do :c
  … done`). Получатель, понявший склеенное сообщение частично (`greater: 1000
  ifTrue: …`), делит его сам: понятая часть — ему, остаток — результату, если
  объявленный вид результата остаток понимает (проверка до исполнения), иначе
  отказ с готовой строкой. Замеры: A/B — строгое с `end` лучше дележа по
  описанию (3/6 против 6/6 на цепочках); v6–v9 — на коротких цепочках агент
  `end` опускает, терпимость получателя закрывает это без второго смысла.
- Описание тула несёт два примера, на которых спотыкались агенты: `ask` —
  первым словом строки, даже если запись внутри блока; два выражения — через
  `.`.
- `define:` берёт имя метода следующим словом как есть (`cardsIn` и `cardsIn:`
  равны): ключ объявлен видом «имя».
- Слова `do`, `end`, `rem`, `--`, знак текста `^`, знак переменной `@`, знак
  параметра `:` — одна константа модуля разбора (как `do`/`end` в 158).

## 2. Модель вычисления

- Строку (или программу) разбирает и вычисляет исполнитель строки (раздел 5);
  значение последнего выражения печатается, формат — после `end`.
- Все значения — объекты одного протокола «получить сообщение»: команды и
  группы реестра, результаты, записи, коллекции, блоки, числа, тексты,
  `true`/`false`, `nil` (один null-объект), методы образа. Вычислитель не
  отличает команду от метода.
- Блок — замыкание: параметры, тело, захваченные переменные; `value`,
  `value:`, `value:value:`. Получатель, которому нужно значение, сам шлёт
  блоку `value` — поэтому `do … end` и группа, и блок.
- Базовые объекты: булевы — две реализации (`ifTrue:`, `ifFalse:`,
  `ifTrue:ifFalse:`, `and:`, `or:`, `not`); число (`plus:` … `div:`,
  `greater:`, `less:`, `equals:`, `timesRepeat:`, `to:do:`); текст
  (`equals:`, `includes:`, `size`); коллекция (`each:`, `collect:`,
  `select:`, `reject:`, `detect:`, `inject:into:`, `size`, `first`, `last`,
  `isEmpty`, `where:is:`, `pick:`); запись — поля унарными, прочее `pick:`.
- **Пределов нет.** Вместо счётчиков — устройство: вычислитель уступает
  управление после каждой отправки сообщения (отмена доходит, соседние строки
  не стоят) и держит свой стек вызовов в куче, не на стеке JS (рекурсия
  ограничена только памятью, исполнитель не падает от глубины). Стоп-кран —
  отмена (Ctrl+C, отмена MCP); память — раздел 5.

## 3. `ask` в составной строке

- Правила разрешений Claude Code видят только начало строки, поэтому `ask`
  ставится **один раз, в начале** строки или программы, если она может дойти
  хоть до одной команды с решением `ask` — в том числе внутри блока или метода
  образа. Внутри блока `ask` не пишется.
- Вопрос человеку — на **каждую** запись в момент, когда вычисление до неё
  дошло, с текстом конкретной строки: цикл по пяти карточкам — пять вопросов.
  Начальный `ask` не разрешает, а объявляет.
- До исполнения исполнитель обходит строку и тела вызываемых методов образа и
  собирает достижимые команды: есть `ask`-команда, а `ask` в начале нет —
  адресный отказ с готовой строкой. Получатель, которого обход знать не может (`@x foo`),
  решается в момент отправки: без начального `ask` — отказ, а до него
  исполнилось только `allow`, то есть чтение.
- Однокомандные строки ведут себя как в 157 (лишний `ask` — «вопроса не
  требует»). Лишний `ask` на составной строке
  без записей — не отказ (решение владельца: агент ставит его из
  осторожности, замер 2026-09-22), исполнение обычное.

## 4. Образ

- **Хранение:** `image.db` (SQLite) рядом с `policy.db`. Метод — получатель,
  имя, исходник (текст определения в формате раздела 1), назначение, описания
  ключей, автор (канал: человек, агент, web), время, хэш нормализованного
  исходника. `define:` и `forget:` пишутся сразу, без буфера.
- **Не в RAM:** метод ищется запросом к SQLite; перед поиском — `PRAGMA
  data_version` (правка из другого процесса видна следующей строке сразу).
- **Определение:** `ask kiten define: cardsIn purpose: ^мои карточки в
  колонке^ do :column … done`. Имя без хвостового `:` или с ним; частей имени
  через `:` (`cardsIn:since`) — столько, сколько параметров у блока; без
  параметров — унарный метод. `purpose:` обязателен (справка — часть
  контракта), `keys:` — описания ключей. Встроенные команды не
  переопределяются. Определение и удаление — строки под правилами (посев
  `ask`).
- **Удаление:** `ask kiten forget: cardsIn`.
- **Решение правил метода** — посев обходом тела (раздел 3): только
  `allow`-команды — `allow`, иначе `ask`; дальше как у любого узла.
- **Программа из файла и stdin** — раздел 6.

### `mpu image sync` — двусторонний, по принципу unison

Файлы — `mpu/image/<получатель>/<имя>.mpu`, один метод на файл, текст
определения. Хэш в файл не пишется. Архив прошлой синхронизации (хэш метода
на обеих сторонах в прошлый раз) — таблица в той же `image.db`. Решение по
методу — база Б, файлы Ф, архив А:

| Б | Ф | Итог |
|---|---|---|
| = Ф | = Б | согласие, архив обновлён |
| ≠ А | = А | файл из базы |
| = А | ≠ А | база из файла |
| ≠ А | ≠ А, ≠ Б | конфликт: обе стороны не тронуты, `prefer: db` / `prefer: files` на метод |
| нет | = А | удалён в базе → файл удаляется |
| = А | нет | удалён в файлах → метод удаляется |
| нет или ≠ А | ≠ А или нет | удалён на одной, изменён на другой — конфликт |
| есть | нет, в А нет | новый в базе → файл |
| нет, в А нет | есть | новый в файлах → метод |

- **Пустая база:** архив живёт в той же `image.db`, новая пустая база — с
  пустым архивом, удаление без архива не выводится: первая синхронизация —
  только объединение. То же спасает от пустого каталога файлов.
- **Массовое удаление:** если синхронизация удалила бы больше половины
  методов стороны или все — отказ с числом; разрешает только `deletes: allow`
  на этот запуск.
- **Кто:** `mpu ask image sync` — пишущая строка. Раз в сутки таймер службы
  запускает синхронизацию без человека: направление «файлы → база» он не
  применяет, только отчитывается (правка файла не обходит подтверждение).
  Коммит в git — человек или агент по просьбе.

## 5. Исполнитель строк и защита от нехватки памяти

- `mpu-back` — лёгкое ядро: HTTP, правила, образ, каналы подтверждения,
  сессии. Строку (и программу) исполняет отдельный процесс-исполнитель из
  тёплого пула: в нём код команд и вычислитель; за решением правил, вопросом
  человеку и образом он ходит к `back`. После строки исполнитель завершается
  (память гарантированно возвращается), пул доливает новый.
- Исполнители запускаются с `oom_score_adj=1000` (повышать пользователю можно
  без привилегий): ядро при нехватке убивает исполнителя, не `back` и не
  супервизор.
- **Сторож в супервизоре** (как `earlyoom`): следит за `MemAvailable` и за
  памятью исполнителей (`/proc/<pid>/status`); ниже порога свободной памяти
  убивает **самого большого** исполнителя; вызывающий получает «строка
  остановлена: машине не хватает памяти, строка заняла N МиБ», код 1. Своих
  пределов у строки нет.
- **Пояс:** `MemoryMax` на службу оставляет машине запас; внутри группы
  службы ядро по `oom_score_adj` выбирает исполнителя.
- Сам супервизор ничего тяжёлого не держит.

## 6. Программа из stdin и из файла

- `mpu` без слов: stdin не терминал — программа из stdin целиком (предела
  длины командной строки нет); терминал — справка корня.
- `mpu run: <путь> [<ключ>: <значение> …]` — программа из файла (имя `run:` —
  первое у обоих агентов замера); параметры внутри — `@ключ`; использованный,
  но не переданный — отказ с именем, лишний — не ошибка.
- Разбор текста — только по пробелам и переводам строк, как параметры
  оболочки; своих кавычек нет. Строка из терминала работает в файле и
  наоборот; исходники методов образа — тот же формат.
- `ask` — один раз в начале программы (`mpu ask run: x.mpu`, `mpu ask <
  x.mpu`). MCP: `{"words": ["run:", "<путь>"]}`.

## 7. Отражение и web

- Методы образа отвечают на протокол корня (`messages`, `understands:`,
  `keys`, `formats`, `variants`, `help`) так же, как команды; `purpose:` и
  параметры дают справку и ключи.
- Дерево web — вывод отражения от корня `mpu`: метод образа — узел под
  получателем с меткой «образ», автором, временем, исходником и правилом (как у
  команды). Протокол корня показан один раз, на корне. Правка исходника и
  удаление — строки `define:`/`forget:` через окно подтверждения; страница
  `image sync` — последний прогон, конфликты («взять базу» / «взять файлы»),
  «синхронизировать».
- `complete:`: после `@` — переменные, видимые в этой точке (присвоенные выше
  и параметры охватывающих блоков); методы образа — наравне с командами.
  Снимок `tree.json` включает методы образа.

## 8. Ошибки и проверка

- `doesNotUnderstand` у любого объекта — с «ближайшими» и готовой строкой;
  блок не с тем числом значений — отказ «блок ждёт N значений, дано M»; место
  ошибки в тексте (`выражение 2, блок each: (строка 1): @c не понимает titel;
  ближайшие: title`). Коды: 2 — разбор, адрес, отказ до исполнения; 1 — ошибка
  вычисления, отказ правил, остановка сторожем; 130 — отмена.
- Частичное исполнение не откатывается; журнал пишет строку и каждую
  дошедшую команду реестра отдельно.
- Проверка: эталон разбора (слова грамматики метками), табличные тесты
  вычислителя, таблица трёх сторон синхронизации на временных каталоге и базе,
  настоящее исчерпание памяти исполнителя в тесте сторожа.
- Обязательные мутации: цикл без вопроса на каждую запись; запись без
  начального `ask`; вычислитель не уступает (вторая строка не отвечает);
  рекурсия на стеке JS (исполнитель падает на глубине 100 000); нет сверки
  `data_version`; очищенный архив удаляет; снят предохранитель массового
  удаления; конфликт перезаписывает сторону; `define:` без `purpose:`;
  исполнитель без `oom_score_adj`; сторож убивает не самого большого.
